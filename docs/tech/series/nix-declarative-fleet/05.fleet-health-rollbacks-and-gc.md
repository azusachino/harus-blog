## Before you start

Nix never overwrites files, so every rebuild leaves the old version in `/nix/store`. That is what makes rollback possible, and it is also why the store keeps growing. A year of updates on a laptop can fill tens of gigabytes. Deleting directories from the store by hand is dangerous, because a program you still use may need one of them.

The chapter treats this as the same problem a language runtime has with memory: work out what is still reachable, and free the rest. Roots such as your current system generation and your development shells mark what is alive, and `nix-collect-garbage` removes everything unreachable. It also covers saving disk space with hard links and saving build time with binary caches, which download a pre-built result instead of compiling it.

Read [chapter 1](/tech/series/nix-declarative-fleet/01.nix-functional-model-and-flakes/) first for the store, and [chapter 2](/tech/series/nix-declarative-fleet/02.multi-platform-fleet-and-home-manager/) for generations.

Terms used in this chapter:

- **garbage collection (GC)**: deleting store paths that nothing live refers to.
- **GC root**: a link that tells the collector a path is in use, such as a generation or a result symlink.
- **generation**: a saved version of a system or profile that you can roll back to; it keeps its packages alive.
- **rollback**: switching back to an earlier generation.
- **mark and sweep**: a GC method that marks everything reachable from the roots, then deletes the unmarked.
- **hard link**: a second directory entry pointing at the same file data on disk.
- **binary cache**: a server holding pre-built store paths that machines can download instead of building.
- **substituter**: Nix's name for a source, such as a binary cache, that can supply a store path.

## Fleet Health, Rollbacks & Garbage Collection

Because Nix enforces pure immutability—never overwriting or mutating existing files in `/nix/store/`—every package update, configuration rebuild, and development shell iteration creates new store paths. Without deliberate lifecycle management, disk utilization on developer workstations and homelab servers expands monotonically.

However, deleting files from `/nix/store/` with standard `rm -rf` breaks system integrity: an active program might depend on a shared library whose path was manually removed, producing `file not found` runtime crashes.

This chapter details the garbage collection and storage optimization mechanics that keep a multi-machine fleet lean and fast: how **GC Roots** preserve live system closures, how **Mark-and-Sweep GC** safely reclaims dead objects, how **Hardlink Deduplication** trims duplicate files, and how **Binary Caches** accelerate fleet-wide builds.

### 1. Garbage Collection Roots & The Liveness Graph

In traditional operating systems, package managers lack a holistic concept of object reachability. Nix borrows directly from managed language runtimes (like the JVM or Go): **storage management is a graph reachability problem**.

```text
[ Root Pointers: /nix/var/nix/gcroots/ ]
  |
  +---> System Profile Generation 42  (/nix/var/nix/profiles/system-42-link)
  |        |
  |        v
  |     [ /nix/store/abc...-system-closure ]
  |        ├── /nix/store/xyz...-linux-kernel-6.6
  |        └── /nix/store/def...-systemd-255
  |
  +---> User Home-Manager Gen 12      (/nix/var/nix/profiles/per-user/haru/home-manager-12-link)
  |        |
  |        v
  |     [ /nix/store/uvw...-home-manager-files ]
  |        └── /nix/store/123...-neovim-0.10.0
  |
  +---> Project `result` Symlink      (~/projects/my-app/result)

[ Dangling Store Paths (Unreachable) ]
  └── /nix/store/999...-old-unused-glibc-2.37  <-- Eligible for GC!
```

#### What Constitutes a GC Root?

A store path is considered "live" if it is reachable via a directed reference chain from any file located under `/nix/var/nix/gcroots/`:

1. **System & User Profiles**: Pointers to current and historical system generations (`/nix/var/nix/profiles/`).
2. **Auto GC Roots**: Created automatically when you run `nix-build` (creating a `./result` symlink in your working directory) or run `nix develop --profile <path>` (which keeps a development shell's tools from being collected).
3. **Running Processes**: At collection time Nix also scans `/proc` (memory maps, open files, environments) and treats store paths used by running programs as live.

### 2. Mark-and-Sweep Garbage Collection

When you invoke `nix-collect-garbage`:

1. **Mark Phase**: The daemon scans all root pointers in `/nix/var/nix/gcroots/`. It reads each path's derivation references (`.drv` closure and runtime binary string references) and marks all reachable store paths as **Alive**.
2. **Sweep Phase**: The daemon iterates across every directory in `/nix/store/`. Any store path *not* present in the live set is unlinked and deleted from disk.

#### Managing Generational History

By default, running `nix-collect-garbage` only deletes unreferenced artifacts—it preserves **all prior generations** of your system and Home Manager configurations, allowing you to roll back at any time.

When disk space must be reclaimed:

```bash
# Delete profile generations older than 14 days (the invoking user's profiles; run as root for system profiles), then collect
nix-collect-garbage --delete-older-than 14d

# Or delete all prior historical generations immediately, keeping only current
nix-collect-garbage -d
```

### 3. Storage Optimization via Hardlink Deduplication

Even after aggressive garbage collection, a multi-machine fleet running diverse tools often accumulates duplicate files:

- Two different compiler toolchain builds might bundle identical header files, documentation, or static runtime libraries.
- Multiple versions of Python or Node.js packages might share identical asset files.

Nix solves this without filesystem-level ZFS/Btrfs deduplication through **POSIX Hardlink Deduplication**:

```bash
# Optimize store manually
nix-store --optimise

# Or enable continuous auto-optimization in flake / configuration
nix.settings.auto-optimise-store = true;
```

#### How Hardlink Deduplication Works

```text
Before Optimisation:
/nix/store/aaa...-ripgrep-14.0/share/man/rg.1  (Inode 5001, 12 KB, Links: 1)
/nix/store/bbb...-ripgrep-14.1/share/man/rg.1  (Inode 6002, 12 KB, Links: 1)
Total disk usage: 24 KB

After Optimisation (nix-store --optimise):
/nix/store/aaa...-ripgrep-14.0/share/man/rg.1  (Inode 5001, 12 KB, Links: 2)
/nix/store/bbb...-ripgrep-14.1/share/man/rg.1  (Inode 5001, 12 KB, Links: 2)
Total disk usage: 12 KB (Inode unified! 50% storage reclaimed)
```

1. The daemon computes the SHA-256 hash of every regular file in `/nix/store/`.
2. It checks its internal table: if an identical hash exists, it replaces the duplicate file with a hard link (`link(2)`) pointing to the existing inode.
3. Because `/nix/store/` files are strictly read-only (`0444` or `0555`), shared hard links can never be accidentally modified by one package to corrupt another.
4. The savings depend on the store: many near-identical package versions dedupe well, a lean store barely changes. Run `nix-store --optimise` once and compare `du` before and after.

### 4. Binary Caches: Eliminating Redundant Compilation

In a distributed fleet, you should never compile the same package twice. If your desktop builds a custom package or toolchain, all other fleet machines (servers, laptops, SBCs) should download the pre-compiled binary artifact.

#### The Binary Cache Architecture

A Nix binary cache (such as `cache.nixos.org` or a self-hosted Attic/Cachix instance) is an HTTP object store serving two artifact types:

1. **`.nar` (Nix ARchive)**: A deterministic archive format that records file contents, the executable bit and symlinks, with no timestamps or ownership. Delivered as compressed `.nar.xz` or `.nar.zst`.
2. **`.narinfo` (Manifest & Cryptographic Signature)**:

   ```text
   StorePath: /nix/store/s66mzxpvicwk0735ipq8j17sf2jh52zh-ripgrep-14.1.0
   URL: nar/1a2b3c...nar.zst
   Compression: zstd
   NarHash: sha256:0123...
   NarSize: 1845120
   References: glibc-2.38 gcc-13.2
   Sig: cache.fleet.internal:ABCD1234... (Ed25519 signature)
   ```

Before downloading an artifact, the client verifies the `.narinfo` cryptographic signature against the fleet's public signing key (`substituters` & `trusted-public-keys`), so a substituted binary is rejected unless it carries a signature from a trusted key.

### 5. Verification Lab: Implementing GC Graph & Deduplication Engine

The following Python script simulates:

1. **GC Roots Reachability Engine**: Traces live reference graphs from active system generations and reclaims unreachable dangling store paths.
2. **Hardlink Inode Deduplication Engine**: Detects identical regular files across distinct store paths, unifies them into simulated shared inodes, and computes reclaimed bytes.

```python
#!/usr/bin/env python3
"""
Lab: Nix Mark-and-Sweep Garbage Collector & Hardlink Store Optimizer
Verifies GC root reachability, safe dead-path sweeping, and hardlink deduplication.
"""

from dataclasses import dataclass, field
from typing import Dict, List, Set, Optional, Tuple
import hashlib

@dataclass
class StoreObject:
    store_path: str
    files: Dict[str, str]  # rel_path -> content
    references: List[str] = field(default_factory=list)  # Referenced store paths

@dataclass
class SimulatedInode:
    inode_id: int
    content_hash: str
    size_bytes: int
    link_count: int = 1

class NixStoreManager:
    """Simulates /nix/store lifecycle, GC root tracing, and inode deduplication."""
    def __init__(self):
        self.store: Dict[str, StoreObject] = {}
        self.gc_roots: Dict[str, str] = {}  # root_name -> live store_path
        self.inode_table: Dict[int, SimulatedInode] = {}
        self.next_inode_id = 1000

    def add_object(self, obj: StoreObject):
        self.store[obj.store_path] = obj

    def add_gc_root(self, root_name: str, target_path: str):
        assert target_path in self.store, f"Target {target_path} not in store!"
        self.gc_roots[root_name] = target_path

    def remove_gc_root(self, root_name: str):
        self.gc_roots.pop(root_name, None)

    def collect_garbage(self) -> Tuple[int, List[str]]:
        """Mark-and-sweep GC starting from active GC roots."""
        # Phase 1: Mark
        reachable: Set[str] = set()

        def mark(path: str):
            if path in reachable or path not in self.store:
                return
            reachable.add(path)
            for ref in self.store[path].references:
                mark(ref)

        for root_target in self.gc_roots.values():
            mark(root_target)

        # Phase 2: Sweep
        dead_paths = [p for p in self.store.keys() if p not in reachable]
        for dp in dead_paths:
            del self.store[dp]

        return len(dead_paths), dead_paths

    def optimize_store(self) -> Tuple[int, int]:
        """
        Simulates hardlink deduplication (nix-store --optimise).
        Returns (deduplicated_file_count, bytes_saved).
        """
        content_to_inode: Dict[str, int] = {}
        bytes_saved = 0
        dedup_count = 0

        for obj in self.store.values():
            for fpath, content in obj.files.items():
                chash = hashlib.sha256(content.encode("utf-8")).hexdigest()
                size = len(content.encode("utf-8"))

                if chash in content_to_inode:
                    # Inode already exists: increment link count and record savings
                    existing_inode_id = content_to_inode[chash]
                    self.inode_table[existing_inode_id].link_count += 1
                    bytes_saved += size
                    dedup_count += 1
                else:
                    # New unique file: allocate new inode
                    new_inode_id = self.next_inode_id
                    self.next_inode_id += 1
                    self.inode_table[new_inode_id] = SimulatedInode(
                        inode_id=new_inode_id,
                        content_hash=chash,
                        size_bytes=size,
                        link_count=1
                    )
                    content_to_inode[chash] = new_inode_id

        return dedup_count, bytes_saved

def test_gc_and_store_optimization():
    manager = NixStoreManager()

    # 1. Populate store with active and dangling objects
    kernel = StoreObject(
        store_path="/nix/store/111-linux-kernel-6.6",
        files={"vmlinuz": "KERNEL_BINARY_BYTES_12345"}
    )
    glibc = StoreObject(
        store_path="/nix/store/222-glibc-2.38",
        files={"lib/libc.so": "LIBC_ELF_SHARED_BYTES_COMMON"}
    )
    system_gen1 = StoreObject(
        store_path="/nix/store/333-system-profile-gen1",
        files={"init": "init_script"},
        references=[kernel.store_path, glibc.store_path]
    )
    # Dangling old package not referenced by any profile
    orphan_pkg = StoreObject(
        store_path="/nix/store/999-old-abandoned-tool",
        files={"bin/tool": "ORPHAN_BYTES"}
    )

    manager.add_object(kernel)
    manager.add_object(glibc)
    manager.add_object(system_gen1)
    manager.add_object(orphan_pkg)

    # 2. Add GC Root for Generation 1
    manager.add_gc_root("profiles/system-1-link", system_gen1.store_path)

    print("=== 1. Mark-and-Sweep Garbage Collection ===")
    reclaimed_count, deleted = manager.collect_garbage()
    print(f"  Reclaimed {reclaimed_count} dead paths: {deleted}")
    assert reclaimed_count == 1
    assert orphan_pkg.store_path in deleted
    # Active system paths must survive!
    assert system_gen1.store_path in manager.store
    assert kernel.store_path in manager.store
    assert glibc.store_path in manager.store

    # 3. Simulate Hardlink Deduplication (nix-store --optimise)
    print("\n=== 2. POSIX Hardlink Inode Deduplication ===")
    # Add two different package versions containing identical documentation files
    app_v1 = StoreObject(
        store_path="/nix/store/444-my-app-1.0",
        files={
            "bin/app": "BINARY_V1",
            "share/doc/manual.txt": "COMMON_MANUAL_TEXT_IDENTICAL_ACROSS_VERSIONS" * 10
        }
    )
    app_v2 = StoreObject(
        store_path="/nix/store/555-my-app-2.0",
        files={
            "bin/app": "BINARY_V2",
            "share/doc/manual.txt": "COMMON_MANUAL_TEXT_IDENTICAL_ACROSS_VERSIONS" * 10
        }
    )
    manager.add_object(app_v1)
    manager.add_object(app_v2)

    dedup_files, saved_bytes = manager.optimize_store()
    print(f"  Deduplicated files: {dedup_files} | Storage reclaimed: {saved_bytes} bytes")
    assert dedup_files >= 1, "Identical manual.txt must be unified into single inode!"
    assert saved_bytes > 0

    print("\nAll Nix GC roots, sweeping, and hardlink deduplication tests PASSED!")

if __name__ == "__main__":
    test_gc_and_store_optimization()
```

### 6. Summary & Key Takeaways

1. **Graph-Theoretic Safety**: Nix avoids `file not found` library breaks by guaranteeing that no path reachable from active `/nix/var/nix/gcroots/` pointers is ever deleted.
2. **Safe Sweeping**: `nix-collect-garbage` cleans disk space safely without rebooting, while retaining rollback capability unless explicit age limits (`--delete-older-than`) are provided.
3. **Hardlink Deduplication**: `nix-store --optimise` unifies identical files across multiple package closures into shared filesystem inodes, reducing the storage footprint by an amount that depends on how much the closures overlap.
4. **Signed Substitution**: Binary caches eliminate redundant CPU compilation across the fleet by serving pre-built `.nar` packages verified by Ed25519 signatures.
