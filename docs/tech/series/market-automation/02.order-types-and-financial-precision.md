## Order Types, Execution Lifecycles & Financial Precision

In standard web applications, rounding `19.99 * 0.08` to two decimal places with IEEE-754 floating-point arithmetic is usually tolerated. In high-frequency trading and market automation, **floating-point inaccuracy is fatal**.

A calculation like `0.1 + 0.2` in standard IEEE-754 double precision (`f64`) produces `0.30000000000000004`. If your trading algorithm submits a limit order with that quantity or price, the exchange's matching engine will immediately reject the order with a filter validation error (`Filter failure: LOT_SIZE` or `PRICE_FILTER`). Over thousands of executions, rounding drift accumulates into irreconcilable account balances and unhedged inventory risk.

This chapter breaks down the mechanics of financial precision in electronic trading: how to represent currency without floating-point errors, how exchanges enforce tick and lot size quantizations, and how advanced order types like **Post-Only**, **IOC**, and **FOK** control execution cost and liquidity.

---

### 1. The Floating-Point Trap in Financial Systems

Computers represent numbers in base-2 (binary). Fractions that have clean base-10 representations (like $0.1 = 1/10$) become repeating infinite binary fractions:

$$
0.1_{10} = 0.0001100110011..._2
$$

When stored in a 64-bit float, the trailing bits are truncated:

```text
>>> 0.1 + 0.2 == 0.3
False
>>> 0.1 + 0.2
0.30000000000000004
```

#### The Architectural Solutions

1. **Integer Scaling (Atomic Units)**: Store all values as integer multiples of the smallest possible sub-unit:
   - Bitcoin: Satoshis ($1 \text{ BTC} = 10^8 \text{ satoshis}$).
   - USD / EUR: Cents ($1 \text{ USD} = 100 \text{ cents}$) or Basis Points ($1 \text{ bp} = 0.0001$).
2. **Fixed-Point Decimal**: Store a 96-bit or 128-bit integer paired with a fixed scale factor (as in Rust's `rust_decimal::Decimal` or Python's `decimal.Decimal`):

```rust
use rust_decimal_macros::dec;

let price = dec!(95000.50);
let qty = dec!(0.001);
let notional = price * qty; // Exactly 95.00050, zero floating-point drift!
```

### 2. Exchange Filter Rules: Ticks, Lots & Min Notional

Every regulated or crypto exchange rejects arbitrary precision. Before an order touches the matching engine, it must pass strict mathematical filters defined per trading pair.

#### Real-World Sample: Binance `exchangeInfo` Filters

Querying `GET /api/v3/exchangeInfo?symbol=BTCUSDT`:

```json
{
  "symbol": "BTCUSDT",
  "filters": [
    {
      "filterType": "PRICE_FILTER",
      "minPrice": "0.01",
      "maxPrice": "1000000.00",
      "tickSize": "0.01"
    },
    {
      "filterType": "LOT_SIZE",
      "minQty": "0.00001",
      "maxQty": "9000.00000",
      "stepSize": "0.00001"
    },
    {
      "filterType": "NOTIONAL",
      "minNotional": "5.00000000"
    }
  ]
}
```

1. **`PRICE_FILTER` (`tickSize`)**:
   Price must be an exact integer multiple of `tickSize`:
   $$(P - \text{minPrice}) \pmod{\text{tickSize}} = 0$$
   If `tickSize = 0.01`, submitting `$95000.505` fails immediately.
2. **`LOT_SIZE` (`stepSize`)**:
   Quantity must be an exact integer multiple of `stepSize`:
   $$(Q - \text{minQty}) \pmod{\text{stepSize}} = 0$$
   If `stepSize = 0.001`, submitting `0.0015` fails immediately.
3. **`MIN_NOTIONAL`**:
   The total gross order value must exceed a threshold (e.g. $\$5.00$):
   $$\text{Price} \times \text{Quantity} \ge \text{minNotional}$$
   This protects the exchange matching engine from spam orders.

### 3. Order Types & Time-in-Force (TIF) Semantics

Different trading strategies require different trade-offs between **price guarantee** and **execution certainty**:

```text
                       [ Order Submission Intent ]
                                    |
          +-------------------------+-------------------------+
          |                                                   |
    Guarantee Execution                              Guarantee Price
    (Suffer Slippage)                                (Risk Non-Execution)
          |                                                   |
          v                                                   v
   [ Market Order ]                                   [ Limit Order ]
          |                                                   |
          |                                +------------------+------------------+
          |                                |                                     |
          v                                v                                     v
  Takes liquidity                Passively quotes                    Aggressively crosses
  Pays taker fee                 Earns maker rebate                  Takes liquidity
```

#### 1. Market Order

- Executes immediately at the best available prices on the opposite side of the book.
- **Advantage**: Execution certainty ($100\%$ fill if depth exists).
- **Risk**: Price uncertainty (slippage). A large market order will sweep through multiple price levels.

#### 2. Standard Limit Order (GTC - Good 'Til Canceled)

- Specifies a maximum buy price or minimum sell price.
- If the price is uncrossed, it rests passively in the order book until filled or canceled.

#### 3. Post-Only (Maker-Only)

- **Critical for market-making algorithms**.
- Guarantees the order will **only rest as a passive maker**.
- If market conditions shifted while your order was in transit and your order would execute immediately as a taker, the exchange **automatically cancels the order with zero fee**.
- This protects market makers from accidentally paying expensive taker fees.

#### 4. Immediate-or-Cancel (IOC)

- Must execute immediately against resting orders upon arrival.
- Any portion of the order that cannot be filled immediately is **canceled**, rather than resting in the book.

#### 5. Fill-or-Kill (FOK)

- The entire quantity must execute immediately in its entirety.
- If the full quantity cannot be filled immediately, the **entire order is canceled with zero fills**.

---

### 4. Maker vs. Taker Fee Economics

Exchanges structure fees to incentivize liquidity:

- **Taker (Liquidity Remover)**: Removes resting orders from the book. Pays higher fees (e.g. $0.040\%$ to $0.050\%$).
- **Maker (Liquidity Provider)**: Places resting limit orders that others can trade against. Pays lower fees ($0.010\%$), zero fees, or even receives a **negative rebate** (e.g. $-0.005\%$).

```text
Example: $100,000 Trade on Binance / OKX VIP Tier
  Taker Fee (0.040%):   Trader pays $40.00
  Maker Rebate (-0.005%): Exchange PAYS the maker $5.00!
```

### 5. Verification Lab: Financial Precision & Filter Quantizer

The following Python script implements a production-grade order validator:

- Uses `Decimal` to ensure exact fixed-point arithmetic.
- Implements Binance/OKX tick and lot size quantization with mathematical truncation.
- Simulates execution policies: **Post-Only**, **IOC**, and **FOK**.
- Calculates net settlement and maker/taker fees, including negative rebates.

```python
#!/usr/bin/env python3
"""
Lab: Fixed-Point Financial Precision, Filter Quantizer & Order Type Policies
Verifies decimal arithmetic, tick/lot quantization, and Post-Only/IOC/FOK mechanics.
"""

from decimal import Decimal, ROUND_DOWN
from dataclasses import dataclass
from typing import Optional, Tuple

@dataclass
class SymbolFilters:
    tick_size: Decimal
    step_size: Decimal
    min_notional: Decimal

    def quantize_price(self, price: Decimal) -> Decimal:
        """Rounds price down to nearest tick_size multiple."""
        return price.quantize(self.tick_size, rounding=ROUND_DOWN)

    def quantize_qty(self, qty: Decimal) -> Decimal:
        """Rounds quantity down to nearest step_size multiple."""
        return qty.quantize(self.step_size, rounding=ROUND_DOWN)

    def validate(self, price: Decimal, qty: Decimal) -> Tuple[bool, str]:
        if (price / self.tick_size) % 1 != 0:
            return False, f"Price {price} does not conform to tickSize {self.tick_size}"
        if (qty / self.step_size) % 1 != 0:
            return False, f"Qty {qty} does not conform to stepSize {self.step_size}"
        notional = price * qty
        if notional < self.min_notional:
            return False, f"Notional {notional} below minNotional {self.min_notional}"
        return True, "VALID"

class OrderExecutionPolicy:
    """Evaluates whether an order can be accepted under TIF policies."""
    @staticmethod
    def evaluate_limit_order(
        side: str,
        price: Decimal,
        qty: Decimal,
        best_bid: Optional[Decimal],
        best_ask: Optional[Decimal],
        post_only: bool = False
    ) -> Tuple[str, Decimal]:
        """
        Returns (action, executable_qty):
        - "REST": rests on book as passive maker
        - "CROSS": crosses and takes liquidity
        - "REJECT": rejected (e.g. Post-Only crossed)
        """
        would_cross = False
        if side == "BUY" and best_ask is not None and price >= best_ask:
            would_cross = True
        elif side == "SELL" and best_bid is not None and price <= best_bid:
            would_cross = True

        if would_cross:
            if post_only:
                return "REJECT_POST_ONLY", Decimal("0")
            return "CROSS_TAKER", qty
        else:
            return "REST_MAKER", qty

def calculate_fee(notional: Decimal, fee_rate: Decimal) -> Decimal:
    """Calculates fee. Negative fee_rate represents a maker rebate."""
    return (notional * fee_rate).quantize(Decimal("0.000001"), rounding=ROUND_DOWN)

def test_financial_precision_and_orders():
    # 1. Setup Binance BTCUSDT Filters
    filters = SymbolFilters(
        tick_size=Decimal("0.01"),
        step_size=Decimal("0.00001"),
        min_notional=Decimal("5.00")
    )

    # 2. Test Quantization (Eliminating floating-point noise)
    raw_price = Decimal("95000.5089")
    raw_qty = Decimal("0.00123999")
    clean_price = filters.quantize_price(raw_price)
    clean_qty = filters.quantize_qty(raw_qty)

    print("=== 1. Tick and Lot Size Quantization ===")
    print(f"  Raw:   Price={raw_price}, Qty={raw_qty}")
    print(f"  Clean: Price={clean_price}, Qty={clean_qty}")
    assert clean_price == Decimal("95000.50")
    assert clean_qty == Decimal("0.00123")

    valid, msg = filters.validate(clean_price, clean_qty)
    assert valid is True, f"Filter validation failed: {msg}"
    print(f"  Validation: {msg} (Notional: ${clean_price * clean_qty})")

    # 3. Test Min Notional Rejection
    small_qty = Decimal("0.00002")  # $95000.50 * 0.00002 = $1.90 < $5.00 minNotional
    valid_small, msg_small = filters.validate(clean_price, small_qty)
    assert valid_small is False
    print(f"  Expected Rejection: {msg_small}")

    # 4. Test Post-Only Order Policy
    print("\n=== 2. Post-Only (Maker-Only) Policy Enforcement ===")
    current_best_bid = Decimal("94999.00")
    current_best_ask = Decimal("95001.00")

    # Passive Buy at $94999.50 (between bid and ask -> does not cross)
    action1, _ = OrderExecutionPolicy.evaluate_limit_order(
        side="BUY",
        price=Decimal("94999.50"),
        qty=Decimal("0.1"),
        best_bid=current_best_bid,
        best_ask=current_best_ask,
        post_only=True
    )
    assert action1 == "REST_MAKER"
    print("  Passive Buy ($94999.50): Accepted as REST_MAKER")

    # Aggressive Buy at $95002.00 (crosses best ask of $95001.00)
    # Post-Only MUST reject to avoid taking liquidity and paying taker fee!
    action2, _ = OrderExecutionPolicy.evaluate_limit_order(
        side="BUY",
        price=Decimal("95002.00"),
        qty=Decimal("0.1"),
        best_bid=current_best_bid,
        best_ask=current_best_ask,
        post_only=True
    )
    assert action2 == "REJECT_POST_ONLY"
    print("  Aggressive Buy ($95002.00, Post-Only): REJECT_POST_ONLY (Protected from taker fee!)")

    # 5. Fee Economics & Negative Maker Rebates
    print("\n=== 3. Fee Economics & Maker Rebates ===")
    notional = Decimal("100000.00")
    taker_fee = calculate_fee(notional, Decimal("0.0004"))    # 0.04% taker fee
    maker_rebate = calculate_fee(notional, Decimal("-0.00005")) # -0.005% maker rebate

    print(f"  Notional: ${notional}")
    print(f"  Taker pays fee:   ${taker_fee}")
    print(f"  Maker receives:   ${abs(maker_rebate)} (Exchange pays trader!)")
    assert taker_fee == Decimal("40.000000")
    assert maker_rebate == Decimal("-5.000000")

    print("\nAll Financial Precision, Filter Quantization & Order Type tests PASSED!")

if __name__ == "__main__":
    test_financial_precision_and_orders()
```

### 6. Summary & Key Takeaways

1. **Zero Floats in Financial Paths**: Never store or calculate prices, quantities, or account balances in IEEE-754 floats. Use fixed-scale decimals (`rust_decimal` or integer atomic units).
2. **Pre-Submission Quantization**: Always clamp orders to exchange `tickSize` and `stepSize` filters before transmitting down the wire to prevent validation rejections.
3. **Execution Semantics**:
   - Use **Post-Only** for liquidity provision to guarantee maker fee rebates.
   - Use **IOC** or **FOK** when taking liquidity to eliminate resting unhedged remnants.
4. **Economic Awareness**: In high-turnover strategies, maker rebates vs taker fees often make the difference between a profitable and unprofitable strategy.
