## Before you start

Your `.py` file is text, and the interpreter does not run text. It first compiles the source into bytecode, a compact list of simple instructions, and then a big C loop reads those instructions one by one. You can see the result yourself: `import dis; dis.dis("len(x)")` prints the instructions.

This chapter follows that path, then shows a newer trick. Since Python 3.11, an instruction that keeps seeing the same kinds of arguments rewrites itself into a faster special-purpose version. A generic `CALL` that keeps hitting `len` becomes `CALL_LEN`, which skips most of the general machinery. The last part covers how CPython can run threads in parallel without the global lock.

It helps to have read [chapter 01](/tech/series/cpython-internals/01.map-and-len/), since the same `len()` call is traced here. For the general idea of bytecode machines, see [Bytecode VMs 01](/tech/series/bytecode-vms/01.lexing-ast-and-bytecode-generation/).

Terms used in this chapter:

- **bytecode**: the compact instruction list the compiler produces from source code.
- **code object**: the structure holding a function's bytecode, constants and names (`PyCodeObject`).
- **evaluation loop**: the C function that fetches and executes bytecode instructions in a loop.
- **specialization**: replacing a general instruction with a faster one for the types it has actually seen (PEP 659).
- **GIL**: the global interpreter lock, which lets only one thread run Python code at a time.
- **free-threaded build**: a CPython build without the GIL (PEP 703), selected at build time.

## CPython Internals 06: From Source to Bytecode, Adaptive Specialization (`CALL_LEN`) & Free-Threading

In Chapters 01 through 05, we traced `len([10, 20, 30])` starting from the C builtin `builtin_len`. How did CPython get from the ASCII characters `"len([10, 20, 30])"` in your `.py` file to calling `builtin_len`—and why, in modern CPython (3.11+), does a hot loop calling `len(items)` eventually bypass `builtin_len` altogether?

In this final chapter, we connect the **CPython Compilation Pipeline**, the **Bytecode Evaluation Loop (`_PyEval_EvalFrameDefault` and `Python/bytecodes.c`)**, **PEP 659 Adaptive Interpreter Specialization (`CALL` $\rightarrow$ `CALL_LEN`)**, and **PEP 703 Free-Threading Synchronization (`@critical_section` & QSBR)**.

### 1. The Four-Stage Compilation Pipeline: From `.py` to `PyCodeObject`

Whenever CPython imports a module or runs `compile()`, source text passes through four compilation stages inside `Parser/` and `Python/`:

```text
Python Source Text: "answer = len(items)"
  │
  ▼  [1. Tokenizer (Parser/tokenizer/)] + [PEG Parser (Grammar/python.gram -> Parser/parser.c)]
Abstract Syntax Tree (AST: ast.Assign -> ast.Call(func=Name('len'), args=[Name('items')]))
  │
  ▼  [2. Symbol Table Analysis (Python/symtable.c)]
Scope & Variable Classification (local 'FAST' slots vs cell/free closures vs globals)
  │
  ▼  [3. AST-to-CFG Bytecode Compiler (Python/compile.c)]
Instruction Control-Flow Graph (Basic blocks of pseudo-instructions)
  │
  ▼  [4. CFG Optimizer & Assembler (Python/flowgraph.c & Python/assemble.c)]
Immutable PyCodeObject (__code__: co_code bytecode bytes, co_consts, co_names, co_varnames)
```

#### 1.1 Inspecting the `CALL` Boundary with `dis`

You never need to read `Python/compile.c` just to find out which C entry point an expression invokes. Python's built-in `dis` module disassembles any `PyCodeObject` into human-readable bytecode instructions:

```python
import dis
dis.dis("items = [10, 20, 30]\nanswer = len(items)\n")
```

```text
  0           RESUME                   0

  1           BUILD_LIST               0
              LOAD_CONST               2 ((10, 20, 30))
              LIST_EXTEND              1
              STORE_NAME               0 (items)

  2           LOAD_NAME                1 (len)
              PUSH_NULL
              LOAD_NAME                0 (items)
              CALL                     1
              STORE_NAME               2 (answer)
              LOAD_CONST               1 (None)
              RETURN_VALUE
```

This is the output of CPython 3.14; 3.12 and 3.13 print byte offsets and use `RETURN_CONST`, and opcode names change between releases.

Look at line 2 of the disassembly:

1. **`LOAD_NAME 1 (len)`**: Resolves `"len"` (finding the built-in function object wrapping `builtin_len`) and pushes it onto the frame's evaluation stack.
2. **`PUSH_NULL`**: Pushes `NULL` to indicate a standalone function call rather than a bound method call (`self` slot).
3. **`LOAD_NAME 0 (items)`**: Pushes the `PyListObject *` onto the stack.
4. **`CALL 1`**: Pops the 1 argument (`items`), `NULL`, and the callable (`len`), invokes `len(items)`, and pushes the returned `PyLongObject` (`3`) onto the stack!

### 2. Inside `_PyEval_EvalFrameDefault` and `Python/bytecodes.c`

Where is the `CALL` instruction implemented in C?

In modern CPython (3.12+), core developers do not hand-edit a giant `switch (opcode)` statement inside `Python/ceval.c`. Instead, all bytecode instructions, micro-ops (`uops`), and stack effects are defined in a single declarative C DSL file: **`Python/bytecodes.c`**.

During the build (`make regen-cases`), `Tools/cases_generator/` parses `Python/bytecodes.c` and automatically generates:

- `Python/generated_cases.c.h` (included directly inside `_PyEval_EvalFrameDefault` in `Python/ceval.c`),
- stack pointer adjustments and reference-lifetime checks (`_PyStackRef`),
- inline cache layouts, and tier-2 JIT micro-op (`uop`) definitions!

#### 2.1 PEP 659: How `CALL` Adaptively Specializes into `CALL_LEN`

In Python, `len` is not a reserved keyword—technically, someone could write `len = my_custom_func`. Historically, that meant every single execution of `len(items)` had to:

1. Check what kind of callable is on the stack (`PyCFunction`).
2. Extract its `METH_O` function pointer (`builtin_len`).
3. Call `builtin_len(module, items)` through an indirect C function pointer.

PEP 659 (**Specializing Adaptive Interpreter**) eliminates that overhead at runtime. In `Python/bytecodes.c`, `CALL` belongs to an instruction family equipped with inline cache slots (`INLINE_CACHE_ENTRIES_CALL`):

<Archify src="./diagrams/pep659-adaptive-eval.workflow.json" />

```c
/* Python/bytecodes.c */
family(CALL, INLINE_CACHE_ENTRIES_CALL) = {
    CALL_BOUND_METHOD_EXACT_ARGS,
    CALL_PY_EXACT_ARGS,
    CALL_TYPE_1,
    CALL_STR_1,
    CALL_TUPLE_1,
    CALL_BUILTIN_CLASS,
    CALL_BUILTIN_O,
    CALL_BUILTIN_FAST,
    CALL_BUILTIN_FAST_WITH_KEYWORDS,
    CALL_LEN,
    CALL_ISINSTANCE,
    CALL_LIST_APPEND,
    /* ... */
};
```

When a function executes `len(items)` in a loop, after a few warmup executions, `_PyEval_EvalFrameDefault` sees that the callable on the stack is the interpreter's built-in `len` (`interp->callable_cache.len`) and **rewrites the bytecode instruction in place in memory from `CALL` to `CALL_LEN`!**

Look at the exact implementation of `CALL_LEN` (`_GUARD_CALLABLE_LEN` + `_CALL_LEN`) in `Python/bytecodes.c`:

```c
/* Python/bytecodes.c */
macro(CALL_LEN) =
    unused/1 +
    unused/2 +
    _GUARD_NOS_NULL +
    _GUARD_CALLABLE_LEN +
    _CALL_LEN +
    POP_TOP +
    POP_TOP;

op(_GUARD_CALLABLE_LEN, (callable, unused, unused -- callable, unused, unused)){
    PyObject *callable_o = PyStackRef_AsPyObjectBorrow(callable);
    PyInterpreterState *interp = tstate->interp;
    EXIT_IF(callable_o != interp->callable_cache.len);
}

op(_CALL_LEN, (callable, null, arg -- res, a, c)) {
    /* len(o) */
    STAT_INC(CALL, hit);
    PyObject *arg_o = PyStackRef_AsPyObjectBorrow(arg);
    Py_ssize_t len_i = PyObject_Length(arg_o);
    if (len_i < 0) {
        ERROR_NO_POP();
    }
    PyObject *res_o = PyLong_FromSsize_t(len_i);
    assert((res_o != NULL) ^ (_PyErr_Occurred(tstate) != NULL));
    if (res_o == NULL) {
        ERROR_NO_POP();
    }
    a = arg;
    c = callable;
    INPUTS_DEAD();
    res = PyStackRef_FromPyObjectSteal(res_o);
}
```

Look at what `CALL_LEN` does once specialized:

1. **`_GUARD_CALLABLE_LEN`**: Checks in a single pointer comparison (`callable_o != interp->callable_cache.len`) that nobody shadowed `len`. If someone *did* shadow `len`, `EXIT_IF` deoptimizes the instruction back to generic `CALL` cleanly!
2. **`_CALL_LEN`**: Calls `PyObject_Length(arg_o)` (an alias for `PyObject_Size`) and `PyLong_FromSsize_t(len_i)` **directly inline inside the evaluation loop**, completely bypassing `builtin_len` and `PyCFunction` dispatch!
3. And notice in `family(CALL)` above that **`CALL_LIST_APPEND`** does the exact same inline specialization for `items.append(x)`!

### 3. PEP 703 Free-Threading Internals (`--disable-gil`)

When CPython runs without the Global Interpreter Lock (`Py_GIL_DISABLED`), how do container operations like `items[a:b] = other` or `items.append(x)` stay thread-safe when multiple OS threads mutate or read the same list simultaneously?

Open `Objects/listobject.c` to see two of the concurrency primitives CPython uses in free-threaded builds:

#### 3.1 Per-Object Critical Sections (`Py_BEGIN_CRITICAL_SECTION`)

Instead of one global lock stalling all threads across the process, every `PyObject` has a 1-byte `PyMutex ob_mutex` in its header (Chapter 02). Argument Clinic methods decorated with `@critical_section` (like `list.append`) get a generated wrapper in `Objects/clinic/listobject.c.h` that holds the object's lock around the C implementation. In a default (GIL) build these macros compile to nothing:

```c
/* Objects/clinic/listobject.c.h */
static PyObject *
list_append(PyObject *self, PyObject *object)
{
    PyObject *return_value = NULL;

    Py_BEGIN_CRITICAL_SECTION(self);
    return_value = list_append_impl((PyListObject *)self, object);
    Py_END_CRITICAL_SECTION();

    return return_value;
}
```

And when an operation touches **two** lists at once (such as `a + b` in `_PyList_Concat`, or `a.extend(b)` for a list `b`), `Objects/listobject.c` uses **`Py_BEGIN_CRITICAL_SECTION2(a, b)`**, which acquires both per-object locks in a deterministic order (by address) to avoid deadlock.

#### 3.2 Lock-Free Reads via QSBR (Quiescent State-Based Reclamation)

Waiting on a mutex for every single `items[i]` read would slow down read-heavy multi-threaded code. To allow lock-free reads on shared lists and dicts, what happens if Thread A is reading `self->ob_item[i]` at the exact instant Thread B appends an item and `list_resize` reallocates `self->ob_item`?

Look at `free_list_items` in `Objects/listobject.c`:

```c
/* Objects/listobject.c */
static void
free_list_items(PyObject** items, bool use_qsbr)
{
#ifdef Py_GIL_DISABLED
    _PyListArray *array = _Py_CONTAINER_OF(items, _PyListArray, ob_item);
    if (use_qsbr) {
        size_t size = sizeof(_PyListArray) + array->allocated * sizeof(PyObject *);
        _PyMem_FreeDelayed(array, size);
    }
    else {
        PyMem_Free(array);
    }
#else
    PyMem_Free(items);
#endif
}
```

When a shared list resizes its backing array in a free-threaded build, it does **not** immediately `free()` the old `ob_item` array! Instead, it passes the old array to **`_PyMem_FreeDelayed()` (QSBR)**, which defers freeing the memory until all active reader threads have passed through a quiescent state—preventing concurrent lock-free readers from ever dereferencing a freed `ob_item` buffer.

### 4. Verification Lab: Observing Live PEP 659 Adaptive Specialization (`CALL` $\rightarrow$ `CALL_LEN`)

In Python 3.11+, `dis.dis(func, adaptive=True)` lets you inspect the **live, mutated bytecode** of a function after it runs! The script below disassembles a function calling `len(items)` and `items.append(x)` **before** and **after** warming it up in a loop, proving that CPython rewrites generic `CALL` opcodes in place into specialized `CALL_LEN` and `CALL_LIST_APPEND` instructions.

```python
#!/usr/bin/env python3
"""
Observe PEP 659 Specializing Adaptive Interpreter in action using
dis.get_instructions(..., adaptive=True):
Watch generic 'CALL' instructions rewrite themselves in-place into
specialized 'CALL_LEN' and 'CALL_LIST_APPEND' instructions after warmup!
"""
import dis


def measure_and_append(items: list[int], val: int) -> int:
    items.append(val)
    return len(items)


def dump_call_opcodes(label: str) -> list[str]:
    # adaptive=True (Python 3.11+) reads the live specialized opcodes from co_code
    instrs = list(dis.get_instructions(measure_and_append, adaptive=True))
    opnames = [ins.opname for ins in instrs]
    print(f"=== {label} ===")
    for ins in instrs:
        if "CALL" in ins.opname or "LOAD" in ins.opname:
            print(f"  offset {ins.offset:2d}: {ins.opname:26s} {ins.argrepr}")
    return opnames


def main() -> None:
    before_ops = dump_call_opcodes("[1] Bytecode BEFORE Warmup (Un-specialized)")

    # Run measure_and_append 100 times to trigger PEP 659 adaptive specialization
    sample: list[int] = []
    for i in range(100):
        measure_and_append(sample, i)

    after_ops = dump_call_opcodes("\n[2] Bytecode AFTER 100 Calls (Adaptively Specialized!)")

    print("\n=== [3] Summary of Specialized Instructions ===")
    print(f"  Before warmup : {before_ops}")
    print(f"  After warmup  : {after_ops}")


if __name__ == "__main__":
    main()
```

#### Output Walkthrough

When you run this script on CPython 3.11+:

1. **Before warmup**, both calls (`items.append(val)` and `len(items)`) are compiled as generic `CALL` instructions (`LOAD_ATTR` + `CALL`).
2. **After warmup**, `dis.get_instructions(..., adaptive=True)` reveals that `_PyEval_EvalFrameDefault` has patched the live bytecode in memory into **`CALL_LIST_APPEND`** and **`CALL_LEN`**—executing the exact `_CALL_LEN` micro-op we read in `Python/bytecodes.c`!
