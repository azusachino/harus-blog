## Before you start

C has no classes, yet CPython needs one function to accept any Python value: an int, a list, a string. The trick is to start every object's struct with the same small header. Any pointer to such a struct can then be treated as a pointer to the header, the way every envelope in a mail system carries an address in the same spot regardless of what is inside.

The chapter also covers how a list grows. `l = []` followed by many `l.append(x)` calls does not ask the allocator for memory each time. The list keeps spare room, so its length and its allocated capacity are different numbers.

Read [chapter 01](/tech/series/cpython-internals/01.map-and-len/) first; this chapter picks up where its `len()` trace ended.

Terms used in this chapter:

- **object header**: the fixed fields at the start of every Python object, including its reference count and type pointer.
- **PyVarObject**: an object header plus a size field, used by objects with a variable number of items such as lists and tuples.
- **ob_size**: the field holding how many items a variable-size object currently has.
- **capacity**: how many items a list has room for before it must grow; stored in `allocated`, separate from `ob_size`.
- **realloc**: the C function that resizes a block of heap memory and may move it.
- **immortal object**: an object whose reference count is never changed, such as `None`, introduced by PEP 683.
- **free-threading**: a CPython build without the global interpreter lock (PEP 703).

## CPython Internals 02: `PyObject` in Memory, `PyVarObject` & `PyListObject` Capacity Math

In Chapter 01, our trace of `len([10, 20, 30])` ended at `PyList_GET_SIZE(a)`, which read a field named `ob_size`. How can C—a language without classes, inheritance, or generics—let `builtin_len(PyObject *obj)` accept a pointer to *any* Python object, and then safely cast that pointer to `PyVarObject *` or `PyListObject *`?

As the comment at the top of `Include/object.h` puts it:

```c
/* Nothing is actually declared to be a PyObject, but every pointer to
 * a Python object can be cast to a PyObject*. This is inheritance built
 * by hand. Similarly every pointer to a variable-size Python object can,
 * in addition, be cast to PyVarObject*.
 */
```

This chapter examines how CPython builds object inheritance by hand in memory, how `PyListObject` separates logical length (`ob_size`) from reserved buffer capacity (`allocated`), and how CPython's growth formula achieves $O(1)$ amortized `list.append()`.

---

### 1. Inheritance Built by Hand: `PyObject` and `PyVarObject`

In C, the first field of a `struct` is guaranteed by the C standard (C11 §6.7.2.1) to reside at **byte offset `0`** with zero leading padding. Therefore, if Struct B embeds Struct A as its very first field, a pointer to Struct B (`B *`) and a pointer to Struct A (`A *`) point to the **exact same memory address** and can be cast back and forth safely.

CPython uses this rule to establish a three-level layout hierarchy for container types like `PyListObject`:

```text
Byte Offset (64-bit Standard Build)
  0 ┌──────────────────────────────────────────────┐ ◄── PyObject *
    │ ob_refcnt (32b) | ob_overflow (16b) | flags  │     (16 bytes)
  8 ├──────────────────────────────────────────────┤
    │ ob_type (PyTypeObject * -> &PyList_Type)     │
 16 ╞══════════════════════════════════════════════╡ ◄── PyVarObject *
    │ ob_size (Py_ssize_t: current length, e.g. 3) │     (24 bytes)
 24 ╞══════════════════════════════════════════════╡ ◄── PyListObject *
    │ ob_item (PyObject **: pointer to slot array) │     (40 bytes)
 32 ├──────────────────────────────────────────────┤
    │ allocated (Py_ssize_t: reserved slot count)  │
 40 └──────────────────────────────────────────────┘
```

#### 1.1 Level 1: `struct _object` (`PyObject`) in `Include/object.h`

Every Python object starts with `PyObject ob_base`. In a standard 64-bit GIL-enabled build (`!defined(Py_GIL_DISABLED)`), `struct _object` is exactly **16 bytes**:

```c
/* Include/object.h (64-bit little-endian standard build) */
struct _object {
    union {
        int64_t ob_refcnt_full;
        struct {
            uint32_t ob_refcnt;
            uint16_t ob_overflow;
            uint16_t ob_flags;
        };
    };
    PyTypeObject *ob_type;
};
```

Why is the first 8-byte word split into a 32-bit `ob_refcnt`, a 16-bit `ob_overflow`, and a 16-bit `ob_flags` in recent CPython?

- **PEP 683 Immortal Objects (`_Py_IMMORTAL_INITIAL_REFCNT`)**: Prior to Python 3.12, even global singletons like `None`, `True`, `False`, and small integers (`-5..256`) mutated their `ob_refcnt` on every single read, causing needless CPU cache-line invalidation across multi-process `fork()` Copy-on-Write pages and multi-core threads. By reserving high flag bits (`_Py_STATICALLY_ALLOCATED_FLAG`, `_Py_IMMORTAL_FLAGS`), `Py_INCREF` and `Py_DECREF` become no-ops on immortal objects, keeping shared memory pages clean!
- **`ob_type`**: An 8-byte pointer to the object's type descriptor (`PyTypeObject *`), which answers "what kind of object is this?" (`Py_TYPE(op)`).

#### 1.2 How PEP 703 Free-Threading (`Py_GIL_DISABLED`) Changes `PyObject`

When CPython is compiled without the Global Interpreter Lock (`./configure --disable-gil`), two threads mutating a single shared `ob_refcnt` with atomic `LOCK XADD` instructions on every local variable access would destroy multi-core scalability.

In `Include/object.h`, the `Py_GIL_DISABLED` build replaces the 16-byte header with a **32-byte Biased Reference Counting header**:

```c
/* Include/object.h (Free-threaded build: Py_GIL_DISABLED) */
struct _object {
    uintptr_t ob_tid;           // Owning thread ID (fast non-atomic path!)
    uint16_t ob_flags;
    PyMutex ob_mutex;           // 1-byte per-object lock for critical sections
    uint8_t ob_gc_bits;         // Cyclic GC state bits
    uint32_t ob_ref_local;      // Non-atomic refcount for the owning thread!
    Py_ssize_t ob_ref_shared;   // Atomic refcount for other threads
    PyTypeObject *ob_type;
};
```

- **Owner Thread Fast Path (`ob_ref_local`)**: If the current thread's ID matches `ob_tid`, `Py_INCREF` and `Py_DECREF` increment/decrement `ob_ref_local` with ordinary **non-atomic** CPU instructions!
- **Cross-Thread Slow Path (`ob_ref_shared`)**: Only when a *different* thread (`tid != ob_tid`) references the object does CPython use an atomic instruction on `ob_ref_shared`.
- **Per-Object `PyMutex ob_mutex`**: A compact 1-byte lock embedded directly in every object header so container operations (`@critical_section` on `list.append` or `dict.__setitem__`) can synchronize per container without a global lock.

### 2. `PyVarObject` and `PyListObject`: Length vs. Capacity

Variable-length objects (`list`, `tuple`, `bytes`) begin with `PyObject_VAR_HEAD`, which embeds `PyVarObject`:

```c
/* Include/object.h */
struct PyVarObject {
    PyObject ob_base;
    Py_ssize_t ob_size; /* Number of items in variable part */
};
```

Now open `Include/cpython/listobject.h` to read the complete `PyListObject` definition:

```c
/* Include/cpython/listobject.h */
typedef struct {
    PyObject_VAR_HEAD
    /* Vector of pointers to list elements. list[0] is ob_item[0], etc. */
    PyObject **ob_item;

    /* ob_item contains space for 'allocated' elements. The number
     * currently in use is ob_size.
     * Invariants:
     *     0 <= ob_size <= allocated
     *     len(list) == ob_size
     *     ob_item == NULL implies ob_size == allocated == 0
     * list.sort() temporarily sets allocated to -1 to detect mutations.
     */
    Py_ssize_t allocated;
} PyListObject;
```

#### 2.1 Why `ob_item` Is `PyObject **` (An Array of Pointers)

In C, an array `int items[4]` stores four raw 32-bit integers side by side. Why can a Python list hold `[42, "hello", [1, 2]]`—mixing an integer, a variable-length Unicode string, and a nested list—while still supporting $O(1)$ indexing `items[i]`?

Because `ob_item` is a contiguous C array of **8-byte pointers (`PyObject *`)**, so the pointer to the first slot has type **`PyObject **`**:

```text
PyListObject (40 bytes on heap)          ob_item Buffer (allocated = 4 slots = 32 bytes)
┌──────────────────────────────┐        ┌──────────────┬──────────────┬──────────────┬──────┐
│ ob_refcnt = 1                │        │ ob_item[0]   │ ob_item[1]   │ ob_item[2]   │ NULL │
│ ob_type   = &PyList_Type     │        └──────┬───────┴──────┬───────┴──────┬───────┴──────┘
│ ob_size   = 3                │               │              │              │
│ ob_item   ───────────────────┼───────────────┘              │              ▼
│ allocated = 4                │               ▼              ▼        PyListObject [1, 2]
└──────────────────────────────┘         PyLongObject   PyUnicodeObject
                                            (42)          ("hello")
```

Every slot in `ob_item` is fixed at 8 bytes (`sizeof(PyObject *)`), so `items[i]` is a simple pointer offset `*(self->ob_item + i)`, while the heterogeneous objects themselves live at their own heap addresses with their own lifetimes and reference counts!

#### 2.2 The `list_resize` Growth Formula in `Objects/listobject.c`

If `list.append()` called `realloc()` to grow `ob_item` by 1 slot on every single call, appending $N$ elements would copy $1 + 2 + \dots + N = O(N^2)$ pointers. Instead, `list_resize()` in `Objects/listobject.c` over-allocates by roughly $12.5\%$ (`newsize >> 3`) rounded up to a multiple of 4:

```c
/* Objects/listobject.c: list_resize() */
/* Add padding to make the allocated size multiple of 4.
 * The growth pattern is: 0, 4, 8, 16, 24, 32, 40, 52, 64, 76, ...
 */
new_allocated = ((size_t)newsize + (newsize >> 3) + 6) & ~(size_t)3;
```

Notice the two-sided invariant in `list_resize`:

1. **Fast Path (No Allocation)**: When `newsize <= self->allocated` and `newsize >= (self->allocated >> 1)`, `list_resize` simply updates `Py_SET_SIZE(self, newsize)` and returns `0` immediately!
2. **Shrinking Threshold**: When you `pop()` elements, CPython does not shrink `ob_item` until `newsize` drops **below half** of `allocated` (`allocated >> 1`), preventing thrashing when a list oscillates between $N$ and $N-1$ elements.
3. **Mutation Detection during `list.sort()`**: Look at the comment in `listobject.h`: *"list.sort() temporarily sets allocated to -1 to detect mutations."* While Timsort works, `list.sort()` moves the elements into a private buffer, leaves the list empty (`ob_item = NULL`, `ob_size = 0`) and sets `self->allocated = -1`. If a custom `__lt__` mutates the list mid-sort (`items.append(x)`), `list_resize` allocates as usual and overwrites `allocated` with a value `>= 0`. When the sort finishes it sees `allocated != -1` and raises `ValueError: list modified during sort`.

### 3. Safe Failure Handling in C Reallocation (`realloc` Temporary Pointer Rule)

When reading or writing container growth code in C (such as `list_resize`), always watch how `realloc()` failures are handled:

```c
/* WRONG: Overwrites self->ob_item with NULL if realloc fails, leaking the old array! */
self->ob_item = PyMem_Realloc(self->ob_item, target_bytes);

/* CORRECT (Objects/listobject.c): Store in temporary 'items' first! */
PyObject **items = PyMem_Realloc(self->ob_item, target_bytes);
if (items == NULL) {
    PyErr_NoMemory();
    return -1;
}
self->ob_item = items;
self->allocated = new_allocated;
```

Because `realloc(ptr, new_size)` leaves the **original memory block intact** when it returns `NULL`, storing the return value into a temporary pointer `items` preserves `self->ob_item` and keeps the Python list completely valid even when an out-of-memory `MemoryError` is raised!

### 4. Verification Lab: Reading Live `PyListObject` Fields (`ob_size` vs. `allocated`)

Using `ctypes` and `sys.getsizeof()`, we can read the live `PyListObject` struct (`ob_size`, `ob_item`, and `allocated`) in memory as we append elements one by one, observing the exact `0, 4, 8, 16, 24, 32...` capacity jumps from `list_resize()` in `Objects/listobject.c`!

```python
#!/usr/bin/env python3
"""
Read live PyListObject memory (ob_size, ob_item pointer, and allocated capacity)
across appends to verify CPython's list_resize() growth pattern:
  new_allocated = ((size_t)newsize + (newsize >> 3) + 6) & ~(size_t)3
"""
import ctypes
import sys


def cpython_growth_formula(newsize: int) -> int:
    if newsize == 0:
        return 0
    return (newsize + (newsize >> 3) + 6) & ~3


def inspect_pylist_capacity(lst: list) -> tuple[int, int]:
    """
    Return (len(lst), allocated_slots) derived from sys.getsizeof(lst).
    sys.getsizeof(lst) calls list___sizeof___impl in Objects/listobject.c:
      sizeof(PyListObject) + lst->allocated * sizeof(PyObject*)
    """
    ptr_size = ctypes.sizeof(ctypes.c_void_p)
    base_size = sys.getsizeof([])  # sizeof(PyListObject) when allocated == 0
    total_bytes = sys.getsizeof(lst)
    allocated_slots = (total_bytes - base_size) // ptr_size
    return len(lst), allocated_slots


def main() -> None:
    items: list[int] = []
    base_bytes = sys.getsizeof(items)
    print(f"sizeof(PyListObject) header = {base_bytes} bytes")
    print(f"{'Step':>10s} | {'ob_size (len)':>13s} | {'allocated':>9s} | {'Formula Check':>13s} | {'Heap Bytes':>10s}")
    print("-" * 68)

    prev_alloc = -1
    for i in range(1, 35):
        items.append(i)
        ob_size, allocated = inspect_pylist_capacity(items)
        if allocated != prev_alloc:
            expected = cpython_growth_formula(ob_size)
            assert allocated == expected, f"Mismatch: {allocated} != {expected}"
            print(
                f"append({i:2d}) | {ob_size:13d} | {allocated:9d} | "
                f"{expected:13d} | {sys.getsizeof(items):10d}"
            )
            prev_alloc = allocated


if __name__ == "__main__":
    main()
```

#### Output Walkthrough

When you run this script, every capacity jump matches the growth comment in `list_resize()` (`0 -> 4 -> 8 -> 16 -> 24 -> 32 -> 40`):

- At `append(1)`, `ob_size` becomes `1`, and `((1 + 0 + 6) & ~3)` allocates **`4` slots**.
- Appends `2`, `3`, and `4` take the zero-allocation fast path (`ob_size <= allocated`).
- At `append(5)`, `((5 + 0 + 6) & ~3)` reallocates `ob_item` to **`8` slots**.
- At `append(9)`, `((9 + 1 + 6) & ~3)` reallocates `ob_item` to **`16` slots**.
