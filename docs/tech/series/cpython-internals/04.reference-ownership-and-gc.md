## Before you start

Python frees an object when nothing refers to it anymore. CPython does this by keeping a counter inside each object: the number of references pointing at it. In Python you never touch the counter. In C extension code you do, and getting it wrong means either a leak (the count never reaches zero) or a crash (the object is freed while you still use it).

The practical question is ownership. If a function hands you a pointer, do you own a reference you must release, or are you merely looking at someone else's? Think of a library book: a strong reference is a loan in your name, a borrowed one is reading over someone's shoulder. If they return the book, you are reading nothing.

Counting cannot free two objects that point at each other, so a second mechanism, the cyclic garbage collector, finds those.

Read [chapter 02](/tech/series/cpython-internals/02.pyobject-and-memory/) first for the object header that holds the count.

Terms used in this chapter:

- **reference count**: the number of references to an object; at zero the object is freed.
- **strong reference**: a reference you own and must release with `Py_DECREF`.
- **borrowed reference**: a pointer you may use but do not own; it is valid only while its owner keeps the object alive.
- **use-after-free**: reading memory after it was freed, which can crash or corrupt data.
- **tp_dealloc**: the type slot that destroys an object when its count hits zero.
- **tp_traverse**: the type slot that lists the other objects an object refers to, used by the cyclic collector.
- **reference cycle**: objects that refer to each other, so their counts never reach zero on their own.

## CPython Internals 04: Reference Ownership, Borrowed vs Strong Refs & Cyclic GC

When reading or writing CPython C code, the single most important question at every line is: **"Who owns a strong reference to this `PyObject *` right now?"**

A mistake in either direction is fatal:

- Forget one `Py_DECREF` on an error branch, and the object (plus everything it references) leaks for the lifetime of the process.
- Call `Py_DECREF` once too often—or hold onto a **borrowed reference** across a call that mutates its container—and CPython frees the object while your C pointer still points to it (**use-after-free** / segfault).

You do not need to guess numeric `ob_refcnt` values to write bug-free CPython code. Instead, CPython core developers track **Reference Ownership** using a small set of explicit contracts (`Py_NewRef`, `Py_DECREF`, `TakeRef` / reference stealing, and Borrowed vs. Strong references).

---

### 1. The Core Reference Operations in CPython

Every `PyObject *` pointer in C is either a **Strong Reference** (you own 1 count in `ob_refcnt` and *must* eventually release it or transfer ownership) or a **Borrowed Reference** (another structure owns the lifetime; you are merely peeking at the pointer without incrementing `ob_refcnt`).

| C API Function / Macro | Action on `ob_refcnt` | Ownership Contract |
| :--- | :--- | :--- |
| **`Py_NewRef(PyObject *o)`** | `+1` (and returns `o`) | Creates and returns a **new strong reference** to `o` (modern functional replacement for `Py_INCREF(o)`). |
| **`Py_XNewRef(PyObject *o)`** | `+1` if `o != NULL` | Null-safe version of `Py_NewRef(o)` (returns `NULL` if `o == NULL`). |
| **`Py_DECREF(PyObject *o)`** | `-1` (if `0`, calls `tp_dealloc`) | Releases **one strong reference** you own. Never call on a borrowed reference or `NULL`! |
| **`Py_XDECREF(PyObject *o)`** | `-1` if `o != NULL` | Null-safe cleanup used in `error:` blocks when a local pointer might still be `NULL`. |
| **`Py_SETREF(dst, src)`** | Decrements old `dst` after assigning `src` | Safely replaces a strong reference variable `dst` with `src` without macro double-evaluation or re-entrancy bugs. |

#### 1.1 Tracing `list.append(value)` in `Objects/listobject.c`

Consider three lines of Python:

```python
value = object()
items = []
items.append(value)
```

After `items.append(value)` returns, the list `items` must keep `value` alive even if the caller later executes `del value`. Open `list_append_impl` in `Objects/listobject.c` to see how `list_append_impl` implements this in three lines of C:

```c
/* Objects/listobject.c */
static PyObject *
list_append_impl(PyListObject *self, PyObject *object)
{
    if (_PyList_AppendTakeRef(self, Py_NewRef(object)) < 0) {
        return NULL;
    }
    Py_RETURN_NONE;
}
```

Why does `list_append_impl` call `Py_NewRef(object)` and pass the result into `_PyList_AppendTakeRef`?

1. **Incoming Arguments Are Borrowed**: When CPython's call machinery invokes `list_append_impl(self, object)`, the caller keeps ownership of `self` and `object` for the duration of the call. `list_append_impl` receives them as **borrowed pointers**—it does not own them and must not `Py_DECREF` them.
2. **Creating the List's Reference (`Py_NewRef(object)`)**: Because `self->ob_item[i]` will store a pointer to `object` that outlives this function call, the list needs its own **strong reference**. `Py_NewRef(object)` increments `object->ob_refcnt` and produces that strong reference.
3. **Reference Stealing (`TakeRef`)**: The suffix `TakeRef` in `_PyList_AppendTakeRef` documents that **the callee steals (takes ownership of) the strong reference passed to it**:
   - **On success (`0`)**: `_PyList_AppendTakeRef` stores the pointer into `self->ob_item[len]`, transferring ownership of that strong reference to the list `self`.
   - **On failure (`-1`, e.g. `MemoryError` inside `list_resize`)**: Because `_PyList_AppendTakeRef` *stole* the reference on entry, **`_PyList_AppendTakeRef` itself calls `Py_DECREF(newitem)` before returning `-1`!** That is why `list_append_impl` simply returns `NULL` without calling `Py_DECREF(object)`.

```c
/* Include/internal/pycore_list.h */
static inline int
_PyList_AppendTakeRef(PyListObject *self, PyObject *newitem)
{
    assert(self != NULL && newitem != NULL);
    Py_ssize_t len = PyList_GET_SIZE(self);
    Py_ssize_t allocated = self->allocated;
    if (allocated > len) {
        PyList_SET_ITEM(self, len, newitem);
        _PyList_SET_SIZE(self, len + 1);
        return 0;
    }
    return _PyList_AppendTakeRefListResize(self, newitem); // Calls Py_DECREF(newitem) on error!
}
```

#### 1.2 The Ownership Ledger Method

Instead of guessing whether `ob_refcnt` is `2`, `3`, or `100` (which varies with stack frames or immortal objects), audit C code by writing an **Ownership Ledger** tracking *which named entities own a strong reference*:

| Execution Point | Entities Owning a Strong Reference to `value` | Why |
| :--- | :--- | :--- |
| After `value = object()` | `{ frame.locals["value"] }` (1 owner) | `object()` returned a new strong ref bound to `value`. |
| Inside `list_append_impl` at `Py_NewRef(object)` | `{ frame.locals["value"], temp_arg_to_TakeRef }` (2 owners) | `Py_NewRef` created a second strong claim for the list. |
| After `items.append(value)` returns | `{ frame.locals["value"], items->ob_item[0] }` (2 owners) | `_PyList_AppendTakeRef` moved the new ref into `ob_item[0]`. |
| After `del value` | `{ items->ob_item[0] }` (1 owner) | `DELETE_FAST` / `DELETE_NAME` called `Py_DECREF` on `value`. |
| After `items.clear()` | `{}` (0 owners $\rightarrow$ `tp_dealloc` runs!) | `list_clear` called `Py_DECREF` on every slot in `ob_item`. |

### 2. The Borrowed Reference Trap (`PyList_GetItem` vs. `PyList_GetItemRef`)

Historically, a few C API functions—most famously **`PyList_GetItem(list, i)`** and **`PyDict_GetItemString(dict, key)`**—returned a **Borrowed Reference** rather than a new strong reference to save an `INCREF`/`DECREF` pair.

Why are borrowed references dangerous, and why did Python 3.13 introduce **`PyList_GetItemRef`** and **`PyDict_GetItemRef`** (and why does PEP 703 free-threading require them)?

#### 2.1 How a Borrowed Reference Turns into a Use-After-Free Crash

Suppose a C extension writes:

```c
/* BUGGY C CODE: Holding a borrowed reference across a call that can run Python code! */
PyObject *item = PyList_GetItem(my_list, 0);  // BORROWED reference from my_list!
if (item == NULL) return NULL;

// Suppose log_event() invokes a Python callback or __repr__() that executes:
//   my_list.clear()
log_event(callback, "processing first item");

// CRASH (Use-After-Free!): my_list.clear() dropped the last strong reference to 'item',
// so 'item' now points to freed memory!
return PyObject_Str(item);
```

Because `item` was **borrowed** from `my_list->ob_item[0]`, its validity depended completely on `my_list` not mutating! The moment `log_event()` invoked Python code (or in a free-threaded build, the moment another thread mutated `my_list` concurrently), `my_list` dropped its strong reference to `ob_item[0]`, freeing `item` while our C local variable `item` still pointed to it!

**The Safe Rule**:

- Always prefer **`PyList_GetItemRef(my_list, 0)`** (or immediately promote a borrowed reference via `Py_NewRef`), which atomically acquires a **strong reference** (under the list's critical section in free-threaded builds), and call `Py_DECREF(item)` when finished.

### 3. Deallocation (`tp_dealloc`) and the Cyclic Garbage Collector

When `Py_DECREF(op)` decrements `op->ob_refcnt` to **`0`**, it immediately invokes `_Py_Dealloc(op)`, which calls the type's deallocator slot: **`Py_TYPE(op)->tp_dealloc(op)`**.

- **Immediate Determinism**: In CPython, any acyclic object whose reference count reaches zero is destroyed **on the exact line of code that dropped the final reference**. That is why `with open(...)` and file/socket finalizers run deterministically in CPython.

#### 3.1 Why Reference Counting Alone Cannot Reclaim Reference Cycles

What happens when two containers reference each other, and all external variables pointing to them are deleted?

```python
a = []
b = [a]
a.append(b)  # Cycle: a->ob_item[0] points to b, and b->ob_item[0] points to a!
del a, b     # Both a and b still have ob_refcnt == 1!
```

```text
After 'del a, b' (No variables on stack or globals can reach a or b!):

   ┌─────────────────────────┐          ┌─────────────────────────┐
   │ PyListObject 'a'        │          │ PyListObject 'b'        │
   │   ob_refcnt = 1  ◄──────┼──────────┼── ob_item[0]            │
   │   ob_item[0] ───────────┼─────────►│   ob_refcnt = 1         │
   └─────────────────────────┘          └─────────────────────────┘
```

Because `a` holds a strong reference to `b` (`b->ob_refcnt == 1`) and `b` holds a strong reference to `a` (`a->ob_refcnt == 1`), neither reference count ever drops to `0`!

#### 3.2 How CPython's Cyclic Garbage Collector (`gc` Module) Finds Isolated Cycles

<Archify src="./diagrams/cpython-cyclic-gc.workflow.json" />

To reclaim isolated reference cycles, container types that can hold pointers to other objects set the `Py_TPFLAGS_HAVE_GC` flag in `PyTypeObject.tp_flags`, prepend a `PyGC_Head` doubly-linked list node before their `PyObject` header, and implement two C slots:

1. **`tp_traverse` (`list_traverse` in `Objects/listobject.c`)**: Visits every outgoing reference stored inside the container (`Py_VISIT(self->ob_item[i])`).
2. **`tp_clear` (`list_clear_slot` in `Objects/listobject.c`)**: Breaks the cycle by emptying the container and calling `Py_DECREF` on its elements.

```c
/* Objects/listobject.c */
static int
list_traverse(PyObject *o, visitproc visit, void *arg)
{
    PyListObject *PSelf = (PyListObject *)o;
    for (Py_ssize_t i = Py_SIZE(PSelf); --i >= 0;) {
        Py_VISIT(PSelf->ob_item[i]);
    }
    return 0;
}
```

When the cyclic GC runs (`Python/gc.c`), it executes a four-step **Trial Deletion Algorithm** across tracked container objects:

1. **Copy `ob_refcnt` into `gc_refs`**: For every tracked container in the generation being collected, copy its current reference count into a scratch field `gc_refs`.
2. **Subtract Internal References (`tp_traverse`)**: Call `tp_traverse` on every tracked container. For each outgoing pointer `child` visited, decrement `child`'s `gc_refs` by 1.
   - Think about what happens to our isolated cycle `a <-> b`: both started with `ob_refcnt = 1` (`gc_refs = 1`). When `list_traverse(a)` visits `b`, `b.gc_refs` becomes **`0`**. When `list_traverse(b)` visits `a`, `a.gc_refs` becomes **`0`**!
   - By contrast, any container that is still referenced from a live stack frame or global variable started with `ob_refcnt >= 2`, so after subtracting internal container references, its `gc_refs` remains **`>= 1`**!
3. **Partition Reachable vs. Unreachable**: Any object with `gc_refs > 0` (plus anything transitively reachable from it via `tp_traverse`) is marked **Reachable**. Everything left with `gc_refs == 0` is proven to be an **isolated, unreachable reference cycle**!
4. **Break the Cycle (`tp_clear`)**: The GC calls `tp_clear` on the unreachable objects, dropping their mutual references so their `ob_refcnt` hits `0` and `tp_dealloc` frees their memory!

### 4. Verification Lab: Proving Immediate Refcount Deallocation vs. Cyclic GC (`tp_traverse` + `tp_clear`)

The script below proves both halves of CPython's memory management in action:

1. Shows that an acyclic object is destroyed **synchronously on the exact line** `del obj` drops its last strong reference, even with the cyclic collector disabled (`gc.disable()`).
2. Constructs a two-node cycle (`node_a.peer = node_b`, `node_b.peer = node_a`), proves `del node_a, node_b` cannot free the pair (each still holds the other, so both counts stay at `1`), inspects the cycle via `gc.get_referents()` (which calls C `tp_traverse`!), and reclaims it via `gc.collect()` (which calls C `tp_clear`).

```python
#!/usr/bin/env python3
"""
Verify CPython's two-tier memory reclamation:
1. Synchronous deterministic destruction via ob_refcnt -> 0 (tp_dealloc).
2. Cyclic garbage collection via tp_traverse (gc.get_referents) and tp_clear (gc.collect).
"""
import gc
import weakref


class TrackedNode:
    def __init__(self, name: str) -> None:
        self.name = name
        self.peer: "TrackedNode | None" = None


def main() -> None:
    # Disable automatic background cyclic GC so we control exact collection points
    gc.disable()
    try:
        # 1. Acyclic object: destroyed immediately when strong refcount hits 0
        acyclic = TrackedNode("acyclic-node")
        w_acyclic = weakref.ref(acyclic)
        assert w_acyclic() is not None

        del acyclic  # ob_refcnt drops from 1 -> 0; tp_dealloc runs immediately!
        print(f"[1] After 'del acyclic' (with GC disabled): alive = {w_acyclic() is not None}")
        assert w_acyclic() is None

        # 2. Cyclic pair: node_a <-> node_b
        node_a = TrackedNode("cycle-A")
        node_b = TrackedNode("cycle-B")
        node_a.peer = node_b
        node_b.peer = node_a

        w_a = weakref.ref(node_a)
        w_b = weakref.ref(node_b)

        # Inspect outgoing pointers via C tp_traverse (exposed by gc.get_referents)
        # Keep only type names: holding the referents themselves would pin node_b
        referent_types = [type(x).__name__ for x in gc.get_referents(node_a.__dict__)]
        print(f"[2] Outgoing referents of node_a.__dict__ via tp_traverse: {referent_types}")

        # Delete both local variables; mutual references keep ob_refcnt == 1!
        del node_a, node_b
        print(f"[3] After 'del node_a, node_b' (before gc.collect): alive = {w_a() is not None and w_b() is not None}")
        assert w_a() is not None and w_b() is not None

        # Run trial-deletion cyclic GC (tp_traverse -> tp_clear -> tp_dealloc)
        reclaimed = gc.collect()
        print(f"[4] After gc.collect() (reclaimed {reclaimed} objects): alive = {w_a() is not None or w_b() is not None}")
        assert w_a() is None and w_b() is None
    finally:
        gc.enable()


if __name__ == "__main__":
    main()
```
