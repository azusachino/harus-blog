## Before you start

Python code raises exceptions and an enclosing `try` catches them. C has nothing like that, so CPython uses a convention. A C function that can fail returns a special value, `NULL` for functions that return an object, `-1` for many that return an int, and it first records the exception in a per-thread slot. The caller checks the return value and, if it signals failure, passes the failure upward.

The two halves must agree. Return `NULL` without setting an exception and Python reports a confusing `SystemError`. Set an exception but return a normal value and the error is silently carried along until something else trips on it.

The chapter also shows how to write and compile a small C extension module yourself.

Read [chapter 04](/tech/series/cpython-internals/04.reference-ownership-and-gc/) first; error paths must also release the references you hold.

Terms used in this chapter:

- **sentinel**: a special return value, such as `NULL` or `-1`, that tells the caller the call failed.
- **thread state**: the per-thread structure where the current exception is stored.
- **exception propagation**: passing a failure up through callers by returning the sentinel at each level.
- **extension module**: a shared library written in C that Python imports like any other module.
- **PyArg_ParseTuple**: the C API function that converts a call's Python arguments into C values.
- **upstream issue**: a bug report on CPython's own tracker; here one is dissected line by line.

## CPython Internals 05: Error Propagation in C, Upstream Bug Anatomy & Writing C Extensions

C has no `try` / `except` / `raise` syntax. When `[].pop()` raises `IndexError: pop from empty list` in Python, how does a C function in `Objects/listobject.c` raise that exception and unwind the call stack?

In CPython, every Python-visible failure is represented by **two separate pieces of state that must always travel together**:

1. **The Thread-State Exception Indicator (`tstate->current_exception`)**: Set via `PyErr_SetString()`, `PyErr_Format()`, or `PyErr_NoMemory()`.
2. **A C Error Return Sentinel**: Either **`NULL`** (for functions returning `PyObject *`) or **`-1`** (for functions returning `int` or `Py_ssize_t`).

Breaking the invariant between these two halves—either returning `NULL` without setting an exception, or returning a valid object while an exception remains set on the thread state—causes immediate `SystemError` crashes in release builds and `assert()` aborts in `--with-pydebug` builds.

### 1. Tracing `[].pop()` in `Objects/listobject.c`

Open `list_pop_impl` in `Objects/listobject.c` to see how it handles an empty list and an out-of-bounds index:

```c
/* Objects/listobject.c */
static PyObject *
list_pop_impl(PyListObject *self, Py_ssize_t index)
{
    PyObject *v;

    if (Py_SIZE(self) == 0) {
        /* Special-case most common failure cause */
        PyErr_SetString(PyExc_IndexError, "pop from empty list");
        return NULL;
    }
    if (index < 0)
        index += Py_SIZE(self);
    if (!valid_index(index, Py_SIZE(self))) {
        PyErr_SetString(PyExc_IndexError, "pop index out of range");
        return NULL;
    }

    PyObject **items = self->ob_item;
    v = items[index];
    if (Py_SIZE(self) == 1) {
        Py_INCREF(v);
        list_clear(self);
        return v;
    }
    /* ... */
```

Look at the two error branches (`Py_SIZE(self) == 0` and `!valid_index(...)`):

1. `PyErr_SetString(PyExc_IndexError, "pop from empty list")` constructs an `IndexError` exception instance and stores it in the calling thread's `PyThreadState->current_exception`.
2. `return NULL;` returns the `0x0` pointer sentinel to the caller.
3. Notice that `PyErr_SetString` is **not** a C++ `throw` or `longjmp`: execution continues linearly to the next C line (`return NULL;`). Every C caller up the chain must check `if (res == NULL)` (or `if (rc < 0)`), clean up any local strong references it owns via `Py_DECREF`, and return its own error sentinel until control reaches the bytecode evaluation loop (`_PyEval_EvalFrameDefault`), which jumps to the `error:` label and searches the Python frame's exception table!

```text
C Call Stack During [].pop()
┌───────────────────────────────────────────────────────────────┐
│ list_pop_impl(self, -1)                                       │
│   1. Sees Py_SIZE(self) == 0                                  │
│   2. Calls PyErr_SetString(PyExc_IndexError, "pop from...")   │
│      └──► Writes IndexError into tstate->current_exception    │
│   3. Returns NULL                                             │
└──────────────────────────────┬────────────────────────────────┘
                               │ returns NULL
                               ▼
┌───────────────────────────────────────────────────────────────┐
│ list_pop (Argument Clinic wrapper in Objects/clinic/...)      │
│   Sees return_value == NULL -> returns NULL to evaluator      │
└──────────────────────────────┬────────────────────────────────┘
                               │ returns NULL
                               ▼
┌───────────────────────────────────────────────────────────────┐
│ _PyEval_EvalFrameDefault (Python/ceval.c / bytecodes.c)       │
│   ERROR_IF(res == NULL) -> unwinds stack or matches 'except:' │
└───────────────────────────────────────────────────────────────┘
```

#### 1.1 The `-1` Ambiguity Rule: `PyLong_AsLong()` and `PyErr_Occurred()`

What if a C API function returns a signed `long` where **`-1` is also a completely valid numeric result**?

Consider **`PyLong_AsLong(PyObject *obj)`**, which converts a Python `int` into a C `long`:

- If you pass Python `-1`, `PyLong_AsLong` succeeds and returns **`-1`**.
- If you pass Python `"hello"` or `10**100` (which overflows a 64-bit `long`), `PyLong_AsLong` sets `TypeError` or `OverflowError` and **also returns `-1`**!

How do you tell whether `-1` meant "the integer minus one" or "an exception occurred"? By checking **`PyErr_Occurred()`** *only when the return value is `-1`*:

```c
long value = PyLong_AsLong(arg);
if (value == -1 && PyErr_Occurred()) {
    /* Genuine conversion error (TypeError or OverflowError already set!) */
    return NULL;
}
/* Otherwise, value is valid (including when value == -1)! */
```

| C API Return Type | Standard Error Sentinel | How to Check for Failure |
| :--- | :--- | :--- |
| `PyObject *` | `NULL` | `if (res == NULL) return NULL;` |
| `int` status (`PyList_Append`, `PyDict_SetItem`) | `-1` (`0` = success) | `if (rc < 0) return NULL;` |
| `Py_ssize_t` length/index (`PyObject_Size`) | `-1` (`>= 0` = valid size) | `if (len < 0) return NULL;` |
| `long` / `size_t` conversion (`PyLong_AsLong`) | `-1` (ambiguous with literal `-1`!) | `if (val == -1 && PyErr_Occurred()) return NULL;` |

### 2. Real Upstream CPython Bug Study: Issue #157892 (`_Py_hashtable_set` Error Sentinel Mismatch)

Understanding return-sentinel contracts is one of the fastest ways to spot real bugs in CPython. Let's examine a real upstream bug ([python/cpython#157892](https://github.com/python/cpython/issues/157892) / [PR #157898](https://github.com/python/cpython/pull/157898)) in static string interning during interpreter initialization.

First, read the callee `_Py_hashtable_set()` in `Python/hashtable.c`:

```c
/* Python/hashtable.c */
int
_Py_hashtable_set(_Py_hashtable_t *ht, const void *key, void *value)
{
    _Py_hashtable_entry_t *entry;
    /* ... */
    entry = ht->alloc.malloc(sizeof(_Py_hashtable_entry_t));
    if (entry == NULL) {
        /* memory allocation failed */
        return -1;
    }
    /* ... */
    if ((float)ht->nentries / (float)ht->nbuckets > HASHTABLE_HIGH) {
        if (hashtable_rehash(ht) < 0) {
            ht->nentries--;
            ht->alloc.free(entry);
            return -1;
        }
    }
    _Py_slist_prepend(&ht->buckets[index], (_Py_slist_item_t*)entry);
    return 0;
}
```

What is `_Py_hashtable_set`'s return contract?

- **Success**: returns **`0`**.
- **Failure (malloc or rehash OOM)**: returns **`-1`**. It *never* returns `-2` or anything less than `-1`.

Now look at how `intern_static()` in `Objects/unicodeobject.c` originally checked the return value of `_Py_hashtable_set()`:

```c
/* Objects/unicodeobject.c: intern_static() — BEFORE FIX (Issue #157892) */
    if (_Py_hashtable_set(INTERNED_STRINGS, s, s) < -1) {
        Py_FatalError("failed to intern static string");
    }
```

Because the caller wrote `< -1` instead of `< 0`, when `_Py_hashtable_set` failed and returned `-1`, `-1 < -1` evaluated to **false**! The fatal-error check was completely dead code, and `intern_static` silently marked the un-interned string as `SSTATE_INTERNED_IMMORTAL_STATIC`!

The fix in `Objects/unicodeobject.c` is a single-character change from `< -1` to `< 0`:

```c
/* Objects/unicodeobject.c: intern_static() — AFTER FIX */
    if (_Py_hashtable_set(INTERNED_STRINGS, s, s) < 0) {
        Py_FatalError("failed to intern static string");
    }
```

> **Contributor Takeaway**: Even a one-character CPython patch requires reading **both** the callee (`Python/hashtable.c`) and the caller (`Objects/unicodeobject.c`) to prove the exact return-value domain (`{0, -1}`).

### 3. Writing and Compiling a Real Python C Extension (`plus_one.c`)

Reading CPython internals clicks permanently the moment you write and compile a C function that Python can `import` and call. Let's examine a complete, production-clean C extension module `plus_one` that:

1. Accepts a single argument (`METH_O`, passed as a **borrowed** `PyObject *arg`).
2. Checks `PyLong_Check(arg)` and sets `TypeError` on non-integers.
3. Converts `arg` via `PyLong_AsLong(arg)`, using `value == -1 && PyErr_Occurred()` to distinguish `-1` from `OverflowError`.
4. Guards against signed C integer overflow (`value == LONG_MAX`).
5. Returns a **new strong reference** via `PyLong_FromLong(value + 1)`.

```c
#define PY_SSIZE_T_CLEAN
#include <Python.h>
#include <limits.h>

static PyObject *
plus_one(PyObject *module, PyObject *arg)
{
    (void)module;
    long value;

    if (!PyLong_Check(arg)) {
        PyErr_SetString(PyExc_TypeError, "expected an integer");
        return NULL;
    }

    value = PyLong_AsLong(arg);
    if (value == -1 && PyErr_Occurred()) {
        return NULL;
    }
    if (value == LONG_MAX) {
        PyErr_SetString(PyExc_OverflowError, "integer is too large");
        return NULL;
    }
    return PyLong_FromLong(value + 1);
}

static PyMethodDef methods[] = {
    {"plus_one", plus_one, METH_O, "Return an integer plus one."},
    {NULL, NULL, 0, NULL} /* Sentinel marking end of method table */
};

static struct PyModuleDef definition = {
    .m_base = PyModuleDef_HEAD_INIT,
    .m_name = "plus_one",
    .m_size = -1,
    .m_methods = methods
};

PyMODINIT_FUNC
PyInit_plus_one(void)
{
    return PyModule_Create(&definition);
}
```

Notice how `PyMethodDef methods[]` mirrors `list_methods[]` inside `Objects/listobject.c`: both are NULL-terminated C structs mapping a Python attribute name (`"plus_one"`) and calling convention flag (`METH_O`) to a C function pointer!

### 4. Verification Lab: Compiling and Testing `plus_one.c` on the Fly

The self-contained Python script below writes `plus_one.c` to a temporary directory, queries `sysconfig` for the running interpreter's `INCLUDEPY` headers and `EXT_SUFFIX` (`cpython-3xx-x86_64-linux-gnu.so`), compiles the shared library with `cc`, dynamically imports it, and verifies all five execution paths (`41 -> 42`, `-2 -> -1`, `True -> 2`, `"41" -> TypeError`, and `10**100 -> OverflowError`).

```python
#!/usr/bin/env python3
"""
Compile, load, and test the 'plus_one' C extension module against the active
CPython interpreter, verifying METH_O argument borrowing, PyLong_AsLong(-1)
disambiguation, and thread-state exception propagation.
"""
import importlib.util
import os
import shutil
import subprocess
import sys
import sysconfig
import tempfile

C_SOURCE = r"""
#define PY_SSIZE_T_CLEAN
#include <Python.h>
#include <limits.h>

static PyObject *
plus_one(PyObject *module, PyObject *arg)
{
    (void)module;
    long value;

    if (!PyLong_Check(arg)) {
        PyErr_SetString(PyExc_TypeError, "expected an integer");
        return NULL;
    }

    value = PyLong_AsLong(arg);
    if (value == -1 && PyErr_Occurred()) {
        return NULL;
    }
    if (value == LONG_MAX) {
        PyErr_SetString(PyExc_OverflowError, "integer is too large");
        return NULL;
    }
    return PyLong_FromLong(value + 1);
}

static PyMethodDef methods[] = {
    {"plus_one", plus_one, METH_O, "Return an integer plus one."},
    {NULL, NULL, 0, NULL}
};

static struct PyModuleDef definition = {
    .m_base = PyModuleDef_HEAD_INIT,
    .m_name = "plus_one",
    .m_size = -1,
    .m_methods = methods
};

PyMODINIT_FUNC
PyInit_plus_one(void)
{
    return PyModule_Create(&definition);
}
"""


def main() -> None:
    cc = shutil.which("cc") or shutil.which("gcc") or shutil.which("clang")
    include_dir = sysconfig.get_path("include")
    ext_suffix = sysconfig.get_config_var("EXT_SUFFIX") or ".so"

    if not cc or not include_dir or not os.path.exists(os.path.join(include_dir, "Python.h")):
        print("C compiler or Python.h headers not found; skipping native build.")
        return

    with tempfile.TemporaryDirectory() as tmpdir:
        c_path = os.path.join(tmpdir, "plus_one.c")
        so_path = os.path.join(tmpdir, f"plus_one{ext_suffix}")
        with open(c_path, "w", encoding="utf-8") as f:
            f.write(C_SOURCE)

        cmd = [cc, "-std=c11", "-Wall", "-Wextra", "-shared", "-fPIC", f"-I{include_dir}", "-o", so_path, c_path]
        if sys.platform == "darwin":
            cmd = [cc, "-std=c11", "-Wall", "-Wextra", "-bundle", "-undefined", "dynamic_lookup", f"-I{include_dir}", "-o", so_path, c_path]

        subprocess.run(cmd, check=True)

        spec = importlib.util.spec_from_file_location("plus_one", so_path)
        assert spec and spec.loader
        mod = importlib.util.module_from_spec(spec)
        spec.loader.exec_module(mod)

        # Verify normal and edge cases
        assert mod.plus_one(41) == 42
        assert mod.plus_one(-2) == -1  # Proves -1 return does not falsely trigger error!
        assert mod.plus_one(True) == 2  # bool is a subclass of int in Python!
        print(f"plus_one(41)   -> {mod.plus_one(41)}")
        print(f"plus_one(-2)   -> {mod.plus_one(-2)} (valid -1 result disambiguated via PyErr_Occurred())")
        print(f"plus_one(True) -> {mod.plus_one(True)}")

        for bad_input in ("41", 10**100):
            try:
                mod.plus_one(bad_input)
            except Exception as exc:
                print(f"plus_one({str(bad_input)[:8]!r}) -> raised {type(exc).__name__}: {exc}")


if __name__ == "__main__":
    main()
```
