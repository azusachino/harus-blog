上一篇我们看到浏览器在完成 HTTP 组包和 DNS 解析后，通过 Socket API 把数据转交给了操作系统。本篇将正式潜入操作系统内核，探索 TCP 协议栈如何管理连接、保证可靠交付，并协调收发节奏。

## 操作系统内核与协议栈的内部结构

当应用程序调用 Socket 库时，控制权转移到操作系统的网络协议栈中。操作系统协议栈的分层结构如下图所示：

![Network tcp abstract layer](/assets/images/2022/02/network-tcp-abstract-layer.webp)

从上到下，协议栈主要分为两大部分：

- **传输层**：
  - **TCP (Transmission Control Protocol)**：面向连接、提供可靠字节流交付的传输协议。负责分段、超时重传、流量控制和拥塞控制。Web 浏览、文件传输、邮件等需要确保数据完整性的应用均使用 TCP。
  - **UDP (User Datagram Protocol)**：无连接、不可靠但开销极小的轻量协议。不对数据包进行重传或顺序校正，适用于 DNS 查询、音视频流媒体等对实时性要求高、允许少量丢包的场景。
- **网络层（IP 协议与辅助协议）**：
  - **IP 协议**：负责将数据包从源节点路由并转发到目标节点。
  - **ICMP (Internet Control Message Protocol)**：用于告知网络传输过程中产生的错误（如目标不可达、TTL 超时）和控制诊断信息（如 `ping`、`traceroute`）。
  - **ARP (Address Resolution Protocol)**：在以太网局域网内，根据目标 IP 地址广播查询对应的 48 位硬件 MAC 地址。

## 套接字的本质是什么？

在很多教程中，套接字（Socket）常被比喻为“管道的开口”或“电话机”。但在操作系统内核中，**套接字既没有实体硬件，也不是一根真实的管道，而是一块记录通信控制信息的内存空间（控制块，Control Block）**。

![Network tcp socket](/assets/images/2022/02/network-tcp-socket.webp)

套接字控制块中记录的核心信息包括：

- 通信双方的标识：本地 IP、本地端口、远端目标 IP、远端目标端口。
- 状态机状态：`CLOSED`、`LISTEN`、`SYN_SENT`、`ESTABLISHED`、`FIN_WAIT_1`、`TIME_WAIT` 等。
- 传输参数：发送窗口大小、接收窗口大小、下一个期待的序号（Sequence Number）、已确认序号（ACK Number）。
- 运行时缓冲区：发送缓冲区（Send Buffer）、接收缓冲区（Receive Buffer）以及各种重传/保活定时器。

在 Windows 下可以通过 `netstat -ano`，在 Linux 下可以通过 `ss -tan` 或 `netstat -tan` 实时查看当前内核中活跃套接字的状态清单。

![Network tcp socket usage](/assets/images/2022/02/network-tcp-socket-usage.webp)

协议栈内部正是依靠查找与当前数据包匹配的套接字控制块，才知道该把收到的字节流塞进哪个应用程序的缓冲区，或者该用什么序号发出下一个数据包。

## 建立连接：三次握手

在应用程序正式发送 HTTP 数据之前，通信双方必须先在彼此内核中建立一个“连接通道”。

**连接的实质**：并非在物理链路上铺设专线，而是在双方主机的内核中各自创建并初始化套接字，互相通告彼此的初始序号（ISN）、窗口大小和支持的选项（如 MSS、窗口缩放、SACK），从而在逻辑上达成共识。

控制信息的交换依赖于 **TCP 首部**：

![Network tcp header](/assets/images/2022/02/network-tcp-header.webp)

TCP 首部中关键的标志位（Control Bits）包括：

- `SYN` (Synchronize)：用于发起连接并同步初始序号。
- `ACK` (Acknowledgment)：确认号有效，表示已成功收到期望序号之前的所有数据。
- `FIN` (Finish)：发送方完成数据发送，请求释放连接。
- `RST` (Reset)：连接出现异常或被拒绝，强制重置。

![Network tcp package](/assets/images/2022/02/network-tcp-package.webp)

### 三次握手过程

![Network tcp connect](/assets/images/2022/02/network-tcp-connect.webp)

1. **第一次握手（SYN）**：客户端协议栈创建一个随机的初始序号 $Seq = x$，将 TCP 首部的 `SYN` 置为 1，发送给服务器。此时客户端进入 `SYN_SENT` 状态。
2. **第二次握手（SYN + ACK）**：服务器收到 SYN 包后，在自己内核中创建连接控制块，分配一个随机初始序号 $Seq = y$，同时设置确认号 $Ack = x + 1$，将 `SYN` 和 `ACK` 同时置 1 返回给客户端。服务器进入 `SYN_RCVD` 状态。
3. **第三次握手（ACK）**：客户端收到服务器的 SYN+ACK 后，确认对方能够收到自己的数据，并将 $Seq = x + 1$、$Ack = y + 1$ 发送给服务器。客户端进入 `ESTABLISHED` 状态；服务器收到该 ACK 后也进入 `ESTABLISHED` 状态。

> 为什么一定是三次握手，而不是两次？
> 两次握手无法防止历史失效的连接请求突然到达服务端导致的误连接，同时也无法在双向信道上确认双方都具备正常的发送和接收能力。

## 传输数据：拆分与发送策略

连接建立完成后，应用程序调用 `write()` 将 HTTP 文本推入 TCP 发送缓冲区。此时协议栈面临两个核心权衡：**包有多大？何时发出？**

### MTU 与 MSS

协议栈并不是应用程序每写 1 个字节就立即发一个物理数据包，而是根据底层网络的容量进行打包。

![Network tcp package mtu](/assets/images/2022/02/network-tcp-package-mtu.webp)

- **MTU (Maximum Transmission Unit)**：最大传输单元，指一个网络包能容纳的最大字节数。在标准以太网中，MTU 通常为 1500 字节（包含 IP 首部、TCP 首部及载荷）。
- **MSS (Maximum Segment Size)**：最大分段大小，指除去 IP 首部（20 字节）和 TCP 首部（20 字节）之后，TCP 净荷所允许的最大长度。在标准以太网中通常为 $1500 - 20 - 20 = 1460$ 字节。

### 发送时机的权衡（长度 vs 延迟）

协议栈内部通过两个维度决定何时将缓冲区中的数据打包发出：

1. **长度优先**：当缓冲区中的待发送数据积累到接近 MSS 时，立即封装成包发出，以获得最高的网络带宽利用率。
2. **时间优先**：若应用只写了少量数据（例如按键交互），协议栈内部定时器超时后也会强制发送，防止数据滞留在缓冲区引发严重延迟。

## 可靠传输的灵魂：滑动窗口与确认应答

TCP 是如何在不可靠的 IP 网络上实现 100% 字节级可靠传输的？其基石是 **序号（Sequence Number）、确认号（ACK）与滑动窗口（Sliding Window）**。

### 序号与累计确认

- **序号（Seq）**：发送方为发送数据流中的每一个字节分配连续编号。TCP 报文中的 Seq 表示本段数据首字节在整个数据流中的偏移量。
- **确认号（Ack）**：接收方收到数据后，回传已正确接收的连续字节流的下一个期望序号。例如 Ack = 1001，意味着“字节 1 到 1000 均已完好收到，请发第 1001 字节”。
- **重传定时器**：发送方发出报文后启动定时器，若在 RTO（Retransmission TimeOut）内未收到对应的 ACK，便判定数据包丢失，自动重新发送该报文。

### 滑动窗口（Sliding Window）

如果每发一个包都必须停下来等待一个 ACK（即“停-等协议”），网络往返延迟（RTT）会使吞吐量极低。

TCP 引入了滑动窗口机制：**接收方在 TCP 首部告知发送方自己当前的空闲接收缓冲区大小（Window Size）。发送方可以在无需等待确认的情况下，连续发送窗口大小以内的数据**。

随着接收方处理并确认数据，窗口不断向前滑动，既避免了网络空等，又防止了发送方过快压垮接收方的缓冲区。

## 断开连接：四次挥手与 TIME_WAIT

数据收发完毕后，任何一方都可以主动发起断开流程。由于 TCP 是全双工通信（双方均可同时作为收发方），关闭一个方向的通道并不代表另一个方向立即停止，因此关闭需要经历四次交互：

1. **第一次挥手（FIN）**：主动方（如客户端）调用 `close()`，发送一个 `FIN=1` 的报文，表示“我不再向你发送数据了”。主动方进入 `FIN_WAIT_1` 状态。
2. **第二次挥手（ACK）**：被动方收到 FIN，回复 `ACK`，表示“我知道你不发数据了，但我可能还有未发送完的数据”。主动方收到后进入 `FIN_WAIT_2` 状态；被动方进入 `CLOSE_WAIT` 状态。
3. **第三次挥手（FIN）**：被动方将剩余数据发完后，也调用 `close()`，发送 `FIN=1` 报文给主动方，进入 `LAST_ACK` 状态。
4. **第四次挥手（ACK）**：主动方收到对方的 FIN，回复最后的 `ACK`，并进入 **`TIME_WAIT`** 状态。被动方收到该 ACK 后立即彻底关闭。

### 为什么主动关闭方必须等待 2MSL 的 TIME_WAIT？

主动方发送最后一个 ACK 后，并不会立即销毁套接字，而是强制停留 $2 \times \text{MSL}$（Maximum Segment Lifetime，报文最大生存时间，通常为 1 到 2 分钟）：

1. **保证第四次挥手的 ACK 可靠到达**：若最后的 ACK 丢失，被动方会超时重发第三次挥手的 FIN。主动方在 2MSL 内可以再次回复 ACK，确保被动方能够正常关闭。
2. **防止“迷途报文”串扰新连接**：等待 2MSL 足够让本次连接在网络中遗留的所有旧数据包彻底消亡，避免新建立的具有相同四元组的连接读入历史脏数据。

## 总结

TCP 的全部设计，都在解决一个根本矛盾：**如何基于不可靠、可能丢包乱序的 IP 底层，向上层应用提供一条严谨、有序、无差错的虚拟数据流**。

- **套接字**：内核中记录连接状态与控制信息的参数结构体。
- **三次握手**：初始化双向序号与窗口，确认双方信道通畅。
- **MSS 与滑动窗口**：在网络利用率与通信吞吐量之间取得动态平衡。
- **ACK 与超时重传**：确保丢失数据必然被补偿。
- **四次挥手与 TIME_WAIT**：从容结束全双工通信，清理网络残留。

当 TCP 完成对数据的切片与首部组装后，它会将 TCP 数据段向下传递给 **IP 模块**。下一篇，我们将观察数据是如何被装上 IP 头部与 MAC 头部，并通过网卡转换为物理电信号的。
