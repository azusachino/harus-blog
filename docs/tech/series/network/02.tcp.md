In the previous chapter, we traced how web browsers parse URLs, serialize HTTP requests, and resolve IP addresses through DNS before passing buffers to the operating system via the Socket API. Now we descend into the operating system kernel to examine how the TCP/IP protocol stack manages connection state, enforces delivery guarantees, and dynamically regulates transmission speed.

## Kernel Protocol Stack Architecture

When an application invokes socket operations, execution control transitions into the kernel's network subsystem. The protocol stack is hierarchically organized:

![Network tcp abstract layer](/assets/images/2022/02/network-tcp-abstract-layer.webp)

From top to bottom, the stack is divided into distinct operational layers:

- **Transport Layer**:
  - **TCP (Transmission Control Protocol)**: A connection-oriented transport protocol delivering a reliable, ordered, and error-checked byte stream. TCP handles packet segmentation, acknowledgment tracking, adaptive retransmission, flow control, and congestion mitigation. Applications requiring guaranteed data delivery—such as HTTP, SSH, and database connections—rely on TCP.
  - **UDP (User Datagram Protocol)**: A lightweight, connectionless datagram protocol with minimal framing overhead. It provides no retransmission, sequencing, or flow control. It is suited for delay-sensitive applications tolerant of occasional loss, such as DNS queries, real-time audio/video streaming, and VoIP.
- **Network Layer (IP and Auxiliary Protocols)**:
  - **IP (Internet Protocol)**: Routes datagrams across interconnected networks from source to destination addresses.
  - **ICMP (Internet Control Message Protocol)**: Reports operational errors (e.g., Destination Unreachable, TTL Exceeded) and diagnostic queries (e.g., `ping` Echo Requests and traceroute probes).
  - **ARP (Address Resolution Protocol)**: Maps Layer 3 IPv4 addresses to Layer 2 physical 48-bit MAC addresses within a shared Ethernet broadcast domain.

## What Is a Socket in Kernel Memory?

Introductory texts often characterize a socket metaphorically as an "endpoint pipe" or a "telephone handset." Within the kernel, however, **a socket is not a physical construct or hardware conduit, but a dedicated kernel data structure known as the Transmission Control Block (TCB)**:

![Network tcp socket](/assets/images/2022/02/network-tcp-socket.webp)

The TCB maintains the comprehensive runtime state of an active communication channel:

- **Connection 4-Tuple**: Local IP, local port, remote IP, and remote port.
- **Finite State Machine (FSM)**: Current connection state, including `CLOSED`, `LISTEN`, `SYN_SENT`, `SYN_RCVD`, `ESTABLISHED`, `FIN_WAIT_1`, `FIN_WAIT_2`, `CLOSE_WAIT`, `LAST_ACK`, and `TIME_WAIT`.
- **Sequence and Window Counters**: Next sequence number to send (`SND.NXT`), unacknowledged bytes (`SND.UNA`), advertised receive window (`RCV.WND`), and expected incoming sequence number (`RCV.NXT`).
- **Buffers and Queues**: Circular ring buffers holding pending transmit data (`Send Buffer`) and received data waiting for application consumption (`Receive Buffer`), along with retransmission queues.
- **Timers**: Retransmission Timeout (RTO) timer, Keepalive timer, and the `TIME_WAIT` (2MSL) timer.

On Linux hosts, active kernel sockets can be inspected using `ss -tan` or `netstat -tan`:

![Network tcp socket usage](/assets/images/2022/02/network-tcp-socket-usage.webp)

When an inbound packet arrives from the network interface driver, the kernel extracts its header tuple, locates the matching socket control block via an internal hash table, and commits the payload bytes to that socket's receive buffer.

## Connection Establishment: The Three-Way Handshake

Before user data can traverse the network, the client and server must coordinate their protocol parameters and establish mutual synchronization.

**The Meaning of a Connection**: A TCP connection does not reserve dedicated physical circuitry. Rather, it represents synchronized state across two remote operating systems—exchanging initial sequence numbers (ISNs), verifying bidirectional reachability, and agreeing on protocol parameters such as MSS and window scale factors.

These control parameters are negotiated within the **TCP Header**:

![Network tcp header](/assets/images/2022/02/network-tcp-header.webp)

Key control flags include:

- `SYN` (Synchronize): Signals connection initiation and synchronizes sequence numbers.
- `ACK` (Acknowledgment): Validates the acknowledgment number field, confirming receipt of prior segments.
- `FIN` (Finish): Informs the remote peer that the sender has finished transmitting data.
- `RST` (Reset): Abruptly terminates an invalid or rejected connection.

![Network tcp package](/assets/images/2022/02/network-tcp-package.webp)

### The Handshake Sequence

![Network tcp connect](/assets/images/2022/02/network-tcp-connect.webp)

1. **Step 1 (SYN)**: The client generates a pseudo-random initial sequence number $Seq = x$, sets the `SYN` flag to 1, and transmits the segment to the server. The client transitions to `SYN_SENT`.
2. **Step 2 (SYN + ACK)**: Upon receiving the SYN, the server allocates state resources, selects its own initial sequence number $Seq = y$, sets $Ack = x + 1$, and responds with both `SYN` and `ACK` flags asserted. The server transitions to `SYN_RCVD`.
3. **Step 3 (ACK)**: The client receives the server's segment, sets $Seq = x + 1$ and $Ack = y + 1$, and transmits an `ACK` segment back to the server. The client transitions to `ESTABLISHED`. Upon receiving this acknowledgment, the server also enters `ESTABLISHED`. Both endpoints can now exchange data payloads.

> **Why are three steps necessary instead of two?**
> A two-way handshake cannot guarantee bidirectional channel integrity. In an asynchronous packet network with non-zero latency, delayed or duplicated historical SYN packets could reach the server long after an original session has died. Under a two-way model, the server would open a phantom connection and allocate resources without confirmation that the client is actually active and expecting that session. Furthermore, both directions require explicit acknowledgment of their initial sequence numbers.

## Data Transmission: Segmentation and Buffer Scheduling

Once the connection is established, the application invokes `write()` or `send()` to push HTTP data into the TCP send buffer. The protocol stack must now resolve two fundamental engineering trade-offs: **how large should each segment be, and when should it be transmitted?**

### MTU and MSS

Network cards cannot transmit unbounded byte streams in a single burst. Data must be divided into discrete segments compatible with physical link constraints:

![Network tcp package mtu](/assets/images/2022/02/network-tcp-package-mtu.webp)

- **MTU (Maximum Transmission Unit)**: The maximum frame size, in bytes, that a physical link layer can transfer. For standard Ethernet, the MTU is 1500 bytes (encompassing IP headers, TCP headers, and payload).
- **MSS (Maximum Segment Size)**: The maximum allowable TCP payload per segment, excluding transport and network headers. On standard Ethernet networks:
  $$\text{MSS} = \text{MTU} - 20(\text{IPv4 Header}) - 20(\text{TCP Header}) = 1460\text{ bytes}$$

### Transmission Timing: Bandwidth Efficiency vs. Latency

The kernel protocol stack balances two competing objectives when scheduling transmissions:

1. **Throughput-Oriented (Segment Accumulation)**: Buffering data until a full MSS segment can be dispatched, maximizing the payload-to-header efficiency ratio.
2. **Latency-Oriented (Timer-Driven Flushing)**: If an application writes small or infrequent payloads (e.g., interactive terminal keystrokes), internal push timers flush the buffer regardless of segment size to avoid arbitrary interactive delays. Algorithms like Nagle's algorithm (`TCP_NODELAY` disables it) explicitly regulate this interaction with delayed ACKs.

## The Foundation of Reliability: Sliding Windows and Acknowledgments

TCP creates an illusion of a 100% reliable, sequential pipe over an uncoordinated, lossy IP network through three interconnected mechanisms: **Sequence Numbers, Cumulative ACKs, and the Sliding Window**.

### Sequence Numbers and Cumulative Acknowledgments

- **Sequence Number (Seq)**: TCP numbers every single byte in the data stream sequentially. The `Seq` field in each header indicates the offset of the first data byte carried in that segment.
- **Acknowledgment Number (Ack)**: The receiving peer returns the sequence number of the next expected byte. An `Ack = 1001` communicates: *"Bytes 1 through 1000 have been successfully received and validated; please send byte 1001 onwards."*
- **Retransmission Timeout (RTO)**: Whenever a segment is dispatched, the sender starts a retransmission timer. If an acknowledgment is not received prior to timeout expiration, the segment is assumed lost and retransmitted. Modern stacks calculate dynamic RTO values derived from Smoothed Round-Trip Times (SRTT) and variance estimators.

### The Sliding Window

If each packet required a discrete round-trip wait before sending the next ("stop-and-wait"), throughput would degrade catastrophically over high-latency paths:

$$\text{Throughput} \approx \frac{\text{Packet Size}}{\text{RTT}}$$

TCP overcomes this through the **Sliding Window**:

- The receiver advertises its available buffer capacity in the `Window Size` header field (`Receive Window`, or `rwnd`).
- The sender is permitted to continuously transmit segments up to the advertised window limit without pausing for intermediate ACKs.
- As the receiver acknowledges incoming bytes and application processes consume buffer contents, the window edges slide forward, achieving continuous transmission at high bandwidth-delay products (BDP).

## Connection Termination: Four-Way Teardown and TIME_WAIT

Because TCP operates as a full-duplex protocol, transmission in each direction is managed independently. Terminating data flow in one direction does not imply that the reverse channel is ready to close. Consequently, termination requires four distinct steps:

1. **First Step (FIN)**: An endpoint (typically the client) calls `close()`, transmitting a segment with `FIN=1`. This informs the peer: *"I have no further data to send."* The active closer transitions to `FIN_WAIT_1`.
2. **Second Step (ACK)**: The passive closer receives the FIN, acknowledges it with `ACK`, and enters `CLOSE_WAIT`. The active closer transitions to `FIN_WAIT_2`. The passive peer may continue sending remaining queued data.
3. **Third Step (FIN)**: Once the passive peer finishes sending its own data, its application invokes `close()`, dispatching a segment with `FIN=1` and entering `LAST_ACK`.
4. **Fourth Step (ACK)**: The active closer receives the remote FIN, sends a final `ACK`, and enters the **`TIME_WAIT`** state. Upon receiving the final ACK, the passive closer transitions immediately to `CLOSED`.

### Why Must the Active Closer Wait 2MSL in TIME_WAIT?

The active closer does not instantly delete its socket upon sending the final ACK. Instead, it enters `TIME_WAIT` for a duration of $2 \times \text{MSL}$ (Maximum Segment Lifetime, typically 60 to 120 seconds in modern OS configurations):

1. **Guaranteed Delivery of the Final ACK**: If the client's final ACK segment is lost in transit, the server will time out and retransmit its step-3 `FIN`. If the client had immediately destroyed its socket, it would respond to the retransmitted FIN with an erroneous `RST`. Remaining in `TIME_WAIT` allows the client to re-acknowledge redundant FIN segments and let the peer terminate gracefully.
2. **Preventing Orphan Segment Contamination**: Over a wide-area network, old duplicated segments can be delayed by dynamic routing anomalies. Waiting 2MSL guarantees that all transit packets associated with the historical 4-tuple expire and disappear from the network before a new connection reuses the identical port tuple.

## Hands-On Kernel Inspection: Observing Live TCP State & Control Blocks

On Linux, you can inspect the kernel's in-memory Transmission Control Block (TCB) parameters—including negotiated MSS, window scaling shifts, congestion control algorithm (`bbr` or `cubic`), congestion window (`cwnd`), and smoothed RTT—using `ss -ti`:

```bash
$ ss -ti state established '( dport = :443 )'
State      Recv-Q Send-Q      Local Address:Port          Peer Address:Port
ESTAB      0      0          192.168.1.100:54328        93.184.216.34:https
     cubic wscale:7,7 rto:204 rtt:3.412/0.481 ato:40 mss:1460 pmtu:1500
     rcvmss:1460 advmss:1460 cwnd:10 bytes_sent:1842 bytes_acked:1843
      bytes_received:45120 segs_out:14 segs_in:38 send 34.2Mbps lastsnd:120
```

- **`wscale:7,7`**: Both endpoints negotiated a TCP Window Scale shift of $2^7 = 128$, allowing the 16-bit window header to advertise up to $65,535 \times 128 \approx 8\text{ MiB}$ of receive buffer.
- **`mss:1460 pmtu:1500`**: Confirmed a 1,500-byte Ethernet Path MTU minus 20 bytes of IPv4 header and 20 bytes of TCP header.
- **`rtt:3.412/0.481 rto:204`**: The kernel measured a smoothed Round-Trip Time of $3.412\text{ ms}$ (variance $0.481\text{ ms}$) and computed a dynamic Retransmission Timeout (`rto`) of $204\text{ ms}$.

## Summary

The entire architecture of TCP revolves around a fundamental operational challenge: **providing an ordered, error-free, and flow-controlled virtual byte stream atop an inherently lossy, unordered, and packet-switched IP network**.

- **Sockets**: In-kernel Transmission Control Blocks tracking state, sequence offsets, and buffer capacities.
- **Three-Way Handshake**: Bidirectional sequence initialization, option negotiation, and channel validation.
- **MSS and Sliding Window**: High-throughput streaming governed by receiver buffer limits and dynamic congestion control.
- **Cumulative ACKs and Retransmission**: Guaranteeing error-free delivery despite dropped packets.
- **Four-Way Handshake and TIME_WAIT**: Coordinated full-duplex shutdown safeguarding network sanity.

Once TCP packages data segments with transport headers, it passes the resulting units down to the **IP module**. In the next chapter, we will follow the packet as it acquires Layer 3 IP and Layer 2 Ethernet headers, resolves hardware MAC addresses, and is converted into physical electrical signals by the network interface card.
