By typing a URL into a browser address bar and hitting Enter, we embark on the first leg of our journey across computer networking: understanding how application-layer software interprets human intent, constructs structured network messages, and resolves network addresses before dispatching bytes onto the wire.

## Before you start

This series is for programmers who call HTTP APIs every day but have never followed a request below the library call. The chapters build on each other and trace one web request from the browser to the other side of the world.

When you type `https://example.com/index.html` and press Enter, a lot happens before any page shows. The browser splits the address into pieces, looks up the server's numeric address, builds a text request, and hands it to the operating system to send. This chapter covers those first steps.

As a tiny example, the request a browser builds is just text: a first line such as `GET /index.html HTTP/1.1`, followed by header lines like `Host: example.com`. The server answers with text in the same shape. You need only basic command-line familiarity to follow along.

Terms used in this chapter:

- **URL**: the address of a resource, made of a scheme (`https`), a host and a path.
- **HTTP**: the request and response text protocol that browsers and web servers speak.
- **Header**: a `Name: value` line in an HTTP message carrying metadata.
- **DNS**: the system that translates hostnames like `example.com` into IP addresses.
- **Resolver**: the program or server that performs a DNS lookup on your behalf.
- **IP address**: the numeric address of a machine on a network.
- **Socket**: the operating system's handle for a network connection, which programs read and write.
- **Protocol stack**: the layered operating-system code that turns application data into network packets.

## Generating HTTP Requests via the Browser

The process begins when a user enters a resource address into the navigation bar—for example, `https://azusachino.com/tech/boring-kubernetes/`.

Two fundamental addressing concepts govern this entry:

- **URL (Uniform Resource Locator)**: Specifies the protocol scheme used to access a resource, the target server hostname or IP address, and the resource's relative path on that host.
- **URI (Uniform Resource Identifier)**: The broader superset representing any named resource. A URL is a specific type of URI that also identifies the access mechanism. The path `/tech/boring-kubernetes/` supplied in an HTTP request line represents the relative URI identifying the target resource.

### Parsing the URL

The browser first tokenizes the URL string, splitting it into its constituent components: the access scheme, server hostname, optional port number (defaulting to standard port 80 for HTTP or 443 for HTTPS when omitted), and resource path:

![Network http elements](/assets/images/2022/02/network-http-elements.webp)

Based on the scheme, the browser invokes the appropriate dispatch logic. While `http:` and `https:` dominate web traffic, browsers also handle schemes such as `file:` (reading files from local persistent storage), and `mailto:` (invoking the operating system's default email client).

### Constructing the HTTP Request Message

Once the target host and path are isolated, the browser serializes an HTTP message conforming to the protocol specification.

The HTTP protocol follows a classic client-server request-response exchange model:

1. **Client Request**: The client dispatches an operational directive specifying which action to perform on a given resource (HTTP Method + Target URI).
2. **Server Response**: The server processes the directive, returns a numeric status code indicating success or error, and delivers the corresponding payload in the message body.

#### Request and Response Structure

Under HTTP/1.1, messages are transmitted as plaintext streams divided into three primary segments:

- **Start Line**: A request line containing the method, request URI, and protocol version (e.g., `GET /index.html HTTP/1.1`), or a status line containing the protocol version, numeric status code, and reason phrase (e.g., `HTTP/1.1 200 OK`).
- **Headers**: Multiple lines formatted as `Field-Name: Value` key-value pairs, negotiating content encodings, cache directives, authentication tokens, connection lifetimes, and cookies.
- **Message Body**: Separated from the headers by an empty line (`\r\n\r\n`), carrying the actual request payload or server response data.

![Network http request](/assets/images/2022/02/network-http-request.webp)

![Network http response](/assets/images/2022/02/network-http-response.webp)

#### Standard HTTP Methods

HTTP defines standard verbs expressing semantics for resource manipulation:

![Network http methods](/assets/images/2022/02/network-http-methods.webp)

- `GET`: Retrieves the specified resource representation. By specification, `GET` operations must be both safe (read-only without server-side state modification) and idempotent (repeated identical calls yield the same state).
- `POST`: Submits an entity payload to the specified resource, frequently triggering server-side mutations or side effects.
- `PUT`: Replaces the current state of the target resource with the uploaded payload, guaranteeing idempotency.
- `DELETE`: Deletes the resource identified by the URI.
- `HEAD`: Identical to `GET` but instructs the server to omit the response body, making it ideal for checking resource existence, caching headers, or content length without transferring bulk data.

## Resolving Hostnames via the Domain Name System (DNS)

After serializing the HTTP message into memory, the browser cannot immediately transmit plaintext across the network. Lower-layer TCP/IP routing relies on fixed-width numeric **IP addresses**.

Why doesn't the internet route packets using domain names directly? Domain names have variable lengths and arbitrary hierarchical depth. Inspecting variable-length string tables at wire speed across core hardware routers would impose unsustainable memory and processing overhead. In contrast, IP addresses have fixed bit widths (32 bits for IPv4, 128 bits for IPv6), enabling high-speed binary lookups and hardware-accelerated routing tables.

### IP Addresses and Subnet Masks

An IPv4 address consists of 4 bytes (32 bits), commonly written in dot-decimal notation (e.g., `192.0.2.1`):

![Network http ip](/assets/images/2022/02/network-http-ip.webp)

Logically, every IP address is partitioned into two segments:

- **Network Identifier**: Identifies the specific subnet or network domain where the host resides.
- **Host Identifier**: Identifies the individual network interface within that subnet.

Subnet masks or CIDR prefix notation (such as `/24`) delineate the boundary between the network and host portions. Hosts sharing the same network prefix communicate directly across Layer 2 data links, whereas cross-subnet communications must be routed through an intermediary gateway.

### The Resolver and Operating System Sockets

A browser traditionally delegates address resolution to the host operating system's standard library resolver (Chromium can also use its own built-in resolver or DNS-over-HTTPS).

In POSIX environments, the historic lookup interface was `gethostbyname`, superseded by modern, IPv6-ready `getaddrinfo`:

```c
#include <stdio.h>
#include <stdlib.h>
#include <netdb.h>
#include <arpa/inet.h>

int main(int argc, char *argv[])
{
    struct addrinfo hints = {0};
    struct addrinfo *res = NULL;

    hints.ai_family = AF_UNSPEC;     // Support both IPv4 and IPv6
    hints.ai_socktype = SOCK_STREAM; // TCP stream

    int status = getaddrinfo("azusachino.com", "443", &hints, &res);
    if (status != 0) {
        fprintf(stderr, "getaddrinfo: %s\n", gai_strerror(status));
        return 1;
    }

    for (struct addrinfo *p = res; p != NULL; p = p->ai_next) {
        void *addr;
        char ipstr[INET6_ADDRSTRLEN];

        if (p->ai_family == AF_INET) {
            struct sockaddr_in *ipv4 = (struct sockaddr_in *)p->ai_addr;
            addr = &(ipv4->sin_addr);
        } else {
            struct sockaddr_in6 *ipv6 = (struct sockaddr_in6 *)p->ai_addr;
            addr = &(ipv6->sin6_addr);
        }

        inet_ntop(p->ai_family, addr, ipstr, sizeof(ipstr));
        printf("Resolved address: %s\n", ipstr);
    }

    freeaddrinfo(res);
    return 0;
}
```

When invoked, the resolver constructs a binary DNS query datagram and delegates transmission to the operating system's kernel protocol stack, targeting the locally configured DNS recursive resolver.

### Hierarchical DNS Resolution

The global domain namespace is organized as an inverted tree:

![Network http dns resolve](/assets/images/2022/02/network-http-dns-resolve.webp)

Rather than maintaining a massive centralized database, DNS resolves names through an iterative, distributed hierarchy:

![Network http dns search](/assets/images/2022/02/network-http-dns-search.webp)

1. **Local DNS Recursive Resolver**: The client queries the ISP or local recursive resolver (such as `1.1.1.1` or `8.8.8.8`). If the answer is cached, it returns immediately. Otherwise, it initiates iterative lookups.
2. **Root Name Servers**: The resolver contacts the root servers governing the domain tree root (`.`). The global root infrastructure comprises 13 logical service identities distributed globally across well over a thousand Anycast instances. The root server returns the referral NS records pointing to the relevant Top-Level Domain (TLD) servers.
3. **TLD Name Servers**: The resolver queries the TLD servers governing `.com`. The TLD server returns the authoritative nameservers managing the target second-level domain (e.g., `azusachino.com`).
4. **Authoritative Name Servers**: The resolver queries the domain's authoritative nameserver for `A` (IPv4) or `AAAA` (IPv6) records.
5. **Answer Delivery & Caching**: The authoritative server returns the final IP mapping. The recursive resolver caches the record according to its TTL (Time to Live) and forwards the result back to the host operating system.

## Delegating Transmission to the Protocol Stack

With the destination IP address resolved and the formatted HTTP request stored in memory, the browser's application-layer responsibilities draw to a close. To transmit data onto the physical network, the application invokes the operating system's socket API, crossing the boundary into kernel space:

![Network http socket](/assets/images/2022/02/network-http-socket.webp)

In standard POSIX socket programming, transmission proceeds through four sequential phases:

1. **Create Socket (`socket`)**: The application requests an endpoint handle from the kernel, allocating a file descriptor associated with a protocol family (e.g., `AF_INET`) and socket type (`SOCK_STREAM` for TCP).
2. **Establish Connection (`connect`)**: The application supplies the destination IP address and port number. The kernel initiates a TCP three-way handshake with the remote host.
3. **Transfer Data (`send` / `recv`)**: Once established, the browser writes HTTP request bytes into the kernel's transmission buffer via `write` or `send`. It then enters a blocking or event-driven read loop (`read` or `recv`) awaiting the server's HTTP response.
4. **Terminate Connection (`close`)**: Once data exchange is complete, either endpoint issues `close()`, initiating the four-way TCP teardown sequence and reclaiming kernel resources.

## Summary

The first phase of the networking lifecycle converts human-readable intentions into machine-executable network messages:

- **The browser structures application intent**: Tokenizing URLs and serializing headers into standardized HTTP protocol messages.
- **DNS provides distributed name-to-address mapping**: Resolving arbitrary domain labels into routable 32-bit or 128-bit IP coordinates via an Anycast-backed hierarchical tree.
- **The socket API bridges userland and kernel**: Handing message buffers and destination endpoints to the operating system's TCP/IP stack.

In the next chapter, we will venture inside the operating system kernel to examine how the TCP protocol establishes reliable, ordered, and flow-controlled virtual byte streams across an inherently unreliable packet network.
