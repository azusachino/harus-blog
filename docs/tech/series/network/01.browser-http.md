## 整体预览

从浏览器敲下回车键开始，旅程的第一站发生在浏览器内部：**解析 URL、生成 HTTP 请求消息，并通过 DNS 获取目标服务器的 IP 地址**。

## 通过浏览器生成 HTTP 请求消息

第一步是在浏览器地址栏中输入网址，例如 `https://azusachino.com/tech/k3s-migration/`。

这里涉及两个基础概念：

- **URL (Uniform Resource Locator)**：统一资源定位符，指明了资源的访问协议、服务器主机名和资源在服务器上的相对路径。
- **URI (Uniform Resource Identifier)**：统一资源标志符，范围更广，URL 是 URI 的子集。通常在 HTTP 请求行中填写的 `/tech/k3s-migration/` 即为请求资源的相对 URI。

### 解析 URL

浏览器的第一项工作是对 URL 字符串进行词法拆解，提取出访问协议（Scheme）、服务器域名（Host）、端口号（Port，若未显式指定则依据协议使用默认端口，如 HTTP 80、HTTPS 443）以及文件路径（Path）。

![Network http elements](/assets/images/2022/02/network-http-elements.webp)

根据 Scheme 的不同，浏览器会选择不同的处理逻辑。除了最常用的 `http:` 与 `https:` 外，浏览器还天然支持 `ftp:`、`file:`（读取本地磁盘文件）以及 `mailto:`（调起本地邮件客户端）等。

### 组装 HTTP 请求

拆解出目标与路径后，浏览器便着手格式化生成符合 HTTP 规范的文本请求。

HTTP 协议基于客户端/服务端的“请求-响应”范式：

1. **客户端请求**：客户端发出一条操作指令，说明希望对服务器上的哪个资源执行什么操作（请求方法 Method + 资源路径 URI）。
2. **服务端响应**：服务端根据指令处理，返回操作状态码（Status Code）以及对应的数据负载（Body）。

#### HTTP 请求与响应报文结构

HTTP 协议是纯文本协议（在 HTTP/1.1 中），消息主要由三部分构成：

- **起始行（Request / Status Line）**：请求行包含方法、URI 和协议版本；响应行包含协议版本、状态码及原因短语。
- **头部字段（Headers）**：由多行 `Key: Value` 键值对构成，用于控制缓存、协商内容类型、传递 Cookie 及鉴权信息。
- **消息主体（Body）**：通过一个空行（`\r\n\r\n`）与头部隔开，存放实际的请求负载或响应内容。

![Network http request](/assets/images/2022/02/network-http-request.webp)

![Network http response](/assets/images/2022/02/network-http-response.webp)

#### 常见 HTTP 方法

HTTP 定义了一组标准谓词来表达对资源的操作语义：

![Network http methods](/assets/images/2022/02/network-http-methods.webp)

- `GET`：获取指定资源，具有安全（Safe）与幂等（Idempotent）特性。
- `POST`：向指定资源提交数据，通常引起服务端状态变化。
- `PUT`：全量替换目标资源，具幂等性。
- `DELETE`：删除指定资源。
- `HEAD`：获取与 GET 相同的响应头，但不返回响应体，常用于探测资源元数据。

## 通过 DNS 服务器查询 Web 服务器的 IP 地址

生成 HTTP 请求消息后，浏览器并不能直接将字符串发送到网络上。在 TCP/IP 体系中，网络底层的寻址依赖于 **IP 地址**。

为什么不直接用域名在网络设备间寻址？因为域名长度不固定、层级复杂，路由器若要在转发表中为变长字符串进行线速查找，硬件成本和查表开销将不可接受。而 IP 地址具有固定长度（IPv4 为 32 位，IPv6 为 128 位），便于硬件高效比对和路由。

### IP 地址与子网掩码

IPv4 地址由 4 个字节（32 位）组成，通常采用点分十进制表示（如 `192.0.2.1`）。

![Network http ip](/assets/images/2022/02/network-http-ip.webp)

IP 地址在逻辑上划分为两部分：

- **网络号（Network Part）**：标识设备所在的子网。
- **主机号（Host Part）**：标识该子网内具体的网络接口。

子网掩码（Netmask）或 CIDR 前缀（如 `/24`）用于区分网络号与主机号的边界。不同子网的主机通信必须跨越路由器，而同子网的主机可通过二层网络直接通信。

### 解析器（Resolver）与 Socket 库

浏览器自身并不内置完整的 DNS 客户端协议栈，而是通过操作系统提供的标准库（通常称为解析器 Resolver）发起解析请求。

在 POSIX 系统中，最经典的系统调用即是 `gethostbyname`（现代应用更推荐使用支持 IPv6 的 `getaddrinfo`）：

```c
#include <stdio.h>
#include <netdb.h>

int main(int argc, char *argv[])
{
    struct hostent *lh = gethostbyname("azusachino.com");
    if (lh)
        puts(lh->h_name);
    else
        herror("gethostbyname");

    return 0;
}
```

调用该函数时，控制权转移到操作系统的解析器代码中。解析器组装一个 DNS 查询包，委托操作系统内核协议栈发送给本地网络配置的首选 DNS 服务器。

### DNS 查询流程与层级接力

全世界的域名空间按照树状层次结构组织：

![Network http dns resolve](/assets/images/2022/02/network-http-dns-resolve.webp)

DNS 服务器并不需要在单台机器上保存全网所有记录，而是通过**层层接力（迭代查询）**完成定位：

![Network http dns search](/assets/images/2022/02/network-http-dns-search.webp)

1. **本地 DNS 服务器（Local DNS）**：客户端将查询发往运营商或本地配置的 DNS 服务器（递归查询）。
2. **根域 DNS 服务器（Root DNS）**：管理顶级域（TLD），如 `.com`、`.cn`、`.org`。全世界分布有 13 个逻辑根域名体系（通过 Anycast 遍布全球镜像）。本地 DNS 首先向根域名服务器询问。
3. **顶级域 DNS 服务器（TLD DNS）**：根域名服务器返回管理 `.com` 的顶级域服务器 IP。本地 DNS 接着向 `.com` 服务器发起查询。
4. **权威 DNS 服务器（Authoritative DNS）**：`.com` 服务器返回管理 `azusachino.com` 的权威 DNS 服务器 IP。
5. **获取 A/AAAA 记录**：本地 DNS 向权威 DNS 发起查询，最终得到目标主机的 IP 地址，将其缓存并返回给客户端。

## 委托协议栈发送消息

拿到了服务器的 IP 地址，同时组装好了 HTTP 请求内容，浏览器的纯应用层工作便告一段落。此时，它必须调用操作系统的网络 API（Socket 抽象接口），将数据正式委托给系统内核的 TCP/IP 协议栈：

![Network http socket](/assets/images/2022/02/network-http-socket.webp)

在 Unix/POSIX 体系中，委托过程遵循经典的四步流程：

1. **创建套接字（Socket）**：调用 `socket()` 系统调用，向内核申请创建通信端点，获取一个文件描述符。
2. **连接服务器（Connect）**：调用 `connect()`，传入目标服务器的 IP 地址与端口号，内核协议栈开始与远端协商建立 TCP 连接（三次握手）。
3. **收发数据（Write / Read）**：连接建立后，调用 `write()` 或 `send()` 将 HTTP 文本写入发送缓冲区；随后调用 `read()` 或 `recv()` 等待接收服务器的 HTTP 响应报文。
4. **断开连接（Close）**：数据交互完毕后，调用 `close()` 发起 TCP 四次挥手，销毁套接字并释放资源。

## 总结

第一章的核心脉络非常清晰：**将人类可读的文字操作转化为计算机网络可执行的二进制指令**。

- 浏览器负责**业务逻辑与表达**：解析 URL，将请求内容打包为标准的 HTTP 协议报文。
- DNS 负责**名字到位置的映射**：利用树状分布式数据库把域名转化为 32 位/128 位的 IP 地址。
- Socket 接口则是**应用层与内核协议栈的分水岭**：浏览器完成前序准备后，将数据指针和目标 IP/端口转交内核，正式跨入操作系统底层的网络协议世界。

下一站，我们将进入操作系统内核，观察 TCP 协议栈如何为不可靠的网络赋予确定性与可靠性。
