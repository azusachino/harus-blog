Enterprise cloud networking has evolved far beyond calculating CIDR blocks and writing static route tables. In the **AWS Certified Solutions Architect - Professional (SAP-C03)** exam, network architecture spans two critical dimensions: the **physical transit backbone** (hybrid connectivity across data centers and global regions) and the **application-layer service mesh** (cross-account microservice discovery without IP collision).

This chapter addresses the end-to-end network hierarchy: designing high-availability hybrid links with AWS Direct Connect and automated BGP failover, orchestrating multi-region enterprise networks with **AWS Cloud WAN**, enforcing deep packet inspection via Gateway Load Balancer (GWLB), and leveraging **Amazon VPC Lattice** to eliminate cross-VPC networking overhead.

---

## 1. Enterprise Hybrid Connectivity: AWS Direct Connect & Automated BGP Failover

When enterprise on-premises data centers connect to AWS, scenarios frequently specify requirements for **dedicated bandwidth, deterministic low latency, and automated sub-minute failover**.

### Direct Connect Fundamentals

- **Dedicated vs Hosted Connections**:
  - *Dedicated Connection*: Physical ports (1 Gbps, 10 Gbps, 100 Gbps) assigned directly to the customer, supporting **MACsec** (IEEE 802.1AE) hardware encryption at Layer 2.
  - *Hosted Connection*: Provisioned through an AWS Direct Connect Partner in fractional capacities (50 Mbps up to 10 Gbps); does not support MACsec directly.
- **Direct Connect Gateway (DXGW)**:
  A globally available routing resource. A single DXGW can associate with multiple Private Virtual Interfaces (Private VIFs) and connect to Transit Gateways across multiple AWS regions (excluding China).

### Active/Passive and Active/Active Failover Topology

In high-stakes scenarios, the architect must choose how to configure redundant links:

```text
On-Premises Data Center
 ├── Primary Path: 10 Gbps Direct Connect (Dedicated Port)
 │    └── BGP Attributes: Local Preference = 200 (Highest), AS-Path = [65000]
 └── Backup Path: Secondary Direct Connect OR IPSec Site-to-Site VPN
      └── BGP Attributes: Local Preference = 100, AS-Path Prepending = [65000, 65000, 65000]
```

### BGP Routing Policy Control

1. **Outbound Traffic (AWS to On-Premises)**:
   - AWS respects **BGP Local Preference** advertised from the customer router. Advertise BGP community `7224:7300` (High) on the primary link and `7224:7100` (Low) on the secondary link.
   - If Local Preference is omitted, AWS evaluates the shortest **AS-Path**. Prepending your own AS number multiple times on the backup link forces AWS to select the primary path.
2. **Inbound Traffic (On-Premises to AWS)**:
   - Controlled by the customer router using internal BGP (iBGP) Local Preference settings.
3. **Bidirectional Forwarding Detection (BFD)**:
   - Standard BGP keep-alive intervals take up to 90 seconds to detect a link failure.
   - Enable **BFD** on the Direct Connect VIF to achieve sub-second link failure detection and trigger instantaneous routing convergence.

## 2. Inter-VPC Evolution: Peering vs Transit Gateway vs AWS Cloud WAN

As organizations expand across dozens of VPCs and multiple global regions, managing network connectivity requires selecting the right aggregation abstraction:

| Dimension | VPC Peering | AWS Transit Gateway (TGW) | AWS Cloud WAN (SAP-C03 Core) |
| :--- | :--- | :--- | :--- |
| **Topology** | Full Mesh (Point-to-Point) | Regional Hub-and-Spoke | Global Core Network (Policy-Driven SD-WAN) |
| **Transitive Routing?** | **No** (VPC A cannot reach C via B) | **Yes** (Hub routes across all attachments) | **Yes** (Built-in global inter-region core) |
| **Multi-Region Peering** | Supported point-to-point | Requires manual TGW-to-TGW peering attachments and route synchronization | **Native**: Centralized Core Network Policy (CNP) defines global segments automatically |
| **Overlapping CIDRs** | Not supported | Not supported without NAT appliances | Supported via private segment boundaries |
| **Hourly & Data Cost** | **Zero hourly cost**; only cross-AZ/cross-region data transfer fees | Hourly fee per attachment + data processing fees ($0.02/GB) | Core network hourly fee + attachment hourly fee + data transfer fees |
| **When to Choose** | High-throughput, latency-critical 1-to-1 links in the same region | Regional aggregation, on-prem VPN/DX termination, multicast workloads | Global enterprise multi-region network with uniform routing segments |

### Deep Dive: AWS Cloud WAN Policy-Based Segmentation

In SAP-C03, AWS Cloud WAN replaces the tedious task of establishing mesh-peered Transit Gateways across five continents.
With Cloud WAN:

1. Define a declarative **Core Network Policy (CNP)** in JSON.
2. Define isolated **Segments** (e.g., `development`, `production`, `shared-services`).
3. Set attachment mapping rules based on AWS Resource Tags (e.g., tags with `Environment=Production` automatically attach to the `production` segment).
4. Routes are propagated and isolated across regions by the AWS-managed backbone without manual inter-region route tables.

## 3. Centralized Traffic Inspection: Gateway Load Balancer & Appliance Mode

Enterprise compliance often mandates that all outbound traffic to the internet (North-South) and all cross-VPC traffic (East-West) must pass through a cluster of third-party stateful Next-Generation Firewalls (NGFWs, such as Palo Alto, Fortinet, or Check Point).

### The Gateway Load Balancer (GWLB) Architecture

- **Layer 3 Gateway + Layer 4 Load Balancer**: Listens on all ports and protocols, forwarding raw packets to a fleet of firewall appliances.
- **GENEVE Protocol (Geneve Port 6081)**: Encapsulates original IP packets, preserving the original client source IP, destination IP, and TCP/UDP ports while injecting metadata (like VPC ID and ENI ID).
- **GWLB Endpoints (GWLBE)**: Powered by AWS PrivateLink, allowing customer VPCs to steer traffic transparently through the inspection fleet without source NAT.

### The Transit Gateway Appliance Mode Gotcha

A classic SAP scenario involves stateful firewalls failing or dropping connections during East-West inspection:

- When traffic flows from VPC A to VPC B via Transit Gateway, the request packet may enter Firewall Instance 1 in AZ-a.
- When VPC B replies, standard Transit Gateway hashing may forward the return packet to Firewall Instance 2 in AZ-b.
- Because Firewall 2 has no record of the TCP handshake state, it drops the packet (asymmetric routing failure).
- **The Solution**: Enable **Appliance Mode** on the Transit Gateway VPC attachment targeting the Inspection VPC. This forces Transit Gateway to use a bidirectional symmetrical flow hash, ensuring both request and response packets traverse the exact same firewall ENI in the same Availability Zone.

## 4. The Zero-Trust Application Networking Revolution: Amazon VPC Lattice

Even with Transit Gateway and Cloud WAN, traditional Layer 3/Layer 4 networking introduces severe enterprise friction:

- **CIDR Overlaps**: Mergers, acquisitions, and rapid team expansion inevitably produce colliding `10.0.0.0/16` IP ranges that cannot be peered.
- **Network Coupling**: Developers must request route table updates, security group CIDR allowances, and DNS peering simply to call an internal REST API.

**Amazon VPC Lattice** (a headline inclusion in SAP-C03) decouples application-layer communication from the underlying IP network:

```text
Consumer VPC (CIDR: 10.0.0.0/16)                     Provider VPC (CIDR: 10.0.0.0/16 - Overlapping!)
 ├── Client Service (EC2, ECS, Lambda, EKS)            ├── Target Service (ECS Task / ALB / Lambda)
 │    │ (Calls payments.internal via DNS)              │    │ (Receives traffic on target port)
 └── Associate with Lattice Service Network            └── Register to Lattice Target Group
                       │                                     │
                       └────────► [ Amazon VPC Lattice ] ◄───┘
                                   ├── IAM SigV4 Auth Policy
                                   ├── TLS 1.3 Encryption
                                   └── Path-based Routing
```

### Core Components of Amazon VPC Lattice

1. **Service Network**: An organizational boundary resource. VPCs and accounts associate with a Service Network to gain access to all published services.
2. **Service**: An independent software application unit. Owns a stable DNS name, listeners, and rules.
3. **Target Group**: The destination compute instances (ALBs, EC2 instances, IP targets, ECS containers, or Lambda functions).
4. **Auth Policy**: Native **IAM SigV4 authorization**. Even if two services communicate across VPCs, Lattice can enforce that requests are signed by an IAM principal belonging to a specific IAM role and contain specific HTTP methods (e.g., allow `GET /orders/*`, deny `POST /orders/*`).
5. **No Peering Required**: Consumer VPC and Provider VPC never need a VPC Peering link, Transit Gateway attachment, or shared route tables. Traffic stays entirely on the AWS hypervisor fabric.

## 6. Exam Scenarios & Deciding Vectors

| Scenario Cue | Naive / Distractor Option | Architectural Winner (SAP-C03 Vector) | Why |
| :--- | :--- | :--- | :--- |
| *"Multiple microservices in separate accounts with overlapping CIDR blocks must communicate over HTTP/HTTPS with mutual IAM authorization."* | Re-IP the secondary VPC subnets and establish a Transit Gateway with complex NAT gateways. | **Deploy Amazon VPC Lattice** and associate both VPCs with a shared Service Network. | VPC Lattice operates at Layer 7; overlapping IP addresses do not collide, and IAM Auth Policies enforce fine-grained access. |
| *"Global enterprise with 40 VPCs across 6 regions needs centralized policy-based network segmentation with minimal operational routing overhead."* | Build a full mesh of inter-region Transit Gateway peerings with manual static route tables. | **Deploy AWS Cloud WAN** with a centralized Core Network Policy (CNP) defining automated regional segments. | Cloud WAN automatically provisions and synchronizes global inter-region transit routing based on declarative policy tags. |
| *"Stateful firewall appliances in an Inspection VPC are intermittently dropping return traffic for cross-VPC packets."* | Disable stateful TCP tracking on the firewall appliances. | **Enable Appliance Mode** on the Transit Gateway attachment connecting to the Inspection VPC. | Ensures symmetrical routing so request and response packets hit the exact same firewall instance in the same AZ. |
| *"Sub-minute automatic failover required between primary Direct Connect link and secondary backup connection."* | Rely on standard BGP keep-alive and hold timers (90 seconds). | **Enable BFD (Bidirectional Forwarding Detection)** on the Direct Connect Virtual Interfaces. | BFD provides sub-second liveliness checks to trigger instantaneous failover to the backup path. |
