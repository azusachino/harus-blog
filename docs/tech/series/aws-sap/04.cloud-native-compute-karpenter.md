In modern cloud infrastructure, managing compute is no longer about sizing static virtual machines. For the **AWS Certified Solutions Architect - Professional (SAP-C03)** exam, Domain 1 accounts for **25% of the total score**, placing heavy emphasis on dynamic, workload-aware compute engines.

The exam tests whether an architect can choose cleanly between **Amazon EKS** and **Amazon ECS**, eliminate autoscaling bottlenecks with **Karpenter**, wire zero-maintenance service discovery with **ECS Service Connect**, and decouple high-throughput microservices using asynchronous serverless choreographies.

## 1. Container Engine Selection: Amazon EKS vs Amazon ECS

Choosing between Amazon Elastic Kubernetes Service (EKS) and Amazon Elastic Container Service (ECS) is a frequent scenario pivot point on the professional exam:

| Architectural Vector | Amazon ECS (AWS-Native Orchestration) | Amazon EKS (Kubernetes Standard) |
| :--- | :--- | :--- |
| **Operational Paradigm** | Simple, opinionated, deeply integrated with AWS primitives (IAM, CloudWatch, ALB) | Standard upstream Kubernetes APIs, Helm charts, CRDs, and open-source cloud-native tooling |
| **Control Plane Cost** | **Zero control plane charge** (pay only for tasks/instances) | **\$0.10/hour per cluster** (\$73/month control plane fee) |
| **Compute Launch Types** | AWS Fargate (Serverless) or EC2 instances | AWS Fargate (pod-level serverless) or EC2 nodes (via Karpenter/NodeGroups) |
| **Service Discovery** | Native AWS Cloud Map / ECS Service Connect | CoreDNS / Kubernetes Services / VPC Lattice / Istio |
| **When to Choose (Exam Vector)** | Team values minimal operations, standard microservices, zero Kubernetes cognitive overhead | Multi-cloud portability, complex stateful sets, advanced scheduling (Karpenter), or existing Helm/K8s investments |

## 2. Node Autoscaling on EKS: Cluster Autoscaler vs Karpenter

One of the most heavily emphasized modern container topics in SAP-C03 is **Karpenter**, the open-source, flexible, high-performance node autoscaler designed specifically for Kubernetes on AWS.

### The Historical Pain of Kubernetes Cluster Autoscaler (CAS)

Traditional EKS clusters relied on the upstream **Kubernetes Cluster Autoscaler (CAS)**:

- CAS is tightly coupled to **EC2 Auto Scaling Groups (ASGs)**.
- If you run mixed workloads (e.g., standard x86 CPU, Graviton ARM64, GPU-accelerated ML pods, Spot instances, high-memory nodes), you must pre-create and manage dozens of separate ASGs across multiple Availability Zones.
- When an unschedulable pod appears, CAS determines which ASG can host it and increases the ASG's `DesiredCapacity`.
- The EC2 ASG invokes EC2 launch workflows, runs standard cloud-init user data, and joins the cluster. This cycle commonly takes several minutes, which is too slow for sudden traffic spikes.

### The Karpenter Paradigm Shift

Karpenter bypasses Auto Scaling Groups completely:

1. **Workload-Aware Group-less Scheduling**: Karpenter listens directly to the Kubernetes API server for pods marked `PodScheduled=False` (Unschedulable).
2. **Dynamic JIT Bin-Packing**: It inspects the pending pods' specific resource requests (`cpu`, `memory`, `gpu`), tolerations, node selectors, and `topologySpreadConstraints`.
3. **Direct EC2 Fleet Invocations**: It calls the EC2 Fleet API directly to provision the single most cost-effective instance type that satisfies the pending pods (e.g., an instant `c7g.2xlarge` Spot instance). Nodes typically register in about a minute or less.
4. **Automated Node Consolidation & De-provisioning**: When workloads scale down, Karpenter actively identifies underutilized nodes, cordons and drains them, and consolidates remaining pods onto smaller or fewer instances to minimize waste.

### Declarative Karpenter Blueprint: `NodePool` & `EC2NodeClass`

In Karpenter v1+, cluster capacity governance is split into two Custom Resource Definitions (CRDs):

- **`NodePool`**: Defines workload scheduling constraints (Spot vs. On-Demand, CPU architectures `amd64`/`arm64`, instance families, disruption budgets, and consolidation policies).
- **`EC2NodeClass`**: Defines AWS infrastructure specifics (AMI family, subnet/security group discovery tags, and IAM node role).

```yaml
apiVersion: karpenter.sh/v1
kind: NodePool
metadata:
  name: general-compute-spot-and-graviton
spec:
  template:
    spec:
      nodeClassRef:
        group: karpenter.k8s.aws
        kind: EC2NodeClass
        name: default-al2023
      requirements:
        - key: kubernetes.io/arch
          operator: In
          values: ["amd64", "arm64"] # Diversify across x86_64 and AWS Graviton
        - key: karpenter.sh/capacity-type
          operator: In
          values: ["spot", "on-demand"]
        - key: karpenter.k8s.aws/instance-category
          operator: In
          values: ["c", "m", "r"]
        - key: karpenter.k8s.aws/instance-generation
          operator: Gt
          values: ["6"]
  disruption:
    consolidationPolicy: WhenEmptyOrUnderutilized
    consolidateAfter: 30s
    budgets:
      - nodes: "10%" # Never disrupt more than 10% of fleet simultaneously
  limits:
    cpu: "1000"
    memory: 4000Gi
```

## 4. Modern Pod Identity: EKS Pod Identity vs IRSA

Historically, giving Kubernetes pods access to AWS services (e.g., S3, DynamoDB) required **IAM Roles for Service Accounts (IRSA)**:

- Required creating an OpenID Connect (OIDC) identity provider per EKS cluster in IAM.
- Required writing complex IAM trust policies matching the exact OIDC issuer URL and Kubernetes service account namespace (`system:serviceaccount:<namespace>:<serviceaccount>`).
- If a cluster was destroyed and recreated, the OIDC URL changed, breaking all trust relationships.

### EKS Pod Identity (The SAP-C03 Standard)

**Amazon EKS Pod Identity** radically streamlines pod authentication:

- Deploys an EKS Pod Identity Agent DaemonSet on the worker nodes.
- You create an IAM role and establish a trust relationship with `pods.eks.amazonaws.com` (no OIDC provider needed!).
- Associate the IAM role directly to the cluster, namespace, and service account via the AWS EKS API or CLI:

  ```sh
  aws eks create-pod-identity-association \
    --cluster-name production-cluster \
    --namespace payment-service \
    --service-account payment-sa \
    --role-arn arn:aws:iam::111122223333:role/PaymentServiceRole
  ```

- The trust policy does not embed a cluster-specific OIDC issuer, so the same role can be reused across clusters without trust-policy edits during cluster migrations.

## 5. Microservice Mesh on ECS: ECS Service Connect

On Amazon ECS, connecting microservices historically required deploying an Application Load Balancer (ALB) in front of every internal service—adding cost (\$16/month per ALB plus data processing) and extra latency hops.

**Amazon ECS Service Connect** delivers native service-to-service communication:

- Injects a lightweight **Envoy proxy sidecar** directly into each ECS task.
- Integrates transparently with **AWS Cloud Map** for private namespace discovery.
- **Client-Side Load Balancing & Retries**: Requests from Service A to `orders.production` are resolved locally by Envoy, load-balanced across healthy container endpoints, and retried automatically on Layer 7 errors.
- **TLS encryption**: Optional TLS between tasks, with certificates issued through AWS Private CA, so you do not manage internal certificates yourself.
- Removes the need for an internal ALB in front of every service, which cuts cost.

## 6. Asynchronous Serverless Choreography

When designing distributed architectures, synchronous REST APIs between services create tight coupling and cascading failure modes. SAP-C03 tests your mastery of event-driven choreographies:

```text
Event Producer (API / Microservice)
       │
       ▼
[ Amazon EventBridge Event Bus ] ──► Advanced Content Filtering Rules
       │
       ├─────────────────────────┬─────────────────────────┐
       ▼                         ▼                         ▼
[ SQS FIFO Queue ]       [ AWS Lambda ]            [ Step Functions ]
 (Ordered Transactions)   (Event Transformation)    (Stateful Orchestration)
```

### Deciding Between EventBridge, SQS, and SNS

1. **Amazon EventBridge**:
   - The central **event bus router**. Best for routing events from multiple sources (SaaS applications, custom microservices, AWS service events) to multiple targets using **declarative JSON content filtering rules** (e.g., a numeric match on `detail.amount` above 1000).
   - Supports schema registry, automated dead-letter queues (DLQ), and event replay capabilities.
2. **Amazon SQS FIFO**:
   - Strictly preserves message ordering (First-In, First-Out) using `MessageGroupId`.
   - Exactly-once processing via `MessageDeduplicationId` (5-minute deduplication interval).
   - High throughput mode raises the limit to tens of thousands of messages per second with batching (quotas vary by Region).
3. **AWS Step Functions Distributed Map**:
   - Coordinates massive serverless batch processing, spawning up to 10,000 parallel executions to process millions of records in S3 (CSV, JSON, Parquet) without hitting Lambda concurrency limits.
