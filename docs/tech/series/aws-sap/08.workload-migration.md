Enterprise cloud migrations are rarely greenfield deployments. The AWS Certified Solutions Architect – Professional (SAP-C03) exam tests your ability to orchestrate multi-phased, zero-downtime workload migrations from legacy on-premises data centers, VMware private clouds, and co-located facilities to AWS. Within Domain 4, migration scenarios evaluate your command over the 7 Rs migration strategy framework, continuous block-level server replication via AWS Application Migration Service (MGN), low-downtime database transitions using AWS DMS and AWS SCT, and petabyte-scale offline data transfers.

Architects must navigate intricate operational constraints: tight maintenance cutover windows, heterogeneous database engine conversions, strict network bandwidth limitations, and regulatory data sovereignty rules.

## 1. The 7 Rs Migration Decision Framework

Selecting the optimal migration strategy balances modernization velocity, total cost of ownership (TCO), operational risk, and architectural agility.

```text
                                [Discovered On-Premises Application]
                                                  │
                   ┌──────────────────────────────┴──────────────────────────────┐
                   ▼                                                             ▼
         Business value still needed?                                  Can it be retired / retained?
         ├── No  ──► [Retire] (Decommission servers)                   ├── Retain (Keep on-prem until EOL)
         └── Yes                                                       └── Retire (Zero migration effort)
             │
             ├─ SaaS replacement available? ──► [Repurchase / Drop-and-Shop] (e.g., Salesforce, Workday)
             │
             ├─ Moving VMware VMs as-is without OS changes? ──► [Relocate] (VMware Cloud on AWS)
             │
             ├─ Need fast migration with minimal operational change?
             │  └── No code change, block-level OS lift-and-shift ──► [Rehost] (AWS MGN)
             │
             ├─ Can improve runtime without modifying core code?
             │  └── Managed DB / Containers / OS upgrade ────────► [Replatform] (RDS, ECS, EKS)
             │
             └─ Complete cloud-native re-architecting? ──────────► [Refactor / Re-architect] (Serverless, Event-Driven)
```

| Strategy | Definition | Primary Drivers | Key AWS Enablers | Typical Timeline & Risk |
| :--- | :--- | :--- | :--- | :--- |
| **Rehost (Lift-and-Shift)** | Move servers as-is at the OS/block level directly into Amazon EC2 without modifying application code or core OS configuration. | Impending data center lease termination; urgent capacity relief; legacy applications lacking source code. | AWS Application Migration Service (AWS MGN). | Weeks; lowest technical risk. |
| **Replatform (Lift-Tinker-and-Shift)** | Make targeted architectural optimizations (e.g., swapping self-managed Oracle to Amazon RDS Custom/PostgreSQL or containerizing applications) without altering core business logic. | Reduce database administration overhead; modernize OS versions; automate patching and backups. | Amazon RDS, AWS Elastic Beanstalk, Amazon ECS. | Months; moderate risk. |
| **Refactor / Re-architect** | Re-architect the application from monolithic codebases into cloud-native, microservices-oriented, or serverless topologies. | Need for extreme scalability, rapid feature deployment velocity, and elasticity. | AWS Lambda, Amazon EventBridge, Amazon DynamoDB, AWS Step Functions. | Quarters to years; highest risk and reward. |
| **Repurchase (Drop-and-Shop)** | Replace custom on-premises applications with modern Software-as-a-Service (SaaS) platforms. | Standardizing business processes (CRM, HR, ERP); retiring bespoke in-house tools. | AWS Marketplace SaaS listings. | Months; vendor-dependent. |
| **Relocate (Hypervisor Lift)** | Move existing virtual machines running on VMware vSphere directly to VMware Cloud on AWS without re-packaging or converting VMDK files. | Maintain identical IP addressing and operational tooling; avoid VM conversion time. | VMware Cloud on AWS (VMC). | Days to weeks; very low risk. |
| **Retain** | Keep applications on-premises due to legacy hardware dependencies, strict local latency requirements, or recent heavy on-premises investments. | Hybrid regulatory compliance; deprecation planned in near future. | AWS Outposts, AWS Direct Connect. | N/A (ongoing). |
| **Retire** | Decommission obsolete, redundant, or orphaned workloads identified during the discovery phase. | Reduce portfolio complexity and eliminate maintenance costs. | AWS Application Discovery Service. | Immediate. |

## 2. Server Migration Factory: AWS Application Migration Service (MGN)

**AWS Application Migration Service (AWS MGN)** is AWS's primary service for lift-and-shift server migrations, superseding the legacy CloudEndure Migration and AWS Server Migration Service (SMS).

### 2.1 Architecture and Data Flow

AWS MGN performs non-disruptive, block-level replication of physical, virtual, or cloud-based source servers into a dedicated staging area inside an AWS VPC.

```text
On-Premises / Source Environment                         AWS Staging Area VPC
┌─────────────────────────────────┐                     ┌────────────────────────────────────────┐
│  Source Server (Linux / Windows)│                     │ Staging Subnet (Low-cost resources)    │
│  ┌───────────────────────────┐  │                     │  ┌──────────────────────────────────┐  │
│  │ AWS MGN Replication Agent │  │  TLS 443 / TCP 1500 │  │ Replication Server (t3.small)    │  │
│  └─────────────┬─────────────┘  ├────────────────────►│  └────────────────┬─────────────────┘  │
│                │                │ (VPN / DX / Public) │                   ▼                    │
│                ▼                │                     │  ┌──────────────────────────────────┐  │
│        Source Disks (Block)     │                     │  │ Low-cost EBS Staging Disks       │  │
│                                 │                     │  │ (Continuous block-level sync)    │  │
└─────────────────────────────────┘                     └──┴────────────────┬─────────────────┘──┘
                                                                            │ Cutover / Test Launch
                                                                            ▼
                                                        AWS Target Production VPC
                                                        ┌────────────────────────────────────────┐
                                                        │ Target Subnet                          │
                                                        │  ┌──────────────────────────────────┐  │
                                                        │  │ Production EC2 Instance          │  │
                                                        │  │ (Configured via Launch Template) │  │
                                                        │  │ - Converted drivers & OS license │  │
                                                        │  │ - Right-sized instance type      │  │
                                                        │  └──────────────────────────────────┘  │
                                                        └────────────────────────────────────────┘
```

1. **Replication Agent Installation**: An agent installed on the source server reads blocks continuously from the local OS storage stack without requiring a reboot.
2. **Staging Subnet**: Encrypted data blocks transmit over port 1500 (using Direct Connect, VPN, or public endpoints) to lightweight EC2 Replication Servers (`t3.small`) attached to low-cost EBS staging disks.
3. **Continuous Data Protection (CDP)**: Block-level delta changes are continuously synchronized in near real-time, maintaining an RPO of seconds.
4. **Non-Disruptive Testing**: Before cutover, administrators initiate test instances. AWS MGN snapshots the staging EBS volumes and provisions fully configured test EC2 instances in an isolated target subnet using an **EC2 Launch Template**.
5. **Final Cutover**: During the planned maintenance window, the source application is stopped to prevent new writes. Once the final delta sync completes, the cutover instance is launched, DNS is switched, and the source server is decommissioned.

### 2.2 Post-Launch Actions & Modernization

AWS MGN supports automated post-launch modernizations via SSM Agent integration:

- Automatically converting commercial Windows/SQL Server licenses to AWS-provided Pay-As-You-Go licenses.
- Upgrading operating system versions during migration (for example, an automated Windows Server version upgrade).
- Installing monitoring agents (CloudWatch Agent, Systems Manager Agent) and security tooling automatically upon instance launch.

## 3. Database Migration & Conversion: AWS DMS and SCT

Migrating databases requires a distinct approach from server block replication because database engines manage in-memory caches, transaction logs, and foreign key constraints that cannot be synchronized blindly at the block level while live writes occur.

### 3.1 Heterogeneous vs Homogeneous Migrations

```text
Homogeneous (Same Engine: Oracle -> Oracle, PG -> PG)
├── Tooling: Native database utilities (Oracle Data Guard, pg_dump/logical replication) OR AWS DMS
└── Schema Conversion: None required (direct compatibility)

Heterogeneous (Cross-Engine: Oracle / SQL Server -> Aurora PostgreSQL / MySQL)
├── Tooling: AWS Schema Conversion Tool (SCT) + AWS Database Migration Service (DMS)
└── Schema Conversion: Mandatory (convert PL/SQL, stored procedures, views, indexes)
```

### 3.2 AWS Schema Conversion Tool (SCT)

When converting heterogeneous database engines (e.g., migrating an on-premises commercial Oracle or Microsoft SQL Server database to open-source Amazon Aurora PostgreSQL):

- **SCT runs locally** on a client workstation or management server.
- It parses database schema objects (DDL), functions, stored procedures, packages, and triggers.
- It generates an **Assessment Report** categorizing objects into:
  1. *Automatically convertible* (most tables, views, and standard queries).
  2. *Action items requiring manual refactoring* (proprietary PL/SQL packages, dynamic SQL, custom spatial extensions).
- SCT outputs converted DDL scripts that are applied to the target Aurora database *before* data migration commences.

### 3.3 AWS Database Migration Service (DMS) with CDC

Once schemas are created on the target database, AWS DMS handles initial data loading and continuous Change Data Capture (CDC):

```text
┌─────────────────────────────────┐                      ┌─────────────────────────────────┐
│     Source Database (Oracle)    │                      │   Target Database (Aurora PG)   │
│  ┌───────────────────────────┐  │                      │  ┌───────────────────────────┐  │
│  │ Transaction Logs / Redo   │  │                      │  │ Converted Tables / Schemas│  │
│  └─────────────┬─────────────┘  │                      │  └─────────────▲─────────────┘  │
└────────────────┼────────────────┘                      └────────────────┼────────────────┘
                 │                                                        │
                 ▼ Reads Redo Logs                                        │ Writes Transactions
┌─────────────────────────────────────────────────────────────────────────┼────────────────┐
│ AWS DMS Replication Instance (or DMS Serverless)                        │                │
│  ┌───────────────────────────────┐        ┌───────────────────────────┐ │                │
│  │ 1. Full Load Task             ├───────►│ 2. Ongoing CDC Task       ├─┘                │
│  │ (Bulk historical data dump)   │        │ (Applies transactional    │                  │
│  │                               │        │  deltas in real-time)     │                  │
│  └───────────────────────────────┘        └───────────────────────────┘                  │
└──────────────────────────────────────────────────────────────────────────────────────────┘
```

#### DMS Migration Workflow

1. **Full Load**: DMS reads existing source records and inserts them in bulk into target tables. Foreign key constraints and secondary indexes should be disabled on the target during this phase to maximize ingestion throughput.
2. **Ongoing Replication (CDC)**: DMS reads transaction logs directly (e.g., Oracle Redo Logs or SQL Server Transaction Logs) without locking application tables. It applies inserts, updates, and deletes to the target in chronological order.
3. **Cutover**: Once replication lag drops to zero, the source application is set to read-only, final transactions synchronize, connection strings are repointed to the Aurora cluster endpoint, and write traffic resumes on AWS.

#### DMS Serverless vs Provisioned

- **DMS Serverless**: Automatically provisions and scales replication capacity (measured in DMS Capacity Units, DCUs) based on transaction volume fluctuations. Ideal for unpredictable burst workloads or continuous cross-account replication.
- **Provisioned DMS Instances**: Fixed EC2-backed replication instances (e.g., `dms.c5.2xlarge`). Recommended for highly predictable large-scale initial loads where fixed compute sizing avoids auto-tuning latencies.

## 4. Massive Scale Data Transfer: Online vs Offline

When migrating petabyte-scale storage tiers (SAN/NAS storage, Hadoop HDFS, archival tape libraries) to Amazon S3, network bandwidth is frequently the limiting bottleneck.

### 4.1 Bandwidth vs Time Calculation

The classic formula governing data transfer velocity over network links:

$$\text{Transfer Time} = \frac{\text{Total Data Size (Bytes)} \times 8}{\text{Link Throughput (Bits/sec)} \times 0.80}$$

*(Assuming an 80% realistic network utilization factor accounting for protocol overhead).*

- Transferring **500 TB** over a dedicated **1 Gbps Direct Connect** connection:
  $$\frac{500 \times 10^{12} \times 8 \text{ bits}}{10^9 \text{ bits/s} \times 0.80} \approx 5,000,000 \text{ seconds} \approx \mathbf{58 \text{ days}}$$
- When transfer duration over available bandwidth exceeds the migration timeline or compromises business operations, **offline physical transfer appliances** are mandatory.

### 4.2 Data Transfer Selection Matrix

```text
                        Data Volume to Transfer
                                   │
              ┌────────────────────┴────────────────────┐
              ▼                                         ▼
         < 10 - 20 TB                               > 20 TB
              │                                         │
    Sufficient Bandwidth?                     Dedicated Link Adequate?
    ├── Yes ──► AWS DataSync                  ├── Yes (Days to complete) ──► AWS DataSync / Direct Connect
    └── No  ──► AWS Snowball Edge             └── No (Weeks to months)   ──► AWS Snow Family Appliance
```

| Transfer Service | Mechanism | Primary Use Case | Target Storage | Network Requirement |
| :--- | :--- | :--- | :--- | :--- |
| **AWS DataSync** | Online automated agent deployed on VMware/Hyper-V/KVM; parallelized data transfers with end-to-end checksum verification. | Continuous synchronization of NAS/SAN filesystems, active migrations, and regular scheduled backups. | S3, EFS, FSx for Windows, FSx for Lustre, FSx for OpenZFS. | Dedicated Direct Connect, VPN, or Public Internet. |
| **Snowball Edge Storage Optimized** | Physical ruggedized appliance (roughly 80 TB usable HDD per device) shipped via courier. Device specifications and availability change, so confirm them in the current AWS documentation. | Bulk offline transfer of tens to hundreds of terabytes where network bandwidth is insufficient. | Amazon S3 (Standard, Glacier), EBS. | Offline (Local 10/25 GbE network for staging). |
| **Snowball Edge Compute Optimized** | Physical ruggedized appliance with more vCPUs and SSD storage, plus an optional GPU. | Edge compute, local machine learning inference, and edge preprocessing before shipping data to AWS. | Amazon S3, EBS. | Offline / Edge connected. |
| **AWS Transfer Family** | Fully managed SFTP, FTPS, FTP, and AS2 endpoints backed directly by object or file storage. | Migrating legacy partner B2B file transfer workflows without modifying external client scripts. | Amazon S3, Amazon EFS. | Public Internet, VPC Endpoints, or Direct Connect. |

## 5. Domain 4 Migration Decision Matrix

Evaluate migration exam questions on SAP-C03 using this proven checklist:

| Primary Constraint | Evaluated Options | Winning Architecture & Exam Justification |
| :--- | :--- | :--- |
| **Migrate 500 physical and virtual Windows servers to AWS within 60 days with minimal manual configuration and low downtime** | • AWS DataSync + manual AMI creation<br>• AWS Application Migration Service (MGN)<br>• VMware Cloud on AWS | **AWS MGN**. Block-level continuous background replication without server reboots; automated launch templates handle EC2 driver injection and instance provisioning in minutes during cutover. |
| **Migrate on-premises Oracle database to Amazon Aurora PostgreSQL with minimal downtime and complex PL/SQL stored procedures** | • AWS DMS alone<br>• Oracle Data Guard<br>• AWS SCT for schema/PL/SQL conversion + AWS DMS for full load and continuous CDC | **AWS SCT + AWS DMS**. SCT converts schema and flags unconverted PL/SQL routines for manual rewriting; DMS handles continuous CDC to keep Aurora synchronized until final cutover. |
| **Transfer 800 TB of uncompressed medical imaging files from an on-premises NAS with only a shared 100 Mbps internet connection** | • AWS DataSync over Internet<br>• S3 Transfer Acceleration<br>• Multiple AWS Snowball Edge Storage Optimized appliances | **AWS Snowball Edge Storage Optimized**. A 100 Mbps connection would take over 2.5 years to transfer 800 TB. Shipping multiple Snowball Edge appliances completes the transfer in a few weeks. |
| **Migrate external partner file exchanges using legacy SFTP scripts to AWS while retaining existing partner credentials and endpoints** | • Self-managed SFTP servers on EC2 with ASGs and EFS<br>• AWS Transfer Family for SFTP backed by Amazon S3<br>• API Gateway with Lambda S3 pre-signed URLs | **AWS Transfer Family**. Fully managed SFTP endpoint backed by S3 with custom identity provider (Secrets Manager / Lambda) integration; eliminates server maintenance without forcing partners to rewrite scripts. |
