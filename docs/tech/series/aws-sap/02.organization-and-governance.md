In modern cloud computing, multi-account architecture is not an operational afterthought; it is the **primary blast-radius containment boundary**. A single shared AWS account hosting production, staging, data platforms, and development workloads introduces unavoidable security friction, noisy-neighbor contention, and insurmountable compliance audits.

For the **AWS Certified Solutions Architect - Professional (SAP-C03)** exam, Domain 2 carries a decisive **25% exam weighting**. The exam rigorously tests your ability to design enterprise-scale multi-account landing zones, enforce multi-perimeter security guardrails without impeding developer agility, implement identity federation with fine-grained Attribute-Based Access Control (ABAC), and architect secure cross-region cryptographic foundations.

---

## Before you start

An AWS account is a hard boundary: its resources, bills and permissions are separate from every other account's. Companies end up with dozens of them, one per team or environment, so a mistake or a breach in one stays there. The problem this chapter covers is how to manage all of those accounts without hand-configuring each one.

Think of an office building. Each tenant has a locked suite (an account), but the landlord sets rules for the whole building: no open flames, fire doors stay shut. AWS Organizations is the landlord's ledger, and policies are the building rules that no tenant can override, even a tenant who is the administrator of their own suite.

Read [chapter 1](/tech/series/aws-sap/01.evolution-and-domains/) first for how the exam is organized. You should also know what an IAM policy is: a JSON document that says who may do what.

Terms used in this chapter:

- **AWS Organizations**: the service that groups many AWS accounts under one management account for billing and policy.
- **SCP (Service Control Policy)**: a rule attached to accounts that caps what identities inside them can do, whatever their own permissions say.
- **RCP (Resource Control Policy)**: a similar cap placed on resources, limiting who can access them.
- **Control Tower**: an AWS service that sets up a recommended multi-account structure with guardrails.
- **ABAC**: attribute-based access control, where access depends on tags such as `team=payments` rather than on a fixed list of names.
- **KMS**: AWS Key Management Service, which stores encryption keys and performs encryption for you.
- **Blast radius**: how much can be damaged when one thing is compromised or broken.

## 1. Enterprise Landing Zone Hierarchy with AWS Organizations & Control Tower

A Well-Architected multi-account structure separates accounts by **lifecycle stage, operational duty, and data sensitivity**. Using AWS Organizations and AWS Control Tower, enterprise workloads are partitioned into functional Organizational Units (OUs):

```text
Root
 ├── Core / Foundational OU
 │    ├── Log Archive Account        (Consolidates CloudTrail, S3 access logs, VPC Flow Logs)
 │    ├── Security Tooling Account   (Security Hub delegated admin, GuardDuty, Macie, IAM Identity Center)
 │    └── Network Shared Account     (Transit Gateway hub, Cloud WAN core, Direct Connect, Inspection VPC)
 ├── Workloads OU
 │    ├── Production OU              (Strict immutable deployments, zero developer SSH/console access)
 │    └── Non-Production / Staging OU (CI/CD automated integration testing environments)
 ├── Sandbox / Policy Staging OU     (Isolated developer experimentation; detached from corporate networks)
 └── Suspended OU                    (Decommissioned accounts under quarantine pending deletion)
```

### Key Architectural Tenets

1. **Delegated Administration**: The Organizations Management (root) account should contain **zero operational workloads**. Delegate administrative authority for security services (GuardDuty, Security Hub, IAM Identity Center, AWS Firewall Manager) to the dedicated Security Tooling member account to preserve the management account's purity and audit trail.
2. **Account Factory for Terraform (AFT)**: Control Tower baseline accounts can be programmatically provisioned and configured using GitOps pipelines, binding Terraform modules to account creation lifecycle events.

## 2. The Dual-Boundary Paradigm: SCPs vs RCPs

One of the most consequential new additions to the SAP-C03 exam blueprint is the introduction of **Resource Control Policies (RCPs)** alongside classic **Service Control Policies (SCPs)**.

Understanding the difference between principal governance and resource governance is the single most important conceptual discriminator in Domain 2:

| Dimension | Service Control Policies (SCPs) | Resource Control Policies (RCPs) |
| :--- | :--- | :--- |
| **Enforcement Target** | **Principals (Identities)** within the account/OU | **Resources** located within the account/OU |
| **What It Restricts** | What actions an IAM user or role *can do* | Who can *access* the resources within the account |
| **Cross-Account Scope** | Governs requests initiated *by* your accounts | Governs requests *to* your resources from any principal, which in practice is used to block principals outside your organization |
| **Primary Use Case** | Preventive guardrails (e.g., deny `s3:DeleteBucket`, deny disabling CloudTrail, deny unapproved regions) | **Data Perimeter Protection** (e.g., ensuring S3 buckets or KMS keys cannot be accessed by external rogue AWS accounts) |
| **Management Account Exempt?** | Yes (SCPs do not apply to the Management root) | Yes (RCPs do not apply to resources in the Management account) |
| **Permissions Granting** | Never grants permissions; only specifies the maximum available authorization ceiling | Never grants permissions; only establishes the maximum allowable inbound perimeter ceiling |

### Combining SCPs, RCPs, and Permissions Boundaries

To answer complex exam scenarios, trace the evaluation hierarchy:

$$\text{Allowed} = \lnot\,\text{Explicit Deny (in Any Layer)} \land \text{SCP Allowed} \land \text{RCP Allowed} \land \text{Permissions Boundary Allowed} \land (\text{Identity Policy} \lor \text{Resource Policy})$$

- If an **SCP** denies an action, no IAM policy inside the account can override it.
- If an **RCP** specifies that S3 buckets in Account A can only be accessed by principals belonging to `aws:PrincipalOrgID == "o-12345678"`, an external attacker with valid credentials from a foreign AWS account will be blocked at the AWS service control layer, regardless of bucket policy misconfigurations.
- A **Permissions Boundary** is attached directly to an IAM user or role to restrict the maximum permissions an administrator delegate can grant to newly created roles (preventing privilege escalation).

## 3. Enterprise Identity: IAM Identity Center & ABAC

In enterprise environments, managing static IAM users and long-lived access keys inside individual accounts is an architectural failure. The SAP-C03 exam demands a centralized identity federation strategy.

### External IdP Integration

Integrate corporate Identity Providers (IdPs)—such as Microsoft Entra ID (Azure AD), Okta, or Ping Identity—with **AWS IAM Identity Center** using:

- **SAML 2.0**: Handles web browser Single Sign-On (SSO) into the Identity Center portal; the AWS CLI v2 then gets short-lived role credentials through `aws sso login`.
- **SCIM (System for Cross-domain Identity Management)**: Automates real-time synchronization of users, groups, and status changes from the IdP into AWS without custom Lambda scripts.

### Role-Based Access Control (RBAC) vs Attribute-Based Access Control (ABAC)

- **RBAC Trap**: As an organization scales to 500 accounts and 50 project teams, RBAC creates **permission explosion** (e.g., `DevTeamRole`, `DataTeamRole`, `AuditRole` cloned across hundreds of accounts).
- **ABAC Strategy**: Define a single generic permission set and propagate user identity attributes (such as `Department`, `CostCenter`, `ProjectCode`) as **session tags** during federation.

Access is evaluated dynamically via IAM policy condition keys:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowAccessMatchingProjectTag",
      "Effect": "Allow",
      "Action": ["ec2:StartInstances", "ec2:StopInstances", "ec2:RebootInstances"],
      "Resource": "arn:aws:ec2:*:*:instance/*",
      "Condition": {
        "StringEquals": {
          "aws:ResourceTag/Project": "${aws:PrincipalTag/Project}"
        }
      }
    }
  ]
}
```

When an engineer assigned to the "DataPlatform" project authenticates, their temporary session carries `aws:PrincipalTag/Project = "DataPlatform"`. They can interact exclusively with resources stamped with `Project = "DataPlatform"`, eliminating role duplication.

## 4. Workload Identity Beyond AWS: IAM Roles Anywhere

What about servers and workloads running on-premises, in colocation data centers, or across other public clouds?

Historical anti-patterns involved generating long-lived IAM user access keys (`AKIA...`), embedding them in server config files, and hoping they wouldn't leak.

**IAM Roles Anywhere** replaces this vulnerability:

1. Establish a **Trust Anchor** in IAM Roles Anywhere pointing to an enterprise internal X.509 Certificate Authority (CA) or AWS Private CA.
2. On-premises servers use their local private key and signed X.509 certificate to sign a request to the Roles Anywhere endpoint.
3. IAM Roles Anywhere validates the certificate chain against the Trust Anchor and returns **short-lived temporary credentials** for the mapped IAM role (one hour by default).
4. No long-lived secret keys ever leave AWS or sit in plain text on physical servers.

## 5. Advanced Cryptography: Multi-Region Keys & Cross-Account KMS Topologies

Enterprise data resilience requires multi-region data replication (e.g., Amazon S3 Cross-Region Replication, Aurora Global Database). However, data encrypted under standard AWS KMS customer managed keys (CMK) presents a major cryptographic challenge.

Standard KMS keys are strictly **regional constructs**:

- A key created in `us-east-1` (`arn:aws:kms:us-east-1:111122223333:key/12345678-...`) cannot be used to decrypt ciphertext in `us-west-2`.
- Historically, replicating encrypted data required reading the ciphertext in region A, decrypting it into plaintext in memory using Key A, re-encrypting it under Key B in region B, and writing it out.

### KMS Multi-Region Keys (MRKs)

KMS Multi-Region Keys solve this at the root:

- You create a **Primary Multi-Region Key** in one region and replicate it to one or more replica regions.
- Multi-Region Keys share the **exact same Key ID and key material** (`arn:aws:kms:*:111122223333:key/mrk-12345678-...`).
- **Envelope Encryption Parity**: Data encrypted in `us-east-1` using the Primary MRK can be decrypted directly in `us-west-2` by the Replica MRK **without decrypting and re-encrypting the data in flight**.
- Regional operational independence is preserved: if `us-east-1` suffers an outage, the replica key in `us-west-2` continues to operate independently with its own local availability zone endpoints.

## 7. Exam Scenarios & Deciding Vectors

| Scenario Cue | Naive / Distractor Option | Architectural Winner (SAP-C03 Vector) | Why |
| :--- | :--- | :--- | :--- |
| *"Prevent any account in the organization from accessing S3 buckets outside approved corporate accounts."* | Deploy VPC Endpoints and block external IP addresses. | **Apply an SCP enforcing `s3:ResourceAccount` condition** matching corporate account IDs on all S3 requests. | Network policies cannot inspect S3 API resource targets; IAM policy condition keys enforce the perimeter at the API layer. |
| *"Prevent third-party AWS accounts from querying S3 buckets hosted inside internal production accounts."* | Update 500 individual bucket policies across all workload accounts. | **Attach an Organization-level Resource Control Policy (RCP)** denying requests where `aws:PrincipalOrgID` does not match your organization ID. | Centrally manages the inbound resource boundary without relying on developer adherence to bucket policy standards. |
| *"Enable cross-region active-active database failover for client-side encrypted fields with sub-second RTO."* | Re-encrypt data using a Lambda function during Cross-Region Replication. | **Use a KMS Multi-Region Key (MRK)** shared across primary and secondary disaster recovery regions. | Allows direct decryption of envelope-encrypted data in the secondary region without pipeline re-encryption latency. |
