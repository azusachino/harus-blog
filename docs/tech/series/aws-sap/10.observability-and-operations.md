Operational Excellence is the foundation upon which resilient, secure, and cost-effective cloud architectures run. In the AWS Certified Solutions Architect – Professional (SAP-C03) exam, Domain 5 (Operational Excellence and Automation) accounts for a substantial 20% of the overall evaluation. Enterprise cloud architects are tested on orchestrating unified observability across hundreds of federated AWS accounts, establishing automated compliance guardrails, and architecting self-healing remediation pipelines that eliminate manual operator interventions.

In this concluding chapter of the SAP-C03 series, we master centralized multi-account telemetry via Amazon CloudWatch and OpenTelemetry (ADOT), fleet-wide compliance enforcement with AWS Config Conformance Packs, and closed-loop automated incident remediation utilizing AWS Systems Manager and Amazon EventBridge.

## Before you start

When a request fails at 3 a.m., somebody has to find out why. Observability means the system gives you enough logs, metrics and traces to answer that without guessing. With dozens of AWS accounts the problem multiplies: each account has its own logs, and nobody wants to log into 40 of them during an incident.

A trace is the easiest piece to picture. A single click on a web page may touch five services. A trace records one ID that follows the request through all five, with the time spent in each, so you can see that the slow part was the third call.

This chapter also covers checking that every account follows your configuration rules, and fixing certain problems automatically. Read [chapter 2](/tech/series/aws-sap/02.organization-and-governance/) first, as the multi-account setup comes from there.

Terms used in this chapter:

- **Metric / log / trace**: a number sampled over time, a line of text an application writes, and a record of one request's path across services.
- **CloudWatch**: the AWS service that stores metrics and logs and raises alarms.
- **Cross-account observability**: viewing telemetry from many accounts in one monitoring account.
- **OpenTelemetry (ADOT)**: a vendor-neutral standard for emitting traces and metrics; ADOT is AWS's distribution of it.
- **AWS Config**: a service that records resource configurations and checks them against rules.
- **Conformance pack**: a bundle of Config rules deployed together across accounts.
- **Systems Manager**: AWS tooling for running commands and runbooks on your machines.
- **Remediation**: automatically fixing a detected problem, for example closing a public storage bucket.

## 1. Multi-Account Observability Architecture

Large-scale enterprise environments structured around AWS Organizations feature dozens to hundreds of isolated member accounts (e.g., Development, Staging, Production-EU, Production-US, Shared Services). Operating individual CloudWatch consoles per account is inefficient and obscures global systemic failures.

```text
┌─────────────────────────────────┐       ┌─────────────────────────────────┐
│     Source Account: App-Prod-1  │       │     Source Account: App-Prod-2  │
│  • CloudWatch Metrics           │       │  • CloudWatch Metrics           │
│  • CloudWatch Logs              │       │  • CloudWatch Logs              │
│  • AWS X-Ray Traces             │       │  • AWS X-Ray Traces             │
└────────────────┬────────────────┘       └────────────────┬────────────────┘
                 │ AWS Organizations                      │ AWS Organizations
                 │ Telemetry Link                         │ Telemetry Link
                 ▼                                        ▼
┌───────────────────────────────────────────────────────────────────────────┐
│                     Central Monitoring Account                            │
│  ┌─────────────────────────────────────────────────────────────────────┐  │
│  │ Amazon CloudWatch Cross-Account Observability                       │  │
│  │ • Unified cross-account dashboards                                  │  │
│  │ • Cross-account CloudWatch Logs Insights queries                    │  │
│  │ • Interactive cross-account AWS X-Ray service maps                   │  │
│  │ • CloudWatch Application Signals (Service Level Objectives - SLOs)  │  │
│  └──────────────────────────────────┬──────────────────────────────────┘  │

│  │ Amazon Data Firehose ──► Amazon S3 / OpenSearch / Datadog          │  │
│  └─────────────────────────────────────────────────────────────────────┘  │

```

### 1.1 Amazon CloudWatch Cross-Account Observability

CloudWatch Cross-Account Observability allows you to designate one or more **Monitoring Accounts** that ingest and visualize operational telemetry from multiple **Source Accounts** without writing custom log forwarders:

- **Shared Telemetry Types**:
  1. **Metrics**: Search, graph, and alarm on metrics originating across all member accounts within unified dashboards.
  2. **Logs**: Query petabytes of logs across accounts simultaneously via CloudWatch Logs Insights syntax (`fields @timestamp, @message | filter ...`).
  3. **Traces**: Traverse end-to-end distributed transaction traces spanning services in separate accounts.
  4. **Application Insights**: View automated health anomalies and error clusters aggregated across enterprise workloads.
- **Security & Setup**: Links are established using AWS Organizations entity sharing or explicit IAM permissions, eliminating the complex Lambda-based log shipping architectures of previous exam generations.

### 1.2 CloudWatch Metric Streams

For organizations that ingest metrics into third-party observability platforms (Datadog, Dynatrace, New Relic, Splunk) or a centralized data lake:

- Traditional polling approaches calling `GetMetricData` hit API rate throttling (`RateExceeded`) and add noticeable delay.
- **CloudWatch Metric Streams** continuously streams metrics in real time via **Amazon Data Firehose** (formerly Kinesis Data Firehose) with near-real-time delivery directly into target destinations in OpenTelemetry or JSON format.

## 2. Distributed Tracing: AWS Distro for OpenTelemetry (ADOT)

Modern microservices, serverless functions, and asynchronous event streams make pinpointing latency bottlenecks challenging. **AWS Distro for OpenTelemetry (ADOT)** is an AWS-supported, vendor-neutral distribution of the Cloud Native Computing Foundation (CNCF) OpenTelemetry project.

```text
Application Workloads (EKS / ECS / EC2 / Lambda)
┌────────────────────────────────────────────────────────┐
│  Service Container (Java / Go / Python / Node / .NET)  │
│  • Instrumented with OpenTelemetry SDK (OTel API)      │
│  • Auto-instruments HTTP, gRPC, DB, AWS SDK calls      │
└───────────────────────────┬────────────────────────────┘
                            │ OTLP Protocol (gRPC / HTTP)
                            ▼
┌────────────────────────────────────────────────────────┐
│  ADOT Collector (DaemonSet / Sidecar / EC2 Agent)      │
│  • Ingests OpenTelemetry Protocol (OTLP) data          │
│  • Batching, sampling, attribute filtering             │
└───────┬───────────────────┬───────────────────┬────────┘
        │                   │                   │
        ▼                   ▼                   ▼
   [AWS X-Ray]     [Amazon CloudWatch]   [Amazon OpenSearch]
  Distributed traces   Metrics & Logs       Log indexing
```

### 2.1 ADOT vs Legacy X-Ray Daemon

- The legacy AWS X-Ray daemon only supported proprietary AWS formats.
- **ADOT is open standards compliant**: Write once using open OTel instrumentation; export simultaneously to AWS X-Ray, Amazon Managed Service for Prometheus (AMP), Amazon Managed Grafana (AMG), and partner SaaS backends.
- **X-Ray Trace Propagation**: Traces carry the `X-Amzn-Trace-Id` header through Amazon API Gateway, Application Load Balancers, AWS Lambda, and Amazon SQS, allowing complete visual reconstruction of end-to-end request latency on the X-Ray Service Map.

## 3. Fleet Configuration & Compliance: AWS Config Conformance Packs

Deploying workloads without automated compliance guarantees leaves an enterprise exposed to security vulnerabilities and configuration drift.

### 3.1 Architecture of Enterprise Compliance

```text
┌────────────────────────────────────────────────────────────────────────┐
│                  AWS Organizations Management Account                  │
│  ┌──────────────────────────────────────────────────────────────────┐  │
│  │ AWS Config Organization Aggregator                               │  │
│  │ • Global multi-region, multi-account inventory aggregator        │  │
│  └──────────────────────────────────┬───────────────────────────────┘  │
│                                     │ Deploys via Organization Hook     │
│                                     ▼                                   │
│  ┌──────────────────────────────────────────────────────────────────┐  │
│  │ AWS Config Conformance Pack (YAML Template)                      │  │
│  │ • CIS AWS Foundations Benchmark                                  │  │
│  │ • PCI-DSS / HIPAA Compliance Pack                                │  │
│  │ • Managed Rules: s3-bucket-ssl-requests-only, root-account-mfa   │  │
│  │ • Custom Rules: Guard-based or Lambda-backed evaluation          │  │
│  └──────────────────────────────────┬───────────────────────────────┘  │
└─────────────────────────────────────┼──────────────────────────────────┘
                                      │ Enforces across all accounts
                ┌─────────────────────┴─────────────────────┐
                ▼                                           ▼
   [Account A: Non-Compliant Event]             [Account B: Compliant Event]
   • S3 bucket created without encryption       • S3 bucket with KMS SSE-KMS
                │                                           │
                ▼ Status: NON_COMPLIANT                     ▼ Status: COMPLIANT
   [Amazon EventBridge (Local)]                 [Config Aggregator History]
                │
                ▼ Invokes SSM Automation Document
   [SSM Automation: AWS-EnableS3BucketEncryption]
                │
                ▼ Automatically remediates resource
   [S3 Bucket Encrypted with KMS key]
```

### 3.2 Conformance Packs vs Individual Config Rules

- **Conformance Packs**: A collection of AWS Config rules and remediation actions packaged into a single YAML template. They are deployed across an entire AWS Organization with a single command or API call.
- **Preventing Drift**: Member account administrators cannot modify or delete Conformance Packs deployed by the Organization management account.
- **AWS CloudFormation Guard**: Allows architects to write declarative, lightweight policy-as-code rules for custom Config checks without developing custom Lambda execution functions.

## 4. Closed-Loop Automated Incident Remediation

Operational Excellence requires moving beyond passive human alerts toward automated self-healing.

### 4.1 EventBridge and Systems Manager Automation Pipeline

When a security or operational compliance violation occurs, manual ticketing introduces dangerous latency windows. The canonical AWS self-healing pattern integrates three services:

1. **Detection (AWS Config / GuardDuty / Security Hub)**: Detects policy violation (e.g., security group opened to `0.0.0.0/0` on port 22).
2. **Routing (Amazon EventBridge)**: Captures the compliance state change event:

   ```json
   {
     "source": ["aws.config"],
     "detail-type": ["Config Rules Compliance Change"],
     "detail": {
       "configRuleName": ["restricted-ssh"],
       "newEvaluationResult": {
         "complianceType": ["NON_COMPLIANT"]
       }
     }
   }
   ```

3. **Execution (AWS Systems Manager Automation)**: EventBridge invokes an SSM Automation Document (e.g., `AWS-DisablePublicAccessForSecurityGroup`) with an assumed administrative IAM execution role. The document parses the resource ID and revokes the inbound rule shortly after Config flags it.

### 4.2 Cross-Account Automated Remediation

In a multi-account organization, remediation runbooks should execute securely without granting excessive permissions:

- The remediation rule in the central security account uses an assumed **SSM Automation cross-account execution role** (`AWS-SystemsManager-AutomationExecutionRole`) in the target member account.
- This ensures centralized auditability, least privilege, and standardized incident resolution across the entire corporate estate.
