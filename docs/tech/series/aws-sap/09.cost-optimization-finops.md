Cost optimization is an active architectural constraint rather than a retrospective accounting exercise. On the AWS Certified Solutions Architect – Professional (SAP-C03) exam, Domain 3 (Cost-Optimized Architecture Design) accounts for 15% of the total score. The exam demands that architects evaluate business value and workload performance requirements while rigorously eliminating unneeded expenses.

In this chapter, we unpack the mathematical mechanics of commitment-based discount models (Savings Plans vs Reserved Instances), deep right-sizing via AWS Compute Optimizer, network data transfer elimination techniques, and automated FinOps governance with Cost Categories, Budgets, and Cost Anomaly Detection.

---

## Before you start

Cloud bills surprise people. Nothing is bought up front, anyone with permission can start a machine, and charges arrive monthly in line items nobody reads. This chapter covers how to lower the bill in three ways: promise AWS steady usage in exchange for a discount, stop paying for machines that are bigger than needed, and avoid the fees for moving data.

An example: an instance costing \$0.10 an hour runs 8,760 hours in a year, about \$876. If you know you will run it all year, a one-year commitment may cut that price by a third or more, but you pay even if you shut it down. Committing is a bet on your own usage.

Read [chapter 4](/tech/series/aws-sap/04.cloud-native-compute-karpenter/) for the Spot and Graviton ideas, which also reduce cost.

Terms used in this chapter:

- **On-demand**: paying the full hourly price with no commitment.
- **Savings Plan**: a commitment to spend a set amount per hour for one or three years in return for a lower rate.
- **Reserved Instance**: an older, narrower commitment tied to specific instance types.
- **Right-sizing**: replacing an over-provisioned machine with a smaller one that still fits the real load.
- **Compute Optimizer**: an AWS tool that analyzes usage and recommends right-sizing.
- **Data transfer cost**: fees for data leaving AWS, or crossing regions or zones.
- **FinOps**: the practice of making engineers and finance share responsibility for cloud spend.
- **Cost allocation tag**: a label on a resource that lets the bill be split by team or project.

## 1. Commitment Discount Models: Savings Plans vs Reserved Instances

AWS provides pricing models that offer up to 72% discounts over standard On-Demand pricing in exchange for committing to a consistent usage amount (measured in dollars per hour) over a 1-year or 3-year term.

```text
Flexibility & Modernization Freedom
  ▲
  │
  │   [Compute Savings Plans]
  │   • Covers EC2, Fargate, and Lambda
  │   • Any family, OS, Region, or Tenancy
  │   • Discounts up to 66%
  │
  │              [EC2 Instance Savings Plans]
  │              • Committed to a specific instance family in a Region (e.g., m7g in us-east-1)
  │              • Flexible across size, OS, and AZ
  │              • Discounts up to 72%
  │
  │                             [Standard Reserved Instances (RIs)]
  │                             • Specific instance family and Region; marketplace sellable
  │                             • Required for non-EC2 services (RDS, ElastiCache, OpenSearch, Redshift)
  │                             • Discounts up to 72%
  └─────────────────────────────────────────────────────────────────────────────► Max Percentage Discount
```

### 1.1 Structural Comparison

| Discount Model | Applies To | Region Flexibility | OS / Tenancy Flexibility | Family Flexibility | Marketplace Resale |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **Compute Savings Plans** | EC2, AWS Fargate, AWS Lambda | **Yes** (any AWS region globally) | **Yes** (Linux, Windows, Dedicated) | **Yes** (e.g., transition from `c5` to `c7g` seamlessly) | No |
| **EC2 Instance Savings Plans** | EC2 instances only | **No** (locked to selected Region) | **Yes** (automatically applies across OS and tenancy) | **No** (locked to selected family, e.g., `m6i`) | No |
| **Standard Reserved Instances** | EC2, RDS, ElastiCache, OpenSearch, Redshift | **No** (Regional RIs offer size flexibility; Zonal RIs provide capacity reservation) | Partial (Linux allows size pooling; Windows does not) | **No** (Fixed family) | **Yes** (EC2 Standard RIs only) |
| **Convertible Reserved Instances** | EC2 instances only | **No** (Region stays fixed) | **Yes** (via manual exchange) | **Yes** (via manual exchange) | No |

### 1.2 Enterprise Commitment Strategy for SAP-C03

- **Compute Savings Plans** are the default choice for dynamic, evolving architectures because they automatically absorb infrastructure transitions: moving workloads from EC2 to Fargate or Lambda, migrating across regions, or upgrading processor architectures (x86 to Graviton arm64) without forfeiting the discount.
- **Reserved Instances for Managed Data Stores**: Compute Savings Plans do *not* cover Amazon RDS, Aurora, ElastiCache, Amazon OpenSearch Service, or Amazon Redshift, so enterprise architectures traditionally combine Compute Savings Plans (for compute/serverless tiers) with Reserved Instances (for relational and cache tiers). AWS has since added Database Savings Plans for some managed databases, so check current coverage before choosing.
- **Payment Options**: Full Upfront (highest discount), Partial Upfront (balanced cash flow), and No Upfront (lowest discount, preserves working capital).

## 2. Intelligent Right-Sizing: AWS Compute Optimizer

Over-provisioning is one of the most widespread sources of enterprise cloud waste. **AWS Compute Optimizer** uses machine learning algorithms trained on millions of workload hours to analyze Amazon CloudWatch metrics (CPU utilization, memory usage, network I/O, disk throughput) and deliver prescriptive right-sizing recommendations.

```text
┌─────────────────────────────────┐
│     CloudWatch Telemetry Feed   │
│  (CPU, Network, Disk I/O, RAM*) │
└────────────────┬────────────────┘
                 │ Requires CloudWatch Agent or SSM for memory metrics
                 ▼
┌─────────────────────────────────────────────────────────────────────────┐
│                       AWS Compute Optimizer Engine                      │
│  - Evaluates historical utilization over 14-day (or 3 months via paid)  │
│  - Detects Over-provisioned, Under-provisioned, and Optimized resources │
└────────────────┬────────────────────────────────────────────────────────┘
                 │
                 ├─► EC2 Instances: Suggests newer Graviton (e.g. m5.xlarge -> m7g.large)
                 ├─► Auto Scaling Groups: Identifies oversized min/max scaling boundaries
                 ├─► EBS Volumes: Flags idle volumes; converts gp2 to gp3; right-sizes IOPS
                 └─► AWS Lambda Functions: Fine-tunes memory allocations to eliminate excess execution duration
```

### 2.1 EC2 & Graviton Modernization Recommendations

Compute Optimizer explicitly identifies opportunities to transition workloads from older Intel/AMD families (`m5`, `c5`) to modern AWS Graviton (`m7g`, `c7g`) instances, delivering up to 40% better price-performance.

- **Under-provisioned Instances**: Instances exhibiting high CPU/RAM bottlenecks. Compute Optimizer recommends upgrading size to eliminate service degradation.
- **Over-provisioned Instances**: Instances where peak CPU and memory rarely exceed 15–20%. Compute Optimizer suggests smaller instance sizes within the same family or switching to a more cost-effective instance family.

### 2.2 EBS Volume Modernization: Migrating `gp2` to `gp3`

On SAP-C03, storage cost optimization scenarios consistently test EBS volume transitions:

- **`gp2` Volume Limitations**: Performance (IOPS and throughput) is statically tied to provisioned storage volume size ($3 \text{ IOPS per GB}$). To achieve 3,000 IOPS, a team is forced to provision a 1,000 GB volume even if they only need 50 GB of storage.
- **`gp3` Volume Architecture**: Baseline performance includes **3,000 IOPS and 125 MB/s throughput completely free**, independent of storage volume. Provisioned storage costs are **20% lower per GB** than `gp2`.
- **Exam Rule**: Any workload operating on `gp2` volumes should immediately be transitioned to `gp3` via EBS Elastic Volumes (an in-place, zero-downtime modification) to achieve instantaneous 20% storage cost reduction and decoupled IOPS provisioning.

### 2.3 Lambda Memory Tuning

AWS Lambda allocates CPU power, network bandwidth, and memory proportionally based on the memory slider (128 MB to 10,240 MB).

- Increasing memory can sometimes *decrease* overall costs because the task executes significantly faster (e.g., executing in 200 ms with 1,024 MB can be cheaper than executing in 2,500 ms with 128 MB). Compute Optimizer analyzes execution curves to pinpoint the sweet spot balancing runtime duration against memory pricing.

## 3. Network Architecture & Data Transfer Minimization

Network data transfer costs represent a silent budget drain in enterprise AWS environments. An architect must know the exact pricing dynamics of data flows across boundaries.

```text
                           [Client on Public Internet]
                                       │
                                       ▼ Inbound Transfer (FREE)
                         ┌───────────────────────────┐
                         │   AWS Cloud (Any Region)  │
                         └─────────────┬─────────────┘
                                       │
                ┌──────────────────────┴──────────────────────┐
                ▼                                             ▼
        [Within Same AZ]                              [Inter-AZ / VPC Peering]
      • Private IP: $0.00 / GB                      • $0.01 / GB egress + $0.01 / GB ingress
      • Cluster Placement Group: $0.00 / GB         • Total = $0.02 / GB round trip
                │                                             │
                ▼                                             ▼
        [Inter-Region Peering]                        [Internet Data Egress]
      • Between US-East and US-West:                • First 100 GB / month free
        $0.02 / GB egress                           • $0.09 / GB thereafter (down to $0.05 / GB)
```

### 3.1 NAT Gateway vs VPC Endpoints

In high-throughput microservice and analytics environments, accessing AWS services through a NAT Gateway creates severe cost penalties:

- **NAT Gateway Pricing**:
  - Hourly charge: $\approx \$0.045 / \text{hour}$ per gateway.
  - Data processing charge: $\mathbf{\$0.045 / \text{GB}}$ processed.
  - A fleet pulling 50 TB of machine learning models or container images from Amazon S3 through a NAT Gateway incurs $50,000 \times \$0.045 = \mathbf{\$2,250}$ in NAT data processing fees alone!

#### Optimization Pattern: VPC Gateway Endpoints

- **VPC Gateway Endpoints** for **Amazon S3** and **Amazon DynamoDB** are completely **free of charge** (zero hourly fee and zero data processing charge).
- Adding a Gateway Endpoint to private subnet route tables diverts all S3 and DynamoDB traffic directly across the AWS private network, bypassing the NAT Gateway entirely and immediately eliminating data processing fees.

#### Optimization Pattern: Interface Endpoints (AWS PrivateLink)

- For other AWS services (Kinesis, Secrets Manager, ECR, Bedrock), **VPC Interface Endpoints** cost \$0.01/hour per endpoint per AZ plus \$0.01/GB processed.
- Because \$0.01/GB is less than a quarter of the NAT Gateway processing fee (\$0.045/GB), high-volume API traffic routed through PrivateLink yields substantial net savings while enhancing security.

### 3.2 Amazon CloudFront for Internet Egress Reduction

When public users download media or web assets directly from Amazon S3 or EC2, standard internet egress rates apply ($\$0.09 / \text{GB}$).

- Data transfer from Amazon S3 or EC2 to **Amazon CloudFront edge locations is \$0.00 / GB (free)**.
- CloudFront data transfer out to the internet is discounted compared to direct AWS egress, and cached assets eliminate backhaul compute and storage requests completely.

## 4. FinOps Governance & Cost Allocation Architecture

FinOps is the operational practice of bringing financial accountability to the variable spend model of cloud computing.

```text
┌────────────────────────────────────────────────────────────────────────┐
│                        FinOps Governance Pipeline                      │
└────────────────────────────────────────────────────────────────────────┘
          │
          ▼
   1. Standardized Cost Allocation Tags
      ├─ AWS-Generated Tags (e.g. aws:createdBy)
      └─ User-Defined Tags: CostCenter, Environment, BusinessUnit, Owner
          │
          ▼ Enforced via Tag Policies in AWS Organizations
   2. AWS Cost Categories
      ├─ Map multi-account structures and tags to organizational business units
      └─ Handle split charges (e.g. allocating shared ECS cluster or EKS cluster costs)
          │
          ▼
   3. Real-Time Detection & Budgets
      ├─ AWS Cost Anomaly Detection (ML model alerts via SNS / Slack within hours)
      └─ AWS Budgets Alert Cascades:
          ├─ 80% Threshold: Send email alert to engineering leads
          ├─ 100% Threshold: Apply restrictive IAM policy or invoke SSM Automation
          └─ 120% Threshold: Stop non-essential dev/test instances
```

### 4.1 Cost Allocation Tags & Tag Policies

- **Tag Activation**: Creating a tag on an EC2 instance does *not* automatically expose it in billing reports. Tags must be explicitly **activated** in the AWS Billing & Cost Management console before they appear in Cost Explorer and AWS Cost and Usage Reports (CUR).
- **Tag Policies in AWS Organizations**: Enforce strict tag key casing and allowable values (e.g., `Environment` must equal `Production`, `Staging`, or `Development`). Tag policies report non-compliant resources (and can block non-compliant tagging operations on supported services); to refuse resource creation without a required tag, add an SCP that checks `aws:RequestTag`.

### 4.2 AWS Cost Anomaly Detection

Traditional budgets notify teams only after spending thresholds are crossed or forecasted to breach at month-end. **AWS Cost Anomaly Detection** uses machine learning models to monitor spending patterns continuously:

- Establishes statistical baselines for normal spending per account, service, or cost allocation tag.
- Detects unexpected anomalies (e.g., an unauthorized GPU instance spinning up or an accidental infinite loop in a Lambda function writing petabytes to S3) and delivers root-cause analysis alerts via Amazon SNS or EventBridge within hours.

## 5. Domain 3 Scenario Decision Matrix

When resolving cost optimization questions on SAP-C03, evaluate competing choices against the following principles:

| Primary Constraint | Evaluated Options | Winning Architecture & Exam Justification |
| :--- | :--- | :--- |
| **Max discount for heterogeneous containerized microservices evolving across EC2, Fargate, and Lambda in multiple regions** | • Standard EC2 Reserved Instances<br>• EC2 Instance Savings Plans<br>• Compute Savings Plans | **Compute Savings Plans**. Automatically applies across EC2, Fargate, and Lambda across any AWS region, family, or OS without manual exchange. |
| **High NAT Gateway processing bills caused by container tasks pulling large data sets from Amazon S3** | • Deploy dual NAT Gateways in each AZ<br>• Configure S3 Gateway Endpoint in private route tables<br>• Move containers into public subnets | **S3 Gateway Endpoint**. Gateway Endpoints for S3 are 100% free with zero data processing charges, completely bypassing the expensive NAT Gateway. |
| **Legacy fleet of 200 EC2 instances using `gp2` EBS volumes requiring higher IOPS without over-provisioning storage** | • Upgrade to `io2` Block Express volumes<br>• Increase `gp2` volume size to 3 TB to burst IOPS<br>• Convert all volumes to `gp3` via Elastic Volumes | **Convert to `gp3`**. `gp3` is 20% cheaper per GB than `gp2` and provides 3,000 baseline IOPS for free with decoupled IOPS/throughput configuration. `io2` is prohibitively expensive for general workloads. |
| **Automate governance to stop dev/test EC2 and RDS instances when project monthly budget exceeds 100%** | • Weekly manual review of Cost Explorer<br>• AWS Budgets with configured Budget Actions (SSM / IAM execution role)<br>• CloudWatch billing alarm with manual SNS email | **AWS Budgets with Budget Actions**. Natively triggers automated target actions (stopping instances or attaching an IAM deny policy) when actual or forecasted budget thresholds are exceeded. |
