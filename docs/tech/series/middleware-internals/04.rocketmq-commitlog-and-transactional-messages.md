If Apache Kafka is the undisputed champion of high-throughput log aggregation and event streaming, why did Alibaba engineer **Apache RocketMQ** to handle China's Singles' Day (11.11) shopping festival?

The architectural divergence boils down to a fundamental physical storage limitation:

- In Kafka, **every partition is an independent physical file on disk**. When a single cluster hosts **10,000 distinct topics or partitions**, concurrent writes scatter across thousands of separate files, degrading sequential disk I/O toward random access (worst on spinning disks; NVMe softens it).
- RocketMQ solves this by routing **100% of all topics and queues into a single, unified sequential file: the `CommitLog`**.

This chapter explores RocketMQ's storage engine, traces how the **`ReputMessageService`** asynchronously builds lightweight 20-byte **`ConsumeQueue`** indices, and analyzes the **Two-Phase Commit (2PC) Half-Message protocol** that guarantees distributed consistency without distributed transactions.

## 1. Unified CommitLog vs. Partitioned Storage: The 10,000-Topic Problem

Compare how Kafka and RocketMQ write messages to physical disks:

```text
  Kafka (Partitioned Files)                 RocketMQ (Unified CommitLog)
  =========================                 ============================
  Topic A, Part 0 -> /orders-0.log          Topic A \
  Topic A, Part 1 -> /orders-1.log          Topic B  ==> Single Append-Only
  Topic B, Part 0 -> /payments-0.log        Topic C /    CommitLog (1 GiB Files)
  Topic C, Part 0 -> /inventory-0.log
```

- **Kafka's Scaling Limit**: When partition counts grow into the thousands, the OS file system can no longer maintain sequential writes across thousands of open file descriptors simultaneously. Disk write buffers saturate, write latency spikes, and broker throughput collapses.
- **RocketMQ's Sequential Invariant**: Regardless of whether you have 10 topics or 50,000 queues, **all incoming messages append sequentially to a single 1 GiB file (`CommitLog`)** mapped into virtual memory using Java's `MappedByteBuffer` (`mmap`). The physical disk head moves strictly forward, maintaining peak sequential write throughput under extreme topic cardinality.

## 2. Asynchronous Dispatch: `ReputMessageService` & the 20-Byte `ConsumeQueue`

If all messages from all topics are intermingled in one massive `CommitLog`, how does a consumer subscribe to only `Topic_Orders` without reading the entire multi-gigabyte log?

RocketMQ separates **Data Storage (`CommitLog`)** from **Consumer Indexing (`ConsumeQueue`)**:

```text
                       CommitLog (1 GiB MappedFile)
  +------------------------------------------------------------------------+
  | [Msg 1: Orders (120B)] | [Msg 2: Payments (450B)] | [Msg 3: Orders]    |
  +------------------------------------------------------------------------+
              |                                            |
              +----------------------+                     |
                                     |                     |
                                     v                     v
                     ConsumeQueue for Topic_Orders (20B Fixed Entries)
                     +-----------------------------------------------+
                     | Entry 0: CommitLogOffset (8B) | Size | TagHash|
                     | Entry 1: CommitLogOffset (8B) | Size | TagHash|
                     +-----------------------------------------------+
```

1. **The Background Dispatcher (`ReputMessageService`)**:
   A dedicated daemon thread continuously polls newly appended bytes in the `CommitLog`.
2. **Fixed-Size 20-Byte `ConsumeQueue` Entries**:
   For each message, `ReputMessageService` writes a fixed **20-byte index entry** into that specific topic's `ConsumeQueue`:
   $$\text{Entry Layout} = \underbrace{\text{CommitLog Offset}}_{8\text{ bytes}} + \underbrace{\text{Message Size}}_{4\text{ bytes}} + \underbrace{\text{Tag HashCode}}_{8\text{ bytes}} = \mathbf{20\text{ bytes}}$$
3. **Consumer Read Flow**:
   - The consumer pulls from the lightweight `ConsumeQueue` file using consumer offset $K$.
   - Because every entry is exactly 20 bytes, calculating the byte position of offset $K$ is a simple multiplication: $\text{pos} = K \times 20$.
   - The broker compares the `Tag HashCode` while serving the pull (the client re-checks the tag string); on a match it reads the 8-byte `CommitLog Offset` and fetches the full payload directly from the `CommitLog`!

## 3. Transactional Messages: The 2PC Half-Message Protocol

In microservice architectures, an order service must insert an order record into a local MySQL database and send an `OrderCreated` message to downstream inventory and payment services. If the database commit succeeds but the message broker crashes (or vice versa), the system enters a split-brain state.

RocketMQ solves this at the protocol level using **Transactional Half-Messages**:

```text
  Producer                     RocketMQ Broker                    MySQL Database
     |                               |                                  |
  1. |-- Send Half-Message --------->| (Saves in RMQ_SYS_TRANS_HALF)    |
     |<-- Half-Message ACK ----------| (Message NOT visible to users!)  |
     |                               |                                  |
  2. |-- Execute Local Transaction ------------------------------------>|
     |                               |                                  |
  3. |-- Commit / Rollback --------->| (If Commit: moves to real topic) |
     |                               | (Consumers now receive message!) |
```

### The Transaction State Machine

1. **Phase 1 (Prepare / Half-Message)**:
   The producer sends a message with transaction flags. The broker intercepts the message and changes its topic to an internal system topic: **`RMQ_SYS_TRANS_HALF_TOPIC`**.
   - Because consumers only subscribe to user topics, **the message is completely invisible to consumer queues**.
   - The broker returns success to the producer.
2. **Phase 2 (Execute Local Transaction)**:
   The producer executes its local database transaction within the same process.
3. **Phase 3 (Commit or Rollback)**:
   - If the database commit succeeds, the producer sends `COMMIT_MESSAGE`. The broker copies the message into the real user topic queue, making it immediately visible to consumers!
   - If the database transaction fails, the producer sends `ROLLBACK_MESSAGE`, and the broker marks the half-message as deleted.

### What If the Producer Crashes Before Phase 3? (Transaction Check Back)

What if the producer's network drops or its JVM crashes immediately after committing to the database, before sending `COMMIT_MESSAGE` to RocketMQ?

- RocketMQ runs a background **Transaction Check-Back Service**:
- If a half-message sits in `RMQ_SYS_TRANS_HALF_TOPIC` for longer than a configurable threshold (seconds to about a minute, depending on version and broker settings), the broker initiates an RPC call back to any available producer instance: *"What was the final status of Transaction ID X?"*
- The producer queries its local database transaction log table and responds with `COMMIT` or `ROLLBACK`, ensuring eventual consistency without distributed two-phase commit locks.

## 4. Verification Lab: RocketMQ CommitLog Append & 2PC Transaction State Machine

The following self-contained Python 3 program (`python3 lab04_rocketmq.py`) implements and verifies:

1. **CommitLog Append & 20-Byte ConsumeQueue Dispatch**: Appends messages from different topics to a unified `CommitLog` and verifies that the `ConsumeQueue` generates 20-byte entries with correct offsets and tag hashes.
2. **2PC Half-Message State Machine with Check-Back**: Simulates a producer crash after local database commit, proving that the broker's check-back routine queries transaction state and commits the message without data loss.

```python
#!/usr/bin/env python3
"""
Verification Lab 04: RocketMQ CommitLog Append, ConsumeQueue Dispatch & 2PC Half-Messages
Run directly: python3 lab04_rocketmq.py
"""
import struct
from dataclasses import dataclass, field
from typing import Dict, List, Optional, Tuple


# ---------------------------------------------------------------------------
# 1. RocketMQ CommitLog & ConsumeQueue Simulator
# ---------------------------------------------------------------------------
@dataclass
class Message:
    topic: str
    tags: str
    body: bytes
    tx_id: Optional[str] = None


class RocketMQBroker:
    HALF_TOPIC = "RMQ_SYS_TRANS_HALF_TOPIC"

    def __init__(self):
        self.commit_log: bytearray = bytearray()
        self.consume_queues: Dict[str, bytearray] = {}  # topic -> 20B entry bytearray
        self.half_messages: Dict[str, Tuple[int, Message]] = {}  # tx_id -> (commitLogOffset, msg)

    def _tag_hash(self, tag: str) -> int:
        return hash(tag) & 0xFFFFFFFFFFFFFFFF

    def append_to_commitlog(self, msg: Message) -> int:
        offset = len(self.commit_log)
        payload = msg.body
        # Write CommitLog record: [size:4B | topic_len:2B | topic | tags_len:2B | tags | payload]
        topic_b = msg.topic.encode()
        tags_b = msg.tags.encode()
        record_len = 4 + 2 + len(topic_b) + 2 + len(tags_b) + len(payload)
        header = struct.pack(">IH", record_len, len(topic_b))
        self.commit_log.extend(header)
        self.commit_log.extend(topic_b)
        self.commit_log.extend(struct.pack(">H", len(tags_b)))
        self.commit_log.extend(tags_b)
        self.commit_log.extend(payload)
        return offset

    def dispatch_consume_queue(self, topic: str, commit_offset: int, msg_size: int, tag: str) -> None:
        if topic not in self.consume_queues:
            self.consume_queues[topic] = bytearray()
        # ConsumeQueue Entry: [CommitLogOffset:8B | Size:4B | TagHash:8B] = 20 Bytes!
        entry = struct.pack(">QIQ", commit_offset, msg_size, self._tag_hash(tag))
        assert len(entry) == 20
        self.consume_queues[topic].extend(entry)

    # -----------------------------------------------------------------------
    # 2PC Half-Message Transaction Lifecycle
    # -----------------------------------------------------------------------
    def send_half_message(self, msg: Message) -> str:
        tx_id = f"tx_{len(self.half_messages) + 1}"
        msg.tx_id = tx_id
        # Save in CommitLog under internal HALF topic so consumers cannot see it!
        half_msg = Message(topic=self.HALF_TOPIC, tags=msg.tags, body=msg.body, tx_id=tx_id)
        offset = self.append_to_commitlog(half_msg)
        self.half_messages[tx_id] = (offset, msg)
        return tx_id

    def commit_transaction(self, tx_id: str) -> None:
        if tx_id not in self.half_messages:
            raise KeyError(f"Unknown transaction ID: {tx_id}")
        offset, original_msg = self.half_messages.pop(tx_id)
        # Commit: Append to CommitLog as real user topic and dispatch ConsumeQueue!
        real_offset = self.append_to_commitlog(original_msg)
        self.dispatch_consume_queue(
            original_msg.topic, real_offset, len(original_msg.body), original_msg.tags
        )

    def check_back_and_resolve(self, producer_tx_status_resolver) -> List[str]:
        resolved = []
        for tx_id, (offset, msg) in list(self.half_messages.items()):
            status = producer_tx_status_resolver(tx_id)
            if status == "COMMIT":
                self.commit_transaction(tx_id)
                resolved.append(f"{tx_id}:COMMIT")
            elif status == "ROLLBACK":
                self.half_messages.pop(tx_id)
                resolved.append(f"{tx_id}:ROLLBACK")
        return resolved


def main() -> None:
    print("=== 1. RocketMQ Unified CommitLog & 20-Byte ConsumeQueue Dispatch ===")
    broker = RocketMQBroker()

    # Append normal messages across different topics to the SAME CommitLog!
    m1 = Message("Orders", "VIP", b"Order #1001 payload")
    m2 = Message("Payments", "Credit", b"Payment #2001 payload")

    off1 = broker.append_to_commitlog(m1)
    broker.dispatch_consume_queue("Orders", off1, len(m1.body), "VIP")

    off2 = broker.append_to_commitlog(m2)
    broker.dispatch_consume_queue("Payments", off2, len(m2.body), "Credit")

    print(f"  Unified CommitLog size: {len(broker.commit_log)} bytes (shared across all topics)")
    print(f"  ConsumeQueue['Orders'] size: {len(broker.consume_queues['Orders'])} bytes (expected 20 bytes)")
    print(f"  ConsumeQueue['Payments'] size: {len(broker.consume_queues['Payments'])} bytes (expected 20 bytes)")
    assert len(broker.consume_queues["Orders"]) == 20
    assert len(broker.consume_queues["Payments"]) == 20

    print("\n=== 2. 2PC Half-Message Transaction & Check-Back Verification ===")
    # Step 1: Producer sends Half-Message
    tx_msg = Message("Orders", "Create", b"Order #1002 $99.00")
    tx_id = broker.send_half_message(tx_msg)
    print(f"  Half-Message sent with tx_id={tx_id} (not visible in Orders ConsumeQueue: len={len(broker.consume_queues.get('Orders', b''))})")
    assert "Orders" not in broker.consume_queues or len(broker.consume_queues["Orders"]) == 20

    # Step 2: Producer commits locally to MySQL, but network drops before sending commit RPC!
    producer_db_state = {tx_id: "COMMIT"}

    # Step 3: Broker triggers Transaction Check-Back to query producer DB state
    resolved = broker.check_back_and_resolve(lambda tid: producer_db_state.get(tid, "UNKNOWN"))
    print(f"  Broker check-back resolved: {resolved}")
    print(f"  Orders ConsumeQueue size post-commit: {len(broker.consume_queues['Orders'])} bytes (now 40 bytes!)")
    assert len(broker.consume_queues["Orders"]) == 40
    print("\nAll RocketMQ Internals Lab 04 invariants verified.")


if __name__ == "__main__":
    main()
```

## Key Takeaways

1. **Unified `CommitLog` maintains sequential disk I/O at high topic scale**: Routing all topics into a single sequential `CommitLog` prevents the multi-file random I/O head thrashing seen in Kafka clusters with 10,000+ partitions.
2. **Fixed 20-byte `ConsumeQueue` entries provide $O(1)$ indexing**: Storing only `commitLogOffset`, `size`, and `tagHash` keeps consumer indices tiny and memory-mapped for high-speed cache-friendly reads.
3. **2PC Half-Messages guarantee cross-service consistency without distributed locks**: Storing half-messages in an invisible system topic combined with transaction check-backs bridges local database commits and asynchronous event delivery reliably.
