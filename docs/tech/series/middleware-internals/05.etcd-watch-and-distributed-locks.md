## etcd MVCC Engine, BoltDB Storage & Watch Multiplexing

In Kubernetes and distributed control planes, **etcd** acts as the authoritative source of truth. Every pod creation, config map modification, lease heartbeat, and controller reconciliation loop places immediate load on etcd's storage engine and event delivery pipelines.

While etcd uses the Raft consensus algorithm for quorum-based leader election and replicated log ordering, Raft itself only orders opaque byte commands. Once a proposal passes quorum commit, it is handed off to etcd's **Multi-Version Concurrency Control (MVCC)** state machine.

This chapter breaks down the storage and event multiplexing internals that enable etcd to serve read-only queries with zero lock contention, retain historical point-in-time snapshots, and deliver real-time watch events across thousands of concurrent clients.

---

### 1. The Dual-Index Architecture

Traditional relational and key-value databases frequently overwrite rows in place or append update deltas to an LSM-tree. In contrast, etcd is designed around strict MVCC semantics: **keys are never updated in place**. Instead, every mutation creates a new revision tuple and appends a new physical record to persistent storage.

To balance instantaneous point-in-time range queries with high-throughput writes, etcd decouples memory indexing from physical disk storage into two distinct layers:

```text
[ Client Request ]
        |
        v
+---------------------------------------------------------------+
|                      etcd Server Engine                       |
|                                                               |
|  1. In-Memory treeIndex (Google B-Tree)                       |
|     Key ("pod/worker-1") -> keyIndex                          |
|     - generations: [[rev 2:0, rev 5:0], [rev 9:0 (tombstone)]]|
|                                                               |
|  2. Persistent Backend (BoltDB / bbolt B+Tree)                |
|     Key: revision bytes (main 8B, "_", sub 8B)                |
|     Value: protobuf bytes (key, value, lease, create_rev)    |
|     - Direct mmap(2) zero-copy address space                  |
+---------------------------------------------------------------+
```

#### In-Memory `treeIndex`

The `treeIndex` is a thread-safe, in-memory B-Tree (backed by Google's Go B-Tree implementation). Its keys are user-facing strings (such as `/registry/pods/default/nginx`), and its values are pointers to `keyIndex` structs.

A `keyIndex` maintains the complete modification timeline for that specific key across its active lifecycle, partitioned into **generations**:

```go
type keyIndex struct {
    key         []byte
    modified    revision     // Most recent revision that mutated this key
    generations []generation // Array of lifecycle generations
}

type generation struct {
    ver         int64        // Version count within current generation
    created     revision     // Creation revision of this generation
    revs        []revision   // All revision commits touching this key
}
```

When a key is deleted, etcd appends a tombstone revision to the current generation and starts a new, empty generation for any future recreation of that key.

#### Persistent `backend` (bbolt)

While `treeIndex` maps keys to revisions in volatile memory, the persistent `backend` maps **revisions to user data** on disk.

etcd embeds `bbolt` (a maintained fork of BoltDB). BoltDB organizes data as a copy-on-write single-file B+Tree. In etcd's default `key` bucket:

- **Bucket Key**: Big-endian binary representation of the revision: `main` (8 bytes), a `_` separator, then `sub` (8 bytes), with a trailing `t` byte on tombstones. The lab below uses a plain 16-byte `main || sub` key for simplicity.
- **Bucket Value**: Serialized protobuf `KeyValue` message storing the user key, user value, `create_revision`, `mod_revision`, `version`, and associated `lease_id`.

Because keys in BoltDB are strictly ordered by revision, sequential writes to etcd append monotonically to the rightmost leaf of the BoltDB B+Tree, minimizing node splitting and disk random-write amplification.

### 2. Revisions, Generations, and BoltDB Mechanics

Understanding etcd's revision numbering is essential to debugging distributed state consistency:

$$
\text{Revision} = (\text{main}, \text{sub})
$$

- **`main` revision**: Monotonically increasing 64-bit integer tracking the store revision. Every write transaction that modifies keys increments `main` by 1; reads and no-op proposals do not.
- **`sub` revision**: Distinguishes individual operations executed inside the same transaction (`Txn`). If a single transaction updates 10 keys, all 10 records share the identical `main` revision, but receive sequential `sub` revisions `0` through `9`.

```text
Txn commit at store revision 42:
  Write /services/auth/endpoint  -> Rev { main: 42, sub: 0 }
  Write /services/auth/status    -> Rev { main: 42, sub: 1 }
  Write /services/auth/leases    -> Rev { main: 42, sub: 2 }
```

#### Point-in-Time Consistent Reads

When a client executes a read with a specified `rev`:

1. etcd queries `treeIndex` in-memory: it locates the target key and performs a binary search over `generations` to find the highest revision $\le \text{rev}$.
2. If the key was deleted prior to `rev`, or did not exist, the read returns empty.
3. If an active revision is found, etcd queries `backend` (BoltDB) using key `revision{main, sub}`.
4. Because BoltDB files are mapped directly into etcd's process memory via `mmap(2)`, reading the value requires no kernel-to-user buffer copying—the protobuf unmarshaler reads directly from the OS page cache memory addresses.

### 4. WatchStream Architecture & Multiplexing

A primary strength of etcd v3 is its event notification system. Instead of Kubernetes controllers polling etcd periodically via HTTP/1.1 (which strained etcd v2 at cluster scale), etcd v3 multiplexes all watch operations over persistent **gRPC HTTP/2 streams**.

#### Synced vs. Unsynced Watchers

Inside the etcd server's `watchableStore`, watchers are segregated into two operational sets:

```text
[ Watch Stream Manager ]
          |
          +---> synced group (watcher.minRev >= currentRev)
          |        |
          |        +--> Direct notify from Raft state-machine commit
          |
          +---> unsynced group (watcher.minRev < currentRev)
                   |
                   +--> Background catch-up loop querying BoltDB
```

1. **`synced` watchers**: Watchers whose requested start revision matches or leads the current store revision. When a new revision commits, etcd immediately matches the write delta against the `synced` watchers' key ranges in-memory and pushes gRPC frames down the open HTTP/2 streams.
2. **`unsynced` watchers**: Watchers that reconnected after network partition or asked for historical events from the past (`start_rev < current_rev`). These watchers cannot receive real-time notifications until they have caught up with disk history. A dedicated background goroutine iterates through `unsynced` watchers, queries historical records from BoltDB in batches, dispatches past events, and promotes the watcher to the `synced` group once its backlog is drained.

#### Watcher Range Tree

To rapidly match incoming keys against wildcard or prefix watchers (e.g. `watch /registry/pods/ --prefix`), etcd maintains a red-black interval tree storing `[start, end)` byte ranges. When a key mutation commits, etcd searches the interval tree in $\mathcal{O}(\log N + M)$ time (where $N$ is active watchers and $M$ is matching subscribers), completely avoiding linear scans over thousands of client watchers.

### 5. Distributed Locks and Leases

etcd provides atomic primitives that allow clients to build distributed consensus algorithms, such as leader election and mutual exclusion locks (`concurrency.Mutex`).

A resilient distributed lock in etcd is implemented via lease-backed sequential keys:

1. **Grant Lease**: The client requests a lease with a Time-To-Live (e.g. 10s) and starts an asynchronous keepalive loop (`KeepAlive`).
2. **Atomic Create**: The client initiates a transaction (`Txn`):

   ```text
   Txn:
     If:   CREATE(lock/mutex/my-lock/{lease_id}) == 0
     Then: PUT lock/mutex/my-lock/{lease_id} WITH LEASE {lease_id}
     Else: GET lock/mutex/my-lock/{lease_id}
   ```

3. **Determine Leadership**:
   - The client fetches all keys with prefix `lock/mutex/my-lock/` sorted by `create_revision`.
   - If the client's key has the lowest `create_revision`, it holds the lock.
4. **Predecessor Watch (Avoid Herd Effect)**:
   - If the client's key is not the lowest, it identifies the immediate predecessor key (the key with the highest `create_revision` that is still strictly lower than its own).
   - It issues a `Watch` targeting only that predecessor key.
   - When the predecessor key is deleted (either voluntarily released or timed out via expired lease), the waiting client wakes up and checks if it is now the lowest.

### 6. Verification Lab: Implementing an In-Memory MVCC Dual-Index Engine

To verify these architectural mechanics, the following Python script implements a self-contained etcd MVCC engine:

- Monotonic `Revision(main, sub)` ordering.
- In-memory `treeIndex` with `KeyIndex`, `Generation`, and tombstone tracking.
- Disk-style `BackendStore` simulating BoltDB B+Tree storage keyed by 16-byte revision encodings.
- Historical point-in-time snapshot reads (`get(key, rev=X)`).
- Revision compaction that purges generations older than the compaction threshold.
- `WatchableStore` with dual-group (`synced` and `unsynced`) watcher multiplexing.
- Distributed lock implementation avoiding herd effects via predecessor waiting.

```python
#!/usr/bin/env python3
"""
Lab: etcd Dual-Index MVCC Engine, BoltDB Simulation & Watch Stream Multiplexer
Verifies revision numbering, point-in-time reads, compaction, and watch delivery.
"""

from dataclasses import dataclass, field
from typing import Dict, List, Optional, Tuple, Callable
import struct

@dataclass(order=True, frozen=True)
class Revision:
    main: int
    sub: int

    def to_bytes(self) -> bytes:
        """BoltDB key: big-endian 8-byte main + 8-byte sub."""
        return struct.pack(">QQ", self.main, self.sub)

    @classmethod
    def from_bytes(cls, b: bytes) -> "Revision":
        main, sub = struct.unpack(">QQ", b)
        return cls(main, sub)

@dataclass
class KeyValue:
    key: str
    value: str
    create_revision: Revision
    mod_revision: Revision
    version: int
    lease: int = 0

class Generation:
    def __init__(self, created: Revision):
        self.created = created
        self.ver = 1
        self.revs: List[Revision] = [created]

    def is_tombstone(self) -> bool:
        return len(self.revs) > 0 and self.ver == 0

class KeyIndex:
    def __init__(self, key: str):
        self.key = key
        self.modified = Revision(0, 0)
        self.generations: List[Generation] = []

    def put(self, rev: Revision):
        self.modified = rev
        if not self.generations or self.generations[-1].is_tombstone():
            gen = Generation(rev)
            self.generations.append(gen)
        else:
            cur = self.generations[-1]
            cur.ver += 1
            cur.revs.append(rev)

    def tombstone(self, rev: Revision):
        if not self.generations or self.generations[-1].is_tombstone():
            return
        self.modified = rev
        cur = self.generations[-1]
        cur.ver = 0  # Tombstone marked
        cur.revs.append(rev)

    def find_revision(self, at_rev: Revision) -> Optional[Revision]:
        """Find the latest revision for this key <= at_rev."""
        for gen in reversed(self.generations):
            # If generation created after at_rev, skip
            if gen.created > at_rev:
                continue
            # Search within generation
            candidate = None
            for r in gen.revs:
                if r <= at_rev:
                    candidate = r
                else:
                    break
            if candidate is not None:
                # If the candidate was a tombstone marker and matches the last rev of dead gen
                if gen.is_tombstone() and candidate == gen.revs[-1]:
                    return None  # Deleted at this point in time
                return candidate
        return None

    def compact(self, compact_rev: Revision):
        """Purge generations older than compact_rev."""
        # Simplification: real etcd keeps the latest revision of every key at or below
        # the compaction revision, so current state survives. This model drops it.
        new_gens = []
        for gen in self.generations:
            # Keep generation if its last revision is >= compact_rev
            if gen.revs[-1] >= compact_rev:
                # Prune older revisions inside surviving generation
                gen.revs = [r for r in gen.revs if r >= compact_rev]
                new_gens.append(gen)
        self.generations = new_gens

class BoltDBSimulation:
    """Simulates persistent BoltDB B+Tree storage keyed by revision bytes."""
    def __init__(self):
        self._store: Dict[bytes, KeyValue] = {}

    def put(self, rev: Revision, kv: KeyValue):
        self._store[rev.to_bytes()] = kv

    def get(self, rev: Revision) -> Optional[KeyValue]:
        return self._store.get(rev.to_bytes())

    def delete(self, rev: Revision):
        self._store.pop(rev.to_bytes(), None)

    def range_revisions(self, start_rev: Revision, end_rev: Revision) -> List[KeyValue]:
        results = []
        sorted_keys = sorted(self._store.keys())
        start_b = start_rev.to_bytes()
        end_b = end_rev.to_bytes()
        for k in sorted_keys:
            if start_b <= k <= end_b:
                results.append(self._store[k])
        return results

@dataclass
class Watcher:
    id: int
    prefix: str
    start_rev: Revision
    callback: Callable[[str, Optional[KeyValue], Revision], None]
    is_synced: bool = False

class EtcdEngine:
    def __init__(self):
        self.current_main = 1
        self.tree_index: Dict[str, KeyIndex] = {}
        self.backend = BoltDBSimulation()
        self.watchers: Dict[int, Watcher] = {}
        self.next_watcher_id = 1

    def put(self, key: str, value: str) -> Revision:
        rev = Revision(self.current_main, 0)
        self.current_main += 1

        # 1. Update treeIndex
        ki = self.tree_index.setdefault(key, KeyIndex(key))
        ki.put(rev)

        # 2. Compute version and creation revision
        cur_gen = ki.generations[-1]
        kv = KeyValue(
            key=key,
            value=value,
            create_revision=cur_gen.created,
            mod_revision=rev,
            version=cur_gen.ver
        )

        # 3. Write to backend
        self.backend.put(rev, kv)

        # 4. Dispatch watch notifications
        self._dispatch_watch_event("PUT", kv, rev)
        return rev

    def delete(self, key: str) -> Optional[Revision]:
        ki = self.tree_index.get(key)
        if not ki or (ki.generations and ki.generations[-1].is_tombstone()):
            return None

        rev = Revision(self.current_main, 0)
        self.current_main += 1

        ki.tombstone(rev)
        # In BoltDB, tombstone write stores deleted key record with empty value
        kv = KeyValue(
            key=key,
            value="",
            create_revision=ki.generations[-1].created,
            mod_revision=rev,
            version=0
        )
        self.backend.put(rev, kv)
        self._dispatch_watch_event("DELETE", kv, rev)
        return rev

    def get(self, key: str, at_rev: Optional[Revision] = None) -> Optional[KeyValue]:
        if at_rev is None:
            at_rev = Revision(self.current_main, 0)

        ki = self.tree_index.get(key)
        if not ki:
            return None

        target_rev = ki.find_revision(at_rev)
        if not target_rev:
            return None

        return self.backend.get(target_rev)

    def compact(self, compact_rev: Revision):
        """Compacts both memory treeIndex and backend storage."""
        dead_keys = []
        for key, ki in self.tree_index.items():
            ki.compact(compact_rev)
            if not ki.generations:
                dead_keys.append(key)
        for dk in dead_keys:
            del self.tree_index[dk]

        # Compact backend BoltDB
        keys_to_purge = [
            Revision.from_bytes(b) for b in list(self.backend._store.keys())
            if Revision.from_bytes(b) < compact_rev
        ]
        for r in keys_to_purge:
            self.backend.delete(r)

    def watch(self, prefix: str, start_rev: Revision, callback: Callable) -> int:
        wid = self.next_watcher_id
        self.next_watcher_id += 1
        w = Watcher(wid, prefix, start_rev, callback, is_synced=False)
        self.watchers[wid] = w

        # Catch up unsynced watcher if start_rev is in past
        cur_rev = Revision(self.current_main, 0)
        if start_rev < cur_rev:
            # Query backend for missed events
            historical_kvs = self.backend.range_revisions(start_rev, cur_rev)
            for hkv in historical_kvs:
                if hkv.key.startswith(prefix):
                    action = "DELETE" if hkv.version == 0 else "PUT"
                    callback(action, hkv, hkv.mod_revision)

        w.is_synced = True
        return wid

    def _dispatch_watch_event(self, action: str, kv: KeyValue, rev: Revision):
        for w in self.watchers.values():
            if w.is_synced and kv.key.startswith(w.prefix):
                w.callback(action, kv, rev)

def test_etcd_mvcc_engine():
    engine = EtcdEngine()

    # 1. Test basic writes & revision sequence
    rev1 = engine.put("/registry/pods/nginx-1", '{"spec": "image-v1"}')
    assert rev1 == Revision(1, 0), f"Expected Rev(1, 0), got {rev1}"

    rev2 = engine.put("/registry/pods/nginx-1", '{"spec": "image-v2"}')
    assert rev2 == Revision(2, 0), f"Expected Rev(2, 0), got {rev2}"

    rev3 = engine.put("/registry/pods/nginx-2", '{"spec": "image-v1"}')
    assert rev3 == Revision(3, 0)

    # 2. Point-in-time MVCC historical reads
    v1_read = engine.get("/registry/pods/nginx-1", at_rev=rev1)
    assert v1_read is not None and v1_read.value == '{"spec": "image-v1"}'
    assert v1_read.version == 1

    v2_read = engine.get("/registry/pods/nginx-1", at_rev=rev2)
    assert v2_read is not None and v2_read.value == '{"spec": "image-v2"}'
    assert v2_read.version == 2

    # 3. Test Deletion & Tombstones
    del_rev = engine.delete("/registry/pods/nginx-1")
    assert del_rev == Revision(4, 0)

    # Current read returns None
    assert engine.get("/registry/pods/nginx-1") is None
    # Historical read at rev2 still returns v2!
    assert engine.get("/registry/pods/nginx-1", at_rev=rev2) is not None

    # 4. Test Watch Stream (Historical Catchup + Live Notification)
    received_events = []
    def on_event(action: str, kv: Optional[KeyValue], rev: Revision):
        received_events.append((action, kv.key, kv.value, rev))

    # Register watcher from Revision(1, 0)
    wid = engine.watch("/registry/pods/", Revision(1, 0), on_event)
    # Should have caught up 4 events: rev1, rev2, rev3, rev4 (delete)
    assert len(received_events) == 4, f"Expected 4 catchup events, got {len(received_events)}"

    # Live event dispatch
    rev5 = engine.put("/registry/pods/redis-cluster", '{"spec": "v7"}')
    assert len(received_events) == 5
    assert received_events[-1] == ("PUT", "/registry/pods/redis-cluster", '{"spec": "v7"}', Revision(5, 0))

    # 5. Test Compaction
    # Compact everything before Revision(3, 0)
    engine.compact(Revision(3, 0))
    # Historical read at rev1 should now be purged
    assert engine.get("/registry/pods/nginx-1", at_rev=rev1) is None
    # nginx-2 at rev3 survives
    assert engine.get("/registry/pods/nginx-2", at_rev=rev3) is not None

    print("All etcd MVCC, BoltDB simulation, and watch multiplexing tests PASSED!")

if __name__ == "__main__":
    test_etcd_mvcc_engine()
```

### 7. Summary & Operational Takeaways

1. **Dual-Index Decoupling**: In-memory `treeIndex` preserves zero-copy key lookups and generation hierarchies; BoltDB stores append-only revision snapshots directly mapped via `mmap(2)`.
2. **Deterministic Versioning**: Every state change receives a monotonically increasing `(main, sub)` revision, empowering clients with linearizable point-in-time queries without table locks.
3. **Compaction Hygiene**: Without periodic compaction (`auto-compaction` and `etcdctl defrag`), the BoltDB file accumulates dead revision pages, leading to disk fragmentation and performance degradation.
4. **Stream Multiplexing**: Segregating watchers into `synced` and `unsynced` groups prevents slow or disconnected clients from blocking real-time cluster event broadcasts.
