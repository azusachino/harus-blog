Why can a single-threaded Redis process store tens of millions of keys in RAM while serving over 100,000 requests per second with sub-millisecond latency?

The primary reason is not the C language or kernel I/O multiplexing (`epoll`). It is Redis's **aggressive mechanical memory layout**:

- A string in C is a raw `char*` requiring $O(N)$ `strlen()` scans and prone to buffer overflows. Redis wraps strings in **Simple Dynamic Strings (SDS)**, fitting header metadata into single-byte flags (`sdshdr8`).
- Small hashes, lists, and sorted sets do not allocate heavy pointer-linked nodes; they pack members into contiguous, cache-friendly byte arrays called **`listpack`**.
- When hash tables grow from thousands to millions of keys, Redis never locks the server to rehash. It amortizes the resizing cost across incoming CRUD commands using **Progressive Dual-Table Rehashing**.

This opening chapter descends into `redis/src/sds.h`, `listpack.c`, and `dict.c` to trace how Redis maximizes CPU L1/L2 cache locality and eliminates memory fragmentation.

## Before you start

This series is for programmers who use Redis, Kafka, RocketMQ, etcd and Nginx and want to know what happens inside them; the chapters build on each other, though each product gets its own chapters.

Redis keeps everything in RAM, so every wasted byte costs money, and it runs commands on one thread, so one slow operation stalls everyone. Both facts push its authors toward compact memory layouts. Try `SET name haru` and `HSET user:1 name haru age 30`: behind these small commands, Redis picks a different internal representation depending on the size of the data.

This chapter covers the string type that replaces C strings, the packed byte array used for small collections, the skiplist behind sorted sets, and how the main hash table grows without freezing the server.

You need only basic C-like ideas (pointers, arrays, malloc). The memory-allocation background is in [Linux systems chapter 05](/tech/series/linux-systems/05.processes-and-virtual-memory/).

Terms used in this chapter:

- **SDS**: Simple Dynamic String, Redis's string type, which stores its length and spare capacity beside the bytes.
- **embstr**: a string encoding that places the header and a short value in one memory allocation.
- **listpack**: a compact, contiguous byte array holding the elements of a small list, hash or sorted set.
- **cascading update**: the old ziplist flaw where growing one entry forced a rewrite of the following entries.
- **skiplist**: a sorted linked list with extra "express" levels that make search take logarithmic time on average.
- **ZSet**: Redis's sorted set, members ordered by a score.
- **rehashing**: moving every entry from a hash table into a larger one.
- **jemalloc**: the memory allocator Redis normally uses, which hands out memory in fixed size classes.

## 1. Simple Dynamic Strings (SDS): `raw` vs. `embstr`

Standard C strings terminate with a null byte (`\0`). To compute the length of a string, `strlen()` must traverse memory byte by byte until it encounters `\0`—costing $O(N)$ CPU instructions and failing if the payload contains binary zeros (such as images, protobufs, or encrypted data).

Redis replaces C strings with **Simple Dynamic Strings (SDS)**:

```c
// From redis/src/sds.h:
struct __attribute__ ((__packed__)) sdshdr8 {
    uint8_t len;         /* used bytes (excluding null terminator) */
    uint8_t alloc;       /* total allocated capacity */
    unsigned char flags; /* 3 bits for type (SDS_TYPE_8), 5 bits unused */
    char buf[];          /* flexible array member */
};
```

Using `__attribute__ ((__packed__))`, the compiler forbids struct field padding: `flags` sits immediately adjacent to `buf[0]`. Given an SDS pointer `s = &buf[0]`, accessing `flags` is a simple constant-offset instruction `s[-1]`, and accessing `len` is `s[-3]`.

### The 64-Byte `jemalloc` Memory Boundary: `embstr` vs. `raw`

When you store a string value, Redis wraps it in a 16-byte object descriptor (`robj`):

```c
typedef struct redisObject {
    unsigned type:4;       /* OBJ_STRING */
    unsigned encoding:4;   /* OBJ_ENCODING_RAW or OBJ_ENCODING_EMBSTR */
    unsigned lru:24;       /* LRU / LFU eviction clock */
    int refcount;          /* 4 bytes */
    void *ptr;             /* 8 bytes pointer to SDS */
} robj;
```

Redis pairs with the high-performance memory allocator **`jemalloc`**, which carves memory into fixed size classes (`8B, 16B, 32B, 48B, 64B, 80B, 96B, 128B...`).

- A `robj` header takes **16 bytes**.
- An `sdshdr8` header takes **3 bytes** (`len:1B + alloc:1B + flags:1B`).
- A null terminator `\0` takes **1 byte**.
- Remaining space in a 64-byte `jemalloc` slab: $64 - 16 - 3 - 1 = \mathbf{44\text{ bytes}}$.

```text
  1. EMBSTR Encoding (len <= 44 bytes): SINGLE 64-Byte Allocation!
  +----------------------+--------------------+---------------------+
  | robj Header (16 B)   | sdshdr8 Header (3B)| String Data (<=44B) |
  +----------------------+--------------------+---------------------+
  ptr points directly to adjacent memory! 1 malloc, 1 L1 cache-line load!

  2. RAW Encoding (len > 44 bytes): TWO Separate Allocations!
  +----------------------+          +--------------------+------------------+
  | robj Header (16 B)   | -------> | sdshdr8/16/32/64  | String Data      |
  +----------------------+          +--------------------+------------------+
```

When a string is $\le 44$ bytes, Redis allocates both `robj` and `sds` in a **single contiguous 64-byte block (`OBJ_ENCODING_EMBSTR`)**. This eliminates heap fragmentation and ensures the CPU loads the entire object into L1 cache in a single memory fetch.

## 2. From `ziplist` to `listpack`: Eliminating Cascading Updates

In older Redis versions, small Lists, Hashes, and ZSets were encoded as a **`ziplist`**—a single byte array packing entries without pointer indirection. However, `ziplist` entries stored the length of the *previous* entry (`prevlen`) to support backward traversal:

```text
  Ziplist Entry: [ prevlen (1B or 5B) | encoding | content ]
```

### The Cascading Update Nightmare

If an entry's size increased from 253 bytes to 254 bytes, the *next* entry's `prevlen` field had to expand from 1 byte to 5 bytes. That expansion increased the *next* entry's size beyond 254 bytes, triggering a **chain reaction of reallocations across thousands of entries (Cascading Update)**!

### Redis 7+ Solution: `listpack`

In Redis 7+, `ziplist` was replaced by **`listpack`** (`listpack.c`) for hashes, sorted sets and the nodes of quicklists:

- `listpack` encodes **only its own element length at the end of each entry** (`backlen`), using a variable-length 7-bit encoding where the high bit indicates continuation:

  ```text
  Listpack Entry: [ encoding | data | backlen (1 to 5 bytes) ]
  ```

- To traverse backwards, Redis reads the `backlen` of the current entry, subtracts it from the current pointer, and lands directly at the start of the previous entry.
- Because an entry never stores the size of its predecessor, modifying or inserting an entry **never triggers cascading updates**.

## 3. Skiplist vs. Red-Black Trees in Sorted Sets (ZSet)

A Redis Sorted Set (`zset`) allows $O(1)$ member score lookups via a hash table (`dict`), while simultaneously supporting $O(\log N + M)$ range queries (`ZRANGEBYSCORE`) via a **Skip List (`zskiplist`)**:

```text
  Level 3: [ Head ] -------------------------------------> [ Node 80 ] -> null
  Level 2: [ Head ] -----------------> [ Node 40 ] ------> [ Node 80 ] -> null
  Level 1: [ Head ] ----> [ Node 20 ] -> [ Node 40 ] ------> [ Node 80 ] -> null
  Level 0: [ Head ] -> [ Node 10 ] -> [ Node 20 ] -> [ Node 40 ] -> [ Node 80 ] -> null
```

Why did Salvatore Sanfilippo choose a **Skip List** over a balanced binary search tree (like a Red-Black Tree or AVL tree)?

1. **Range Traversal Simplicity**: In a skip list, level 0 is an ordinary doubly linked list. Once you locate the starting score in $O(\log N)$, finding the next $M$ elements is a simple linear pointer traversal (`node = node->forward[0]`). In a Red-Black tree, finding in-order successors requires complex tree walks.
2. **Memory Overhead**: While a Red-Black tree requires 2 child pointers plus a parent pointer and color bit per node (always 3 pointers), a skip list node assigns levels probabilistically ($P = 0.25$, max 32 levels). On average, each node carries only $1 / (1 - 0.25) \approx \mathbf{1.33\text{ forward pointers}}$, consuming less memory than a balanced tree!
3. **Lock-Free Potential**: Skip lists are far easier to adapt to concurrent lock-free mutations than balancing rotations in self-balancing trees.

## 4. Progressive Dual-Table Rehashing (`dict.c`)

When a Redis dictionary (`dict`) grows beyond its load factor (1.0 under normal operation; while a `bgsave`/AOF-rewrite child exists Redis tolerates a much higher ratio, about 4 to 5 depending on the version, to minimize Copy-on-Write memory), it must expand its hash table array to the next power of two.

If a Redis instance holds **20,000,000 keys**, reallocating the array and re-hashing all 20 million keys in a single operation would block the single-threaded event loop for **hundreds of milliseconds**, triggering timeout alerts across upstream applications.

Redis solves this via **Progressive Rehashing**:

```text
  dict (Dual Table Struct)
  +-------------------------------------------------------------+
  | ht_table[0] : Old Hash Table (Dict entries being migrated)  |
  | ht_table[1] : New Hash Table (Double size: 2^(B+1))         |
  | rehashidx   : Index of current bucket being migrated (-1=off)|
  +-------------------------------------------------------------+
```

1. **Incremental Step on Every Command (`_dictRehashStep`)**: Every time a client executes `HGET`, `HSET`, `HDEL`, or `HGETALL`, Redis checks `dictIsRehashing(d)`. If true, it calls `dictRehash(d, 1)`—migrating **exactly 1 bucket** from `ht_table[0]` to `ht_table[1]` and incrementing `rehashidx`.
2. **Background Time-Slice Rehashing (`databasesCron`)**: If the server has idle CPU cycles, the background cron loop runs `dictRehashMilliseconds(d, 1)`: spending **at most 1 millisecond per tick** migrating buckets continuously.
3. **Read Path Split**: Lookups first search `ht_table[0]`. If not found, they search `ht_table[1]`.
4. **Write Path Convergence**: All new inserts (`dictAdd`) write **exclusively to `ht_table[1]`**, ensuring that `ht_table[0]` monotonically shrinks until `ht_table[0].used == 0`. At that point, `ht_table[0]` is freed, `ht_table[1]` becomes `ht_table[0]`, and `rehashidx` resets to `-1`.

## 5. Verification Lab: SDS Byte Layout, Listpack Backlen & Progressive Rehashing

The following self-contained Python 3 program (`python3 lab01_redis_internals.py`) models and verifies:

1. **SDS Memory Packing & `embstr` 44-Byte Boundary**: Verifies that strings $\le 44$ bytes fit inside a single 64-byte `jemalloc` slab.
2. **Listpack Variable-Length `backlen` Backward Traversal**: Proves that reading an entry from right to left using self-contained `backlen` requires zero cascading updates.
3. **Progressive Dual-Table Rehashing Simulator**: Runs a dual-table hash table where insertions trigger an expansion from size 4 to 8, proving that lookups and inserts maintain data consistency across incremental rehash steps without a full-table lock.

```python
#!/usr/bin/env python3
"""
Verification Lab 01: SDS Packing, Listpack backlen & Progressive Dict Rehashing
Run directly: python3 lab01_redis_internals.py
"""
from dataclasses import dataclass, field
from typing import Dict, List, Optional, Tuple


# ---------------------------------------------------------------------------
# 1. SDS & embstr 44-Byte Boundary Verification
# ---------------------------------------------------------------------------
def calculate_redis_string_allocation(payload_len: int) -> Tuple[str, int]:
    ROBJ_HEADER_BYTES = 16
    SDS_HDR8_BYTES = 3
    NULL_TERMINATOR_BYTES = 1
    total_embedded = ROBJ_HEADER_BYTES + SDS_HDR8_BYTES + payload_len + NULL_TERMINATOR_BYTES

    if payload_len <= 44:
        # jemalloc 64-byte size class holds robj + sdshdr8 + 44B data + \0
        return "OBJ_ENCODING_EMBSTR", 64
    else:
        # RAW encoding: 16B robj + separate malloc for SDS
        sds_size = (3 if payload_len < 256 else 5) + payload_len + 1
        return "OBJ_ENCODING_RAW", ROBJ_HEADER_BYTES + sds_size


# ---------------------------------------------------------------------------
# 2. Listpack Variable-Length backlen Encoding (redis/src/listpack.c)
# ---------------------------------------------------------------------------
def encode_listpack_backlen(length: int) -> bytes:
    """Encodes length into 1-5 bytes as in Redis lpEncodeBacklen (listpack.c).
    Stored big-endian with bit 7 set on all bytes except the first byte,
    allowing backward traversal to detect the entry boundary.
    """
    if length <= 127:
        return bytes([length])
    parts = []
    val = length
    while val > 0:
        parts.append(val & 0x7F)
        val >>= 7
    res = bytearray()
    res.append(parts[-1])  # first byte has bit 7 == 0 (boundary stop)
    for b in reversed(parts[:-1]):
        res.append(b | 0x80)  # trailing bytes have bit 7 == 1
    return bytes(res)


def decode_listpack_backlen(data: bytes, end_idx: int) -> int:
    """Decodes length scanning backwards from end_idx (lpDecodeBacklen in listpack.c)."""
    length = 0
    shift = 0
    idx = end_idx
    while True:
        b = data[idx]
        length |= (b & 0x7F) << shift
        if (b & 0x80) == 0:
            break
        shift += 7
        idx -= 1
    return length


# ---------------------------------------------------------------------------
# 3. Progressive Dual-Table Dict Rehashing Simulator (redis/src/dict.c)
# ---------------------------------------------------------------------------
class ProgressiveDict:
    def __init__(self, initial_cap: int = 4):
        self.ht_table: List[Optional[List[List[Tuple[str, str]]]]] = [
            [[] for _ in range(initial_cap)],
            None,
        ]
        self.rehashidx = -1
        self.count = 0

    def is_rehashing(self) -> bool:
        return self.rehashidx != -1

    def _hash(self, key: str, size: int) -> int:
        return hash(key) % size

    def rehash_step(self) -> bool:
        if not self.is_rehashing():
            return False
        # Migrate 1 non-empty bucket from ht_table[0] to ht_table[1]
        while self.rehashidx < len(self.ht_table[0]):
            bucket = self.ht_table[0][self.rehashidx]
            if bucket:
                # Move all entries in this bucket to ht_table[1]
                new_size = len(self.ht_table[1])
                for k, v in bucket:
                    new_idx = self._hash(k, new_size)
                    self.ht_table[1][new_idx].append((k, v))
                self.ht_table[0][self.rehashidx] = []
                self.rehashidx += 1
                return True
            self.rehashidx += 1

        # Finished rehashing!
        self.ht_table[0] = self.ht_table[1]
        self.ht_table[1] = None
        self.rehashidx = -1
        return False

    def put(self, key: str, val: str) -> None:
        if self.is_rehashing():
            self.rehash_step()

        # Check if resize is needed (load factor >= 1.0)
        if not self.is_rehashing() and self.count >= len(self.ht_table[0]):
            self.ht_table[1] = [[] for _ in range(len(self.ht_table[0]) * 2)]
            self.rehashidx = 0

        # Writes always go to ht_table[1] if rehashing!
        target_ht = self.ht_table[1] if self.is_rehashing() else self.ht_table[0]
        idx = self._hash(key, len(target_ht))
        target_ht[idx].append((key, val))
        self.count += 1

    def get(self, key: str) -> Optional[str]:
        if self.is_rehashing():
            self.rehash_step()

        # Look in ht_table[0] first
        idx0 = self._hash(key, len(self.ht_table[0]))
        for k, v in self.ht_table[0][idx0]:
            if k == key:
                return v

        # If rehashing, look in ht_table[1]
        if self.is_rehashing() and self.ht_table[1] is not None:
            idx1 = self._hash(key, len(self.ht_table[1]))
            for k, v in self.ht_table[1][idx1]:
                if k == key:
                    return v
        return None


def main() -> None:
    print("=== 1. SDS & embstr 44-Byte Boundary Verification ===")
    enc44, bytes44 = calculate_redis_string_allocation(44)
    enc45, bytes45 = calculate_redis_string_allocation(45)
    print(f"  String len=44 bytes -> Encoding: {enc44}, Allocated: {bytes44} bytes (single slab)")
    print(f"  String len=45 bytes -> Encoding: {enc45}, Allocated: {bytes45} bytes (dual alloc)")
    assert enc44 == "OBJ_ENCODING_EMBSTR" and bytes44 == 64
    assert enc45 == "OBJ_ENCODING_RAW"

    print("\n=== 2. Listpack backlen Variable-Length Encoding ===")
    encoded_backlen = encode_listpack_backlen(512)
    decoded_backlen = decode_listpack_backlen(encoded_backlen, len(encoded_backlen) - 1)
    print(f"  Entry length 512 encoded to {len(encoded_backlen)} bytes -> Decoded backwards: {decoded_backlen}")
    assert decoded_backlen == 512

    print("\n=== 3. Progressive Dual-Table Rehashing Verification ===")
    d = ProgressiveDict(initial_cap=4)
    for i in range(5):
        d.put(f"user:{i}", f"data_{i}")

    print(f"  After 5 inserts: rehashing={d.is_rehashing()}, rehashidx={d.rehashidx}")
    assert d.is_rehashing() is True

    # Progressively read keys to advance rehash steps
    for i in range(5):
        val = d.get(f"user:{i}")
        assert val == f"data_{i}"

    print(f"  After reads: rehashing={d.is_rehashing()}, new ht0 size={len(d.ht_table[0])}")
    assert d.is_rehashing() is False and len(d.ht_table[0]) == 8
    print("\nAll Redis Internals Lab 01 invariants verified.")


if __name__ == "__main__":
    main()
```

## Key Takeaways

1. **Keep small strings under 44 bytes to leverage `embstr`**: Strings $\le 44$ bytes are embedded contiguously with the `robj` header into a single 64-byte `jemalloc` chunk, halving allocation calls and improving L1 cache hit rates.
2. **`listpack` eliminates `ziplist` cascading reallocations**: Encoding self-contained backwards lengths (`backlen`) rather than previous entry lengths ensures insertions never trigger multi-entry resizing cascades.
3. **Progressive rehashing guarantees bounded command latency**: Migrating 1 bucket per CRUD operation and time-slicing cron tasks spreads the cost of growing massive hash tables across millions of requests instead of one long pause.
