When an in-memory database crashes, how does it recover without losing hours of writes? And when a single node exhausts its CPU or RAM capacity, how does it distribute keys across dozens of shards without a centralized proxy bottleneck?

Redis answers durability with a hybrid combination of **RDB Snapshots** and **Append-Only Files (AOF)**, and answers horizontal scaling with **Redis Cluster 16,384 Hash Slots**.

Yet beneath those simple commands (`bgsave`, `bgrewriteaof`, `cluster meet`) lurk critical operating system mechanics: the hidden latency cost of Linux **`fork(2)` page table duplication**, the memory cliff of **Copy-on-Write (CoW)**, and the exact bandwidth trade-off that dictated why Redis Cluster has **precisely 16,384 slots** instead of 65,536.

This chapter dissects the durability and clustering architecture of Redis.

---

## Before you start

Redis holds its data in memory, and memory vanishes on restart. Two questions follow. How do you save the data without freezing a server that must answer in under a millisecond? And when one machine cannot hold everything, how do clients know which of several machines owns a key?

Redis saves with snapshots (a full dump now and then) and an append-only log of write commands. To snapshot without pausing, it asks the operating system to clone the process; the clone writes the file while the original keeps serving. That trick is cheap until memory changes quickly, which is where this chapter spends its time. For scaling, Redis Cluster divides all keys into 16,384 slots and gives each node a range of them: `CLUSTER KEYSLOT user:1` tells you the slot, and a client sends the command to its owner.

Chapter 01 covers how Redis lays out memory, which explains the sizes quoted here; start with [compact encodings](/tech/series/middleware-internals/01.redis-compact-encodings-and-dict/). Virtual memory and `fork` are explained in [Linux systems chapter 05](/tech/series/linux-systems/05.processes-and-virtual-memory/).

Terms used in this chapter:

- **RDB**: a point-in-time snapshot of the whole dataset written to one file.
- **AOF**: append-only file, a log of every write command that can be replayed to rebuild the data.
- **fork**: the system call that creates a child process sharing the parent's memory pages.
- **copy-on-write (CoW)**: shared pages are copied only when one side modifies them, so a busy parent makes memory use grow.
- **replication backlog**: a fixed-size buffer of recent writes on the master, used to resync a briefly disconnected replica.
- **psync2**: Redis's partial resynchronization protocol, which resumes from an offset instead of re-sending everything.
- **hash slot**: one of 16,384 buckets of keys, each owned by one cluster node.
- **hash tag**: braces in a key, like `{user:1}`, so related keys hash to the same slot.

## 1. RDB & AOF: The Linux `fork(2)` Copy-on-Write Trap

Redis executes background snapshotting (`BGSAVE`) and background log compaction (`BGREWRITEAOF`) without halting the primary event loop by delegating the disk I/O to a child process created via Linux **`fork(2)`**:

```text
  Parent Redis Process (Port 6379, Event Loop)
  ===========================================
  1. Calls fork() -> Clones process virtual memory tables (Page Table Entries)
  2. Continues serving client writes!
         |
         | Writes modify Page X: Kernel traps -> allocates fresh private 4 KiB RAM page!
         v
  Child Process (bgsave / aof rewrite)
  ====================================
  1. Inherits read-only pointer to parent's memory snapshot at the moment of fork()
  2. Streams raw bytes sequentially to dump.rdb or appendonly.aof on disk
  3. Exits cleanly
```

### The Two Hidden Costs of `fork(2)` in Production

1. **Page Table Duplication Latency Stalls**:
   While `fork()` does not copy physical RAM pages, it **must copy the parent's Page Table Entries (PTEs)**!
   - For a Redis instance with **32 GiB of RAM** using standard 4 KiB Linux pages, there are $32\text{ GiB} / 4\text{ KiB} = \mathbf{8,388,608\text{ page entries}}$, consuming approximately **64 MiB of page table memory**.
   - Copying 64 MiB of PTEs freezes the parent process for anywhere from tens to hundreds of milliseconds depending on hardware and virtualization (the Redis docs put it on the order of 10 ms per GB of RSS), which shows up as p99 tail-latency spikes on the event loop.
2. **Copy-on-Write (CoW) Memory Exhaustion**:
   After `fork()`, the kernel marks all physical memory pages as **read-only**. Whenever the parent process writes to or modifies an existing key, the CPU triggers a page fault: the kernel allocates a new physical 4 KiB page, copies the original data, and updates the parent's PTE.
   - If your application writes heavily (e.g., updating 20% of the dataset per minute), memory consumption can surge by **several gigabytes during a single `bgsave`**, potentially triggering the Linux kernel **OOM Killer (`SIGKILL 137`)**!

> **Disable Transparent Huge Pages (THP)**:
> In Linux, THP merges 4 KiB pages into 2 MiB huge pages. With THP enabled, writing to a single 10-byte string during `bgsave` forces the kernel to copy an entire **2 MiB page** instead of 4 KiB, multiplying CoW memory consumption by up to $512\times$! Always verify THP is disabled:
>
> ```bash
> echo never > /sys/kernel/mm/transparent_hugepage/enabled
> ```

## 2. Multi-Part AOF (Redis 7.0+)

Before Redis 7.0, running `BGREWRITEAOF` required the parent process to write newly arriving commands into an in-memory **AOF Rewrite Buffer** while the child wrote the new base AOF file. Once the child finished, the parent had to flush the entire rewrite buffer to disk, causing a secondary disk I/O stall.

Redis 7.0 introduced **Multi-Part AOF**:

- The AOF is partitioned into three distinct file types managed by an `appendonly.aof.manifest` file:
  1. **Base File (`appendonly.aof.1.base.rdb`)**: Generated by the child process during compaction (can be binary RDB or text AOF).
  2. **Incremental Files (`appendonly.aof.1.incr.aof`)**: Active append log receiving live commands during and after the rewrite.
  3. **Manifest (`appendonly.aof.manifest`)**: Tracks active base and incremental file sequences.
- When compaction completes, the parent simply closes the active incremental file, updates the manifest atomically, and begins appending to a new incremental file—**completely eliminating the in-memory rewrite buffer**!

## 3. High Availability Replication: The `psync2` Protocol

How does a replica catch up after a network blip without resending the entire multi-gigabyte dataset?

Redis implements **Partial Resynchronization (`psync2`)**:

```text
  Master (ReplId1 = "4a8b...12", Master Offset = 1048576)
  +-------------------------------------------------------------+
  | Circular Replication Backlog (e.g. 16 MiB repl-backlog-size)|
  | [ ... | byte 1032192 | ... | byte 1048576 ]                 |
  +-------------------------------------------------------------+
                             ^
                             | Replica reconnects after 3-second network split:
                             | "PSYNC 4a8b...12 1035000"
```

1. **Replication ID & Offset**: Every master generates a random 40-character **`master_replid`** and increments an atomic **`master_repl_offset`** for every byte of command stream processed.
2. **Replication Backlog Buffer (`repl-backlog-size`)**: The master maintains a circular FIFO buffer in memory storing recent command bytes.
3. **The Partial Resync Decision**:
   - When a disconnected replica reconnects, it sends `PSYNC <replid> <offset>`.
   - If the replica's `replid` matches and its `offset` is **still present inside the master's circular backlog**, the master sends `+CONTINUE` and streams only the missing delta bytes (**Partial Resync**).
   - If the network split lasted too long and the replica's offset was overwritten in the circular buffer, the master responds with `+FULLRESYNC <replid> <offset>`—forcing a heavyweight `BGSAVE`, transmitting a full multi-gigabyte RDB snapshot over the network, and flushing all replica memory!

## 4. Redis Cluster: Why Exactly 16,384 Hash Slots?

Redis Cluster distributes the dataset across up to 1,000 master nodes using **16,384 virtual Hash Slots**:
$$\text{Slot} = \text{CRC16}(\text{Key}) \pmod{16384}$$

### Why Did Redis Choose 16,384 (16k) Slots Instead of 65,536 (64k)?

The CRC16 checksum natively outputs 16 bits ($2^{16} = 65,536$ possible values). Why did Salvatore Sanfilippo constrain the modulo to $16,384$ ($2^{14}$)?

1. **Heartbeat Network Packet Overhead**:
   Every node in a Redis Cluster periodically exchanges **Gossip Ping/Pong packets** with random peers to detect failures and propagate routing state.
   - Each heartbeat packet includes a **bitmap of all slots assigned to that node**.
   - With **16,384 slots**, the slot bitmap requires:
     $$\frac{16384\text{ bits}}{8\text{ bits/byte}} = \mathbf{2,048\text{ bytes (2 KiB)}}$$
   - If Redis had used 65,536 slots, the bitmap would require **8 KiB** per heartbeat packet! Across a 200-node cluster gossiping continuously, the extra 6 KiB per packet would consume substantial network bandwidth purely on cluster maintenance.
2. **Practical Cluster Size**:
   Redis Cluster is designed for clusters of up to **1,000 nodes**. With 16,384 slots, a 1,000-node cluster still averages ~16 slots per node—providing ample granularity for rebalancing.

### Hash Tags: Forcing Colocation for Multi-Key Operations

Because multi-key transactions (`MGET`, `EVAL` Lua scripts) in Redis Cluster **require all keys to reside on the same node**, how do you guarantee that a user's profile and orders map to the identical slot?

Use **Hash Tags `{...}`**:

```text
  Key 1: user:{10086}:profile
  Key 2: user:{10086}:orders
```

When Redis encounters `{...}` in a key, it computes the CRC16 hash **strictly over the string inside the curly braces** (`"10086"`), guaranteeing both keys resolve to the exact same hash slot!

def crc16(buf: bytes) -> int:
    crc = 0
    for byte in buf:
        crc = ((crc << 8) & 0xFF00) ^ CRC16_TABLE[((crc >> 8) ^ byte) & 0xFF]
    return crc & 0xFFFF


def extract_key_or_tag(key: str) -> str:
    """Extracts content inside first pair of {} if present."""
    s = key.find("{")
    if s != -1:
        e = key.find("}", s + 1)
        if e != -1 and e > s + 1:
            return key[s + 1 : e]
    return key


def key_hash_slot(key: str) -> int:
    target = extract_key_or_tag(key)
    return crc16(target.encode("utf-8")) % 16384

        return "+CONTINUE", delta_bytes

## Key Takeaways

1. **Disable Transparent Huge Pages to prevent `fork()` CoW explosion**: While `BGSAVE` runs, modifying keys with THP active forces Linux to copy 2 MiB memory pages instead of 4 KiB, rapidly exhausting host RAM.
2. **Size `repl-backlog-size` generously to avoid catastrophic full resyncs**: If a replica disconnects for longer than it takes the master to overwrite its circular buffer, the master falls back from a lightweight `+CONTINUE` delta to a cluster-stalling `+FULLRESYNC`.
3. **16,384 slots balance cluster rebalancing with 2 KiB gossip heartbeat frames**: Use curly-brace hash tags `{tag}` to guarantee that related records hash to the same slot for atomic multi-key operations.
