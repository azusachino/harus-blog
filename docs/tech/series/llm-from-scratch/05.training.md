At the end of chapter 04 we had a complete model whose weights are random numbers, so asked what follows "To be or not to", it answers with noise. **Training** is the process of fixing that, and its core is a loop of four moves: show the model some text, measure how wrong its guesses are, work out which way to change each weight to be less wrong, and change them a little. Repeat a thousand times. This chapter walks through each move with a small example and then reads calc's training loop, which is about 20 lines.

## 1. Where the right answers come from

Training needs examples with correct answers. For language, the text supplies its own: at every position, the correct answer is the next token. This is the shifted-window idea from chapter 01. Here it is with characters:

```text
text:    T  o  _  b  e  ,  _  o  r
input:   T  o  _  b  e  ,  _  o
target:  o  _  b  e  ,  _  o  r
```

Given `T`, the right answer is `o`. Given `To`, it is a space. Given `To be, o`, it is `r`. The causal mask from chapter 03 guarantees the model only uses the characters to the left of each position when it answers. One window of length T thus gives T training examples.

calc's `batch` function in `calc/core/train.py` picks random windows from the data:

```python
def batch(data: torch.Tensor) -> tuple[torch.Tensor, torch.Tensor]:
    starts = torch.randint(len(data) - config.BLOCK_SIZE, (config.BATCH_SIZE,))
    x = torch.stack([data[i : i + config.BLOCK_SIZE] for i in starts])
    y = torch.stack([data[i + 1 : i + config.BLOCK_SIZE + 1] for i in starts])
    return x, y
```

`torch.randint` picks `BATCH_SIZE` (32) random start positions. For each, `x` is a slice of `BLOCK_SIZE` (64) token IDs and `y` is the same slice shifted by one. `torch.stack` piles the 32 slices into one tensor. So `x` and `y` are both `[32, 64]`: 32 windows, 64 tokens each. Using random windows rather than reading the file in order keeps each step's data varied.

## 2. Measuring how wrong: loss

The model's output for each position is a row of **logits**, one raw score per vocabulary entry (chapter 04). To compare with the right answer we first convert them to probabilities with **softmax**, as in chapter 03: exponentiate, divide by the sum. Say a model with a 4-token vocabulary outputs logits `[2.0, 1.0, 0.1, -1.0]`. The probabilities come out as `[0.64, 0.23, 0.10, 0.03]`.

If the correct token is the first one, the model gave it 0.64, which is pretty good. If it was the last one, the model gave it 0.03, which is bad. The **loss** for a position is the negative natural logarithm of the probability given to the correct token:

```text
p(correct) = 0.64  ->  loss = -ln(0.64) = 0.45
p(correct) = 0.03  ->  loss = -ln(0.03) = 3.5
p(correct) = 1.00  ->  loss = 0
```

The logarithm turns "close to 1 is good" into "close to 0 is good", and punishes confident wrong answers heavily. This loss is called **cross-entropy**. Average it over all 32 * 64 = 2,048 positions and you have one number for the batch. Training tries to make it small.

A useful reference point: a model that knows nothing and gives all 46 characters the same probability has loss `-ln(1/46) = ln(46) = 3.83`. A randomly initialized model starts near there, and below it means the model has learned something.

In code this is a single call, inside `LanguageModel.forward`:

```python
loss = F.cross_entropy(logits.reshape(-1, logits.size(-1)), targets.reshape(-1))
```

`F.cross_entropy` expects a list of rows of logits and a list of correct IDs. `reshape(-1, ...)` flattens `[32, 64, 46]` into `[2048, 46]` and `[32, 64]` into `[2048]`. It applies the softmax and logarithm itself, which is why `forward` hands it raw logits.

## 3. Which way to adjust: gradients

The loss is a function of all 110,126 weights. If we nudge one weight up slightly, the loss goes up or down by some amount. The **gradient** of the loss with respect to that weight is that rate of change: positive means "increase this weight and the loss rises, so decrease it". Collected over all weights, the gradient points in the direction that increases the loss fastest, so we step the opposite way. ([Gradients and Backprop](/tech/series/math-for-ai/05.gradients-and-backprop/) explains the calculus.)

You do not compute these by hand. PyTorch records every operation during the forward pass, and `loss.backward()` replays them in reverse (the name for this is backpropagation) to fill in `.grad` on every parameter automatically.

An **optimizer** then applies the update. The simplest is `weight = weight - learning_rate * gradient`. The **learning rate** is the step size: too big and training overshoots and bounces around, too small and it crawls. calc uses **AdamW**, a popular variant that keeps a running average of recent gradients and scales the step for each weight individually, so weights with consistently large gradients do not take wild steps. calc sets the learning rate to `3e-4`, which is 0.0003.

## 4. The loop

This is calc's loop (checkpoint saving and the evaluation block are explained below):

```python
optimizer = torch.optim.AdamW(model.parameters(), lr=config.LEARNING_RATE)
model.train()
...
for step in range(config.STEPS):
    x, y = batch(train_data)
    _, loss = model(x, y)
    optimizer.zero_grad(set_to_none=True)
    loss.backward()
    optimizer.step()
    if step % 100 == 0 or step == config.STEPS - 1:
        model.eval()
        with torch.no_grad():
            vx, vy = batch(validation_data)
            _, validation_loss = model(vx, vy)
        print(f"step {step:4d}: train {loss.item():.3f}, val {validation_loss.item():.3f}")
        model.train()
```

(The `...` stands for a few lines in the real file that handle the `--inspect-step` option.) Line by line:

1. `batch(train_data)` gets a batch of inputs and targets.
2. `model(x, y)` runs the forward pass and returns logits and loss. We ignore the logits (`_`).
3. `optimizer.zero_grad` clears gradients left from the previous step; PyTorch accumulates them otherwise.
4. `loss.backward()` computes the gradient of the loss for every weight.
5. `optimizer.step()` changes every weight a little.

Every 100 steps it also measures the loss on data the model has not trained on. `model.eval()` switches off dropout, and `torch.no_grad()` tells PyTorch not to record operations, since no gradients are needed. `model.train()` switches back.

## 5. Training and validation data

Before the loop, `train.py` splits the encoded text:

```python
split = int(0.9 * len(tokens))
train_data, validation_data = tokens[:split], tokens[split:]
```

The first 90% is for learning; the last 10% is held back. A model with enough weights can memorize its training text, which gives a low training loss and says nothing about new text. The held-out **validation loss** is the honest measure. When training loss keeps falling while validation loss stalls or rises, the model is **overfitting**.

## 6. What the numbers look like

`make inspect` runs one batch and one optimizer step, and prints what happened:

```text
input:  shape=(32, 64), dtype=torch.int64
target: shape=(32, 64), dtype=torch.int64
example input:  ' keeper closed the door, but the stories waited patiently for an'
example target: 'keeper closed the door, but the stories waited patiently for ano'
logits: shape=(32, 64, 46)
loss: 3.9754
gradient token_embedding.weight: shape=(46, 64), norm=0.035846
gradient output.weight: shape=(46, 64), norm=0.573722
one optimizer step applied; checkpoint not written
```

The target text is the input shifted by one character. The loss of 3.98 sits just above the 3.83 you get from uniform guessing, as it should for random weights. The two gradient lines show that the error signal reaches both the embedding table and the output layer; "norm" is just the overall size of those gradients.

`make train` then runs the full 1,000 steps. Here are six of the printed lines:

```text
step    0: train 3.975, val 3.913
step  100: train 2.717, val 2.687
step  300: train 2.378, val 2.470
step  500: train 2.235, val 2.461
step  800: train 2.102, val 2.425
step  999: train 1.995, val 2.395
```

Both losses fall fast at first. After roughly step 300, validation loss improves slowly while training loss keeps dropping, and the gap is the beginning of overfitting on a corpus of only about 2,350 characters. These numbers come from one seeded run on a laptop CPU (about 17 seconds); yours can differ slightly with the PyTorch version.

## Going deeper (optional)

You can skip this section. calc uses none of the techniques below; they matter for large runs.

**Perplexity** is `exp(loss)`, read as "the number of equally likely tokens the model is effectively choosing among". Loss 3.83 means perplexity 46 (pure guessing over 46 characters); loss 2.4 is about 11.

**Numerical stability.** Computing `exp(z)` for a large logit overflows, so library implementations of cross-entropy subtract the largest logit first (the log-sum-exp trick). You get this for free from `F.cross_entropy`.

**Adam and AdamW.** Adam keeps running averages of each weight's gradient and squared gradient, and divides one by the root of the other to set the step size. AdamW applies weight decay (a small shrinkage of the weights each step) separately from that, which Loshchilov and Hutter (2017) showed generalizes better than putting the penalty into the gradient. calc uses the default weight decay.

**Big-run stabilizers.** Gradient clipping caps the overall gradient size so one odd batch cannot wreck the weights. A learning-rate schedule ramps up for a few steps and then decays along a cosine curve. Mixed precision (bfloat16) uses lower-precision numbers to go faster. None are needed for a 17-second run.

## Recap and next chapter

Training repeats one cycle: take a batch of windows, compute cross-entropy against the shifted targets, call `backward()` to get gradients, and let AdamW move every weight a little. Watching validation loss next to training loss tells you whether the model is learning or memorizing. `make train` also writes the trained weights to `artifacts/model.pt`. **[LLM from Scratch 06 - Text Generation & Inference Sampling](/tech/series/llm-from-scratch/06.generation/)** loads them and makes the model write.
