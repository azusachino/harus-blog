When should you reach for `sync.Mutex` instead of a channel? As noted in our Apricot concurrency route: **"Share memory by communicating" is a design prompt, not a religious ban on mutexes.** When a state invariant belongs to a single struct (an in-memory cache, a connection pool, a rate-limiter bucket, or a metrics registry), a `sync.Mutex` is faster, allocates zero `sudog` wrappers on the uncontended fast path, and expresses ownership directly.

Under the hood, Go's `sync` package is a masterclass in mechanical sympathy: packing a hybrid barging/FIFO lock into a single 32-bit integer (`sync.Mutex`), eliminating cross-core lock contention with per-`P` lock-free deques and two-cycle GC victim caches (`sync.Pool`), and propagating cancellation down hierarchical trees (`context.Context`).

## 1. Inside `sync.Mutex`: Normal Barging vs. 1ms Starvation Mode

Open `src/internal/sync/mutex.go` (or `src/sync/mutex.go`). An entire `sync.Mutex` occupies just **8 bytes** (`state int32` + `sema uint32`), and its zero value is an unlocked mutex ready for immediate use.

All the intelligence of `sync.Mutex` lives inside the 32 bits of **`m.state`**:

```text
  31                                                  3       2         1         0
  +----------------------------------------------------+----------+---------+---------+
  |              Waiter Count (29 bits)                | Starving |  Woken  | Locked  |
  |          Number of goroutines parked on sema       |  (1<<2)  | (1<<1)  | (1<<0)  |
  +----------------------------------------------------+----------+---------+---------+
```

- **Bit 0 (`mutexLocked = 1`)**: `1` if the mutex is currently held by a goroutine.
- **Bit 1 (`mutexWoken = 2`)**: `1` if a spinning goroutine or `Unlock()` has already notified a waiter so `Unlock()` doesn't needlessly wake a second waiter.
- **Bit 2 (`mutexStarving = 4`)**: `1` if the mutex has entered **1ms Starvation Mode** (`starvationThresholdNs = 1e6`).
- **Bits 3..31 (`mutexWaiterShift = 3`)**: Unsigned 29-bit count of goroutines currently parked on the runtime semaphore `m.sema`.

### Why a Pure FIFO Mutex Has Terrible Throughput ("Barging" in Normal Mode)

Suppose Goroutine `G1` releases a mutex (`Unlock()`) and wakes Goroutine `G2`, which was sleeping at the head of the semaphore wait queue. For `G2` to acquire the lock:

1. The scheduler must move `G2` from `_Gwaiting` to `_Grunnable`, place it on a run queue, context-switch an `M` onto `G2`, and pull the protected data structure's cache lines into that CPU core.
2. Meanwhile, suppose Goroutine `G3` is **already running on a CPU core right now** and calls `Lock()`!

In **Normal Mode (`mutexStarving == 0`)**, Go allows **`G3` to "barge in" and steal the lock** before `G2` finishes waking up:

- Even more aggressively, if `G3` sees the lock held (`mutexLocked == 1`) and `runtime_canSpin(iter)` is true (multi-core CPU, `< 4` spin iterations, local `P` run queue is empty, and the lock holder is actively running), `G3` executes **`runtime_doSpin()`** (`30` `PAUSE` instructions) waiting for the holder to release the lock so `G3` can grab it via CAS without ever parking!
- If `G2` wakes up and loses the CAS race against the barging `G3`, `G2` is pushed back to the **front (LIFO)** of the semaphore wait queue and goes back to sleep.

### The Tail-Latency Problem & Go 1.9's 1ms Starvation Mode

Barging maximizes aggregate throughput because the CPU never stalls waiting for a context switch. However, under heavy contention, newly arriving goroutines (`G3`, `G4`, `G5`...) can barge in repeatedly and starve poor `G2` at the head of the wait queue for hundreds of milliseconds!

To bound worst-case tail latency while keeping normal-mode throughput:

1. Whenever a woken waiter `G2` fails to acquire the lock and sees that it has been waiting for **more than `1 millisecond` (`1e6` ns)**, it sets the **`mutexStarving` (`1 << 2`)** bit on `m.state` before going back to sleep.
2. In **Starvation Mode**:
   - **No Barging & No Spinning**: Newly arriving goroutines (`G3`) do **not** spin and do **not** even try to CAS `mutexLocked`! They immediately enqueue themselves at the **tail (FIFO)** of the semaphore wait queue and park.
   - **Direct Ownership Hand-Off (`handoff = true`)**: When the current lock holder calls `Unlock()`, it does **not** clear `mutexLocked`! Instead, it calls `runtime_Semrelease(&m.sema, handoff=true, 1)`, which **transfers lock ownership directly to the oldest waiting goroutine `G2`** and schedules `G2` immediately (`gnext`) on the current `P`.
3. **Exiting Starvation Mode**: When a waiter receives the lock via direct handoff and sees either (a) it was the **last waiter** in the queue (`waiterCount == 1`), or (b) its own total wait time was **`< 1 millisecond`**, it clears the `mutexStarving` bit and restores high-throughput Normal Mode!

## 2. Why `sync.Once` Cannot Be Replaced by `atomic.CompareAndSwap`

A classic concurrency mistake in interviews and production code is trying to "optimize" `sync.Once` using a single `atomic.CompareAndSwapUint32`:

```go
// ❌ BROKEN: Do NOT write this!
if atomic.CompareAndSwapUint32(&initialized, 0, 1) {
    expensiveInit() // Takes 50ms to initialize sharedResource
}
return sharedResource // BUG: Concurrent callers see initialized == 1 and read nil sharedResource!
```

Look at what happens when Goroutine B arrives 1 microsecond after Goroutine A flips `initialized` from `0` to `1`: `CompareAndSwap` returns `false`, so Goroutine B **skips `expensiveInit()` and immediately reads `sharedResource` before Goroutine A has finished initializing it!**

By contrast, `sync.Once` (`src/sync/once.go`) pairs an **inlined `atomic.Uint32` fast path** with a **slow-path `sync.Mutex`**:

```go
func (o *Once) Do(f func()) {
    if o.done.Load() == 0 { // Inlined fast path (1 CPU instruction once done == 1)
        o.doSlow(f)         // Out-of-line slow path acquires o.m.Lock()!
    }
}

func (o *Once) doSlow(f func()) {
    o.m.Lock()
    defer o.m.Unlock()
    if o.done.Load() == 0 {
        defer o.done.Store(1) // Only sets done = 1 AFTER f() returns!
        f()
    }
}
```

Because `o.done.Store(1)` only runs *after* `f()` completes (via `defer`), any concurrent caller seeing `o.done.Load() == 0` blocks on `o.m.Lock()` until initialization is 100% finished (`f()` returnshappens-before `Once.Do` returns on all callers).

## 3. Inside `sync.Pool`: Per-`P` Shards & the Two-Cycle Victim Cache

When high-throughput servers allocate and discard temporary `*bytes.Buffer` or JSON encoder buffers on every request, `sync.Pool` recycles them across requests. How does `sync.Pool` avoid becoming a global mutex bottleneck itself?

```text
             sync.Pool.Get() / Put() on Processor P_i
             ========================================
  1. Pin current G to P_i (procPin() disables preemption)
  2. Check local[P_i].private (Single pointer slot: 0 locks, 0 atomics!)
  3. Check local[P_i].shared  (Lock-free poolChain: popHead by owner P_i)
  4. Steal from local[P_j].shared of peer processors (popTail via CAS)
  5. Check victim[P_i]        (Objects that survived the previous GC cycle!)
  6. Call Pool.New()
```

### Why Go 1.13 Added the `victim` Cache (`poolCleanup`)

Before Go 1.13, every garbage collection cycle (`runtime.GC()`) completely wiped 100% of all `sync.Pool` caches (`local = nil`). That caused a severe **post-GC latency saw-tooth**: immediately after every GC cycle, every request missed `sync.Pool` and had to allocate fresh buffers simultaneously, spiking both p99 latency and heap allocation rate!

Since Go 1.13, `poolCleanup()` at the start of each GC uses a **two-generation Victim Cache**:

1. On GC Cycle $N$, `local` is **not** discarded; instead, `victim = local` and `local = nil`.
2. If a pooled buffer is requested during Cycle $N$, `Get()` pulls it from `victim` and `Put()` promotes it back into the active `local` shard!
3. Only objects in `victim` that go **completely unused for an entire GC cycle** are dropped on GC Cycle $N+1$.

## 4. `context.Context` Cancellation Trees & `AfterFunc`

In Go servers, every incoming RPC or HTTP request constructs a root `ctx, cancel := context.WithTimeout(req.Context(), 2*time.Second)` and passes `ctx` as the first parameter down every database query, HTTP client call, and worker goroutine.

Under the hood (`src/context/context.go`), `cancelCtx` forms an **intrusive parent-to-children cancellation tree**:

- When you derive `childCtx, cancel := context.WithCancel(parentCtx)`, `propagateCancel` registers `childCtx` inside `parentCtx.children` (`map[canceler]struct{}`).
- **Why you must ALWAYS `defer cancel()`**: Even if `parentCtx` will eventually time out in 5 minutes, failing to call `cancel()` when the child operation finishes early leaves `childCtx` (and its timer/goroutine references) attached inside `parentCtx.children` for the entire lifetime of the parent!
- **Channel Close Broadcast**: `ctx.Done()` returns a read-only `<-chan struct{}`. When `cancel()` is invoked, it closes that channel (`close(d)`) under `c.mu.Lock()`, immediately unblocking every `select { case <-ctx.Done(): }` across hundreds of descendant goroutines simultaneously!

## 5. Verification Lab: `sync.Mutex` State Word, `sync.Once` Safety & `Context` Trees

The following self-contained Go verification program (`go run`) proves three synchronization invariants:

1. **`sync.Mutex` State-Word Bit Layout & Starvation Hand-Off**: Simulates the exact 32-bit `state` word transitions (`mutexLocked | mutexWoken | mutexStarving | waiterCount<<3`), verifying how a waiter stalled for `> 1ms` flips `mutexStarving` and forces `Unlock()` into direct FIFO ownership handoff (`handoff=true`).
2. **Broken CAS-Once vs. `sync.Once`**: Proves how a naive `atomic.CompareAndSwap` races when a second goroutine arrives during initialization, whereas `sync.Once` blocks concurrent callers on `doSlow` until initialization completes.
3. **Hierarchical `context.WithCancelCause` Propagation**: Verifies that cancelling a middle node in a 3-level `Context` tree immediately cancels all its descendants (`context.Cause(grandchild)`) while leaving sibling subtrees untouched.

```go
package main

import (
	"context"
	"errors"
	"fmt"
	"sync"
	"sync/atomic"
	"time"
)

// ---------------------------------------------------------------------------
// 1. Exact sync.Mutex 32-Bit State Word Simulator (src/internal/sync/mutex.go)
// ---------------------------------------------------------------------------
const (
	mutexLocked      = 1 << iota // 1 (bit 0)
	mutexWoken                   // 2 (bit 1)
	mutexStarving                // 4 (bit 2)
	mutexWaiterShift = iota      // 3 (bits 3..31 count parked waiters)
)

type MutexStateWord struct {
	state int32
}

func (m *MutexStateWord) LockFast() bool {
	return atomic.CompareAndSwapInt32(&m.state, 0, mutexLocked)
}

func (m *MutexStateWord) ParkWaiter() {
	m.state += 1 << mutexWaiterShift
}

func (m *MutexStateWord) WakeAndEnterStarvationIfOver1ms(waitedNs int64) {
	// Waiter wakes up after holder unlocked, consumes 1 waiter count, acquires lock,
	// and if waited > 1ms (1e6 ns), sets mutexStarving bit!
	delta := int32(mutexLocked) - int32(1<<mutexWaiterShift)
	if waitedNs > 1_000_000 {
		delta |= mutexStarving
	}
	m.state += delta
}

func (m *MutexStateWord) Unlock() (directHandoffToFIFOHead bool) {
	newState := m.state - mutexLocked
	m.state = newState
	if (newState & mutexStarving) != 0 {
		// In Starvation Mode, Unlock does NOT leave lock free for barging;
		// ownership is handed directly to the FIFO head waiter!
		m.state = (newState + mutexLocked) - (1 << mutexWaiterShift)
		return true
	}
	return false
}

func verifyMutexStateWordAndStarvation() {
	var mu MutexStateWord
	ok := mu.LockFast() // G1 acquires on fast path (state = 1)
	mu.ParkWaiter()     // G2 parks (waiters = 1, state = 9)
	mu.ParkWaiter()     // G3 parks (waiters = 2, state = 17)
	if !ok || mu.state != (2<<mutexWaiterShift)|mutexLocked {
		panic("Unexpected mutex state after 2 parked waiters")
	}

	// G1 unlocks in Normal Mode -> G2 wakes up after waiting 1.5ms (> 1ms threshold!)
	handoff1 := mu.Unlock()
	mu.WakeAndEnterStarvationIfOver1ms(1_500_000)
	isStarving := (mu.state & mutexStarving) != 0

	// Now G2 unlocks while mutexStarving is set -> direct FIFO handoff to G3!
	handoff2 := mu.Unlock()
	fmt.Printf("  [1. sync.Mutex 32-Bit State Word]  normal unlock handoff=%v -> wait=1.5ms sets Starving=%v -> next unlock directHandoff=%v\n",
		handoff1, isStarving, handoff2)
	if handoff1 != false || !isStarving || handoff2 != true {
		panic("Mutex starvation handoff invariant failed")
	}
}

// ---------------------------------------------------------------------------
// 2. Broken CAS-Only Once vs. Real sync.Once Verification
// ---------------------------------------------------------------------------
func verifySyncOnceGuarantee() {
	var once sync.Once
	var sharedConfig *string
	var wg sync.WaitGroup

	for i := 0; i < 16; i++ {
		wg.Add(1)
		go func() {
			defer wg.Done()
			once.Do(func() {
				time.Sleep(10 * time.Millisecond) // Simulate slow initialization
				val := "db://prod-cluster:5432"
				sharedConfig = &val
			})
			// Every single goroutine MUST observe non-nil sharedConfig when once.Do returns!
			if sharedConfig == nil || *sharedConfig != "db://prod-cluster:5432" {
				panic("sync.Once returned before initialization finished!")
			}
		}()
	}
	wg.Wait()
	fmt.Println("  [2. sync.Once Initialization]      all 16 concurrent callers waited cleanly for slow init completion")
}

// ---------------------------------------------------------------------------
// 3. Context Cancellation Tree & WithCancelCause Verification
// ---------------------------------------------------------------------------
func verifyContextTreePropagation() {
	rootCtx := context.Background()
	branchACtx, cancelA := context.WithCancelCause(rootCtx)
	branchBCtx, cancelB := context.WithCancel(rootCtx)
	defer cancelB()

	leafA1Ctx, cancelA1 := context.WithTimeout(branchACtx, 10*time.Second)
	defer cancelA1()

	errUpstream := errors.New("upstream quota exceeded")
	cancelA(errUpstream) // Cancelling branchA must cancel leafA1, but NOT branchB!

	select {
	case <-leafA1Ctx.Done():
	default:
		panic("Expected leafA1Ctx to be cancelled immediately when branchACtx was cancelled")
	}
	if branchBCtx.Err() != nil {
		panic("Sibling branchBCtx must remain active")
	}
	cause := context.Cause(leafA1Ctx)
	fmt.Printf("  [3. Context Cancellation Tree]     leafA1 cancelled=%v (cause=%q), sibling branchB err=%v\n",
		leafA1Ctx.Err() != nil, cause, branchBCtx.Err())
	if !errors.Is(cause, errUpstream) {
		panic("Expected Cause(leafA1Ctx) to preserve errUpstream")
	}
}

func main() {
	fmt.Println("=== Go Runtime Lab 05: sync.Mutex Starvation, sync.Once & Context Trees ===")
	verifyMutexStateWordAndStarvation()
	verifySyncOnceGuarantee()
	verifyContextTreePropagation()
	fmt.Println("All Go Runtime Lab 05 invariants verified.")
}
```

## Key Takeaways

1. **`sync.Mutex` balances throughput and tail latency automatically**: In Normal Mode, active CPU goroutines spin (`PAUSE`) and barge ahead of sleeping waiters to maximize throughput; if any waiter is starved for `> 1ms`, the mutex flips `mutexStarving` and switches to strict FIFO direct handoff.
2. **Never replace `sync.Once` with `atomic.CompareAndSwap`**: `CompareAndSwap` lets losing callers race past an in-progress initializer, whereas `sync.Once.Do` uses an atomic fast path backed by a mutex slow path so no caller proceeds until `f()` returns.
3. **`sync.Pool` items survive one GC cycle via `victim`, not forever**: Never store stateful resources requiring deterministic teardown (such as open sockets or database transactions) inside `sync.Pool`, and always reset pooled buffers (`buf.Reset()`) before returning them via `Put()`.
