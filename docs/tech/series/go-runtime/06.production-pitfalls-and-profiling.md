Nearly every famous bug in [*100 Go Mistakes and How to Avoid Them*](https://100go.co/book/) ceases to look like an arbitrary language quirk the moment you inspect the underlying runtime memory layout we studied in Chapters 01–05:

- Why does returning a `nil` pointer as an `error` make `err != nil` evaluate to `true`? Because an interface is a **16-byte `(itab, data)` struct**!
- Why does slicing a 20-byte header out of a network buffer leak 1 MiB of RAM? Because Go's garbage collector marks at the **`mspan` object granularity**, not individual slice offsets!
- Why does launching a sub-goroutine with an unbuffered channel inside a `select { case <-ctx.Done(): }` block leak goroutines under timeout spikes? Because an unbuffered `hchan` has **`dataqsiz == 0`**, parking the sender in `c.sendq` forever!

This concluding chapter connects the sharpest production pitfalls in Go directly to their runtime mechanics and pairs them with a systematic **`pprof` + `trace` + `-race` diagnostic workflow**.

## Before you start

Some Go bugs look like language trivia and turn out to be runtime behavior. A slice is not the data; it is a three-word descriptor (pointer, length, capacity) pointing at a shared array. So `b := a[:2]` shares memory with `a`, and writing through one changes the other. Keeping a tiny slice of a huge array keeps the whole array alive. Likewise, `delete(m, k)` on a map does not give memory back, and an interface holding a nil pointer is not equal to `nil`.

This chapter walks through those pitfalls using what the earlier chapters taught about memory layout, then shows how to find such problems in a running service with `pprof`, Go's built-in profiler.

It builds on the series, especially [Go Runtime 02](/tech/series/go-runtime/02.memory-allocator-and-escape-analysis/) for how memory is laid out and [Go Runtime 03](/tech/series/go-runtime/03.tricolor-gc-and-write-barriers/) for what the collector can and cannot free.

Terms used in this chapter:

- **slice**: a view onto an array, made of a pointer, a length and a capacity.
- **backing array**: the array a slice points into, shared by every slice made from it.
- **capacity**: how many elements the slice can hold before an append must allocate a new array.
- **full slice expression**: `a[low:high:max]`, which caps the capacity so appends cannot overwrite the original array.
- **typed nil**: an interface holding a nil pointer of a concrete type, which compares as not equal to `nil`.
- **goroutine leak**: a goroutine that blocks forever, for example on a channel nobody uses, and never exits.
- **pprof**: Go's profiling tool and format for CPU, heap and goroutine profiles.

## 1. Slice Descriptor Mechanics: Backing-Array Corruption & Capacity Leaks

In `src/runtime/slice.go`, a Go slice `[]T` is a 24-byte value header passed on the stack:

```go
type slice struct {
    array unsafe.Pointer // 8B pointer to the contiguous backing mspan object
    len   int            // 8B number of accessible elements
    cap   int            // 8B total elements from 'array' to end of backing allocation
}
```

Two production bugs stem directly from this 24-byte header:

### Bug 1: Silent Backing-Array Mutation via Sub-Slicing (`a[low:high]` vs. `a[low:high:max]`)

When you take a sub-slice `s1 := a[1:3]` from a slice `a := []int{10, 20, 30, 40, 50}`, what is `cap(s1)`?

- `len(s1)` is `3 - 1 = 2` (`{20, 30}`).
- **`cap(s1)` is `cap(a) - 1 = 4`!** Because `len(s1) < cap(s1)`, calling `s2 := append(s1, 999)` does **not** allocate a new backing array—it silently **overwrites `a[3]` (`40` $\to$ `999`)** in the caller's slice!

```text
  Original Slice a (len=5, cap=5):     [ 10 | 20 | 30 | 40 | 50 ]
                                              ^         ^
  Naive Sub-Slice s1 := a[1:3]                |         |
  (len=2, cap=4 -> shares tail of a!):        +---------+--> append(s1, 999) overwrites a[3]!

  Full Slice Expression s1 := a[1:3:3]        +---------+
  (len=2, cap=3-1=2 -> capped!):              append(s1, 999) MUST allocate a new array!
```

- **The Fix**: Whenever you return or pass a sub-slice that must not clobber the parent slice's remaining elements on `append`, use Go's **Three-Index Full Slice Expression `a[low:high:max]`** (`a[1:3:3]`), which restricts the sub-slice's capacity to `max - low` (`3 - 1 = 2`), forcing any subsequent `append` to allocate a fresh backing array!

### Bug 2: The 1 MiB Slice Capacity Leak & Pointer-Tail Retention

Because Go's garbage collector tracks reachability at the granularity of an entire **`mspan` object allocation** (not individual byte offsets inside an `mspan`), any live pointer into the middle or beginning of a backing array keeps the **entire backing array** alive in memory:

1. **Slicing a small header from a large buffer**:

   ```go
   // ❌ BAD: Reading a 1 MiB message and returning msg[:32] pins the entire 1 MiB mspan in RAM!
   func parseHeaderBad(msg []byte) []byte {
       return msg[:32]
   }

   // ✅ GOOD: bytes.Clone(msg[:32]) copies the 32 bytes into a fresh 32B mspan slot!
   func parseHeaderGood(msg []byte) []byte {
       return bytes.Clone(msg[:32])
   }
   ```

2. **Shrinking a slice of pointers (`[]*Conn` or `[]BufferStruct`)**:
   If you pop the last 500 elements off a 1,000-element slice (`s = s[:500]`), the elements at indices `500..999` inside the underlying backing array **still hold live pointers** that the GC must trace and retain! Always call the built-in **`clear(s[500:1000])`** before reslicing so the dead tail pointers are zeroed (`nil`).

## 2. Map Bucket Retention: Why `delete(m, k)` Never Shrinks RAM

In Go (`src/runtime/map.go` / SwissTable maps in Go 1.24+), a `map[K]V` is a pointer to an `hmap` header referencing a power-of-two array of hash buckets ($2^B$). Suppose an in-memory cache or session table spikes to **2,000,000 entries** (`B = 19`, allocating megabytes of bucket arrays) during peak traffic, and later you call `delete(m, k)` on all 2,000,000 keys (or `clear(m)`).

- `len(m)` drops to `0`.
- **How many bytes of bucket memory are freed back to the heap? Zero!**
- Calling `delete(m, k)` merely marks the slot inside the bucket as empty (tombstone / empty `tophash`). The bucket array `2^B` only ever *grows*; it never shrinks for the entire lifetime of that map instance.
- **The Fix**: For long-lived caches whose key count fluctuates by orders of magnitude, periodically copy the active live entries into a brand-new `make(map[K]V, len(oldMap))` and drop the old map reference so GC reclaims the oversized $2^B$ bucket array.

## 3. The Typed-Nil Interface Trap (`iface` 16-Byte Representation)

Why does `validate(1) != nil` evaluate to `true` in the following innocent-looking Go code?

```go
type ValidationError struct{ Field string }
func (e *ValidationError) Error() string { return e.Field }

func validate(x int) error {
    var err *ValidationError = nil // Concrete typed pointer is nil
    if x > 0 {
        return err                 // Boxed into 'error' interface!
    }
    return nil
}
```

Inspect `src/runtime/runtime2.go`. A non-empty interface like `error` is represented in memory by the 16-byte struct `iface`:

```go
type iface struct {
    tab  *itab          // 8B pointer to (inter *interfacetype, _type *_type, fun [1]uintptr)
    data unsafe.Pointer // 8B pointer to the concrete value
}
```

An interface value equals `nil` (`err == nil`) **if and only if BOTH `tab == nil` AND `data == nil` (`(0x0, 0x0)`)**:

| Return Statement in `validate()` | `iface.tab` (Type Descriptor) | `iface.data` (Value Pointer) | `err == nil`? |
| :--- | :--- | :--- | :--- |
| **`return nil`** | `0x0` (`nil`) | `0x0` (`nil`) | **`true`** |
| **`return err`** (where `var err *ValidationError = nil`) | **`0x4c8a20` (`*itab` for `*ValidationError`)** | `0x0` (`nil`) | **`false` (`err != nil`!)** |

- **The Fix**: Never declare a concrete error pointer variable (`var err *ValidationError`) that you unconditionally return as an `error` interface. Either declare `var err error`, or explicitly `return nil` on the success path!

## 4. Unbuffered Channel Goroutine Leaks & `defer` Evaluation Rules

### The Unbuffered Timeout Leak

Consider a handler that spawns a child goroutine to fetch a result with a timeout:

```go
func fetchWithTimeout(ctx context.Context) (Result, error) {
    ch := make(chan Result) // ❌ BUG if unbuffered (cap == 0)!
    go func() {
        ch <- slowRPC()     // Blocks forever in hchan.sendq if ctx times out first!
    }()
    select {
    case res := <-ch:
        return res, nil
    case <-ctx.Done():
        return Result{}, ctx.Err()
    }
}
```

If `ctx.Done()` fires before `slowRPC()` finishes, `fetchWithTimeout` returns immediately. When `slowRPC()` eventually finishes 200 ms later, the child goroutine executes `ch <- res` on an **unbuffered channel (`cap == 0`) with zero remaining receivers**. The child goroutine parks in `ch.sendq` (`_Gwaiting`) **forever**—leaking its 2 KiB+ stack, the `hchan`, and any heap objects reachable from its stack frames until the process restarts!

- **The Fix**: Always size one-shot result channels to **`make(chan Result, 1)`** (buffer capacity `1`) so the child goroutine can deposit its result into `c.buf[0]` and exit cleanly even after the parent has timed out and abandoned the channel!

### `defer` Eager Argument Evaluation

Remember two runtime rules for `defer`:

1. **`defer` arguments (including value method receivers!) are evaluated immediately when `defer` is registered**, not when the function returns. If you write `defer logStatus(status)` at the top of a function and mutate `status = "error"` later, `logStatus` will print the *initial* value unless you wrap it in a closure: `defer func() { logStatus(status) }()`.
2. **`defer` runs at function exit, not lexical block exit**: Putting `defer file.Close()` or `defer rows.Close()` directly inside a `for` loop queues every `_defer` record until the outer function returns—exhausting OS file descriptors (`EMFILE`) or database pool connections mid-loop! Extract the loop body into a helper function so `defer` runs on every iteration.

## 5. Production Diagnostics Workflow (`-race`, `pprof`, `trace`)

When diagnosing a production Go service, match the symptom to the exact runtime probe:

| Symptom | Primary Tool & Command | What to Inspect |
| :--- | :--- | :--- |
| **Suspected data race / corrupted map or slice** | **`go test -race ./...`** | Compiler-instrumented ThreadSanitizer (`TSan`) vector-clock shadow memory tracking unsynchronized read/write pairs. |
| **High CPU utilization** | **`go tool pprof http://.../debug/pprof/profile?seconds=30`** | Compare `flat` (CPU spent inside the function itself) vs. `cum` (cumulative CPU including callees). Look for `runtime.mallocgc` or `runtime.scanobject` > 20% indicating allocation churn. |
| **Container RSS / Heap growing monotonically (Memory Leak)** | **`pprof` `--inuse_space`** (`/debug/pprof/heap`) | Shows objects **still live on the heap right now** (slice capacity leaks, un-shrunk maps, leaked caches). |
| **High GC CPU / Short-lived allocation churn** | **`pprof` `--alloc_space` / `--alloc_objects`** | Cumulative bytes/objects allocated since process start (even if already garbage-collected!). Pair with `go build -gcflags="-m=2"`. |
| **Goroutine count climbing (`runtime.NumGoroutine()`)** | **`/debug/pprof/goroutine?debug=2`** | Dumps full stack traces and wait durations (`chan send [42 minutes]`) of every parked goroutine. |
| **Tail latency spikes with low CPU usage** | **`/debug/pprof/mutex`**, **`/debug/pprof/block`**, or **`go tool trace`** | Reveals lock contention (`sync.Mutex`), channel/select blocking stalls, `sysmon` preemption delays, and GC Mutator Assist pauses. |

## 6. Verification Lab: Proving & Fixing Four Classic Go Runtime Bugs

The following self-contained Go verification program (`go run`) reproduces and verifies the runtime fix for all four classic pitfalls from this chapter:

1. **Sub-Slice Append Corruption vs. Full Slice Expression (`a[1:3:3]`)**.
2. **1 MiB Slice Capacity Retention across `runtime.GC()` vs. Explicit Copy (`bytes.Clone`)**.
3. **The 16-Byte `iface` Typed-Nil Interface Trap (`[2]uintptr` inspection)**.
4. **Unbuffered vs. Buffered (`cap=1`) Channel Goroutine Leak under Context Timeout**.

```go
package main

import (
	"bytes"
	"context"
	"fmt"
	"runtime"
	"time"
	"unsafe"
)

// 1. Sub-slice append corruption vs. Full Slice Expression a[low:high:max]
func verifyFullSliceExpression() {
	origBad := []int{10, 20, 30, 40, 50}
	subBad := origBad[1:3] // len=2, cap=4 -> shares backing array tail!
	_ = append(subBad, 999)
	corruptedFourthElem := origBad[3] // 40 was silently overwritten with 999!

	origGood := []int{10, 20, 30, 40, 50}
	subGood := origGood[1:3:3] // Full Slice Expression: len=2, cap=3-1=2!
	_ = append(subGood, 999)   // Forced to allocate a brand-new backing array
	preservedFourthElem := origGood[3]

	fmt.Printf("  [1. Full Slice Expression a[1:3:3]] naive a[1:3] mutated orig[3]=%d | capped a[1:3:3] preserved orig[3]=%d\n",
		corruptedFourthElem, preservedFourthElem)
	if corruptedFourthElem != 999 || preservedFourthElem != 40 {
		panic("Full slice expression invariant failed")
	}
}

// 2. Slice capacity memory leak across GC vs. bytes.Clone()
func verifySliceCapacityLeak() {
	allocateAndSlice := func(cloneHeader bool) uint64 {
		headers := make([][]byte, 20)
		for i := range headers {
			oneMiB := make([]byte, 1024*1024)
			oneMiB[0] = byte(i)
			if cloneHeader {
				headers[i] = bytes.Clone(oneMiB[:32]) // Releases 1 MiB backing array!
			} else {
				headers[i] = oneMiB[:32] // Pins entire 1 MiB mspan per slice!
			}
		}
		runtime.GC()
		var m runtime.MemStats
		runtime.ReadMemStats(&m)
		runtime.KeepAlive(headers)
		return m.HeapAlloc / 1024
	}

	heapLeakedKiB := allocateAndSlice(false)
	heapClonedKiB := allocateAndSlice(true)
	fmt.Printf("  [2. Slice Capacity Leak (20x 1MiB)] naive msg[:32] live heap=%d KiB | bytes.Clone(msg[:32]) live heap=%d KiB\n",
		heapLeakedKiB, heapClonedKiB)
	if heapLeakedKiB < 18*1024 || heapClonedKiB > 4*1024 {
		panic("Expected naive sub-slice to retain >18 MiB and bytes.Clone to drop <4 MiB")
	}
}

// 3. Typed-Nil Interface 16-Byte iface (itab, data) Inspection
type CustomErr struct{ Code int }

func (e *CustomErr) Error() string { return "err" }

func returnTypedNilErr() error {
	var p *CustomErr = nil
	return p // Boxes (*itab(&CustomErr), 0x0) into 16-byte iface!
}

func verifyTypedNilInterfaceLayout() {
	err := returnTypedNilErr()
	rawWords := *(*[2]uintptr)(unsafe.Pointer(&err))
	fmt.Printf("  [3. Typed-Nil Interface Layout]     err!=nil is %v | raw iface words: itab=0x%x, data=0x%x\n",
		err != nil, rawWords[0], rawWords[1])
	if err == nil || rawWords[0] == 0 || rawWords[1] != 0 {
		panic("Expected non-zero itab and zero data pointer for typed-nil interface")
	}
}

// 4. Unbuffered vs. Cap-1 Channel Goroutine Leak on Timeout
func verifyChannelTimeoutGoroutineLeak() {
	runTimeoutCall := func(chanCap int, unblockStuck chan struct{}) {
		ctx, cancel := context.WithTimeout(context.Background(), 5*time.Millisecond)
		defer cancel()

		ch := make(chan int, chanCap)
		go func() {
			time.Sleep(20 * time.Millisecond) // Finishes AFTER ctx timeout!
			select {
			case ch <- 42:
			case <-unblockStuck:
			}
		}()

		select {
		case <-ch:
		case <-ctx.Done():
		}
	}

	cleanupUnbuffered := make(chan struct{})
	baseG := runtime.NumGoroutine()
	for i := 0; i < 10; i++ {
		runTimeoutCall(0, cleanupUnbuffered) // Unbuffered (cap=0) -> all 10 child goroutines get stuck!
	}
	time.Sleep(35 * time.Millisecond)
	leakedG := runtime.NumGoroutine() - baseG
	close(cleanupUnbuffered) // Clean up the 10 stuck goroutines for the next test
	time.Sleep(10 * time.Millisecond)

	baseG2 := runtime.NumGoroutine()
	for i := 0; i < 10; i++ {
		runTimeoutCall(1, nil) // Buffered (cap=1) -> all 10 child goroutines deposit result and exit!
	}
	time.Sleep(35 * time.Millisecond)
	leakedG2 := runtime.NumGoroutine() - baseG2

	fmt.Printf("  [4. Timeout Goroutine Leak (10x)]   unbuffered make(chan T) leaked=%d goroutines | buffered make(chan T, 1) leaked=%d\n",
		leakedG, leakedG2)
	if leakedG < 10 || leakedG2 > 0 {
		panic(fmt.Sprintf("Unexpected goroutine leak counts: unbuffered=%d, buffered=%d", leakedG, leakedG2))
	}
}

func main() {
	fmt.Println("=== Go Runtime Lab 06: Production Pitfalls (100 Go Mistakes) Verification ===")
	verifyFullSliceExpression()
	verifySliceCapacityLeak()
	verifyTypedNilInterfaceLayout()
	verifyChannelTimeoutGoroutineLeak()
	fmt.Println("All Go Runtime Lab 06 invariants verified.")
}
```

## Key Takeaways

1. **Cap sub-slices with `a[low:high:max]` and clone small headers (`bytes.Clone`)**: A 24-byte slice header shares and pins the entire underlying `mspan` backing array; use full slice expressions to prevent `append` corruption and `bytes.Clone` to release large buffers.
2. **An interface is `nil` only when both `(itab, data)` words are zero**: Never return a typed `nil` pointer (`var err *MyErr = nil`) through an `error` interface; explicitly `return nil`.
3. **Buffer one-shot child result channels (`make(chan T, 1)`)**: Whenever a parent goroutine selects between a child goroutine's result channel and `<-ctx.Done()`, give the result channel a buffer of `1` so the child goroutine never leaks in `hchan.sendq` if the context expires first.
