"Do not communicate by sharing memory; instead, share memory by communicating." Go's famous proverb often leads developers to treat `chan T` as magical, lock-free hardware pipes.

If you open **`src/runtime/chan.go`**, however, you immediately discover that every Go channel (`struct hchan`) is a **heap-allocated struct containing a `runtime.mutex`**, a circular ring buffer, and two doubly linked queues of waiting goroutines (`sudog`). Yet channels also perform one of the boldest optimizations in the Go runtime: when a receiver is already waiting, the sender **writes directly into the sleeping receiver's private goroutine stack (`sendDirect`)** without touching the channel's buffer!

This chapter dissects `hchan`, `sudog`, the two-ordering trick inside `select` (`pollorder` vs. `lockorder`), and the exact **`happens-before` equations** defined by the [Go Memory Model](https://go.dev/ref/mem).

---

## Before you start

Channels let goroutines pass values to each other: `ch <- 5` in one, `v := <-ch` in another. From the outside a channel is a pipe. Inside, it is an ordinary struct with a lock, an optional ring buffer, and two queues of goroutines waiting to send or receive. This chapter opens that struct and shows what happens when a send finds a buffer full, or a receiver already waiting.

It also covers `select`, which waits on several channels at once and picks a ready one at random, and the Go memory model. The memory model answers a practical question: when goroutine A writes a variable, when is goroutine B guaranteed to see the write? The answer is "only when something orders them", and channel operations are one of those orderings.

It helps to know goroutines first; see [Go Runtime 01](/tech/series/go-runtime/01.gmp-scheduler-and-preemption/).

Terms used in this chapter:

- **channel**: a typed conduit for passing values between goroutines, optionally buffered.
- **buffered channel**: a channel with room for a fixed number of values, so a send does not wait for a receiver until the buffer is full.
- **hchan**: the runtime struct that implements a channel.
- **sudog**: a record for a goroutine waiting on a channel, kept in the channel's wait queues.
- **park**: putting a goroutine to sleep until it is woken by another goroutine.
- **select**: the statement that waits on several channel operations and runs whichever is ready.
- **happens-before**: the ordering guarantee that makes one goroutine's write visible to another's read.
- **data race**: two goroutines accessing the same variable at once, at least one writing, with no ordering between them.

## 1. Anatomy of `struct hchan` and `struct sudog` (`runtime/chan.go`)

When you call `ch := make(chan Task, 4)`, the compiler lowers it to `runtime.makechan`, which allocates an **`hchan`** header on the heap and Returns a pointer `*hchan` (which is why passing a channel by value in Go copies only an 8-byte pointer):

```text
                       struct hchan (Heap Allocated)
  +-------------------------------------------------------------------+
  | qcount   : uint       (current elements in ring buffer)           |
  | dataqsiz : uint       (capacity = 4)                              |
  | buf      : unsafe.Pointer ---> [ Slot 0 | Slot 1 | Slot 2 | Slot 3 ]
  | elemsize : uint16                                ^        ^       |
  | closed   : uint32                                |        |       |
  | elemtype : *_type                              recvx    sendx     |
  | sendx    : uint       (ring write index)                          |
  | recvx    : uint       (ring read index)                           |
  | recvq    : waitq      ---> [ sudog(G_r1, elem=&dst1) ] <-> ...    |
  | sendq    : waitq      ---> [ sudog(G_s1, elem=&src1) ] <-> ...    |
  | lock     : mutex      (protects all fields of hchan)              |
  +-------------------------------------------------------------------+
```

### How `makechan` Allocates Memory across Three Cases

1. **Unbuffered Channel (`make(chan T, 0)`) or Zero-Sized Element (`make(chan struct{}, 100)`)**:
   Allocates only the 96-byte `hchan` struct itself (`mallocgc(hchanSize, nil, true)`). `buf` points to `&hchan` (no separate buffer allocation!).
2. **Buffered Channel of Pointer-Free Elements (`noscan`, e.g., `make(chan int64, 64)`)**:
   Performs a **single contiguous allocation** (`mallocgc(hchanSize + 64*8, ...)`), placing both `hchan` and its circular buffer in one block.
3. **Buffered Channel of Pointer-Bearing Elements (`!noscan`, e.g., `make(chan *Request, 64)`)**:
   Allocates `hchan` and `buf` (`newarray(elem, 64)`) separately so the garbage collector has an exact pointer-type bitmap for the circular buffer elements.

### Why Wait Queues Store `sudog` Instead of `*g` Directly

Why don't `recvq` and `sendq` simply link `*g` structs into a list? Because a single goroutine `G` executing a **`select` statement over 4 channels** must sit in the wait queues of **all 4 channels simultaneously**! Therefore, the runtime wraps `(g *g, elem unsafe.Pointer, c *hchan)` inside a lightweight **`sudog`** node pooled in each processor `P`'s `p.sudogcache`.

## 2. The Three Paths of `ch <- v` (`chansend`) & `sendDirect`

When goroutine `G_send` executes `ch <- v`, `runtime.chansend` acquires `c.lock` and branches into one of three distinct paths:

| Channel State at `ch <- v` | Runtime Execution Path | Copies & Scheduler Transitions |
| :--- | :--- | :--- |
| **Path 1: Waiting Receiver in `c.recvq`** (`sg := c.recvq.dequeue()` is non-nil) | **`send(c, sg, ep, unlockf)` $\to$ `sendDirect`** | **1 copy (`G_send` stack $\to$ `G_recv` stack directly!)**. Bypasses `c.buf` completely, invokes write barrier (`memmove`), releases `c.lock`, and calls `goready(G_recv)` (placing `G_recv` into `p.runnext`!). |
| **Path 2: Space Available in `c.buf`** (`c.qcount < c.dataqsiz`) | **Ring-Buffer Enqueue** | **1 copy (`G_send` stack $\to$ `c.buf[sendx]`)**. Increments `sendx` and `qcount`, releases `c.lock`, and `G_send` continues running without parking! (Later `<-ch` performs a 2nd copy from `c.buf[recvx]` $\to$ `G_recv` stack.) |
| **Path 3: Buffer Full (or Unbuffered with No Receiver)** | **Park on `c.sendq`** | **0 copies yet**. Acquires a `sudog` pointing to `&v` on `G_send`'s stack, appends `sudog` to `c.sendq`, and calls **`gopark()`** to put `G_send` into `_Gwaiting`. |

> **Why `sendDirect` Is Extraordinary**:
> Normally, goroutine stacks in Go are strictly private: no goroutine may hold a pointer into another goroutine's stack because `copystack()` can move a running goroutine's stack at any moment! Why is `sendDirect` allowed to copy `v` straight into `sg.elem` on `G_recv`'s stack? Because `G_recv` is currently parked (`_Gwaiting`), so its stack is guaranteed **not to grow** while `sendDirect` runs (and the GC stack shrinker explicitly coordinates with channel locks)!

### Edge-Case Semantics Matrix (`nil` vs. `closed` Channels)

| Operation | On a **`nil` Channel** (`var ch chan T`) | On a **`closed` Channel** (`close(ch)`) | On an **Open Channel** |
| :--- | :--- | :--- | :--- |
| **`ch <- v` (Send)** | **Blocks forever** (`gopark` without wait queue; great for disabling a send case in `select`!) | **`panic: send on closed channel`** | Sends or blocks until receiver ready |
| **`v, ok := <-ch` (Receive)** | **Blocks forever** (great for disabling a receive case in `select` once an input stream closes!) | **Returns immediately** with `(zeroValue, false)` after draining buffered items | Receives `(v, true)` or blocks |
| **`close(ch)`** | **`panic: close of nil channel`** | **`panic: close of closed channel`** | Wakes **all** waiting receivers (`recvq` gets zero values) and **all** waiting senders (`sendq` panics!) |

## 3. Inside `select` (`runtime/select.go`): `pollorder` vs. `lockorder`

What happens when a goroutine executes a `select` block across multiple channels?

```go
select {
case v := <-chA:
    handleA(v)
case chB <- msg:
    handleB()
}
```

`runtime.selectgo` must solve **two competing correctness problems** at once:

1. **Starvation Prevention**: If `chA` and `chB` are *both* ready on every iteration of a loop, checking `case 0` (`chA`) first deterministically would starve `chB` forever.
2. **AB-BA Deadlock Prevention**: If Goroutine 1 runs `select` on `{chA, chB}` and locks `chA.lock` then `chB.lock`, while Goroutine 2 runs `select` on `{chB, chA}` and locks `chB.lock` then `chA.lock`, the two goroutines will **deadlock inside the runtime**!

Go solves both inside `selectgo` by building two index arrays on the stack before touching any lock:

```text
  scases[0..N-1] (Cases in source-code order)
        |
        +---> 1. pollorder : Randomized via Fisher-Yates shuffle (cheaprand)
        |                    Ensures uniform 50/50 fairness when multiple cases are ready!
        |
        +---> 2. lockorder : Heap-sorted by channel memory address (uintptr(c))
                             Locks channels in strictly ascending address order (and deduplicates
                             repeated channels) so AB-BA deadlocks are mathematically impossible!
```

1. **Lock Phase (`sellock`)**: Acquires `c.lock` on every non-nil channel in ascending **`lockorder`**.
2. **Pass 1 — Non-Blocking Poll**: Iterates through cases in randomized **`pollorder`**. If any channel is immediately ready (or if a `default:` case is present), executes that case, unlocks all channels in reverse `lockorder` (`selunlock`), and returns!
3. **Pass 2 — Enqueue on All Channels & Park**: If no case is ready and there is no `default:`, allocates one `sudog` per case, links the current goroutine `G` into the `recvq`/`sendq` of **every channel in the `select`**, unlocks all channels, and parks via `gopark()`.
4. **Pass 3 — Wakeup & Unlink**: The first channel that becomes ready wakes `G` (`param = winning_sudog`), and `selectgo` re-locks all channels in `lockorder` to **unlink `G`'s unused `sudog` nodes from all the losing channels** before returning the winning case index!

## 4. The Formal Go Memory Model for Channels (`go.dev/ref/mem`)

The [Go Memory Model](https://go.dev/ref/mem) specifies four formal **`happens-before` ($\prec_{\text{hb}}$)** edges for channels:

1. **Send $\prec_{\text{hb}}$ Receive Completion**: The $k$-th send on a channel happens-before the $k$-th receive from that channel completes.
2. **`close(ch)` $\prec_{\text{hb}}$ Zero-Value Receive**: Closing a channel happens-before a receive that returns a zero value because the channel is closed.
3. **Unbuffered Channel Rule**: **A receive from an unbuffered channel happens-before the corresponding send on that channel completes.** (Look closely: the *receive starts/completes synchronization* before `ch <- v` returns on the sender side!)
4. **Capacity-$C$ Buffered Channel Rule**: **The $k$-th receive on a channel with capacity $C$ happens-before the $(k+C)$-th send from that channel completes.**

Notice why Rule 4 is so important: it proves that a buffered channel `sem := make(chan struct{}, C)` acts as a valid **counting semaphore** when **`sem <- struct{}{}` acquires a permit** and **`<-sem` releases the permit**! Because the $k$-th release (`<-sem`) happens-before the $(k+C)$-th acquire (`sem <- struct{}{}`) completes, at most $C$ goroutines can execute inside the critical section concurrently with full memory visibility.

## 5. Verification Lab: `select` Random Fairness, `nil`-Channel State Machine & Semaphore Visibility

The following self-contained Go verification program (`go run`) proves three channel runtime guarantees:

1. **`select` `pollorder` Uniform Randomness**: When two buffered channels `chA` and `chB` are **both ready simultaneously** across `2,000` iterations of a `select` statement, `selectgo`'s Fisher-Yates `pollorder` picks each branch ~50% of the time instead of starving the second case.
2. **Idiomatic Fan-In Merge using `nil`-Channel Disabling**: Demonstrates how setting a closed input channel variable to `nil` (`inA = nil`) dynamically disables that `select` branch (`scase.c == nil` is skipped by `selectgo`) without busy-spinning on `(zero, false)` receives!
3. **Capacity-$C$ Semaphore Bound**: Verifies that a buffered channel of capacity $C = 3$ strictly bounds peak concurrent workers to $\le 3$ across 24 concurrent goroutines.

```go
package main

import (
	"fmt"
	"sync"
	"sync/atomic"
)

func verifySelectPollOrderFairness() {
	chA := make(chan int, 1)
	chB := make(chan int, 1)
	pickedA, pickedB := 0, 0

	const trials = 2000
	for i := 0; i < trials; i++ {
		// Ensure BOTH chA and chB are ready before entering selectgo!
		chA <- 1
		chB <- 1
		select {
		case <-chA:
			pickedA++
			<-chB // drain the other
		case <-chB:
			pickedB++
			<-chA // drain the other
		}
	}
	ratioA := float64(pickedA) / float64(trials)
	fmt.Printf("  [1. select pollorder Fairness (2,000 dual-ready trials)] pickedA=%d (%.1f%%), pickedB=%d (%.1f%%)\n",
		pickedA, ratioA*100, pickedB, (1-ratioA)*100)
	if ratioA < 0.35 || ratioA > 0.65 {
		panic(fmt.Sprintf("Expected ~50/50 Fisher-Yates pollorder distribution, got ratioA=%.2f", ratioA))
	}
}

func verifyNilChannelSelectFanIn() {
	inA := make(chan int, 3)
	inB := make(chan int, 3)
	inA <- 10
	inA <- 20
	close(inA)
	inB <- 100
	inB <- 200
	inB <- 300
	close(inB)

	var merged []int
	// Idiomatic zero-spin fan-in: setting a closed channel variable to nil disables its select case!
	for inA != nil || inB != nil {
		select {
		case v, ok := <-inA:
			if !ok {
				inA = nil // Disables case <-inA in future select iterations!
				continue
			}
			merged = append(merged, v)
		case v, ok := <-inB:
			if !ok {
				inB = nil // Disables case <-inB in future select iterations!
				continue
			}
			merged = append(merged, v)
		}
	}
	sum := 0
	for _, x := range merged {
		sum += x
	}
	fmt.Printf("  [2. nil-Channel Select Disabling Fan-In]                 merged %d items, sum=%d (zero busy-spins)\n",
		len(merged), sum)
	if len(merged) != 5 || sum != 630 {
		panic("Fan-in merge failed")
	}
}

func verifyBufferedChannelSemaphoreBound() {
	const maxConcurrency = 3
	sem := make(chan struct{}, maxConcurrency)

	var active atomic.Int32
	var peakActive atomic.Int32
	var wg sync.WaitGroup

	for i := 0; i < 24; i++ {
		wg.Add(1)
		go func() {
			defer wg.Done()
			sem <- struct{}{} // Acquire permit (blocks once 3 permits are in flight)
			cur := active.Add(1)
			for {
				prevPeak := peakActive.Load()
				if cur <= prevPeak || peakActive.CompareAndSwap(prevPeak, cur) {
					break
				}
			}
			active.Add(-1)
			<-sem // Release permit (k-th receive happens-before (k+C)-th send completes)
		}()
	}
	wg.Wait()
	fmt.Printf("  [3. Buffered Channel Semaphore (cap=%d, 24 workers)]      peak_concurrent=%d\n",
		maxConcurrency, peakActive.Load())
	if peakActive.Load() > maxConcurrency || peakActive.Load() == 0 {
		panic(fmt.Sprintf("Semaphore invariant violated: peak=%d", peakActive.Load()))
	}
}

func main() {
	fmt.Println("=== Go Runtime Lab 04: Channels (hchan), select & Memory Model ===")
	verifySelectPollOrderFairness()
	verifyNilChannelSelectFanIn()
	verifyBufferedChannelSemaphoreBound()
	fmt.Println("All Go Runtime Lab 04 invariants verified.")
}
```

## Key Takeaways

1. **Sends to a parked receiver perform a direct cross-stack `memmove` (`sendDirect`)**: When a receiver is already parked in `recvq`, the sender writes directly into the receiver's stack slot and places the receiver into `p.runnext`, avoiding the two-step buffer copy of buffered channels.
2. **`select` shuffles poll order and sorts lock order**: Fisher-Yates `pollorder` guarantees statistical fairness across ready cases, while heap-sorting channel addresses in `lockorder` makes concurrent `select` AB-BA deadlocks impossible.
3. **Use `ch = nil` to disable closed branches in a `select` loop**: Receiving from a closed channel returns `(zero, false)` immediately on every iteration, causing a 100% CPU busy-spin unless you set the local channel variable to `nil` once `ok == false`.
