Why can a single Go process spawn **500,000 concurrent goroutines** on an 8-core machine without exhausting virtual memory or grinding the Linux kernel scheduler (`CFS` / `EEVDF`) to a halt?

If you spawn 500,000 OS threads (`pthread_create`), each thread reserves an 8 MiB virtual stack guard region and a kernel `task_struct`, and every blocking socket read triggers a ring-3 $\leftrightarrow$ ring-0 context switch costing ~1.5–3 $\mu\text{s}$ plus L1/L2 cache pollution. By contrast, a goroutine starts with a **2 KiB dynamically resizable stack** (`_StackMin = 2048`) and switches execution context in user space in **~100–200 nanoseconds** without entering the kernel.

To achieve this, the Go runtime (`src/runtime/proc.go`) implements a cooperative-and-preemptive **$M:N$ work-stealing scheduler** built around three core structs: **`G` (Goroutine)**, **`M` (Machine / OS Thread)**, and **`P` (Logical Processor)**.

This opening chapter separates language-level concurrency guarantees from runtime implementation mechanics: tracing how `schedule()` selects work, how `handoffp()` survives blocking system calls, how the integrated **Network Poller (`netpoll`)** turns blocking Go socket reads into non-blocking `epoll` events, and how `sysmon` preempts tight CPU loops via **`SIGURG`**.

## Before you start

This series is for programmers who write Go (or another language) and want to know what the runtime does underneath; the chapters build on each other, so read them in order.

`go f()` starts a goroutine, and you can start a hundred thousand of them. The operating system could not run that many threads, so the Go runtime has its own scheduler that multiplexes goroutines onto a small number of OS threads. This chapter explains how: three kinds of objects (G, M, P) cooperate, idle workers steal work from busy ones, and a goroutine stuck in a blocking system call does not hold up the others.

It also covers preemption: how the runtime stops a goroutine that never yields, such as one in a tight `for {}` loop.

You only need basic Go and a rough idea of what a thread is.

Terms used in this chapter:

- **goroutine (G)**: Go's lightweight unit of concurrent work, with its own small stack.
- **M**: a machine, meaning an OS thread that runs Go code.
- **P**: a processor, a token that grants an M the right to run goroutines; the count equals `GOMAXPROCS`.
- **run queue**: a list of goroutines that are ready to run, kept per P.
- **work stealing**: an idle P taking goroutines from another P's queue.
- **syscall**: a request to the operating system, such as reading a file, which may block the thread.
- **netpoller**: the runtime component that waits on network sockets (via epoll on Linux) without blocking a thread per connection.
- **preemption**: forcibly pausing a running goroutine so others can run.

## 1. The Three Core Structs (`G`, `M`, `P`) in `runtime/runtime2.go`

Before Go 1.1, the scheduler used only `G` (goroutines) and `M` (OS threads) sharing a single global run queue protected by a central mutex (`sched.lock`). Under high concurrency, threads spent more CPU cycles contending on `sched.lock` and passing memory allocations across CPU cores than executing user code.

Dmitry Vyukov's redesign introduced **`P` (Processor)**—a logical token representing one unit of Go execution concurrency (`len(allp) == GOMAXPROCS`):

| Runtime Struct | Count in Process | Key Fields (`runtime2.go`) | Architectural Role |
| :--- | :--- | :--- | :--- |
| **`g` (Goroutine)** | $1\text{..Millions}$ | `stack` (`lo`, `hi`), `sched` (`gobuf`: `sp`, `pc`, `bp`), `atomicstatus` (`_Grunnable`, `_Grunning`, `_Gwaiting`, `_Gsyscall`), `preempt` | Lightweight user-space execution context. Holds its own 2 KiB+ contiguous stack and saved instruction/stack pointers. |
| **`m` (Machine)** | Dynamic (default max `10,000`) | `g0` (`*g` scheduler stack), `curg` (`*g` current user `G`), `p` (`puintptr` attached `P`), `mOS` | A real kernel OS thread (`clone(CLONE_VM\|CLONE_THREAD)` on Linux). An `M` **cannot run Go code unless it holds a `P`** (though it can execute blocking syscalls or `cgo` without a `P`). |
| **`p` (Processor)** | `GOMAXPROCS` | `runnext` (`guintptr`), `runq` (`[256]guintptr` ring), `runqhead`, `runqtail`, `mcache` (`*mcache`), `wbBuf`, `timers` | Per-core execution context that owns a **lock-free local run queue**, a **per-`P` memory allocator cache (`mcache`)**, and a GC write-barrier buffer. |

### Why Every `M` Has a Dedicated `g0` Stack

Every OS thread `M` owns a special goroutine struct `m.g0` backed by a fixed-size system stack (when the runtime allocates it on Linux without cgo it is 16 KiB; with cgo it is the OS thread stack). Whenever the runtime needs to run scheduler logic (`schedule()`), grow a user goroutine's stack (`morestack`), allocate heap spans, or run garbage collection, the CPU switches stacks from `m.curg` (the tiny 2 KiB user stack) onto `m.g0` via `mcall(fn)`. Why? Because executing complex runtime scheduler or GC code directly on a user goroutine's 2 KiB stack would trigger recursive stack growth!

## 2. Where Do Runnable Goroutines Live? The Four-Tier Run Queue Hierarchy

When `go fn()` (`runtime.newproc`) creates a runnable goroutine on processor `P`, where is it placed, and in what order does `findRunnable()` pick the next `G` to run?

```text
              Processor P (Local State - Lock-Free CAS)
  +---------------------------------------------------------------+
  | 1. p.runnext : [ G_newest ]  (1-slot LIFO hot cache)          |
  |                      | (displaced G pushed to tail of runq)   |
  |                      v                                        |
  | 2. p.runq    : [ G1 | G2 | G3 | ... | G256 ] (256-slot FIFO)  |
  +---------------------------------------------------------------+
                         | (if runq is full, spills half + new G)
                         v
  +---------------------------------------------------------------+
  | 3. sched.runq : Global Run Queue (Protected by sched.lock)    |
  | 4. netpoll    : epoll / kqueue / IOCP Ready List (netpoll())  |
  +---------------------------------------------------------------+
```

1. **The `p.runnext` 1-Slot LIFO Priority Slot**:
   When a goroutine spawns a new `G` (or wakes a blocked receiver on a channel), `runqput(_p_, gp, next=true)` places `gp` into `_p_.runnext` via atomic CAS. If `runnext` already held a goroutine `old_g`, `old_g` is kicked out to the tail of `_p_.runq`.
   - *Why a 1-slot LIFO?* Because a newly woken producer/consumer goroutine almost always shares hot L1 cache lines with the currently running goroutine on that core! Running it next maximizes cache locality without allowing unbounded LIFO starvation.
2. **The `p.runq` 256-Element Lock-Free Ring Buffer**:
   Owned by `P` (`runqhead`, `runqtail`). The owning `P` pops from `runqhead` using lock-free atomic operations. If `p.runq` fills all 256 slots, `runqputslow` acquires `sched.lock` and moves **half of `p.runq` (128 goroutines)** plus the new `G` into the **Global Run Queue** in a single batch.
3. **The `schedtick % 61 == 0` Global Fairness Rule**:
   If a `P` only ever checked its own `p.runnext` and `p.runq`, two ping-ponging goroutines on `P` could starve goroutines waiting in the Global Run Queue (`sched.runq`) forever!
   To prevent starvation, on **every 61st scheduler tick (`_p_.schedtick % 61 == 0`)**, `schedule()` checks the **Global Run Queue *before* checking `p.runnext` or `p.runq`**. (Why `61`? A prime is presumably chosen so the check does not line up with power-of-two loop patterns; the constant is a heuristic, not a derived value.)
4. **Work-Stealing (`stealWork`) & `netpoll`**:
   If `p.runnext`, `p.runq`, and `sched.runq` are all empty, `findRunnable()` polls the non-blocking **Network Poller (`netpoll(0)`)**, and then randomly iterates over all other processors `allp` (starting at a randomized coprime offset) calling `runqsteal`: **stealing exactly half of a victim `P`'s local `runq`** (and optionally its `runnext`) in a single atomic batch!

## 3. Blocking System Calls (`handoffp`) vs. Non-Blocking Network I/O (`netpoll`)

What happens when a running goroutine `G1` performs I/O? The Go runtime takes two completely different paths depending on whether the file descriptor is pollable by `epoll`/`kqueue`:

### Path A: Pollable Network Sockets (`net.Conn` $\to$ `netpoll` + `gopark`)

When you read from a TCP socket in Go (`conn.Read(buf)`), your goroutine looks synchronous, **but the underlying OS socket is configured with `O_NONBLOCK`**.

1. `conn.Read` executes `read(fd, buf)` directly. If data is already in the kernel socket buffer, it returns immediately without touching the scheduler!
2. If the kernel returns `-EAGAIN` (`EWOULDBLOCK`), the runtime registers `fd` with the node's `epoll` instance (`runtime.netpollopen` with `EPOLLIN | EPOLLOUT | EPOLLET`) and calls **`gopark()`** on `G1`.
3. `gopark()` transitions `G1` from `_Grunning` to `_Gwaiting`, stores `G1`'s pointer inside the runtime's `pollDesc` struct for that socket, and **immediately switches `M` to the next runnable goroutine `G2` on the exact same `P`**. Zero OS threads block!
4. Later, when `netpoll()` (called by `findRunnable()` or the background `sysmon` thread) receives the `epoll_wait` readiness event for `fd`, it calls **`goready(G1)`**, pushing `G1` right back into a `P`'s run queue.

### Path B: Blocking OS Syscalls & `cgo` (`entersyscall` $\to$ `handoffp`)

What if `G1` invokes a synchronous filesystem syscall (`os.ReadFile` on a local disk without `epoll` support) or a blocking `C` function via `cgo`? The OS kernel will block the calling OS thread `M1`!

1. Before entering the syscall, `runtime.entersyscall()` saves `G1`'s stack/PC, sets `G1` to `_Gsyscall`, and **unlinks `M1` from `P1`** (`_p_.m = 0`, `m.p = 0`, `_p_.status = _Psyscall`).
2. If `M1` completes the syscall quickly (within microseconds) and `P1` is still idle in `_Psyscall`, `exitsyscall()` re-acquires `P1` on the fast path (`exitsyscallfast`) and continues running `G1` with zero thread handoff!
3. If the syscall blocks for **more than ~20 $\mu\text{s}$ to 10 ms**, the background monitor thread **`sysmon`** notices `P1` sitting idle in `_Psyscall`, retakes `P1`, and calls **`handoffp(P1)`**—waking an idle OS thread `M2` (or spawning a new OS thread) to take ownership of `P1` and keep draining `P1`'s local run queue while `M1` sleeps in the kernel!
4. When `M1` eventually returns from the slow syscall, if no free `P` is available, `M1` places `G1` onto the Global Run Queue and parks itself in the idle `M` pool.

## 4. From Cooperative Stack-Check Preemption to `SIGURG` Asynchronous Preemption

Prior to **Go 1.14**, goroutine preemption was purely **cooperative at function prologues**:

- The compiler inserted a tiny stack-bound check at the entry of every non-inlined function (`if SP < g.stackguard0 { runtime.morestack_noctxt() }`).
- To preempt a goroutine running for more than **10 milliseconds** (`forcePreemptNS = 10ms`), `sysmon` set `g.stackguard0 = stackPreempt` (`0xfffffade`). On the next function call, the stack check triggered `morestack`, which yielded the goroutine.
- **The Pre-1.14 Deadlock Trap**: If a goroutine ran a tight numerical loop (`for i := 0; i < 1e12; i++ { sum += i }`) that made **no function calls** (or whose calls were all inlined by the compiler), `g.stackguard0` was never checked! That goroutine hogged its `P` forever and froze Stop-The-World (STW) garbage collection across the entire process.

### Go 1.14+ Signal-Based Asynchronous Preemption (`SIGURG`)

Starting in Go 1.14 (`runtime/preempt.go` and `runtime/signal_unix.go`), `sysmon` enforces **non-cooperative asynchronous preemption**:

1. When `sysmon` sees a goroutine running continuously for `> 10 ms` (or when GC needs to scan stacks), it calls `preemptM(mp)`, which sends the POSIX signal **`SIGURG`** (`tgkill(pid, mp.procid, _SIGURG)`) to the target OS thread `M`.
   - *Why `SIGURG`?* Because `SIGURG` ("urgent out-of-band socket data") is almost never used by modern programs, does not interfere with debuggers (`SIGTRAP`/`SIGINT`), and is not blocked by `cgo` libraries.
2. The Linux kernel interrupts `M` at an arbitrary instruction, saves all CPU registers into `ucontext_t` on `M`'s `gsignal` stack, and invokes Go's `sighandler`.
3. If the interrupted instruction is at an **async-safe point** (not in the middle of mutating runtime allocator/scheduler locks or unmarked pointer registers), `sighandler` modifies the saved `ucontext_t` program counter (`RIP` / `PC`) to point to `runtime.asyncPreempt`.
4. When `sighandler` returns, the thread resumes directly inside `asyncPreempt`, which spills all general-purpose and SIMD registers onto `G`'s stack and calls `gopreempt_m` $\to$ `schedule()`, yielding the CPU cleanly even inside an infinite function-call-free loop!

## 5. Verification Lab: Observing Asynchronous Preemption, `GOMAXPROCS` & Work-Stealing in Go

The following self-contained Go program (`go run`) proves three core runtime invariants on your machine:

1. **`SIGURG` Asynchronous Preemption**: Runs a tight, call-free CPU loop alongside a short latency-sensitive goroutine on **`GOMAXPROCS(1)`** (a single `P`). Without Go 1.14+ `SIGURG` preemption, the tight loop would starve the latency probe forever; with `SIGURG`, `sysmon` preempts the loop in ~10 ms so the latency probe completes cleanly!
2. **Syscall Hand-Off (`handoffp`)**: Blocks 4 goroutines simultaneously inside raw OS sleep syscalls (`syscall.Nanosleep`, which exists on Linux only and bypasses Go's timer netpoller and enters `_Gsyscall`) under **`GOMAXPROCS(1)`**, proving that the runtime detaches the single `P` from the sleeping OS threads (`M`) so a 5th compute goroutine finishes immediately without waiting for the OS syscalls.
3. **Run-Queue LIFO `runnext` Ordering**: Demonstrates how newly spawned goroutines on `GOMAXPROCS(1)` execute the last-spawned goroutine *first* because it lands in `p.runnext`!

```go
package main

import (
	"fmt"
	"runtime"
	"sync"
	"sync/atomic"
	"syscall"
	"time"
)

func verifyAsyncPreemptionOnSingleP() {
	prev := runtime.GOMAXPROCS(1)
	defer runtime.GOMAXPROCS(prev)

	var stopLoop atomic.Bool
	var loopIters atomic.Uint64
	preemptedCh := make(chan time.Duration, 1)

	// Start a tight CPU-bound goroutine with ZERO function calls inside the loop body
	go func() {
		var acc uint64
		for !stopLoop.Load() {
			acc += 1
			if acc&0xFFFFF == 0 {
				loopIters.Add(0x100000)
			}
		}
	}()

	// Wait until the tight CPU loop is actively hogging the single P
	for loopIters.Load() == 0 {
		runtime.Gosched()
	}

	start := time.Now()
	go func() {
		// On GOMAXPROCS(1), this goroutine can ONLY run after sysmon preempts the tight loop via SIGURG!
		preemptedCh <- time.Since(start)
	}()

	waitLatency := <-preemptedCh
	stopLoop.Store(true)
	fmt.Printf("  [1. SIGURG Async Preemption on GOMAXPROCS=1] latency=%v (loop iterations=%d)\n",
		waitLatency.Round(time.Microsecond), loopIters.Load())
	if waitLatency > 500*time.Millisecond {
		panic("Expected SIGURG preemption within <500ms on GOMAXPROCS=1")
	}
}

func verifySyscallHandoffP() {
	prev := runtime.GOMAXPROCS(1)
	defer runtime.GOMAXPROCS(prev)

	var wg sync.WaitGroup
	start := time.Now()

	// Spawn 4 goroutines that enter raw blocking OS syscalls (syscall.Nanosleep for 120ms).
	// Even though GOMAXPROCS=1, entersyscall() detaches P so handoffp() lets other goroutines run!
	for i := 0; i < 4; i++ {
		wg.Add(1)
		go func() {
			defer wg.Done()
			ts := syscall.Timespec{Sec: 0, Nsec: 120_000_000} // 120ms blocking OS syscall
			_ = syscall.Nanosleep(&ts, nil)
		}()
	}

	// Give the 4 goroutines a moment to enter _Gsyscall
	time.Sleep(15 * time.Millisecond)

	computeStart := time.Now()
	doneCh := make(chan time.Duration, 1)
	go func() {
		sum := 0
		for i := 0; i < 100_000; i++ {
			sum += i
		}
		_ = sum
		doneCh <- time.Since(computeStart)
	}()

	computeElapsed := <-doneCh
	wg.Wait()
	totalWall := time.Since(start)
	fmt.Printf("  [2. Syscall handoffp() on GOMAXPROCS=1]      compute ran in %v while 4 M threads slept in OS syscall (total wall=%v)\n",
		computeElapsed.Round(time.Microsecond), totalWall.Round(time.Millisecond))
	if computeElapsed > 80*time.Millisecond {
		panic("Expected P handoff to execute compute goroutine without waiting for 120ms OS syscalls")
	}
}

func verifyRunnextLIFOSlot() {
	prev := runtime.GOMAXPROCS(1)
	defer runtime.GOMAXPROCS(prev)

	order := make([]int, 0, 4)
	var wg sync.WaitGroup
	wg.Add(4)

	// Spawn 4 goroutines directly on the current P before parking on wg.Wait():
	// G0 -> runnext; G1 -> runnext (G0 pushed to runq[0]); G2 -> runnext (G1 pushed to runq[1]);
	// G3 -> runnext (G2 pushed to runq[2]). When wg.Wait() parks, P pops runnext (G3) first: [3, 0, 1, 2]!
	for i := 0; i < 4; i++ {
		id := i
		go func() {
			order = append(order, id)
			wg.Done()
		}()
	}
	wg.Wait()
	fmt.Printf("  [3. P.runnext 1-Slot LIFO + FIFO runq Order]  spawned [0, 1, 2, 3] -> executed %v\n", order)
	if len(order) != 4 || order[0] != 3 {
		panic(fmt.Sprintf("Expected G3 in P.runnext to execute first, got %v", order))
	}
}

func main() {
	fmt.Println("=== Go Runtime Lab 01: GMP Scheduler, SIGURG Preemption & Syscall Hand-Off ===")
	verifyAsyncPreemptionOnSingleP()
	verifySyscallHandoffP()
	verifyRunnextLIFOSlot()
	fmt.Println("All Go Runtime Lab 01 invariants verified.")
}
```

## Key Takeaways

1. **`P` decouples concurrency width from OS thread count**: `GOMAXPROCS` bounds how many OS threads execute *Go user code simultaneously*, while blocked OS syscalls (`_Gsyscall`) detach their `M` from `P` via `handoffp()` and network sockets (`net.Conn`) park goroutines on the `epoll` netpoller with zero blocked OS threads.
2. **Never rely on goroutine creation order for correctness**: Because every `P` places the newest goroutine in its 1-slot LIFO `runnext` cache, checks the Global Run Queue every `61` ticks, and steals half of peer `runq` rings at random, execution order is non-deterministic by design.
3. **`SIGURG` preemption bounds CPU-loop tail latency to ~10 ms**: Even loops without function calls are asynchronously preempted via POSIX `SIGURG` signals injected by `sysmon` at compiler-generated async-safe instruction points.
