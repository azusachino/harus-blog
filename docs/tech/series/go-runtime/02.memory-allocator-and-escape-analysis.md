In C or Rust, you choose between the stack and the heap explicitly at the syntax level (`T` vs. `malloc()` / `Box::new(T)`). In Go, **syntax never dictates where a variable lives**. Calling `new(User)` or `&User{}` might allocate on the **goroutine stack** with zero garbage-collection overhead, whereas declaring a plain local variable `var x int` can allocate on the **heap** if a closure or returned pointer outlives the stack frame!

Where a Go value lives—and how fast it is allocated—is decided by the collaboration of two systems:

1. **Compile-Time Escape Analysis (`cmd/compile/internal/escape`)**: Static dataflow analysis on the Abstract Syntax Tree (AST) that proves whether a variable's lifetime is strictly bounded by its declaring stack frame.
2. **Runtime Memory Allocator (`src/runtime/malloc.go`)**: A high-throughput, TCMalloc-inspired hierarchical allocator built around **per-`P` lock-free caches (`mcache`)**, **68 size classes**, and **`noscan` vs. `scan` span segregation**.

## Before you start

In Go you write `p := &Point{1, 2}` and never say whether it lives on the stack or the heap. The compiler decides. A value that does not outlive its function can sit on the stack, which is nearly free to allocate and clean up. A value whose address escapes, say because you return it, must go on the heap, where the garbage collector has to track it. Seeing which one you got matters when a hot path is slow: `go build -gcflags=-m` prints the compiler's decisions.

This chapter covers both halves: how the compiler decides (escape analysis), and how the runtime hands out heap memory quickly without every goroutine fighting over one lock. It also explains how goroutine stacks grow.

Read [Go Runtime 01](/tech/series/go-runtime/01.gmp-scheduler-and-preemption/) first; the per-P caches here rely on the P described there.

Terms used in this chapter:

- **stack**: per-goroutine memory for local variables, released automatically when the function returns.
- **heap**: shared memory for values that outlive their function; reclaimed by the garbage collector.
- **escape analysis**: the compiler pass that decides whether a value can stay on the stack.
- **size class**: one of a fixed set of object sizes; a request is rounded up to the nearest one.
- **mspan**: a run of pages divided into equal-sized slots of one size class.
- **mcache**: a per-P cache of spans, so common allocations need no lock.
- **noscan**: a span holding objects with no pointers, which the garbage collector can skip.
- **stack growth**: when a goroutine's stack is full, the runtime allocates a bigger one and copies the contents over.

## 1. The Four-Tier Heap Hierarchy (`mspan` $\to$ `mcache` $\to$ `mcentral` $\to$ `mheap`)

Why doesn't `mallocgc` simply acquire a global heap lock and find a free block on every allocation? Because on a 64-core server running thousands of goroutines, a central heap lock would serialize every CPU core on L3 cache-line invalidations.

Instead, Go organizes virtual memory into **8 KiB runtime pages** (`_PageSize = 8192`) grouped into **64 MiB `heapArena`s** (on 64-bit Linux/macOS), and caches pre-sliced runs of pages (`mspan`) directly inside each logical processor **`P`** (`p.mcache`):

```text
          Goroutine G running on Processor P (Lock-Free Fast Path!)
          =========================================================
                                      |
             +------------------------+------------------------+
             | Tiny (<16B, noscan)    | Small (16B .. 32 KiB)  | Large (>32 KiB)
             v                        v                        |
  +--------------------------------------------------------+   |
  | 1. Per-P mcache (No locks! Attached to P, not M)       |   |
  |    - tiny allocator (packs bool/int8/int32 into 16B)   |   |
  |    - alloc[136]*mspan (68 size classes x scan/noscan)  |   |
  +--------------------------------------------------------+   |
                             | (if mspan is full)              |
                             v                                 |
  +--------------------------------------------------------+   |
  | 2. mcentral[136] (Per-SpanClass Mutex)                 |   |
  |    - partial (swept/unswept spans with free slots)     |   |
  |    - full    (swept/unswept spans with no free slots)  |   |
  +--------------------------------------------------------+   |
                             | (if mcentral is empty)          |
                             v                                 v
  +-------------------------------------------------------------------+
  | 3. mheap (Global Page Allocator Radix Tree + OS mmap/madvise)     |
  +-------------------------------------------------------------------+
```

### Inside `mspan` and the 136 `spanClass` Buckets

An **`mspan`** is a contiguous run of one or more 8 KiB pages carved into fixed-size object slots of a single **Size Class** (from `8 bytes`, `16 bytes`, `24 bytes`, `32 bytes`, `48 bytes`... up to `32,768 bytes` across **68 size classes** defined in `runtime/sizeclasses.go`).

Crucially, Go doubles those 68 size classes into **136 `spanClass` buckets**:
$$\text{spanClass} = (\text{sizeClass} \ll 1) \;\mid\; \text{noscan}$$

- **`scan` (`noscan == 0`)**: Objects that contain one or more pointers (such as `*T`, `string`, `[]T`, `map`, `chan`, or `any`). The garbage collector must trace through their pointer bitmaps during the mark phase.
- **`noscan` (`noscan == 1`)**: Objects that contain **zero pointers** (such as `[1024]byte`, `struct{ ID uint64; Price float64 }`, or the backing array of `[]byte` / `string`).
  - **Why `noscan` Is a Superpower**: When you allocate a `[]byte` buffer or a pointer-free struct in a map (`map[[16]byte]uint64`), it lands in a `noscan` `mspan`. During Garbage Collection, the GC marks the `mspan` slot bit as reachable and **stops immediately without scanning a single byte inside the object**!

### The Three Allocation Paths in `mallocgc()`

| Object Category | Size & Pointer Rule | Allocation Path in `runtime/malloc.go` | Lock Contention |
| :--- | :--- | :--- | :--- |
| **1. Tiny Objects** | `< 16 bytes` AND **`noscan`** (no pointers!) | Packed together into a shared 16-byte block (`mcache.tiny`, `tinyoffset`) using bump-pointer alignment (`2B`, `4B`, `8B`). Up to sixteen 1-byte `bool`s share a single 16B slot! | **Zero locks** (per-`P` `mcache`) |
| **2. Small Objects** | `16 B .. 32 KiB` (or `< 16B` containing a pointer) | Rounded up to one of 67 size classes (`8B..32KiB`). Finds next `0` bit in `mcache.alloc[spc].allocBits` via hardware `ctz` instruction (`nextFreeFast`). | **Zero locks** until `mspan` fills; then acquires per-class `mcentral` lock |
| **3. Large Objects** | `> 32,768 bytes` (`_MaxSmallSize`) | Bypasses `mcache` and `mcentral` completely; allocates a custom multi-page `mspan` directly from `mheap.alloc()` radix tree. | Acquires global `mheap.lock` |

## 2. How Goroutine Stacks Grow: Segmented "Hot Splits" vs. Contiguous Copying

Every newly spawned goroutine begins with a **2 KiB stack** (`_FixedStack = 2048`). What happens when a deep call chain exceeds 2 KiB?

In Go 1.0 to 1.2, the runtime used **segmented stacks** (linked lists of stack chunks). However, segmented stacks suffered from a notorious pathology called the **"Hot Split" problem**: if a tight `for` loop sat right at the boundary of a stack segment and called a function on every iteration, every single call allocated and linked a new stack segment (`morestack`) and every return freed it (`lessstack`), adding hundreds of nanoseconds of overhead per loop iteration!

Since **Go 1.3**, Go uses **contiguous resizable stacks** (`runtime/stack.go`):

1. At function entry, if `SP <= g.stackguard0`, the prologue calls `runtime.morestack_noctxt()` (switching onto `m.g0`).
2. `newstack()` allocates a brand-new contiguous stack segment of **double the current size** ($2\text{ KiB} \to 4\text{ KiB} \to 8\text{ KiB} \to \dots$, drawing from a per-`P` stack cache for sizes `< 32 KiB`).
3. `copystack()` copies the entire active stack frame memory from the old stack to the new stack and **walks every active stack frame's pointer map, rewriting any stack-to-stack pointers** (`old_addr + delta`) to point into the new stack!
4. The old stack is freed immediately, and subsequent iterations of a loop run at full native speed with zero "hot split" penalty. (Conversely, during GC stack scanning, if a goroutine uses less than $1/4$ of its stack, `shrinkstack` halves it back down.)

## 3. Compiler Escape Analysis: Two Fundamental Invariants

How does `cmd/compile` decide whether a variable can stay on that cheap, self-cleaning 2 KiB goroutine stack or must escape to the shared `mheap`?

You can ask the Go compiler directly with `-gcflags="-m=2"`:

```bash
go build -gcflags="-m=2" .
```

The escape analyzer constructs a static dataflow graph governed by two core invariants (often summarized by Bill Kennedy as *"Sharing Down vs. Sharing Up"*):

```text
  1. Sharing DOWN to a Callee (Stays on Stack!)
  =============================================
  func parent() {
      u := User{ID: 42}       // Allocated in parent()'s stack frame
      validate(&u)            // Pointer passed DOWN into validate();
  }                           // parent() outlives validate(), so &u is safe on stack!

  2. Sharing UP to a Caller (Escapes to Heap!)
  ============================================
  func createUser() *User {
      u := User{ID: 42}       // Returned UP after createUser()'s frame is popped!
      return &u               // "moved to heap: u" -> rewritten into runtime.newobject()
  }
```

### The Five Classic Escape Triggers in Production Go

1. **Returning a pointer (`*T`) or storing a pointer into a heap-reachable struct/slice/channel**: Sharing up outlives the declaring stack frame.
2. **Interface Boxing & Dynamic Dispatch (`any`, `fmt.Println(x)`, `io.Reader`)**:
   - In Go, an empty interface (`any` / `interface{}`) is a 16-byte pair `(type *_type, data unsafe.Pointer)`, and a non-empty interface (`io.Reader`) is `(itab *itab, data unsafe.Pointer)`.
   - Notice the second word is always an **`unsafe.Pointer` (`data`)**! Passing a concrete non-pointer value `x` (larger than a machine word or not covered by static small-integer table `staticuint64s[0..255]`) into an interface requires boxing `x` via `runtime.convT`! And if the compiler cannot devirtualize the interface method call (`io.Reader.Read(buf)`), it must assume the unknown concrete implementation might store `buf` on the heap—causing `buf` to escape!
3. **Capturing mutable variables in a Closure or `go func()`**: If a closure modifies a local variable `count` declared in the outer function (or if the closure escapes to another goroutine), `count` is promoted to a heap-allocated box so both scopes share its address.
4. **Slice allocations with runtime-variable size or $> 64\text{ KiB}$**:
   - `buf := make([]byte, 4096)` (constant size $\le 64\text{ KiB}$ that does not escape) is allocated **directly on the goroutine stack**!
   - `buf := make([]byte, n)` where `n` is only known at runtime escapes to the heap (`make([]byte, n) escapes to heap`), because goroutine stack frame offsets must be statically known at compile time! Recent Go releases relax this for small sizes: since Go 1.25 the compiler can back a variable-size `make` with a small stack buffer when `n` turns out to be small (32 bytes), so only the larger cases in the lab below are guaranteed to hit the heap.
5. **Pointers stored inside a Slice (`[]*T`) or Map (`map[K]*T`)**: If the slice or map backing store is heap-allocated, or the compiler cannot prove it stays local, the stored pointee (`s[0] = &item`) is forced onto the heap too.

## 4. Verification Lab: `noscan` vs. `scan` Spans, Escape Analysis & Contiguous Stack Copying

The following self-contained Go verification program (`go run`) demonstrates and verifies three runtime memory behaviors using `runtime.ReadMemStats` and stack address inspection:

1. **Stack vs. Heap Escape (`make([]byte, 4096)` vs. `make([]byte, n)`)**: Proves that a constant-size 4 KiB slice stays on the stack (`0 allocs/op`), whereas a runtime-variable length slice `make([]byte, n)` escapes to the heap on every call.
2. **Contiguous Stack Copying & Pointer Adjustment (`copystack`)**: Takes the raw memory address (`uintptr(unsafe.Pointer(&localVar))`) of a stack-allocated `int` before and after recursive stack growth (`2 KiB -> 64 KiB`), proving that Go's contiguous stack allocator **physically moves the stack frame to a new virtual address** and rewrites the Go pointer `&localVar` seamlessly!
3. **Size-Class Rounding (`mspan` internal fragmentation)**: Verifies through `TotalAlloc` that heap-allocating a 33-byte slice (`make([]byte, 33)`) consumes a **48-byte** size-class slot per allocation.

```go
package main

import (
	"fmt"
	"runtime"
	"unsafe"
)

//go:noinline
func sumConstantStackSlice(seed byte) int {
	// Constant size <= 64 KiB that does not escape -> allocated on Goroutine stack!
	buf := make([]byte, 4096)
	buf[0] = seed
	buf[4095] = seed + 1
	return int(buf[0]) + int(buf[4095])
}

//go:noinline
func sumDynamicHeapSlice(n int, seed byte) int {
	// Non-constant size n -> compiler cannot size stack frame statically -> escapes to heap!
	buf := make([]byte, n)
	buf[0] = seed
	buf[n-1] = seed + 1
	return int(buf[0]) + int(buf[n-1])
}

//go:noinline
func growStackRecursively(depth int, p *int) int {
	var pad [512]byte // Forces stack growth across recursive frames
	pad[0] = byte(depth)
	if depth == 0 {
		*p += 100
		return int(pad[0]) + *p
	}
	return growStackRecursively(depth-1, p) + int(pad[0])
}

func verifyStackVsHeapEscape() {
	var mBefore, mAfter runtime.MemStats

	runtime.ReadMemStats(&mBefore)
	acc := 0
	for i := 0; i < 1000; i++ {
		acc += sumConstantStackSlice(byte(i))
	}
	runtime.ReadMemStats(&mAfter)
	stackMallocs := mAfter.Mallocs - mBefore.Mallocs

	runtime.ReadMemStats(&mBefore)
	for i := 0; i < 1000; i++ {
		acc += sumDynamicHeapSlice(4096, byte(i))
	}
	runtime.ReadMemStats(&mAfter)
	heapMallocs := mAfter.Mallocs - mBefore.Mallocs
	_ = acc

	fmt.Printf("  [1. Escape Analysis (1,000 calls)] constant make([]byte, 4096) heap allocs=%d | dynamic make([]byte, n) heap allocs=%d\n",
		stackMallocs, heapMallocs)
	if stackMallocs != 0 || heapMallocs < 1000 {
		panic(fmt.Sprintf("Unexpected allocation counts: stack=%d, heap=%d", stackMallocs, heapMallocs))
	}
}

func verifyContiguousStackCopyAndPointerRewrite() {
	done := make(chan struct{})
	go func() {
		defer close(done)
		localVal := 42
		ptrToLocal := &localVal // Points into initial 2 KiB goroutine stack

		addrBefore := uintptr(unsafe.Pointer(ptrToLocal))
		_ = growStackRecursively(60, ptrToLocal) // Grows stack > 32 KiB, triggering copystack()!
		addrAfter := uintptr(unsafe.Pointer(ptrToLocal))

		fmt.Printf("  [2. Contiguous Stack Growth]       localVal=%d | stack addr before=0x%x -> after=0x%x (moved=%v)\n",
			*ptrToLocal, addrBefore, addrAfter, addrBefore != addrAfter)
		if *ptrToLocal != 142 || addrBefore == addrAfter {
			panic("Expected copystack() to relocate stack frame and update ptrToLocal")
		}
	}()
	<-done
}

func verifySizeClassRounding() {
	// runtime/sizeclasses.go: size classes around 32B are: 8, 16, 24, 32, 48, 64...
	b32 := make([]byte, 32)
	b33 := make([]byte, 33)
	// When Go allocates a slice backing array on the heap (or via runtime.makeslice),
	// let's force heap allocation by sending through a channel to inspect mspan rounding:
	ch := make(chan []byte, 2)
	ch <- make([]byte, 32)
	ch <- make([]byte, 33)
	h32, h33 := <-ch, <-ch
	_ = b32
	_ = b33

	var m1, m2 runtime.MemStats
	sink := make([][]byte, 1000)
	runtime.ReadMemStats(&m1)
	for i := 0; i < 1000; i++ {
		sink[i] = make([]byte, 33) // 33 bytes rounds up to the 48-byte mspan size class!
	}
	runtime.ReadMemStats(&m2)
	bytesPer33BAlloc := (m2.TotalAlloc - m1.TotalAlloc) / 1000
	runtime.KeepAlive(sink)
	runtime.KeepAlive(h32)
	runtime.KeepAlive(h33)

	fmt.Printf("  [3. mspan Size-Class Rounding]     requesting 33 bytes allocates %d bytes per slot in mspan (48B size class)\n",
		bytesPer33BAlloc)
	if bytesPer33BAlloc < 48 {
		panic(fmt.Sprintf("Expected 33-byte allocation to round up to 48-byte size class, got %d", bytesPer33BAlloc))
	}
}

func main() {
	fmt.Println("=== Go Runtime Lab 02: Memory Allocator, Size Classes & Escape Analysis ===")
	verifyStackVsHeapEscape()
	verifyContiguousStackCopyAndPointerRewrite()
	verifySizeClassRounding()
	fmt.Println("All Go Runtime Lab 02 invariants verified.")
}
```

## Key Takeaways

1. **Per-`P` `mcache` makes small allocations lock-free**: Objects $\le 32\text{ KiB}$ are served straight from the executing processor `P`'s `mcache` across 68 size classes without touching a global mutex.
2. **Eliminate pointers from large caches to unlock `noscan` spans**: Replacing `map[string]*Record` with a value struct containing integer indices (`noscan`) lets the garbage collector skip scanning the entire collection during the mark phase.
3. **Never take the address of a Go stack variable in C or across `uintptr`**: Because `copystack()` relocates goroutine stacks to a new virtual address when they grow and rewrites typed Go pointers (`*T`), storing a raw `uintptr` to a stack variable will dangle the moment the stack doubles!
