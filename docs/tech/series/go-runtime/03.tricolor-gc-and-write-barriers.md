Unlike the Java HotSpot JVM (`G1GC`, `Generational ZGC`) or the .NET CLR, Go's garbage collector (`src/runtime/mgc.go`) is **non-generational** and **non-compacting** (it does not move heap objects). Why?

1. **Why non-compacting?** As we saw in Chapter 02, Go's TCMalloc-derived allocator partitions every 8 KiB `mspan` into fixed-size slots across 68 size classes. Because objects of a given size class always occupy identical slot widths, **external fragmentation within an `mspan` is impossible**, and sweeping a freed object requires only flipping a single bit (`allocBits = gcmarkBits`) in $O(1)$ time!
2. **Why non-generational?** A generational collector requires a **write barrier to run 100% of the time** (even when GC is idle) to track old-to-young pointers in a Remembered Set / Card Table. In Go, **compile-time escape analysis** already keeps the vast majority of short-lived "nursery" objects on the goroutine stack—where they are freed in zero instructions when the function returns—leaving Go's write barrier completely turned off (`writeBarrier.enabled == false`) outside the concurrent mark phase!

This chapter traces how Go achieves sub-millisecond Stop-The-World (STW) pauses using **Concurrent Tricolor Mark-Sweep**, why Go 1.8 combined Dijkstra and Yuasa barriers into the **Hybrid Write Barrier**, how **Mutator Assists** prevent runaway allocators from outrunning background markers, and how to tune **`GOGC` + `GOMEMLIMIT`** in cgroup-constrained containers.

## Before you start

Go frees heap memory with a garbage collector that runs while your program keeps running. That is the difficulty. To find garbage, the collector walks from the live variables and marks what it reaches; if your code rewires pointers during the walk, the collector can miss a live object and free it, which would corrupt the program.

The chapter explains the bookkeeping that prevents this. Objects are colored white (not yet seen), grey (seen, children not checked) or black (done). A write barrier is a few extra instructions on every pointer write that keeps the rule "a black object never points to a white one" true. You will also meet the two tuning knobs you can set in production, `GOGC` and `GOMEMLIMIT`.

Read [Go Runtime 02](/tech/series/go-runtime/02.memory-allocator-and-escape-analysis/) first for how heap objects and spans are laid out.

Terms used in this chapter:

- **mark-sweep**: a collection scheme that first marks reachable objects, then frees the rest.
- **concurrent GC**: a collector that runs at the same time as your program rather than pausing it for the whole cycle.
- **mutator**: the GC literature's word for your program, because it mutates the object graph.
- **tricolor marking**: tracking marking progress with white, grey and black object states.
- **write barrier**: code the compiler adds to pointer writes during marking so the collector sees changes.
- **mutator assist**: a goroutine that allocates quickly being made to do some marking work itself.
- **GOGC**: the setting for how much the heap may grow, as a percentage over live data, before the next cycle.
- **GOMEMLIMIT**: a soft cap on the total memory the Go runtime uses.

## 1. The Tricolor Abstraction & the Concurrent Lost-Object Bug

Edsger Dijkstra's tricolor marking algorithm partitions every object in the graph into three sets during a GC cycle:

- **White (Unvisited / Candidate for Collection)**: Objects not yet reached by the marker. At the start of marking, all heap objects are White; at the end of marking, any remaining White objects are unreachable garbage and are reclaimed.
- **Grey (Discovered, Pending Field Scan)**: Objects proven reachable, sitting on a per-`P` **`gcWork` worklist**, whose outgoing pointer fields have not yet been inspected.
- **Black (Scanned & Live)**: Objects proven reachable whose outgoing pointers have all been scanned (they hold no pointers to White objects at the moment they turn Black).

### How Concurrent Mutation Breaks Naive Tricolor Marking

If the collector runs **concurrently** while user goroutines (**mutators**) modify pointers, a live White object `C` will be **erroneously freed (the Lost Object Bug)** if and only if **two conditions occur simultaneously**:

1. **Condition 1**: A **Black** object `A` is mutated to point to a **White** object `C` (`A.next = C`).
2. **Condition 2**: Every existing path from any **Grey** object `B` to that **White** object `C` is destroyed (`B.next = nil`) before the marker scans `B`.

```text
  Before Mutator Edits:        Root -> [Black A]    [Grey B] ---> [White C]

  Mutator Executes:
    1. A.next = C              Root -> [Black A] ---------------> [White C]
    2. B.next = nil                    [Grey B]  --X (path broken)

  Result Without Write Barrier:
    Black A is already scanned (won't be scanned again).
    Grey B no longer points to C.
    White C is swept as garbage while Black A still holds a live pointer to C!
```

To prevent this without stopping the world, the collector only needs to falsify **either** Condition 1 **or** Condition 2 using a compiler-inserted **Write Barrier** (`if writeBarrier.enabled { gcWriteBarrier(...) }`):

| Invariant / Barrier | Rule Enforced on `*slot = ptr` | Advantage | Fatal Drawback on Goroutine Stacks |
| :--- | :--- | :--- | :--- |
| **Strong Tricolor Invariant — Dijkstra Insertion Barrier** | Forbids Black $\to$ White edges by shading the **new target** `shade(ptr)` Grey whenever a pointer is written into the heap. | Conservative and simple on heap slots. | Putting a write barrier on every *stack* register/local write would cripple CPU speed; so stacks must stay un-instrumented and **all active goroutine stacks had to be re-scanned during STW Mark Termination** (taking 10–100 ms with 100,000 goroutines!). |
| **Weak Tricolor Invariant — Yuasa Deletion Barrier (SATB)** | Preserves Snapshot-at-the-Beginning paths by shading the **overwritten old target** `shade(*slot)` Grey when a pointer is deleted/overwritten. | Requires **zero STW stack re-scanning** at Mark Termination. | Lower recall ("floating garbage"): requires shading stacks or intercepting stack-to-heap moves if a new reference is copied from an unscanned stack. |

## 2. Go 1.8's Hybrid Write Barrier (`runtime/mbarrier.go`)

To eliminate Stop-The-World stack re-scanning completely while keeping stack operations barrier-free, Austin Clements and Rick Hudson introduced the **Hybrid Write Barrier** in Go 1.8:

```go
// Conceptual pseudocode of Go's Hybrid Write Barrier on heap write (*slot = ptr):
func writePointer(slot *unsafe.Pointer, ptr unsafe.Pointer) {
    shade(*slot) // 1. Yuasa deletion barrier: shade the overwritten old pointer Grey!
    if currentGoroutineStackIsGrey() {
        shade(ptr) // 2. Dijkstra insertion barrier: shade the new pointer Grey!
    }
    *slot = ptr
}
```

Combined with the rule that **every goroutine stack is scanned once (turning the stack permanently Black for that GC cycle) and all newly allocated objects during Mark are born Black**, the Hybrid Write Barrier guarantees:

1. User stack writes (`x := p.field`) execute at full native CPU speed with **zero write barriers**.
2. Once a goroutine's stack is scanned during the concurrent mark phase, it stays Black—**Mark Termination requires zero stack re-scanning**, dropping STW pauses to **$\sim 50\text{–}300\ \mu\text{s}$** largely independent of how many goroutines you have, because stacks are no longer re-scanned in the pause!
3. Instead of locking the global work queue on every pointer write, each processor `P` buffers shaded pointers inside a 512-entry per-`P` **`wbBuf`** cache and flushes them to `gcWork` in batches.

### "Green Tea GC": Span-Local Memory-Order Scanning

Green Tea shipped as an experiment in Go 1.25 (`GOEXPERIMENT=greenteagc`) and became the default in Go 1.26. In traditional object-graph traversal, popping pointers from the `gcWork` queue jumps randomly across the heap, so a large share of GC time goes to waiting on cache and memory misses.

Go's **Green Tea GC** redesigns small-object marking around **`mspan` page locality**: instead of immediately chasing isolated pointers across random memory addresses, small objects are queued on **span-granular worklists** (`pageMarks` / `pageScanned` bitmaps) and scanned in address order (with vector instructions on CPUs that support them), reducing cache misses. The Go team reports roughly 10–40% less GC CPU on GC-heavy programs; your gain depends on the heap shape.

## 3. Mutator Assists & Tuning `GOGC` vs. `GOMEMLIMIT`

By default, Go dedicates **25% of `GOMAXPROCS` CPU capacity** (`gcBackgroundUtilization = 0.25`) to background mark workers (`gcBgMarkWorker`).

What happens if a burst of incoming HTTP requests causes user goroutines to allocate new heap memory **faster** than the 25% background workers can finish scanning the heap?

### Mutator Assists (`gcAssistAlloc`)

To prevent heap overshoot before marking completes, the runtime enforces a **pay-as-you-allocate backpressure mechanism**:

- Every goroutine has a `g.gcAssistBytes` credit balance.
- When a goroutine calls `mallocgc` during the mark phase and its assist balance goes negative, `mallocgc` forces the user goroutine itself to run **`gcAssistAlloc()`**—scanning $N$ bytes of grey heap work proportional to the bytes it just allocated (the `assistWorkPerByte` ratio computed by the GC Pacer)!

### The Two Knobs: `GOGC` (`SetGCPercent`) vs. `GOMEMLIMIT` (`SetMemoryLimit`)

Until Go 1.19, the GC Pacer had only one knob: **`GOGC`** (default `100`), which sets the target heap growth ratio relative to the **live marked heap**:
$$\text{Target Heap} = \text{Live Heap} \times \left(1 + \frac{\text{GOGC}}{100}\right)$$

Notice the trap inside a Kubernetes container with `memory.max = 2 GiB`:

- If a transient spike raises your Live Heap to `1.2 GiB`, `GOGC=100` sets the next GC target to **$2.4\text{ GiB}$**—causing the Linux kernel cgroup v2 controller to **OOM-kill (`137`)** your container even though 800 MiB of the heap was collectable garbage!
- Conversely, if you lowered `GOGC=20` permanently, the collector would waste CPU running constant GC cycles even when the container was only using 200 MiB of its 2 GiB limit!

**Go 1.19+ `GOMEMLIMIT` (`debug.SetMemoryLimit`)** solves this cleanly:

- Set **`GOGC=100`** (or even **`GOGC=off`** for batch/cache workloads) and set **`GOMEMLIMIT` to ~85–90% of the container's cgroup `memory.max`** (e.g., `GOMEMLIMIT=1800MiB` on a `2 GiB` Pod, leaving 10–15% headroom for non-Go C/OS memory and transient overshoot).
- As long as total runtime memory stays well below `GOMEMLIMIT`, `GOGC=100` governs normal low-CPU collection cadence. As the heap approaches `GOMEMLIMIT`, the GC Pacer automatically accelerates collection cycles to stay underneath the container ceiling. (And to prevent a "death spiral" if live memory genuinely reaches 100% of `GOMEMLIMIT`, the runtime caps total GC + Assist CPU utilization at **50%** over a `1 * GOMAXPROCS`-second window rather than freezing the application at 100% GC CPU.)

## 4. Verification Lab: Tricolor Hybrid Write Barrier & `GOMEMLIMIT` Pacer in Go

The following self-contained Go verification program (`go run`) tests and verifies:

1. **The Lost-Object Scenario & Hybrid Write Barrier**: Simulates the exact concurrent sequence where a Black node `A` acquires a pointer to a White node `C` (`A.Child = C`) while the Grey node `B` drops its pointer (`B.Child = nil`), proving that without the Hybrid Write Barrier (`shade(*slot)`), `C` is lost, whereas the Hybrid Write Barrier preserves `C` with **zero stack re-scans**.
2. **Live Runtime GC Telemetry via `runtime/metrics` & `debug.SetMemoryLimit`**: Configures a soft memory limit via `debug.SetMemoryLimit` and reads exact GC cycle counts, live marked heap bytes (`/gc/heap/live:bytes`), and memory limit telemetry directly from Go's lock-free `runtime/metrics` subsystem.

```go
package main

import (
	"fmt"
	"runtime"
	"runtime/debug"
	"runtime/metrics"
)

// ---------------------------------------------------------------------------
// 1. Tricolor Mark-Sweep & Go 1.8 Hybrid Write Barrier Verifier
// ---------------------------------------------------------------------------
type Color uint8

const (
	White Color = iota
	Grey
	Black
)

type HeapNode struct {
	Name  string
	Color Color
	Child *HeapNode
}

type TricolorGCSimulator struct {
	EnableHybridBarrier bool
	GreyWorklist        []*HeapNode
	StackReScans        int
}

func (gc *TricolorGCSimulator) shade(n *HeapNode) {
	if n != nil && n.Color == White {
		n.Color = Grey
		gc.GreyWorklist = append(gc.GreyWorklist, n)
	}
}

// Hybrid Write Barrier executed on heap pointer assignment: *slot = newPtr
func (gc *TricolorGCSimulator) writePointer(slot **HeapNode, newPtr *HeapNode, stackIsGrey bool) {
	if gc.EnableHybridBarrier {
		// 1. Yuasa deletion barrier: shade the overwritten old target (*slot)
		gc.shade(*slot)
		// 2. Dijkstra insertion barrier (only if current goroutine stack is still grey)
		if stackIsGrey {
			gc.shade(newPtr)
		}
	}
	*slot = newPtr
}

func (gc *TricolorGCSimulator) drainMarkWorklist() {
	for len(gc.GreyWorklist) > 0 {
		curr := gc.GreyWorklist[len(gc.GreyWorklist)-1]
		gc.GreyWorklist = gc.GreyWorklist[:len(gc.GreyWorklist)-1]
		if curr.Child != nil && curr.Child.Color == White {
			gc.shade(curr.Child)
		}
		curr.Color = Black
	}
}

func runLostObjectExperiment(enableBarrier bool) Color {
	// Initial graph: BlackA (already scanned), GreyB -> WhiteC
	nodeC := &HeapNode{Name: "C", Color: White}
	nodeB := &HeapNode{Name: "B", Color: Grey, Child: nodeC}
	nodeA := &HeapNode{Name: "A", Color: Black, Child: nil}

	gc := &TricolorGCSimulator{
		EnableHybridBarrier: enableBarrier,
		GreyWorklist:        []*HeapNode{nodeB},
	}

	// Mutator runs concurrently after its stack was already scanned (stackIsGrey = false):
	// Step 1: Black nodeA points to White nodeC
	gc.writePointer(&nodeA.Child, nodeC, false)
	// Step 2: Grey nodeB drops its pointer to White nodeC BEFORE marker scans nodeB!
	gc.writePointer(&nodeB.Child, nil, false)

	// Marker drains remaining GreyWorklist with ZERO stack re-scans
	gc.drainMarkWorklist()
	return nodeC.Color
}

// ---------------------------------------------------------------------------
// 2. Live Go Runtime GOMEMLIMIT & runtime/metrics Verification
// ---------------------------------------------------------------------------
func verifyRuntimeMetricsAndMemoryLimit() {
	prevLimit := debug.SetMemoryLimit(64 * 1024 * 1024) // 64 MiB soft memory limit
	defer debug.SetMemoryLimit(prevLimit)

	// Allocate several 256 KiB slices so GC Pacer observes live heap and runs a cycle
	retained := make([][]byte, 8)
	for i := range retained {
		retained[i] = make([]byte, 256*1024)
	}
	runtime.GC()

	samples := []metrics.Sample{
		{Name: "/gc/cycles/total:gc-cycles"},
		{Name: "/gc/heap/live:bytes"},
		{Name: "/gc/gomemlimit:bytes"},
	}
	metrics.Read(samples)
	cycles := samples[0].Value.Uint64()
	liveBytes := samples[1].Value.Uint64()
	memLimit := samples[2].Value.Uint64()
	runtime.KeepAlive(retained)

	fmt.Printf("  [2. runtime/metrics Telemetry]   gc_cycles=%d | live_heap=%d KiB | gomemlimit=%d MiB\n",
		cycles, liveBytes/1024, memLimit/(1024*1024))
	if cycles == 0 || memLimit != 64*1024*1024 {
		panic("Expected runtime/metrics to report active GC cycles and 64 MiB GOMEMLIMIT")
	}
}

func main() {
	fmt.Println("=== Go Runtime Lab 03: Tricolor GC, Hybrid Write Barrier & GOMEMLIMIT ===")
	colorWithoutBarrier := runLostObjectExperiment(false)
	colorWithHybridBarrier := runLostObjectExperiment(true)

	colorName := map[Color]string{White: "White (LOST / FREED BUG!)", Grey: "Grey", Black: "Black (SAFE & MARKED)"}
	fmt.Printf("  [1. Concurrent Mutation A.Child=C; B.Child=nil]\n")
	fmt.Printf("      Without Write Barrier : Node C ended as %s\n", colorName[colorWithoutBarrier])
	fmt.Printf("      With Hybrid Barrier   : Node C ended as %s (0 STW stack re-scans)\n", colorName[colorWithHybridBarrier])

	if colorWithoutBarrier != White || colorWithHybridBarrier != Black {
		panic("Hybrid write barrier invariant failed")
	}
	verifyRuntimeMetricsAndMemoryLimit()
	fmt.Println("All Go Runtime Lab 03 invariants verified.")
}
```

## Key Takeaways

1. **Go's write barrier is off outside the Mark phase**: Because Go is non-generational and allocates short-lived values on the goroutine stack via escape analysis, pointer writes execute with zero barrier overhead whenever GC is not actively marking.
2. **The Hybrid Write Barrier (`shade(*slot)` + `shade(ptr)`) eliminates STW stack re-scanning**: Shading overwritten heap pointers (Yuasa) combined with born-Black allocations lets Go scan each goroutine stack only once per cycle, keeping STW pauses in the microsecond range.
3. **Always pair container `memory.max` with `GOMEMLIMIT`**: Configure `GOMEMLIMIT` to 85–90% of your container's cgroup v2 `memory.max` limit so the GC Pacer automatically reclaims garbage before the Linux OOM killer intervenes.
