When you write `new Object()` in Java, how many bytes of physical RAM are allocated on the HotSpot 64-bit heap?

The answer is **16 bytes**: an empty Java object contains no user fields, but it carries an 8-byte **Mark Word**, a 4-byte compressed **Klass Word** (`CompressedClassPointers`), and 4 bytes of alignment padding to reach an 8-byte address boundary.

Every runtime capability of the Java language—from identity hash codes (`System.identityHashCode()`) and generational GC aging (`age <= 15`) to intrinsic locks (`synchronized`) and biased locking transitions—is bit-packed directly into the **Mark Word** of the object's header (`oopDesc`).

## 1. HotSpot 64-Bit Object Layout: Mark Word, Klass Word & Field Packing

In HotSpot C++ terminology, an ordinary Java object on the heap is represented by an **`instanceOop`** (`ordinary object pointer`). Its memory layout consists of three contiguous regions:

```text
  +------------------------------------------------------------------------+
  | 1. Mark Word (8 bytes = 64 bits)                                       |
  |    Holds GC age, identity hash code, lock bits, and monitor pointers   |
  +------------------------------------------------------------------------+
  | 2. Klass Word (4 bytes compressed with +UseCompressedClassPointers)    |
  |    Points to InstanceKlass in Metaspace (C++ native memory)            |
  +------------------------------------------------------------------------+
  | 3. Instance Fields (Variable size)                                     |
  |    Primitive fields (long/double:8B, int/float:4B, short/char:2B,      |
  |    byte/boolean:1B) and references (4B compressed oops)               |
  +------------------------------------------------------------------------+
  | 4. Padding (0 to 7 bytes)                                              |
  |    Rounds total object allocation up to the nearest 8-byte boundary    |
  +------------------------------------------------------------------------+
```

### The 64-Bit Mark Word Bit Encoding Matrix

Open `src/hotspot/share/oops/markWord.hpp`. The lowest **2 bits** (`[1:0]`) of the 64-bit Mark Word determine the lock state:

| Lock State | Bits `[63:3]` | `[2]` (Biased) | `[1:0]` (Lock) | Description |
| :--- | :--- | :--- | :--- | :--- |
| **Normal / Unlocked** | `[unused:25]` `[identity_hashcode:31]` `[unused:1]` `[age:4]` | `0` | **`01`** | Default state for newly allocated objects without lock contention. |
| **Lightweight (Thin Lock)** | **62-bit Pointer to Lock Record on Owner's Stack** | `0` | **`00`** | Single thread holds the lock, or uncontended synchronized block. |
| **Heavyweight (Inflated)** | **62-bit Pointer to `ObjectMonitor` in C++ Heap** | `0` | **`10`** | Contended synchronization; waiting threads parked on kernel futex. |
| **Marked for GC** | **Mark bits used during STW / Concurrent Mark** | `0` | **`11`** | Set by garbage collector during mark phase. |

Notice why the maximum GC tenure age before promotion to Old Gen is **15**: because `age` occupies only **4 bits** ($2^4 - 1 = 15$). Setting `-XX:MaxTenuringThreshold=16` fails with an argument error!

## 2. CompressedOops: How 32-Bit Offsets Address 32 GiB of 64-Bit RAM

On a 64-bit architecture, native pointers are 8 bytes long. If every object reference in a large heap were 8 bytes, pointer overhead alone would consume 30–40% of the entire heap!

HotSpot solves this via **CompressedOops (`-XX:+UseCompressedOops`)**:

- Because HotSpot aligns all objects to an **8-byte boundary**, the lowest 3 bits of every object's physical byte address are always `000` (`addr % 8 == 0`).
- By discarding those 3 zero bits, a **32-bit integer** can represent $2^{32} \times 8\text{ bytes} = \mathbf{32\text{ GiB}}$ of heap space!
- The CPU converts between compressed 32-bit oops (`narrowOop`) and 64-bit memory addresses using a single register bit-shift:
  $$\text{Real Address} = \text{HeapBase} + (\text{narrowOop} \ll 3)$$

> **The 32 GiB Heap Cliff**:
> If you configure `-Xmx32g` or higher, HotSpot can no longer fit the shifted offset in 32 bits. It disables `CompressedOops`, forcing all object references back to 8 bytes! A heap sized at `31 GiB` with CompressedOops typically holds **more usable live objects** than a heap sized at `33 GiB` without CompressedOops!

## 3. The Synchronization Lock Inflation Lifecycle

In HotSpot, entering a `synchronized(obj)` block is not a static kernel mutex call. The JVM dynamically inflates the lock through three tiers based on measured contention:

### Tier 1: Biased Locking (Historical Context)

- Historically, HotSpot assumed locks are acquired mostly by a single thread repeatedly (`biasable`). It wrote the owner thread ID directly into the Mark Word.
- *Status in Modern Java*: In complex multi-threaded workloads, revoking a bias required expensive Stop-The-World safepoints. HotSpot deprecated biased locking in JDK 15 (`JEP 374`) and disabled/removed it in modern JDKs.

### Tier 2: Lightweight Lock (Thin Lock) via Stack Lock Records

When a thread `T1` executes `monitorenter` on an unlocked object `obj` (`lock == 01`):

1. `T1` allocates a **Lock Record** in its own execution stack frame (`BasicObjectLock`).
2. `T1` copies the object's current Mark Word into the Lock Record (the **Displaced Mark Word**).
3. `T1` executes an atomic CAS: attempting to replace the object's Mark Word with a **pointer to `T1`'s Stack Lock Record**, with the lowest 2 bits set to **`00`**.
4. If CAS succeeds, `T1` holds the lightweight lock! The entire synchronization operation required **zero kernel transitions and zero heap allocations**.
5. When `T1` exits `monitorexit`, it CASes the Displaced Mark Word back from its stack frame into `obj`.

### Tier 3: Contention & Heavyweight Monitor Inflation

What happens if Thread `T2` calls `synchronized(obj)` while `T1` still holds the lightweight lock?

1. `T2`'s CAS fails because the lowest bits are `00` (already locked).
2. If `T2` observes `T1` is actively running on another CPU core, it executes **Adaptive Spinning** (spinning in a tight `PAUSE` loop for a few dozen iterations, predicting `T1` will release shortly).
3. If the spin limit is exhausted before `T1` unlocks, the lock **inflates into a Heavyweight Monitor**:
   - HotSpot allocates an **`ObjectMonitor`** instance in native C++ heap memory.
   - The object's Mark Word is updated via CAS to point to the `ObjectMonitor*`, with the lowest 2 bits set to **`10`**.
   - `ObjectMonitor` maintains an owner field (`_owner = T1`) and two wait queues: **`_cxq`** (Contention Queue — a lock-free LIFO stack where newly contending threads CAS themselves onto the head) and **`_EntryList`** (threads ready to re-compete for ownership).
   - Thread `T2` suspends itself using **Linux `futex` / `pthread_mutex`** (`PlatformEvent::park()`), consuming zero CPU cycles until `T1` calls `monitorexit` and wakes a successor via `unpark()`.

## 4. ClassLoading Architecture: Delegation & the 3-Phase Linkage Contract

In Java, classes are loaded dynamically on demand. The runtime architecture rests on two foundational rules:

### 1. Dual-Identity Rule

A class in the JVM is uniquely identified **not by its binary name alone**, but by the tuple:
$$\text{Class Identity} = \bigl(\text{Binary Name}, \text{Defining ClassLoader Instance}\bigr)$$
Two classes named `com.example.User` loaded by two different `ClassLoader` instances are completely incompatible: assigning one to the other throws `ClassCastException`!

### 2. The 3-Phase Linkage Contract (`Loading` $\to$ `Linking` $\to$ `Initialization`)

```text
  [1. Loading]
       |  Locates byte array (.class file or network jar) via ClassLoader.findClass()
       v
  [2. Linking]
       +--> A. Verification: Checks 0xCAFEBABE magic, bytecode stack bounds, no invalid jumps
       +--> B. Preparation : Allocates static fields in Metaspace and zeroes them to default values!
       +--> C. Resolution  : Resolves symbolic references in Constant Pool to direct memory pointers
       v
  [3. Initialization]
       Executes static initializer <clinit>() and static variable initializers under a lock!
```

> **The `<clinit>` Deadlock Trap**:
> The JVM specification mandates that class initialization (`<clinit>`) is thread-safe: the runtime acquires an internal Class Initialization Lock on the class object. If Class `A`'s static block references Class `B`, while Class `B`'s static block simultaneously references Class `A`, two threads initializing them concurrently will **deadlock forever inside the JVM classloader** with zero stack traces in Java code!

## 5. Verification Lab: Mark Word Bit Layout & Contended Monitor Inflation

The following self-contained Java 21 program (`java Lab01.java`) proves and verifies:

1. **Object Header Overhead & Identity Hash Code Mutation**: Proves that calling `System.identityHashCode(obj)` generates an identity hash that permanently mutates the object's Mark Word.
2. **Lightweight Lock to Heavyweight Monitor Inflation**: Launches 8 concurrent worker threads contending heavily on a single synchronized object, confirming that contested locks inflate from thread stack records into OS-parked monitors.
3. **ClassLoader Parent Hierarchy**: Traverses and verifies the `AppClassLoader` $\to$ `PlatformClassLoader` $\to$ `null` (Bootstrap ClassLoader) delegation tree.

```java
import java.lang.management.ManagementFactory;
import java.lang.management.ThreadInfo;
import java.lang.management.ThreadMXBean;
import java.util.concurrent.CountDownLatch;
import java.util.concurrent.atomic.AtomicInteger;

public class Lab01 {

    static class SyncTarget {
        // Shared lock target
    }

    public static void main(String[] args) throws Exception {
        System.out.println("=== HotSpot JVM Lab 01: Object Header, Monitor Inflation & ClassLoader ===");

        // 1. Identity HashCode Mutation in Mark Word
        SyncTarget target = new SyncTarget();
        int hash1 = System.identityHashCode(target);
        int hash2 = System.identityHashCode(target);
        System.out.printf("  [1. Identity HashCode] hash=0x%08x (consistent=%b)%n", hash1, (hash1 == hash2));
        if (hash1 != hash2) {
            throw new AssertionError("Identity hash must be immutable once generated in Mark Word");
        }

        // 2. ClassLoader Parent Hierarchy Verification
        ClassLoader currentLoader = Lab01.class.getClassLoader();
        ClassLoader topParent = currentLoader;
        System.out.printf("  [2. ClassLoader Hierarchy] Initiating ClassLoader=%s%n", currentLoader.getClass().getSimpleName());
        while (topParent != null) {
            System.out.printf("                             Parent Loader=%s%n", topParent.getClass().getName());
            if (topParent.getParent() == null) {
                break;
            }
            topParent = topParent.getParent();
        }
        ClassLoader bootstrapLoader = topParent.getParent(); // bootstrap loader is represented as null in Java!
        System.out.printf("                             BootstrapLoader=%s (null is C++ bootstrap)%n", bootstrapLoader);
        if (bootstrapLoader != null) {
            throw new AssertionError("Bootstrap ClassLoader must be null in Java reflection");
        }

        // 3. Multithreaded Contention & Heavyweight Monitor Inflation
        final int THREAD_COUNT = 8;
        final CountDownLatch startGun = new CountDownLatch(1);
        final CountDownLatch doneLatch = new CountDownLatch(THREAD_COUNT);
        final AtomicInteger sharedCounter = new AtomicInteger(0);

        for (int i = 0; i < THREAD_COUNT; i++) {
            new Thread(() -> {
                try {
                    startGun.await();
                    for (int j = 0; j < 1000; j++) {
                        synchronized (target) {
                            sharedCounter.incrementAndGet();
                            if (j % 200 == 0) {
                                Thread.sleep(1); // Force lock contention & monitor inflation!
                            }
                        }
                    }
                } catch (Exception e) {
                    e.printStackTrace();
                } finally {
                    doneLatch.countDown();
                }
            }).start();
        }

        startGun.countDown(); // Fire start gun!

        // Inspect thread states during active contention
        Thread.sleep(5);
        ThreadMXBean mxBean = ManagementFactory.getThreadMXBean();
        ThreadInfo[] threadInfos = mxBean.getThreadInfo(mxBean.getAllThreadIds());
        int blockedOrWaitingCount = 0;
        for (ThreadInfo info : threadInfos) {
            if (info != null && (info.getThreadState() == Thread.State.BLOCKED || info.getThreadState() == Thread.State.TIMED_WAITING)) {
                blockedOrWaitingCount++;
            }
        }
        System.out.printf("  [3. Contended Monitor Inflation] Active parked/blocked threads=%d, Counter=%d%n",
                blockedOrWaitingCount, sharedCounter.get());

        doneLatch.await();
        System.out.printf("  [3. Completed] All 8 threads completed cleanly. Final counter=%d%n", sharedCounter.get());
        if (sharedCounter.get() != THREAD_COUNT * 1000) {
            throw new AssertionError("Counter mismatch under synchronized");
        }

        System.out.println("All HotSpot JVM Lab 01 invariants verified.");
    }
}
```

## Key Takeaways

1. **Every Java object carries an 8-byte Mark Word**: GC aging (max 15), identity hash codes, and lock pointers share a single 64-bit word distinguished by its lowest 2 bits (`01` unlocked, `00` thin lock, `10` heavyweight monitor, `11` GC).
2. **Keep heaps under 32 GiB for CompressedOops efficiency**: Crossing 32 GiB shifts pointers from 4-byte narrow offsets to full 8-byte native addresses, frequently wasting 4–8 GiB of physical RAM purely on pointer bloat.
3. **Lock contention inflates to kernel futexes automatically**: Uncontended synchronized blocks use fast stack-local CAS (`00`), while multi-threaded contention inflates the Mark Word to point to an `ObjectMonitor` (`10`) that parks threads via native OS primitives.
