Nearly every advanced concurrency primitive in `java.util.concurrent`—from `ReentrantLock`, `Semaphore`, and `CountDownLatch` to `ReentrantReadWriteLock`—is built upon a single foundational framework written by Doug Lea: **`AbstractQueuedSynchronizer` (AQS)**.

Before AQS, building a custom synchronizer required manually managing thread wait queues, handling thread interruption, avoiding race conditions between lock acquisition and release, and orchestrating native thread parking. AQS abstracts this entire mechanical complexity into three primitives:

1. An atomic, 32-bit `volatile int state` variable.
2. A lock-free, bidirectional **CLH wait queue** of waiting threads.
3. Native thread parking via **`LockSupport.park()` and `unpark()`**.

## 1. The AQS Core: State, CLH Queue & LockSupport

Open `java.base/java.util/concurrent/locks/AbstractQueuedSynchronizer.java`. AQS defines the skeleton algorithm for synchronizers:

```java
// The core state variable of AQS:
private volatile int state;

protected final int getState() { return state; }
protected final void setState(int newState) { state = newState; }
protected final boolean compareAndSetState(int expect, int update) {
    return STATE.compareAndSet(this, expect, update);
}
```

How different synchronizers map this single 32-bit `state` variable:

- **`ReentrantLock`**: `state == 0` means unlocked; `state > 0` represents the lock hold count by the `exclusiveOwnerThread` (reentrancy!).
- **`Semaphore`**: `state` represents the number of available permits.
- **`CountDownLatch`**: `state` represents the remaining count; `countDown()` decrements state, and `await()` blocks until `state == 0`.
- **`ReentrantReadWriteLock`**: Upper 16 bits hold the shared read lock count (`state >>> 16`); lower 16 bits hold the exclusive write lock count (`state & 0xFFFF`).

### The CLH Bidirectional Node Queue

When a thread fails to acquire the lock (`tryAcquire` returns `false`), AQS enqueues the thread at the tail of a bidirectional queue:

```text
  Head (Dummy / Sentinel Node) <---> Node (Thread 1) <---> Tail (Thread 2)
  [ waitStatus: SIGNAL (-1) ]        [ waitStatus: 0 ]     [ waitStatus: 0 ]
```

- **`waitStatus` States** (the classic constants of JDK 16 and earlier; JDK 17 rewrote the node states, using `WAITING = 1` and `CANCELLED = 0x80000000`, but the protocol is the same):
  - **`SIGNAL (-1)`**: The successor of this node is parked and requires unparking when this node releases.
  - **`CANCELLED (1)`**: The thread timed out or was interrupted; the node is unlinked from the queue.
  - **`CONDITION (-2)`**: The node is waiting on a `ConditionObject` wait queue.
  - **`PROPAGATE (-3)`**: Used in Shared mode (`Semaphore`) to ensure release broadcasts propagate to subsequent nodes.
- **Why `SIGNAL` Is Stored on the Predecessor**: A thread cannot safely set its own node to `SIGNAL` without risking race conditions if the owner releases concurrently. Instead, a waiting thread sets its **predecessor's `waitStatus` to `SIGNAL`** before calling `LockSupport.park()`. When the predecessor releases, it checks its own `waitStatus`: if it sees `SIGNAL`, it calls `unparkSuccessor()`.

## 2. ReentrantLock: Fair vs. Non-Fair Barging

When constructing a `ReentrantLock(boolean fair)`, what is the architectural difference between `FairSync` and `NonfairSync`?

```java
// Non-fair lock acquisition:
final boolean nonfairTryAcquire(int acquires) {
    final Thread current = Thread.currentThread();
    int c = getState();
    if (c == 0) {
        if (compareAndSetState(0, acquires)) { // BARGES IN DIRECTLY!
            setExclusiveOwnerThread(current);
            return true;
        }
    }
    // ...
}

// Fair lock acquisition:
protected final boolean tryAcquire(int acquires) {
    final Thread current = Thread.currentThread();
    int c = getState();
    if (c == 0) {
        if (!hasQueuedPredecessors() && compareAndSetState(0, acquires)) { // CHECKS QUEUE!
            setExclusiveOwnerThread(current);
            return true;
        }
    }
    // ...
}
```

- **Non-Fair Mode (Default)**: When a thread calls `lock()`, it immediately attempts a fast-path CAS (`compareAndSetState(0, 1)`). If the lock happens to be free at that exact microsecond, **it steals the lock immediately (barging)**, bypassing all threads waiting in the CLH queue!
  - *Why Non-Fair is faster*: An active thread already has its instruction pipeline and data caches loaded on the CPU. Letting it barge in saves a full context switch (~1.5–3 $\mu\text{s}$). Under high contention, `NonfairSync` can deliver several times the throughput of `FairSync` (measure on your own workload; the gap depends on contention and hold time).
- **Fair Mode**: A thread checks `hasQueuedPredecessors()` before calling CAS. If any thread is already waiting ahead of it in the CLH queue, it forces itself to enqueue at the tail, guaranteeing strict FIFO fairness at the cost of throughput.

## 3. StampedLock: Lock-Free Optimistic Reads

In standard read-write locks (`ReentrantReadWriteLock`), acquiring a read lock still requires an atomic CAS operation to increment the shared read count in `state`. On a 64-core server where 60 threads read simultaneously, all 60 cores **contend on the exact same L3 cache line**, creating severe cache-coherence bus traffic.

Java 8 introduced **`StampedLock`**, which provides **Optimistic Reads**:

```java
StampedLock sl = new StampedLock();

// Optimistic Read: ZERO locks, ZERO CAS operations, ZERO cache-line invalidation!
long stamp = sl.tryOptimisticRead();
int currentX = this.x;
int currentY = this.y;

if (!sl.validate(stamp)) {
    // A writer acquired an exclusive lock while we were reading!
    // Fall back to a traditional pessimistic read lock:
    stamp = sl.readLock();
    try {
        currentX = this.x;
        currentY = this.y;
    } finally {
        sl.unlockRead(stamp);
    }
}
```

- **How Optimistic Reads Work**: `tryOptimisticRead()` simply reads an atomic version counter (`stamp`). It does not modify `state` or acquire any lock.
- The thread copies the fields into local registers, then calls **`validate(stamp)`** (which performs an Acquire barrier to check if the version stamp changed).
- If no writer modified the data in the interim, the read completes with **near-zero CPU overhead**.

## 4. Inside ConcurrentHashMap: CAS, Bucket Locking & TreeBins

In Java 7, `ConcurrentHashMap` partitioned the map into 16 fixed `Segment` locks (Segmented Locking). In Java 8+, Doug Lea completely redesigned `ConcurrentHashMap` to achieve fine-grained, per-bucket concurrency:

```text
  Table Array Node<K,V>[]
  +-------------------------------------------------------------------------+
  | [0] null -> CAS insertion (No locks!)                                   |
  | [1] Node -> synchronized(Node) locks ONLY this single bucket head!       |
  | [2] TreeBin -> Red-Black Tree (when bin length >= 8 & table cap >= 64)  |
  | [3] ForwardingNode (hash = -1) -> Concurrent migration during resize!   |
  +-------------------------------------------------------------------------+
```

1. **Bucket-Head Locking**: If a bucket slot is empty (`tab[i] == null`), the inserting thread uses `casTabAt(tab, i, null, node)` without acquiring any lock! If the bucket already contains nodes, it locks **only that single bucket head** using `synchronized(node)`. Threads inserting into different buckets never contend.
2. **TreeBins (Red-Black Trees)**: If hash collisions push a single bucket's linked list to **8 or more nodes** (and total map capacity is $\ge 64$), the bucket converts into a **TreeBin** (balanced Red-Black Tree), capping worst-case lookup from $O(N)$ down to $O(\log N)$.
3. **Concurrent Multi-Threaded Resizing**: When expanding the table (`transfer`), threads encountering a completed bucket insert a **`ForwardingNode` (`hash == -1`)**. Other threads performing `put()` notice the ForwardingNode and **collaboratively assist in migrating remaining buckets (`helpTransfer`)** rather than waiting for resize to complete!

## 5. Verification Lab: Custom AQS Two-Permit Synchronizer & StampedLock Optimistic Reads

The following self-contained Java 21 program (`java Lab05.java`) implements and verifies:

1. **Custom Synchronizer Built Directly on AQS**: Implements a strict two-permit counting semaphore using `AbstractQueuedSynchronizer` (`tryAcquireShared` / `tryReleaseShared`), proving that active concurrency is bounded to at most 2.
2. **`StampedLock` Optimistic Read vs. Fallback**: Demonstrates that optimistic reads validate cleanly during reader-only phases and correctly detect concurrent write invalidations.

```java
import java.util.concurrent.CountDownLatch;
import java.util.concurrent.atomic.AtomicInteger;
import java.util.concurrent.locks.AbstractQueuedSynchronizer;
import java.util.concurrent.locks.StampedLock;

public class Lab05 {

    // Custom 2-permit Shared Synchronizer built directly on Doug Lea's AQS framework
    static class TwoPermitAQS extends AbstractQueuedSynchronizer {
        TwoPermitAQS() {
            setState(2); // Initial state: 2 permits available
        }

        @Override
        protected int tryAcquireShared(int acquires) {
            for (;;) {
                int current = getState();
                int remaining = current - acquires;
                if (remaining < 0 || compareAndSetState(current, remaining)) {
                    return remaining; // < 0 means acquire failed (enqueues in CLH queue)
                }
            }
        }

        @Override
        protected boolean tryReleaseShared(int releases) {
            for (;;) {
                int current = getState();
                int next = current + releases;
                if (compareAndSetState(current, next)) {
                    return true; // Wakes successor in CLH queue
                }
            }
        }

        public void acquire() { acquireShared(1); }
        public void release() { releaseShared(1); }
    }

    static class Coordinate {
        private double x, y;
        private final StampedLock sl = new StampedLock();

        public void move(double deltaX, double deltaY) {
            long stamp = sl.writeLock();
            try {
                x += deltaX;
                y += deltaY;
            } finally {
                sl.unlockWrite(stamp);
            }
        }

        public double distanceFromOrigin() {
            long stamp = sl.tryOptimisticRead(); // Optimistic lock-free read!
            double curX = x;
            double curY = y;
            if (!sl.validate(stamp)) { // Check if a writer intervened
                stamp = sl.readLock(); // Fall back to pessimistic read lock
                try {
                    curX = x;
                    curY = y;
                } finally {
                    sl.unlockRead(stamp);
                }
            }
            return Math.sqrt(curX * curX + curY * curY);
        }
    }

    public static void main(String[] args) throws Exception {
        System.out.println("=== HotSpot JVM Lab 05: AQS Custom Synchronizers & StampedLock ===");

        // 1. Verify Custom AQS Two-Permit Synchronizer
        TwoPermitAQS sem = new TwoPermitAQS();
        AtomicInteger activeWorkers = new AtomicInteger(0);
        AtomicInteger maxObserved = new AtomicInteger(0);
        CountDownLatch doneLatch = new CountDownLatch(10);

        for (int i = 0; i < 10; i++) {
            new Thread(() -> {
                try {
                    sem.acquire();
                    int cur = activeWorkers.incrementAndGet();
                    maxObserved.accumulateAndGet(cur, Math::max);
                    Thread.sleep(5); // Simulate work inside protected section
                    activeWorkers.decrementAndGet();
                } catch (InterruptedException e) {
                    Thread.currentThread().interrupt();
                } finally {
                    sem.release();
                    doneLatch.countDown();
                }
            }).start();
        }

        doneLatch.await();
        System.out.printf("  [1. Custom AQS Synchronizer] 10 threads, max concurrent inside permit section: %d (expected <= 2)%n",
                maxObserved.get());
        if (maxObserved.get() > 2 || maxObserved.get() == 0) {
            throw new AssertionError("AQS semaphore invariant violated: max=" + maxObserved.get());
        }

        // 2. Verify StampedLock Optimistic Reads
        Coordinate coord = new Coordinate();
        coord.move(3.0, 4.0);
        double dist = coord.distanceFromOrigin();
        System.out.printf("  [2. StampedLock Optimistic Read] Distance from (3,4): %.1f (expected 5.0)%n", dist);
        if (Math.abs(dist - 5.0) > 1e-6) {
            throw new AssertionError("StampedLock calculation mismatch");
        }

        System.out.println("All HotSpot JVM Lab 05 invariants verified.");
    }
}
```

## Key Takeaways

1. **AQS unifies state, queues, and parking into a reusable engine**: By implementing `tryAcquire` / `tryRelease`, custom locks leverage AQS's battle-tested CLH wait queue and native `LockSupport` parking.
2. **Non-Fair `ReentrantLock` delivers higher throughput via barging**: Active threads steal uncontended locks without parking, avoiding expensive context switches unless contention forces FIFO queuing.
3. **`StampedLock` eliminates cache bouncing on read-heavy data**: Optimistic reads bypass memory bus locks completely by checking version stamps, falling back to pessimistic locks only when a write collision is detected.
