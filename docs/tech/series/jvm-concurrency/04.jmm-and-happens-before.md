A common misconception among developers learning multi-threading is visualizing the **Java Memory Model (JMM)** as a literal physical diagram: "every thread has its own private CPU cache box, and there is one shared Main Memory box in the middle."

In reality, the JMM is **not hardware architecture**—it is a **formal specification** ([JLS Chapter 17: Threads and Locks](https://docs.oracle.com/javase/specs/jls/se25/html/jls-17.html)) defining the legal constraints under which a compiler, JIT optimizer, and out-of-order CPU pipeline may reorder memory reads and writes.

This chapter strips away the myths, analyzes the four CPU memory barriers emitted by HotSpot, explores how `volatile` enforces memory visibility, explains why `final` fields are immune to data races, and demonstrates modern **`VarHandle`** Acquire/Release synchronization.

---

## Before you start

Consider two threads sharing `boolean done` and `int result`. One sets `result = 42; done = true;`. The other loops until `done` is true, then reads `result`. It seems the reader must see 42. In Java it might not. Compilers reorder statements, CPUs buffer writes, and each core has its own cache, so one thread can see another's writes late or in a different order.

The Java Memory Model is the contract that says when a write is guaranteed to be visible to a read. Its core rule is happens-before: if action A happens-before action B, B sees A's effects. Declaring `done` as `volatile`, taking a lock, or starting a thread each create such an edge. The chapter shows the rules and the hardware fences the JVM emits to enforce them.

Read [JVM 03](/tech/series/jvm-concurrency/03.garbage-collectors-g1-to-zgc/) first for barriers as the JVM uses them. Go has a similar contract: see [Go Runtime 04](/tech/series/go-runtime/04.channels-select-and-happens-before/).

Terms used in this chapter:

- **visibility**: whether one thread can see a value another thread wrote.
- **reordering**: the compiler or CPU executing operations in a different order than the source shows.
- **happens-before**: a guarantee that one action's effects are visible to a later one.
- **volatile**: a field modifier that makes reads and writes ordered and visible across threads.
- **memory barrier**: an instruction that stops certain reads and writes from being reordered across it.
- **final field**: a field set once in a constructor, safely visible to other threads after construction without locking.
- **VarHandle**: a Java API for atomic and ordered access to fields, with selectable strength.

## 1. The Happens-Before ($\prec_{\text{hb}}$) Relationship

In a single-threaded program, the compiler and CPU may reorder instructions arbitrarily as long as the transformation preserves single-threaded program order (**as-if-serial semantics**).

In a multi-threaded program, however, two threads reading and writing shared variables without synchronization enter a **Data Race**:
$$\text{Data Race} = \text{Two accesses to the same memory location, at least one write, without synchronization}$$

To restore deterministic reasoning, the JMM defines the **Happens-Before ($\prec_{\text{hb}}$)** partial order. If action $A \prec_{\text{hb}} B$, then the runtime guarantees that all memory writes executed by $A$ are visible to, and ordered before, action $B$.

### Key Happens-Before Edges in Java

| Synchronization Action | Happens-Before Rule |
| :--- | :--- |
| **Program Order Rule** | Each action in a thread happens-before every subsequent action in that thread according to program order. |
| **Monitor Lock Rule** | An unlock on an intrinsic monitor (`monitorexit` / `synchronized`) happens-before every subsequent lock on that exact same monitor. |
| **Volatile Variable Rule** | A write to a `volatile` field happens-before every subsequent read of that exact same `volatile` field. |
| **Thread Start Rule** | A call to `Thread.start()` happens-before any action in the started thread. |
| **Thread Termination Rule** | Any action in a thread happens-before any other thread successfully returns from `Thread.join()` on that thread. |
| **Transitivity Rule** | If $A \prec_{\text{hb}} B$ and $B \prec_{\text{hb}} C$, then $A \prec_{\text{hb}} C$. |

## 2. Hardware Memory Barriers: LoadLoad, LoadStore, StoreStore & StoreLoad

Modern CPUs (such as x86-64 and ARM64) use **Store Buffers** and out-of-order execution pipelines to hide memory latency:

- When a CPU core writes to a variable, it immediately writes the value to its local Store Buffer and continues executing the next instruction without waiting for the L1/L2 cache or DRAM to respond.
- On **x86-64 (TSO: Total Store Order)**, loads are not reordered with earlier loads, stores are not reordered with earlier stores, and stores are not reordered with earlier loads. The **only hardware reordering permitted on x86 is: Store followed by Load to a different address (`StoreLoad` reordering)!**
- On **ARM64 / POWER (Weakly Ordered)**, almost all combinations of loads and stores can be reordered by hardware.

To enforce JMM semantics uniformly across architectures, HotSpot models four conceptual memory barriers:

```text
  1. LoadLoad   : Guarantees earlier reads complete before later reads.
  2. LoadStore  : Guarantees earlier reads complete before later writes.
  3. StoreStore : Guarantees earlier writes flush to cache before later writes.
  4. StoreLoad  : The heaviest barrier! Drains the entire CPU store buffer to cache
                  before allowing any subsequent read to proceed.
```

### HotSpot volatile Read/Write Barrier Emission

When HotSpot compiles a `volatile` read or write on x86-64, it inserts the following barrier sequence:

```text
  Volatile Write:
    [StoreStore]             ; Flushes prior plain writes to store buffer (no-op on x86)
    mov [field], val         ; Write the volatile field value
    [StoreLoad]              ; Emits: lock addl [rsp], 0 (or mfence) to drain store buffer!

  Volatile Read:
    mov val, [field]         ; Read volatile field from cache
    [LoadLoad | LoadStore]   ; Prevents later reads/writes from reordering above (no-op on x86)
```

Notice that on x86-64, a volatile read costs **0 extra instructions** (standard `mov` already has Acquire semantics in TSO hardware)! The primary performance cost of `volatile` on x86 is the **`StoreLoad` barrier emitted on volatile writes** (`lock addl`), which stalls the CPU pipeline until the store buffer drains.

## 3. Final Fields: Freezing State without Locks (JLS §17.5)

Why are immutable objects (`String`, `Integer`, `record`) safe to share across threads without a `volatile` modifier or mutex?

Under the JMM, `final` fields are governed by **Final Field Freeze Semantics**:

1. When a constructor initializes a `final` field (`this.x = 42`), the compiler emits a **`StoreStore` barrier** at the end of the constructor before returning the object reference.
2. Any thread that obtains a reference to that object after the constructor completes is **guaranteed to see the fully initialized value of all `final` fields**, even if the object reference was published across threads without synchronization!

> **The Escaping `this` Anti-Pattern**:
> Final-field freeze semantics only apply if the object reference does **not escape during construction**! If your constructor registers `this` into an event listener, launches a new thread (`new Thread(this).start()`), or assigns `this` to a static field before the constructor returns, other threads can observe uninitialized `final` fields!

## 4. Modern Memory Access Modes: `VarHandle` (JDK 9+)

Before Java 9, developers seeking fine-grained memory barriers had to reach for the dangerous, unsupported `sun.misc.Unsafe` internal API.

Java 9 introduced **`java.lang.invoke.VarHandle`**, providing strongly typed, JVM-intrinsic access modes modeled directly after the C++11 memory model:

| Access Mode | Methods on `VarHandle` | Memory Barrier Semantics | Performance |
| :--- | :--- | :--- | :--- |
| **Plain** | `get`, `set` | Standard reads and writes; JIT and CPU may reorder freely. | Fastest |
| **Opaque** | `getOpaque`, `setOpaque` | Coherence: no word-tearing (64-bit atomic), program-order preserved for that single field, but no cross-variable synchronization. | Fast |
| **Acquire / Release** | `getAcquire`, `setRelease` | **One-way barrier**: `setRelease` flushes prior writes; `getAcquire` sees all prior writes. Does not emit expensive full `StoreLoad` barriers! | Very Fast |
| **Volatile** | `getVolatile`, `setVolatile` | Full two-way barrier (`StoreLoad` on writes); identical to `volatile` field. | Slower on writes |

Using `VarHandle.setRelease` on a producer and `VarHandle.getAcquire` on a consumer gives you a correct happens-before publication edge while saving the expensive `StoreLoad` bus-lock instruction required by `volatile`!

## 5. Verification Lab: Proving `VarHandle` Acquire/Release Happens-Before in Java 21

The following self-contained Java 21 program (`java Lab04.java`) demonstrates and verifies:

1. **`VarHandle` Lookup & Reflection Linkage**: Looks up a `VarHandle` for an instance variable using `MethodHandles.lookup()`.
2. **Safe Publication via Acquire/Release**: Spawns a producer thread writing data and publishing a flag via `vhFlag.setRelease()`, and a consumer thread reading via `vhFlag.getAcquire()`, proving that all non-volatile payload data is visible to the consumer. Note that x86 hardware rarely exposes a missing barrier, so a pass here confirms the pattern is correct but would not catch a broken one.

```java
import java.lang.invoke.MethodHandles;
import java.lang.invoke.VarHandle;
import java.util.concurrent.atomic.AtomicInteger;

public class Lab04 {

    static class DataPacket {
        // Plain fields (NOT marked volatile!)
        int payload1 = 0;
        int payload2 = 0;
        String message = null;

        // Synchronization flag controlled via VarHandle
        int ready = 0;

        private static final VarHandle VH_READY;

        static {
            try {
                VH_READY = MethodHandles.lookup()
                        .findVarHandle(DataPacket.class, "ready", int.class);
            } catch (ReflectiveOperationException e) {
                throw new ExceptionInInitializerError(e);
            }
        }

        public void publish(int p1, int p2, String msg) {
            this.payload1 = p1;
            this.payload2 = p2;
            this.message = msg;
            // setRelease: StoreStore barrier ensures prior payload writes flush before ready = 1!
            VH_READY.setRelease(this, 1);
        }

        public boolean tryConsume(int[] out) {
            // getAcquire: LoadLoad & LoadStore barrier ensures subsequent payload reads see latest values!
            if ((int) VH_READY.getAcquire(this) == 1) {
                out[0] = this.payload1;
                out[1] = this.payload2;
                return true;
            }
            return false;
        }
    }

    public static void main(String[] args) throws Exception {
        System.out.println("=== HotSpot JVM Lab 04: Java Memory Model & VarHandles ===");

        final AtomicInteger successCount = new AtomicInteger(0);

        for (int i = 0; i < 5; i++) {
            DataPacket packet = new DataPacket();
            int[] consumed = new int[2];

            Thread producer = new Thread(() -> {
                packet.publish(42, 84, "Hello from Producer");
            });

            Thread consumer = new Thread(() -> {
                // No latch or join between the threads: only the acquire read orders the payload
                while (!packet.tryConsume(consumed)) {
                    Thread.onSpinWait(); // CPU PAUSE instruction hint
                }
                if (consumed[0] == 42 && consumed[1] == 84 && "Hello from Producer".equals(packet.message)) {
                    successCount.incrementAndGet();
                }
            });

            consumer.start();
            producer.start();
            producer.join();
            consumer.join();
        }

        System.out.printf("  [1. VarHandle Acquire/Release Verification] Successful cross-thread publications: %d / 5%n",
                successCount.get());
        if (successCount.get() != 5) {
            throw new AssertionError("VarHandle Acquire/Release failed to establish happens-before edge!");
        }

        System.out.println("All HotSpot JVM Lab 04 invariants verified.");
    }
}
```

## Key Takeaways

1. **JMM is a contract, not a hardware diagram**: The specification dictates permissible reorderings; hardware CPU store buffers and caches are implementation details that compilers bridge using memory barriers.
2. **Volatile writes are expensive on x86, reads are cheap**: A volatile write emits a hardware `StoreLoad` (`lock addl`) barrier to drain the store buffer, while a volatile read on x86 is a standard machine `mov`.
3. **Consider `VarHandle` Acquire/Release where `volatile` writes show up in a profile**: One-way Acquire/Release semantics establish safe publication happens-before ordering without the heavy two-way `StoreLoad` bus stall.
