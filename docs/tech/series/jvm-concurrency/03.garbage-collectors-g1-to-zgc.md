Garbage collection in modern Java has evolved through three generational eras:

1. **The Monolithic Era (`ParallelGC`, `CMS`)**: The heap was split into two physically fixed, contiguous memory slabs: a Young Generation and an Old Generation. A full GC was a stop-the-world catastrophe that locked gigabytes of memory for seconds.
2. **The Region-Based Incremental Era (`G1 GC`)**: HotSpot partitioned the heap into **2,048 dynamic regions** (1 MiB to 32 MiB each), introducing **Card Tables** and **Remembered Sets (RSets)** to collect young and high-garbage regions incrementally within a user-configured pause target (`-XX:MaxGCPauseMillis=200`).
3. **The Concurrent Sub-Millisecond Era (`ZGC` and Generational ZGC, JDK 21+)**: By encoding object liveness metadata directly into unused 64-bit virtual memory address bits (**Colored Pointers**) and intercepting pointer reads via **Load Barriers**, Generational ZGC executes marking, relocation, and reference updating concurrently—keeping Stop-The-World pauses **under 1 millisecond** even on a 16-terabyte heap!

## Before you start

Java frees memory automatically, and the cost shows up as pauses: moments when the collector stops your threads to work. For a web service, a 500 ms pause is a latency spike for everyone in flight. Different collectors make different bargains. G1, the default, splits the heap into many regions and collects the ones with the most garbage first, aiming for short pauses. ZGC does nearly all its work while your threads run, so pauses stay very short even on huge heaps.

The difficulty is that collecting part of the heap means knowing which other parts point into it, without scanning everything. The chapter explains the bookkeeping for that, and how ZGC hides collector metadata in pointer bits.

Read [JVM 02](/tech/series/jvm-concurrency/02.jit-compilation-and-escape-analysis/) first, since the JIT emits the extra code described here. For the general ideas, see [Bytecode VMs 06](/tech/series/bytecode-vms/06.garbage-collection-and-memory-management/).

Terms used in this chapter:

- **pause**: a period when application threads are stopped so the collector can work.
- **region**: one of many equal-sized slices of the heap that G1 collects independently.
- **humongous object**: an object at least half a region in size, which G1 allocates specially.
- **collection set**: the regions chosen for evacuation in one collection.
- **card table**: a byte array marking which small areas of memory had a pointer written into them.
- **remembered set**: per-region record of which other regions hold pointers into it.
- **write barrier**: code run on pointer writes so the collector learns about them.
- **colored pointer**: a ZGC pointer whose spare bits record collection state.
- **load barrier**: code run when a pointer is read, which lets ZGC fix stale pointers on the fly.

## 1. G1 GC: Heap Regions, Humongous Objects & Collection Sets (CSet)

Defaulting as Java's primary collector since Java 9, the **Garbage-First (G1) Collector** replaces static memory boundaries with a grid of approximately **2,048 equal-sized regions** ($2048 \times \text{RegionSize} \approx \text{HeapSize}$):

```text
  +------+------+------+------+------+------+------+------+
  | E    | E    | S    | O    | O    | H    | H-c  | Free |  E = Eden
  +------+------+------+------+------+------+------+------+  S = Survivor
  | O    | E    | E    | S    | Free | O    | O    | Free |  O = Old Generation
  +------+------+------+------+------+------+------+------+  H = Humongous Start
  | Free | Free | E    | O    | Free | Free | E    | Free |  H-c = Humongous Cont.
  +------+------+------+------+------+------+------+------+
```

- **Dynamic Roles**: A region is not permanently Eden or Old. A free region can be assigned to Eden, filled with allocations, evacuated into a Survivor or Old region, and recycled back into the global free list.
- **Humongous Objects**: Any single object whose size exceeds **50% of a region's capacity** (`size > RegionSize / 2`) is classified as **Humongous**. Humongous objects bypass normal Eden TLAB allocation; they are allocated directly into a contiguous run of Old regions, which can lead to premature heap fragmentation if large byte arrays are allocated frequently.
- **Garbage-First CSet Selection**: During a **Mixed GC**, G1 ranks all Old regions by their measured "garbage density" (regions containing the highest percentage of dead objects) and selects a **Collection Set (CSet)** of Eden, Survivor, and top-density Old regions that can be evacuated within your target pause time (`-XX:MaxGCPauseMillis`).

## 2. The Cross-Region Reference Problem: Card Tables & Remembered Sets

Suppose G1 wants to collect only the Eden and Survivor regions during a **Young GC**.

- What if an active object in an **Old Gen region** holds a reference to a live object inside an **Eden region**?
- If G1 had to scan every object in all 1,500 Old Gen regions just to find pointers pointing into Eden, Young GC would take hundreds of milliseconds and destroy the pause time target!

G1 solves this using **Card Tables** and **Remembered Sets (RSets)**:

### 1. The Byte Card Table

HotSpot allocates a contiguous array called the **Card Table** where **1 byte represents 512 bytes of physical heap memory**:
$$\text{CardIndex} = \text{HeapAddress} \gg 9$$

### 2. The JIT Post-Write Barrier

Whenever a Java mutator thread executes an object reference write (`objA.field = objB`), the compiler emits a post-write barrier. This is the simplified card-marking core; the real G1 barrier first filters same-region and null stores and skips cards that are already dirty:

```assembly
shr rbx, 9                     ; Convert slot address to Card Table index
mov [r10 + rbx], 0x01          ; Mark the card byte as DIRTY (0x01)
```

### 3. Concurrent Refinement Threads (`G1ConcurrentRefineThread`)

1. When a thread dirties a card, it appends the card index to a thread-local **Dirty Card Queue (DCQ)**.
2. When the DCQ fills, it flushes to a shared global buffer.
3. Background **`G1ConcurrentRefineThread`** daemons pop dirty cards, parse the 512-byte memory slice for references crossing region boundaries, and if Old Region `A` points to Young Region `B`, **insert Region `A`'s card index into Region `B`'s Remembered Set (RSet)**!
4. During a Young GC, G1 scans only the **roots + Region `B`'s RSet**—instantly locating every cross-region inbound pointer without inspecting the rest of the Old Generation!

## 3. Generational ZGC (JDK 21+): Colored Pointers & Self-Healing Load Barriers

While G1 pauses mutators during the evacuation phase (copying objects out of the CSet to defragment memory), **ZGC (Generational ZGC arrived in JDK 21 via JEP 439, became the default mode in JDK 23, and the single-generation mode was removed in JDK 24)** performs **concurrent evacuation**: user application threads continue reading and writing to objects *while those exact objects are being moved to new memory locations*!

How is this physically possible without data corruption or reading stale memory?

### 1. 64-Bit Colored Pointers (Reference Metadata in Virtual Address Bits)

> The layout below is the classic single-generation ZGC design, which is the easiest to read. Generational ZGC keeps the colored-pointer idea but moves the color bits to the low end of the pointer, drops the multi-mapping trick, and adds store barriers to maintain its remembered sets. Treat the exact bit positions as illustrative.

ZGC does not store GC state in object headers (`markWord`). Instead, it stores GC metadata in the **upper bits of the 64-bit reference pointer itself**:

```text
  63      48 47          44 43                                             0
  +---------+--------------+-----------------------------------------------+
  | Unused  | Metadata     | Physical Virtual Address Offset (up to 16 TB) |
  | 16 bits | 4 bits:      |                                               |
  |         | Finalizable  |                                               |
  |         | Remapped     |                                               |
  |         | Marked0      |                                               |
  |         | Marked1      |                                               |
  +---------+--------------+-----------------------------------------------+
```

Using Linux virtual-memory page aliasing (`mmap` with three different virtual address ranges mapping to the exact same physical memory pages), reading a pointer with `Marked0`, `Marked1`, or `Remapped` set resolves to the identical physical heap address.

### 2. The Self-Healing Load Barrier

ZGC relies mainly on an ultra-fast **JIT Load Barrier** (Generational ZGC adds store barriers for its remembered sets) emitted whenever a thread reads a reference from the heap:

```java
// Java code:
Object o = customer.order;

// What JIT compiles with ZGC Load Barrier:
mov rax, [customer + offset]   // Read reference pointer
test rax, [AddressBadMask]      // Check if Colored Pointer bits match current GC phase!
jnz zgc_load_barrier_slow_path  // Fast path: matches! (1 CPU cycle). Slow path only if uncolored!
```

### The Slow Path: Self-Healing in Action

1. If the pointer has not yet been relocated (`test AddressBadMask` fails), the thread jumps to `zgc_load_barrier_slow_path`.
2. The thread checks the region's **Forwarding Table**:
   - If the object was already evacuated to a new location `new_addr`, the thread reads `new_addr`.
   - If the object has not yet been copied, the thread copies it to `new_addr` right now and updates the Forwarding Table atomically!
3. **Self-Healing**: The thread updates the field on the heap (`customer.order = new_addr_colored`) before returning `new_addr`.
4. The very next read on `customer.order` hits the fast path with zero overhead.

Because all relocation and reference updates happen concurrently with mutators via self-healing load barriers, **ZGC Stop-The-World pauses drop to sub-millisecond durations ($\le 1\text{ ms}$)** regardless of whether the heap is 100 GiB or 16 TiB!

## 4. Verification Lab: GC Telemetry, Region Metrics & Heap Allocation Inspection

The following self-contained Java 21 program (`java Lab03.java`) monitors the active garbage collector and verifies generational telemetry:

1. **GC MXBean Telemetry**: Detects whether the active collector is G1, ZGC, or Parallel, and queries cumulative collection counts and pause durations.
2. **Generational Allocation & GC Notification**: Registers a `NotificationListener` on `GarbageCollectorMXBean` to capture exact GC start/end timestamps, memory pool usage before/after collection during an allocation loop.

```java
import com.sun.management.GarbageCollectionNotificationInfo;
import java.lang.management.GarbageCollectorMXBean;
import java.lang.management.ManagementFactory;
import java.lang.management.MemoryPoolMXBean;
import java.lang.management.MemoryUsage;
import java.util.ArrayList;
import java.util.List;
import java.util.Map;
import java.util.concurrent.atomic.AtomicInteger;
import javax.management.NotificationEmitter;
import javax.management.openmbean.CompositeData;

public class Lab03 {

    public static void main(String[] args) throws Exception {
        System.out.println("=== HotSpot JVM Lab 03: Garbage Collectors (G1 to Generational ZGC) ===");

        // 1. Inspect Active Garbage Collectors
        List<GarbageCollectorMXBean> gcBeans = ManagementFactory.getGarbageCollectorMXBeans();
        System.out.printf("  [1. Active Collectors] Registered GC MXBeans (%d):%n", gcBeans.size());
        for (GarbageCollectorMXBean gc : gcBeans) {
            System.out.printf("      - Name: %-25s | Collections: %d | Total Pause Time: %d ms%n",
                    gc.getName(), gc.getCollectionCount(), gc.getCollectionTime());
        }

        // 2. Attach JMX GC Notification Listener
        AtomicInteger notificationCount = new AtomicInteger(0);
        for (GarbageCollectorMXBean gcBean : gcBeans) {
            if (gcBean instanceof NotificationEmitter emitter) {
                emitter.addNotificationListener((notification, handback) -> {
                    if (notification.getType().equals(GarbageCollectionNotificationInfo.GARBAGE_COLLECTION_NOTIFICATION)) {
                        CompositeData cd = (CompositeData) notification.getUserData();
                        GarbageCollectionNotificationInfo info = GarbageCollectionNotificationInfo.from(cd);
                        notificationCount.incrementAndGet();
                        long durationMs = info.getGcInfo().getDuration();
                        String action = info.getGcAction();
                        String cause = info.getGcCause();
                        System.out.printf("  [GC Event #%d] %s (%s) caused by [%s] in %d ms%n",
                                notificationCount.get(), info.getGcName(), action, cause, durationMs);
                    }
                }, null, null);
            }
        }

        // 3. Trigger Allocation Pressure & Explicit GC
        List<byte[]> memoryPressure = new ArrayList<>();
        for (int i = 0; i < 50; i++) {
            memoryPressure.add(new byte[1024 * 1024]); // Allocate 50 MiB in 1 MiB chunks
        }
        System.out.printf("  [2. Memory Pressure] Allocated %d MiB of byte arrays.%n", memoryPressure.size());
        memoryPressure.clear(); // Make them eligible for collection

        System.gc(); // Request GC cycle to exercise MXBean listener
        Thread.sleep(100); // Allow async JMX notification to fire

        // 4. Memory Pool Usage Post-GC
        System.out.println("  [3. Memory Pools Post-Collection]:");
        for (MemoryPoolMXBean pool : ManagementFactory.getMemoryPoolMXBeans()) {
            MemoryUsage usage = pool.getUsage();
            if (usage.getMax() > 0) {
                System.out.printf("      - %-25s : Used: %6.1f MiB / Max: %6.1f MiB%n",
                        pool.getName(), usage.getUsed() / (1024.0 * 1024.0), usage.getMax() / (1024.0 * 1024.0));
            }
        }

        System.out.println("All HotSpot JVM Lab 03 invariants verified.");
    }
}
```

## Key Takeaways

1. **G1 bounds latency with region-based partial evacuation**: Dividing the heap into 2,048 regions lets G1 prioritize high-garbage areas for collection within `-XX:MaxGCPauseMillis`.
2. **Remembered Sets decouple Young GC from Old Gen scanning**: The JIT post-write barrier dirties 512-byte cards in the Card Table, which background refine threads compile into target region RSets so Young GC never traverses old generation heaps.
3. **Generational ZGC achieves sub-millisecond pauses via Colored Pointers**: Encoding metadata into virtual address bits paired with self-healing load barriers allows ZGC to relocate objects concurrently with mutator execution.
