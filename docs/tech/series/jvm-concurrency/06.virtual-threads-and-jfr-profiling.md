For nearly thirty years, `java.lang.Thread` was a **1:1 wrapper around an operating system thread** (`pthread_create` on Linux). Because each OS thread reserves a dedicated 1 MiB virtual stack and requires kernel context switches, an enterprise Java application could rarely sustain more than 5,000 to 10,000 active threads before running out of memory or exhausting the Linux thread table.

To achieve high concurrency, developers were forced into reactive frameworks (`Project Reactor`, `RxJava`, `Netty`), rewriting imperative code into callback chains and losing sequential stack traces and debuggability.

**JDK 21 Project Loom (JEP 444: Virtual Threads)** fundamentally changes this paradigm: restoring the straightforward "one thread per request" imperative programming model while scaling to **millions of concurrent tasks** on a single JVM.

This concluding chapter dissects how Virtual Threads mount and unmount onto carrier threads via **Continuations**, explains the **Thread Pinning** problem and how JDK 24 changed it, and outlines a production diagnostic workflow using **Java Flight Recorder (JFR)** and **Async-Profiler**.

---

## Before you start

A classic Java server gives each request a thread, and an OS thread costs on the order of a megabyte of stack and a context switch each time it blocks. A few thousand is a practical ceiling, which is why people moved to callback and reactive code. Virtual threads, final in Java 21, bring back the simple one-thread-per-request style. They are cheap Java-managed threads scheduled onto a small pool of real threads. When one blocks on I/O, it steps off its carrier thread and another virtual thread takes over.

The catch is pinning: in some situations, notably blocking inside a `synchronized` block on the JDK versions covered here, the virtual thread cannot step off and holds its carrier. The chapter explains that, structured concurrency, and how to find problems with JFR, the JVM's built-in profiler.

Read [JVM 05](/tech/series/jvm-concurrency/05.aqs-locks-and-concurrent-collections/) first for locks and parking. For the Go equivalent, see [Go Runtime 01](/tech/series/go-runtime/01.gmp-scheduler-and-preemption/).

Terms used in this chapter:

- **platform thread**: a traditional Java thread backed one-to-one by an OS thread.
- **virtual thread**: a lightweight thread managed by the JVM rather than the OS.
- **carrier thread**: the platform thread a virtual thread currently runs on.
- **continuation**: a saved execution state that lets a virtual thread be paused and resumed.
- **pinning**: a virtual thread being unable to unmount from its carrier while blocked.
- **structured concurrency**: tying the lifetime of child tasks to the scope that started them.
- **JFR**: Java Flight Recorder, a low-overhead event recorder built into the JVM.
- **safepoint bias**: profiler error from sampling threads only at safepoints rather than anywhere.

## 1. Platform Threads vs. Virtual Threads: The $M:N$ Architecture

| Dimension | Platform Thread (`Thread.ofPlatform()`) | Virtual Thread (`Thread.ofVirtual()`) |
| :--- | :--- | :--- |
| **Mapping** | **1:1** with an OS Kernel Thread (`pthread`) | **$M:N$** user-space task managed by HotSpot |
| **Stack Memory** | Fixed **1 MiB** OS virtual guard allocation | **Few hundred bytes** initial heap allocation; grows dynamically |
| **Creation Cost** | Slow (calls kernel `clone(2)`) | Fast (allocates a lightweight Java heap object) |
| **Max per Process** | Typically $\sim 5,000\text{--}10,000$ | **Millions** |
| **Blocking Cost** | Blocks the underlying OS kernel thread | **Unmounts** from carrier thread; OS thread runs other tasks! |

```text
  Virtual Threads (Millions of user tasks in heap)
  [ VThread 1 ]   [ VThread 2 ]   [ VThread 3 ]   [ VThread 4 ] ... [ VThread N ]
         \              |               /
          \             |              /  Mounted via jdk.internal.vm.Continuation
           v            v             v
  Carrier Threads (ForkJoinPool worker threads, sized to CPU core count)
  [ Carrier M1 ]   [ Carrier M2 ]   [ Carrier M3 ]   [ Carrier M4 ]
         |                |                |                |
  [ OS Thread 1 ]  [ OS Thread 2 ]  [ OS Thread 3 ]  [ OS Thread 4 ] (Linux Kernel)
```

### How Continuations Mount and Unmount

At the core of Project Loom sits **`jdk.internal.vm.Continuation`**:

1. When a Virtual Thread runs, HotSpot **mounts** its call stack onto an underlying **Carrier Thread** (a standard `ForkJoinPool` worker thread).
2. When the Virtual Thread executes a blocking operation—such as reading from a non-ready network socket (`java.net.Socket`), reading a channel, or calling `LockSupport.park()`:
   - HotSpot captures the Virtual Thread's stack frames from the carrier thread and copies them into a **Continuation chunk on the Java heap**.
   - The Virtual Thread **unmounts** from the carrier thread!
   - The carrier thread is now immediately free to pick up and execute another ready Virtual Thread.
3. Later, when the OS socket receives network data (notified via `epoll` on Linux inside the JDK's network poller), the poller re-enqueues the Virtual Thread into the `ForkJoinPool`, which mounts the continuation back onto any available carrier thread and resumes execution!

## 2. Thread Pinning: Why `synchronized` Stalled Loom (JDK 21-23)

Some operations keep a Virtual Thread from unmounting: **Thread Pinning**. The `synchronized` case below applies to JDK 21 through 23. JDK 24 (JEP 491) reimplemented monitors so a virtual thread blocked inside `synchronized` or `Object.wait()` unmounts like any other, and on JDK 25 (the LTS used in late 2026) the main remaining pin is a native or FFM frame on the stack. The advice here still matters if you run JDK 21.

When a Virtual Thread becomes pinned, its underlying carrier thread **blocks in the kernel along with the virtual thread**, defeating the entire purpose of Loom and exhausting the carrier `ForkJoinPool`!

### What Causes Pinning?

1. **Blocking inside a `synchronized` block or method (JDK 21-23)**: the monitor is owned by the carrier thread rather than the virtual thread, so the continuation cannot be unmounted while it holds one.
2. **Executing native JNI or Foreign Function & Memory (FFM) calls**: Native C/Rust code holds physical stack frames that cannot be migrated to the Java heap.

```java
// PINNED on JDK 21-23: blocks the carrier thread when calling blocking I/O inside synchronized!
synchronized (lock) {
    String response = httpClient.send(request, HttpResponse.BodyHandlers.ofString()).body();
}

// UNPINNED: ReentrantLock uses AQS (LockSupport.park()), which unmounts cleanly!
lock.lock();
try {
    String response = httpClient.send(request, HttpResponse.BodyHandlers.ofString()).body();
} finally {
    lock.unlock();
}
```

> **Production rule on JDK 21-23**: avoid blocking network I/O or sleep inside a `synchronized` block in a virtual-thread application, and use **`java.util.concurrent.locks.ReentrantLock`** around blocking calls instead. Detect pinning with `-Djdk.tracePinnedThreads=full` on those releases, or with the `jdk.VirtualThreadPinned` JFR event, which still exists on newer ones.

## 3. Structured Concurrency: Eliminating Thread Leaks

Historically, spawning asynchronous tasks with `ExecutorService.submit()` created decoupled lifecycles: if a parent task failed or timed out, child tasks continued running in the background as **orphaned threads**, wasting database connections and CPU cycles.

**Structured Concurrency (`StructuredTaskScope`)** brings structured programming principles to multi-threading: **subtasks are strictly bounded by the syntactic scope of their parent**:

```java
// Conceptual StructuredTaskScope (JDK 21 preview API, needs --enable-preview;
// the API was reshaped in later previews, so check the current JEP before copying):
try (var scope = new StructuredTaskScope.ShutdownOnFailure()) {
    Supplier<User> userSubtask = scope.fork(() -> fetchUser(id));
    Supplier<Order> orderSubtask = scope.fork(() -> fetchOrder(id));

    scope.join();           // Waits for both subtasks to finish...
    scope.throwIfFailed();  // ...and if either fails, cancels the other automatically!

    return new Dashboard(userSubtask.get(), orderSubtask.get());
} // Both threads are guaranteed closed and terminated here! Zero orphan leaks!
```

## 4. Production Profiling: JFR vs. Async-Profiler (Safepoint Bias)

When debugging performance regressions in production Java services, understanding your profiling tool's sampling mechanism is critical:

| Diagnostic Feature | Standard Thread Dumps (`jstack`) | Java Flight Recorder (JFR) | Async-Profiler |
| :--- | :--- | :--- | :--- |
| **Sampling Mechanism** | Requests global JVM Safepoint | Event-driven kernel + JVM timers | Linux `perf_events` + `AsyncGetCallTrace` |
| **Safepoint Bias?** | **High**: Only samples threads at safepoints! | Low | **Zero Safepoint Bias**: Samples anywhere in user, kernel, or JIT code! |
| **Overhead** | High pause duration | Low with default settings (designed for always-on use) | Low at typical sampling intervals |
| **Output** | Raw text thread dumps | `.jfr` event recordings (view in JMC) | Interactive SVG Flame Graphs |

### What Is Safepoint Bias?

Traditional profilers request a safepoint before sampling where threads are spending CPU time. If a thread is stuck in a counted loop, a JNI library call, or an inlined cryptographic function that contains no safepoints, the thread **cannot be sampled until it exits that loop**! Consequently, standard profilers attribute CPU spikes to the innocent instructions immediately *after* the hot loop, pointing developers toward the wrong bottleneck!

Prefer **Async-Profiler** (`./asprof -d 30 -f flamegraph.html <pid>`) for accurate CPU and wall-clock flame graphs in production.

## 5. Verification Lab: Spawning 10,000 Virtual Threads & Non-Blocking Scalability

The following self-contained Java 21 program (`java Lab06.java`) proves and verifies:

1. **Virtual Thread Scalability**: Launches **10,000 concurrent Virtual Threads** using `Executors.newVirtualThreadPerTaskExecutor()`, each simulating a 50 ms I/O latency.
2. **Carrier Thread Unmounting**: Measures total completion time and verifies that 10,000 concurrent tasks finish in a fraction of a second using only a handful of CPU carrier threads!

```java
import java.util.concurrent.CountDownLatch;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.atomic.AtomicInteger;

public class Lab06 {

    public static void main(String[] args) throws Exception {
        System.out.println("=== HotSpot JVM Lab 06: Virtual Threads (Project Loom) Scalability ===");

        final int TASK_COUNT = 10_000;
        final AtomicInteger completedCount = new AtomicInteger(0);
        final CountDownLatch latch = new CountDownLatch(TASK_COUNT);

        long startTime = System.currentTimeMillis();

        // Use Java 21 Virtual Thread Per Task Executor!
        try (ExecutorService executor = Executors.newVirtualThreadPerTaskExecutor()) {
            for (int i = 0; i < TASK_COUNT; i++) {
                executor.submit(() -> {
                    try {
                        // Simulates non-blocking network socket read or LockSupport.park().
                        // The virtual thread UNMOUNTS from its carrier thread during sleep!
                        Thread.sleep(50);
                        completedCount.incrementAndGet();
                    } catch (InterruptedException e) {
                        Thread.currentThread().interrupt();
                    } finally {
                        latch.countDown();
                    }
                });
            }

            latch.await();
        }

        long elapsedMs = System.currentTimeMillis() - startTime;
        System.out.printf("  [1. Virtual Thread Throughput] Spawned & completed %d virtual threads in %d ms!%n",
                completedCount.get(), elapsedMs);

        // 10,000 50ms tasks on standard OS platform threads would need 10,000 OS threads, or a bounded pool
        // that serializes the sleeps (200 threads => ~2.5 s). Virtual threads typically finish in a few hundred ms.
        if (completedCount.get() != TASK_COUNT) {
            throw new AssertionError("Task completion mismatch: " + completedCount.get());
        }

        System.out.println("All HotSpot JVM Lab 06 invariants verified.");
    }
}
```

## Key Takeaways

1. **Virtual Threads decouple concurrency from OS thread limits**: By capturing execution state into continuations on the Java heap, Virtual Threads scale to millions of concurrent tasks on a small pool of carrier threads.
2. **Know what pins a virtual thread on your JDK**: on JDK 21-23 a monitor held across a blocking call pins the carrier, so use `ReentrantLock` there; JDK 24+ lifts that, leaving native frames.
3. **Avoid Safepoint Bias with Async-Profiler**: Standard thread dumps sample only at safepoints; use `AsyncGetCallTrace` and Linux `perf_events` for true production CPU flame graphs.
