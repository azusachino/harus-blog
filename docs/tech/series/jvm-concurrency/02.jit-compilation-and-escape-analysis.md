When a Java application boots, it starts by executing raw bytecode inside the **Template Interpreter**. Yet within seconds of sustained load, the application matches the throughput of compiled C++ or Rust.

How does the Java Virtual Machine turn interpreted bytecode into blazing-fast native machine code without requiring manual profile-guided optimization flags?

The secret lies in HotSpot's **Tiered Compilation (`-XX:+TieredCompilation`)** architecture: combining the ultra-fast startup of the **C1 Client Compiler** with the deep, speculative optimizations of the **C2 Server Compiler (Opto)**.

This chapter analyzes how HotSpot detects hot code, compiles active stack frames via **On-Stack Replacement (OSR)**, devirtualizes polymorphic method calls with **Monomorphic Inline Caches**, decomposes objects into CPU registers via **Escape Analysis & Scalar Replacement**, and coordinates Stop-The-World pauses using **Thread-Local Safepoint Handshakes**.

---

## Before you start

Java source compiles to bytecode, and the JVM starts by interpreting it, which is slow. While the program runs, the JVM counts how often each method and loop executes. Hot ones are compiled to machine code at run time by the JIT (just-in-time) compiler. That is why a Java benchmark gets faster after a warm-up and why a first request can be slower than the thousandth.

The JIT uses assumptions it observes. If a call site has only ever seen one class, it calls that class's method directly, and if the assumption later breaks, the JVM throws away the compiled code and falls back (deoptimization). The chapter also covers escape analysis, which can skip heap allocation for objects that never leave a method, and safepoints, the moments where the JVM can pause threads safely.

Read [JVM 01](/tech/series/jvm-concurrency/01.object-header-and-classloading/) first for the object layout that these optimizations remove or reuse.

Terms used in this chapter:

- **interpreter**: the part of the JVM that executes bytecode one instruction at a time without compiling.
- **JIT compiler**: compiles hot bytecode to machine code while the program runs.
- **C1 and C2**: HotSpot's two JIT compilers; C1 compiles quickly with fewer optimizations, C2 compiles slowly and optimizes heavily.
- **tiered compilation**: starting in the interpreter, then C1, then C2 as code gets hotter.
- **OSR**: on-stack replacement, switching a running loop from interpreted to compiled code mid-execution.
- **inline cache**: a call-site cache that remembers the class last seen so the call can be direct.
- **escape analysis**: proving an object is not visible outside a method so it need not be allocated on the heap.
- **safepoint**: a point where a thread can be stopped safely so the JVM can do work such as GC.

## 1. The Five Levels of Tiered Compilation (Tier 0 to Tier 4)

In modern OpenJDK (Java 8+ by default), HotSpot uses a **5-tier compilation pipeline**:

```text
  [Tier 0: Interpreter]
       |  Executes bytecode via template assembly; counts method invocations & loop backedges
       v (invocation counter > Tier3InvocationThreshold ~200)
  [Tier 3: C1 with Full Profiling]
       |  Compiles fast native code; emits MDO (MethodDataOop) profiling probes:
       |  branches taken/untaken, type feedback on invokevirtual, nullness
       v (MDO counters saturated > Tier4InvocationThreshold ~5000)
  [Tier 4: C2 Server Compiler (Opto)]
       Deep speculative optimization: method inlining, loop unrolling, scalar replacement,
       vectorization, devirtualization -> generates peak performance machine assembly!
```

| Level | Compiler Engine | Profile Data Generated? | Primary Objective |
| :--- | :--- | :--- | :--- |
| **Tier 0** | **Interpreter** | Yes (invocation & backedge counters) | Instant startup; zero compilation pause. |
| **Tier 1** | **C1 (Client)** | No profiling | Fast native code for trivial methods without branches. |
| **Tier 2** | **C1 (Client)** | Basic profiling | Used when Tier 3 compile queue is backlogged. |
| **Tier 3** | **C1 (Client)** | **Full Profiling (MethodDataOop)** | Generates branch probabilities and receiver type profiles for C2. |
| **Tier 4** | **C2 (Server / Opto)** | Consumes MDO profiling | **Peak performance**: speculates on profile data; deoptimizes back to Tier 0 if assumptions are violated! |

### What Triggers Deoptimization ("Deopt")?

C2 is an **optimistic compiler**: if profiling in Tier 3 indicates that an `interface Payment` was *only ever called with `CreditCardPayment`*, C2 speculatively inlines `CreditCardPayment.pay()` and emits a single unconditional machine instruction!

- What happens if a third-party plugin suddenly calls `pay()` with `CryptoPayment`?
- The guard check fails: HotSpot triggers **Deoptimization (`uncommon_trap`)**, dynamically reconstructing the interpreter stack frame from machine registers and dropping execution back to **Tier 0 Interpreter** before re-profiling!

## 2. On-Stack Replacement (OSR): Compiling Active Hot Loops

What if a long-running batch job or machine-learning calculation consists of a single massive `for` loop inside `main()` that executes a billion times?

- Because `main()` is only invoked **once**, its method invocation counter will never reach the compilation threshold!
- If the JVM only compiled at method boundaries, `main()` would run in the slow interpreter forever.

HotSpot solves this with **On-Stack Replacement (OSR)**:

1. Every backward branch (the end of a `for` or `while` loop) increments an **OSR Backedge Counter**.
2. When the backedge counter exceeds the tier backedge thresholds (`Tier3BackEdgeThreshold`, `Tier4BackEdgeThreshold`; `-XX:CompileThreshold` only applies with tiered compilation off), HotSpot compiles an **OSR-specialized native code blob**.
3. At the loop boundary, the JVM **replaces the active interpreted stack frame on the fly with the compiled native stack frame**, jumping directly into the compiled machine loop while the method is actively executing!

## 3. Inline Caches: Turning Virtual Dispatch into Direct Jumps

In Java, all non-static, non-final, non-private methods are **virtual** by default (`invokevirtual` or `invokeinterface`). Naive virtual dispatch requires inspecting the target object's `Klass*` vtable pointer on every invocation, adding memory indirection and stalling CPU branch predictors.

HotSpot uses **Inline Caching (IC)** at every call site:

```text
  1. Monomorphic Call Site (100% of calls pass class Cat)
     HotSpot inlines Cat.meow() directly behind a 1-instruction type check:
     cmp [rax + klass_offset], Cat.class;  je Cat_meow_inlined

  2. Bimorphic Call Site (Calls pass Dog or Cat)
     Emits a two-branch conditional jump:
     if (klass == Dog) Dog_bark(); else if (klass == Cat) Cat_meow();

  3. Megamorphic Call Site (3 or more distinct concrete classes at the call site)
     Falls back to a full vtable / itable table lookup!
```

> **The Megamorphic Cliff**:
> Passing 3 or more concrete implementations through the exact same call site (e.g., `logger.log(msg)` across 10 different handlers) turns the call site **megamorphic**, completely preventing C2 from inlining the method body!

## 4. Escape Analysis & Scalar Replacement in C2

Unlike Go's escape analysis (which decides whether to allocate on the goroutine stack or the heap), HotSpot's C2 escape analyzer (`-XX:+DoEscapeAnalysis`) is even more radical: **HotSpot does not allocate objects on the stack at all!**

Instead, if C2 proves that an object has **`NoEscape`** (its reference never escapes the method and is not stored into any field of a heap-reachable object), it performs **Scalar Replacement (`-XX:+EliminateAllocations`)**:

```java
// User Code:
public long compute() {
    Point p = new Point(10, 20); // Point object allocated?
    return p.x + p.y;
}

// What C2 actually compiles:
public long compute() {
    long p_x = 10; // Point object completely DISAPPEARS!
    long p_y = 20; // Decomposed into raw CPU registers rbx and rcx!
    return p_x + p_y; // 0 heap allocations, 0 GC overhead!
}
```

The object is completely disassembled into its constituent primitive fields (**scalars**), which are assigned directly to **CPU registers or the native stack frame**. No object header is built, no memory is reserved on the heap, and the garbage collector never sees it!

## 5. Safepoints & Thread-Local Handshakes

When HotSpot needs to execute a Stop-The-World (STW) operation—such as taking a thread dump (`jstack`), revoking locks, deoptimizing a method, or beginning a GC cycle—how does it pause running Java threads safely?

It cannot freeze a thread at an arbitrary machine instruction because the thread might be in the middle of modifying an internal object header or heap pointer. A thread may only pause at a **Safepoint**—a state where all object references on the thread's stack are precisely known in GC root maps (`OopMap`).

### Thread-Local Handshakes

- In modern OpenJDK (Java 10+), HotSpot eliminated global memory-protection page faults (`mprotect` on a global safepoint page) by adopting **Thread-Local Handshakes (JEP 312)**, which lets the JVM run an operation on one thread without stopping the rest. Global safepoints still exist for GC and similar operations.
- HotSpot arms a per-thread poll page (`JavaThread::_poll_data`). The JIT compiler inserts an inlined safepoint poll instruction at **every method return and loop backedge**:

  ```assembly
  test [r15 + poll_offset], eax   ; Reads per-thread handshake page
  ```

- Under normal execution, the page is readable, costing **~0 CPU cycles**.
- When the JVM needs to pause Thread `T1`, it arms `T1`'s individual polling page. `T1`'s next backedge poll triggers a trap, causing `T1` to safely park itself on a handshake monitor!

> **The Uncounted `int` Loop Trap**:
> C2 automatically removes safepoint polls from **counted `int` loops** (`for (int i = 0; i < len; i++)`) to maximize loop unrolling and SIMD vectorization! If an `int` loop takes 15 seconds to run, the entire JVM may stall waiting for that single thread to reach the end of its loop before beginning a GC cycle! (Modern JDKs mitigate this with loop strip mining, `-XX:LoopStripMiningIter`, which keeps a poll in the outer loop).

## 6. Verification Lab: Scalar Replacement & Monomorphic vs. Megamorphic Call Sites

The following self-contained Java 21 program (`java Lab02.java`) proves and verifies:

1. **Scalar Replacement Allocations**: Runs 20,000,000 iterations allocating a short-lived `Point` object, measuring total memory allocated via `com.sun.management.ThreadMXBean.getThreadAllocatedBytes()`. When C2 kicks in, scalar replacement reduces heap allocation rate to **effectively zero bytes**!
2. **Monomorphic vs. Megamorphic Dispatch**: Compares call-site throughput when dispatching through a single concrete implementation versus alternating between 4 concrete implementations.

```java
import com.sun.management.ThreadMXBean;
import java.lang.management.ManagementFactory;

public class Lab02 {

    static final class Point {
        final int x;
        final int y;
        Point(int x, int y) { this.x = x; this.y = y; }
    }

    // Scalar Replacement Candidate: Point never escapes this method!
    static long runScalarLoop(int iterations) {
        long sum = 0;
        for (int i = 0; i < iterations; i++) {
            Point p = new Point(i, i + 1); // C2 scalar replacement decomposes Point into CPU registers!
            sum += (p.x + p.y);
        }
        return sum;
    }

    interface Shape { int area(); }
    static final class Square implements Shape { public int area() { return 4; } }
    static final class Circle implements Shape { public int area() { return 3; } }
    static final class Triangle implements Shape { public int area() { return 2; } }
    static final class Hexagon implements Shape { public int area() { return 6; } }

    static long runDispatch(Shape[] shapes, int iterations) {
        long sum = 0;
        int len = shapes.length;
        for (int i = 0; i < iterations; i++) {
            sum += shapes[i % len].area(); // Inlined if monomorphic, megamorphic if len >= 4!
        }
        return sum;
    }

    public static void main(String[] args) throws Exception {
        System.out.println("=== HotSpot JVM Lab 02: JIT Compilation, Escape Analysis & Inline Caches ===");
        ThreadMXBean mxBean = (ThreadMXBean) ManagementFactory.getThreadMXBean();

        // 1. Scalar Replacement Verification
        // Warmup JIT C2
        for (int w = 0; w < 5; w++) {
            runScalarLoop(100_000);
        }

        long bytesBefore = mxBean.getThreadAllocatedBytes(Thread.currentThread().threadId());
        long result = runScalarLoop(20_000_000);
        long bytesAfter = mxBean.getThreadAllocatedBytes(Thread.currentThread().threadId());
        long totalAllocatedBytes = bytesAfter - bytesBefore;

        System.out.printf("  [1. Scalar Replacement in C2] 20,000,000 Point allocations -> Allocated Heap Bytes: %d bytes (result=%d)%n",
                totalAllocatedBytes, result);

        // If Scalar Replacement works, 20 million 24-byte Point objects (~480 MB) should allocate < 10 KiB!
        if (totalAllocatedBytes > 500 * 1024) {
            System.out.printf("    NOTE: JVM allocated %d bytes (JIT warmup threshold may require more iterations)%n", totalAllocatedBytes);
        } else {
            System.out.println("    SUCCESS: Scalar replacement completely eliminated ~480 MB of heap allocations!");
        }

        // 2. Monomorphic vs. Megamorphic Call Site
        Shape[] monomorphic = new Shape[]{ new Square() };
        Shape[] megamorphic = new Shape[]{ new Square(), new Circle(), new Triangle(), new Hexagon() };

        // Warm up the monomorphic shape only: warming both through the same method
        // would pollute its type profile and make the "monomorphic" run megamorphic too.
        for (int w = 0; w < 5; w++) {
            runDispatch(monomorphic, 200_000);
        }

        long t0 = System.nanoTime();
        long monoSum = runDispatch(monomorphic, 50_000_000);
        long t1 = System.nanoTime();
        long megaSum = runDispatch(megamorphic, 50_000_000);
        long t2 = System.nanoTime();

        long monoNs = t1 - t0;
        long megaNs = t2 - t1;

        System.out.printf("  [2. Inline Caching] Monomorphic (Square only) : %6.2f ms (sum=%d)%n", monoNs / 1e6, monoSum);
        System.out.printf("                      Megamorphic (4 Shapes)    : %6.2f ms (sum=%d)%n", megaNs / 1e6, megaSum);

        System.out.println("All HotSpot JVM Lab 02 invariants verified.");
    }
}
```

## Key Takeaways

1. **Tiered Compilation balances fast startup with peak throughput**: Tier 0–3 collect rich profiling data (MDOs) that enables Tier 4 C2 to aggressively inline methods and eliminate branches.
2. **Scalar Replacement turns heap objects into CPU registers**: If an object does not escape the allocating method, C2 never puts it on the heap or even on the stack—it decomposes the fields into hardware registers.
3. **Guard against megamorphic call-site degradation**: Passing 3+ concrete classes through the same interface call site prevents inlining; refactor critical loops to monomorphic or bimorphic call sites.
