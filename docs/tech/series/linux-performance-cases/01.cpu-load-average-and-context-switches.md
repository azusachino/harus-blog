## Before you start

This series is for programmers who deploy or debug services on Linux and want a method for "the server is slow", starting with the CPU. The chapters build on each other, and each ends with a small simulator you can run.

The first number most people look at is load average, and it is easy to misread. On a 4-core machine a load of 4 means the cores are roughly full, and a load of 12 means about eight threads are waiting in line, either for a CPU or for slow I/O. High load with low CPU usage points at the second case. Run `uptime` and compare the three load numbers with `nproc`. The chapter also separates a thread that gives up the CPU on its own from one the scheduler kicks off, and shows what to do when `top` shows no culprit.

For the underlying system call and scheduling background, see [System Call Boundaries, Context Switches & Load Average](/tech/series/linux-systems/01.syscalls-and-abi/) in the Linux Systems series.

Terms used in this chapter:

- **load average**: the one, five and fifteen minute average count of threads running, runnable, or in uninterruptible I/O wait.
- **context switch**: the CPU stops one thread and resumes another.
- **voluntary context switch**: a thread gave up the CPU itself, usually to wait for I/O or a lock.
- **involuntary context switch**: the scheduler took the CPU away because the thread used its time slice or a higher-priority thread arrived.
- **softirq**: deferred kernel work, such as handling received network packets.
- **ksoftirqd**: the kernel thread that runs softirq work when it overflows the normal budget.
- **`pidstat`**: a tool that reports per-process CPU, I/O and context-switch figures.

## Linux Performance Cases 01: CPU Subsystem, Load Average & Context Switches

When an alarm triggers alerting that "CPU Load Average is 45 on an 8-core server," junior engineers frequently assume the CPU is 100% pegged and scramble to scale compute instances. Yet inspecting `top` reveals that CPU utilization is sitting at a relaxed 12%.

How can a machine have an enormous load average while its CPU cores are mostly idle?

The answer lies in the Linux kernel scheduler's definition of **Load Average**, and understanding the precise physical distinction between **Running (`R`)**, **Interruptible Sleep (`S`)**, and **Uninterruptible Disk Sleep (`D`)** task states.

---

### 1. What Linux Load Average Actually Measures

In original UNIX systems, Load Average measured the average number of threads in the **Runnable (`TASK_RUNNING`)** state—either currently executing on a CPU core or waiting in a scheduler runqueue.

In 1993, Linux kernel developer Matthias Urlichs made a deliberate modification: Linux includes threads in the **Uninterruptible Sleep (`TASK_UNINTERRUPTIBLE` / `D` state)** in the load average calculation:

$$\text{Load} = \text{Threads}_{TASK\_RUNNING} + \text{Threads}_{TASK\_UNINTERRUPTIBLE}$$

Threads enter `TASK_UNINTERRUPTIBLE` when waiting on hardware events that cannot be safely interrupted by POSIX signals without corrupting kernel state:

- Waiting for physical disk block I/O reads or writes (`fsync`, Page Cache writeback).
- Waiting for NFS or distributed network file system RPC responses.
- Waiting on kernel internal uninterruptible semaphores or mutex locks (`down()` / `mutex_lock()`).

#### The Physics of Load Average

The three numbers reported by `uptime` (`load average: 2.50, 4.20, 8.10`) are not simple arithmetic means. They are **Exponentially Damped Moving Averages** computed at 5-second intervals via a kernel decay constant:

$$\text{Load}_{new} = \text{Load}_{prev} \times e^{-5 / 60} + \text{Active} \times (1 - e^{-5 / 60})$$

- If `Load Average` $\approx$ CPU Core Count: CPUs are fully utilized with zero queue delay.
- If `Load Average` $\gg$ CPU Core Count with **High `%usr` / `%sys`**: CPU compute saturation (too many active threads computing or executing system calls).
- If `Load Average` $\gg$ CPU Core Count with **High `%iowait` or Low CPU utilization**: Storage or block device saturation (threads piling up in `D` state waiting on slow disks).

### 2. Context Switching: Voluntary vs Involuntary

Every time the Linux kernel switches physical CPU execution from one thread to another, it executes a **Context Switch**:

1. Saves hardware register state (instruction pointer, stack pointer, general-purpose registers, floating-point state).
2. When switching to a thread of a different process, swaps the page-table root (CR3 register on x86-64), which invalidates or tags TLB entries (threads of the same process skip this step).
3. Restores the incoming thread's register state.

Using `pidstat -w 1`, context switches are broken down into two distinct indicators:

```text
UID     PID   cswch/s  nvcswch/s  Command
1000   4821   12500.0       2.10  redis-server
1000   4822       4.5    8900.20  stress-ng-cpu
```

#### 1. Voluntary Context Switches (`cswch/s`)

Occur when a thread voluntarily yields the CPU because it is waiting on an external resource:

- Blocking on I/O (`read()`, `write()`, `epoll_wait()`).
- Waiting on concurrency synchronization (`pthread_mutex_lock`, condition variables, channels).
- Sleeping (`nanosleep()`, `sleep()`).

*High `cswch/s` symptom*: High I/O wait, lock contention, or excessive thread counts competing for scarce locks.

#### 2. Involuntary Context Switches (`nvcswch/s`)

Occur when the kernel scheduler forcefully preempts a running thread because:

- Its allocated CFS (Completely Fair Scheduler) time slice has expired.
- A higher-priority real-time task became runnable.

*High `nvcswch/s` symptom*: Extreme CPU saturation. Dozens of threads are actively fighting for CPU execution time, thrashing CPU caches and wasting cycles on scheduler overhead.

### 3. Diagnosing High CPU with No Obvious Process

A classic production nightmare occurs when `top` reports `%usr` at 95%, but the process table shows no individual process consuming more than 1% or 2% CPU.

**Root Cause: Ephemeral Short-Lived Process Forking**
When scripts, cron jobs, or CGI handlers spawn thousands of ephemeral subprocesses per second (e.g. `sh -c "grep ... | awk ..."` inside a tight loop):

- Each process lives for only 2 milliseconds.
- Standard tools like `top` and `ps` sample `/proc` every 1 to 3 seconds, consistently missing processes that terminate between sample intervals.

**Diagnostic Remediation**:
Trace process execution events using eBPF or `perf`:

```bash
# Trace all process executions in real time
execsnoop-bpfcc

# Or record process creation tracepoints with perf
perf record -e sched:sched_process_fork -a -g -- sleep 5
perf script
```

### 4. Softirqs and `ksoftirqd` Saturation

Linux splits interrupt handling into two stages to prevent physical hardware interrupts from starving the system:

1. **Top-Half (Hard IRQ)**: Executes with interrupts disabled, does minimal work (acknowledges the hardware, masks the interrupt), and schedules a softirq.
2. **Bottom-Half (Softirq)**: Executes asynchronously with interrupts enabled to process heavy tasks (network packet processing, timer events).

If softirqs accumulate faster than they can be serviced, the kernel delegates processing to per-CPU kernel threads named `[ksoftirqd/0]`, `[ksoftirqd/1]`:

```bash
watch -d cat /proc/softirqs
```

| Softirq Type | Common Cause of Saturation | Diagnostic Path |
|---|---|---|
| **`NET_RX`** | Ingress network packet storm, SYN floods, lack of RPS/RFS | High `sar -n DEV` packet rate, undersized NIC ring buffers |
| **`NET_TX`** | Outgoing socket buffer congestion | Network egress link saturation |
| **`TIMER`** | Many short timers (frequent sleeps, timeouts, polling loops) | `perf top`, `/proc/softirqs` TIMER delta |
| **`SCHED`** | CFS scheduler rebalancing across NUMA nodes | Excessive thread migration across sockets |

When `ksoftirqd` consumes 100% of a CPU core, network packets are delayed, leading to TCP retransmissions and dropped connections.

### 5. Verification Lab: Scheduler Queue, Load Average & Softirq Simulator

The following self-contained Python lab simulates the Linux scheduler's runqueue:

1. Tracks `TASK_RUNNING` and `TASK_UNINTERRUPTIBLE` tasks.
2. Computes the **exact exponential decay load average** formula used by the Linux kernel.
3. Simulates **voluntary vs involuntary context switches** under CFS time slicing.
4. Models **Softirq packet bursts** and validates `ksoftirqd` thread activation.

```python
"""
Linux Performance Cases Lab 01: CPU Scheduler, Load Average & Context Switches
Simulates Linux kernel load average decay, voluntary/involuntary preemption, and softirq storms.
"""

import math
from typing import List, Dict, Tuple
from enum import Enum, auto

class TaskState(Enum):
    RUNNING = auto()          # TASK_RUNNING (R)
    INTERRUPTIBLE = auto()    # TASK_INTERRUPTIBLE (S)
    UNINTERRUPTIBLE = auto()  # TASK_UNINTERRUPTIBLE (D) - disk/nfs wait
    ZOMBIE = auto()           # TASK_DEAD / EXIT_ZOMBIE (Z)

class SimulatedTask:
    def __init__(self, pid: int, name: str, state: TaskState):
        self.pid = pid
        self.name = name
        self.state = state
        self.time_slice_remaining = 10  # ms
        self.voluntary_switches = 0
        self.involuntary_switches = 0

class LinuxCPUScheduler:
    def __init__(self, num_cores: int):
        self.num_cores = num_cores
        self.tasks: Dict[int, SimulatedTask] = {}
        # Linux 5-second exponential decay constants
        # e^(-5 / (60 * 1)), e^(-5 / (60 * 5)), e^(-5 / (60 * 15))
        self.exp_1 = math.exp(-5.0 / 60.0)
        self.exp_5 = math.exp(-5.0 / 300.0)
        self.exp_15 = math.exp(-5.0 / 900.0)
        self.load_1 = 0.0
        self.load_5 = 0.0
        self.load_15 = 0.0
        # Softirq counters
        self.net_rx_count = 0
        self.ksoftirqd_active = False

    def add_task(self, pid: int, name: str, state: TaskState):
        self.tasks[pid] = SimulatedTask(pid, name, state)

    def count_active_load_threads(self) -> int:
        """
        Linux load average includes BOTH TASK_RUNNING (R) and TASK_UNINTERRUPTIBLE (D)!
        """
        active = 0
        for task in self.tasks.values():
            if task.state in (TaskState.RUNNING, TaskState.UNINTERRUPTIBLE):
                active += 1
        return active

    def tick_5_seconds(self):
        """Computes exponential moving average load across 1, 5, and 15 minute windows."""
        active = float(self.count_active_load_threads())
        self.load_1 = self.load_1 * self.exp_1 + active * (1.0 - self.exp_1)
        self.load_5 = self.load_5 * self.exp_5 + active * (1.0 - self.exp_5)
        self.load_15 = self.load_15 * self.exp_15 + active * (1.0 - self.exp_15)

    def simulate_cfs_time_slice(self, pid: int, execution_time_ms: int, blocks_for_io: bool):
        task = self.tasks[pid]
        if blocks_for_io:
            # Voluntary context switch (yields CPU to wait for socket/disk)
            task.voluntary_switches += 1
            task.state = TaskState.UNINTERRUPTIBLE
        else:
            task.time_slice_remaining -= execution_time_ms
            if task.time_slice_remaining <= 0:
                # Involuntary context switch (time slice exhausted)
                task.involuntary_switches += 1
                task.time_slice_remaining = 10  # Reset slice

    def process_network_packet_burst(self, packet_count: int):
        self.net_rx_count += packet_count
        # If softirq batch exceeds budget (e.g. netdev_budget = 300), ksoftirqd wakes up
        if packet_count > 300:
            self.ksoftirqd_active = True
        else:
            self.ksoftirqd_active = False

def run_lab():
    # -------------------------------------------------------------
    # Test 1: The 'D-State' High Load Average Paradox
    # 4-core machine: 1 compute task (R), 15 disk-blocked tasks (D), 20 sleeping tasks (S)
    # -------------------------------------------------------------
    scheduler = LinuxCPUScheduler(num_cores=4)
    # 1 compute task
    scheduler.add_task(1001, "cpu_worker", TaskState.RUNNING)
    # 15 tasks blocked in uninterruptible disk wait (D state)
    for i in range(15):
        scheduler.add_task(2000 + i, f"db_flush_{i}", TaskState.UNINTERRUPTIBLE)
    # 20 idle sleeping tasks (S state)
    for i in range(20):
        scheduler.add_task(3000 + i, f"idle_worker_{i}", TaskState.INTERRUPTIBLE)

    # Total active tasks in Linux load average = 1 (R) + 15 (D) = 16!
    # Sleeping tasks (S) MUST NOT be counted in load average.
    assert scheduler.count_active_load_threads() == 16

    # Simulate 12 ticks (60 seconds) under steady state
    for _ in range(12):
        scheduler.tick_5_seconds()

    # After 1 minute of 16 active tasks, load_1 converges toward 16.0
    assert scheduler.load_1 > 9.0  # Decayed substantially toward 16
    assert scheduler.load_1 < 16.0

    # -------------------------------------------------------------
    # Test 2: Voluntary vs Involuntary Context Switches
    # -------------------------------------------------------------
    # Task A: I/O bound worker making frequent blocking calls
    scheduler.simulate_cfs_time_slice(pid=1001, execution_time_ms=2, blocks_for_io=True)
    task_a = scheduler.tasks[1001]
    assert task_a.voluntary_switches == 1
    assert task_a.involuntary_switches == 0
    assert task_a.state == TaskState.UNINTERRUPTIBLE

    # Task B: CPU intensive loop exhausting CFS time slices
    scheduler.add_task(4001, "cpu_burner", TaskState.RUNNING)
    task_b = scheduler.tasks[4001]
    for _ in range(5):
        # 5 executions of 10ms = 5 time slice expirations
        scheduler.simulate_cfs_time_slice(pid=4001, execution_time_ms=10, blocks_for_io=False)

    assert task_b.voluntary_switches == 0
    assert task_b.involuntary_switches == 5

    # -------------------------------------------------------------
    # Test 3: Softirq Burst & ksoftirqd Triggering
    # -------------------------------------------------------------
    # Normal ingress: 50 packets -> handled in hard IRQ bottom half directly
    scheduler.process_network_packet_burst(packet_count=50)
    assert not scheduler.ksoftirqd_active

    # Ingress storm: 1500 packets exceeds budget -> ksoftirqd awakened
    scheduler.process_network_packet_burst(packet_count=1500)
    assert scheduler.ksoftirqd_active
    assert scheduler.net_rx_count == 1550

    print(f"Load Average 1m: {scheduler.load_1:.2f} (Active R+D threads: {scheduler.count_active_load_threads()})")
    print(f"Voluntary switches: {task_a.voluntary_switches}, Involuntary: {task_b.involuntary_switches}")
    print(f"ksoftirqd activation on NET_RX storm verified: {scheduler.ksoftirqd_active}")
    print("Linux Performance Cases Lab 01 passed.")

if __name__ == "__main__":
    run_lab()
```
