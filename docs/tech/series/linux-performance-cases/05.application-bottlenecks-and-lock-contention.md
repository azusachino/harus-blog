## Before you start

Sometimes every system metric looks calm and the service is still slow, because threads are waiting on each other rather than on hardware. Picture one toilet and twenty people: the building is not busy, yet the line is long. A mutex in a multithreaded program behaves the same way, so latency climbs while CPU stays low. The chapter shows how that looks on Linux, then two familiar cases: a single-threaded Redis stalled by one slow command or by a fork, and a JVM that stops all application threads at a safepoint. A stack dump with `jstack <pid>` for Java, or `pstack` for native code, shows which threads are waiting.

[Case 01](/tech/series/linux-performance-cases/01.cpu-load-average-and-context-switches/) explains voluntary context switches, which is how blocked threads show up in the numbers.

Terms used in this chapter:

- **mutex**: a lock that lets only one thread at a time into a section of code.
- **futex**: the Linux kernel primitive behind most user-space locks; it enters the kernel only when a lock is contended.
- **lock convoy**: many threads repeatedly queue on the same lock, so they take turns and throughput collapses.
- **off-CPU time**: time a thread spends not running because it is blocked or waiting.
- **copy-on-write (COW)**: after `fork`, parent and child share memory pages and a page is copied only when one of them writes to it.
- **big key**: a Redis key holding a very large value, whose deletion or scan takes long enough to block other clients.
- **safepoint**: a moment when the JVM can pause all Java threads, for example for garbage collection.
- **thread dump**: a snapshot of what every thread in a process is doing.

## Linux Performance Cases 05: Application Bottlenecks & Lock Contention

Operating system metrics (CPU utilization, free memory, disk `await`, packet rates) are physical manifestations of application behavior. When an API server's response latency degrades from 5 ms to 2,000 ms, inspecting `top` often reveals no obvious hardware saturation: CPU is at 20%, disk is idle, and memory is plentiful.

The system is not resource-constrained; it is **internally congested**.

Application threads are blocking on shared synchronization primitives, single-threaded in-memory queues, or language runtime pauses. Diagnosing these application bottlenecks requires bridging the gap between OS kernel events and user-space runtime architectures.

---

### 1. Lock Contention & Linux Fast Userspace Mutexes (Futex)

In modern Linux runtimes (C++, Java, Go, Rust), synchronization primitives like mutexes and condition variables avoid making costly system calls whenever possible using the **Futex (Fast Userspace Mutex)** subsystem (`kernel/futex/` in current kernels).

#### The Two Paths of a Futex

1. **Uncontended Fast Path**: If no other thread holds the lock, acquisition is a single atomic Compare-And-Swap (CAS) instruction in user space (`lock cmpxchg`). Zero system calls, zero kernel mode switches, executing in ~10 nanoseconds.
2. **Contended Slow Path**: If the atomic CAS fails (another thread holds the lock), the thread must not spin and burn 100% CPU. It invokes the `futex()` system call with `FUTEX_WAIT`:

   ```c
   futex(&lock_word, FUTEX_WAIT_PRIVATE, expected_val, NULL);
   ```

   The kernel puts the calling thread into `TASK_INTERRUPTIBLE` sleep and queues it in a kernel hash bucket. When the lock holder releases the mutex, it invokes `futex(..., FUTEX_WAKE_PRIVATE, 1)` to wake the next queued thread.

#### The Lock Convoy Phenomenon

When hundreds of threads compete for a single high-contention mutex:

- Each release triggers a context switch to wake a waiting thread.
- Before the awakened thread can acquire the lock, another already-running thread may steal it.
- Threads spend 99% of their lifespan cycling between `FUTEX_WAIT` and `FUTEX_WAKE`, causing massive voluntary context switch spikes (`cswch/s` in `pidstat`) while application throughput collapses to near zero.

### 2. Redis Latency Anomalies: Single-Thread Bottlenecks

Redis is famously fast because its core command execution loop runs on a **single thread**, avoiding all locking and context switching overhead. However, this single-threaded design means **any operation that blocks that thread freezes all other connected clients**:

#### 1. Big Key `O(N)` Deletions

Deleting a hash or set containing 1,000,000 members via `DEL my_big_key` requires the single thread to traverse and free 1,000,000 memory structures in a tight loop. While deleting, Redis cannot respond to ping or read commands, inducing 500 ms latency spikes across microservices.

- *Remediation*: Use asynchronous deletion: `UNLINK my_big_key`.

#### 2. Fork Copy-On-Write (COW) Latency

When Redis executes `BGSAVE` or `BGREWRITEAOF`, it calls `fork()` to spawn a background snapshot child process.
Although `fork()` does not copy physical memory pages immediately, it **must duplicate the process page table**:

- For a 32 GB Redis instance with standard 4 KB page frames, the page table alone spans ~64 MB.
- Copying 64 MB of page tables while holding the the process memory-map lock (`mmap_lock`, called `mmap_sem` before Linux 5.8) halts the main Redis thread for 50 ms to 200 ms.
- Furthermore, as the main thread writes new data, Linux Copy-On-Write duplicates modified 4 KB pages, causing physical memory amplification.
- *Remediation*: Disable Transparent Huge Pages (THP): `echo never > /sys/kernel/mm/transparent_hugepage/enabled`.

### 3. JVM SafePoint Pauses & Thread Dumps

In Java (HotSpot JVM), garbage collection and thread dumps require all application mutator threads to halt at a known, coordinated state called a **SafePoint**:

1. In the classic scheme, the JVM protects a global polling page so that any access to it faults (recent HotSpot versions use thread-local polling words with the same idea).
2. JIT-compiled code contains polling checks at method returns and loop back-edges. When a thread polls the protected page, it takes a hardware `SIGSEGV`, transferring control to the JVM SafePoint handler.
3. Once **all application threads** reach the SafePoint, the Stop-The-World (STW) phase begins.

#### The SafePoint Straggler Problem

If 99 threads reach the SafePoint in 1 millisecond, but 1 thread is stuck in a long-running `int`-indexed counted loop (which HotSpot historically compiles without a safepoint poll; loop strip mining since JDK 10 reduces the problem), all 99 threads sit idle waiting for the single straggler.
The resulting "GC pause" appears to take 500 ms in application APM tools, even though the actual garbage collection took only 20 ms!

- *Diagnostic*: Enable safepoint logging with `-Xlog:safepoint=debug` (JDK 9+); on JDK 8 use `-XX:+PrintGCApplicationStoppedTime`.

### 4. Verification Lab: Futex Contention & Off-CPU Latency Simulator

The following self-contained Python lab simulates the synchronization mechanics of a high-concurrency server:

1. Implements a **User-Space Mutex with Fast Path & Futex Waiter Queue**.
2. Simulates **uncontended fast-path lock acquisitions** (0 system calls).
3. Simulates **contended lock acquisitions** measuring `FUTEX_WAIT` queueing time and off-CPU latency.
4. Generates an **Off-CPU Latency Report** detailing lock hold times, wait times, and convoy delays.

```python
"""
Linux Performance Cases Lab 05: Application Bottlenecks & Lock Contention
Simulates futex fast-path CAS vs slow-path FUTEX_WAIT queueing and off-CPU latency.
"""

from typing import List, Dict, Optional

class SimulatedThread:
    def __init__(self, tid: int, name: str):
        self.tid = tid
        self.name = name
        self.on_cpu_time_ms = 0.0
        self.off_cpu_wait_ms = 0.0
        self.fast_path_acquisitions = 0
        self.futex_wait_calls = 0

class FutexMutex:
    def __init__(self, name: str):
        self.name = name
        self.is_locked = False
        self.owner_tid: Optional[int] = None
        self.wait_queue: List[SimulatedThread] = []

    def acquire(self, thread: SimulatedThread, current_time_ms: float) -> bool:
        """
        Fast Path: Atomic CAS in user space without entering the kernel.
        """
        if not self.is_locked:
            self.is_locked = True
            self.owner_tid = thread.tid
            thread.fast_path_acquisitions += 1
            return True

        # Slow Path: Lock is held! Thread must invoke FUTEX_WAIT and sleep.
        thread.futex_wait_calls += 1
        self.wait_queue.append(thread)
        return False

    def release(self, current_time_ms: float, lock_hold_duration_ms: float) -> Optional[SimulatedThread]:
        """
        Releases lock and wakes up next waiter via FUTEX_WAKE.
        """
        if not self.is_locked:
            return None

        self.is_locked = False
        self.owner_tid = None

        if self.wait_queue:
            # Wake first waiting thread (FUTEX_WAKE 1)
            next_thread = self.wait_queue.pop(0)
            self.is_locked = True
            self.owner_tid = next_thread.tid
            next_thread.off_cpu_wait_ms += lock_hold_duration_ms
            return next_thread

        return None

def run_lab():
    mutex = FutexMutex(name="db_connection_pool_lock")

    t1 = SimulatedThread(tid=101, name="worker_1")
    t2 = SimulatedThread(tid=102, name="worker_2")
    t3 = SimulatedThread(tid=103, name="worker_3")

    # -------------------------------------------------------------
    # Test 1: Uncontended Fast-Path Acquisition
    # -------------------------------------------------------------
    # Thread 1 acquires free lock: CAS succeeds instantly
    acquired = mutex.acquire(t1, current_time_ms=0.0)
    assert acquired is True
    assert mutex.is_locked is True
    assert mutex.owner_tid == 101
    assert t1.fast_path_acquisitions == 1
    assert t1.futex_wait_calls == 0

    # -------------------------------------------------------------
    # Test 2: Contended Slow-Path & FUTEX_WAIT Queueing
    # -------------------------------------------------------------
    # While Thread 1 holds lock, Thread 2 and Thread 3 try to acquire
    acquired_2 = mutex.acquire(t2, current_time_ms=2.0)
    assert acquired_2 is False
    assert t2.futex_wait_calls == 1
    assert len(mutex.wait_queue) == 1

    acquired_3 = mutex.acquire(t3, current_time_ms=3.0)
    assert acquired_3 is False
    assert t3.futex_wait_calls == 1
    assert len(mutex.wait_queue) == 2

    # -------------------------------------------------------------
    # Test 3: Lock Release & Waiter Handoff
    # Thread 1 finishes after 20ms hold time
    # -------------------------------------------------------------
    # Release wakes Thread 2
    woken_thread = mutex.release(current_time_ms=20.0, lock_hold_duration_ms=20.0)
    assert woken_thread is t2
    assert mutex.owner_tid == 102
    assert t2.off_cpu_wait_ms == 20.0
    assert len(mutex.wait_queue) == 1  # Thread 3 still waiting

    # Thread 2 finishes after 15ms hold time
    woken_thread_3 = mutex.release(current_time_ms=35.0, lock_hold_duration_ms=15.0)
    assert woken_thread_3 is t3
    assert mutex.owner_tid == 103
    assert t3.off_cpu_wait_ms == 15.0
    assert len(mutex.wait_queue) == 0

    # Thread 3 releases; lock is now completely free
    mutex.release(current_time_ms=50.0, lock_hold_duration_ms=10.0)
    assert mutex.is_locked is False
    assert mutex.owner_tid is None

    # Cumulative off-CPU wait time caused by lock contention = 35 ms
    total_off_cpu = t1.off_cpu_wait_ms + t2.off_cpu_wait_ms + t3.off_cpu_wait_ms
    assert total_off_cpu == 35.0

    print(f"Mutex: {mutex.name}")
    print(f"Thread 1 (Owner): Fast-Path CAS={t1.fast_path_acquisitions}, Futex Waits={t1.futex_wait_calls}")
    print(f"Thread 2 (Contended): Futex Waits={t2.futex_wait_calls}, Off-CPU Wait={t2.off_cpu_wait_ms}ms")
    print(f"Thread 3 (Contended): Futex Waits={t3.futex_wait_calls}, Off-CPU Wait={t3.off_cpu_wait_ms}ms")
    print(f"Total Off-CPU Contention Stall: {total_off_cpu}ms")
    print("Linux Performance Cases Lab 05 passed.")

if __name__ == "__main__":
    run_lab()
```
