## Before you start

After five chapters of single-subsystem cases, this one deals with the harder real-world situation: you get paged, something is slow, and you do not yet know whether it is CPU, memory, disk, network or the application. Random commands waste time and mislead. A doctor does not order every test at once; she asks about symptoms, checks vital signs, then narrows down. The chapter lays out the same routine for a server: define the scope of the problem, run a quick scan across all subsystems, then drill into the one that stands out. It then walks through a failure where one problem cascades into others, and lists habits that send investigations the wrong way.

This chapter assumes you have seen the earlier cases, especially [case 05 on lock contention](/tech/series/linux-performance-cases/05.application-bottlenecks-and-lock-contention/). The Linux Systems series ends with a related method in [Network Stack Tuning, eBPF & the USE Method](/tech/series/linux-systems/08.performance-and-ebpf/).

Terms used in this chapter:

- **scope**: which hosts, endpoints, users and time window are affected by the problem.
- **subsystem scan**: a short, fixed set of commands such as `uptime`, `vmstat`, `iostat` and `sar` that covers CPU, memory, disk and network in about a minute.
- **kernel space / user space**: code running inside the kernel versus ordinary application code; a drilldown decides which side the time is spent on.
- **cascading failure**: one fault triggers another, so the loudest symptom is not the original cause.
- **root cause**: the earliest fault in the chain that, if fixed, stops the symptoms.
- **anti-pattern**: a common investigation habit, such as changing several settings at once, that obscures the cause.

## Linux Performance Cases 06: Systematic Troubleshooting & Root Cause Analysis

When a complex distributed system suffers a performance degradation, rarely does a single component break in clean isolation. In real production incidents, **failures cascade across kernel subsystems**:

$$\text{Memory Leak} \longrightarrow \text{Direct Reclaim} \longrightarrow \text{Disk I/O Saturation} \longrightarrow \text{Thread Lock Contention} \longrightarrow \text{Network Drop Storm}$$

Attempting to resolve such incidents by inspecting metrics in isolation leads to misleading diagnoses. An engineer inspecting disk latency sees 100% disk utilization and blames the storage array. Another engineer inspecting network metrics sees dropped TCP packets and blames the top-of-rack switch. Both are treating downstream symptoms while the true root cause was a memory leak in a logging daemon.

True performance engineering requires a **systematic troubleshooting methodology** that traces causal chains across kernel boundaries to isolate the root cause.

### 1. The Systematic Troubleshooting Decision Tree

A structured performance investigation follows a disciplined decision tree from symptoms to root cause isolation:

<Archify src="./diagrams/systematic-performance-triage.workflow.json" />

#### Phase 1: Establish Problem Scope

Before touching the terminal, establish the invariant facts:

1. **What is the symptom?** (Latency spike, throughput collapse, error rate breach, complete hang).
2. **What is the blast radius?** (Single container, single physical host, entire cluster, specific endpoint).
3. **What was the trigger?** (New code release, traffic surge, cron job execution, hardware degradation).

#### Phase 2: The 60-Second Subsystem Scan

Execute Brendan Gregg's 60-second triage (`uptime`, `vmstat 1`, `mpstat -P ALL 1`, `pidstat 1`, `iostat -xz 1`, `free -m`, `sar -n DEV,TCP 1`).

- Check **CPU**: Is load average high? Is time spent in `%usr` (user space computation) or `%sys` (system calls / kernel locks)?
- Check **Memory**: Is `available` memory exhausted? Are `si` / `so` (swap) counters non-zero?
- Check **Storage**: Are `await` and `aqu-sz` elevated?
- Check **Network**: Are packet drops (`rx_dropped`) or TCP retransmissions (`retrans/s`) non-zero?

#### Phase 3: Kernel vs User Space Boundary Drilldown

- If `%sys` is elevated: Trace system calls via `perf trace` or eBPF `syscount` to identify which syscalls (`futex`, `epoll_wait`, `read`, `write`) dominate kernel execution time.
- If `%usr` is elevated: Sample on-CPU stack traces with `perf record -F 99 -g` and generate a CPU Flame Graph.
- If CPU is idle but latency is high: Trace off-CPU thread sleep with `offcputime` or `bpftrace` to identify lock contention or downstream socket wait.

### 2. Deconstructing a Cascading Multi-Subsystem Failure

Consider the post-mortem of a production incident where an API gateway began returning `504 Gateway Timeout` errors under moderate load:

```text
Incident Timeline & Causal Cascade:
[ Step 1: Memory Subsystem ]
An analytics daemon in the background allocates 24 GB of RAM, dropping free memory below the min watermark.
                    │
                    ▼
[ Step 2: Direct Reclaim Stalls ]
The kernel halts memory allocations and initiates synchronous direct page reclaim.
kworker threads begin flushing dirty Page Cache pages to disk at maximum IOPS.
                    │
                    ▼
[ Step 3: Block Layer Saturation ]
Physical SSD write queues saturate: iostat reports await surging from 0.8 ms to 140.0 ms.
                    │
                    ▼
[ Step 4: Application Lock Contention ]
The API gateway attempts to append access logs via write() to an ext4 file.
Because the block layer is saturated, write() blocks inside the kernel holding the inode mutex.
All worker threads attempting to log requests queue behind the mutex in FUTEX_WAIT.
                    │
                    ▼
[ Step 5: Network Drop Storm & Timeout ]
With all worker threads blocked, the accept queue and socket receive buffers fill up.
The kernel starts dropping new connections; clients experience 504 Gateway Timeouts.
```

**The Diagnostic Lesson**:
If you only looked at the network stack, you would see dropped packets. If you only looked at the application, you would see mutex lock contention. If you only looked at disk I/O, you would see elevated `await`.
Only by correlating metrics chronologically across memory, storage, locks, and network does the true causal chain become unmistakable.

---

### 3. Diagnostic Anti-Patterns to Eliminate

1. **The "Reboot and Pray" Anti-Pattern**: Rebooting a sluggish server temporarily clears in-memory queues and provides brief relief, but it completely destroys the transient forensic evidence (kernel ring buffer logs, unswapped heap allocations, thread dumps) needed to identify the permanent root cause.
2. **The "Blame the Database/Network" Anti-Pattern**: Jumping to conclusion without metric evidence. Always verify whether the database actually received the queries and whether the network dropped packets before escalating across teams.
3. **Premature Horizontal Scaling**: Adding 10 more server instances to a cluster suffering from distributed lock contention or database lock table serialization **amplifies the bottleneck**, because more clients compete for the exact same contested lock.

### 4. Verification Lab: Multi-Subsystem Anomaly Correlation Engine

The following self-contained Python lab implements an automated **Systems Performance Anomaly Correlation Engine**:

1. Ingests synthetic multi-subsystem metric vectors (CPU `%usr`, `%sys`, `%iowait`, load average, free memory, `si/so`, `await`, `%util`, packet drop rate).
2. Evaluates the **USE Method anomaly matrix** across CPU, memory, storage, and networking.
3. Traces causal dependencies to isolate the primary trigger from secondary cascading symptoms.
4. Outputs an actionable diagnostic root-cause report verified by unit assertions.

```python
"""
Linux Performance Cases Lab 06: Systematic Troubleshooting & Anomaly Correlation
Simulates multi-subsystem metric ingestion, cascade correlation, and automated diagnosis.
"""

from typing import Dict, List, Tuple
from enum import Enum, auto

class SubsystemStatus(Enum):
    HEALTHY = auto()
    UTILIZED = auto()
    SATURATED = auto()
    ERROR = auto()

class SystemMetrics:
    def __init__(
        self,
        load_avg_1m: float,
        cpu_cores: int,
        cpu_usr: float,
        cpu_sys: float,
        cpu_iowait: float,
        mem_available_pct: float,
        swap_io_rate: float,
        disk_await_ms: float,
        disk_util_pct: float,
        net_retrans_rate: float,
        net_drop_rate: float
    ):
        self.load_avg_1m = load_avg_1m
        self.cpu_cores = cpu_cores
        self.cpu_usr = cpu_usr
        self.cpu_sys = cpu_sys
        self.cpu_iowait = cpu_iowait
        self.mem_available_pct = mem_available_pct
        self.swap_io_rate = swap_io_rate
        self.disk_await_ms = disk_await_ms
        self.disk_util_pct = disk_util_pct
        self.net_retrans_rate = net_retrans_rate
        self.net_drop_rate = net_drop_rate

class AnomalyDiagnosticEngine:
    def __init__(self, metrics: SystemMetrics):
        self.m = metrics
        self.subsystems: Dict[str, SubsystemStatus] = {}
        self.diagnoses: List[str] = []

    def evaluate_use_matrix(self):
        # 1. CPU Subsystem Evaluation
        cpu_saturated = (self.m.load_avg_1m > self.m.cpu_cores * 1.5) or (self.m.cpu_usr + self.m.cpu_sys > 90.0)
        if cpu_saturated:
            self.subsystems["cpu"] = SubsystemStatus.SATURATED
        else:
            self.subsystems["cpu"] = SubsystemStatus.HEALTHY

        # 2. Memory Subsystem Evaluation
        mem_saturated = (self.m.mem_available_pct < 5.0) or (self.m.swap_io_rate > 10.0)
        if mem_saturated:
            self.subsystems["memory"] = SubsystemStatus.SATURATED
        else:
            self.subsystems["memory"] = SubsystemStatus.HEALTHY

        # 3. Disk Subsystem Evaluation
        disk_saturated = (self.m.disk_await_ms > 20.0) or (self.m.disk_util_pct > 95.0) or (self.m.cpu_iowait > 25.0)
        if disk_saturated:
            self.subsystems["disk"] = SubsystemStatus.SATURATED
        else:
            self.subsystems["disk"] = SubsystemStatus.HEALTHY

        # 4. Network Subsystem Evaluation
        net_saturated = (self.m.net_retrans_rate > 5.0) or (self.m.net_drop_rate > 0.5)
        if net_saturated:
            self.subsystems["network"] = SubsystemStatus.SATURATED
        else:
            self.subsystems["network"] = SubsystemStatus.HEALTHY

    def correlate_root_cause(self) -> str:
        self.evaluate_use_matrix()

        # Rule 1: Memory Exhaustion causing Disk Thrashing (Cascade)
        if self.subsystems["memory"] == SubsystemStatus.SATURATED and self.subsystems["disk"] == SubsystemStatus.SATURATED:
            if self.m.swap_io_rate > 0:
                return "ROOT CAUSE: Memory exhaustion inducing swap disk thrashing (high await & iowait)."
            return "ROOT CAUSE: Direct reclaim stall flushing dirty page cache to disk."

        # Rule 2: Pure Storage Block I/O Bottleneck
        if self.subsystems["disk"] == SubsystemStatus.SATURATED and self.subsystems["memory"] == SubsystemStatus.HEALTHY:
            return "ROOT CAUSE: Storage block device bottleneck (await >> service time, queue saturated)."

        # Rule 3: Pure CPU Compute or Kernel Lock Saturation
        if self.subsystems["cpu"] == SubsystemStatus.SATURATED:
            if self.m.cpu_sys > 40.0:
                return "ROOT CAUSE: High kernel %sys CPU (futex lock contention, interrupt storm, or memory fragmentation)."
            return "ROOT CAUSE: User-space CPU saturation (%usr pegging cores; scale compute or profile CPU flame graphs)."

        # Rule 4: Network Packet Loss
        if self.subsystems["network"] == SubsystemStatus.SATURATED:
            return "ROOT CAUSE: Network stack packet drops or TCP retransmission storm (check ring buffers and conntrack)."

        return "SYSTEM HEALTHY: No subsystem saturation detected."

def run_lab():
    # -------------------------------------------------------------
    # Scenario A: Cascading Memory Leak inducing Swap Thrashing
    # -------------------------------------------------------------
    leak_metrics = SystemMetrics(
        load_avg_1m=14.5,
        cpu_cores=8,
        cpu_usr=15.0,
        cpu_sys=20.0,
        cpu_iowait=55.0,        # High iowait!
        mem_available_pct=2.1,  # Exhausted RAM!
        swap_io_rate=250.0,     # Active swapping!
        disk_await_ms=85.0,     # Disk struggling with swap writes!
        disk_util_pct=99.0,
        net_retrans_rate=0.1,
        net_drop_rate=0.0
    )
    engine_a = AnomalyDiagnosticEngine(leak_metrics)
    root_cause_a = engine_a.correlate_root_cause()
    assert "Memory exhaustion inducing swap disk thrashing" in root_cause_a
    assert engine_a.subsystems["memory"] == SubsystemStatus.SATURATED
    assert engine_a.subsystems["disk"] == SubsystemStatus.SATURATED

    # -------------------------------------------------------------
    # Scenario B: Pure Storage Block Layer Bottleneck
    # RAM is healthy (65% available), but disk await is 95ms
    # -------------------------------------------------------------
    storage_metrics = SystemMetrics(
        load_avg_1m=8.2,
        cpu_cores=8,
        cpu_usr=12.0,
        cpu_sys=8.0,
        cpu_iowait=45.0,
        mem_available_pct=65.0, # Plenty of free RAM
        swap_io_rate=0.0,       # Zero swap
        disk_await_ms=95.0,     # Saturated disk!
        disk_util_pct=100.0,
        net_retrans_rate=0.0,
        net_drop_rate=0.0
    )
    engine_b = AnomalyDiagnosticEngine(storage_metrics)
    root_cause_b = engine_b.correlate_root_cause()
    assert "Storage block device bottleneck" in root_cause_b
    assert engine_b.subsystems["memory"] == SubsystemStatus.HEALTHY
    assert engine_b.subsystems["disk"] == SubsystemStatus.SATURATED

    # -------------------------------------------------------------
    # Scenario C: High Kernel %sys (Lock Contention)
    # CPU usr = 20%, CPU sys = 75%
    # -------------------------------------------------------------
    lock_metrics = SystemMetrics(
        load_avg_1m=22.0,
        cpu_cores=8,
        cpu_usr=20.0,
        cpu_sys=75.0,           # Massive %sys!
        cpu_iowait=2.0,
        mem_available_pct=40.0,
        swap_io_rate=0.0,
        disk_await_ms=1.2,
        disk_util_pct=10.0,
        net_retrans_rate=0.1,
        net_drop_rate=0.0
    )
    engine_c = AnomalyDiagnosticEngine(lock_metrics)
    root_cause_c = engine_c.correlate_root_cause()
    assert "High kernel %sys CPU" in root_cause_c
    assert engine_c.subsystems["cpu"] == SubsystemStatus.SATURATED

    print(f"Scenario A Diagnosis: {root_cause_a}")
    print(f"Scenario B Diagnosis: {root_cause_b}")
    print(f"Scenario C Diagnosis: {root_cause_c}")
    print("Linux Performance Cases Lab 06 passed.")

if __name__ == "__main__":
    run_lab()
```
