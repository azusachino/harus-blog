## Before you start

Run `free -h` on a healthy server and it often shows almost no "free" memory. That alarms newcomers, but Linux deliberately fills spare RAM with cached file data and gives it back when programs need it. The number that matters is "available". This chapter explains how to read `free`, how the kernel decides what to reclaim as memory gets tight, why a process can stall in the middle of an allocation, and how the OOM killer picks its victim. A small example: a 16 GB machine showing 200 MB free and 11 GB available is fine; one showing 200 MB available and heavy swap activity is not.

Read the [Processes and Virtual Memory](/tech/series/linux-systems/05.processes-and-virtual-memory/) chapter of the Linux Systems series for the background on page faults and `kswapd`; this chapter's CPU companion is [case 01](/tech/series/linux-performance-cases/01.cpu-load-average-and-context-switches/).

Terms used in this chapter:

- **page cache**: RAM the kernel uses to keep recently used file contents.
- **buffers**: cached block-device metadata; a small part of what `free` reports as buff/cache.
- **available**: the kernel's estimate of memory a new program could get without swapping.
- **anonymous memory**: memory not backed by a file, such as a program's heap and stack.
- **file-backed page**: a memory page whose contents come from a file and can be re-read from disk.
- **watermark**: a free-memory threshold (min, low, high) that decides when background reclaim starts and stops.
- **direct reclaim**: a program freeing memory itself, blocked, because background reclaim could not keep up.
- **OOM killer**: the kernel routine that kills a process when memory cannot be freed.

## Linux Performance Cases 02: Memory Subsystem, Page Cache & OOM Killer

In Linux, "free memory" is wasted memory. Modern kernels aggressively allocate unused physical RAM to the **Page Cache** to accelerate disk I/O, often leaving only 1% to 3% reported as completely idle in `free -m`.

Yet this dynamic caching model frequently creates diagnostic confusion:

- When does high memory usage indicate healthy caching versus a critical memory leak?
- Why do systems with gigabytes of Page Cache suddenly experience severe latency stalls?
- How does the **Out-Of-Memory (OOM) Killer** choose which process to sacrifice?

---

### 1. Demystifying `free`: Buffers, Cache & Available

Running `free -m` presents three critical memory categories:

```text
               total        used        free      shared  buff/cache   available
Mem:           31980       14210         420         180       17350       17120
Swap:           8192         256        7936
```

1. **`free` (420 MB)**: Unallocated physical memory containing zero data.
2. **`buff/cache` (17,350 MB)**:
   - **Buffers**: Raw disk block caches (metadata like superblocks, directory entries, block headers).
   - **Cache**: The **Page Cache**—in-memory 4 KB page frames caching file content read from or written to disk.
3. **`available` (17,120 MB)**: The actual amount of memory available for starting new applications without swapping. It includes `free` plus reclaimable Page Cache and slab dentries/inodes, minus reserved memory watermarks.

**Rule of Thumb**: When diagnosing memory pressure, ignore `free`; monitor **`available`**.

---

### 2. Anonymous Memory vs File-Backed Pages

Physical memory pages fall into two distinct classifications:

```text
Physical RAM (Page Frames)
├── File-Backed Pages (Page Cache)
│   ├── Clean Pages: Can be immediately evicted without disk I/O (discard from RAM)
│   └── Dirty Pages: Must be written to disk (writeback) before eviction
└── Anonymous Pages (Heap, Stack, BSS, Anonymous mmap)
    ├── Cannot be discarded (data would be lost)
    └── Can ONLY be reclaimed by writing them to physical Swap disk
```

When memory pressure mounts, the kernel must decide whether to reclaim **file-backed pages** (evicting Page Cache) or **anonymous pages** (swapping to disk). This ratio is governed by `/proc/sys/vm/swappiness`:

$$\text{Swap Ratio} = \frac{\text{swappiness}}{200 - \text{swappiness}}$$

A `swappiness` value of 60 means the kernel balances cache eviction and swapping. Setting `swappiness = 10` forces the kernel to aggressively evict file-backed Page Cache before writing anonymous application heap to swap disk.

---

### 3. Memory Watermarks & Direct Reclaim Stalls

Every NUMA memory zone maintains three internal watermark thresholds: **`min`**, **`low`**, and **`high`** (configurable via `/proc/sys/vm/min_free_kbytes`):

```text
Memory Level:
  ▲
  │  Free Memory Plenty (> high watermark)
──┼─────────────────────────────────────── high watermark
  │  kswapd0 sleeps; allocations proceed at zero cost
  │
──┼─────────────────────────────────────── low watermark
  │  kswapd0 wakes up in the background; asynchronously reclaims pages
  │
──┼─────────────────────────────────────── min watermark
  │  CRITICAL: Direct Reclaim Stalls!
  │  Allocating threads BLOCK synchronously, waiting for page eviction!
  ▼
```

1. **Above `high`**: System is healthy; `kswapd0` sleeps.
2. **Between `low` and `min`**: The kernel background reclamation thread (`kswapd0`) wakes up and begins asynchronously evicting clean page cache.
3. **Below `min`**: **Direct Reclaim Stalls**. If allocations outpace `kswapd0`, any process calling `malloc()` or faulting in memory is **halted in place**. The application thread itself is forced to synchronously write dirty pages to disk and evict blocks before its memory request is fulfilled.

**Production Impact**: Direct reclaim induces massive latency spikes (hundreds of milliseconds) in database and API threads, visible in `sar -B` under the `pgscand/s` (pages scanned directly) metric.

---

### 4. The Out-Of-Memory (OOM) Killer

When available physical RAM drops below `min` and swap is exhausted or unable to satisfy the allocation, the kernel invokes the **OOM Killer** (`mm/oom_kill.c`).

The kernel cannot simply panic the machine. Instead, it iterates through every process in the system and computes an integer **`badness()` score** between 0 and 1000:

$$\text{points} = \frac{\text{RSS} + \text{swap\_usage}}{\text{total\_ram}} \times 1000 + \text{oom\_score\_adj}$$

#### Influencing Factors

1. **Memory Footprint (RSS, swap, page tables)**: High-memory processes receive proportionally higher badness scores.
2. **`oom_score_adj` Protection**: Administrators can explicitly tune `/proc/[pid]/oom_score_adj`:
   - Range: `-1000` to `+1000`.
   - Setting `-1000` completely immune-shields critical daemons (`sshd`, `systemd`, `k3s-agent`) from being killed.
   - Setting `+1000` designates low-priority batch workers or cache daemons as the first sacrifice.

### 5. Verification Lab: Watermark Reclamation & OOM Heuristic Simulator

The following self-contained Python lab simulates the Linux memory management subsystem:

1. Tracks anonymous memory, clean page cache, and dirty page cache across physical RAM.
2. Computes the **`min`, `low`, and `high` zone watermarks**.
3. Simulates **`kswapd0` asynchronous eviction** vs **Direct Reclaim latency stalls**.
4. Implements the Linux **OOM `badness()` calculation**, verifying that processes with negative `oom_score_adj` are protected while large consumers are prioritized for termination.

```python
"""
Linux Performance Cases Lab 02: Memory Subsystem, Page Cache & OOM Killer
Simulates memory zone watermarks, direct reclaim stalls, and OOM killer badness scoring.
"""

from typing import List, Dict, Optional

class ProcessMemory:
    def __init__(self, pid: int, name: str, rss_mb: int, swap_mb: int, oom_score_adj: int = 0):
        self.pid = pid
        self.name = name
        self.rss_mb = rss_mb
        self.swap_mb = swap_mb
        self.oom_score_adj = oom_score_adj  # -1000 (immune) to +1000 (first killed)
        self.is_alive = True

    def compute_badness(self, total_ram_mb: int) -> int:
        if self.oom_score_adj == -1000:
            return -1  # Immune from OOM killer
        # Base points: proportion of RAM + swap consumed (0 to 1000)
        usage = self.rss_mb + self.swap_mb
        points = int((usage / total_ram_mb) * 1000)
        points += self.oom_score_adj
        return max(0, min(1000, points))

class MemorySubsystem:
    def __init__(self, total_ram_mb: int):
        self.total_ram_mb = total_ram_mb
        # Watermarks (derived from min_free_kbytes)
        self.watermark_min = int(total_ram_mb * 0.05)   # 5%
        self.watermark_low = int(total_ram_mb * 0.08)   # 8%
        self.watermark_high = int(total_ram_mb * 0.12)  # 12%

        # Memory allocations
        self.anonymous_mb = 0
        self.clean_page_cache_mb = 0
        self.dirty_page_cache_mb = 0

        # Metrics
        self.kswapd_wakes = 0
        self.direct_reclaim_stalls = 0
        self.oom_kills = 0

    @property
    def free_mb(self) -> int:
        used = self.anonymous_mb + self.clean_page_cache_mb + self.dirty_page_cache_mb
        return max(0, self.total_ram_mb - used)

    @property
    def available_mb(self) -> int:
        # available = free + clean_cache - reserved_min
        reclaimable = self.clean_page_cache_mb
        return max(0, self.free_mb + reclaimable - self.watermark_min)

    def allocate_memory(self, amount_mb: int, is_anonymous: bool = True):
        # Check if allocation drops below watermarks
        projected_free = self.free_mb - amount_mb

        if projected_free < self.watermark_min:
            # DIRECT RECLAIM STALL: Application thread blocks synchronously!
            self.direct_reclaim_stalls += 1
            # Synchronously reclaim clean page cache
            reclaim_needed = self.watermark_low - projected_free
            evicted = min(self.clean_page_cache_mb, reclaim_needed)
            self.clean_page_cache_mb -= evicted

        elif projected_free < self.watermark_low:
            # kswapd0 wakes up in background
            self.kswapd_wakes += 1
            # Asynchronously evict clean page cache down to high watermark
            evicted = min(self.clean_page_cache_mb, 50)
            self.clean_page_cache_mb -= evicted

        if is_anonymous:
            self.anonymous_mb += amount_mb
        else:
            self.clean_page_cache_mb += amount_mb

    def trigger_oom_killer(self, processes: List[ProcessMemory]) -> Optional[ProcessMemory]:
        self.oom_kills += 1
        best_target = None
        highest_badness = -1

        for proc in processes:
            if not proc.is_alive:
                continue
            score = proc.compute_badness(self.total_ram_mb)
            if score > highest_badness:
                highest_badness = score
                best_target = proc

        if best_target:
            best_target.is_alive = False
            self.anonymous_mb = max(0, self.anonymous_mb - best_target.rss_mb)

        return best_target

def run_lab():
    # -------------------------------------------------------------
    # Test 1: Watermarks and Direct Reclaim
    # Total RAM: 1000 MB
    # min: 50 MB, low: 80 MB, high: 120 MB
    # -------------------------------------------------------------
    mem = MemorySubsystem(total_ram_mb=1000)
    assert mem.watermark_min == 50
    assert mem.watermark_low == 80
    assert mem.watermark_high == 120

    # Fill Page Cache with 600 MB of clean cached files
    mem.allocate_memory(600, is_anonymous=False)
    assert mem.clean_page_cache_mb == 600
    assert mem.free_mb == 400

    # Allocate anonymous memory: 330 MB
    # Remaining free = 400 - 330 = 70 MB (below low watermark 80 MB -> kswapd wakes)
    mem.allocate_memory(330, is_anonymous=True)
    assert mem.kswapd_wakes == 1
    assert mem.direct_reclaim_stalls == 0

    # Allocate another 350 MB: projected free drops below min watermark (50 MB)
    # Direct reclaim stall must trigger and synchronously evict clean page cache!
    mem.allocate_memory(350, is_anonymous=True)
    assert mem.direct_reclaim_stalls == 1

    # -------------------------------------------------------------
    # Test 2: OOM Killer Badness Heuristic
    # -------------------------------------------------------------
    procs = [
        # Process 1: Database buffer pool (400 MB), protected by oom_score_adj = -800
        ProcessMemory(pid=100, name="postgres", rss_mb=400, swap_mb=0, oom_score_adj=-800),
        # Process 2: System daemon (20 MB), completely immune (oom_score_adj = -1000)
        ProcessMemory(pid=1, name="systemd", rss_mb=20, swap_mb=0, oom_score_adj=-1000),
        # Process 3: Batch analytics job leaking memory (350 MB), default oom_score_adj = 0
        ProcessMemory(pid=500, name="python_leak", rss_mb=350, swap_mb=50, oom_score_adj=0),
        # Process 4: Low-priority cache worker (100 MB), sacrificial oom_score_adj = +500
        ProcessMemory(pid=800, name="redis_cache", rss_mb=100, swap_mb=0, oom_score_adj=500),
    ]

    # Verify individual badness scores out of 1000:
    # systemd: -1 (immune)
    assert procs[1].compute_badness(total_ram_mb=1000) == -1
    # postgres: (400/1000)*1000 - 800 = 400 - 800 = -400 -> clamped to 0
    assert procs[0].compute_badness(total_ram_mb=1000) == 0
    # python_leak: (400/1000)*1000 + 0 = 400
    assert procs[2].compute_badness(total_ram_mb=1000) == 400
    # redis_cache: (100/1000)*1000 + 500 = 600
    assert procs[3].compute_badness(total_ram_mb=1000) == 600

    # Even though python_leak uses 400 MB and redis_cache only uses 100 MB,
    # redis_cache has oom_score_adj = 500 (score 600 > 400), so it is terminated first!
    victim1 = mem.trigger_oom_killer(procs)
    assert victim1 is not None
    assert victim1.name == "redis_cache"
    assert not victim1.is_alive

    # On second OOM invocation, python_leak (score 400) is the next victim
    victim2 = mem.trigger_oom_killer(procs)
    assert victim2 is not None
    assert victim2.name == "python_leak"
    assert not victim2.is_alive

    # Critical processes remain alive
    assert procs[0].is_alive  # postgres alive
    assert procs[1].is_alive  # systemd alive

    print(f"Memory watermarks verified: min={mem.watermark_min}MB, low={mem.watermark_low}MB")
    print(f"kswapd background wakes: {mem.kswapd_wakes}, Direct reclaim stalls: {mem.direct_reclaim_stalls}")
    print(f"OOM victims sacrificed in order: [{victim1.name}, {victim2.name}]")
    print("Linux Performance Cases Lab 02 passed.")

if __name__ == "__main__":
    run_lab()
```
