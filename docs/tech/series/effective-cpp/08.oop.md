面向对象设计（OOP）绝非简单地堆叠 `class`、拉取继承关系线。在 C++ 中，继承是一柄精细却充满隐蔽暗坑的手术刀。一旦滥用 public 继承、扭曲了概念模型，或者忽视了虚函数的绑定时机，整个软件的领域模型与运行时行为就会彻底脱节。本章从**里氏替换原则、名称遮掩、接口与实现分离、NVI 惯用法到多重继承**展开全面梳理。

---

## 确定你的 public 继承塑模出 "is-a" 关系

在 C++ 面向对象世界中，**public 继承（Public Inheritance）具有极其神圣的数学与语义契约：它塑模的是 "is-a"（是一种）的关系**。

> **里氏替换原则（Liskov Substitution Principle, LSP）**：
> 每一个派生类对象，都必须能无缝替换其基类对象，而调用者的任何预期行为都不会被破坏。

### 企鹅与鸟的经典悖论

日常语言中的概念分类往往充满直觉误差：

```cpp
class Bird {
public:
    virtual void fly(); // 鸟类都会飞
};

class Penguin : public Bird { ... }; // 企鹅是一种鸟（编译通过！）
```

在现实生物学中，企鹅确实是一种鸟；但在程序的世界里，企鹅根本不能飞！如果你写出如下代码：

```cpp
void makeBirdFly(Bird& b) {
    b.fly(); // 契约保证所有鸟都能飞！
}

Penguin p;
makeBirdFly(p); // 企鹅应该怎么办？抛出运行时异常？
```

如果在 `Penguin::fly()` 内部抛出异常，说明你的系统在欺骗调用者——你打破了“所有鸟都能飞”的公共契约。代码能够通过编译，绝不代表设计是正确的。

**严谨的领域建模方案**是剥离出严格的能力接口：

```cpp
class Bird { ... }; // 不具备 fly 接口
class FlyingBird : public Bird {
public:
    virtual void fly();
};
class Penguin : public Bird { ... }; // 编译期彻底杜绝企鹅飞行的可能
```

## 避免遮掩继承而来的名称

在 C++ 的作用域解析规则中：**内层作用域的名称会无情遮掩外围作用域的所有同名函数，无论其参数类型或虚函数状态如何**。

考虑如下派生类重载陷阱：

```cpp
class Base {
public:
    virtual void mf1() = 0;
    virtual void mf1(int); // 重载版本
    virtual void mf2();
    void mf3();
    void mf3(double);      // 重载版本
};

class Derived : public Base {
public:
    virtual void mf1() override; // 仅重写了无参版本
    void mf3();                  // 仅定义了无参版本
    void mf4();
};

Derived d;
int x = 10;

d.mf1();   // 正常调用 Derived::mf1()
d.mf1(x);  // 编译报错！Base::mf1(int) 被完全遮掩！
d.mf3();   // 正常调用 Derived::mf3()
d.mf3(x);  // 编译报错！Base::mf3(double) 被完全遮掩！
```

编译器在搜索函数名时，一旦在 `Derived` 类的本地作用域内找到了名字为 `mf1` 的符号，**名称查找阶段立刻终止**！它绝不会跨越作用域去基类中继续寻找参数匹配的重载。

### 优雅破局：使用 using 声明式

若要让基类中所有重载的重名版本在派生类中重新可见，只需在派生类中使用 `using` 声明式：

```cpp
class Derived : public Base {
public:
    using Base::mf1; // 让 Base 内所有名为 mf1 的重载在 Derived 作用域中可见！
    using Base::mf3; // 让 Base 内所有名为 mf3 的重载在 Derived 作用域中可见！

    virtual void mf1() override;
    void mf3();
};

Derived d;
d.mf1(x); // 完美编译并调用 Base::mf1(int)！
```

## 区分接口继承和实现继承

在设计基类的成员函数时，C++ 提供了三种层次截然不同的继承模式：

1. **纯虚函数（Pure Virtual Function）**：`virtual void draw() const = 0;`
   - **目的**：仅要求派生类继承**函数接口**。派生类必须显式提供自己的实现，基类不做强制规定。
2. **简朴非纯虚函数（Impure Virtual Function）**：`virtual void error(const std::string& msg);`
   - **目的**：要求派生类继承**函数接口与一份缺省实现**。
   - **隐藏危险**：如果新增了一个特性特殊的派生类，但开发者忘记重写该虚函数，编译器会静默套用基类的默认实现，导致业务失控（例如让超音速飞机错误套用了普通民航机的降落算法）。
   - **防御手段**：将默认实现拆分为一个受保护的独立函数（如 `defaultFly()`），迫使派生类必须在自己的虚函数内显式决定是否调用它。
3. **非虚函数（Non-Virtual Function）**：`int objectID() const;`
   - **目的**：强制派生类继承**函数接口与一份强制性实现**。它代表了类继承体系中凌驾于一切特异性之上的**不变性（Invariants）**，任何派生类都绝不应当重新定义它！

## 考虑 virtual 函数以外的其他选择

虚函数并非实现多态与算法变动的唯一途径。过度依赖纯粹的虚函数重写，常常导致类层次臃肿，难以维护。

### 1. NVI 惯用法（Non-Virtual Interface / Template Method 模式）

NVI 的核心思想是：**让基类的公共接口为非虚函数，在内部调用私有的虚函数作为可插拔的算法钩子（Hooks）**。

<Archify src="./diagrams/nvi-template-method.sequence.json" />

```cpp
class GameCharacter {
public:
    int healthValue() const { // 公共非虚接口：构筑防御骨架
        // 步骤 1：事前环境准备（加锁、校验入参、记录审计日志）
        doPreamble();

        // 步骤 2：调用实际计算的私有虚函数钩子
        int retVal = doHealthValue();

        // 步骤 3：事后状态清理与不变量校验（解锁、校验合法范围）
        doPostscript(retVal);

        return retVal;
    }
private:
    virtual int doHealthValue() const {
        return 100; // 默认算法，派生类可选择性重写！
    }
};

class BossCharacter : public GameCharacter {
private:
    virtual int doHealthValue() const override {
        return 5000; // 定制大 Boss 的血量计算逻辑
    }
};
```

NVI 的巨大优势在于：基类对接口的调用时机、调用前后环境（如互斥锁的获取与释放、参数合法性守卫）拥有绝对控制权，派生类只需纯粹关注局部核心算法的定制。

### 2. 基于函数对象的 Strategy 模式

将算法完全从类继承体系中抽离，借助 `std::function` 在运行期动态组合：

```cpp
class GameCharacter;

using HealthCalcFunc = std::function<int(const GameCharacter&)>;

int defaultHealthCalc(const GameCharacter& gc);

class GameCharacter {
public:
    explicit GameCharacter(HealthCalcFunc hcf = defaultHealthCalc)
        : healthFunc(std::move(hcf)) {}

    int healthValue() const {
        return healthFunc(*this);
    }
private:
    HealthCalcFunc healthFunc; // 策略模式：运行时随时可被热替换
};
```

同一个角色类的不同实例，甚至可以在运行期动态更换掉扣血计算逻辑，彻底解除了代码与固定继承体系的硬编码耦合。

## 绝不重新定义继承而来的 non-virtual 函数

非虚函数是**静态绑定（Static Binding）**的。当通过指针或引用调用非虚函数时，调用哪个版本完全取决于该指针所声明的**静态类型（Static Type）**，与它底层实际指向什么对象毫无关系：

```cpp
class Base {
public:
    void mf(); // 非虚函数
};

class Derived : public Base {
public:
    void mf(); // 错误行为：重新定义了基类的非虚函数！
};

Derived d;
Base* pb = &d;
Derived* pd = &d;

pb->mf(); // 静态绑定：调用 Base::mf()！
pd->mf(); // 静态绑定：调用 Derived::mf()！
```

同一个对象 `d`，仅仅因为经由基类指针调用还是派生类指针调用，就展现出了完全分裂的两面派行为！这不仅违反了 public 继承的 "is-a" 契约，更在大型团队协作中制造了无法预估的逻辑死角。**只要一个函数是非虚函数，派生类就必须绝对尊重其继承而来的既定实现**。

## 绝不重新定义继承而来的缺省参数值

如果非虚函数不该被重新定义，那么带有默认参数的**虚函数**又该如何？

C++ 标准制定了一条极其反直觉的规则：**虚函数是动态绑定的（Dynamically Bound），但函数上的缺省参数值却是静态绑定的（Statically Bound）**！

```cpp
class Shape {
public:
    enum ShapeColor { Red, Green, Blue };
    virtual void draw(ShapeColor color = Red) const = 0; // 默认颜色：Red
};

class Rectangle : public Shape {
public:
    // 错误：派生类重新指定了不同的默认参数值！
    virtual void draw(ShapeColor color = Green) const override;
};

Shape* pr = new Rectangle();
pr->draw(); // 灾难降临：调用的究竟是什么颜色？
```

执行分析：

1. `draw` 是虚函数，动态绑定机制精确生效，在运行期正确调用了 `Rectangle::draw` 的函数体。
2. 然而默认参数值是**在编译期由指针的静态类型决定的**！静态类型是 `Shape*`，因此编译器提取出的默认参数是 `Shape::Red`！
3. 最终结果：你执行了 `Rectangle` 的绘制逻辑，但传入的颜色却是 `Base` 定义的 `Red`！

为了避免这种精神分裂式的陷阱，**绝不要重新定义继承而来的缺省参数值**。结合前面的 NVI 惯用法，将默认参数绑定在基类的非虚公共接口上，即可彻底杜绝这一隐患。

## 通过复合塑模出 "has-a" 或 "根据某物实现出"

所谓复合（Composition），是指在一个类中将另一个类作为自己的数据成员。

在应用领域建模中，复合代表 **"has-a"（有一个）** 的关系：

- 一个人（`Person`）“拥有一个”姓名（`Name`）和地址（`Address`）。

在纯技术实现中，复合代表 **"is-implemented-in-terms-of"（根据某物实现出）** 的关系：

- 很多初学者为了快速实现一个集合类 `Set`，直接让 `Set` public 继承自标准库的 `std::list`。
- 这是极其严重的错误！因为 `std::list` 允许包含大量重复元素，如果在 `Set` 上调用继承来的 `push_back`，就会破坏集合不含重复元素的数学不变量。
- 正确做法是通过复合：`Set` 内部持有一个 `std::list` 成员，并在其 `insert()` 函数中调用 `find()` 进行查重，再委托给底层的链表操作。

## 明智而审慎地使用 private 继承

如果两个类之间是 private 继承：

1. 编译器不会自动将派生类对象转换为基类对象（多态机制对外失效）。
2. 由基类继承而来的所有成员在派生类中全部变为 `private` 属性。

这说明：**private 继承纯粹是一种实现技术，在概念上意味着 "根据某物实现出"，它与面向对象所推崇的 "is-a" 没有任何关系**。

### 优选复合，审慎使用 private 继承

在 95% 的场景下，复合都比 private 继承更加简洁清晰，且能通过 PIMPL 防火墙降低编译依赖。只有在以下两种极端场景下，private 继承才具备不可替代的技术优势：

1. **需要访问基类的 protected 成员，或者需要重写基类的 virtual 函数**。
2. **空白基类最优化（Empty Base Optimization, EBO）**：在 C++ 中，即使一个类没有任何数据成员，单独为它实例化时其大小也必须至少占 1 字节以保证每个对象地址独立。而一旦该空白类被作为基类继承（Private 继承），编译器可以将它紧凑压缩，派生类的大小无需因此多增加任何字节偏移。

## 明智而审慎地使用多重继承（Multiple Inheritance）

多重继承（MI）最令人头痛的问题莫过于**菱形继承（Diamond Problem）**：

```text
       ┌───────────┐
       │   A (x)   │
       └─────┬─────┘
             │
      ┌──────┴──────┐
      ▼             ▼
┌───────────┐ ┌───────────┐
│     B     │ │     C     │
└─────┬─────┘ └─────┬─────┘
      │             │
      └──────┬──────┘
             ▼
       ┌───────────┐
       │     D     │
       └───────────┘
```

如果底层的 `D` 访问祖先 `A` 的成员变量 `x`，它究竟该走 `B` 路径还是 `C` 路径？默认情况下，`D` 内部会存在两份 `A` 的独立数据拷贝！

为了消除歧义，必须采用**虚继承（Virtual Inheritance）**：`class B : virtual public A`。但虚继承不是免费的午餐：

- 它会增加对象体积（需要额外的虚基类指针）。
- 访问虚基类成员需要跨越间接寻址指针，严重损耗执行速度。
- 最底层的派生类必须越过直接父类，承担起最顶层虚基类的显式初始化责任。

**多重继承的最佳实践**：将其用途严格局限于 **“Public 继承一个或多个纯抽象接口类（Interface Classes）+ Private 继承一个协助具体实现的工具类”**。远离复杂的数据菱形，保持接口契约的清晰纯正。
