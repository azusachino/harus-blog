Software design is fundamentally about establishing contracts between developers and machines. C++ offers immense expressive freedom, but poorly designed class interfaces create subtle assumptions, type ambiguities, and misuse hazards. The guiding objective of this chapter is straightforward: **design interfaces that are easy to use correctly and hard to use incorrectly**.

---

## Before you start

A class's public functions are a contract with everyone who calls them, and callers will find every way to misread it. Take a date constructor `Date(int month, int day, int year)`. Both `Date(3, 30, 1995)` and `Date(30, 3, 1995)` compile, and only one is a real date. This chapter is about designing declarations so the compiler rejects the wrong call, and about the choices that decide whether a function copies its arguments, returns a reference or returns a new object.

Read [chapter 03](/tech/series/effective-cpp/03.resource-management/) first; several items here build on smart pointers and on what copying costs.

Terms used in this chapter:

- **interface**: the functions and types a class exposes to its callers.
- **invariant**: a condition that must always hold for an object, such as "month is between 1 and 12".
- **pass by value**: the function receives a copy of the argument.
- **pass by reference-to-const**: the function receives the original object without copying it and promises not to change it, written `const T&`.
- **slicing**: copying a derived object into a base-class value, which throws away the derived part.
- **dangling reference**: a reference to an object that has already been destroyed.
- **encapsulation**: keeping data private so only a small set of functions can touch it.
- **swap**: exchanging the contents of two objects, ideally without throwing exceptions.

## Item 18: Make Interfaces Easy to Use Correctly and Hard to Use Incorrectly

Ideal interfaces act like keyed connectors: code that compiles is almost certainly correct; misuse is rejected immediately by the compiler.

### Enforcing Invariants with Strong Types

Consider a date constructor that accepts raw integers:

```cpp
class Date {
public:
    Date(int month, int day, int year); // Fragile design
};

Date d1(30, 3, 1995); // Ambiguous: March 30 or the 30th month?
Date d2(3, 40, 2020); // Day 40 is illegal, yet the compiler compiles without complaint
```

Introduce strong, domain-specific wrapper types to prevent positional mistakes at compile time:

```cpp
struct Day {
    explicit Day(int d) : val(d) {}
    int val;
};

struct Month {
    explicit Month(int m) : val(m) {}
    int val;
};

struct Year {
    explicit Year(int y) : val(y) {}
    int val;
};

class Date {
public:
    Date(const Month& m, const Day& d, const Year& y);
};

// Date d(Day(30), Month(3), Year(1995)); // Compile error: argument types mismatched!
Date d(Month(3), Day(30), Year(1995));   // Explicit, unambiguous, verified by compiler
```

### Consistency with Built-in Types

Unless a compelling reason dictates otherwise, user-defined types should behave consistently with built-in primitives. For example, `a * b` should never mutate `a` or `b`; `operator+` should return a new value rather than modifying operands in place. Preserving behavioral parity eliminates surprise and aligns with developer intuition.

### Eliminating Caller Resource Burden

Returning raw pointers forces callers to remember `delete` or guess whether to use `delete[]`. Modern interfaces encapsulate ownership in smart pointers:

```cpp
// Flawed: burdens caller with manual lifetime management
Investment* createInvestment();

// Idiomatic: interface explicitly defines exclusive ownership
std::unique_ptr<Investment> createInvestment();
```

## Item 19: Treat Class Design as Type Design

In C++, defining a new class introduces a new type into the language's type system. Class authors must approach design with the same scrutiny language implementers apply to built-in types:

1. **How should objects be created and destroyed?** Dictates constructor, destructor, and custom allocator design.
2. **How does initialization differ from assignment?** Distinguishes copy/move constructors from copy/move assignment operators.
3. **What does pass-by-value mean for the new type?** Defined by the copy and move constructors.
4. **What are the legal values and class invariants?** Determines error handling, bounds checking, and defensive preconditions.
5. **Does the new type fit into an inheritance hierarchy?** Dictates whether destructors must be `virtual`.
6. **What type conversions are permitted?** Determine whether single-argument constructors must be `explicit`.
7. **Which operators and functions make sense?** Distinguishes member functions from non-member functions.
8. **Which standard functions should be disallowed?** Mark unwanted operations as `= delete`.
9. **Who should have access to members?** Define strict encapsulation boundaries (`public`, `protected`, `private`, `friend`).
10. **What is the undocumented contract?** Guarantees regarding exception safety, thread safety, and resource invariants.
11. **How general is the type?** Should it be a concrete class or a generic class template?
12. **Is a new type truly necessary?** Could a type alias (`using`), standard container, or non-member function satisfy the requirement?

## Item 20: Prefer Pass-by-Reference-to-Const to Pass-by-Value

By default, C++ passes function arguments by value, copying arguments via their copy constructors:

```cpp
class Person {
public:
    Person();
    virtual ~Person();
private:
    std::string name;
    std::string address;
};

class Student : public Person {
public:
    Student();
    ~Student();
private:
    std::string schoolName;
    std::string schoolAddress;
};

bool validateStudent(Student s); // Pass-by-value: costly copy chain
```

Passing `Student` by value triggers:

- 1 `Student` copy constructor
- 1 `Person` base copy constructor
- 4 `std::string` copy constructors (heap allocations and deep buffer copies)
- 6 corresponding destructor executions on return!

Passing by reference-to-const eliminates this entire overhead:

```cpp
bool validateStudent(const Student& s); // Zero copy overhead; passes a single machine pointer
```

### Preventing Object Slicing

Pass-by-value causes **object slicing** when polymorphic objects are passed to base-class parameters:

```cpp
class Window {
public:
    std::string name() const;
    virtual void display() const;
};

class CircleWindow : public Window {
public:
    void display() const override;
};

void printNameAndDisplay(Window w) { // Pass-by-value: SLICING BUG!
    std::cout << w.name();
    w.display(); // ALWAYS calls Window::display(); derived behavior is sliced away!
}

CircleWindow cw;
printNameAndDisplay(cw);
```

When `cw` is passed by value, the compiler invokes `Window`'s copy constructor. The parameter `w` becomes a sliced base `Window` instance whose `vptr` points to `Window`'s virtual table, discarding `CircleWindow`'s overrides.

Passing via `const Window&` preserves runtime polymorphism:

```cpp
void printNameAndDisplay(const Window& w) {
    w.display(); // Dispatches dynamically to CircleWindow::display()
}
```

> **Exceptions**: For primitive types (`int`, `double`), standard iterators, and function objects, pass-by-value is preferred. These types are small (4–16 bytes) and map directly to CPU registers.

## Item 21: Don't Try to Return a Reference When You Must Return an Object

To avoid pass-by-value costs, developers sometimes mistakenly attempt to return references to objects that must be constructed inside the function:

```cpp
class Rational {
public:
    Rational(int numerator = 0, int denominator = 1);
private:
    int n, d;
    friend const Rational operator*(const Rational& lhs, const Rational& rhs);
};
```

Multiplying two rational numbers produces a mathematically distinct new value. Returning a reference introduces critical failures:

```cpp
// Anti-Pattern 1: Returning reference to a local stack object
const Rational& operator*(const Rational& lhs, const Rational& rhs) {
    Rational result(lhs.n * rhs.n, lhs.d * rhs.d);
    return result; // UNDEFINED BEHAVIOR: returns dangling reference to destroyed stack frame!
}

// Anti-Pattern 2: Allocating on heap and returning reference
const Rational& operator*(const Rational& lhs, const Rational& rhs) {
    Rational* result = new Rational(lhs.n * rhs.n, lhs.d * rhs.d);
    return *result; // Memory leak: callers cannot easily obtain the pointer to delete it
}

Rational w, x, y, z;
w = x * y * z; // Two heap allocations; zero opportunity for callers to invoke delete!
```

### Embracing Return Value Optimization (RVO)

When a function must return a newly created object, return it **by value**:

```cpp
inline const Rational operator*(const Rational& lhs, const Rational& rhs) {
    return Rational(lhs.n * rhs.n, lhs.d * rhs.d);
}
```

Compilers apply **Return Value Optimization (RVO)** to construct the returned object directly in the caller's storage. Since C++17 this is mandatory when you return a temporary (as above); eliding a named local (NRVO) is still optional. (Modern style also drops the top-level `const` from by-value returns, because it blocks moves; the book's `const Rational` return was meant to stop `(a * b) = c`.)

## Item 22: Declare Data Members Private

Declaring data members `private` provides essential encapsulation guarantees:

1. **Syntactic Consistency**: Callers access attributes consistently through member functions (`obj.length()`).
2. **Fine-Grained Access Control**: Authoring read-only, write-only, or read-write access is straightforward via tailored getters and setters.
3. **Class Invariant Enforcement**: Setters can validate ranges, trigger cache updates, enforce state transitions, and acquire synchronization locks.

> **Why `protected` is not more encapsulated than `public`**:
> Encapsulation is measured by how much code breaks when an implementation changes. Modifying a `public` member breaks all external client code. Modifying a `protected` member breaks all current and future derived classes across every codebase that inherits from it. In both cases, the maintenance burden is unbounded. Only `private` members provide true encapsulation.

## Item 23: Prefer Non-Member Non-Friend Functions to Member Functions

It might seem intuitive to place all related functionality inside a class as member functions. However, from an encapsulation perspective:

> The more code that can directly access an object's private data members, the less encapsulated that data is.

Consider clearing browser caches:

```cpp
class WebBrowser {
public:
    void clearCache();
    void clearHistory();
    void removeCookies();

    // Approach A: Member function
    void clearEverything();
};

// Approach B: Non-member non-friend function
void clearBrowser(WebBrowser& wb) {
    wb.clearCache();
    wb.clearHistory();
    wb.removeCookies();
}
```

Approach B (non-member non-friend) provides **superior encapsulation**: it cannot access private data members of `WebBrowser`, relying solely on the public interface. When private data structures change, non-member functions require zero maintenance.

Organize non-member helpers in the same namespace across separate header files:

```cpp
// webbrowser.h
namespace WebBrowserCore {
    class WebBrowser { /* Core interface */ };
}

// webbrowser_bookmarks.h
namespace WebBrowserCore {
    void bookmarkPage(WebBrowser& wb, const std::string& url);
}

// webbrowser_cookies.h
namespace WebBrowserCore {
    void clearCookies(WebBrowser& wb);
}
```

This pattern matches the standard library's architecture (e.g., `<vector>`, `<algorithm>`, `<numeric>`).

## Item 24: Declare Non-Member Functions When Type Conversions Should Apply to All Parameters

If a binary operator needs to support implicit type conversions on all operands (including the left operand), implement it as a non-member function:

```cpp
class Rational {
public:
    Rational(int numerator = 0, int denominator = 1); // Allows implicit conversion from int
    int numerator() const;
    int denominator() const;

    const Rational operator*(const Rational& rhs) const; // Member function version
};

Rational oneHalf(1, 2);
Rational result;

result = oneHalf * 2; // Compiles: translated to oneHalf.operator*(Rational(2))
// result = 2 * oneHalf; // COMPILE ERROR: translated to 2.operator*(oneHalf); int has no member operator*!
```

Implicit conversions only occur when arguments appear in the explicit parameter list. The left-hand caller (`this`) is never implicitly converted.

Declare symmetric arithmetic operators as non-member functions:

```cpp
const Rational operator*(const Rational& lhs, const Rational& rhs) {
    return Rational(lhs.numerator() * rhs.numerator(),
                    lhs.denominator() * rhs.denominator());
}

result = 2 * oneHalf; // Compiles cleanly: translated to operator*(Rational(2), oneHalf)
```

## Item 25: Consider Support for a Non-Throwing swap

Default `std::swap` performs one copy construction and two copy assignments (since C++11 it uses moves instead, which is cheap for types that implement them):

```cpp
template <typename T>
void swap(T& a, T& b) {
    T temp(a);
    a = b;
    b = temp;
}
```

For classes using the **PIMPL (Pointer to Implementation)** idiom:

```cpp
class WidgetImpl { /* ... heavy internal state ... */ };

class Widget {
public:
    void swap(Widget& other) noexcept {
        using std::swap;
        swap(pImpl, other.pImpl); // Only exchanges an 8-byte pointer!
    }
private:
    WidgetImpl* pImpl;
};
```

Default `std::swap` copies the entire internal representation needlessly. Customizing swap requires four steps:

1. Provide a `public noexcept` member `swap` that exchanges raw internal pointers.
2. Provide a non-member `swap` in the same namespace as your class that delegates to the member function.
3. For non-template classes, specialize `std::swap` in `namespace std`.
4. Call `swap` using Argument-Dependent Lookup (ADL):

```cpp
template <typename T>
void doSomething(T& obj1, T& obj2) {
    using std::swap;  // Make std::swap available as fallback
    swap(obj1, obj2); // ADL selects custom swap if available; falls back to std::swap
}
```

## Summary Checklist

| Guideline | Key Takeaway | Modern Practice |
| :--- | :--- | :--- |
| **Easy to Use, Hard to Misuse** | Introduce strong types; eliminate client resource duties | Strong types, `std::unique_ptr` factory returns |
| **Pass-by-Reference-to-Const** | Avoid deep copy construction chains and object slicing | `const&` for objects; by-value for primitives/iterators |
| **Return Objects by Value** | Never return references to local stack objects | Rely on Return Value Optimization (RVO/NRVO) |
| **Declare Data Members Private** | Protect class invariants; `protected` is not encapsulated | Encapsulate fields; provide explicit accessors |
| **Non-Member Non-Friend** | Maximizes encapsulation by decoupling from private fields | Namespace-partitioned helper headers |
| **Symmetric Conversions** | Use non-member functions when left operand needs conversion | Non-member operator overloads |
| **Non-Throwing Swap** | Provide pointer-swapping member and ADL non-member `swap` | `noexcept` swap for Copy-and-Swap idiom |
