如果说面向对象编程（OOP）通过运行期多态与虚表为 C++ 奠定了强大的抽象能力，那么模板（Templates）与泛型编程则将 C++ 的表现力推向了另一个维度：**在编译期完成类型推导、契约验证与代码生成，实现零运行时抽象开销（Zero-Cost Abstractions）**。本章深入剖析隐式接口、从属名称决议、编译期分发与代码膨胀控制等核心机制。

---

## 了解隐式接口和编译期多态

面向对象的世界围绕着**显式接口（Explicit Interfaces）**和**运行期多态（Runtime Polymorphism）**运转：

```cpp
// 面向对象风格
class Widget {
public:
    virtual ~Widget();
    virtual std::size_t size() const;
    virtual void normalize();
    void swap(Widget& other);
};

void doProcessing(Widget& w) {
    if (w.size() > 10 && w != someNastyWidget) {
        Widget temp(w);
        temp.normalize();
        temp.swap(w);
    }
}
```

在这里：

- 接口是显式的：以头文件中明确写出的函数签名（Signature）为准。
- 多态是运行期的：`w.normalize()` 调用哪个版本，完全取决于运行期 `w` 的虚表指针。

而在模板的世界中，一切被逆转为**隐式接口（Implicit Interfaces）**与**编译期多态（Compile-Time Polymorphism）**：

```cpp
// 模板泛型风格
template<typename T>
void doProcessing(T& w) {
    if (w.size() > 10 && w != someNastyWidget) {
        T temp(w);
        temp.normalize();
        temp.swap(w);
    }
}
```

在这里：

- **隐式接口**：`T` 根本不需要继承自任何特定的基类，它只需满足代码中出现的一组**有效表达式（Valid Expressions）**。例如 `w.size()` 必须返回一个能与 `10` 进行比较的类型；`w != someNastyWidget` 必须有重载的 `operator!=` 支持。
- **编译期多态**：`doProcessing` 针对不同的类型实参进行具现化（Instantiation）。函数调用通过重载决议和内联在编译期直接绑定，消除了虚表指针跳转的间接寻址开销。

## 了解 typename 的双重意义

在声明模板类型参数时，`class` 与 `typename` 完全等价：

```cpp
template<class T> class Widget;
template<typename T> class Widget; // 两者没有任何语义差异
```

但在处理模板内部的**嵌套从属类型名称（Nested Dependent Type Name）**时，`typename` 承担着无可替代的语法解析职责：

```cpp
template<typename C>
void print2nd(const C& container) {
    if (container.size() >= 2) {
        C::const_iterator iter = container.begin(); // 编译报错！
        ...
    }
}
```

### 编译器的解析困境

在编译器遇到 `C::const_iterator` 时，它尚不知道 `C` 的具体类型。假设某个恶意的程序员在全局写了如下特化：

```cpp
class SpecialContainer {
public:
    static int const_iterator; // 一个静态整数变量！
};
int iter;
```

那么 `C::const_iterator * iter;` 在语法上就会被解析为一个**相乘表达式**，而非**类型指针声明**！

为了消解这种二义性，C++ 制定了一条严格规则：**当解析到一个依赖于模板参数的嵌套从属名称时，编译器默认将其视为一个变量或值，而非类型**。如果你希望它被视为一个类型，必须在其紧邻的前方显式加上 `typename`：

```cpp
typename C::const_iterator iter = container.begin(); // 明确告知编译器这是一个类型名称
```

### 不可使用 typename 的例外位置

`typename` 仅用于指明嵌套从属类型名称，有两个位置**严禁出现**：

1. **基类列表（Base Class List）**：`template<typename T> class Derived : public Base<T>::Nested`（禁止在 `Base<T>::Nested` 前加 `typename`）。
2. **成员初值列中的基类标识符**：`Derived(int x) : Base<T>::Nested(x)`（同样禁止加 `typename`）。

## 学习处理来自 templatized base classes 内的名称

假设我们正在构建一个支持不同加密方式的消息发送系统：

```cpp
class MsgInfo { ... };

template<typename Company>
class MsgSender {
public:
    void sendClear(const MsgInfo& info);
    void sendSecret(const MsgInfo& info);
};

template<typename Company>
class LoggingMsgSender : public MsgSender<Company> {
public:
    void sendClearMsg(const MsgInfo& info) {
        // 记录发送日志...
        sendClear(info); // 编译报错！编译器声称找不到 sendClear 函数！
    }
};
```

为什么派生类明明白白继承了 `MsgSender<Company>`，编译器却视而不见？

### 模板全特化（Total Template Specialization）引发的警惕

编译器拒绝在泛型基类中搜索名称，是因为 C++ 允许模板被**全特化**。假设有人针对特定公司编写了一个不提供明文发送的特化版本：

```cpp
class CompanyZ { ... };

template<> // 全特化版本：没有提供 sendClear 函数！
class MsgSender<CompanyZ> {
public:
    void sendSecret(const MsgInfo& info);
};
```

当 `Company == CompanyZ` 时，`sendClear` 在基类中根本不存在！编译器在初次解析 `LoggingMsgSender` 模板定义时，深知基类未来可能被特化，因此默认**拒绝进入带有模板参数的基类中搜寻未修饰的名称**。

### 三种标准破局方法

1. **显式使用 `this->`**：

   ```cpp
   this->sendClear(info); // 告诉编译器推迟到具现化阶段再去解析
   ```

2. **使用 `using` 声明式**：

   ```cpp
   template<typename Company>
   class LoggingMsgSender : public MsgSender<Company> {
   public:
       using MsgSender<Company>::sendClear; // 明确将基类函数拉入当前作用域
       void sendClearMsg(const MsgInfo& info) {
           sendClear(info);
       }
   };
   ```

3. **显式指明基类作用域限定符**：

   ```cpp
   MsgSender<Company>::sendClear(info); // 但这会关闭虚函数多态分发能力
   ```

## 将与参数无关的代码抽离 templates

模板能大幅减少人工手写重复代码的劳作，但如果不加节制，它很容易在编译后产生成倍膨胀的目标二进制文件（Code Bloat）。

### 非类型模板参数（Non-type Template Parameters）引发的膨胀

考虑一个固定尺寸的矩阵模板类：

```cpp
template<typename T, std::size_t n>
class SquareMatrix {
public:
    void invert(); // 求逆矩阵
private:
    T data[n * n];
};

SquareMatrix<double, 5> sm1;
SquareMatrix<double, 10> sm2;
sm1.invert(); // 生成一份专门服务于 5x5 的机器码
sm2.invert(); // 生成一份专门服务于 10x10 的完全独立的机器码！
```

虽然 `sm1` 与 `sm2` 的元素类型完全相同，仅仅因为维度不同，编译器就会为 `invert()` 分别生成两套除了循环上限不同、核心算法完全雷同的汇编指令。

### 共用基类抽取共性

将与尺寸无关的共性算法抽离到一个不带尺寸参数的基类中，并以指针或参数传递维度信息：

```cpp
template<typename T>
class SquareMatrixBase {
protected:
    SquareMatrixBase(std::size_t n, T* pMem) : size(n), pData(pMem) {}
    void invert(); // 整个程序内仅具现化一份通用的矩阵求逆二进制代码！
private:
    std::size_t size;
    T* pData;
};

template<typename T, std::size_t n>
class SquareMatrix : private SquareMatrixBase<T> {
public:
    SquareMatrix() : SquareMatrixBase<T>(n, data) {}
    using SquareMatrixBase<T>::invert; // 内联调用基类统一实现
private:
    T data[n * n];
};
```

## 运用成员函数模板接受所有兼容类型

在面向对象中，派生类指针可以天然隐式转换为基类指针：

```cpp
class Top { ... };
class Middle : public Top { ... };
class Bottom : public Middle { ... };

Top* pt = new Bottom(); // 天然合法
```

然而，如果我们将这些类型放进模板智能指针中，`SmartPtr<Bottom>` 与 `SmartPtr<Top>` 在编译器眼中属于完全无关的两个独立类：

```cpp
template<typename T>
class SmartPtr {
public:
    explicit SmartPtr(T* realPtr);
};

SmartPtr<Top> pt = SmartPtr<Bottom>(new Bottom()); // 编译报错！无法类型转换
```

### 成员模板构造函数（Member Template Constructor）

解决这一问题的标准手段是引入**泛化拷贝构造函数（Generalized Copy Constructor）**：

```cpp
template<typename T>
class SmartPtr {
public:
    SmartPtr(T* realPtr = nullptr) : heldPtr(realPtr) {}

    // 成员函数模板：接受任意兼容的 SmartPtr<U>
    template<typename U>
    SmartPtr(const SmartPtr<U>& other)
        : heldPtr(other.get()) {} // 关键：如果 U* 无法隐式转换为 T*，此处编译报错！

    T* get() const { return heldPtr; }
private:
    T* heldPtr;
};
```

这不仅支持了跨层次的派生转换，同时将转换合法性审查巧妙委托给了底层的指针隐式转换规则：只有当 `U*` 能合法转换为 `T*` 时，代码才能编译通过。

> **提示**：声明了泛化拷贝构造函数并不会阻止编译器自动合成默认的普通拷贝构造函数。如果你需要接管类的纯原生拷贝行为，仍然必须显式声明非模板的 `SmartPtr(const SmartPtr& other);`。

## 需要类型转换时请为模板定义非成员函数

我们在第 04 章学过：若希望所有操作数（包括左操作数）都能参与隐式类型转换，应当使用非成员函数。

然而将这一原则应用到模板类时，会遇上更深层的阻碍：

```cpp
template<typename T>
class Rational {
public:
    Rational(const T& numerator = 0, const T& denominator = 1);
};

template<typename T>
const Rational<T> operator*(const Rational<T>& lhs, const Rational<T>& rhs);

Rational<int> oneHalf(1, 2);
Rational<int> result = oneHalf * 2; // 编译报错！
```

### 模板实参推导的盲区

在解析 `oneHalf * 2` 时，编译器试图推导 `operator*` 的模板参数 `T`：

- 第一个参数 `oneHalf` 告诉编译器：`T` 应该是 `int`。
- 第二个参数是字面量 `2`。然而**C++ 规定在模板实参推导（Template Argument Deduction）阶段，绝不考虑隐式类型转换**！编译器不会主动尝试把 `2` 构造为 `Rational<int>` 之后再去推导 `T`。因此推导当场失败。

### 友元内嵌定义法

化解此难题的标准范式，是将非成员函数直接以 `friend` 形式定义在 class template 内部：

```cpp
template<typename T>
class Rational {
public:
    Rational(const T& numerator = 0, const T& denominator = 1);

    // 在类模板内部声明并内联定义非成员友元函数！
    friend const Rational operator*(const Rational& lhs, const Rational& rhs) {
        return Rational(lhs.numerator() * rhs.numerator(),
                        lhs.denominator() * rhs.denominator());
    }
};
```

当 `Rational<int>` 被具现化时，一个以它为参数的普通非模板函数 `operator*(const Rational<int>&, const Rational<int>&)` 伴随着被自动生成。在面对普通函数重载时，隐式类型转换便能全速运转，完美通过编译。

## 请使用 traits classes 表现类型信息

在 STL 算法中，我们经常需要根据迭代器的能力类别（如只支持单步前移的输入迭代器，还是支持 `$O(1)$` 随机跳跃的随机访问迭代器）选择最高效的实现：

```cpp
template<typename IterT, typename DistT>
void advance(IterT& iter, DistT d) {
    if (/* iter 是随机访问迭代器 */) {
        iter += d; // O(1)
    } else {
        while (d--) ++iter; // O(n)
    }
}
```

如果在运行期通过 `if-else` 分支做判断，对于不支持 `+=` 操作符的单向迭代器，`iter += d;` 所在的代码行即使永远不会被执行，也会在**编译期直接报错**！必须在编译期根据类型完成分发。

### 迭代器萃取机（Iterator Traits）与标签分发（Tag Dispatch）

通过标准库定义的 5 种迭代器空标签类，并在迭代器内部或特化版本中暴露出类型标签：

```cpp
struct input_iterator_tag {};
struct bidirectional_iterator_tag : public input_iterator_tag {};
struct random_access_iterator_tag : public bidirectional_iterator_tag {};

// 重载实现一：随机访问迭代器
template<typename IterT, typename DistT>
void doAdvance(IterT& iter, DistT d, std::random_access_iterator_tag) {
    iter += d;
}

// 重载实现二：双向迭代器
template<typename IterT, typename DistT>
void doAdvance(IterT& iter, DistT d, std::bidirectional_iterator_tag) {
    if (d >= 0) { while (d--) ++iter; }
    else        { while (d++) --iter; }
}

// 主接口：利用 iterator_traits 提取标签类型并在编译期分发重载
template<typename IterT, typename DistT>
void advance(IterT& iter, DistT d) {
    doAdvance(iter, d, typename std::iterator_traits<IterT>::iterator_category());
}
```

Traits 技术通过“外部嵌套包装 + 偏特化”的手法，使得无论是自定义类的内部类型别名，还是原生裸指针（`T*` 偏特化为 `random_access_iterator_tag`），都能被统一萃取出标准化的元数据信息。

> 在现代 C++17/20 中，`if constexpr` 与 `Concepts`（概念）进一步革新了这一范式，直接书写 `if constexpr (std::is_same_v<...>)` 或使用约束模板，即可免去繁重的 Tag 重载样板代码。
