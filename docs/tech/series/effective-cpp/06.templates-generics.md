Where Object-Oriented Programming (OOP) provides runtime abstraction through virtual tables and dynamic dispatch, Templates and Generic Programming introduce an orthogonal dimension: **executing type deduction, contract verification, and code synthesis at compile time, achieving zero-cost runtime abstractions**. This chapter explores implicit interfaces, dependent name lookup, code bloat mitigation, and traits-based type introspection.

## Item 41: Understand Implicit Interfaces and Compile-Time Polymorphism

Object-oriented programming revolves around **explicit interfaces** and **runtime polymorphism**:

```cpp
// Object-Oriented Paradigm
class Widget {
public:
    virtual ~Widget();
    virtual std::size_t size() const;
    virtual void normalize();
    void swap(Widget& other);
};

void doProcessing(Widget& w) {
    if (w.size() > 10 && w != someNastyWidget) {
        Widget temp(w);
        temp.normalize();
        temp.swap(w);
    }
}
```

In OOP:

- The interface is **explicit**: defined concretely by method signatures in header files.
- Polymorphism is **runtime-bound**: the implementation called by `w.normalize()` depends on `w`'s dynamic virtual table pointer (`vptr`).

In the template world, these concepts invert to **implicit interfaces** and **compile-time polymorphism**:

```cpp
// Template Generic Paradigm
template <typename T>
void doProcessing(T& w) {
    if (w.size() > 10 && w != someNastyWidget) {
        T temp(w);
        temp.normalize();
        temp.swap(w);
    }
}
```

In Generic Programming:

- **Implicit Interface**: `T` is not required to inherit from a common base class. It must only satisfy a set of **valid expressions** (e.g., `w.size()` must return an object comparable with `int`, and `operator!=` must be supported).
- **Compile-Time Polymorphism**: Instantiating `doProcessing<Widget>` or `doProcessing<SpecialWidget>` produces concrete, specialized functions at compile time. Static resolution removes virtual dispatch and lets the compiler inline the calls.

## Item 42: Understand the Two Meanings of typename

In template parameter declarations, `class` and `typename` are semantically identical:

```cpp
template <class T> class Widget;
template <typename T> class Widget; // Exactly equivalent
```

However, when qualifying **nested dependent type names**, `typename` resolves a critical parsing ambiguity:

```cpp
template <typename C>
void print2nd(const C& container) {
    if (container.size() >= 2) {
        // C::const_iterator iter = container.begin(); // COMPILE ERROR!
        typename C::const_iterator iter = container.begin(); // Required!
        // ...
    }
}
```

### The Compiler's Parsing Dilemma

When the compiler parses `C::const_iterator`, it does not yet know the concrete type of `C`. A developer could write an adversarial specialization:

```cpp
class SpecialContainer {
public:
    static int const_iterator; // A static data member!
};
int iter;
```

If `C` were `SpecialContainer`, then `C::const_iterator * iter;` would be a **multiplication expression**, not a **pointer variable declaration**!

To resolve this ambiguity, C++ establishes a fundamental parsing rule: **any nested dependent name is assumed to denote a value or member variable, NOT a type, unless preceded explicitly by `typename`**.

### Exceptions Where `typename` is Prohibited

`typename` must **never** precede a nested dependent type name in two specific contexts:

1. **The Base Class List**:

   ```cpp
   template <typename T>
   class Derived : public Base<T>::Nested { // Do NOT add typename here!
   ```

2. **The Base Class Identifier in Member Initialization Lists**:

   ```cpp
   Derived(int x) : Base<T>::Nested(x) { // Do NOT add typename here!
   ```

## Item 43: Know How to Access Names in Templatized Base Classes

Consider a messaging hierarchy parameterized by company configuration:

```cpp
class MsgInfo { /* ... */ };

template <typename Company>
class MsgSender {
public:
    void sendClear(const MsgInfo& info);
    void sendSecret(const MsgInfo& info);
};

template <typename Company>
class LoggingMsgSender : public MsgSender<Company> {
public:
    void sendClearMsg(const MsgInfo& info) {
        // Log sending action...
        sendClear(info); // COMPILE ERROR: compiler cannot find sendClear!
    }
};
```

Even though `LoggingMsgSender` inherits from `MsgSender<Company>`, the compiler rejects unqualified calls to `sendClear`.

### The Threat of Total Template Specialization

Compilers refuse to look inside templatized base classes because C++ permits **total template specialization**. A developer might specialize `MsgSender` for an insecure company:

```cpp
class InsecureCompany {};

template <> // Total specialization: Omits sendClear entirely!
class MsgSender<InsecureCompany> {
public:
    void sendSecret(const MsgInfo& info);
};
```

If `Company == InsecureCompany`, `sendClear` does not exist in the base class. Because the primary template definition cannot know whether future specializations omit members, the compiler **refuses to search templatized base classes for unqualified names**.

### Three Standard Solutions

```cpp
template <typename Company>
class LoggingMsgSender : public MsgSender<Company> {
public:
    // Solution 1: Use this-> to defer lookup to instantiation time
    void sendClearMsg1(const MsgInfo& info) {
        this->sendClear(info); // Idiomatic and clear
    }

    // Solution 2: Bring the name into scope via using declaration
    using MsgSender<Company>::sendClear;
    void sendClearMsg2(const MsgInfo& info) {
        sendClear(info); // Unqualified name lookup now succeeds
    }

    // Solution 3: Explicit scope resolution (disables virtual dispatch)
    void sendClearMsg3(const MsgInfo& info) {
        MsgSender<Company>::sendClear(info);
    }
};
```

## Item 44: Factor Parameter-Independent Code Out of Templates

Templates automate code generation, but unconstrained instantiations trigger **binary code bloat**.

### Code Bloat from Non-Type Template Parameters

Consider a fixed-dimension matrix template:

```cpp
template <typename T, std::size_t n>
class SquareMatrix {
public:
    void invert(); // Inverts an n x n matrix
private:
    T data[n * n];
};

SquareMatrix<double, 5> sm1;
SquareMatrix<double, 10> sm2;

sm1.invert(); // Generates machine code for 5x5 inversion
sm2.invert(); // Generates identical algorithm for 10x10 inversion!
```

Even though both matrices hold `double`, differences in the non-type parameter `n` force the compiler to synthesize distinct machine code copies for `invert()`.

### Factoring into Size-Agnostic Base Classes

Move dimension-independent algorithmic logic into a common base class:

```cpp
template <typename T>
class SquareMatrixBase {
protected:
    SquareMatrixBase(std::size_t n, T* pMem) : size(n), pData(pMem) {}
    void invert(); // Shared binary code generated ONCE for all dimensions of type T!

private:
    std::size_t size;
    T* pData;
};

template <typename T, std::size_t n>
class SquareMatrix : private SquareMatrixBase<T> {
public:
    SquareMatrix() : SquareMatrixBase<T>(n, data) {}
    using SquareMatrixBase<T>::invert; // Forward to shared base implementation

private:
    T data[n * n];
};
```

## Item 45: Use Member Function Templates to Accept "All Compatible Types"

In OOP, a pointer to a derived class converts implicitly to a base class pointer:

```cpp
class Top {};
class Middle : public Top {};
class Bottom : public Middle {};

Top* pt = new Bottom(); // Valid implicit conversion
```

However, template instantiations are distinct types. By default, `SmartPtr<Bottom>` cannot convert to `SmartPtr<Top>`:

```cpp
template <typename T>
class SmartPtr {
public:
    explicit SmartPtr(T* realPtr = nullptr);
};

// SmartPtr<Top> pt = SmartPtr<Bottom>(new Bottom()); // COMPILE ERROR!
```

### Generalized Copy Constructors

Introduce a member function template to support conversions across compatible type instantiations:

```cpp
template <typename T>
class SmartPtr {
public:
    explicit SmartPtr(T* realPtr = nullptr) : heldPtr(realPtr) {}

    // Generalized copy constructor
    template <typename U>
    SmartPtr(const SmartPtr<U>& other)
        : heldPtr(other.get()) {} // Compiles ONLY if U* implicitly converts to T*!

    T* get() const noexcept { return heldPtr; }

private:
    T* heldPtr;
};
```

This generalized constructor automatically enforces type compatibility: attempting to convert `SmartPtr<Top>` to `SmartPtr<Bottom>` fails at compile time because raw `Top*` cannot convert to `Bottom*`.

> **Note**: A generalized copy constructor does not suppress the compiler-generated default copy constructor. If custom copy behavior is required between identical types (`SmartPtr<T>` to `SmartPtr<T>`), declare an explicit non-template copy constructor.

## Item 46: Define Non-Member Functions Inside Templates When Type Conversions Are Desired

In Item 24, we established that symmetric operators should be non-member functions to support implicit conversions on all arguments. Applying this to class templates encounters template argument deduction limits:

```cpp
template <typename T>
class Rational {
public:
    Rational(const T& numerator = 0, const T& denominator = 1);
};

template <typename T>
const Rational<T> operator*(const Rational<T>& lhs, const Rational<T>& rhs);

Rational<int> oneHalf(1, 2);
// Rational<int> result = oneHalf * 2; // COMPILE ERROR!
```

### The Deduction Blind Spot

During `oneHalf * 2`, the compiler deduces `T` for `operator*`:

- `lhs` (`oneHalf`) indicates `T` is `int`.
- `rhs` is literal `2`. However, **C++ template argument deduction never considers implicit type conversions**. The compiler will not construct a `Rational<int>` from `2` during deduction, causing resolution to fail.

### In-Class Friend Definitions

Define the non-member function directly inside the class template as a `friend`:

```cpp
template <typename T>
class Rational {
public:
    Rational(const T& numerator = 0, const T& denominator = 1);

    // In-class inline friend definition
    friend const Rational operator*(const Rational& lhs, const Rational& rhs) {
        return Rational(lhs.numerator() * rhs.numerator(),
                        lhs.denominator() * rhs.denominator());
    }
};
```

When `Rational<int>` is instantiated, the compiler synthesizes a concrete non-template function `operator*(const Rational<int>&, const Rational<int>&)`. Because it is an ordinary function rather than a template requiring deduction, implicit conversions on arguments succeed seamlessly.

## Item 47: Use Traits Classes for Information About Types

In generic algorithms, implementation strategies often depend on type capabilities (e.g., advancing a single-pass input iterator versus an $O(1)$ random-access iterator):

```cpp
template <typename IterT, typename DistT>
void advance(IterT& iter, DistT d) {
    // If evaluated with a runtime if-else, iter += d will FAIL TO COMPILE
    // for iterators that lack operator+= (such as std::list::iterator)!
}
```

Code for all branches must compile, even if a branch is never executed at runtime. Compile-time branching requires **Traits Classes** and **Tag Dispatch**:

```cpp
// 1. Tag dispatch hierarchy in <iterator> (these live in namespace std)
struct input_iterator_tag {};
struct output_iterator_tag {};
struct forward_iterator_tag : public input_iterator_tag {};
struct bidirectional_iterator_tag : public forward_iterator_tag {};
struct random_access_iterator_tag : public bidirectional_iterator_tag {};

// 2. Overload for random-access iterators (O(1))
template <typename IterT, typename DistT>
void doAdvance(IterT& iter, DistT d, std::random_access_iterator_tag) {
    iter += d;
}

// 3. Overload for bidirectional iterators (O(n), can move backward)
template <typename IterT, typename DistT>
void doAdvance(IterT& iter, DistT d, std::bidirectional_iterator_tag) {
    if (d >= 0) { while (d--) ++iter; }
    else        { while (d++) --iter; }
}

// 3b. Overload for input and forward iterators (O(n), forward only)
template <typename IterT, typename DistT>
void doAdvance(IterT& iter, DistT d, std::input_iterator_tag) {
    if (d < 0) throw std::out_of_range("negative distance");
    while (d--) ++iter;
}

// 4. Primary interface using std::iterator_traits
template <typename IterT, typename DistT>
void advance(IterT& iter, DistT d) {
    doAdvance(iter, d, typename std::iterator_traits<IterT>::iterator_category());
}
```

Through template specialization, `std::iterator_traits<T*>` maps raw pointers to `random_access_iterator_tag`, ensuring primitive arrays and smart iterators work uniformly.

In modern C++17 and C++20, `if constexpr` and `Concepts` simplify this pattern:

```cpp
template <typename IterT, typename DistT>
void advanceModern(IterT& iter, DistT d) {
    using Category = typename std::iterator_traits<IterT>::iterator_category;
    if constexpr (std::is_base_of_v<std::random_access_iterator_tag, Category>) {
        iter += d;
    } else if constexpr (std::is_base_of_v<std::bidirectional_iterator_tag, Category>) {
        if (d >= 0) while (d--) ++iter;
        else while (d++) --iter;
    } else {
        while (d--) ++iter; // input/forward iterators only move forward
    }
}
```

## Item 48: Be Aware of Template Metaprogramming

**Template Metaprogramming (TMP)** is the process of writing template-based C++ programs that execute inside the compiler during compilation rather than at runtime. Once TMP evaluation finishes, the resulting concrete C++ source code is compiled into machine instructions with zero runtime computation overhead.

### 1. How TMP Shifts Work from Runtime to Compile Time

Because C++ templates are Turing-complete, loops in classic TMP are expressed via **recursive template instantiation**, and branches are expressed via **template specialization**:

```cpp
// Classic C++98/03 TMP: Compile-time factorial via template recursion
template <unsigned n>
struct Factorial {
    enum { value = n * Factorial<n - 1>::value };
};

// Base case: explicit full specialization terminates recursion at n = 0
template <>
struct Factorial<0> {
    enum { value = 1 };
};

int main() {
    // Evaluated completely during compilation; emits immediate constant 120 in assembly
    constexpr int f5 = Factorial<5>::value;
    static_assert(f5 == 120);
}
```

### 2. Core Engineering Use Cases for TMP

1. **Ensuring Dimensional & Type Correctness**: In scientific and financial engines, encoding physical units (mass, length, time) as template parameters guarantees that adding a velocity to an acceleration fails at compile time rather than corrupting a simulation at runtime.
2. **Optimizing Matrix & Expression Templates**: Libraries like Eigen use **Expression Templates** so that an expression like `Matrix result = A + B + C;` does not allocate two temporary matrices on the heap; instead, TMP fuses the chained `operator+` proxies into a single cache-friendly loop at compile time.
3. **Generative Custom Design Patterns**: Policy-based design and the Curiously Recurring Template Pattern (`class Derived : public Base<Derived>`) achieve static polymorphism without `vptr` / `vtable` indirection.

### 3. Modern C++ Evolution: From Recursive Templates to `constexpr` and `consteval`

While classic TMP relies on recursive `struct` instantiations (which slow compilation and produce verbose diagnostics), modern C++14/17/20 replaces value-level TMP with `constexpr` and `consteval` functions while retaining `<type_traits>` and `concept` constraints for type-level metaprogramming:

```cpp
// C++20 consteval: Guaranteed compile-time evaluation with clean imperative syntax
consteval unsigned factorial(unsigned n) {
    unsigned result = 1;
    for (unsigned i = 2; i <= n; ++i) {
        result *= i;
    }
    return result;
}

static_assert(factorial(5) == 120);
```

## Summary Checklist

| :--- | :--- | :--- |
| **Implicit Interfaces** | Rely on valid expressions rather than explicit inheritance | C++20 Concepts (`std::integral`, `std::ranges`) |
| **Dependent Names** | Precede nested dependent type names with `typename` | `typename` mandatory; relaxed in C++20 `using` aliases |
| **Templatized Bases** | Use `this->` or `using` declarations to access base members | `this->member` or `using Base<T>::member;` |
| **Mitigate Bloat** | Factor parameter-independent code into common base classes | Non-templated or type-erased base wrappers |
| **Universal Converters**| Use member function templates for generalized copying | Generic copy/move constructors constrained by SFINAE/Concepts |
| **In-Class Friends** | Define non-member operators inside templates for implicit conversions | Friend function definitions within class template bodies |
| **Type Introspection** | Extract metadata via traits classes and tag dispatch | `std::iterator_traits`, `if constexpr`, C++20 Concepts |
| **Template Metaprogramming** | Shift invariants, unit checks, and loop fusion to compile time | `constexpr`, `consteval`, `<type_traits>`, Expression Templates |
