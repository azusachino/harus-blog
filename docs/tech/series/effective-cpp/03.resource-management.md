In C++, a "resource" is any entity that must be released back to the operating system after acquisition. Dynamic heap memory is only the most obvious example; file descriptors, mutex locks, database connections, network sockets, thread pools, and GPU context handles are equally critical.

Relying on manual cleanup via explicit `delete` or `close` statements is the leading cause of memory leaks and resource starvation in production systems. The deterministic C++ solution is **RAII (Resource Acquisition Is Initialization)**.

---

## Before you start

Anything you must give back after taking it is a resource: heap memory, an open file, a lock. The usual bug is forgetting to give it back on some path. You write `FILE* f = fopen(...)`, process the file, call `fclose(f)` at the end, and then someone adds an early `return` in the middle. The file stays open. C++ has a guarantee that fixes this: when a local object goes out of scope, its destructor runs, whether the function returned normally, returned early or threw an exception. Put the cleanup in a destructor and it can no longer be skipped. This chapter shows that idea and the standard-library classes built on it.

You should have read [chapter 02](/tech/series/effective-cpp/02.construct-destruct-assign/), because it explains destructors and what copying an object does.

Terms used in this chapter:

- **resource**: anything acquired that must later be released, such as memory, a file descriptor, a mutex or a socket.
- **RAII**: Resource Acquisition Is Initialization; acquire the resource in a constructor and release it in the destructor.
- **smart pointer**: an object that behaves like a pointer and releases what it points to automatically.
- **`std::unique_ptr`**: a smart pointer with a single owner; it cannot be copied, only moved.
- **`std::shared_ptr`**: a smart pointer that counts its owners and frees the object when the last one goes away.
- **custom deleter**: a function you give a smart pointer to say how to release the resource, for example `fclose` instead of `delete`.
- **raw pointer**: an ordinary `T*` with no ownership logic.
- **`new[]` / `delete[]`**: the array forms of allocation and release; they must be used as a matched pair.

## Item 13: Use Objects to Manage Resources (RAII)

Consider this common resource leak pattern:

```cpp
void processInvestment() {
    Investment* pInv = createInvestment(); // Factory function allocating on heap

    doSomethingRisky(); // If this throws an exception or returns early...

    delete pInv; // NEVER REACHED: permanent resource leak!
}
```

Even without an explicit early `return`, premature `goto`, `break`, or an unhandled exception thrown from a sub-operation will cause control flow to bypass `delete`, leaving the allocated memory orphaned.

### The Two Pillars of RAII

1. **Resources are acquired and immediately transferred to managing objects**: The lifecycle of the acquired resource is bound directly to the lifetime of a stack-allocated managing object. Acquisition happens in the constructor.
2. **Managing objects use destructors to guarantee release**: Regardless of how control leaves a scope—whether via normal return, `break`, or exception stack unwinding—C++ guarantees that destructors for all fully constructed stack objects execute automatically.

### From auto_ptr to Modern Smart Pointers

In C++98, `std::auto_ptr` was introduced as an early RAII smart pointer. However, without rvalue references and move semantics, `auto_ptr` attempted to emulate unique ownership by hijacking the copy constructor:

```cpp
// Flawed C++98 auto_ptr semantics:
std::auto_ptr<Investment> pInv1(createInvestment());
std::auto_ptr<Investment> pInv2(pInv1); // Copies transfer ownership; pInv1 silently becomes nullptr!
pInv1->someMethod();                   // Segmentation fault at runtime!
```

Because copying stripped the source pointer, `auto_ptr` could not be stored safely in STL containers. It was deprecated in C++11 and removed in C++17.

Modern C++ provides dedicated, standardized smart pointers:

- **`std::unique_ptr` (Exclusive Ownership)**: Copying is disabled (`= delete`); ownership can only be transferred via explicit `std::move`. With the default deleter there is no runtime overhead and the object is the size of a raw pointer.
- **`std::shared_ptr` (Shared Ownership)**: Implements strong reference counting via a thread-safe control block. The managed resource is released when the last `shared_ptr` pointing to it is destroyed.
- **`std::weak_ptr` (Non-Owning Observer)**: Observes an object managed by `shared_ptr` without incrementing its strong reference count, preventing circular reference memory leaks.

```cpp
// Modern C++ RAII with unique_ptr
void processInvestmentModern() {
    std::unique_ptr<Investment> pInv = createInvestmentUnique();
    doSomethingRisky();
    // Guaranteed automatic cleanup when pInv leaves scope
}
```

## Item 14: Think Carefully About Copying Behavior in Resource-Managing Classes

Not all resources fit naturally into generic smart pointers. When authoring custom RAII wrappers for C libraries or operating system handles, copying semantics must be defined deliberately:

```cpp
class Lock {
public:
    explicit Lock(std::mutex* pm) : mutexPtr(pm) {
        mutexPtr->lock(); // Acquire resource
    }
    ~Lock() {
        mutexPtr->unlock(); // Release resource on scope exit
    }
private:
    std::mutex* mutexPtr;
};

std::mutex m;
Lock m1(&m);
// Lock m2(m1); // What would copying a lock mean? Mutexes cannot be cloned!
```

Four strategies address copying in custom RAII classes:

### 1. Prohibit Copying

For resources that model exclusive states (e.g., locks or unique hardware ports), prohibit copying entirely:

```cpp
class Lock {
public:
    explicit Lock(std::mutex* pm) : mutexPtr(pm) { mutexPtr->lock(); }
    ~Lock() { mutexPtr->unlock(); }

    Lock(const Lock&) = delete;
    Lock& operator=(const Lock&) = delete;
private:
    std::mutex* mutexPtr;
};
```

### 2. Reference-Count the Underlying Resource

If multiple objects can safely share a resource until the final reference expires, wrap the raw handle in a `std::shared_ptr` configured with a **custom deleter**:

```cpp
class SharedLock {
public:
    explicit SharedLock(std::mutex* pm)
        : mutexPtr(pm, [](std::mutex* m) { m->unlock(); }) {
        pm->lock();
    }
private:
    std::shared_ptr<std::mutex> mutexPtr; // When refcount drops to 0, lambda unlocks mutex
};
```

### 3. Deep-Copy the Underlying Resource

Create a new, independent replica of the underlying resource (e.g., duplicating a bitmap buffer or cloning a socket descriptor).

### 4. Transfer Ownership (Move Semantics)

Provide move constructors and move assignment operators that transfer the raw handle to the target object while resetting the source handle to an empty state.

## Item 15: Provide Access to Raw Resources in Resource-Managing Classes

While RAII wrappers encapsulate low-level details, real-world systems interact with legacy C APIs and system libraries that expect raw pointers or handles:

```cpp
int daysHeld(const Investment* pi); // Legacy C-style API expecting raw pointer

std::shared_ptr<Investment> pInv = std::make_shared<Investment>();
// int days = daysHeld(pInv); // Compile error: shared_ptr does not implicitly match raw pointer
```

Resource-managing classes should provide access to their underlying raw resource through explicit or implicit conversions.

### Explicit Access: Safety First

Standard smart pointers provide explicit member functions (`.get()`):

```cpp
int days = daysHeld(pInv.get()); // Explicit, unambiguous, clear intent
```

### Implicit Access: Convenience for Tightly-Bound Types

For lightweight wrappers like font handles or color descriptors, explicit calls can add unnecessary friction:

```cpp
using FontHandle = void*;
void changeFontSize(FontHandle fh, int newSize);

class Font {
public:
    explicit Font(FontHandle fh) : handle(fh) {}
    ~Font() { releaseFont(handle); }

    // Implicit conversion operator to raw handle
    operator FontHandle() const noexcept { return handle; }

    FontHandle get() const noexcept { return handle; } // Explicit accessor

private:
    FontHandle handle;
};

Font f(getFont());
changeFontSize(f, 16); // Implicit conversion: clean and idiomatic
```

> **Tradeoff**: Implicit conversions risk unintentional copying of raw handles, which can outlive the owning RAII wrapper and result in dangling pointers. Prefer explicit `.get()` unless interfacing frequently with C APIs.

## Item 16: Use the Same Form in Corresponding Uses of new and delete

In C++, single-object allocation and array allocation employ completely different memory representations:

```cpp
std::string* strPtr = new std::string;
std::string* strArray = new std::string[100];

delete strPtr;     // Single-object delete
delete[] strArray; // Array delete[] MUST match new[]
```

### The Array Size Cookie

- `new T`: Allocates memory for a single `T` and invokes `T`'s constructor once.
- `new T[N]`: Allocates memory for $N$ instances of `T`, records an internal **array size cookie** preceding the first element to track element count, and calls the constructor $N$ times.

If you invoke single-object `delete strArray` on an array:

The behavior is undefined. Typically:

1. The runtime treats the address as a single object, calling the destructor for only element 0. The remaining 99 objects are never destroyed, leaking internal resources.
2. The memory deallocator is handed an address that is not the start of the allocation (because of the cookie), which can corrupt the heap.

```cpp
// Typedef Array Anti-Pattern:
typedef std::string AddressLines[4];

// Risky: 'pal' points to an array, but the typedef hides it
std::string* pal = new AddressLines; // new on an array typedef yields std::string*
// delete pal;   // BUG: undefined behavior! Requires delete[] pal
delete[] pal; // Required, but easily overlooked

// Idiomatic Modern C++:
std::array<std::string, 4> lines; // Stack-allocated, zero heap overhead
std::vector<std::string> dynamicLines(4); // Managed dynamically, safe deletion
```

## Item 17: Store newed Objects in Smart Pointers in Standalone Statements

Consider this multi-argument function call:

```cpp
int priority();
void processWidget(std::shared_ptr<Widget> pw, int priority);

// Vulnerable to exception leaks prior to C++17!
processWidget(std::shared_ptr<Widget>(new Widget), priority());
```

### Parameter Evaluation Order Hazards

Prior to C++17, the C++ standard did not define the evaluation order of function arguments. A compiler could interleave operations as follows:

1. Execute `new Widget`.
2. Call `priority()`.
3. Construct `std::shared_ptr<Widget>`.

If `priority()` throws an exception in step 2:

- The memory allocated by `new Widget` in step 1 has not yet been encapsulated inside the `std::shared_ptr`.
- The exception unwinds the stack, completely orphaning the newly allocated `Widget` and causing a memory leak.

### Modern Solution: `std::make_unique` and `std::make_shared`

The book's fix is to put the `new` in a standalone statement, so no other argument can run between the allocation and the smart pointer's construction:

```cpp
std::shared_ptr<Widget> pw(new Widget);
processWidget(pw, priority());
```

In modern code, use factory functions instead:

```cpp
// Modern C++ Best Practice:
processWidget(std::make_shared<Widget>(), priority());
```

`std::make_shared` provides three major benefits:

1. **Exception Safety**: Allocation and control block initialization are atomic with respect to other function arguments.
2. **Single Allocation Optimization**: Combines the managed object and the reference-count control block into a single contiguous heap allocation, reducing `malloc` overhead and improving CPU cache locality.
3. **Clean Syntax**: Avoids repeating type names (`std::make_shared<Widget>()` vs `std::shared_ptr<Widget>(new Widget)`).

## Summary Checklist

| Principle | Guideline | Modern Idiom |
| :--- | :--- | :--- |
| **RAII Management** | Bind resources to stack object lifetimes | `std::unique_ptr`, `std::shared_ptr` |
| **Copying Policies** | Explicitly choose: prohibit, reference count, deep copy, or move | `= delete`, custom deleter lambdas |
| **Raw Handle Access** | Provide `.get()` for interoperability with legacy C APIs | `.get()` for explicit access; implicit conversions only for lightweight types |
| **Matching new / delete** | Pair `new` with `delete`, and `new[]` with `delete[]` | Avoid raw dynamic arrays; use `std::vector` or `std::array` |
| **Atomic Smart Pointer Creation**| Never pass raw `new` inside function arguments | `std::make_unique` (C++14), `std::make_shared` (C++11) |
