Object construction, destruction, and assignment form the foundational lifecycle backbone of C++ systems. Custom classes frequently interact with functions synthesized implicitly by the compiler. Without a rigorous understanding of these silent mechanics, projects encounter silent memory leaks, partial destruction, slicing bugs, and runtime termination.

---

## Item 5: Know What Functions C++ Silently Writes and Calls

When an empty class is declared in C++:

```cpp
class Empty {};
```

The compiler will automatically synthesize four inline, public special member functions on demand:

1. **Default Constructor**: Synthesized only if no constructors are declared explicitly.
2. **Copy Constructor**: Performs memberwise copy construction of non-static data members.
3. **Copy Assignment Operator (`operator=`)**: Performs memberwise copy assignment.
4. **Destructor**: Non-virtual by default (unless inheriting from a base class with a virtual destructor).

In C++11 and later, the compiler may also synthesize **Move Constructor** and **Move Assignment Operator** if no custom copy operations, move operations, or destructors are declared (the Rule of Zero/Five).

```cpp
class Empty {
public:
    Empty() { /* ... */ }                            // Default constructor
    Empty(const Empty& rhs) { /* ... */ }            // Copy constructor
    Empty(Empty&& rhs) noexcept { /* ... */ }        // Move constructor (C++11)
    Empty& operator=(const Empty& rhs) { /* ... */ } // Copy assignment
    Empty& operator=(Empty&& rhs) noexcept { /* ... */} // Move assignment (C++11)
    ~Empty() { /* ... */ }                           // Destructor
};
```

### When Compilers Refuse to Synthesize Copy Assignment

The compiler refuses to synthesize `operator=` if doing so would violate language invariants:

```cpp
template <class T>
class NamedObject {
public:
    NamedObject(std::string& name, const T& value)
        : nameValue(name), objValue(value) {}

private:
    std::string& nameValue; // Reference member: cannot be reseated!
    const T objValue;       // Const member: cannot be reassigned!
};

std::string newDog("Persephone");
std::string oldDog("Satchmo");
NamedObject<int> p(newDog, 2);
NamedObject<int> s(oldDog, 36);

// p = s; // COMPILE ERROR: compiler refuses to generate operator=
```

Because C++ references cannot be reseated to refer to different objects, and `const` members cannot be mutated, the compiler rejects synthesizing copy assignment for classes containing reference or `const` members.

## Item 6: Explicitly Disallow Compiler-Generated Functions You Do Not Want

Certain classes model inherently unique entities—such as file descriptors, database connections, socket handles, or thread synchronizers—that should never be duplicated:

```cpp
class HomeForSale { /* ... */ };

HomeForSale house1;
HomeForSale house2;
// HomeForSale house3(house1); // Logical absurdity: a physical house cannot be cloned
// house1 = house2;            // Equally invalid!
```

### Classic C++98 Approach: Private Declarations Without Definitions

In C++98, developers prevented copying by declaring the copy constructor and copy assignment operator `private` and intentionally omitting their definitions:

```cpp
class Uncopyable {
protected:
    Uncopyable() = default;
    ~Uncopyable() = default;

private:
    Uncopyable(const Uncopyable&);            // Declared private, not defined
    Uncopyable& operator=(const Uncopyable&);
};

class HomeForSale : private Uncopyable {};
```

1. External code attempting to copy `HomeForSale` is rejected at compile time due to `private` access restrictions.
2. Member functions or friends attempting to copy trigger linker errors due to missing definitions.

### Modern C++: Use `= delete`

In C++11 and later, `= delete` provides clean, explicit compile-time suppression:

```cpp
class HomeForSale {
public:
    HomeForSale() = default;

    // Explicitly delete copy semantics
    HomeForSale(const HomeForSale&) = delete;
    HomeForSale& operator=(const HomeForSale&) = delete;

    // Move semantics can be preserved if ownership transfer is desired
    HomeForSale(HomeForSale&&) noexcept = default;
    HomeForSale& operator=(HomeForSale&&) noexcept = default;
};
```

## Item 7: Declare Destructors Virtual in Polymorphic Base Classes

This is one of the most critical rules in object-oriented C++: **deleting a derived class instance through a pointer to a base class with a non-virtual destructor results in undefined behavior**.

In practice, this causes **partial destruction**: the derived class destructor never runs, leaking resources.

```cpp
class TimeKeeper {
public:
    TimeKeeper() = default;
    ~TimeKeeper() { /* Non-virtual: dangerous for base classes! */ }
};

class AtomicClock : public TimeKeeper {
public:
    AtomicClock() : timeBuffer(new char[1024]) {}
    ~AtomicClock() { delete[] timeBuffer; }

private:
    char* timeBuffer;
};

TimeKeeper* ptk = new AtomicClock();
delete ptk; // BUG: calls only TimeKeeper::~TimeKeeper(); timeBuffer is leaked!
```

### Mechanics of Virtual Destructors

When `TimeKeeper`'s destructor is non-virtual, `delete ptk` performs static binding based strictly on the pointer type (`TimeKeeper*`). It executes only `TimeKeeper::~TimeKeeper()`.

By declaring the base destructor `virtual`:

```cpp
class TimeKeeper {
public:
    virtual ~TimeKeeper() = default;
};
```

The compiler looks up the object's virtual table pointer (`vptr`), dispatches to `AtomicClock::~AtomicClock()`, and then chains automatically back to `TimeKeeper::~TimeKeeper()`.

> **When NOT to use virtual destructors**: Do not declare virtual destructors on classes not intended for polymorphic inheritance (e.g., standard containers like `std::string` or `std::vector`). Adding a virtual function introduces a `vptr` (8 bytes on 64-bit systems), breaking layout compatibility with C structures and cache locality.

## Item 8: Prevent Exceptions from Leaving Destructors

C++ allows destructors to catch exceptions internally, but **exceptions must never escape a destructor's boundary**.

When an exception triggers stack unwinding, the runtime destroys all local objects in the exiting scopes. If a destructor running during stack unwinding throws a second unhandled exception, C++ cannot handle two simultaneous active exceptions and immediately calls `std::terminate()`.

```cpp
class DBConn {
public:
    void close() { // Primary interface: allows caller to handle failure
        db.close();
        closed = true;
    }

    ~DBConn() noexcept { // Destructors are implicitly noexcept in C++11
        if (!closed) {
            try {
                db.close();
            } catch (const std::exception& e) {
                // Swallow and log: never allow exception to escape
                std::cerr << "Destruction failure: " << e.what() << '\n';
            }
        }
    }

private:
    Database db;
    bool closed{false};
};
```

**Key engineering design rules**:

1. Never let exceptions escape destructors. Catch and swallow them (or abort the process if state is irrecoverably corrupt).
2. If clients need to handle operational failures (e.g., flushing buffers or closing sockets), provide an explicit method (like `close()`). The destructor serves solely as a fallback guarantee.

## Item 9: Never Call Virtual Functions During Construction or Destruction

Consider this transaction logging hierarchy:

```cpp
class Transaction {
public:
    Transaction() {
        logTransaction(); // Anti-pattern: calling virtual function in constructor!
    }
    virtual void logTransaction() const = 0;
};

class BuyTransaction : public Transaction {
public:
    void logTransaction() const override {
        std::cout << "Logging BuyTransaction: " << transactionId << '\n';
    }
private:
    int transactionId{42};
};

BuyTransaction b; // Instantiation
```

During construction of `BuyTransaction b`, the execution order is: **base class constructor runs before derived class constructor**.

When `Transaction::Transaction()` executes, `BuyTransaction`'s private fields (`transactionId`) have not yet been initialized. To prevent virtual functions from accessing uninitialized memory, **C++ specifies that during base class construction, the object's dynamic type is the base class**. Virtual dispatch will not descend into derived classes.

### Idiomatic Solution: Pass Construction Data Upward

Replace the virtual function with a non-virtual method and pass initialization data upward through the constructor chain:

```cpp
class Transaction {
public:
    explicit Transaction(const std::string& logInfo) {
        logTransaction(logInfo); // Safe: non-virtual call
    }

    void logTransaction(const std::string& logInfo) const {
        std::cout << logInfo << '\n';
    }
};

class BuyTransaction : public Transaction {
public:
    BuyTransaction() : Transaction(createLogString()) {}

private:
    static std::string createLogString() {
        return "BuyTransaction initialized";
    }
};
```

## Item 10: Have Assignment Operators Return a Reference to *this

To support chained assignments consistent with built-in primitives (`x = y = z = 15;`), assignment operators should return a reference to `*this`:

```cpp
class Widget {
public:
    Widget& operator=(const Widget& rhs) {
        // ... perform assignment ...
        return *this; // Return reference to left-hand object
    }

    Widget& operator+=(const Widget& rhs) {
        // ... compound assignment ...
        return *this;
    }
};
```

This convention is followed consistently throughout the C++ standard library.

## Item 11: Handle Self-Assignment in operator=

Self-assignment occurs when an object is assigned to itself:

```cpp
Widget w;
w = w;        // Direct self-assignment
a[i] = a[j];  // Indirect self-assignment when i == j
*px = *py;    // Potential aliasing if px and py point to the same memory
```

If a class manages raw resources, self-assignment can cause dangling pointers:

```cpp
// Flawed implementation
Widget& Widget::operator=(const Widget& rhs) {
    delete pb;               // Deletes current resource
    pb = new Bitmap(*rhs.pb); // If rhs == *this, rhs.pb was just deleted!
    return *this;
}
```

### Method 1: Identity Test

```cpp
Widget& Widget::operator=(const Widget& rhs) {
    if (this == &rhs) return *this; // Identity test

    Bitmap* pOrig = pb;             // Remember original pointer
    pb = new Bitmap(*rhs.pb);       // Allocate new resource (exception safe)
    delete pOrig;                   // Delete old resource after successful allocation
    return *this;
}
```

### Method 2: The Copy-and-Swap Idiom (Recommended)

The copy-and-swap idiom provides strong exception safety and natural self-assignment protection:

```cpp
class Widget {
public:
    void swap(Widget& other) noexcept {
        using std::swap;
        swap(pb, other.pb);
    }

    // Pass-by-value creates a copy on the stack
    Widget& operator=(Widget rhs) noexcept {
        swap(rhs);   // Swap internal state with the copy
        return *this; // When rhs exits scope, its destructor cleans up the old state
    }

private:
    Bitmap* pb{nullptr};
};
```

## Item 12: Copy All Parts of an Object

When implementing copy constructors or copy assignment operators manually:

1. **Copy all local data members**: Whenever a member is added to the class, update all copying functions.
2. **Invoke base class copy functions explicitly**:

```cpp
class Customer {
public:
    Customer(const Customer& rhs) : name(rhs.name) {}
    Customer& operator=(const Customer& rhs) {
        name = rhs.name;
        return *this;
    }
private:
    std::string name;
};

class PriorityCustomer : public Customer {
public:
    PriorityCustomer(const PriorityCustomer& rhs)
        : Customer(rhs), // CRITICAL: Explicitly invoke base class copy constructor!
          priority(rhs.priority) {}

    PriorityCustomer& operator=(const PriorityCustomer& rhs) {
        Customer::operator=(rhs); // CRITICAL: Explicitly invoke base class operator=!
        priority = rhs.priority;
        return *this;
    }

private:
    int priority{0};
};
```

If `Customer(rhs)` is omitted, the compiler invokes `Customer`'s default constructor, silently leaving the base class portion uninitialized from `rhs`.

## Summary Checklist

| Principle | Guideline | Pitfall to Avoid |
| :--- | :--- | :--- |
| **Synthesized Functions** | Know what the compiler creates (`default`, `copy`, `move`, `destructor`) | Classes with reference/const members blocking `operator=` |
| **Disallowing Copies** | Use `= delete` (or `Uncopyable` base in C++98) | Relying on runtime exceptions for copy prevention |
| **Polymorphic Destructors** | Base classes with virtual functions must declare `virtual ~Base()` | Partial destruction slicing through base pointers |
| **Exception Safety in Destructors** | Never let exceptions leave destructors; swallow or abort | Program termination via `std::terminate` during stack unwinding |
| **Virtuals in Constructors** | Never invoke virtual functions during construction or destruction | Dynamic dispatch resolving to base type before derived fields exist |
| **Self-Assignment** | Use identity checks or Copy-and-Swap | Deleting current resources before copying from self |
| **Copy All Parts** | Explicitly copy local fields and invoke base class copy operations | Slicing away base class state during manual copy construction |
