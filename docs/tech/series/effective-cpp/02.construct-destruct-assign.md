对象的构造、析构与拷贝赋值构成了 C++ 面向对象世界的核心生命周期骨架。几乎每个自定义类都要与编译器在幕后生成的默认函数打交道。如果对这些暗流涌动的隐式规则缺乏敬畏，内存泄漏、部分销毁、未定义行为与静默崩溃就会接踵而至。

---

## 了解 C++ 默默编写并调用哪些函数

如果我们在 C++ 中声明一个空类：

```cpp
class Empty {};
```

当编译器处理完它后，只要代码中有需要，它就会默默为这个类声明四个基础成员函数（编译器版本均为 `public` 且 `inline`）：

1. **默认构造函数（Default Constructor）**：只有在类没有显式声明任何构造函数时才会合成。
2. **拷贝构造函数（Copy Constructor）**：执行非静态成员的逐个成员拷贝（Memberwise Copy）。
3. **拷贝赋值运算符（Copy Assignment Operator）**：执行成员的逐个赋值。
4. **析构函数（Destructor）**：默认为非虚函数（除非该类继承自带有虚析构函数的基类）。

等价于编译器补全了如下形式：

```cpp
class Empty {
public:
    Empty() { ... }                            // 默认构造
    Empty(const Empty& rhs) { ... }            // 拷贝构造
    ~Empty() { ... }                           // 析构函数
    Empty& operator=(const Empty& rhs) { ... } // 拷贝赋值
};
```

### 拒绝自动合成的边界场景

编译器并非在所有情况下都会无条件生成拷贝赋值运算符。如果一个类内含有 **引用成员（Reference Member）** 或 **const 成员**，编译器就会直接拒绝合成拷贝赋值：

```cpp
template<class T>
class NamedObject {
public:
    NamedObject(std::string& name, const T& value)
        : nameValue(name), objValue(value) {}
private:
    std::string& nameValue; // 引用成员
    const T objValue;       // const 常量成员
};

std::string newDog("Persephone");
std::string oldDog("Satchmo");
NamedObject<int> p(newDog, 2);
NamedObject<int> s(oldDog, 36);

p = s; // 编译报错！C++ 坚决拒绝让引用改指其他对象，也拒绝修改 const 数据
```

C++ 语法规则禁止让一个引用改指向不同的对象。因此，面对内含引用或 const 变量的类，编译器宁可直接报错，也不会生成非法的拷贝赋值代码。如果你的类需要支持赋值，必须显式定义属于自己的 `operator=`。

## 明确拒绝不想使用的编译器自动生成函数

现实开发中，有些类在语义上是独一无二的，绝不允许被随意复制，例如房产资产记录、Socket 句柄、文件流对象或线程互斥锁：

```cpp
class HomeForSale { ... };

HomeForSale house1;
HomeForSale house2;
HomeForSale house3(house1); // 逻辑荒谬：一处真实的房产岂能被复制？
house1 = house2;            // 同样荒谬！
```

### 经典做法：声明为 private 且不予实现

在 C++98 时代，标准的阻止拷贝手段是将拷贝构造函数与拷贝赋值运算符声明为 `private`，并且**故意不提供函数体实现**：

```cpp
class Uncopyable {
protected:
    Uncopyable() {}
    ~Uncopyable() {}
private:
    Uncopyable(const Uncopyable&);            // 只有声明，没有实现
    Uncopyable& operator=(const Uncopyable&);
};

class HomeForSale : private Uncopyable {};
```

这样设计的精妙之处在于：

1. 普通外部代码尝试调用拷贝时，编译器会在编译期直接拦截（`private` 访问权限拒绝）。
2. 即使类的友元或成员函数在内部尝试调用，链接器（Linker）也会因为找不到函数体定义而报错（Unresolved symbol）。

### 现代 C++ 规范：使用 = delete

在 C++11 之后，`= delete` 成为标准原生关键字，语义更加直截了当，且能够在更早的编译期给出极度清晰的错误指引：

```cpp
class HomeForSale {
public:
    HomeForSale() = default;
    HomeForSale(const HomeForSale&) = delete;            // 明确禁止拷贝构造
    HomeForSale& operator=(const HomeForSale&) = delete; // 明确禁止拷贝赋值
};
```

## 为多态基类声明 virtual 析构函数

这是 C++ 面向对象编程中最致命、最隐蔽的内存泄漏陷阱之一。

C++ 标准明确规定：**当派生类对象经由一个基类指针被删除，而该基类带有非虚析构函数时，其执行结果属于未定义行为（Undefined Behavior）**。在绝大多数编译器实现中，实际发生的是**部分销毁（Partial Destruction）**。

```cpp
class TimeKeeper {
public:
    TimeKeeper();
    ~TimeKeeper(); // 非虚析构函数：埋下隐患！
};

class AtomicClock : public TimeKeeper {
public:
    ~AtomicClock();
private:
    std::string* timeData; // 派生类特有动态分配资源
};

TimeKeeper* ptk = new AtomicClock();
delete ptk; // 灾难爆发：仅执行了 ~TimeKeeper()，~AtomicClock() 被静默跳过！
```

### 原理解析

当 `TimeKeeper` 的析构函数是非虚函数时，编译器在遇到 `delete ptk` 时只根据指针的静态类型（`TimeKeeper*`）进行静态绑定，直接调用 `TimeKeeper::~TimeKeeper()`。结果是：

- 属于 `AtomicClock` 内部特有的成员变量、动态分配的内存以及打开的操作系统资源完全未被释放。
- 整个派生类切片静默泄漏，且没有任何编译期警告。

一旦在基类析构函数前加上 `virtual`：

```cpp
virtual ~TimeKeeper();
```

编译器便会借助对象的虚表指针（`vptr`）在运行期动态分发，准确先调用派生类的 `AtomicClock::~AtomicClock()`，待其私有资源清理完毕后，再自动链式调用基类的 `TimeKeeper::~TimeKeeper()`，最后完整回收堆内存。

> **何时不该声明 virtual 析构函数**：如果一个类并不打算作为基类使用，且没有任何虚函数（例如标准库的 `std::string` 或 `std::vector`），切勿盲目为其添加 `virtual` 析构函数。因为哪怕只有一个虚函数，对象实例就会多出一个虚表指针（`vptr`，在 64 位机器上占 8 字节），破坏内存布局与缓存局部性，使得原本紧凑的 C-like struct 无法与 C 语言二进制接口（ABI）保持兼容。

## 别让异常逃离析构函数

C++ 绝对不禁止析构函数抛出异常，但**强力禁止让异常逃逸出析构函数的边界**。

原因在于栈展开（Stack Unwinding）机制。假设一个函数在运行过程中抛出异常，为了跳出栈帧寻找匹配的 `catch` 块，运行时系统必须销毁该作用域内创建的所有局部对象。如果此时某个对象的析构函数在执行清理时又抛出了第二个异常，在两个活跃异常同时存在的绝境下，C++ 运行时别无选择，只能直接调用 `std::terminate` 强制终止整个进程。

```cpp
class DBConn {
public:
    void close() { // 提供主动关闭接口，将异常交给调用者处理
        db.close();
        closed = true;
    }
    ~DBConn() {
        if (!closed) {
            try {
                db.close();
            } catch (...) {
                // 必须在析构函数内部将异常完全吞掉并记录日志
                // 绝不让它向外逃逸！
                logDestructionFailure();
            }
        }
    }
private:
    Database db;
    bool closed{false};
};
```

工程守则非常清晰：

1. 析构函数绝对不能让异常溢出，必须在析构函数内部捕获并消化（或直接 `std::abort`）。
2. 如果客户需要对某种操作的失败（如关闭数据库连接、刷新磁盘缓存）做出业务响应，应该**提供一个普通的成员函数执行该操作**，让调用者在正常执行流中捕获异常。析构函数只作为防御性的最后底线。

在现代 C++11 中，所有的析构函数默认都被隐式标记为 `noexcept`。一旦析构函数有未捕获异常逃逸，程序会立刻暴毙。

## 绝不在构造和析构过程中调用 virtual 函数

假设你正在编写一个股票交易系统的基类：

```cpp
class Transaction {
public:
    Transaction() {
        logTransaction(); // 调用虚函数！
    }
    virtual void logTransaction() const = 0;
};

class BuyTransaction : public Transaction {
public:
    virtual void logTransaction() const override;
};

BuyTransaction b; // 实例化派生类
```

在执行 `BuyTransaction b;` 时，构造过程的严格顺序是：**基类构造函数先于派生类构造函数执行**。

当执行到 `Transaction` 的构造函数本体时，派生类 `BuyTransaction` 的专属成员变量甚至根本还没有被初始化。为了防止虚函数访问到未初始化的危险垃圾内存，C++ 制定了根本规则：**在基类构造期间，对象的动态类型就是基类自身，虚函数绝不会下潜分发到派生类中**。

同理，在析构函数中：派生类的析构函数先运行，派生类成员被销毁；当执行到基类析构函数时，对象已然蜕变为基类类型，调用虚函数调用的也是基类版本。

### 替代方案：向上传递数据

如果基类构造时确实需要派生类定制日志信息，应该将虚函数改为普通成员函数，并由派生类通过基类构造函数实参向上显式传递：

```cpp
class Transaction {
public:
    explicit Transaction(const std::string& logInfo) {
        logTransaction(logInfo); // 非虚函数
    }
    void logTransaction(const std::string& logInfo) const;
};

class BuyTransaction : public Transaction {
public:
    BuyTransaction() : Transaction(createLogString()) {} // 静态辅助函数生成信息
private:
    static std::string createLogString();
};
```

## 令 operator= 返回一个 reference to *this

为了与 C++ 内置类型的链式赋值行为保持完全一致（例如 `x = y = z = 15;`），自定义类的赋值运算符必须遵循协议约定，返回一个指向当前左操作数的引用：

```cpp
class Widget {
public:
    Widget& operator=(const Widget& rhs) {
        ...
        return *this; // 返回左侧对象的引用
    }

    Widget& operator+=(const Widget& rhs) { // 复合赋值运算符同样适用
        ...
        return *this;
    }
};
```

这虽然不是语法强制规则，但它是整个 C++ 标准库与工程界统一遵守的契约。

## 在 operator= 中处理“自我赋值”

所谓自我赋值，是指对象被赋值给自己：

```cpp
Widget w;
w = w; // 显式自我赋值
a[i] = a[j]; // 当 i == j 时的潜在隐式自我赋值
*px = *py;   // 当 px 与 py 指向同一地址时的别名现象（Aliasing）
```

如果类内部管理着动态分配的堆内存，自我赋值常常引发崩溃：

```cpp
// 危险且脆弱的 operator= 实现
Widget& Widget::operator=(const Widget& rhs) {
    delete pb;               // 释放自身的旧内存
    pb = new Bitmap(*rhs.pb); // 灾难：如果 rhs 就是 *this，刚刚被 delete 的正是 rhs.pb！
    return *this;
}
```

### 证同测试（Identity Test）

最直观的方法是在开头判断地址：

```cpp
Widget& Widget::operator=(const Widget& rhs) {
    if (this == &rhs) return *this; // 证同测试：如果是同一个对象，立刻返回

    delete pb;
    pb = new Bitmap(*rhs.pb); // 但注意：如果 new Bitmap 抛出异常，pb 依然成了野指针！
    return *this;
}
```

### 兼具异常安全性的最佳实践：Copy and Swap

要同时保证自我赋值安全与强异常安全性，最佳手段是采用 **Copy and Swap** 惯用法：

```cpp
class Widget {
    void swap(Widget& rhs) noexcept; // 交换内部指针的高效不抛异常函数

    Widget& operator=(Widget rhs) {  // 注意这里按值传递：隐式在栈上创建拷贝副本！
        swap(rhs);                   // 与副本交换内部数据
        return *this;                // 退出函数时，rhs 离开作用域，自动析构并销毁原先的旧数据
    }
};
```

## 复制对象时切勿忘记其每一个成分

当你决定手动接管类的拷贝构造函数或拷贝赋值运算符时，编译器便退出了安全警戒。此时你必须对对象的完整性负起百分之百的责任：

1. **复制所有的本地成员变量**：每当向类中新增一个字段，必须同步在所有拷贝函数中补上该字段的拷贝。
2. **切勿遗忘基类成分的复制**：

```cpp
class PriorityCustomer : public Customer {
public:
    PriorityCustomer(const PriorityCustomer& rhs)
        : Customer(rhs), // 极其重要：显式调用基类的拷贝构造函数！
          priority(rhs.priority) {}

    PriorityCustomer& operator=(const PriorityCustomer& rhs) {
        Customer::operator=(rhs); // 极其重要：显式调用基类的拷贝赋值运算符！
        priority = rhs.priority;
        return *this;
    }
private:
    int priority;
};
```

如果遗漏了 `Customer(rhs)`，派生类的拷贝构造函数只会静默调用基类的**默认构造函数**，导致基类成员根本没有被复制，产生隐蔽的状态截断。
