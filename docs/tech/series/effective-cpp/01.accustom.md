C++ 不是一门单一范式的孤立语言，而是一座经过几十年演化、相互交融又保留着不同时期设计理念的庞大联邦。初读 Scott Meyers 的《Effective C++》，第一章便从最底层的心智模型切入：**先破除对单一编程范式的执念，建立对类型系统、常量语义与对象生命周期初始化的肌肉记忆**。

---

## 视 C++ 为一个语言联邦

很多人初学 C++ 时容易陷入困惑：为什么某些场景推崇值传递，某些场景严禁值传递？为什么有时错误在编译期爆发，有时却在运行期诡异崩溃？

答案在于 C++ 从不是单一范式语言。理解 C++ 的最佳视角，是将其视为由四个次语言（Sublanguages）组成的联邦，每个次语言有自己的一套高效编程守则：

1. **C 语言根基**：区块、语句、预处理器、内置数据类型、数组与原始指针。这里没有模板，没有异常，没有重载。传递对象时遵循 C 的高效值传递与指针操作。
2. **面向对象 C++（Object-Oriented C++）**：类、封装、继承、多态与虚函数（动态绑定）。这一部分是经典的面向对象范式，关注派生关系与接口契约，pass-by-reference-to-const 成为常态。
3. **模板 C++（Template C++）**：泛型编程与编译期元编程（TMP）。在这个领域，类型不再是固定的内存布局，而是由操作表达式隐式约束。执行期规则在这里被编译期具现化取代，代码膨胀与编译报错成为需要权衡的焦点。
4. **标准模板库（STL）**：由容器（Containers）、迭代器（Iterators）、算法（Algorithms）与函数对象（Function Objects）严密咬合的生态。它建立在一整套独特的迭代器类别与算法复杂度保证之上。

当我们在这些次语言之间切换时，最佳实践也随之转移：在纯 C 模块里传递内置整数时值传递最快；而在面向对象 C++ 中传递大型类实例时，必须优先选择常量引用传递；切换到 STL 算法时，仿函数和迭代器又回到了高效值传递的习惯。

## 尽量以 const、enum、inline 替换 #define

“宁可以编译器替换预处理器”，这是现代 C++ 规范中最基础也是最深远的一条规则。

`#define` 在预处理阶段由文本替换机制处理，它从不曾进入编译器的符号表（Symbol Table）。当使用宏定义常量时，编译器只看得到替换后的裸字面量：

```cpp
#define ASPECT_RATIO 1.653
```

如果代码在编译或符号链接阶段报错，错误信息只会指涉 `1.653`，而绝不会出现 `ASPECT_RATIO` 这个名字。如果是别人的头文件里定义的宏，排查起来就是无尽的盲猜。

### 常量替换宏

改用真正的常量定义：

```cpp
const double AspectRatio = 1.653; // 拥有明确类型，进入符号表
```

定义指针或类专属常量时有两点细节：

1. **头文件内的常量指针**：由于常量定义通常放在头文件，为了防止多重定义并保护指针指向，不仅被指物要声明为 `const`，指针本身也应是 `const`：

   ```cpp
   const char* const authorName = "Scott Meyers";
   // 更推荐使用现代 C++ 的 std::string_view 或 constexpr std::string_view
   ```

2. **类专属常量（Class-specific constants）**：为了限制常量作用域于类内，必须将其声明为 static 成员：

   ```cpp
   class CostEstimate {
   private:
       static const double FudgeFactor; // 声明式
   };
   // 在实现文件定义：
   const double CostEstimate::FudgeFactor = 1.35;
   ```

### “Enum Hack” 与编译期整型常量

如果某个类内常量必须在编译期已知（例如静态数组的长度定义），在 C++98 时代，旧编译器可能不允许在类内初值设定非整型静态常量。此时的惯用手法是 **Enum Hack**：

```cpp
class GamePlayer {
private:
    enum { NumTurns = 5 }; // "the enum hack"
    int scores[NumTurns];
};
```

Enum hack 的行为在很多方面比 const 更接近 `#define`：取一个 enum 值的地址是不合法的，绝不会导致非必要的内存分配，也不会为符号生成实体引用。

> 在现代 C++11 及更高版本中，`constexpr` 与 `inline constexpr` 彻底统一了这一范畴，直接使用 `static constexpr int NumTurns = 5;` 即可享有最严格的编译期求值与作用域约束。

### 用 inline 函数替换宏函数

用宏编写伪函数常常引发出人意料的副作用：

```cpp
// 经典的带副作用宏
#define CALL_WITH_MAX(a, b) ((a) > (b) ? (a) : (b))

int a = 5, b = 0;
CALL_WITH_MAX(++a, b);    // a 被递增两次！
CALL_WITH_MAX(++a, b + 10); // a 被递增一次！
```

解决这种荒谬行为的方法是采用 template inline 函数：

```cpp
template<typename T>
inline void callWithMax(const T& a, const T& b) {
    f(a > b ? a : b);
}
```

它不仅保留了宏的高效率（无函数调用开销），更拥有严密的类型安全、真正的作用域和明确的求值顺序。

## 尽可能使用 const

`const` 是 C++ 赋予工程师最强有力的契约工具之一。它允许你向编译器与调用者明确表态：**此处的语义约束不可被破坏**。

### 指针与 const 的左右法则

区分指针本身的常量性与所指物的常量性，取决于 `const` 关键字相对于星号 `*` 的位置：

```cpp
char greeting[] = "Hello";

char* p = greeting;                // 非 const 指针，非 const 数据
const char* p = greeting;          // 非 const 指针，const 数据（被指物不可改）
char* const p = greeting;          // const 指针，非 const 数据（指针自身不可改）
const char* const p = greeting;    // const 指针，const 数据（两者均不可改）
```

> 记忆法则：如果 `const` 出现在 `*` 的左边，表示被指物是常量；如果出现在 `*` 的右边，表示指针本身是常量。

### const 成员函数与双重常量性

声明成员函数为 `const` 的核心目的，是明确该成员函数可作用于 const 对象。这直接支撑了两大基础需求：

1. 让接口更容易被理解：一眼看出哪些函数会修改对象状态，哪些不会。
2. 支撑 pass-by-reference-to-const：如果一个函数接收常量引用，它只能调用目标对象的 const 成员函数。

在语言设计层面，存在两种关于常量性的哲学：

- **物理常量性（Bitwise Constness）**：成员函数绝不修改对象的任何非静态数据成员的任何一个比特位。这是 C++ 编译器的默认检查基准。
- **逻辑常量性（Logical Constness）**：const 成员函数可以修改对象内的部分数据，只要这种修改不会在外部被调用者察觉（例如内部缓存、锁状态、统计计数器）。

当物理常量性与实际业务冲突时，使用 `mutable` 关键字释放特定成员的比特约束：

```cpp
class TextBlock {
public:
    std::size_t length() const {
        if (!lengthIsValid) {
            textLength = text.length(); // 合法：mutable 变量允许在 const 成员函数中修改
            lengthIsValid = true;
        }
        return textLength;
    }
private:
    std::string text;
    mutable std::size_t textLength{0};
    mutable bool lengthIsValid{false};
};
```

### 避免 const 与 non-const 成员函数的代码重复

当类的重载函数（如 `operator[]`）在 const 与 non-const 版本中具有完全相同的边界检查、日志记录和数据访问逻辑时，为了避免复制粘贴带来的维护灾难，应该让 **non-const 版本复用 const 版本**：

```cpp
class TextBlock {
public:
    const char& operator[](std::size_t pos) const {
        // 复杂的越界检查、访问日志、完整性验证...
        return text[pos];
    }

    char& operator[](std::size_t pos) {
        return const_cast<char&>(
            static_cast<const TextBlock&>(*this)[pos]
        );
    }
private:
    std::string text;
};
```

这里包含了两次转型：

1. `static_cast<const TextBlock&>(*this)`：为 `*this` 强行加上 `const` 约束，迫使编译器调用已有的 const 版本 `operator[]`。
2. `const_cast<char&>(...)`：从 const 版本的返回值中安全移除 `const` 限制。

反向操作（用 const 版本调用 non-const 版本）是绝对禁止的，因为那破坏了 const 对象“绝不被修改”的契约承诺。

## 确定对象被使用前已被初始化

在 C++ 中读取未初始化的变量，结果是未定义行为（Undefined Behavior）。有时它恰巧是零，有时是内存残留的垃圾值，最终导致偶发难以复现的内存越界与计算畸变。

### 区分“赋值”与“初值列（Member Initialization List）”

在类的构造函数内部，很多初学者习惯用常规赋值语句：

```cpp
class PhoneNumber {};

class AddressEntry {
public:
    AddressEntry(const std::string& name, const std::string& address,
                 const std::list<PhoneNumber>& phones);
private:
    std::string name;
    std::string address;
    std::list<PhoneNumber> phones;
    int numTimesConsulted;
};

// 错误/低效示范：这是赋值，不是初始化
AddressEntry::AddressEntry(const std::string& name, const std::string& address,
                           const std::list<PhoneNumber>& phones) {
    this->name = name;           // 先调用默认构造，再调用 copy assignment operator
    this->address = address;     // 同上
    this->phones = phones;       // 同上
    this->numTimesConsulted = 0; // 内置类型赋值
}
```

C++ 规则明确规定：**对象的成员变量的初始化动作发生在进入构造函数本体之前**。在上面的错误范例中，`name`、`address` 和 `phones` 在进入大括号前，就已经调用了各自类的默认构造函数；在大括号内，又执行了一次拷贝赋值操作。前面的默认构造完全被浪费掉了。

高效的做法是使用成员初值列：

```cpp
// 最佳实践：成员初值列（Member Initialization List）
AddressEntry::AddressEntry(const std::string& name, const std::string& address,
                           const std::list<PhoneNumber>& phones)
    : name(name),
      address(address),
      phones(phones),
      numTimesConsulted(0) {}
```

初值列直接调用各成员的拷贝构造函数，一步到位。如果成员变量带有 `const` 或属于引用类型（Reference），它们**必须**在初值列中进行初始化，因为 const 和引用都不允许二次赋值。

> **成员初始化次序陷阱**：C++ 总是按照成员在类定义中声明的先后顺序进行初始化，与它们在初值列中书写的先后顺序毫无关系。为了避免难以察觉的依赖未初始化成员 Bug，初值列表达顺序务必与类声明顺序严格保持一致。

### 跨编译单元 non-local static 对象的初始化次序谜题

所谓 static 对象，其寿命从被构造出来一直持续到程序完全结束。这包括：

- 全局对象（Global objects）
- 定义于 namespace 作用域内的对象
- 类内部声明为 static 的对象
- 文件作用域内声明为 static 的对象

所谓编译单元（Translation Unit），是指生成单个目标文件（`.o` / `.obj`）的单一源码文件以及它所包含的所有头文件。

当系统存在定义在不同编译单元内的两个 non-local static 对象时，灾难降临了：**C++ 对不同编译单元内 non-local static 对象的初始化相对次序没有任何规范**。

考虑如下文件系统日志场景：

```cpp
// FileSystem.h
class FileSystem {
public:
    std::size_t numDisks() const;
};
extern FileSystem tfs; // 外部声明的全局对象

// Directory.cpp (属于另一个编译单元)
class Directory {
public:
    Directory() {
        std::size_t disks = tfs.numDisks(); // 如果 tfs 还没被初始化，这里直接崩溃！
    }
};
Directory tempDir;
```

如果链接器先初始化了 `Directory.cpp` 中的 `tempDir`，而此时 `FileSystem.cpp` 中的 `tfs` 尚未初始化，程序就会尝试读取尚未准备就绪的内存。

### Meyers' Singleton 优雅破局

解决这一跨编译单元初始化次序死结的标准方案，是将每个 non-local static 对象搬到专门的专属函数内部，将其转化为 **local static 对象**：

```cpp
class FileSystem {
public:
    std::size_t numDisks() const;
};

// 用函数包裹 local static 对象
FileSystem& tfs() {
    static FileSystem fs; // 第一次调用时才会初始化，且保证被初始化
    return fs;
}

class Directory {
public:
    Directory() {
        std::size_t disks = tfs().numDisks(); // 绝对安全
    }
};

Directory& tempDir() {
    static Directory td;
    return td;
}
```

C++ 语言保证：函数内的 local static 对象会在“该函数被调用期间首次遇上该对象的定义式时”被精确初始化。通过函数返回引用，我们把不确定的编译单元依赖链转换成了绝对可靠的函数调用链。

在现代 C++11 及更高版本中，C++ 标准更进一步明确：**local static 变量的初始化过程天然保证线程安全**（Magic Statics），无需手动添加互斥锁即可抵御高并发竞争。
