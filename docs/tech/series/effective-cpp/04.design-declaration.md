软件设计的本质，是在人与机器之间建立契约。C++ 赋予了程序员极大的表达自由，但这柄双刃剑也极易割伤团队。一个设计糟糕的类接口，往往充满隐式假设与隐匿陷阱，让调用者防不胜防。本章的核心命题非常直接：**如何在声明期构筑防线，让接口“容易被正确使用，而不易被误用”**。

---

## 让接口容易被正确使用，不易被误用

理想的软件接口，应该像防呆插头一样：只要代码能通过编译，它大概率就是正确的；如果使用方式有误，编译器在第一秒钟就应当无情拒绝。

### 引入强类型包装（Strong Types）

考虑一个表示日期的类构造函数：

```cpp
class Date {
public:
    Date(int month, int day, int year); // 极度脆弱的设计
};

Date d1(30, 3, 1995); // 究竟是 3 月 30 日，还是 30 月 3 日？
Date d2(3, 40, 2020); // 40 日显然是非法的，但编译器毫无察觉
```

调用者很容易传错参数顺序，或者传入超出合理范围的脏数据。借助类型系统进行约束：

```cpp
struct Day {
    explicit Day(int d) : val(d) {}
    int val;
};

struct Month {
    explicit Month(int m) : val(m) {}
    int val;
};

struct Year {
    explicit Year(int y) : val(y) {}
    int val;
};

class Date {
public:
    Date(const Month& m, const Day& d, const Year& y);
};

Date d(Day(30), Month(3), Year(1995)); // 编译期直接拦截类型错位！
```

### 接口行为与内置类型保持一致性

除非有极充分的理由，否则自定义类的操作行为必须与 C++ 原生内置类型保持一致。例如 `a * b` 绝对不应该修改 `a` 或 `b` 的内部状态；重载的 `operator+` 应当返回一个新对象，而不是修改自身。保持一致性能够最大化调动调用者的直觉，消除不必要的意外。

### 消除客户的资源管理负担

如果工厂函数返回裸指针，调用者很容易忘记 `delete` 或误用 `delete[]`。现代接口应当强制将资源所有权打包在智能指针中返回：

```cpp
// 糟糕：把内存归还责任推给调用者
Investment* createInvestment();

// 优秀：接口自解释其所有权语义，不释放绝无法编译通过
std::unique_ptr<Investment> createInvestment();
```

## 视 class 设计为 type 设计

在 C++ 中，每定义一个新 class，就意味着在类型系统中增添了一个全新的 type。类设计者必须像语言设计者定义内置类型一样严肃考量以下问题：

1. **新 type 的对象应该如何被创建和销毁？** 直接影响构造函数、析构函数以及内存分配算子的设计。
2. **对象的初始化与赋值有什么差异？** 明确区分拷贝构造与拷贝赋值。
3. **新 type 如果被 pass-by-value 意味着什么？** 拷贝构造函数定义了按值传递的物理实现与性能成本。
4. **什么是新 type 的“合法值”？** 类的成员变量在什么范围内才符合类的不变量（Class Invariants）？构造函数和成员函数需要做哪些防卫断言？
5. **新 type 是否需要配合某个继承体系？** 如果要作为基类，析构函数必须为 `virtual`。
6. **新 type 需要什么样的类型转换？** 隐式转换极易带来灾难，单参构造函数是否需要加 `explicit`？
7. **什么样的操作符和函数对此新 type 是合理的？** 哪些应为成员函数，哪些应为非成员函数？
8. **什么样的标准函数应该被拒绝？** 是否需要明确 `= delete` 默认构造或拷贝赋值？
9. **谁该取用新 type 的成员？** 明确划分 `public`、`protected`、`private` 以及友元边界。
10. **什么是新 type 的“未声明接口”（Undocumented Interface）？** 你的类对资源管理、异常安全性以及多线程并发做出了哪些隐性保证？
11. **新 type 有多么一般化？** 它是一个孤立的实体类，还是一个应当被提炼为 class template 的泛型概念？
12. **你真的需要一个新 type 吗？** 如果只是想定义非成员辅助函数，或者单纯给既有类增加衍生操作，组合或命名空间函数是否更好？

## 宁以 pass-by-reference-to-const 替换 pass-by-value

默认情况下，C++ 以 pass-by-value（按值传递）的方式传递函数实参。这意味着每一次函数调用，实参都会通过拷贝构造函数复制出一份完整的临时副本。

### 规避深层构造/析构链的开销

考虑一个简单的对象传递：

```cpp
class Person {
public:
    Person();
    virtual ~Person();
private:
    std::string name;
    std::string address;
};

class Student : public Person {
public:
    Student();
    ~Student();
private:
    std::string schoolName;
    std::string schoolAddress;
};

bool validateStudent(Student s); // 按值传递：性能灾难！
```

仅仅为了传递一个 `Student` 对象，背后触发的开销包括：

- 1 次 `Student` 拷贝构造函数
- 1 次基类 `Person` 拷贝构造函数
- 4 次 `std::string` 成员的拷贝构造函数（深拷贝动态字符数组）
- 函数返回时对应的 6 次析构函数！

改用常量引用传递：

```cpp
bool validateStudent(const Student& s); // 零拷贝开销，仅传递一个底层指针大小
```

### 杜绝对象切割（Object Slicing）

按值传递不仅带来性能浪费，更会引发致命的逻辑缺陷——**对象切割**：

```cpp
class Window {
public:
    std::string name() const;
    virtual void display() const; // 虚函数
};

class CircleWindow : public Window {
public:
    virtual void display() const override;
};

void printNameAndDisplay(Window w) { // 错误：按值传递
    std::cout << w.name();
    w.display(); // 永远只会调用 Window::display()！
}

CircleWindow cw;
printNameAndDisplay(cw); // cw 被硬生生“切掉”了派生类成分！
```

当 `CircleWindow` 被传给 `printNameAndDisplay` 时，编译器调用的是 `Window` 的拷贝构造函数。传进去的参数 `w` 纯粹是一个基类 `Window` 对象，其虚表指针（`vptr`）指向的是基类虚表，派生类独有的多态行为被完全抹杀。

采用 `const Window&` 传递，底层以指针间接寻址，完美保全了对象的完整动态多态性。

> **例外准则**：对于内置类型（如 `int`、`double`）、标准库的迭代器（Iterators）和函数对象（Function Objects），按值传递不仅体积小（通常只有 4~8 字节），而且更利于编译器将数据放入 CPU 寄存器中极致优化。

## 绝不要返回 pointer 或 reference 指向 local stack 对象

意识到按值传递的开销后，许多程序员会陷入另一个极端：试图在任何地方都返回引用，哪怕面对一个必须在函数内部新生成的对象。

```cpp
class Rational {
public:
    Rational(int numerator = 0, int denominator = 1);
private:
    int n, d;
    friend const Rational operator*(const Rational& lhs, const Rational& rhs);
};
```

两个有理数相乘必须产生一个全新的数学结果。有人为了“优化”，尝试返回引用：

```cpp
// 致命错误 1：返回局部栈对象的引用
const Rational& operator*(const Rational& lhs, const Rational& rhs) {
    Rational result(lhs.n * rhs.n, lhs.d * rhs.d);
    return result; // 灾难！result 在函数退出时瞬间析构，返回悬垂引用（Dangling Reference）
}

// 致命错误 2：在堆上 new 出来并返回引用
const Rational& operator*(const Rational& lhs, const Rational& rhs) {
    Rational* result = new Rational(lhs.n * rhs.n, lhs.d * rhs.d);
    return *result; // 谁来负责 delete？
}

Rational w, x, y, z;
w = x * y * z; // 连续调用两次 operator*，产生孤立内存泄漏，外部根本没有机会获取指针来 delete！
```

### 拥抱返回值优化（RVO / NRVO）

如果一个函数必须返回一个新对象，就必须老老实实地**按值返回**：

```cpp
inline const Rational operator*(const Rational& lhs, const Rational& rhs) {
    return Rational(lhs.n * rhs.n, lhs.d * rhs.d);
}
```

在现代 C++ 编译器中，**返回值优化（RVO / NRVO）** 会直接在调用者的栈帧空间中构造目标对象，连一次拷贝或移动构造的开销都不会发生。用错误的引用换取虚幻的性能，只会换来无法排查的未定义崩溃。

## 将成员变量声明为 private

把数据成员声明为 `private`，是实现面向对象封装性的铁律：

1. **语法一致性**：客户代码访问类的任何属性时一律使用圆括号 `obj.length()`，不需要去猜某个字段到底是属性还是函数。
2. **细粒度的访问控制**：通过仅提供 getter、同时提供 getter/setter，或者仅提供内部受限操作，精准控制字段的只读/读写属性。
3. **不变量验证与防线**：在 setter 中可以进行范围校验、惰性计算、触发监听器、甚至加锁同步，而直接暴露字段会让这一切防御形同虚设。

> **为什么 protected 并不比 public 更具封装性**？
> 衡量一个成员被修改时带来的维护冲击，取决于“有多少代码可能被破坏”。如果一个 public 成员被修改，全世界所有使用该类的外部代码全都会挂掉；如果一个 protected 成员被修改，该体系下所有已存在的和未来可能出现的派生类代码全都会挂掉。两者的破坏性同样是无限的。因此，只有 `private` 才能提供真正的封装隔离。

## 宁以 non-member non-friend 函数替换 member 函数

直觉上，面向对象推崇“把所有与该类相关的操作都放进类内作为成员函数”。但从**封装性（Encapsulation）**的严谨数学定义来看，事实恰恰相反：

> 封装的本质，是向外界隐藏实现细节。能够直接访问私有成员的代码越少，系统的封装性就越好。

考虑一个清理浏览器缓存的场景：

```cpp
class WebBrowser {
public:
    void clearCache();
    void clearHistory();
    void removeCookies();

    // 方案 A：作为成员函数
    void clearEverything();
};

// 方案 B：作为非成员非友元函数
void clearBrowser(WebBrowser& wb) {
    wb.clearCache();
    wb.clearHistory();
    wb.removeCookies();
}
```

方案 B（非成员非友元函数）明显具有更强的封装性！因为它并没有被授予访问 `WebBrowser` 内部私有字段的特权。它仅仅是对公共接口的组合封装。将其移出类外，意味着未来类的私有数据成员发生变更时，方案 B 的代码完全不受任何影响。

在组织大型库时，可以将这些辅助函数放在与类相同的 namespace 中，并根据功能拆分到不同的头文件（例如 `webbrowser_bookmarks.h`、`webbrowser_cookies.h`），这正是 C++ 标准库（如 `<algorithm>`）的经典架构模式。

## 若所有参数皆需类型转换，请为此采用 non-member 函数

如果一个函数的所有参数（包括通过 `this` 指针隐式传递的左操作数）都需要支持隐式类型转换，那么这个函数必须是非成员函数。

考虑有理数乘法：

```cpp
class Rational {
public:
    Rational(int numerator = 0, int denominator = 1); // 允许从 int 隐式转换
    int numerator() const;
    int denominator() const;

    const Rational operator*(const Rational& rhs) const; // 成员函数版本
};

Rational oneHalf(1, 2);
Rational result;

result = oneHalf * 2; // 顺利编译！等价于 oneHalf.operator*(Rational(2))
result = 2 * oneHalf; // 编译报错！等价于 2.operator*(oneHalf)，int 根本没有该成员函数！
```

只有当实参位于函数参数列表（Parameter List）中时，编译器才会尝试调用构造函数进行隐式类型转换。位于左侧的调用宿主 `this` 绝不会被隐式转换。

解决办法是将其声明为非成员函数：

```cpp
const Rational operator*(const Rational& lhs, const Rational& rhs) {
    return Rational(lhs.numerator() * rhs.numerator(),
                    lhs.denominator() * rhs.denominator());
}

result = 2 * oneHalf; // 完美编译！等价于 operator*(Rational(2), oneHalf)
```

## 考虑支持一个不抛异常的 swap 函数

`std::swap` 是算法与异常安全编程（如 Copy-and-Swap）的基础工具。在默认实现中，`std::swap` 依赖一次拷贝构造与两次拷贝赋值：

```cpp
template<typename T>
void swap(T& a, T& b) {
    T temp(a);
    a = b;
    b = temp;
}
```

如果你的类采用 **PIMPL（Pointer to Implementation）** 惯用法，内部只持有一个指向具体实现对象的裸指针：

```cpp
class WidgetImpl { ... };

class Widget {
public:
    void swap(Widget& other) noexcept {
        using std::swap;
        swap(pImpl, other.pImpl); // 仅需交换内部指针！
    }
private:
    WidgetImpl* pImpl;
};
```

交换两个 `Widget` 仅仅需要交换一个 8 字节的指针，而默认的 `std::swap` 却会触发整个对象的深拷贝，产生极大的性能浪费。

### 定制 swap 的完整四步法

1. 提供一个 `public` 且 `noexcept` 的 `swap` 成员函数，直接高效置换内部指针。
2. 在类所在的同一个命名空间内，提供一个同名的非成员 `swap` 函数，内部直接调用成员函数。
3. 如果是在编写 class（非 class template），特化 `std::swap`。
4. 在调用端，永远使用 `using std::swap;` 配合无命名空间修饰的裸 `swap`：

```cpp
template<typename T>
void doSomething(T& obj1, T& obj2) {
    using std::swap; // 让 std::swap 在候选中可见
    swap(obj1, obj2); // 通过 ADL（参数依赖查找）优先找到类型专属的最佳 swap
}
```

通过这一套机制，C++ 能在编译期自动选择最具效率的特化 swap，同时在找不到定制版本时优雅回落到标准实现。
