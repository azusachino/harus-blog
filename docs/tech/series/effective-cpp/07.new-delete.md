C++ gives systems programmers explicit control over memory allocation and deallocation lifecycles. Developers can bypass general-purpose heap managers to build fixed-size chunk pools, insert buffer-overflow guard canaries, or implement lock-free allocators. However, replacing `new` and `delete` demands strict adherence to language conventions: **violating hidden runtime contracts triggers infinite loops, memory leaks, or silent heap corruption**.

---

## Item 49: Understand the Behavior of the new-handler

When `operator new` cannot satisfy an allocation request, it invokes a client-specified callback function—the **new-handler**—before throwing `std::bad_alloc`:

```cpp
#include <new>

namespace std {
    typedef void (*new_handler)();
    new_handler set_new_handler(new_handler p) noexcept;
}
```

Registering a global out-of-memory handler:

```cpp
void outOfMemory() {
    std::cerr << "Fatal: System out of memory! Aborting...\n";
    std::abort();
}

int main() {
    std::set_new_handler(outOfMemory);
    // int* pLargeBuffer = new int[10000000000000ULL]; // Triggers new-handler
}
```

### The New-Handler Contract

A new-handler must not simply log and return. When it returns, `operator new` immediately **retries the allocation**. If memory remains insufficient, an infinite loop ensues. A well-designed new-handler must perform one of five actions:

1. **Make more memory available**: Deallocate emergency reserve buffers acquired at startup to provide memory for ongoing operations.
2. **Install a different new-handler**: If the current handler cannot free memory, install a fallback handler with alternate strategies.
3. **Uninstall the new-handler**: Pass `nullptr` to `std::set_new_handler`, causing `operator new` to throw `std::bad_alloc` on its next retry.
4. **Throw `std::bad_alloc` (or a derived exception)**: Breaks the retry loop and transfers control to enclosing `catch` blocks.
5. **Abort or Exit**: Call `std::abort()` or `std::exit()` immediately to prevent execution with corrupted state.

### Class-Specific new-handlers via CRTP

To configure custom handlers for specific high-memory classes, combine RAII with the **Curiously Recurring Template Pattern (CRTP)**:

```cpp
// RAII holder: restores previous handler on scope exit
class NewHandlerHolder {
public:
    explicit NewHandlerHolder(std::new_handler nh) : handler(nh) {}
    ~NewHandlerHolder() { std::set_new_handler(handler); }

    NewHandlerHolder(const NewHandlerHolder&) = delete;
    NewHandlerHolder& operator=(const NewHandlerHolder&) = delete;

private:
    std::new_handler handler;
};

// CRTP Mixin Base Template
template <typename T>
class NewHandlerSupport {
public:
    static std::new_handler set_new_handler(std::new_handler nh) noexcept {
        std::new_handler oldHandler = currentHandler;
        currentHandler = nh;
        return oldHandler;
    }

    static void* operator new(std::size_t size) {
        NewHandlerHolder h(std::set_new_handler(currentHandler));
        return ::operator new(size);
    }

private:
    static std::new_handler currentHandler;
};

template <typename T>
std::new_handler NewHandlerSupport<T>::currentHandler = nullptr;

// Usage: inheriting provides class-specific new-handler support
class Widget : public NewHandlerSupport<Widget> {};
```

## Item 50: Understand When It Makes Sense to Replace new and delete

In most production environments, default memory managers (glibc `malloc`, `jemalloc`, `mimalloc`) are thoroughly optimized. Custom allocators should only be written to solve concrete architectural requirements:

1. **Detecting Buffer Overflows & Underflows**: Prepend and append signature byte sequences ("canaries") around allocated memory blocks and verify their integrity on `delete`.
2. **Collecting Performance Telemetry**: Track allocation size histograms, lifetime distributions, peak memory usage, and fragmentation metrics.
3. **Maximizing Allocation Speed (Fixed-Size Pools)**: For classes allocated in high volumes (e.g., nodes in graph or tree structures), a fixed-size chunk allocator eliminates general-purpose lock contention.
4. **Minimizing Header Overhead**: General-purpose allocators attach 8–16 byte bookkeeping headers to every allocation. Fixed-size pools eliminate this overhead.
5. **Enforcing Hardware Alignment**: Satisfy SIMD (SSE/AVX) or GPU memory alignment constraints (e.g., 16/32/64-byte boundaries).
6. **Optimizing Cache Locality**: Cluster related objects frequently accessed together onto contiguous memory pages.

## Item 51: Adhere to Convention When Writing new and delete

Custom implementations of `operator new` and `operator delete` must follow strict standard conventions:

### Custom `operator new` Conventions

```cpp
void* operator new(std::size_t size) {
    using namespace std;

    // Convention 1: Zero-byte allocations must return a valid, non-null pointer
    if (size == 0) {
        size = 1;
    }

    // Convention 2: Infinite loop attempting allocation
    while (true) {
        void* pMem = malloc(size);
        if (pMem) return pMem; // Success

        // Allocation failed: query current new-handler
        // (C++11 and later: new_handler globalHandler = get_new_handler();)
        new_handler globalHandler = set_new_handler(nullptr);
        set_new_handler(globalHandler);

        if (globalHandler) {
            (*globalHandler)(); // Attempt to free memory
        } else {
            throw bad_alloc(); // No handler: throw exception
        }
    }
}
```

### Handling Inherited Class Allocations

When `operator new` is defined inside a base class, derived classes without custom allocators inherit the base version. Check the requested allocation size:

```cpp
class Base {
public:
    static void* operator new(std::size_t size) {
        if (size != sizeof(Base)) {
            // Derived class with larger size inherited Base::operator new!
            return ::operator new(size); // Forward to global allocator!
        }
        return allocateBaseChunk(); // Custom fixed-size allocation
    }

    static void operator delete(void* rawMemory, std::size_t size) noexcept {
        if (rawMemory == nullptr) return; // Standard: deleting nullptr is a no-op
        if (size != sizeof(Base)) {
            ::operator delete(rawMemory);
            return;
        }
        deallocateBaseChunk(rawMemory);
    }
};
```

The `size` argument of `operator delete` is only reliable if `Base` has a virtual destructor; without one, deleting a `Derived` through a `Base*` is undefined behavior anyway (Item 7).

## Item 52: Write Placement delete if You Write Placement New

A **placement new** is any `operator new` overload that accepts parameters beyond the required `std::size_t`:

```cpp
void* operator new(std::size_t size, std::ostream& logStream);
```

### The Exception Rollback Hazard

Consider constructing an object with placement new:

```cpp
Widget* pw = new (std::cerr) Widget();
```

This operation proceeds in two distinct steps:

1. Call custom placement `operator new(sizeof(Widget), std::cerr)` to allocate raw memory.
2. Invoke `Widget`'s constructor.

**If the constructor throws an exception in step 2**:

- The caller never receives the returned pointer, making client cleanup impossible.
- The C++ runtime must automatically release the memory allocated in step 1.
- To do so, the runtime searches for a **placement delete** whose parameter signature matches the placement new exactly:

```cpp
void operator delete(void* rawMemory, std::ostream& logStream) noexcept;
```

If no matching placement delete is declared, the runtime **gives up and does nothing**, permanently leaking the allocated memory.

> **Name Hiding Warning**: Declaring any `operator new` in a class hides the global versions. To keep the standard forms available alongside your placement overloads, either declare them in the class too, or inherit them from a base class that forwards to the global ones and pull them in with `using`:
>
> ```cpp
> class StandardNewDeleteForms {
> public:
>     static void* operator new(std::size_t size) { return ::operator new(size); }
>     static void* operator new(std::size_t size, void* ptr) noexcept { return ::operator new(size, ptr); }
>     static void operator delete(void* p) noexcept { ::operator delete(p); }
> };
>
> class Widget : public StandardNewDeleteForms {
> public:
>     using StandardNewDeleteForms::operator new;
>     using StandardNewDeleteForms::operator delete;
>     static void* operator new(std::size_t size, std::ostream& logStream);
>     static void operator delete(void* rawMemory, std::ostream& logStream) noexcept;
> };
> ```

## Items 53–55: Compiler Warnings, Modern C++, and the Standard Library

### Item 53: Pay Careful Attention to Compiler Warnings

Treat compiler diagnostics as first-class defect indicators. Configure builds with strict warning flags:

- GCC/Clang: `-Wall -Wextra -Wpedantic -Werror`
- MSVC: `/W4 /WX`

Warnings frequently pinpoint uninitialized members, sign-comparison bugs, implicit slicing, and non-virtual destructors before code enters production.

### Item 54 & 55: Familiarize Yourself with Standard C++ and Boost

*Effective C++* was published during the transition from C++03 to TR1. In modern development:

- **TR1 has been absorbed into ISO C++**: `std::shared_ptr`, `std::function`, `std::unordered_map` and `std::tuple` came from it, and C++11 added `std::unique_ptr` and `<chrono>`.
- **Modern Standards (C++11/14/17/20)**: Move semantics (`std::move`), perfect forwarding (`std::forward`), compile-time evaluation (`constexpr`), structured bindings, and Concepts replace legacy idioms.
- **Boost as the Precursor**: Boost has long served as an incubator for the standard; `std::filesystem`, `std::optional` and `std::regex` all trace back to Boost libraries.

## Summary Checklist

| Topic | Rule | Pitfall to Avoid |
| :--- | :--- | :--- |
| **new-handler** | Must free memory, install replacement, uninstall, or abort | Infinite retry loops on allocation failure |
| **Allocation Conventions** | Treat 0 bytes as 1 byte; forward unexpected sizes to `::operator new` | Failing to route derived class allocations to global allocator |
| **Placement Deletion** | Pair every placement new with an identical placement delete | Memory leaks when constructor throws during placement new |
| **Warnings as Errors** | Enable strict compiler flags (`-Wall -Wextra -Werror`) | Ignoring signedness mismatches or uninitialized fields |
