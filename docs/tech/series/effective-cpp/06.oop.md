Object-Oriented Design (OOP) in C++ is far more rigorous than simply stacking classes and connecting inheritance lines. Inheritance is a surgical instrument: misusing public inheritance, breaking domain invariants, or misunderstanding virtual dispatch causes architectural drift. This chapter provides a comprehensive treatment of **the Liskov Substitution Principle, name hiding, interface inheritance, the NVI idiom, default parameter traps, and multiple inheritance**.

---

## Before you start

Inheritance lets one class build on another, and virtual functions let code call the right version of a function without knowing the exact type. The difficulty is deciding when inheritance is the right tool. A `Penguin` class derived from `Bird` looks natural until `Bird` has a `fly()` function and a caller asks every bird to fly. This chapter covers when "is a" really holds, how a derived class can accidentally hide base-class functions, and the alternatives to inheritance when it does not fit.

Read [chapter 05](/tech/series/effective-cpp/05.implementations/) first.
Terms used in this chapter:

- **public inheritance**: `class D : public B`, which says a `D` can be used anywhere a `B` is expected.
- **is-a**: the relationship public inheritance is supposed to model, as in "a square is a shape".
- **Liskov Substitution Principle**: code written for a base class must keep working when given a derived object.
- **virtual function**: a member function whose version is chosen at run time from the object's real type.
- **name hiding**: a function in a derived class with the same name as a base-class one hides all the base overloads.
- **NVI**: non-virtual interface; a public non-virtual function calls a private virtual one that derived classes override.
- **default argument**: a parameter value supplied by the caller's static type, not the object's real type.
- **composition**: holding another object as a member instead of inheriting from it.
- **multiple inheritance**: deriving from more than one base class.

## Item 32: Make Sure Public Inheritance Models "is-a"

In C++, **public inheritance has a sacred semantic contract: it models an "is-a" (is a kind of) relationship**.

> **Liskov Substitution Principle (LSP)**:
> Functions that use pointers or references to base classes must be able to use objects of derived classes without knowing it, and without breaking expected invariants.

### The Penguin and Bird Paradox

Everyday linguistic classifications frequently mislead software models:

```cpp
class Bird {
public:
    virtual void fly(); // All birds can fly
};

class Penguin : public Bird { /* ... */ }; // A penguin is a bird (compiles!)
```

Biologically, penguins are birds; in software contracts, penguins cannot fly! If you write:

```cpp
void makeBirdFly(Bird& b) {
    b.fly(); // Contract promises flight capability!
}

Penguin p;
makeBirdFly(p); // What should a penguin do? Throw a runtime error?
```

Throwing an exception in `Penguin::fly()` violates the base contract. Code that compiles cleanly does not guarantee architectural correctness.

**A rigorous domain model separates behavioral capabilities**:

```cpp
class Bird { /* General avian traits (feathers, beaks) */ };

class FlyingBird : public Bird {
public:
    virtual void fly();
};

class Penguin : public Bird {
public:
    void swim(); // Compile-time rejection of flight attempts!
};
```

## Item 33: Avoid Hiding Inherited Names

C++ scope resolution follows an uncompromising rule: **names in an inner scope hide names in an outer scope, regardless of parameter signatures or virtual status**.

Consider this derived class overload trap:

```cpp
class Base {
public:
    virtual void mf1() = 0;
    virtual void mf1(int);
    virtual void mf2();
    void mf3();
    void mf3(double);
};

class Derived : public Base {
public:
    virtual void mf1() override; // Overrides parameterless version only
    void mf3();                  // Defines parameterless version only
    void mf4();
};

Derived d;
int x = 10;

d.mf1();   // Calls Derived::mf1()
// d.mf1(x);  // COMPILE ERROR: Base::mf1(int) is hidden!
d.mf3();   // Calls Derived::mf3()
// d.mf3(x);  // COMPILE ERROR: Base::mf3(double) is hidden!
```

When the compiler resolves `d.mf1(x)`, it searches `Derived`'s local scope. Finding the identifier `mf1`, **name lookup stops immediately**. The compiler never searches `Base` for matching argument overloads.

### Resolving with `using` Declarations

Make hidden base-class overloads visible in derived classes using `using` declarations:

```cpp
class Derived : public Base {
public:
    using Base::mf1; // Expose all Base overloads named mf1 in Derived!
    using Base::mf3; // Expose all Base overloads named mf3 in Derived!

    virtual void mf1() override;
    void mf3();
};

Derived d;
d.mf1(x); // Compiles cleanly and dispatches to Base::mf1(int)!
```

## Item 34: Differentiate Between Interface Inheritance and Implementation Inheritance

C++ provides three distinct levels of inheritance:

1. **Pure Virtual Functions (`virtual void draw() const = 0;`)**:
   - **Purpose**: Inherit **interface only**. Derived classes must supply their own concrete implementations; the base class mandates the contract.
2. **Simple (Impure) Virtual Functions (`virtual void error(const std::string& msg);`)**:
   - **Purpose**: Inherit **interface plus a default implementation**.
   - **Hazard**: If a specialized derived class is introduced and the developer forgets to override the default, the base implementation runs silently (e.g., applying commercial airliner landing behavior to a supersonic jet).
   - **Defensive Pattern**: Make the pure virtual function mandatory while providing the default implementation in a protected non-virtual helper (`defaultFly()`), requiring derived classes to opt-in explicitly.
3. **Non-Virtual Functions (`int objectID() const;`)**:
   - **Purpose**: Inherit **interface plus a mandatory implementation**. Non-virtual functions enforce class invariants across the entire hierarchy and must never be redefined by derived classes.

## Item 35: Consider Alternatives to Virtual Functions

Virtual functions are not the only mechanism for achieving dynamic algorithm customization.

### 1. The Non-Virtual Interface (NVI) Idiom / Template Method Pattern

The **NVI** idiom declares public interfaces as non-virtual functions that wrap private virtual hooks:

<Archify src="./diagrams/nvi-template-method.sequence.json" />

```cpp
class GameCharacter {
public:
    int healthValue() const { // Public non-virtual interface
        // Step 1: Pre-conditions (acquire locks, audit logging)
        doPreamble();

        // Step 2: Invoke customizable private virtual hook
        int retVal = doHealthValue();

        // Step 3: Post-conditions (validate invariants, release locks)
        doPostscript(retVal);

        return retVal;
    }

private:
    virtual int doHealthValue() const {
        return 100; // Default algorithm
    }

    void doPreamble() const {}
    void doPostscript(int val) const {}
};

class BossCharacter : public GameCharacter {
private:
    int doHealthValue() const override {
        return 5000; // Specialized health calculation
    }
};
```

NVI guarantees the base class controls the execution wrapper (locks, validation, metrics) while letting derived classes focus exclusively on localized core algorithmic details.

### 2. Strategy Pattern with `std::function`

Decouple calculation logic completely from class hierarchies:

```cpp
class GameCharacter;
using HealthCalcFunc = std::function<int(const GameCharacter&)>;

int defaultHealthCalc(const GameCharacter& gc);

class GameCharacter {
public:
    explicit GameCharacter(HealthCalcFunc hcf = defaultHealthCalc)
        : healthFunc(std::move(hcf)) {}

    int healthValue() const {
        return healthFunc(*this);
    }

private:
    HealthCalcFunc healthFunc; // Can be swapped dynamically at runtime!
};
```

Individual instances can swap calculation strategies at runtime using lambdas, eliminating rigid inheritance dependencies.

## Item 36: Never Redefine an Inherited Non-Virtual Function

Non-virtual functions are **statically bound**. When invoked through a pointer or reference, the implementation called depends strictly on the pointer's **static type**:

```cpp
class Base {
public:
    void mf(); // Non-virtual function
};

class Derived : public Base {
public:
    void mf(); // Anti-Pattern: Redefining non-virtual member!
};

Derived d;
Base* pb = &d;
Derived* pd = &d;

pb->mf(); // Static binding: calls Base::mf()!
pd->mf(); // Static binding: calls Derived::mf()!
```

Invoking `mf()` on the exact same object `d` produces divergent behavior depending entirely on pointer typing. This violates public inheritance's "is-a" contract. If derived classes need to vary behavior, make the function `virtual`.

## Item 37: Never Redefine a Function's Inherited Default Parameter Value

C++ establishes an unintuitive rule: **virtual functions are dynamically bound, but default parameter values are statically bound**!

```cpp
class Shape {
public:
    enum ShapeColor { Red, Green, Blue };
    virtual void draw(ShapeColor color = Red) const = 0; // Default: Red
};

class Rectangle : public Shape {
public:
    // Flawed: Redefines default parameter value!
    void draw(ShapeColor color = Green) const override;
};

Shape* pr = new Rectangle();
pr->draw(); // Which color is used?
```

Execution analysis:

1. `draw` is virtual: dynamic dispatch correctly executes `Rectangle::draw()`.
2. However, default parameter values are resolved **at compile time based on the static type** (`Shape*`). The default value passed is `Shape::Red`!
3. **Result**: `Rectangle::draw()` executes, but with the base class's default argument `Red`.

**Guideline**: Never redefine default argument values on inherited virtual functions. Use the NVI idiom to bind default parameters to public non-virtual wrapper methods.

## Item 38: Model "has-a" or "is-implemented-in-terms-of" Through Composition

**Composition** means embedding an instance of another class as a member variable.

In domain modeling, composition represents **"has-a"**:

- A `Person` *has-a* `Name` and an `Address`.

In implementation engineering, composition represents **"is-implemented-in-terms-of"**:

- To build a `Set` class, do not inherit publicly from `std::list`. A `std::list` permits duplicates, which violates set invariants.
- Instead, compose: `Set` holds a private `std::list` member and wraps insertion operations with duplicate checks.

## Item 39: Use Private Inheritance Judiciously

When inheritance is marked `private`:

1. The compiler will not convert derived class objects into base class objects (polymorphism is hidden).
2. All inherited public and protected members become `private` in the derived class.

Private inheritance is an **implementation technique**, meaning "is-implemented-in-terms-of". It has no relation to "is-a".

### Composition vs. Private Inheritance

Most of the time, composition is cleaner and decouples better. Private inheritance is justified in two specific scenarios:

1. **Accessing Protected Members or Overriding Virtual Functions**: When an implementation class must customize virtual callbacks from an existing utility.
2. **Empty Base Optimization (EBO)**: An empty class with no non-static data members occupies at least 1 byte as a standalone object, but compilers may give an empty base class subobject zero size. A member of that type cannot get the same treatment (before C++20's `[[no_unique_address]]`, which now covers the member case).

## Item 40: Use Multiple Inheritance Judiciously

Multiple inheritance introduces the **Diamond Inheritance Problem**:

```text
       ┌───────────┐
       │   A (x)   │
       └─────┬─────┘
             │
       ┌─────┴─────┐
       ▼           ▼
 ┌───────────┐ ┌───────────┐
 │     B     │ │     C     │
 └─────┬─────┘ └─────┬─────┘
       │           │
       └─────┬─────┘
             ▼
       ┌───────────┐
       │     D     │
       └───────────┘
```

If `D` accesses field `x` from ancestor `A`, standard multiple inheritance embeds two separate copies of `A` inside `D`.

### Virtual Base Classes

To unify the ancestor subobject, inherit virtually: `class B : virtual public A`. However, virtual inheritance incurs tradeoffs:

- Increases object memory footprint (stores virtual base table pointers).
- Slows member access via pointer indirections.
- Requires the most derived class (`D`) to initialize virtual base classes directly.

**Best Practice**: Restrict multiple inheritance to **publicly inheriting one or more pure abstract interfaces, combined with privately inheriting a utility class for implementation details**.

## Summary Checklist

| Principle | Guideline | Pitfall to Avoid |
| :--- | :--- | :--- |
| **Model is-a** | Public inheritance must satisfy Liskov Substitution Principle | Modeling non-flying penguins as flying birds |
| **Un-Hide Names** | Use `using Base::function;` to expose hidden base overloads | Derived declarations masking overloaded base methods |
| **Inheritance Tiers** | Differentiate pure virtual (interface), simple virtual (default), non-virtual (mandatory) | Leaving critical base algorithms open to unintended overrides |
| **Virtual Alternatives**| Prefer NVI idiom or Strategy pattern with `std::function` | Rigid virtual hierarchies lacking wrapper validation |
| **Non-Virtual Immutability** | Never redefine inherited non-virtual methods | Divergent behavior between base and derived pointers |
| **Default Parameters** | Never redefine default arguments on virtual functions | Static argument binding creating argument mismatches |
| **Composition over Inheritance** | Use composition for has-a and implementation reuse | Publicly inheriting containers to implement sets |
| **Multiple Inheritance**| Combine pure abstract interfaces with private utility mixins | Complex diamond inheritance hierarchies |
