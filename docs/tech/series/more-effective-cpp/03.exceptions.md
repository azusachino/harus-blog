Exception handling decoupled normal execution flow from error recovery in C++. It allows low-level runtime errors to propagate across stack frames to handlers equipped to resolve them. However, non-local control transfers introduce subtle traps: **what happens when constructors throw? Why do throwing destructors abort the process? And how does throwing an exception differ fundamentally from invoking a virtual function?**

---

## Before you start

An exception is a way for a function to say "I cannot continue" without returning an error code. When code runs `throw`, execution jumps out of the current function, then the caller, and onward until some `catch` handles it. Every local object in the functions it leaves is destroyed on the way. That cleanup is what saves you and also what makes exceptions risky. Suppose a constructor allocates one buffer, then a second `new` throws. The object was never fully built, so its destructor will not run, and the first buffer leaks. This chapter shows how to write code that stays correct when any line can throw.

You should know RAII, the idea of cleanup in destructors, from [Effective C++ chapter 03](/tech/series/effective-cpp/03.resource-management/). The previous chapter in this series is [chapter 02](/tech/series/more-effective-cpp/02.operators/).

Terms used in this chapter:

- **exception**: an object thrown with `throw` to signal an error that the current function cannot handle.
- **stack unwinding**: the process of leaving functions one by one while destroying their local objects after a throw.
- **`catch`**: the block that handles a thrown exception of a matching type.
- **RAII**: tying a resource's release to an object's destructor.
- **smart pointer**: an object that owns heap memory and frees it automatically.
- **`std::terminate`**: the function that ends the program; it runs if a destructor throws while another exception is already unwinding.
- **`noexcept`**: a promise that a function will not throw an exception.
- **exception specification**: a declaration of what a function may throw; `noexcept` is its modern form.

## Item 9: Use Destructors to Prevent Resource Leaks

Without RAII, resource cleanup relies on manual statements placed before every return path:

```cpp
void processFile(const char* fileName) {
    FILE* fp = fopen(fileName, "r");
    // High-risk parsing operations...
    if (ferror(fp)) {
        fclose(fp); // Tedious, error-prone manual cleanup
        return;
    }
    // ... more processing ...
    fclose(fp);
}
```

If an exception is thrown inside a sub-operation, control immediately unwinds the current stack frame toward the nearest `catch` block. All subsequent cleanup statements (`fclose`, `delete`, `unlock`) are bypassed, leaking resources permanently.

**The Invariant Guarantee of C++**:
Regardless of how control exits a scope—via regular `return`, `break`, or exception stack unwinding—**destructors of all fully constructed stack objects are guaranteed to execute**. Wrapping raw handles in RAII objects is the only foolproof defense against exception-induced leaks.

## Item 10: Prevent Resource Leaks in Constructors

Constructor exceptions present one of the most subtle memory leak risks in C++:

```cpp
class BookEntry {
public:
    BookEntry(const std::string& name, const std::string& imageFileName,
              const std::string& audioClipFileName)
        : theName(name),
          theImage(new Image(imageFileName)),          // Allocation 1
          theAudioClip(new AudioClip(audioClipFileName)) // Allocation 2
    {}

    ~BookEntry() {
        delete theImage;
        delete theAudioClip;
    }
private:
    std::string theName;
    Image* theImage;
    AudioClip* theAudioClip;
};
```

Suppose `new AudioClip` exhausts memory and throws `std::bad_alloc`. What happens to `theImage`?

### The Core Invariant of the C++ Object Model

> **An object is considered fully constructed only when its constructor finishes execution without throwing an exception**.

If an exception escapes a constructor:

1. In the eyes of the C++ runtime, the object **never existed**.
2. Consequently, **its destructor (`~BookEntry()`) will never run**.

The memory allocated for `theImage` in step 1 is permanently orphaned!

### The Idiomatic Solution: Smart Pointer Members

While function try-blocks can manually catch and roll back allocations, the cleanest and most robust solution uses **smart pointer members**:

```cpp
class BookEntry {
public:
    BookEntry(const std::string& name, const std::string& imageFileName,
              const std::string& audioClipFileName)
        : theName(name),
          theImage(std::make_unique<Image>(imageFileName)),
          theAudioClip(std::make_unique<AudioClip>(audioClipFileName)) {}

private:
    std::string theName;
    std::unique_ptr<Image> theImage;         // Managed member
    std::unique_ptr<AudioClip> theAudioClip; // Managed member
};
```

Standard C++ guarantees that when a constructor throws, **all subobjects and members successfully constructed before the exception are destroyed in reverse order of declaration during stack unwinding**. Because `theImage` is a `std::unique_ptr`, its destructor runs automatically, releasing the image buffer cleanly without custom cleanup boilerplate.

## Item 11: Prevent Exceptions from Leaving Destructors

Destructors execute in two distinct contexts:

1. **Normal Flow**: An object leaves scope or is explicitly deleted.
2. **Stack Unwinding**: An active exception is propagating, and the runtime is destroying local objects on exiting stack frames.

### Two Simultaneous Exceptions: Immediate Termination

If a destructor invoked during stack unwinding throws a second unhandled exception:

> **C++ strictly forbids multiple active unhandled exceptions**. Encountering two simultaneous active exceptions leaves the runtime with no safe recovery path, prompting an immediate call to `std::terminate()`.

All resource cleanup in destructors must be wrapped in `try...catch` blocks to swallow or log failures:

```cpp
~DBConn() noexcept {
    try {
        db.close();
    } catch (const std::exception& e) {
        std::cerr << "Destructor caught error during close: " << e.what() << '\n';
    }
}
```

In modern C++11, destructors are implicitly marked `noexcept`. Any exception that escapes triggers immediate program termination.

## Item 12: Understand How Throwing Differs from Parameter Passing and Virtual Dispatch

While `throw Widget()` superficially resembles calling a function `doSomething(Widget())`, their operational semantics differ fundamentally:

### 1. Exception Objects Are Always Copied

When passing a local object to a function by value, it is destroyed when the function returns. In contrast, thrown exception objects must survive beyond the exited stack frame until handled by a matching `catch` block.

**Regardless of whether you throw by value, pointer, or reference, the compiler copies the thrown entity into a dedicated exception storage area via its copy/move constructor**.

### 2. Restrictive Type Conversions in Catch Blocks

Ordinary functions support implicit conversions (e.g., converting `int` to `double` or invoking non-explicit single-argument constructors). In contrast, `catch` blocks prohibit almost all conversions:

- Base class references/pointers can catch derived exceptions.
- Non-const exceptions can convert to const references (`catch (const Widget&)`).
- A typed pointer can be caught by a `catch (const void*)` clause.
- All other types must match exactly (e.g., `catch (double)` will not catch a thrown `int`).

### 3. First-Fit Matching vs. Best-Match Dispatch

Virtual function calls resolve using **best-match dynamic dispatch**. In contrast, `catch` blocks evaluate using **first-fit sequential evaluation** from top to bottom. If a base class `catch` block appears before a derived class `catch` block, the derived block becomes dead code.

## Item 13: Catch Exceptions by Reference-to-Const

There are three ways to write a catch clause:

- **Catch by Pointer (`catch (Widget* pw)`)**: Throwing pointers to stack variables produces dangling pointers after stack unwinding. Throwing pointers to heap objects (`throw new Widget`) creates ownership ambiguity over who must call `delete`.
- **Catch by Value (`catch (Widget w)`)**: Incurs two copy operations and causes **object slicing**: derived exception types are sliced down to base types, stripping specialized fields and virtual methods.
- **Catch by Reference-to-Const (`catch (const std::exception& ex)`)**:

```cpp
try {
    executeTransaction();
} catch (const std::runtime_error& ex) {
    std::cerr << "Runtime failure: " << ex.what() << '\n'; // Preserves polymorphism, zero copy overhead
}
```

Catching by reference-to-const prevents slicing, avoids unnecessary copies, and ensures derived polymorphic methods execute properly.

## Item 14: Use Exception Specifications Judiciously (Embrace noexcept)

In C++98, dynamic exception specifications declared allowable exception types:

```cpp
void f() throw(int, std::bad_alloc); // C++98: promised to throw only int or bad_alloc
```

This feature proved problematic: the specification was enforced at runtime rather than compile time, with a cost on every call. If an unlisted exception escaped, the program invoked `std::unexpected()`, which by default terminated execution. Dynamic exception specifications were deprecated in C++11 and removed in C++17.

Modern C++ replaces dynamic specifications with the boolean **`noexcept`** specifier:

```cpp
void swap(Widget& lhs, Widget& rhs) noexcept;
```

`noexcept` provides a strong contractual guarantee. Crucially, it enables performance optimizations in standard containers: `std::vector` resize operations only use move constructors if they are marked `noexcept`. If a move constructor can throw and the type is copyable, `std::vector` falls back to copying to preserve the strong exception safety guarantee (this is `std::move_if_noexcept`).

## Item 15: Understand the Costs of Exception Handling

Exceptions introduce two architectural tradeoffs:

1. **Binary Size Overhead**: Modern compilers use **table-based exception handling** (such as DWARF on Linux or SEH on Windows). On the happy path where no exceptions are thrown, execution incurs zero instruction overhead ("zero-cost exceptions"). However, the compiler must generate unwind tables and cleanup descriptors, increasing binary size. Older measurements put the growth at roughly 5% to 10%; measure your own toolchain.
2. **Unwinding Latency**: When an exception is thrown, traversing unwind tables, restoring CPU registers, and running destructors across stack frames is orders of magnitude slower than a simple branch instruction.

**Guideline**: Reserve exceptions for genuinely exceptional failure conditions. Never use exceptions for normal control flow or expected loop terminations.

## Summary Checklist

| Principle | Guideline | Antipattern to Avoid |
| :--- | :--- | :--- |
| **RAII Guard** | Manage resources in stack object destructors | Manual `delete` or `close` before returns |
| **Constructor Safety**| Use smart pointer members for dynamic resources | Raw pointer allocations in initialization lists |
| **Destructor Invariants**| Never allow exceptions to escape destructors | Throwing exceptions during stack unwinding (`std::terminate`) |
| **Exception Handling**| Catch exceptions by `const&` | Catching by value (slicing) or pointer (leaks) |
