异常处理（Exception Handling）彻底革新了 C/C++ 传统的错误码检查范式。它将“正常执行流”与“异常恢复流”在物理层面割裂开来，让深层嵌套的错误能够越级传递到具备处理能力的顶层。然而，这种跨越栈帧的非局部跳转也带来了巨大的工程挑战：**如果构造函数中途抛出异常怎么办？析构函数中抛出异常为什么会导致整个进程瞬间暴毙？抛出异常与传递普通函数参数有什么本质区别？**

---

## 利用 destructors 避免泄露资源

在没有异常机制的时代，或者在缺乏 RAII 意识的代码中，资源清理往往严重依赖函数末尾的手工收尾：

```cpp
void processFile(const char* fileName) {
    FILE* fp = fopen(fileName, "r");
    // 执行一长串高风险的数据解析...
    if (ferror(fp)) {
        fclose(fp); // 必须在每一个提前 return 处手动补全释放
        return;
    }
    // ...更多处理...
    fclose(fp);
}
```

一旦函数中间调用的第三方模块抛出了 C++ 异常，执行流会瞬间跨越当前函数栈帧，直奔外层的 `catch` 块。位于后方的所有 `fclose`、`delete`、`unlock` 将被彻底绕过，发生确凿的资源泄漏。

**C++ 运行时的铁律承诺**：无论控制流如何离开一个函数作用域（无论正常 `return`、`goto`、还是异常栈展开），**已完整构造的栈上局部对象的析构函数必定会被确定性调用**。将资源封装进 RAII 对象的析构函数，是抵御异常导致资源泄漏的唯一根本解法。

## 在 constructors 内阻止资源泄露

这是 C++ 对象模型中最反直觉、最隐秘的内存泄漏暗礁。

思考如下包含两个动态分配成员的类：

```cpp
class BookEntry {
public:
    BookEntry(const std::string& name, const std::string& imageFileName,
              const std::string& audioClipFileName)
        : theName(name),
          theImage(new Image(imageFileName)),          // 动态分配成员 1
          theAudioClip(new AudioClip(audioClipFileName)) // 动态分配成员 2
    {}

    ~BookEntry() {
        delete theImage;
        delete theAudioClip;
    }
private:
    std::string theName;
    Image* theImage;
    AudioClip* theAudioClip;
};
```

假设在执行 `new AudioClip` 时，系统内存耗尽，抛出了 `std::bad_alloc` 异常。此时会发生什么？

### C++ 对象模型的根本规则

> **在 C++ 中，一个对象只有在其构造函数完全执行完毕且成功退出大括号的一瞬间，才被视为“已被完整构造（Fully Constructed）”**。

如果一个对象的构造函数在执行中途被异常打断：

1. 这个对象在语言层面上**从未真正存在过**！
2. 因此，C++ 运行时**坚决不会调用该对象的析构函数**（`~BookEntry()` 永远不会被触发）！

结果是灾难性的：由于 `~BookEntry()` 未被执行，前面第一步成功分配出来的 `theImage` 裸指针瞬间沦为不可回收的孤魂野鬼，发生彻底的内存泄漏！

### 终极解法：使用智能指针管理成员

虽然可以用复杂的 `try...catch` 块（或函数级 try-block）包裹每一个构造阶段并手动回滚，但最简洁、最鲁棒的方案是**永远使用 RAII 智能指针作为类成员**：

```cpp
class BookEntry {
public:
    BookEntry(const std::string& name, const std::string& imageFileName,
              const std::string& audioClipFileName)
        : theName(name),
          theImage(std::make_unique<Image>(imageFileName)),
          theAudioClip(std::make_unique<AudioClip>(audioClipFileName)) {}
private:
    std::string theName;
    std::unique_ptr<Image> theImage;         // RAII 成员
    std::unique_ptr<AudioClip> theAudioClip; // RAII 成员
};
```

语言规范保证：虽然宿主类自身的析构函数不会运行，但**在异常抛出之前已经成功构造完成的子对象与成员变量，会随着栈展开被逐一逆序析构**！`theImage` 作为 `unique_ptr` 实例，其内部持有的析构函数会被自动调用，彻底释放底层图片内存，达成真正的零泄漏。

## 禁止异常流出 destructors 之外

析构函数在两种场景下会被调用：

1. 正常执行：对象离开其声明的作用域，或被显式 `delete`。
2. 异常栈展开（Stack Unwinding）：某个异常正在向外传播，运行时正在销毁途中各个栈帧内的局部对象。

### 两个异常并存时的终极审判

如果析构函数本身是在第二种场景（处理栈展开）中被调用的，而其内部又抛出了第二个新的异常：

> **C++ 绝不允许两个处于活跃状态的未捕获异常同时存在**。此时运行时系统别无选择，只能立刻调用 `std::terminate()` 强制崩溃整个进程！

因此，**绝不允许让任何异常逃离析构函数的边界**。所有可能抛出异常的清理动作（如关闭网络连接、刷新文件缓冲区），必须在析构函数内部用 `try...catch(...)` 完全消化、记录日志，或者为客户提供一个普通成员函数在正常执行流中主动处理。

## 理解抛出异常与传递参数及调用虚函数的差异

从表面语法上看，抛出异常 `throw Widget()` 与函数调用传参 `doSomething(w)` 极为相似，但在底层语义上存在本质割裂：

### 1. 异常对象永远会被复制

当你传递一个局部对象作为函数实参时，函数执行完毕后局部对象随之销毁；但对于抛出的异常对象，它必须脱离当前栈帧一直向外层传播。

因此，**无论你抛出的是值、指针还是引用，编译器都必定会在专用暂存区（Exception Storage）通过拷贝构造函数复制一份异常对象副本**。即使传入 `catch (Widget& w)`，这个 `w` 引用的也是暂存区里的那份副本，而非早已被栈展开销毁的局部变量。

### 2. 捕获类型转换的严格限制

普通函数在匹配实参时支持广泛的隐式类型转换（例如 `int` 转 `double`，或者单参构造函数的类型提升）；而在 `catch` 匹配阶段，**编译器严禁绝大多数隐式转换**！除了以下两种转换外，其他类型必须完全精确匹配：

- 允许基类指针/引用捕获派生类异常。
- 允许非常量类型转换为常量类型（如 `catch (const Widget&)`）。

### 3. 匹配顺序与虚函数分发完全相反

虚函数的分发机制是“最佳匹配（Best Match）”；而 `catch` 块的匹配顺序是纯粹的**自上而下的首个匹配（First Fit）**。如果把捕获基类的 `catch` 块写在派生类之前，派生类的 `catch` 块将永远处于被遮蔽的死代码状态！

## 以 reference 方式捕获 exceptions

在编写 `catch` 语句时，有三种选择：按指针捕获、按值捕获、以及按引用捕获。

- **按指针捕获（Catch by pointer）**：如果抛出一个指向局部对象的指针，栈展开后指针瞬间悬垂；如果是在堆上 `new` 出异常对象抛出指针，捕获端根本搞不清楚谁来负责 `delete`，极易引发内存泄漏。
- **按值捕获（Catch by value）**：会触发两次对象深拷贝；更致命的是会发生**对象切割（Object Slicing）**，如果抛出的是派生类异常，捕获端拿到的基类对象会被切除所有派生类特有字段和虚函数行为。
- **按常量引用捕获（Catch by reference to const）**：

  ```cpp
  catch (const std::exception& ex) {
      std::cerr << ex.what(); // 多态行为完美保留，零多余深拷贝！
  }
  ```

## 明智运用 exception specifications 与现代 noexcept

在 C++98 时代，语言引入了动态异常说明（Dynamic Exception Specifications）：

```cpp
void f() throw(int, std::bad_alloc); // 宣称只抛出 int 或 bad_alloc
```

实践证明这是一项失败的设计：编译器并不会在编译期验证函数的抛出行为；一旦函数在运行期抛出了列表之外的异常，系统会直接调用 `std::unexpected()` 导致崩溃。

在现代 C++11 中，动态异常说明已被彻底废弃并移除，取而代之的是纯粹的布尔化契约——**`noexcept`**：

```cpp
void swap(Widget& lhs, Widget& rhs) noexcept; // 保证绝不抛出任何异常
```

声明为 `noexcept` 的函数不仅意图明确，更为标准库容器（如 `std::vector` 扩容时的移动语义优化）提供了至关重要的安全依据：只有当移动构造函数为 `noexcept` 时，`vector` 扩容才会使用高效的 `std::move`，否则为了保证强烈异常安全，只能退化为低效的深拷贝。

## 了解异常处理的成本

异常并非免费的午餐，它的成本主要体现为两方面：

1. **空间与二进制体积开销**：现代编译器普遍采用基于表的异常处理模型（Table-based Exception Handling，如 DWARF / SEH）。虽然在没有异常发生的正常路径上几乎零指令开销（Zero-Cost Exceptions），但编译器必须生成庞大的栈展开表（Unwind Tables）与清理描述符，使得最终的二进制文件体积显著增大。
2. **栈展开与缓存冲击**：一旦异常真正被触发，运行期展开栈帧、解析表结构、查找匹配 `catch` 块的耗时，比普通的条件分支和函数跳转慢几个数量级。

**结论**：将异常严格限制在真正的**异常突发情况（Exceptional Events）**上，绝不要把异常当作常规业务控制流的跳转工具。
