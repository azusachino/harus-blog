## 局域化未来可能发生的变动（在未来时态下编程）

所谓的“在未来时态下编程（Program in the Future Tense）”，核心理念非常质朴：**承认变化是软件世界唯一的永恒**。今天为你一个人编写的独立脚本，明天可能被纳入公司的基础设施；今天被认定“绝不需要被继承”的具体类，下个月可能就会出现定制派生需求。

### 1. 提供完备的接口组合

如果为一个类重载了 `operator==`，就应当顺理成章地重载 `operator!=`；如果提供了 `operator+`，就应当同步提供 `operator+=`。不要因为“当前项目暂不需要”就偷工减料留下一半接口。残缺的抽象只会给未来的协作同事埋下反直觉的陷阱。

### 2. 严守类的封装不变量

不要为了图一时之快暴露私有数据成员（即使是暴露为 `protected`）。一旦实现细节被派生类或外部广泛依赖，任何微小的内部重构都会演化为动辄波及全库的破坏性变更。

### 3. 绝不假设对象不会被复制

如果类内持有着独占的底层指针资源，且该类未被声明为禁止复制，那么一定要显式实现深拷贝构造函数或将其 `= delete`。永远不要抱有侥幸心理：“调用者知道这个类不能复制，他们肯定不会手滑拷贝的”。在团队协作中，墨菲定律从不缺席。

## 将非尾端类（Non-leaf Classes）设计为抽象类

考虑一个图形库中具体的矩形与正方形继承体系：

```cpp
class Rectangle { ... }; // 具体的具象类（Concrete Class）

class Square : public Rectangle { ... }; // 派生自具象类
```

让一个具象类直接继承自另一个具象类，会在赋值操作符上引发棘手的**部分赋值（Partial Assignment）**漏洞：

```cpp
void assignObject(Rectangle& lhs, const Rectangle& rhs) {
    lhs = rhs; // 赋值操作
}

Square s1, s2;
assignObject(s1, s2); // 灾难：仅执行了 Rectangle::operator=，Square 特有成员完全未被赋值！
```

### 抽象基类隔离方案

消除此类弊端的工业级范式是：**将继承体系中的所有非叶子节点（Non-leaf Classes）全部设计为纯抽象类（Abstract Base Classes）**：

```text
       ┌──────────────────────┐
       │ AbstractShape (抽象)  │
       └──────────┬───────────┘
                  │
        ┌─────────┴─────────┐
        ▼                   ▼
┌───────────────┐   ┌───────────────┐
│   Rectangle   │   │    Square     │
│  (具象叶子类)  │   │  (具象叶子类)  │
└───────────────┘   └───────────────┘
```

如果一个基类中所有的业务虚函数都具有合理的默认实现，如何将它强制转为纯抽象类？

**技巧：声明纯虚析构函数（Pure Virtual Destructor）**：

```cpp
class AbstractShape {
public:
    virtual ~AbstractShape() = 0; // 纯虚析构函数：迫使类变为纯抽象！
};

// 关键：必须在类外提供纯虚析构函数的空实现！
AbstractShape::~AbstractShape() = default;
```

因为派生类在析构时必定会链式向上调用基类的析构函数，如果缺乏函数体定义，链接器会报未解析符号错误。这样既成功阻止了基类被直接实例化，又确保了析构链路的绝对安全。

## 如何在同一个程序中结合 C++ 和 C

大型基础系统（如操作系统调用、数据库存储引擎、高性能网络库）往往由 C 与 C++ 混合构筑。跨越这两种语言的边界，需要坚守四道物理防线：

### 1. 符号重命名机制（Name Mangling）与 extern "C"

C++ 支持函数重载，因此编译器会将函数名与参数类型编码为一个混淆后的内部符号（例如 `f(int)` 编码为 `_Z1fi`）；而 C 编译器只会生成原样符号 `_f`。

为了让 C++ 编译器以 C 的规约处理接口，必须使用 `extern "C"`：

```cpp
#ifdef __cplusplus
extern "C" {
#endif

// 供 C 和 C++ 共同包含的标准 C 接口头文件
void* allocateBuffer(size_t size);
int processNetworkPacket(const uint8_t* data, size_t len);

#ifdef __cplusplus
}
#endif
```

### 2. 二进制内存布局契约（Standard-Layout Types）

只有满足 C++ **标准布局（Standard Layout）**的类/结构体，才能够跨语言传递给 C 语言函数：

- 没有虚函数、没有虚表指针（`vptr`）。
- 没有虚基类。
- 所有非静态数据成员具有相同的访问控制级别（全部为 `public`）。

### 3. 内存管理归属边界

**C 与 C++ 的内存管理器严禁交叉混用**：

- 在 C 端由 `malloc` / `calloc` 分配的内存，必须由 C 端的 `free` 释放。
- 在 C++ 端由 `new` / `new[]` 分配的内存，必须由 C++ 端的 `delete` / `delete[]` 释放。
- 绝对不要把 `new` 出来的对象地址丢给 `free`，反之亦然。

### 4. 严禁 C++ 异常跨越 C 语言栈帧

C 语言运行时根本没有栈展开表（Unwind Tables）的概念。如果一个 C++ 回调函数在被 C 库代码调用期间抛出未捕获的 C++ 异常：

- 异常试图穿透 C 语言编译的机器码栈帧向外传播。
- 其结果在绝大多数操作系统平台上属于未定义行为，通常直接引发段错误或不可恢复的栈损坏。

**铁律**：所有暴露给 C 语言调用的 C++ 回调入口，必须在最外层用 `try...catch(...)` 进行全面防卫，将异常在边界内截断并转换为 C 风格的整数错误码。

## 让自己熟悉语言标准的最新发展

《More Effective C++》成书于 C++ 语言标准化前夕。站在现代 C++ 的高台回望，Scott Meyers 在书中探索的诸多先驱设计模式，早已被正式吸收并升华为了 C++ 核心语言特性的基石：

- **智能指针演进**：书中手写的 `RCPtr` 与引用计数基类，在 C++11 中演进为成熟的 `std::unique_ptr`、`std::shared_ptr` 与 `std::weak_ptr`。
- **类型萃取与编译期分支**：繁琐的 Tag Dispatching 被 C++17 的 `if constexpr` 与 C++20 的 `Concepts` 彻底颠覆，编译期多态的书写如普通代码般自然直观。
- **移动语义彻底解放 RVO**：C++11 右值引用（`&&`）与移动语义的引入，使得即使无法触发 RVO 的场景也能通过零拷贝移动将资源转移，彻底化解了临时对象带来的性能梦魇。
- **协程、模块与无畏并发**：C++20 的 `Modules` 终结了文本包含的漫长编译，`Coroutines` 将异步网络 IO 的复杂度降至线性逻辑。

学透经典著作的深层意义，不在于死记硬背过去的特定语法补丁，而在于**理解那些在严苛物理资源约束下诞生的权衡智慧**。掌握了底层的对象模型与性能本质，无论语言标准如何推陈出新，你都能在瞬息万变的技术浪潮中锚定系统的最优解。
