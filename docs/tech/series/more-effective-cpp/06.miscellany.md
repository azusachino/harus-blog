After surveying operator contracts, exception boundaries, low-level efficiency, and advanced idioms, Scott Meyers' final chapter addresses long-term software architecture: **how does code withstand the erosion of time?** When requirements change, class hierarchies evolve, and modern C++ must interface with legacy C libraries, what defensive boundaries should system architects construct? This chapter explores programming in the future tense and navigating inter-language FFI boundaries.

---

## Before you start

Code outlives the plan it was written for. A class you wrote for one project gets reused, someone derives from it, and the program is linked against a C library from the 1980s. This last chapter is about writing with that in mind. Give a class the operators people will expect, make base classes abstract so nobody instantiates them by accident, and know what changes at the boundary between C and C++. A concrete example of that boundary: C++ allows two functions both named `process`, so the compiler encodes the argument types into the symbol name, and a C library cannot find it unless you say otherwise.

Read [chapter 05](/tech/series/more-effective-cpp/05.techniques/) first, as it introduces the class-hierarchy techniques this one relies on.

Terms used in this chapter:

- **programming in the future tense**: writing code on the assumption that requirements will change and the class will be used in ways you did not plan.
- **abstract class**: a class with at least one pure virtual function; it cannot be instantiated.
- **pure virtual function**: a virtual function declared with `= 0` that derived classes must override.
- **leaf class**: a class nothing else derives from, the bottom of a hierarchy.
- **name mangling**: the encoding of a function's name and parameter types into a single symbol, which makes overloading possible.
- **`extern "C"`**: a declaration that tells the C++ compiler to use C naming and linkage for the enclosed functions.
- **linkage**: the rules for how names in separately compiled files are matched up by the linker.

## Item 32: Program in the Future Tense

The guiding philosophy of "programming in the future tense" acknowledges a fundamental truth: **software requirements are guaranteed to evolve**. A standalone utility class written today will eventually be integrated into broader frameworks; a class assumed to be final may eventually be extended.

### 1. Provide Complete Operator Suites

If an arithmetic class overloads `operator==`, provide `operator!=`. If it overloads `operator+`, provide `operator+=`. Avoid leaving half-implemented interface suites merely because immediate code does not use them:

```cpp
class ComplexNumber {
public:
    ComplexNumber(double real, double imag);

    ComplexNumber& operator+=(const ComplexNumber& rhs) noexcept;
    friend ComplexNumber operator+(ComplexNumber lhs, const ComplexNumber& rhs) noexcept {
        lhs += rhs;
        return lhs;
    }

    friend bool operator==(const ComplexNumber& lhs, const ComplexNumber& rhs) noexcept;
    friend bool operator!=(const ComplexNumber& lhs, const ComplexNumber& rhs) noexcept {
        return !(lhs == rhs);
    }
};
```

In modern C++20, the three-way comparison operator (`operator<=>`, "spaceship operator") simplifies this by synthesizing all six relational operators from a single definition:

```cpp
#include <compare>

class ModernPoint {
public:
    int x;
    int y;
    auto operator<=>(const ModernPoint&) const = default; // Generates ==, !=, <, <=, >, >= automatically!
};
```

### 2. Guard Encapsulation Invariants

Never expose data members as `protected` to give derived classes convenient access. Once derived classes take dependencies on internal layout details, future internal refactoring becomes impossible without breaking subclasses.

### 3. Never Assume Objects Will Not Be Copied

If a class manages raw resources, explicitly implement deep copy constructors or delete them (`= delete`). Never rely on unspoken team assumptions that callers will avoid copying.

## Item 33: Make Non-Leaf Classes Abstract

Consider an inheritance hierarchy where one concrete class derives directly from another concrete class:

```cpp
class Rectangle { /* Concrete representation with width/height */ };

class Square : public Rectangle { /* Concrete square with side constraint */ };
```

Deriving a concrete class from another concrete class introduces the **Partial Assignment** defect:

```cpp
void assignObject(Rectangle& lhs, const Rectangle& rhs) {
    lhs = rhs; // Polymorphic assignment
}

Square s1, s2;
assignObject(s1, s2); // Defect: executes Rectangle::operator=; Square-specific fields are never assigned!
```

### The Abstract Base Class Paradigm

Resolve this issue by enforcing that **all non-leaf classes in an inheritance hierarchy are abstract**:

```text
       ┌────────────────────────┐
       │ AbstractShape (Pure)   │
       └───────────┬────────────┘
                   │
         ┌─────────┴─────────┐
         ▼                   ▼
 ┌───────────────┐   ┌───────────────┐
 │   Rectangle   │   │    Square     │
 │ (Concrete)    │   │ (Concrete)    │
 └───────────────┘   └───────────────┘
```

If a base class contains no naturally pure virtual business methods, how can you force it to be an abstract class?

### The Pure Virtual Destructor Idiom

Declare the base destructor **pure virtual**, but provide an **out-of-line definition**:

```cpp
class AbstractShape {
public:
    virtual ~AbstractShape() = 0; // Pure virtual: forces class to be abstract!
};

// CRITICAL: Must provide an out-of-line empty definition!
AbstractShape::~AbstractShape() = default;
```

Because derived class destructors always chain upward to invoke base class destructors, omitting the base definition causes unresolved symbol linker errors. This idiom prevents direct instantiation of `AbstractShape` while guaranteeing safe polymorphic destruction chains.

## Item 34: Understand How to Combine C++ and C in the Same Program

Production systems (operating system kernels, database storage engines, network stacks) frequently bridge C and C++. Navigating this boundary requires strict adherence to four rules (Meyers' original list also covers static initialization: have a C++ `main`, or the C++ static objects may never be constructed):

### 1. Name Mangling and `extern "C"`

C++ supports function overloading, so compilers mangle function names and parameter types into encoded symbol names (e.g., `process(int)` becomes `_Z7processi`). C compilers generate plain symbols (e.g., `process`, with a leading underscore on some platforms).

Use `extern "C"` to instruct the C++ compiler to emit unmangled C linkage conventions:

```c
#ifdef __cplusplus
extern "C" {
#endif

void* allocateSystemBuffer(size_t size);
int processNetworkPacket(const uint8_t* buffer, size_t length);

#ifdef __cplusplus
}
#endif
```

### 2. Standard-Layout Types

Only types meeting the C++ **Standard-Layout** criteria can be passed safely across C ABI boundaries:

- No virtual functions and no virtual table pointers (`vptr`).
- No virtual base classes.
- All non-static data members share the same access control (`public`).
- No non-standard-layout members or bases, and no base class with data members when the derived class has them as well (the full list is in the language standard).

```cpp
struct PacketHeader { // Standard-layout struct: safe for C FFI
    uint32_t magic;
    uint16_t length;
    uint16_t checksum;
};
static_assert(std::is_standard_layout_v<PacketHeader>, "Must be standard layout for C ABI compatibility");
```

### 3. Strict Memory Allocation Boundaries

**Never cross allocator boundaries**:

- Memory allocated via C's `malloc` / `calloc` must be freed via `free`.
- Memory allocated via C++'s `new` / `new[]` must be deallocated via `delete` / `delete[]`.
- Passing memory from `new` to `free` (or vice-versa) corrupts allocator free-lists and triggers heap corruption.

### 4. Exceptions Must Never Escape Across C Stack Frames

C code usually carries no cleanup or unwind information. If a C++ callback invoked by a C library throws an exception that propagates through C stack frames, the behavior is undefined: typically the process terminates, or the C frames are skipped without running their cleanup.

**Golden Rule**: Wrap all C-facing C++ callbacks in top-level `try...catch(...)` guards:

```cpp
extern "C" int cCallbackHandler(void* userData) noexcept {
    try {
        auto* obj = static_cast<MyService*>(userData);
        obj->executeOperation();
        return 0; // Success
    } catch (const std::exception& e) {
        logError(e.what());
        return -1; // Convert exception to C-style error code
    } catch (...) {
        return -2; // Unknown error
    }
}
```

## Item 35: Familiarize Yourself with Language Evolution

Scott Meyers wrote *More Effective C++* during the formative years of standard C++. Many of the manual idioms pioneered in the book have been absorbed into modern ISO C++:

- **Smart Pointers**: Manual reference counting (`RCPtr`) evolved into standardized `std::unique_ptr`, `std::shared_ptr`, and `std::weak_ptr`.
- **Compile-Time Dispatch**: Tag dispatching has been superseded by `if constexpr` (C++17) and `Concepts` (C++20).
- **Move Semantics & RVO**: C++11 rvalue references (`&&`) and C++17 guaranteed copy elision eliminate the performance penalties of temporary objects.
- **Coroutines & Modules**: C++20 Modules replace textual `#include` files with compile-firewalled translation units, and Coroutines convert asynchronous callbacks into sequential logic.

Understanding these idioms provides insight into the mechanical constraints of hardware, memory layouts, and type systems. With this foundation, you can navigate both legacy codebases and modern standards with clarity.

## Summary Checklist

| Principle | Guideline | Hazard to Avoid |
| :--- | :--- | :--- |
| **Future Tense** | Provide complete operator sets (`==` and `!=`); enforce encapsulation | Partial interfaces that break developer expectations |
| **Abstract Non-Leaf** | Make non-leaf classes abstract using pure virtual destructors | Partial assignment defects when slicing derived classes |
| **C / C++ Linkage** | Wrap C declarations in `extern "C"`; use standard-layout structs | Linker errors caused by C++ name mangling |
| **Allocator Segregation**| Never mix `malloc`/`free` with `new`/`delete` | Heap corruption and invalid free-list offsets |
| **FFI Exception Barrier**| Catch all exceptions at C callback boundaries (`try...catch(...)`) | Stack unwinding through C frames causing crashes |
