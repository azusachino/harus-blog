C++ is renowned for its expressive power. When language primitives do not directly accommodate complex architectural constraints, seasoned engineers leverage **idioms**—patterns rooted in type system mechanics and object layouts. From polymorphic cloning and instance thresholds to proxy classes and multi-object double dispatch, this chapter reveals the mechanics behind these foundational techniques.

---

## Before you start

An idiom is a known way to get something the language does not give you directly. Say a drawing program holds a `Shape*` that really points at a `Circle`, and the user chooses "duplicate". A constructor cannot be virtual, so how do you copy the right kind of object without knowing its type? The usual answer is a virtual `clone()` function that each class implements by copying itself. The chapter collects a set of such techniques: smart pointers, reference counting, objects that stand in for other objects, and ways to choose behavior based on two objects at once.

Read [chapter 04](/tech/series/more-effective-cpp/04.efficiency/) first for the cost of copying, and [Effective C++ chapter 03](/tech/series/effective-cpp/03.resource-management/) for ownership.

Terms used in this chapter:

- **idiom**: a recurring, named solution to a problem the language does not solve directly.
- **clone idiom**: a virtual function that returns a copy of the object it is called on, standing in for a virtual copy constructor.
- **smart pointer**: a class that acts like a pointer and adds behavior such as automatic deletion.
- **reference counting**: tracking how many owners share an object and freeing it when the count reaches zero.
- **proxy class**: a small object returned in place of a real value, for example by `operator[]`, so the class can tell a read from a write.
- **double dispatch**: choosing a function based on the run-time types of two objects, not one.
- **heap-based object**: an object created with `new`, as opposed to a local variable on the stack.

## Item 25: Virtualizing Constructors and Non-Member Functions

In standard C++, constructors cannot be `virtual` (an object's virtual table pointer does not exist prior to construction); similarly, non-member functions cannot be `virtual` directly (they lack a `this` pointer to dispatch through). However, software architectures frequently require both behaviors.

### 1. The Virtual Copy Constructor (The Clone Idiom)

In graphical document editors or game engines, code often holds a base pointer `Shape*` to an unknown concrete object selected by the user. When duplicating the selection, how can the engine clone the exact derived instance polymorphically?

Define a pure virtual `clone()` member function:

```cpp
class Shape {
public:
    virtual ~Shape() = default;
    virtual std::unique_ptr<Shape> clone() const = 0; // Virtual copy constructor idiom
};

class Circle : public Shape {
public:
    virtual std::unique_ptr<Shape> clone() const override {
        return std::make_unique<Circle>(*this); // Invokes private/public copy constructor
    }
};

class Rectangle : public Shape {
public:
    virtual std::unique_ptr<Shape> clone() const override {
        return std::make_unique<Rectangle>(*this);
    }
};

void duplicateShape(const Shape* s) {
    std::unique_ptr<Shape> replica = s->clone(); // Exact polymorphic replica, zero type inspection
}
```

### 2. Virtual Non-Member Functions

Non-member functions (such as stream insertion `operator<<`) cannot be marked `virtual`. Instead, delegate them to a virtual member function:

```cpp
class Shape {
public:
    virtual ~Shape() = default;
    virtual void print(std::ostream& os) const = 0; // Virtual worker
};

// Non-member facade
inline std::ostream& operator<<(std::ostream& os, const Shape& s) {
    s.print(os); // Dynamic polymorphic dispatch
    return os;
}
```

## Item 26: Limiting the Number of Objects of a Class

Certain system entities model singletons or have strict concurrency quotas:

### 1. Prohibiting Any Instantiation (Utility Classes)

Delete the default constructor:

```cpp
class MathUtils {
public:
    MathUtils() = delete; // Uninstantiable utility namespace
    static double square(double x) noexcept { return x * x; }
};
```

### 2. Singletons (At Most One Instance)

Use Meyers' Singleton:

```cpp
class Printer {
public:
    static Printer& getInstance() {
        static Printer instance; // Guaranteed thread-safe in C++11
        return instance;
    }

private:
    Printer() = default;
    Printer(const Printer&) = delete;
    Printer& operator=(const Printer&) = delete;
};
```

### 3. Instance Quota Limiters

Enforce an upper bound on concurrent instances using static counters:

```cpp
class LimitedInstance {
public:
    class TooManyObjects : public std::runtime_error {
        using std::runtime_error::runtime_error;
    };

    LimitedInstance() {
        if (numObjects >= maxObjects) {
            throw TooManyObjects("Exceeded maximum instance threshold of 5");
        }
        ++numObjects;
    }

    ~LimitedInstance() noexcept {
        --numObjects;
    }

private:
    static inline std::size_t numObjects{0};
    static constexpr std::size_t maxObjects{5};
};
```

This only counts objects built by the default constructor. A copy constructor (implicitly generated here) would bypass the count, so a real quota class must define or delete it; Meyers puts the counting in a reusable `Counted<T>` base class.

## Item 27: Requiring or Prohibiting Heap-Based Objects

### 1. Requiring Heap Allocation (Heap-Only Objects)

When objects are large enough to threaten stack limits, require allocation via `new`:

```cpp
class HeapOnlyWidget {
public:
    static HeapOnlyWidget* create() {
        return new HeapOnlyWidget();
    }

    void destroy() noexcept {
        delete this; // Allowed: member function can access private destructor
    }

private:
    ~HeapOnlyWidget() = default; // Declaring destructor private prevents stack allocation!
};

// HeapOnlyWidget w; // COMPILE ERROR: cannot access private destructor on scope exit
auto* pw = HeapOnlyWidget::create(); // Legal
pw->destroy();                       // Controlled cleanup
```

### 2. Prohibiting Heap Allocation (Stack-Only Objects)

For objects tied to local RAII lifetimes (e.g., stack scope locks), prohibit dynamic allocation by deleting `operator new`:

```cpp
class NonHeapWidget {
public:
    static void* operator new(std::size_t) = delete;
    static void* operator new[](std::size_t) = delete;
};

NonHeapWidget w; // Legal: stack allocation succeeds
// auto* pw = new NonHeapWidget(); // COMPILE ERROR: operator new is deleted!
```

## Item 28: Smart Pointers

Smart pointers wrap raw C++ pointers inside stack-allocated class templates that overload `operator*` and `operator->` to automate lifetime management, resource cleanup, and access interception.

### Core Anatomy of a Smart Pointer Template

```cpp
template <typename T>
class SmartPtr {
public:
    explicit SmartPtr(T* realPtr = nullptr) noexcept : pointee(realPtr) {}
    ~SmartPtr() { delete pointee; }

    // Exclusive ownership: the implicit copy would double-delete
    SmartPtr(const SmartPtr&) = delete;
    SmartPtr& operator=(const SmartPtr&) = delete;
    SmartPtr(SmartPtr&& other) noexcept : pointee(other.release()) {}

    // 1. Dereferencing operators
    T* operator->() const noexcept { return pointee; }
    T& operator*() const noexcept { return *pointee; }

    // 2. Safe boolean null check (explicit operator bool prevents accidental arithmetic conversion)
    explicit operator bool() const noexcept { return pointee != nullptr; }

    // 3. Generalized conversion for derived-to-base polymorphism (e.g., SmartPtr<Derived> -> SmartPtr<Base>)
    template <typename U>
    SmartPtr(SmartPtr<U>&& other) noexcept : pointee(other.release()) {}

    T* release() noexcept {
        T* old = pointee;
        pointee = nullptr;
        return old;
    }

private:
    T* pointee;
};
```

### Critical Implementation Nuances

1. **`operator->` Chaining Semantics**: C++ evaluates `pt->member` recursively—if `operator->()` returns a raw pointer `T*`, the compiler accesses `T::member`; if it returns another smart pointer or proxy object, the compiler invokes `operator->()` again until a raw pointer is reached.
2. **Testing for Null Safely**: In pre-C++11 code, providing an implicit `operator void*()` allowed `if (sp)` checks, but accidentally permitted nonsensical expressions like `delete sp;`. Modern C++ solves this with `explicit operator bool() const noexcept`, which participates in contextual boolean conditions (`if (sp)`, `!sp`) while forbidding implicit integer or pointer arithmetic.
3. **Emulating Derived-to-Base and `const` Conversions**: Just as `Derived*` converts implicitly to `Base*` and `T*` converts to `const T*`, smart pointer templates use member function templates constrained by `std::is_convertible_v<U*, T*>` (as standardized in `std::unique_ptr<T>` and `std::shared_ptr<T>`).

## Item 29: Reference Counting

Reference counting allows multiple objects with identical values to share a single underlying heap representation until one of them needs to mutate it (**Copy-on-Write, COW**), amortizing both heap allocations and deep-copy CPU cycles.

### Implementing an Intrusive Reference-Counted Base (`RCObject` & `RCPtr`)

By separating the reference-counting machinery into a base class `RCObject` and an automated smart pointer `RCPtr<T>`, domain classes remain clean:

```cpp
#include <cstring>
#include <cstddef>

// 1. Intrusive reference-counted base class
class RCObject {
public:
    void addReference() noexcept { ++refCount; }
    void removeReference() noexcept {
        if (--refCount == 0) delete this;
    }
    void markUnshareable() noexcept { shareable = false; }
    bool isShareable() const noexcept { return shareable; }
    bool isShared() const noexcept { return refCount > 1; }

protected:
    RCObject() = default;
    RCObject(const RCObject&) : refCount(0), shareable(true) {}
    RCObject& operator=(const RCObject&) { return *this; }
    virtual ~RCObject() = default;

private:
    std::size_t refCount{0};
    bool shareable{true};
};

// 2. Automated intrusive smart pointer managing RCObject lifetimes
template <typename T>
class RCPtr {
public:
    explicit RCPtr(T* realPtr = nullptr) : pointee(realPtr) { init(); }
    RCPtr(const RCPtr& rhs) : pointee(rhs.pointee) { init(); }
    ~RCPtr() { if (pointee) pointee->removeReference(); }

    RCPtr& operator=(const RCPtr& rhs) {
        if (pointee != rhs.pointee) {
            T* oldPointee = pointee;
            pointee = rhs.pointee;
            init();
            if (oldPointee) oldPointee->removeReference();
        }
        return *this;
    }

    T* operator->() const noexcept { return pointee; }
    T& operator*() const noexcept { return *pointee; }

private:
    T* pointee;
    void init() {
        if (!pointee) return;
        if (!pointee->isShareable()) {
            pointee = new T(*pointee); // Deep copy if marked unshareable
        }
        pointee->addReference();
    }
};
```

> **Modern C++ Context**: While C++98 allowed Copy-on-Write `std::string`, C++11 effectively ruled out COW for `std::basic_string`: its reference and iterator invalidation rules (a non-const `operator[]` must not invalidate other references) and thread-safety expectations are hard to meet with shared buffers, and the atomic reference count adds cost in multi-threaded code. Modern C++ uses **Small String Optimization (SSO)** for `std::string`, non-owning `std::string_view` for zero-copy slicing, and `std::shared_ptr<const T>` or `boost::intrusive_ptr<T>` when explicit shared immutable state is required.

## Item 30: Proxy Classes

Proxy classes act as intermediary wrappers between client code and target objects.

### 1. Intercepting Read vs. Write in `operator[]`

With Copy-on-Write strings, normal `char& operator[](size_t)` returns a non-const reference. The compiler cannot tell whether the caller is **reading** (`char c = s[0]`) or **writing** (`s[0] = 'x'`).

A proxy class resolves this ambiguity:

```cpp
class String {
public:
    class CharProxy {
    public:
        CharProxy(String& str, std::size_t index) : theString(str), theIndex(index) {}

        // Lvalue assignment intercept (write): s[0] = 'x'
        CharProxy& operator=(char c) {
            theString.detachAndMutate(theIndex, c); // Trigger Copy-on-Write!
            return *this;
        }

        // Rvalue conversion intercept (read): char c = s[0]
        operator char() const {
            return theString.readDirectly(theIndex); // Zero copy overhead
        }

    private:
        String& theString;
        std::size_t theIndex;
    };

    CharProxy operator[](std::size_t index) {
        return CharProxy(*this, index);
    }
};
```

### 2. Emulating 2D Array Subscripts (`matrix[i][j]`)

C++ does not support multi-argument subscripts `operator[][](i, j)`. Implementing `operator[](i)` to return a lightweight `RowProxy` that in turn implements `operator[](j)` provides natural two-dimensional subscript syntax.

## Item 31: Making Functions Virtual with Respect to More Than One Object (Double Dispatch)

Standard C++ virtual dispatch is **Single Dispatch**: the executed overload depends strictly on the dynamic type of the calling object (`this`).

In interactive applications (such as physics engines or space simulations), collision resolution depends on the dynamic types of **two interacting objects**:

```cpp
class GameObject { /* ... */ };
class SpaceShip : public GameObject { /* ... */ };
class SpaceStation : public GameObject { /* ... */ };
class Asteroid : public GameObject { /* ... */ };

void checkCollision(GameObject& obj1, GameObject& obj2);
```

### Double Dispatch via Two Virtual Calls

Rather than cascading slow, brittle `dynamic_cast` ladders, implement **Double Dispatch** via two successive virtual calls (the Visitor Pattern):

<Archify src="./diagrams/double-dispatch.sequence.json" />

```cpp
class SpaceShip;
class SpaceStation;
class Asteroid;

class GameObject {
public:
    virtual ~GameObject() = default;

    // Hop 1: Resolve self type
    virtual void collide(GameObject& other) = 0;

    // Hop 2: Resolve target type via overloaded visitor callbacks
    virtual void collideWith(SpaceShip& other) = 0;
    virtual void collideWith(SpaceStation& other) = 0;
    virtual void collideWith(Asteroid& other) = 0;
};

class SpaceShip : public GameObject {
public:
    virtual void collide(GameObject& other) override {
        other.collideWith(*this); // Passes strongly typed *this (SpaceShip&)!
    }

    virtual void collideWith(SpaceShip& other) override {
        // Ship-on-ship collision logic
    }
    virtual void collideWith(SpaceStation& other) override {
        // Ship docking or station collision logic
    }
    virtual void collideWith(Asteroid& other) override {
        // Ship hitting asteroid explosion logic
    }
};
```

**Dispatch Flow**:

1. First virtual call `obj1.collide(obj2)`: Resolves `obj1`'s derived type (e.g., `SpaceShip::collide`).
2. Inside `SpaceShip::collide`, `this` is statically known as `SpaceShip&`. Calling `other.collideWith(*this)` executes the **second virtual call**.
3. Dynamic dispatch routes cleanly to `obj2.collideWith(SpaceShip&)`.

Two virtual function dispatches achieve full multi-type polymorphic binding in $O(1)$ time, eliminating RTTI overhead.

## Summary Checklist

| Idiom | Architecture Value | Implementation Key |
| :--- | :--- | :--- |
| **Virtual Constructor** | Polymorphic duplication without knowing concrete type | `clone()` returning `std::unique_ptr<Base>` |
| **Virtual Non-Member** | Multi-type output formatting | Non-member operator delegating to virtual method |
| **Heap-Only Enforcement**| Prevents stack overflow on huge objects | Private destructor with public `destroy()` method |
| **Non-Heap Enforcement** | Guarantees deterministic stack/local lifecycles | `= delete` on `operator new` and `operator new[]` |
| **Smart Pointers** | Automates RAII cleanup and polymorphic pointer conversions | `operator*`, `operator->`, `explicit operator bool()`, member templates |
| **Reference Counting** | Shares immutable heap representations across owners | Intrusive `RCObject` / `RCPtr<T>` or `std::shared_ptr<const T>` |
| **Proxy Classes** | Distinguishes read vs. write in subscript operators | Returning an intermediate proxy with conversion operators |
| **Double Dispatch** | Multi-object polymorphic resolution | Two virtual dispatch hops (Visitor Pattern) |
