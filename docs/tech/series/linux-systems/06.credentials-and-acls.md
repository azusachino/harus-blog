## Linux Systems & Performance 06: Credentials, Capabilities, Namespaces, cgroups & Container Debugging

In traditional UNIX, privilege was binary: either a process ran as superuser (`UID 0`, bypassing every permission check) or as an unprivileged user. And isolation was machine-wide: every process saw the same process table, network interfaces, and host memory statistics.

Modern Linux replaces both assumptions with three orthogonal kernel mechanisms:

1. **Fine-Grained Credentials & POSIX Capabilities**: Splitting root privilege into ~41 bitmask capabilities (`CAP_NET_BIND_SERVICE`, `CAP_SYS_ADMIN`, `CAP_NET_RAW`).
2. **Namespaces (`CLONE_NEW*`)**: Partitioning what a process can **see** (PIDs, mount tables, network stacks, hostnames, UIDs).
3. **Control Groups (`cgroups v2`)**: Metering and limiting what a process can **consume** (CPU quotas, memory limits, IOPS/BPS ceilings, PID counts).

Together, Capabilities + Namespaces + cgroups **are** what we call a Linux container. Understanding how they work in the kernel is essential when debugging why a container service suffers 200 ms latency spikes at only `20%` host CPU utilization (**CFS CPU throttling**), why `top` and `free -h` lie inside a container, or how to attach host `tcpdump`/`perf`/`ss` into a minimal distroless container via `nsenter`.

### 1. The Four Process UIDs and Thread Capabilities

Every Linux thread (`task_struct->cred`) carries four distinct User IDs and four Group IDs (viewable in `/proc/self/status`):

| Credential | Kernel Field | Purpose |
| :--- | :--- | :--- |
| **Real UID (`ruid`)** | `cred->uid` | Identifies the human user or service account that launched the process. |
| **Effective UID (`euid`)** | `cred->euid` | Checked by the kernel for most privilege and signal-sending decisions; copied into `fsuid`. |
| **Saved Set-UID (`suid`)** | `cred->suid` | Records the initial `euid` after `execve()` so a privileged daemon can temporarily drop `euid` and restore it later (unless dropped permanently via `setresuid(uid, uid, uid)`). |
| **Filesystem UID (`fsuid`)** | `cred->fsuid` | Checked specifically by the VFS when opening or creating files; normally tracks `euid`. |

#### 1.1 The Five Linux Capability Bitmasks

Instead of running a web server or network exporter as `root` just so it can bind port `443` (`< 1024`) or open raw ICMP sockets for health pings, Linux divides root authority into discrete **Capabilities** (`man 7 capabilities`). Every thread tracks five 64-bit capability bitmasks in `/proc/<PID>/status`:

```text
$ grep Cap /proc/self/status
CapInh: 0000000000000000
CapPrm: 0000000000000000
CapEff: 0000000000000000
CapBnd: 000001ffffffffff
CapAmb: 0000000000000000
```

```bash
# Decode a hexadecimal CapEff / CapBnd bitmask into human-readable names
capsh --decode=00000000a80425fb
```

1. **Effective (`CapEff`)**: The bitmask the kernel actually checks on every privileged system call (`bind()` on port 80 checks `CAP_NET_BIND_SERVICE`; `perf`/`bpf()` checks `CAP_PERFMON` + `CAP_BPF` or `CAP_SYS_ADMIN`).
2. **Permitted (`CapPrm`)**: The ceiling of capabilities this thread is allowed to activate into `CapEff`. Dropping a capability from `CapPrm` is irreversible without `execve()`.
3. **Inheritable (`CapInh`)**: Capabilities preserved across `execve()` when combined with file capabilities (`setcap`) or ambient capabilities.
4. **Bounding (`CapBnd`)**: A security ceiling restricting which capabilities can ever be gained during `execve()`, even from a `setuid-root` binary! Container runtimes drop dangerous capabilities like `CAP_SYS_MODULE` (loading kernel modules) and `CAP_SYS_TIME` (changing the host clock) from `CapBnd`.
5. **Ambient (`CapAmb`, Linux 4.3+)**: Allows a parent process (like `systemd` with `AmbientCapabilities=CAP_NET_BIND_SERVICE`) to pass specific capabilities across `execve()` to a normal non-root binary without needing `setcap` extended attributes on the filesystem.

### 2. Linux Namespaces: Partitioning Kernel Visibility

A Linux container is not a virtual machine with its own kernel; it is a normal host process running on the shared host kernel whose `task_struct->nsproxy` points to isolated **Namespaces**:

| Namespace | `clone()` Flag | `/proc/<PID>/ns/*` Entry | What It Isolates |
| :--- | :--- | :--- | :--- |
| **Mount** | `CLONE_NEWNS` | `mnt` | Filesystem mount table (`/proc/<PID>/mountinfo`), enabling container `pivot_root`. |
| **UTS** | `CLONE_NEWUTS` | `uts` | Hostname (`uname().nodename`) and NIS domain name. |
| **IPC** | `CLONE_NEWIPC` | `ipc` | System V IPC and POSIX message queues (`/dev/mqueue`). |
| **PID** | `CLONE_NEWPID` | `pid` | Process ID numbering (`PID 1` inside the container maps to e.g. `PID 28410` in the host root namespace). |
| **Network** | `CLONE_NEWNET` | `net` | Network interfaces (`lo`, `eth0`/`veth`), IP routing tables, `iptables`/`nftables`, socket port tables (`ss`), and `/proc/net/*` counters! |
| **User** | `CLONE_NEWUSER` | `user` | Maps `UID 0` inside the container to an unprivileged host UID (e.g. `UID 100000`) via `/proc/<PID>/uid_map`. |
| **Cgroup** | `CLONE_NEWCGROUP` | `cgroup` | Virtualizes `/proc/self/cgroup` paths so the container sees its own cgroup as `/`. |
| **Time** | `CLONE_NEWTIME` | `time` | Per-namespace offsets for `CLOCK_MONOTONIC` and `CLOCK_BOOTTIME`. |

#### 2.1 The PID 1 Signal & Zombie Reaping Contract Inside Containers

In a PID namespace, the very first process spawned receives container **`PID 1`**. In the Linux kernel, `PID 1` has two hardcoded behaviors:

1. **Orphan Adoption**: Whenever any process inside that PID namespace exits while still having running children, `PID 1` becomes their new `PPID` and is responsible for calling `waitpid()` to reap them when they exit. If your container entry point is a naive daemon that does not reap unknown children, orphaned subprocesses accumulate as `Z` (Zombie) tasks forever.
2. **Signal Immunity**: By default, the kernel **ignores any unhandled `SIGTERM` or `SIGINT` sent to `PID 1`** if `PID 1` has not explicitly registered a `sigaction()` handler for that signal! That is why `docker stop` (which sends `SIGTERM`) hangs for 10 seconds and falls back to `SIGKILL` when an app inside a container runs as `PID 1` without a signal handler or an init wrapper (`tini` / `dumb-init`).

### 3. Performance Debugging Playbook: Troubleshooting Containers in Production

Containerized workloads introduce three classic debugging traps that fool engineers accustomed to bare-metal Linux.

#### 3.1 Trap 1: The `/proc` Host Illusion (`top`, `free`, and `nproc` Lying Inside Containers)

Unless a container runtime overlays virtualized `/proc` files (via FUSE such as `lxcfs`), **mounting `/proc` inside a container exposes the host kernel's global `/proc/meminfo`, `/proc/stat`, `/proc/cpuinfo`, and `/proc/uptime`!**

- If a Kubernetes Pod has a `2 GiB` memory limit (`memory.max`) and a `2.0 CPU` limit (`cpu.max`) on a 64-core, 256 GiB Kubernetes node:
  - Running `free -h` inside the container reports **256 GiB total RAM**!
  - Running `nproc` or `lscpu` reports **64 CPU cores**!
  - If a JVM, Go runtime (`GOMAXPROCS`), or Node/Python worker pool sizes its thread count (`64` threads) or heap (`64 GiB`) from `/proc/cpuinfo` and `/proc/meminfo` instead of reading `cgroups v2` limits, it immediately triggers **massive CPU context-switch storms** and **instant cgroup OOM kills**!

> **Modern Runtime Fix**: Ensure Go (1.25+ derives `GOMAXPROCS` from the cgroup CPU limit; older versions need `automaxprocs`), JDK 17+ (`-XX:+UseContainerSupport`, on by default), and custom thread pools read **cgroup v2** limits from `/sys/fs/cgroup/cpu.max` and `/sys/fs/cgroup/memory.max`.

#### 3.2 Trap 2: Container Latency Spikes at Low Host CPU (`nr_throttled` CFS Quota Throttling)

Suppose a latency-sensitive microservice Pod has a Kubernetes limit of `limits.cpu: "1000m"` (1.0 core) and runs 8 worker threads. Average container CPU usage over a minute is only `30%`, and the host node is `80%` idle—yet P99 API latency spikes by **80 to 100 milliseconds**!

**Root Cause — CFS Bandwidth Quota Accounting (`cpu.max`)**:

1. Linux `cgroups` enforces a `1.0 CPU` limit using two numbers in `/sys/fs/cgroup/.../cpu.max`: a **quota** (`100000` $\mu$s = 100 ms) per **period** (`100000` $\mu$s = 100 ms wall clock).
2. When a batch of requests arrives, all **8 worker threads** wake up simultaneously on 8 physical cores.
3. Because 8 cores run in parallel, they burn through the entire **100 ms CPU quota in just 12.5 ms of wall-clock time** ($8 \text{ cores} \times 12.5\text{ ms} = 100\text{ ms}$)!
4. For the remaining **87.5 ms** of the 100 ms period, the Linux CFS scheduler **forcibly throttles every thread in the container**, freezing your request mid-flight even though the host CPUs are completely idle!

```text
100ms CFS Period (Quota = 100ms across all cores)
├───────────────┼───────────────────────────────────────────────────────────┤
│ 0ms .. 12.5ms │ 12.5ms ............................................ 100ms │
│ 8 threads run │ CONTAINER THROTTLED FOR 87.5ms! (All threads frozen)      │
│ in parallel   │ (Even if host CPUs are 90% idle!)                         │
└───────────────┴───────────────────────────────────────────────────────────┘
```

**How to Diagnose CFS Throttling in 5 Seconds**:
Inspect `/sys/fs/cgroup/cpu.stat` (cgroups v2) or `/sys/fs/cgroup/cpu/cpu.stat` (cgroups v1) inside the container or pod cgroup:

```text
$ cat /sys/fs/cgroup/cpu.stat
usage_usec 481920100
user_usec 391020000
system_usec 90900100
nr_periods 142010
nr_throttled 28940
throttled_usec 2149082100
```

- If `nr_throttled / nr_periods` exceeds `5%` (here it is about `20.4%`, with over 2,149 seconds of cumulative `throttled_usec`), your container is being crushed by CFS quota throttling!
- **Fixes**:
  1. Match your application thread-pool size (`GOMAXPROCS`, Tokio/Netty worker threads) to the container's CPU quota rather than the host core count.
  2. Raise or remove hard CPU limits (`cpu.max`) for latency-critical RPC services, relying on CPU requests/weights (`cpu.weight`) so idle host cores can absorb micro-bursts.

#### 3.3 Trap 3: Cgroup OOM Kills vs. Host OOM Kills

When a container exceeds `/sys/fs/cgroup/memory.max`, the kernel triggers a **memcg (memory cgroup) OOM kill**. The host has plenty of free RAM (`free -h` on the host looks completely healthy), yet the container process dies with `exit code 137` (`128 + 9 = SIGKILL`).

Verify a cgroup OOM kill via two authoritative sources:

1. Check `/sys/fs/cgroup/memory.events` for the container's cgroup (`oom` and `oom_kill` counters increment):

   ```text
   $ cat /sys/fs/cgroup/memory.events
   low 0
   high 0
   max 1842
   oom 1
   oom_kill 1
   ```

2. Check `dmesg -T | grep -i "Memory cgroup out of memory"`, which prints the exact `memory: usage ... limit ...` of the container cgroup at the moment of death.

#### 3.4 Debugging Distroless / Minimal Containers from the Host with `nsenter`

Production containers rarely include `tcpdump`, `ss`, `strace`, `lsof`, or `perf`—and installing packages into a live container mutates its filesystem and wastes precious minutes during an incident.

Because a container is just a host process attached to isolated namespaces (`/proc/<PID>/ns/*`), **you can run any diagnostic binary installed on the host while entering the container's Network, PID, or Mount namespace via `nsenter`**:

```bash
# 1. Find the host PID of the container process (via docker inspect, crictl, or ps)
CONTAINER_PID=$(docker inspect -f '{{.State.Pid}}' my-container)

# 2. Run the HOST's 'ss' or 'tcpdump' binary inside the container's Network namespace (-n)!
sudo nsenter --target "$CONTAINER_PID" --net ss -antp
sudo nsenter --target "$CONTAINER_PID" --net tcpdump -nn -i eth0 port 8080

# 3. Inspect the container's mounted rootfs directly from the host without nsenter:
ls -la "/proc/$CONTAINER_PID/root/etc/"
```

Notice why `nsenter --target $PID --net` is so powerful: it executes the binary from the **host's root filesystem** (where all your debug tools live) while switching only the calling process's `net` namespace pointer to the container's virtual network stack!

### 4. Verification Lab: Inspecting Live Capabilities, Namespaces, and Cgroup Limits

The Python script below inspects the current process's `/proc/self/status` capability bitmasks, lists its active namespace inode identifiers from `/proc/self/ns/`, and parses its live `cgroups v2` CPU and memory limits/throttling counters from `/sys/fs/cgroup`.

```python
#!/usr/bin/env python3
"""
Inspect the current process's Linux Credentials, Capability bitmasks,
Namespace inode IDs (/proc/self/ns/*), and cgroup v2 CPU/Memory limits.
"""
import os


def inspect_credentials_and_caps() -> None:
    wanted = {"Uid", "Gid", "CapPrm", "CapEff", "CapBnd", "CapAmb", "NoNewPrivs"}
    print("=== [1] Process Credentials & Capabilities (/proc/self/status) ===")
    with open("/proc/self/status", "r", encoding="utf-8") as f:
        for line in f:
            key = line.split(":", 1)[0]
            if key in wanted:
                print(f"  {line.strip()}")


def inspect_namespaces() -> None:
    print("\n=== [2] Active Kernel Namespaces (/proc/self/ns/*) ===")
    ns_dir = "/proc/self/ns"
    for entry in sorted(os.listdir(ns_dir)):
        target = os.readlink(os.path.join(ns_dir, entry))
        print(f"  {entry:18s} -> {target}")


def inspect_cgroup_v2() -> None:
    print("\n=== [3] Cgroup Membership & Resource Telemetry ===")
    with open("/proc/self/cgroup", "r", encoding="utf-8") as f:
        rel_path = f.read().strip().split(":")[-1]
    print(f"  Cgroup path : {rel_path}")

    # Check either the process's specific cgroup or root /sys/fs/cgroup
    cg_dir = os.path.join("/sys/fs/cgroup", rel_path.lstrip("/"))
    if not os.path.isdir(cg_dir):
        cg_dir = "/sys/fs/cgroup"

    for fname in ("cpu.max", "memory.max", "memory.current"):
        fpath = os.path.join(cg_dir, fname)
        if os.path.exists(fpath):
            with open(fpath, "r", encoding="utf-8") as f:
                print(f"  {fname:14s}: {f.read().strip()}")


if __name__ == "__main__":
    inspect_credentials_and_caps()
    inspect_namespaces()
    inspect_cgroup_v2()
```

#### Summary of Container & Privilege Diagnostic Commands

| Symptom | Primary Tool | What to Inspect |
| :--- | :--- | :--- |
| `EACCES` / `EPERM` on non-root port or syscall | `grep Cap /proc/<PID>/status`, `capsh --decode=<HEX>` | Check `CapEff` and `CapBnd` for `CAP_NET_BIND_SERVICE`, `CAP_NET_RAW`, `CAP_SYS_ADMIN` |
| High container tail latency at low CPU % | `cat /sys/fs/cgroup/.../cpu.stat` | Check `nr_throttled` and `throttled_usec` (CFS bandwidth quota throttling) |
| Container exited with `137` (`SIGKILL`) | `cat /sys/fs/cgroup/.../memory.events`, `dmesg -T` | Check `oom_kill` count and `Memory cgroup out of memory` log |
| Need `tcpdump`/`ss`/`lsof` inside a distroless container | `sudo nsenter -t <HOST_PID> -n ss -antp` | Enter only the container's `--net` namespace while running host diagnostic binaries |
