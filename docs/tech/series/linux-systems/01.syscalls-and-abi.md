## Before you start

This series is for programmers who write code in one language and use a shell, but have not looked inside Linux; the chapters build on each other, so read them in order.

Your program cannot touch the disk, the network or other processes' memory directly. It asks the kernel to do it, and each request is a system call. Think of a bank counter: you can fill in the slip yourself, but only the teller reaches the vault, and every trip to the counter has a cost. This chapter covers that cost, and two symptoms engineers see in production: a "load average" much bigger than the CPU usage suggests, and a server that burns CPU switching between threads instead of doing work. A quick way to see system calls yourself is `strace -c ls`, which counts the calls `ls` makes.

You only need basic command-line use here. Later chapters in this series reuse the tools introduced in this one (`vmstat`, `pidstat`, `strace`).

Terms used in this chapter:

- **system call**: a request from a program to the kernel, such as reading a file or opening a socket.
- **user mode / kernel mode**: the two CPU privilege levels; ordinary programs run in user mode, the kernel runs in kernel mode.
- **vDSO**: a small piece of kernel code mapped into every process so a few calls, like reading the clock, avoid entering the kernel.
- **context switch**: the CPU stops running one thread and starts another, saving and restoring the thread's registers.
- **load average**: the average number of threads that are running, waiting for a CPU, or stuck in uninterruptible I/O wait.
- **EINTR**: the error code a call returns when a signal interrupted it before it finished.
- **`%sys` / `%usr`**: the share of CPU time spent in kernel mode and in user mode.

## Linux Systems & Performance 01: System Call Boundaries, Context Switches & Load Average Debugging

Every instruction a Linux process executes runs in one of two hardware privilege rings: unprivileged **User Mode** (Ring 3 on x86_64) or privileged **Kernel Mode** (Ring 0). Whenever an application reads a socket, allocates physical pages, or spawns a thread, it must cross that boundary.

Understanding the exact mechanics of this boundary is not just an exercise in systems programming—it is the foundation of **Linux performance debugging**. When an on-call engineer sees Load Average spike to `24.0` on an 8-core server while CPU utilization sits at `15%`, or sees `%sys` CPU climb above `60%` during a traffic surge, the answer always lies at the intersection of system call traps, thread scheduling states, and context switches.

```text
  User Space (Ring 3)                          Kernel Space (Ring 0)
┌────────────────────────┐                   ┌─────────────────────────────┐
│ Application Code       │                   │ entry_SYSCALL_64            │
│   │                    │                   │   ├── Swap GS & Stack       │
│   ▼                    │   syscall (trap)  │   ├── Save pt_regs          │
│ glibc Wrapper          │ ────────────────► │   ├── sys_call_table[rax]   │
│   ├── rax = __NR_read  │                   │   │     └── vfs_read()      │
│   └── syscall          │ ◄──────────────── │   └── sysretq               │
│   │                    │   rax = -errno    └─────────────────────────────┘
│   ▼                    │     or bytes
│ if (rax < 0):          │
│   errno = -rax; ret -1 │
└────────────────────────┘
```

### 1. The System Call ABI and the Cost of Crossing Rings

User-space code cannot jump directly to an arbitrary kernel address; doing so triggers a hardware general-protection fault. Instead, the CPU exposes a controlled trap instruction (`syscall` on x86_64, `svc #0` on ARM64) that atomically switches the privilege level, swaps the instruction pointer to a kernel-registered entry vector (`MSR_LSTAR` pointing to `entry_SYSCALL_64`), and switches to the current thread's kernel stack.

#### 1.1 Register Conventions and the `-4095` Error Boundary

Standard C functions pass arguments on the x86_64 System V ABI (`rdi`, `rsi`, `rdx`, `rcx`, `r8`, `r9`). Because the `syscall` instruction clobbers `rcx` (to store the user-space return address `rip`) and `r11` (to store `rflags`), the Linux kernel ABI substitutes `r10` for the fourth argument:

| Parameter | x86_64 Function Call ABI | x86_64 Linux Syscall ABI |
| :--- | :--- | :--- |
| Syscall Number / Return | — / `rax` | `rax` / `rax` |
| Arg 1 .. 3 | `rdi`, `rsi`, `rdx` | `rdi`, `rsi`, `rdx` |
| Arg 4 | `rcx` | `r10` (`rcx` clobbered by `syscall`) |
| Arg 5 .. 6 | `r8`, `r9` | `r8`, `r9` |

When the kernel finishes executing a handler such as `ksys_read()`, it writes a single signed 64-bit integer into `rax`:

- **Success**: a non-negative integer (bytes read, file descriptor number, or `0`) or a valid user-space pointer (for `mmap`).
- **Failure**: a negative error code in the range `[-4095, -1]` (for example, `-EAGAIN` is `-11`, `-EINTR` is `-4`). Because kernel virtual addresses reside at the top of the 64-bit address space and page-aligned user pointers never land in the final 4,095 bytes (`0xfffffffffffff001` through `0xffffffffffffffff`), the libc wrapper unambiguously checks `if ((unsigned long)rax >= (unsigned long)-4095L)`. Only then does libc negate `rax`, store the positive code into thread-local `errno`, and return `-1`.

#### 1.2 Bypassing the Ring Switch with `vDSO`

<Archify src="./diagrams/linux-syscall-trampoline.sequence.json" />

Since Meltdown and Spectre mitigations (Kernel Page-Table Isolation, KPTI) were introduced, a full user-to-kernel-and-back transition flushes TLB entries or switches page-table roots (`CR3`), costing hundreds of CPU cycles. For high-frequency read-only queries like `clock_gettime()` or `gettimeofday()`, paying for a ring switch on every log timestamp or latency span would devastate throughput.

Linux solves this via the **vDSO (Virtual Dynamic Shared Object)**: the kernel maps a small read-only ELF shared library (`linux-vdso.so.1`) plus a shared data page (`_vdso_data`) directly into every process's user-space address space. When your application calls `clock_gettime(CLOCK_MONOTONIC, &ts)`, glibc invokes the vDSO function in Ring 3, which reads the CPU's Time Stamp Counter (`rdtsc`) and applies the kernel-updated calibration multipliers from the shared page—completing in ~15 nanoseconds with **zero system calls** and **zero context switches**.

#### 1.3 `EINTR` and Deadline-Driven Retry Loops

Blocking system calls on "slow" devices (sockets, pipes, terminals, timers) can be interrupted before any data transfers if the thread receives a signal whose handler runs. Depending on whether the signal was registered with `SA_RESTART` and which syscall is executing, the kernel may abort the wait and return `-EINTR`.

A naive `while (poll(...) == -1 && errno == EINTR)` loop introduces a subtle production bug: if you pass a relative timeout (`timeout_ms = 5000`) and a periodic profiler or `SIGCHLD` interrupts the call every 2 seconds, restarting with the full 5,000 ms timeout lets the effective timeout stretch well past 5 seconds, indefinitely if the interrupts keep coming. Production systems programming always computes an **absolute monotonic deadline** first and recalculates the remaining budget on every `EINTR`.

### 2. Performance Debugging Playbook: Dissecting Load Average

The very first command most engineers run during an incident is `uptime` or `top`:

```text
$ uptime
 08:15:40 up 42 days, 14:22,  1 user,  load average: 16.42, 11.80, 4.15
```

#### 2.1 What Load Average Actually Measures

A widespread misconception is that Load Average measures CPU utilization. In Linux, **Load Average is the exponentially damped moving average (over 1, 5, and 15 minutes) of the number of threads in two specific kernel states**:

1. **`R` (`TASK_RUNNING`)**: Threads currently executing on a CPU core **or** waiting in a CPU runqueue (`rq`) for a core to become free.
2. **`D` (`TASK_UNINTERRUPTIBLE`)**: Threads blocked inside the kernel waiting for non-interruptible hardware completion—most commonly synchronous disk I/O, NFS mounts, or kernel mutexes held across I/O paths.

Why does Linux include `D`-state threads in Load Average? Because `TASK_UNINTERRUPTIBLE` protects kernel and hardware state invariants: if a process has submitted a DMA read to an NVMe controller and is waiting for the bio completion interrupt, delivering a signal and tearing down its address space mid-DMA would corrupt kernel memory. Consequently, `D`-state threads ignore even `SIGKILL` (`kill -9`) until the underlying I/O call returns. Thus, **Load Average measures total system demand across both CPU and storage I/O**.

#### 2.2 Reading Load Trends and CPU Normalization

Before panicking over a Load Average number, divide it by the number of logical CPUs (`nproc` or `grep -c ^processor /proc/cpuinfo`):

- On a **16-core host**, a Load Average of `16.0` means every core has roughly 1 active or I/O-waiting thread (`100%` capacity). On a **2-core VM**, `16.0` means 14 threads are queued behind the 2 running ones (`700%` overload).
- **Compare the 3 windows (`1m`, `5m`, `15m`)**:
  - `16.42, 11.80, 4.15` ($1\text{m} > 5\text{m} > 15\text{m}$): The bottleneck just started and is actively escalating.
  - `2.10, 8.50, 14.20` ($1\text{m} < 5\text{m} < 15\text{m}$): The spike has already subsided; inspect historical logs rather than live process states.

#### 2.3 The Three Root Causes of High Load Average

When Load Average spikes, it falls into one of three distinct signatures. You can distinguish all three in 5 seconds using `vmstat 1` and `mpstat -P ALL 1`:

```text
                       High Load Average Detected
                                   │
                  Run: mpstat -P ALL 1  &  vmstat 1
                                   │
         ┌─────────────────────────┼─────────────────────────┐
         ▼                         ▼                         ▼
┌─────────────────────┐   ┌─────────────────────┐   ┌─────────────────────┐
│ Scenario A          │   │ Scenario B          │   │ Scenario C          │
│ CPU-Bound Contention│   │ I/O-Wait Stall      │   │ Context-Switch Storm│
├─────────────────────┤   ├─────────────────────┤   ├─────────────────────┤
│ • %usr is high      │   │ • %iowait is high   │   │ • %sys is high      │
│ • vmstat 'r' >> CPUs│   │ • vmstat 'b' >= 1   │   │ • vmstat 'cs' > 100k│
│ • vmstat 'b' == 0   │   │ • ps shows 'D' state│   │ • vmstat 'r' >> CPUs│
└─────────────────────┘   └─────────────────────┘   └─────────────────────┘
```

| `vmstat 1` Column | Kernel Meaning | Healthy Baseline | Symptom Threshold |
| :--- | :--- | :--- | :--- |
| `r` (runqueue) | Threads running or waiting for CPU (`R` state) | $\le$ CPU core count | $> 2 \times \text{CPUs}$ indicates CPU saturation |
| `b` (blocked) | Threads in uninterruptible sleep (`D` state) | `0` | $\ge 1$ sustained indicates disk/NFS I/O stall |
| `in` (interrupts/s) | Hardware interrupts per second | Hundreds to low thousands | $> 50,000/\text{s}$ points to NIC/storage IRQ storm |
| `cs` (context switches/s) | Kernel task context switches per second | $< 10,000/\text{s}$ per core | $> 100,000/\text{s}$ wastes CPU on scheduler overhead |
| `us` / `sy` / `wa` | User CPU % / Kernel CPU % / I/O Wait % | `us` dominant, `wa < 5%` | High `sy` = syscall/lock/switch storm; High `wa` = storage bottleneck |

### 3. Performance Debugging Playbook: Context-Switch Storms

Even when user-space code does almost no computation, excessive context switching can push Load Average into the dozens and burn 70%+ of CPU in `%sys`.

#### 3.1 What Makes a Context Switch Expensive?

Not all context switches cost the same:

1. **System Call Transition (Same Thread)**: Switching from Ring 3 to Ring 0 and back within the *same* task (`current` stays identical) saves/restores CPU registers on the thread's kernel stack. Cost: ~100–300 ns.
2. **Thread Context Switch (Same Process / Shared `mm_struct`)**: Switching between two `pthread` threads of the same process swaps general-purpose registers, FPU/AVX state, stack pointer (`rsp`), and instruction pointer (`rip`), plus the thread-local storage base (`FS` register), **without** flushing the Virtual Memory TLB because both threads share `mm_struct` (`CR3`). Cost: ~1–2 $\mu$s direct, plus L1/L2 cache warmup.
3. **Process Context Switch (Different `mm_struct`)**: Switching between unrelated processes replaces `CR3` (the page-table root), invalidating non-PCID TLB entries and polluting L1/L2/L3 caches and the branch predictor. Cost: 2–10+ $\mu$s including indirect cache-miss penalties.

#### 3.2 Voluntary vs. Involuntary Context Switches (`pidstat -w`)

When `vmstat 1` shows `cs` climbing into the hundreds of thousands alongside elevated `%sys`, `vmstat` only tells you the **host-wide** total. To pinpoint the offending process or thread, run `pidstat -w -u 1` (add `-t` to break down per thread `TID`):

```text
$ pidstat -w -t 1
08:20:01      UID      TGID       TID   cswch/s nvcswch/s  Command
08:20:02     1000     18420         -      12.0       0.0  worker-pool
08:20:02     1000         -     18421   48520.0     110.0  |__worker-0
08:20:02     1000         -     18422   48490.0     145.0  |__worker-1
08:20:02     1000     19104     19104       0.0    1985.0  compute-job
```

The two columns in `pidstat -w` tell completely different stories:

- **`cswch/s` (Voluntary Context Switches)**: The thread yielded the CPU *on its own* because a resource it requested was unavailable—for example, `futex()` lock contention, `read()` on an empty pipe/socket, `epoll_wait()` with tiny batches, or `nanosleep()`.
  - *Diagnosis*: If `cswch/s` is huge, threads are ping-ponging across a mutex, condition variable, or synchronous channel. Inspect lock contention (`perf lock` or `strace -c -p PID` looking for `futex` calls).
- **`nvcswch/s` (Involuntary Context Switches)**: The thread wanted to keep running, but the kernel scheduler forcibly preempted it because its timeslice expired (`SCHED_OTHER` CFS vruntime) or a higher-priority thread woke up.
  - *Diagnosis*: If `nvcswch/s` is huge (and `vmstat` `r` $\gg$ CPU count), far too many runnable threads are competing for too few physical cores. Reduce thread-pool size to match core count or apply CPU affinity (`taskset` / `sched_setaffinity`).

### 4. Verification Lab: Observing Syscalls, vDSO, and Context Switches

The following self-contained Python verification script exercises three scenarios on live Linux `/proc` counters:

1. Measures the speed ratio between a vDSO clock read (`time.clock_gettime`) and a real kernel-crossing syscall (`os.uname()` / `os.read()`).
2. Measures exact per-thread `voluntary_ctxt_switches` and `nonvoluntary_ctxt_switches` from `/proc/thread-self/status` (`/proc/self/status` would report only the main thread) before and after a pipe ping-pong storm.
3. Demonstrates a monotonic-deadline `EINTR`-safe wrapper.

```python
#!/usr/bin/env python3
"""
Verify syscall vs vDSO latency and inspect /proc/thread-self/status context-switch
counters during a voluntary pipe ping-pong storm.
"""
import errno
import os
import select
import threading
import time


def read_ctxt_switches() -> tuple[int, int]:
    """Read (voluntary, nonvoluntary) context switches of the calling thread from /proc/thread-self/status."""
    voluntary = nonvoluntary = 0
    with open("/proc/thread-self/status", "r", encoding="utf-8") as f:
        for line in f:
            if line.startswith("voluntary_ctxt_switches:"):
                voluntary = int(line.split()[1])
            elif line.startswith("nonvoluntary_ctxt_switches:"):
                nonvoluntary = int(line.split()[1])
    return voluntary, nonvoluntary


def poll_with_deadline(fd: int, timeout_sec: float) -> bool:
    """Wait for fd readability using an absolute monotonic deadline across EINTR."""
    deadline = time.monotonic() + timeout_sec
    poller = select.poll()
    poller.register(fd, select.POLLIN)
    while True:
        remaining_ms = max(0.0, (deadline - time.monotonic()) * 1000.0)
        try:
            events = poller.poll(remaining_ms)
            return bool(events)
        except InterruptedError:
            if time.monotonic() >= deadline:
                return False
        except OSError as exc:
            if exc.errno == errno.EINTR:
                if time.monotonic() >= deadline:
                    return False
                continue
            raise


def benchmark_vdso_vs_syscall(iterations: int = 100_000) -> None:
    t0 = time.perf_counter_ns()
    for _ in range(iterations):
        time.clock_gettime(time.CLOCK_MONOTONIC)
    vdso_ns = (time.perf_counter_ns() - t0) / iterations

    # os.uname() invokes the uname(2) syscall in Ring 0 every call
    t1 = time.perf_counter_ns()
    for _ in range(iterations):
        os.uname()
    syscall_ns = (time.perf_counter_ns() - t1) / iterations

    print(f"[1] vDSO clock_gettime avg : {vdso_ns:6.1f} ns/call")
    print(f"[1] Ring-0 uname(2) avg    : {syscall_ns:6.1f} ns/call")
    print(f"[1] Syscall overhead ratio : {syscall_ns / max(vdso_ns, 1.0):5.1f}x")


def trigger_voluntary_switch_storm(rounds: int = 5_000) -> None:
    r1, w1 = os.pipe()
    r2, w2 = os.pipe()

    peer_switches = [0, 0]

    def peer() -> None:
        v0, nv0 = read_ctxt_switches()
        for _ in range(rounds):
            os.read(r1, 1)
            os.write(w2, b"x")
        v1, nv1 = read_ctxt_switches()
        peer_switches[0] = v1 - v0
        peer_switches[1] = nv1 - nv0

    v_before, nv_before = read_ctxt_switches()
    t = threading.Thread(target=peer)
    t.start()

    for _ in range(rounds):
        os.write(w1, b"x")
        os.read(r2, 1)

    t.join()
    v_after, nv_after = read_ctxt_switches()

    os.close(r1)
    os.close(w1)
    os.close(r2)
    os.close(w2)

    print(
        f"[2] Main thread switches   : +{v_after - v_before} voluntary, "
        f"+{nv_after - nv_before} nonvoluntary"
    )
    print(
        f"[2] Peer thread switches   : +{peer_switches[0]} voluntary, "
        f"+{peer_switches[1]} nonvoluntary"
    )


if __name__ == "__main__":
    benchmark_vdso_vs_syscall()
    trigger_voluntary_switch_storm()
```

#### Summary of Diagnostic Commands

| Symptom | Primary Tool | What to Inspect |
| :--- | :--- | :--- |
| Load Average high, unsure why | `uptime`, `nproc`, `vmstat 1` | Compare 1m/5m/15m load to CPU count; check `r` (CPU queue) vs `b` (uninterruptible I/O sleep) |
| High `%iowait` and `b > 0` | `ps -eo pid,stat,comm \| awk '$2 ~ /D/'` | Identify processes stuck in `D` (`TASK_UNINTERRUPTIBLE`) state |
| High `%sys` and `vmstat` `cs` $> 100\text{k}$ | `pidstat -w -t 1` | Separate `cswch/s` (lock/I/O blocking) from `nvcswch/s` (CPU oversubscription preemption) |
| Mystery `%sys` CPU on a single PID | `strace -c -p <PID>` or `perf top -p <PID>` | Count syscall frequency/time (`futex`, `epoll_wait`, `read`) and hot kernel symbols |
