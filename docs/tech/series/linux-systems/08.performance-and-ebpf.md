## Before you start

A network request passes through many queues before your program sees it: the network card, the kernel, the TCP handshake queues, and finally the socket buffer. Each queue can overflow in its own way, and each leaves a different counter behind. This chapter walks that path, including a classic oddity where requests take exactly 40 ms because two reasonable TCP features wait on each other. It then closes the series with two working habits: tracing a live system safely with eBPF, and checking every resource for utilization, saturation and errors (the USE method) instead of guessing. To see a queue yourself, run `ss -lnt` and read the `Recv-Q` and `Send-Q` columns for listening sockets.

You should have read [chapter 7](/tech/series/linux-systems/07.signals-and-timers/) on softirqs, since packet receive work runs there.

Terms used in this chapter:

- **SYN queue / accept queue**: the two kernel queues for new TCP connections, one for half-open handshakes and one for completed ones waiting for `accept()`.
- **TIME_WAIT**: a TCP state a closed connection stays in for a while so stray late packets are not mistaken for a new connection.
- **Nagle's algorithm**: a TCP rule that holds back small writes until earlier data is acknowledged.
- **delayed ACK**: a receiver holding an acknowledgement briefly, hoping to send it along with data.
- **eBPF**: a way to run small, verified programs inside the kernel to collect data without changing it.
- **bpftrace**: a high-level tool for writing short eBPF tracing scripts.
- **USE method**: for each resource, check Utilization, Saturation and Errors.
- **NUMA**: a hardware layout where memory is closer to some CPUs than others.

### 1. The End-to-End Linux Network RX/TX Path and Where Packets Drop

When a packet arrives at a network interface card (NIC), it passes through five distinct queues and layers before your application's `read()` or `recv()` returns:

```text
Incoming Wire Packet
  │
  ▼  [Drop point 1: NIC FIFO / RingBuffer overflow -> ethtool -S rx_missed_errors / ifconfig 'overruns']
1. NIC DMA RingBuffer (rx_ring)
  │  • DMA engine copies frame to kernel memory; raises MSI-X hardirq -> NAPI poll (NET_RX_SOFTIRQ)
  ▼  [Drop point 2: netdev_max_backlog / softnet time squeeze -> /proc/net/softnet_stat]
2. Kernel struct sk_buff (skb) + Gro / Netfilter (conntrack / iptables / nftables)
  │  • Drop point 3: nf_conntrack table full! -> dmesg "nf_conntrack: table full, dropping packet"
  ▼
3. TCP Layer (Handshake & Ordering Queues)
  │  • Half-open SYN Queue (max = net.ipv4.tcp_max_syn_backlog)
  │  • Completed Accept Queue (max = min(backlog, net.core.somaxconn))
  ▼  [Drop point 4: Socket Receive Buffer full -> netstat -s / ss -m (skmem_r >= rcvbuf)]
4. Socket Receive Buffer (sk_rcvbuf, tuned by net.ipv4.tcp_rmem)
  │
  ▼  epoll_wait() wakes thread -> recv() copies skb payload to user space
5. User-Space Application Buffer
```

#### 1.1 Checking Packet Drops Across All Four Layers

Never stop at `ifconfig` or `ip -s link` when hunting packet loss; each layer records drops in its own counter:

| Layer | Diagnostic Command | Critical Counter & Root Cause |
| :--- | :--- | :--- |
| **1. NIC Hardware & RingBuffer** | `ethtool -S eth0`, `ethtool -g eth0`, `ip -s link` | `rx_fifo_errors` / `rx_missed_errors` / `overruns`: NIC RingBuffer overflowed before NAPI could drain it. Increase ring size (`ethtool -G eth0 rx 4096`). |
| **2. NAPI Softnet Queue** | `cat /proc/net/softnet_stat` | Column 1 = processed frames; **Column 2 (`dropped`)** = `net.core.netdev_max_backlog` overflow; **Column 3 (`time_squeeze`)** = `net.core.netdev_budget` exhausted before NAPI poll finished! |
| **3. Netfilter Conntrack** | `sysctl net.netfilter.nf_conntrack_count`, `dmesg -T` | If `nf_conntrack_count` hits `nf_conntrack_max`, the firewall silently drops new connections! Raise `nf_conntrack_max` or bypass tracking (`NOTRACK`) for high-PPS endpoints. |
| **4. TCP Protocol & Backlog** | `netstat -s \| grep -iE 'listen|drop|overflow|retrans'`, `ss -lnt` | `SYNs to LISTEN sockets dropped` or `times the listen queue of a socket overflowed`. |

### 2. Performance Debugging Playbook: TCP Queues, `TIME_WAIT`, and the 40 ms Latency Trap

#### 2.1 SYN Queue vs. Accept Queue Overflow (`ss -lnt`)

Every listening TCP socket (`LISTEN` state) maintains two queues:

1. **SYN Queue (Incomplete Connection Queue)**: Holds connections that received `SYN` and sent `SYN+ACK` (`SYN_RECV` state), waiting for the client's final `ACK`. Bounded by `net.ipv4.tcp_max_syn_backlog` (and protected during floods by `net.ipv4.tcp_syncookies = 1`).
2. **Accept Queue (Complete Connection Queue)**: Holds connections that completed the 3-way handshake (`ESTABLISHED`) and are waiting for the user-space server thread to call `accept4()`.
   - **Maximum capacity**: $\min(\text{application } \texttt{listen(fd, backlog)}, \texttt{net.core.somaxconn})$.
   - **How to inspect live queue depth with `ss -lnt`**:
     For **`LISTEN` sockets**, `ss -lnt` repurposes the `Recv-Q` and `Send-Q` columns:
     - **`Recv-Q`**: Current number of completed connections sitting in the **Accept Queue** waiting for `accept4()`.
     - **`Send-Q`**: The configured maximum capacity of that socket's Accept Queue!

```text
$ ss -lnt
State    Recv-Q    Send-Q       Local Address:Port        Peer Address:Port
LISTEN   129       128                0.0.0.0:8080             0.0.0.0:*
```

In the output above, `Recv-Q (129) > Send-Q (128)`: **the Accept Queue is 100% full**! Any new client completing a handshake will have its `ACK` ignored (or receive `RST` if `net.ipv4.tcp_abort_on_overflow = 1`), causing client connection timeouts. Fix by raising **both** `net.core.somaxconn` (e.g., `4096`) and the application's `listen()` backlog parameter, and ensuring worker threads aren't blocked by GC or synchronous I/O.

#### 2.2 `TIME_WAIT` Port Exhaustion vs. `CLOSE_WAIT` Leaks

Run `ss -s` (summary) to view socket state totals in $< 1\text{ ms}$ (never run slow `netstat -ant` when a host has 100,000+ sockets!):

```text
$ ss -s
Total: 34120
TCP:   32890 (estab 1420, closed 31200, orphaned 12, timewait 31180)
```

Never confuse `TIME_WAIT` with `CLOSE_WAIT`:

- **`TIME_WAIT` (Active Closer)**: Appears on the side that initiates `close()` first (sending the first `FIN`). The socket remains in `TIME_WAIT` for $2 \times \text{MSL}$ (`60 seconds` on Linux) to absorb stray duplicate packets in the network and ensure the peer received the final `ACK`.
  - *Symptom*: An HTTP reverse proxy or service making thousands of short-lived outbound connections per second without HTTP Keep-Alive / connection pooling exhausts its ephemeral port range (`net.ipv4.ip_local_port_range`, default `32768..60999` = ~28,000 ports) and fails `connect()` with **`EADDRNOTAVAIL` (`Cannot assign requested address`)**.
  - *Fix*: Enable **Connection Pooling / HTTP Keep-Alive** first! Then widen `net.ipv4.ip_local_port_range = 10240 65535` and enable **`net.ipv4.tcp_tw_reuse = 1`** (allows outbound `connect()` calls to safely reuse `TIME_WAIT` sockets older than 1 second when TCP timestamps are enabled). *(Note: `tcp_tw_recycle` was broken behind NAT and was completely removed from the Linux kernel in 4.12).*
- **`CLOSE_WAIT` (Passive Closer Bug)**: Appears when the remote peer closed the connection (sent `FIN`), your kernel replied with `ACK`, and your kernel is waiting for **your application code to call `close(fd)`**!
  - *Symptom*: Hundreds or thousands of sockets stuck in `CLOSE_WAIT` for hours, eventually hitting `EMFILE` (`Too many open files`).
  - *Fix*: **No sysctl can fix `CLOSE_WAIT`**—it is 100% an application code bug (a missing `defer conn.Close()`, `try-with-resources`, or failing to close the socket after `read()` returns `0` EOF).

#### 2.3 The Classic 40 ms Tail-Latency Trap: Nagle's Algorithm + TCP Delayed ACK

Suppose an RPC call between two microservices on the same 10 Gbps LAN takes `0.4 ms` for 99% of requests, but requests that send a small header followed by a small body (`write(header); write(body); read(response)`) consistently take **exactly `40.5 ms`**!

**Root Cause**: The interaction between **Nagle's Algorithm** on the sender and **TCP Delayed ACK** on the receiver:

```text
Sender (Nagle Enabled: default)                   Receiver (Delayed ACK Enabled)
       │                                                 │
       ├── 1. write(header, 100B) ──────────────────────►│ (Sent immediately)
       │                                                 ├── Waits up to 40ms for
       ├── 2. write(body, 200B)                          │   application response to
       │   • Nagle holds 'body' in send buffer because   │   piggyback ACK!
       │     chunk < MSS (1460B) AND chunk 1 is          │   (But app is waiting for
       │     still unacknowledged!                       │    'body' before replying!)
       │                                                 │
       │            ... 40 ms deadlock timer ...         │
       │                                                 ├── 40ms Delayed ACK timer
       │◄───────────────── 3. Bare TCP ACK ──────────────┤   expires!
       ├── 4. Sends 'body' (200B) ──────────────────────►│
```

- **Fix**: On every latency-sensitive TCP socket (HTTP, gRPC, Redis, database drivers, message brokers), disable Nagle's Algorithm by setting **`TCP_NODELAY`** (`setsockopt(fd, IPPROTO_TCP, TCP_NODELAY, &one, sizeof(one))`), or coalesce logical message frames into a single `writev()` buffer before sending.

### 3. Safe Production Observability with eBPF (`BCC` & `bpftrace`)

Traditional `strace` uses `ptrace()`, which stops the target process twice on every single system call (entry and exit), slowing a high-throughput service down by **10x to 50x**. Kernel modules can inspect state at full speed, but a pointer bug crashes the entire machine.

**eBPF (Extended Berkeley Packet Filter)** solves both problems:

1. You write an event handler attached to a **Kernel Tracepoint**, **`kprobe`/`kretprobe`**, **`uprobe`/`uretprobe`**, or network hook (`XDP` / `tc`).
2. Before loading your bytecode into the kernel (`bpf()` syscall), the **In-Kernel eBPF Verifier** statically proves that the program terminates (no unbounded loops), never dereferences unchecked pointers, and never overflows its 512-byte stack.
3. The **JIT Compiler** compiles the verified bytecode into native x86_64/ARM64 machine instructions, aggregating latency histograms or stack traces **in-kernel** via **BPF Maps** so only compact summaries cross to user space!

#### High-Value eBPF One-Liners (`bpftrace`) for Production Triage

```bash
# 1. System-wide latency histogram (in microseconds) of ext4_sync_file (fsync)
sudo bpftrace -e 'kprobe:ext4_sync_file { @ts[tid] = nsecs; }
  kretprobe:ext4_sync_file /@ts[tid]/ {
    @usecs = hist((nsecs - @ts[tid]) / 1000); delete(@ts[tid]);
  }'

# 2. Count syscalls across the system by process name without ptrace overhead!
sudo bpftrace -e 'tracepoint:raw_syscalls:sys_enter { @[comm] = count(); }'

# 3. Trace TCP retransmissions with source/destination IP and TCP state
sudo tcpretrans-bpfcc
```

### 4. The Master Diagnostic Framework: Brendan Gregg's USE Method

When facing an unfamiliar performance incident, avoid "streetlight debugging" (running random tools you happen to remember). Instead, systematically check **every resource** across three metrics (**Utilization, Saturation, Errors**):

- **Utilization**: Percentage of time the resource was busy servicing work (e.g., `85%` CPU busy, `90%` RAM allocated).
- **Saturation**: Degree to which queued work is waiting because demand exceeds capacity (e.g., `vmstat` `r` runqueue length, `iostat` `aqu-sz` queue depth, `sar -B` page-scan rate, TCP `ss -lnt` `Recv-Q` backlog). **Saturation is the primary driver of tail latency!**
- **Errors**: Explicit failure events (NIC `dropped`/`overruns`, TCP retransmits, `dmesg` I/O or OOM errors, `ENOSPC`/`EMFILE`). Always check Errors early—they are unambiguous and fast to read.

| Subsystem | Utilization Check | Saturation (Queue / Wait) Check | Errors Check |
| :--- | :--- | :--- | :--- |
| **CPU** | `mpstat -P ALL 1` (`%usr`, `%sys`, `%soft`, `%steal`) | `vmstat 1` (`r` > CPUs), `pidstat -w 1` (`nvcswch/s`), `/sys/fs/cgroup/cpu.stat` (`nr_throttled`) | `perf stat` (PMI / thermal throttle events), `dmesg` (MCE hardware errors) |
| **Memory** | `free -h` (`MemAvailable`), `/proc/<PID>/smaps_rollup` (`PSS`, `USS`), `slabtop -s c` | `vmstat 1` (`si`/`so` > 0), `sar -B 1` (`pgscand/s` direct reclaim), `pidstat -r 1` (`majflt/s`) | `dmesg -T \| grep -i oom`, `/sys/fs/cgroup/memory.events` (`oom_kill`) |
| **Storage I/O** | `iostat -d -x 1` (`%util`, `r/s + w/s`, `rkB/s + wkB/s`) | `iostat -d -x 1` (`aqu-sz`, `r_await`, `w_await`), `vmstat 1` (`b` > 0 `D`-state tasks) | `dmesg -T \| grep -iE 'blk_update_request\|I/O error'`, `smartctl -a` |
| **Network** | `sar -n DEV 1` (`rxpck/s` PPS, `rxkB/s` BPS, `%ifutil`) | `ss -lnt` (`Recv-Q` accept backlog), `/proc/net/softnet_stat` (`time_squeeze`), `netstat -s` | `ethtool -S eth0`, `ip -s link` (`dropped`/`overruns`), `sar -n EDEV 1`, `tcpretrans-bpfcc` |

### 5. The Disciplined Diagnostic Loop: Solving Elusive Infrastructure Bugs

What happens when all four standard subsystems look normal at first glance, or when two identical servers running the exact same binary behave completely differently?

Consider a post-mortem of this shape (an illustrative case with rounded numbers, not a measurement from my own machines): a production server began dropping network packets and suffering high `NET_RX` softirq CPU on one specific NUMA node, even though PPS was moderate and NIC settings matched every healthy peer in the cluster.

Walking through the **4-Step Disciplined Diagnostic Loop** revealed why:

1. **Localize the Anomaly (Diff Healthy vs. Sick)**:
   `perf top` on the degraded server showed `ksoftirqd` spending over `60%` of its CPU cycles inside a single kernel instruction—`memcpy_erms` (`REP MOVSB`) while copying incoming packet data into `sk_buff` memory on **NUMA Node 1**, whereas **NUMA Node 0** on the *same server* copied packets in 1/17th the cycles!
2. **Formulate Falsifiable Hypotheses**:
   Why would `memcpy` into RAM on Socket 1 run at **1/17th (`~6%`) the memory bandwidth** of Socket 0?
   - *Hypothesis A*: CPU frequency scaling (`cpufreq`) throttled Socket 1 cores down to 800 MHz.
   - *Hypothesis B*: Cross-NUMA remote memory access (`numastat` remote misses).
   - *Hypothesis C*: Physical DDR memory controller throttling on Socket 1.
3. **Test One Variable at a Time (Isolate with Micro-Benchmarks)**:
   - Checked `/proc/cpuinfo` and `turbostat`: both sockets ran at 3.2 GHz (*Hypothesis A falsified*).
   - Pinned a pure memory-bandwidth benchmark (`mbw` / `stream`) exclusively to Node 0 (`numactl --cpunodebind=0 --membind=0`) vs. Node 1 (`numactl --cpunodebind=1 --membind=1`): Node 0 achieved `13,800 MB/s`, while Node 1 achieved only **`810 MB/s`**—reproducing the exact 17x slowdown completely outside the network stack!
4. **Root Cause Verification**:
   Inspecting hardware IPMI / EDAC / `dmesg` logs revealed that a DIMM on Socket 1 was generating thousands of **Correctable ECC Memory Errors per second**, triggering firmware thermal/error throttling on Socket 1's memory controller! What looked like a "Linux network softirq bug" was in fact degraded physical RAM bandwidth starving DMA and `sk_buff` copies.

### 6. Verification Lab: Live TCP Backlog Inspector & Nagle (`TCP_NODELAY`) Latency Benchmark

The script below demonstrates two critical network diagnostics on a local loopback socket pair:

1. Inspects `/proc/net/softnet_stat` to verify zero NAPI `dropped` or `time_squeeze` events across all CPU cores.
2. Measures write-write-read micro-frames with `TCP_NODELAY` enabled and then disabled on the client (the server always keeps it on). Loopback can hide the 40 ms stall because of the kernel's quick-ACK heuristics, so treat a small gap as expected and reproduce the real effect across a LAN.

```python
#!/usr/bin/env python3
"""
1. Parse /proc/net/softnet_stat across all CPUs to check NAPI processed,
   dropped, and time_squeeze counters.
2. Time write-write-read round trips with TCP_NODELAY on and off.
"""
import socket
import threading
import time


def inspect_softnet_stat() -> None:
    """Parse hex counters in /proc/net/softnet_stat (col 0=processed, 1=dropped, 2=time_squeeze)."""
    processed = dropped = time_squeeze = 0
    cpus = 0
    with open("/proc/net/softnet_stat", "r", encoding="utf-8") as f:
        for line in f:
            cols = line.split()
            if len(cols) >= 3:
                cpus += 1
                processed += int(cols[0], 16)
                dropped += int(cols[1], 16)
                time_squeeze += int(cols[2], 16)
    print("=== [1] Kernel NAPI /proc/net/softnet_stat Summary ===")
    print(f"  CPUs inspected     : {cpus}")
    print(f"  Total packets      : {processed:,}")
    print(f"  Backlog dropped    : {dropped:,}")
    print(f"  NAPI time_squeeze  : {time_squeeze:,}")


def benchmark_tcp_nodelay(nodelay: bool, rounds: int = 200) -> None:
    srv = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
    srv.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
    srv.bind(("127.0.0.1", 0))
    srv.listen(128)
    port = srv.getsockname()[1]

    def echo_server() -> None:
        conn, _ = srv.accept()
        conn.setsockopt(socket.IPPROTO_TCP, socket.TCP_NODELAY, 1)
        try:
            for _ in range(rounds):
                data = b""
                while len(data) < 64:
                    chunk = conn.recv(64 - len(data))
                    if not chunk:
                        return
                    data += chunk
                conn.sendall(b"OK")
        finally:
            conn.close()

    t = threading.Thread(target=echo_server, daemon=True)
    t.start()

    cli = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
    cli.setsockopt(socket.IPPROTO_TCP, socket.TCP_NODELAY, int(nodelay))
    cli.connect(("127.0.0.1", port))

    t0 = time.perf_counter()
    for _ in range(rounds):
        # Two small consecutive writes (header + body) followed by response read
        cli.send(b"H" * 16)
        cli.send(b"B" * 48)
        resp = cli.recv(2)
        assert resp == b"OK"
    elapsed_ms = (time.perf_counter() - t0) * 1000.0

    nodelay_val = cli.getsockopt(socket.IPPROTO_TCP, socket.TCP_NODELAY)
    cli.close()
    srv.close()
    t.join(timeout=1.0)

    print(f"\n=== [2] Write-Write-Read with TCP_NODELAY={int(nodelay)} ===")
    print(f"  TCP_NODELAY state  : {nodelay_val}")
    print(f"  {rounds}x split-write RTT : {elapsed_ms:6.2f} ms total ({elapsed_ms / rounds * 1000:5.1f} us/req)")


if __name__ == "__main__":
    inspect_softnet_stat()
    # Loopback often hides the 40 ms stall (quick-ACK heuristics), so the gap
    # may be small here; on a real LAN with a delayed-ACK peer it is large.
    benchmark_tcp_nodelay(nodelay=True)
    benchmark_tcp_nodelay(nodelay=False)
```

8. **Chapter 08 (Network Stack, eBPF & The USE Method)**: End-to-end RX/TX packet drop points, SYN vs. Accept queues (`ss -lnt`), `TIME_WAIT` vs. `CLOSE_WAIT`, the 40 ms Nagle + Delayed ACK trap (`TCP_NODELAY`), safe eBPF histograms, and the USE Method.
