## Before you start

Some events do not wait for your program to ask. When you press Ctrl-C, the kernel sends the process a signal and interrupts whatever it was doing, like a phone ringing mid-sentence. A signal handler runs in that interrupted context, so it can only do a few safe things. Hardware works the same way: when a network card receives a packet it interrupts a CPU, and the kernel defers most of the real work to a later stage. On a machine receiving a flood of tiny packets, that deferred work can eat a whole core. Run `kill -l` to list the signals, and `cat /proc/softirqs` to see the deferred-work counters per CPU.

Chapter 1 introduced system calls and context switches, which interrupts and signals both cause more of: [System Call Boundaries](/tech/series/linux-systems/01.syscalls-and-abi/).

Terms used in this chapter:

- **signal**: a small numbered notification the kernel delivers to a process, such as `SIGTERM` or `SIGCHLD`.
- **async-signal-safe**: a function that is safe to call from a signal handler, because it cannot deadlock on state the interrupted code holds.
- **`signalfd` / `timerfd`**: descriptors that deliver signals or timer expirations as readable data, so an event loop can wait on them.
- **hardirq (top half)**: the minimal code that runs immediately when a device interrupts the CPU.
- **softirq (bottom half)**: deferred kernel work, such as network packet processing, run shortly after the hardirq.
- **ksoftirqd**: a per-CPU kernel thread that takes over softirq work when it gets too heavy.
- **`%si`**: the share of CPU time spent handling softirqs.
- **PPS**: packets per second, as opposed to bytes per second.

## Linux Systems & Performance 07: Signals, Hardware/Software Interrupts (ksoftirqd) & Small-Packet Storms

Asynchronous notifications occur at two levels in Linux:

1. **Kernel-to-User Notifications (Signals & Timers)**: The kernel interrupts a user-space thread's normal instruction flow to deliver `SIGINT`, `SIGTERM`, `SIGCHLD`, `SIGSEGV`, or timer expirations.
2. **Hardware-to-Kernel Notifications (Hardware IRQs & Software IRQs)**: Physical devices (NICs, NVMe drives, hardware timers) assert interrupt lines on the CPU's APIC, preempting whatever process is running so the kernel can service incoming packets or completed disk I/O.

Both mechanisms share the same core engineering challenge: **if an asynchronous handler runs with interrupts or locks disabled for too long, it deadlocks or starves the entire system**. In user space, violating async-signal-safety deadlocks `malloc()` or `printf()`. In kernel space, a flood of tiny network packets overwhelms Bottom-Half software interrupts (`NET_RX`), pinning `%si` (softirq CPU) and `ksoftirqd/N` near `100%` while normal user processes appear idle.

### 1. User-Space Asynchronous Control: Signals, Masks, and `signalfd`

A **Signal** is a software interrupt delivered to a specific thread or process (`task_struct`). The kernel tracks signals per thread in two bitmasks (visible in `/proc/<PID>/status` as `SigPnd`, `ShdPnd`, `SigBlk`, `SigIgn`, `SigCgt`):

- **Pending Mask (`pending` / `shared_pending`)**: Signals that have been generated for this thread or thread group but not yet delivered. Standard UNIX signals (`1..31`, like `SIGTERM` or `SIGCHLD`) are **non-queuing booleans**: if five child processes exit simultaneously while `SIGCHLD` is blocked, the kernel sets the single `SIGCHLD` bit (`1 << (SIGCHLD - 1)`) once! A `SIGCHLD` handler must therefore loop on `while (waitpid(-1, &status, WNOHANG) > 0)` until no more children remain to be reaped.
- **Blocked Mask (`blocked` / `sigprocmask` / `pthread_sigmask`)**: Signals currently masked from delivery; they remain pending until unblocked (`SIGKILL = 9` and `SIGSTOP = 19` cannot be blocked, caught, or ignored).

#### 1.1 The Async-Signal-Safety Trap (Why `printf` and `malloc` Deadlock in Signal Handlers)

When the kernel delivers a caught signal to a thread (typically upon returning from a system call or timer interrupt back to Ring 3), it hijacks the thread's user-space instruction pointer (`rip`) to run the registered `sigaction` handler on the **exact same thread**.

Suppose your thread is half-way through calling `malloc()` or `printf()` (holding the internal glibc heap mutex `main_arena.mutex` or `stdout` lock) when `SIGTERM` arrives:

1. The kernel pauses your thread right inside `malloc()`—while it still holds the non-recursive heap lock!
2. Your signal handler runs on the same thread and calls `syslog()`, `printf()`, or `free()`, which internally tries to acquire `main_arena.mutex`.
3. Because the interrupted frame below it on the same thread's stack already holds that lock, **the thread deadlocks against itself forever (`futex_wait_queue_me`)**!

**Two Production-Safe Architectures for Signal Handling**:

1. **Strict `async-signal-safe` Handler (`man 7 signal-safety`)**: Keep the traditional signal handler restricted to setting a `volatile sig_atomic_t` flag or writing 1 byte (`write(pipe_wfd, "!", 1)`) into a self-pipe monitored by your main `epoll` loop.
2. **Synchronous File-Descriptor Signals (`signalfd`)**: Block the signals across all threads with `pthread_sigmask(SIG_BLOCK, &mask, NULL)`, and call `signalfd(-1, &mask, SFD_NONBLOCK | SFD_CLOEXEC)`. The kernel turns pending signals into 128-byte `struct signalfd_siginfo` records that your normal `epoll_wait()` event loop reads synchronously—allowing you to safely use `malloc`, logging, and mutexes!

#### 1.2 Monotonic Clocks and `timerfd`

Never use wall-clock time (`CLOCK_REALTIME` / `gettimeofday`) to measure timeouts or schedule intervals: if `chronyd` or `ntpd` steps the system clock backward by 500 ms, relative durations go negative or freeze. Always use:

- **`CLOCK_MONOTONIC`**: Guaranteed strictly non-decreasing tick counter since boot (adjusted smoothly in frequency by NTP slewing, never stepped backward).
- **`CLOCK_BOOTTIME`**: Identical to `CLOCK_MONOTONIC`, except it **continues ticking across system suspend/hibernate** states.
- **`timerfd_create(CLOCK_MONOTONIC, TFD_NONBLOCK | TFD_CLOEXEC)`**: Exposes high-resolution kernel timers (`hrtimer`) as a standard file descriptor that becomes readable inside `epoll_wait()` on expiration, returning an 8-byte `uint64_t` count of elapsed expirations.

### 2. Kernel Interrupt Architecture: Top-Half (`hardirq`) vs. Bottom-Half (`softirq`)

When a network card receives a packet or an NVMe drive completes a read, it asserts a hardware interrupt (MSI-X) on a CPU core.

Why doesn't the kernel do all TCP/IP checksum validation, netfilter firewall matching, and socket queuing directly inside the hardware interrupt handler? Because **hardware interrupt handlers (`hardirq`) execute with local CPU interrupts disabled**. If a hardware IRQ handler took 200 microseconds to parse packets, the CPU would miss timer ticks, drop other hardware interrupts, and freeze interactive tasks.

Linux solves this by splitting interrupt processing into two halves:

```text
Physical NIC / NVMe Device
       │
       │ 1. Hardware MSI-X Interrupt
       ▼
┌─────────────────────────────────────────────────────────────────────────┐
│ TOP-HALF: Hardware Interrupt Handler (hardirq, %irq / 'hi' in top)      │
│ • Runs with local interrupts disabled; must finish in < a few microsecs │
│ • Acknowledges hardware IRQ, disables NIC IRQ line (NAPI), and raises   │
│   a Software Interrupt bit (e.g. NET_RX_SOFTIRQ)                        │
│ • Counted in: /proc/interrupts                                          │
└──────────────────────────────┬──────────────────────────────────────────┘
                               │ 2. Raises softirq bit
                               ▼
┌─────────────────────────────────────────────────────────────────────────┐
│ BOTTOM-HALF: Software Interrupt (softirq, %soft / 'si' in top)          │
│ • Runs with hardware interrupts RE-ENABLED!                             │
│ • Polls DMA ring buffer (NAPI poll), allocates sk_buff, runs IP/TCP     │
│   stack, wakes blocked user-space socket threads                        │
│ • If softirq load exceeds budget, offloaded to kernel thread ksoftirqd/N│
│ • Counted in: /proc/softirqs                                            │
└─────────────────────────────────────────────────────────────────────────┘
```

#### 2.1 Reading `/proc/interrupts` and `/proc/softirqs`

Linux exposes per-CPU cumulative counters for both halves:

- **`/proc/interrupts` (Top-Half Hard IRQs)**: Shows each hardware IRQ line, per-CPU count, interrupt controller (`PCI-MSI-edge`), and device name (`nvme0q1`, `eth0-TxRx-0`).
  - *Imbalance check*: If all interrupts for `eth0-TxRx-0` land on `CPU0` while `CPU1..CPU15` sit at `0`, check the IRQ affinity mask in `/proc/irq/<IRQ_NUM>/smp_affinity_list` and verify whether `irqbalance` or multi-queue RSS (Receive Side Scaling) is enabled.
- **`/proc/softirqs` (Bottom-Half Soft IRQs)**: Lists the 10 fixed kernel software interrupt types across every CPU core:

```text
$ cat /proc/softirqs
                    CPU0       CPU1       CPU2       CPU3
          HI:          3          0          1          0
       TIMER:   14820192   14192011   13910421   14019284
      NET_TX:      48210      39104      41209      38910
      NET_RX:  891402190   12491020   11940210   12104912
       BLOCK:     918240     841209     791024     812049
    IRQ_poll:          0          0          0          0
     TASKLET:        412        118         94        102
       SCHED:   28491021   27192041   26910412   27410921
     HRTIMER:       1420       1190       1210       1180
         RCU:   19482011   18910421   18412091   18719204
```

Notice `NET_RX` on `CPU0` above (`891,402,190` vs ~12M on `CPU1..3`)! When `NET_RX` or `TIMER` or `SCHED` grows rapidly, softirq processing consumes significant CPU time (`%soft` in `mpstat`, `si` in `top`). And when softirqs arrive faster than the kernel's immediate post-IRQ loop (`__do_softirq`, capped at `MAX_SOFTIRQ_RESTART = 10` loops or 2 ms) can drain them, the kernel wakes the per-core kernel thread **`ksoftirqd/<cpu>`** so user-space threads aren't completely starved.

### 3. Performance Debugging Playbook: High `%si` (`ksoftirqd`) & Small-Packet Storms

Consider a classic production incident from *Linux Performance Optimization in Practice*:

- An nginx/API server becomes sluggish and unresponsive.
- You run `top` or `mpstat -P ALL 1`:
  - User CPU (`%usr`) is only `4%`, system CPU (`%sys`) is `3%`.
  - However, **`%soft` (`si` in `top`) on `CPU0` is pinned at `85%`**, and the top process in `top` is **`ksoftirqd/0`**!

```text
$ mpstat -P ALL 1 1
08:45:01     CPU    %usr   %nice    %sys %iowait    %irq   %soft  %steal  %guest  %gnice   %idle
08:45:02     all    2.10    0.00    1.80    0.00    0.50   44.20    0.00    0.00    0.00   51.40
08:45:02       0    1.00    0.00    2.00    0.00    1.00   86.00    0.00    0.00    0.00   10.00
08:45:02       1    3.20    0.00    1.60    0.00    0.00    2.40    0.00    0.00    0.00   92.80
```

How do you go from "`ksoftirqd/0` is using 86% softirq CPU" to the exact root cause in under 60 seconds? Follow this four-step diagnostic cascade:

#### Step 1: Watch the Rate of Change in `/proc/softirqs`

Remember that `/proc/softirqs` holds **cumulative** counts since boot! A large historical number might be from last month. Always inspect the **live delta per second** using `watch -d`:

```bash
watch -n 1 -d cat /proc/softirqs
```

Looking at the highlighted changing numbers (`-d`), you immediately see **`NET_RX`** jumping by **hundreds of thousands per second** on `CPU0` (far outpacing `TIMER`, `SCHED`, or `RCU`). That proves the bottleneck is **network packet reception (`NET_RX_SOFTIRQ`)**.

#### Step 2: Inspect Network PPS vs. BPS with `sar -n DEV 1`

Why would network reception burn 86% of a CPU core? Most engineers only check bandwidth (`MB/s`), see `30 MB/s` on a `10 Gbps` NIC, and conclude "the network is barely used!"

Run `sar -n DEV 1` to inspect **both Packets Per Second (`rxpck/s`, PPS) and Kilobytes Per Second (`rxkB/s`, BPS)**:

```text
$ sar -n DEV 1
08:46:01     IFACE   rxpck/s   txpck/s    rxkB/s    txkB/s   rxcmp/s   txcmp/s  rxmcst/s   %ifutil
08:46:02      eth0  685420.0  342100.0   36155.9   18045.8      0.00      0.00      0.00      2.96
```

Look closely at those two numbers for `eth0`:

- **Bandwidth (`rxkB/s`)**: $36,155.9\text{ KB/s} \approx 35.3\text{ MB/s}$ ($\sim 296\text{ Mbps}$, only `2.96%` of link bandwidth!).
- **Packet Rate (`rxpck/s`)**: **$685,420$ packets per second!**
- **Average Bytes Per Packet**:

$$\frac{36,155.9 \times 1024\text{ bytes/sec}}{685,420\text{ packets/sec}} \approx \mathbf{54\text{ bytes/packet}}$$

A **54-byte Ethernet frame** ($14\text{B Ethernet header} + 20\text{B IPv4 header} + 20\text{B TCP header} = 54\text{ bytes}$, with **0 bytes of payload**) is the typical signature of a **small-packet flood (such as a TCP `SYN` flood or bare `ACK` storm)**! Because Linux softirq overhead (`sk_buff` allocation, DMA unmapping, routing lookup, netfilter `conntrack` table lookup, TCP state lookup) scales with **Packets Per Second (PPS)** rather than bytes per second, 685k tiny packets/sec completely saturates `ksoftirqd/0` even at 3% bandwidth.

#### Step 3: Capture the Offending Frames with `tcpdump`

Confirm the packet type, source/destination IPs, and TCP flags (`S` = `SYN`) using `tcpdump`:

```bash
# -n: do not resolve DNS names (critical during incidents!)
# -i eth0: capture on eth0
# -c 10: stop after 10 packets
# filter: TCP SYN packets to port 80 only
$ sudo tcpdump -nn -i eth0 -c 10 'tcp port 80 and tcp[tcpflags] & tcp-syn != 0'
08:47:10.104912 IP 198.51.100.42.51824 > 10.0.1.15.80: Flags [S], seq 294810291, win 64240, length 0
08:47:10.104914 IP 198.51.100.89.39104 > 10.0.1.15.80: Flags [S], seq 918204912, win 64240, length 0
```

#### Step 4: Mitigations for High `NET_RX` Softirq and Small-Packet Floods

1. **Multi-Queue NIC RSS / RPS (Receive Packet Steering)**:
   Notice in `mpstat` above that `CPU0` was at `86%` `%soft` while `CPU1..3` were at `2.4%`. Enable multi-queue NIC interrupts (`ethtool -L eth0 combined 4`), distribute IRQ affinity across cores (`/proc/irq/*/smp_affinity_list`), or enable software **RPS (`rps_cpus`)** in `/sys/class/net/eth0/queues/rx-0/rps_cpus` so `NET_RX` softirqs spread across all CPU cores.
2. **NIC Offloads & Interrupt Coalescing**:
   Verify **GRO (Generic Receive Offload)** is enabled (`ethtool -k eth0 | grep generic-receive-offload`) so the NAPI poll merges sequential TCP segments into a single super-packet before traversing the IP/TCP stack, and tune interrupt coalescing (`ethtool -C eth0 rx-usecs 50`).
3. **Drop Malicious Traffic Before the TCP Stack (`XDP` / `tcp_syncookies`)**:
   Enable `net.ipv4.tcp_syncookies = 1`, increase `net.ipv4.tcp_max_syn_backlog`, or drop DDoS packets inside the NIC driver before `sk_buff` allocation using **eBPF XDP (eXpress Data Path)**.

### 4. Verification Lab: Live `/proc/softirqs` Delta Analyzer & Signal Mask Inspector

The script below parses `/proc/softirqs` over a sampling window to rank the top software interrupt sources per CPU core (just like `watch -d cat /proc/softirqs`), and inspects the calling process's signal bitmasks (`SigBlk`, `SigIgn`, `SigCgt`) from `/proc/self/status`.

```python
#!/usr/bin/env python3
"""
1. Compute live per-second deltas across /proc/softirqs (NET_RX, TIMER, SCHED, RCU).
2. Decode the process's blocked/ignored/caught signal bitmasks from /proc/self/status.
"""
import signal
import time


def parse_softirqs() -> dict[str, int]:
    """Return total softirq counts summed across all CPUs for each vector."""
    totals: dict[str, int] = {}
    with open("/proc/softirqs", "r", encoding="utf-8") as f:
        lines = f.readlines()
    for line in lines[1:]:
        if ":" not in line:
            continue
        name, counts_str = line.split(":", 1)
        totals[name.strip()] = sum(int(x) for x in counts_str.split())
    return totals


def decode_sigmask_hex(hex_str: str) -> list[str]:
    mask = int(hex_str.strip(), 16)
    names: list[str] = []
    for sig in signal.Signals:
        if mask & (1 << (sig.value - 1)):
            names.append(sig.name)
    return names


def main() -> None:
    s0 = parse_softirqs()
    time.sleep(0.25)
    s1 = parse_softirqs()

    print("=== [1] Live /proc/softirqs Activity (0.25s sample across all CPUs) ===")
    deltas = sorted(((k, s1[k] - s0[k]) for k in s0), key=lambda x: x[1], reverse=True)
    for vec, diff in deltas[:6]:
        print(f"  {vec:10s}: +{diff:6d} softirqs ({diff * 4:7d}/sec est.)")

    # Block SIGUSR1 temporarily and verify /proc/self/status SigBlk reflects it
    signal.pthread_sigmask(signal.SIG_BLOCK, [signal.SIGUSR1])
    print("\n=== [2] Signal Bitmasks in /proc/self/status (with SIGUSR1 blocked) ===")
    with open("/proc/self/status", "r", encoding="utf-8") as f:
        for line in f:
            key = line.split(":", 1)[0]
            if key in ("SigBlk", "SigIgn", "SigCgt"):
                hex_val = line.split(":", 1)[1].strip()
                decoded = decode_sigmask_hex(hex_val)
                print(f"  {key}: {hex_val} -> {decoded}")
    signal.pthread_sigmask(signal.SIG_UNBLOCK, [signal.SIGUSR1])


if __name__ == "__main__":
    main()
```

#### Summary of Interrupt & Signal Diagnostic Commands

| Symptom | Primary Tool | What to Inspect |
| :--- | :--- | :--- |
| High `%irq` (`hi`) or single-CPU IRQ bottleneck | `watch -d cat /proc/interrupts` | Check hardware IRQ rate per core and `/proc/irq/<N>/smp_affinity_list` |
| High `%soft` (`si`) and `ksoftirqd/N` burning CPU | `watch -d cat /proc/softirqs` | Identify whether `NET_RX`, `TIMER`, `SCHED`, or `RCU` is spiking |
| `NET_RX` spiking at low network bandwidth (`MB/s`) | `sar -n DEV 1`, `tcpdump -nn -i eth0` | Compare `rxpck/s` (PPS) to `rxkB/s` (BPS); $\sim 54\text{ B/pkt}$ proves a small-packet / SYN storm |
| Process deadlocked inside a signal handler | `cat /proc/<PID>/stack`, `pstack <PID>` | Look for `futex_wait` inside `malloc`/`free`/`syslog` invoked from `__restore_rt` (signal frame) |
