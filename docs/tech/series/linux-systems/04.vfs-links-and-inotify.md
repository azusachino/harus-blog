## Before you start

A file name is not the file. On Linux the name is an entry in a directory that points at an inode, which holds the size, owner and the location of the data. That split explains puzzles that look like bugs. You delete a 20 GB log, `df` still says the disk is full, because a running process holds it open and the data is freed only when the last user lets go. Or the disk shows 50% free but writes fail with "No space left on device", because the filesystem ran out of inodes rather than bytes. Try `df -h` next to `df -i` to see both budgets.

The kernel hides all filesystem types behind one interface, the VFS, which is why the same `read()` works on a disk, a network share and `/proc`. Read [chapter 3](/tech/series/linux-systems/03.buffered-and-direct-io/) first for the page cache that these caches sit beside.

Terms used in this chapter:

- **VFS**: the kernel layer that gives every filesystem the same set of operations.
- **inode**: the on-disk record describing one file's metadata and data location, but not its name.
- **dentry**: a cached link between a name in a directory and an inode.
- **hard link / symbolic link**: a hard link is another name for the same inode; a symbolic link is a small file holding a path.
- **slab cache**: kernel memory pools for frequently allocated small objects such as inodes and dentries.
- **mount namespace**: a per-process view of which filesystems are mounted where.
- **inotify**: a kernel interface that tells a program when files in a watched directory change.

## Linux Systems & Performance 04: VFS, Dentry/Inode Slab Caches, Mount Namespaces & Metadata Debugging

How can a single `read()` system call work identically on an NVMe-backed `ext4` partition, an in-memory `tmpfs` mount, a remote `NFS` share, and a virtual `/proc/self/status` file generated on the fly?

The answer is the **Virtual File System (VFS)**—an object-oriented dispatch layer written in C inside the Linux kernel. Every filesystem registers function-pointer tables (`inode_operations`, `file_operations`, `dentry_operations`) behind four core kernel objects. Understanding how those four objects live in **Kernel Slab Caches** and interact with the Page Cache is essential for debugging three notorious production incidents:

1. `No space left on device` (`ENOSPC`) when `df -h` reports `60%` free disk space.
2. `df -h` reporting `99%` disk usage while `du -sh /` adds up to only `10%`.
3. Latency spikes caused by aggressive `vm.vfs_cache_pressure` tuning or negative-dentry slab bloat.

### 1. The Four Core VFS Objects

<Archify src="./diagrams/vfs-page-cache-writeback.workflow.json" />

Whenever a process resolves a path like `/var/log/nginx/access.log`, the VFS walks four interconnected C structures in kernel memory:

```text
┌─────────────────────────────────────────────────────────────────────────┐
│ 1. struct super_block (Mounted Filesystem Instance)                     │
│    • Block size, filesystem type (ext4, xfs, proc), dirty inode list    │
│    • s_op -> alloc_inode(), statfs(), sync_fs()                         │
└───────────────────────────────┬─────────────────────────────────────────┘
                                │ owns
                                ▼
┌─────────────────────────────────────────────────────────────────────────┐
│ 2. struct dentry (Directory Entry / Path Component Cache)               │
│    • Maps a single path component ("var" -> "log" -> "access.log")      │
│    • Exists purely in RAM (dentry_cache slab); drives fast path lookup  │
└───────────────────────────────┬─────────────────────────────────────────┘
                                │ d_inode pointer
                                ▼
┌─────────────────────────────────────────────────────────────────────────┐
│ 3. struct inode (Filesystem Object Metadata + Data Blocks)              │
│    • Inode number (i_ino), mode, UID/GID, size, hard-link count (i_nlink│
│    • i_mapping -> struct address_space (owns the file's Page Cache!)    │
└───────────────────────────────▲─────────────────────────────────────────┘
                                │ f_inode pointer
┌───────────────────────────────┴─────────────────────────────────────────┐
│ 4. struct file (Open File Description for an active process FD)         │
│    • Current offset (f_pos), status flags (O_APPEND, O_NONBLOCK)        │
└─────────────────────────────────────────────────────────────────────────┘
```

#### 1.1 Hard Links vs. Symbolic Links at the Inode Boundary

A directory on disk is simply a special file containing a table of `(filename -> inode_number)` mappings:

- **Hard Link (`ln target link_name`)**: Adds a second directory entry pointing to the **exact same `inode_number`** and increments `inode->i_nlink`. Both names are equal peers; neither is the "original."
  - *Two architectural limits*: Because inode numbers are only unique within a single mounted filesystem (`super_block`), hard links **cannot cross mount points** (`EXDEV`). And to prevent cycles in the directory tree that would trap `fsck` and `find` in infinite loops, user space **cannot create hard links to directories** (`EPERM`).
- **Symbolic Link (`ln -s target_path link_name`)**: Creates a **brand-new inode** (`S_IFLNK`) whose data payload is the literal text string `"target_path"` (if the string is under 60 bytes on ext4, it is stored inline inside the inode's block pointers area—a *fast symlink*). Symlinks can cross filesystems and point to directories or non-existent paths (*dangling symlinks*).

### 2. The Unlinked-Open-File Lifecycle and the `df` vs. `du` Mystery

Why is the Linux system call to delete a file named `unlink(const char *pathname)` rather than `delete()`?

Because `unlink()` only removes the `(filename -> inode)` entry from the parent directory and decrements `inode->i_nlink`. **The kernel frees the inode and reclaims its disk blocks if and only if BOTH conditions hold**:

1. **`i_nlink == 0`** (no directory entry points to the inode).
2. **`i_count / open f_count == 0`** (no process holds an open `struct file` referencing the inode).

#### 2.1 Intentional Use vs. Production Incident

- **Intentional Security Pattern**: Databases, compilers, and `tmpfile(3)` create a file and **immediately call `unlink()` while keeping the `fd` open**. The process can read and write the file normally, no other process can see or tamper with it in the directory tree, and if the process crashes (`SIGKILL`), the kernel automatically closes the `fd` and reclaims the disk blocks—leaving zero orphaned temp files behind.
- **Production Incident (`df -h` says 99% full, `du -sh` says 12 GB)**:
  A service writes to `/var/log/app.log` without logrotate's `copytruncate` or a `SIGHUP` reopen handler. An operator runs `rm /var/log/app.log` to free 80 GB of disk space.
  - `du -sh /var/log` walks directory trees via `readdir()` + `stat()`. Since the directory entry was unlinked, `du` no longer sees `app.log` and reports only 12 GB used.
  - `df -h` queries the filesystem `super_block` via `statfs()`, which counts actually allocated disk blocks. Because the running daemon still holds `fd 4` open to the unlinked inode, all 80 GB of blocks remain allocated on disk—and keep growing!

#### 2.2 Resolving Deleted-But-Open Files Without Restarting the Service

1. **Find the exact PID and FD holding unlinked files (`i_nlink == 0`)**:

   ```bash
   # List all open files whose link count is < 1
   $ lsof +L1
   COMMAND     PID USER   FD   TYPE DEVICE    SIZE/OFF NLINK    NODE NAME
   app-srv   14920 root    4w   REG  259,1 85899345920     0 1049218 /var/log/app.log (deleted)
   ```

2. **Truncate the file in place via `/proc/<PID>/fd/<FD>` (Zero-Downtime Recovery)**:
   If you cannot immediately restart `PID 14920`, you can truncate its unlinked inode to `0` bytes through `/proc` (assuming the daemon opened the log with `O_APPEND`; otherwise its `f_pos` remains at 80 GB and the next write creates a sparse hole):

   ```bash
   : > /proc/14920/fd/4
   ```

### 3. Performance Debugging Playbook: VFS Slab Caches and Inode Exhaustion

#### 3.1 Incident 1: `No space left on device` (`ENOSPC`) with Plenty of Free GBs

Every file, directory, symlink, and socket file on `ext4` consumes one **inode** from a fixed table created at `mkfs.ext4` time. If an application (such as a build cache, mail queue, or Prometheus/session spool) creates millions of 100-byte files, the filesystem runs out of inodes long before it runs out of 4 KB data blocks:

```bash
# Always check BOTH block capacity (df -h) AND inode capacity (df -i)
$ df -i /
Filesystem       Inodes   IUsed  IFree IUse% Mounted on
/dev/nvme0n1p1  6553600 6553600      0  100% /

# Find which directory subtree holds millions of tiny files
$ find / -xdev -printf '%h\n' | sort | uniq -c | sort -k 1 -nr | head -n 10
```

#### 3.2 Incident 2: Kernel Slab Memory Bloat (`SReclaimable` vs. `SUnreclaim`)

When `free -h` shows `buff/cache` or used memory climbing steadily even though no user process has high `RSS` in `top`, inspect the kernel **Slab Allocator** in `/proc/meminfo` and `slabtop`:

```text
$ grep -E 'Slab|SReclaimable|SUnreclaim' /proc/meminfo
Slab:            6420180 kB
SReclaimable:    5980120 kB
SUnreclaim:       440060 kB
```

- **`SReclaimable`**: Kernel slab caches that `kswapd` can shrink under memory pressure—primarily **`dentry`** (path lookup cache) and **`ext4_inode_cache` / `xfs_inode`** (VFS inodes).
- **`SUnreclaim`**: Unreclaimable kernel slabs (`kmalloc-*`, network `skbuff_head_cache`, leaked kernel objects).

To see which specific slab cache is consuming gigabytes of RAM in real time, run `slabtop -s c` (sort by cache size):

```text
$ sudo slabtop -o -s c | head -n 12
  OBJS ACTIVE  USE OBJ SIZE  SLABS OBJ/SLAB CACHE SIZE NAME
28412000 28410112 99%    0.19K 1352952       21   5411808K dentry
 4120400  4119800 99%    1.06K  274693       15   4395088K ext4_inode_cache
```

- **Why `dentry` explodes**: Every time an application calls `stat("/path/to/nonexistent_file")` and gets `-ENOENT`, the kernel caches a **negative dentry** (`d_inode = NULL`) in the `dentry` slab so future lookups for that missing file return `-ENOENT` from RAM without hitting disk! If a service probes millions of random UUID paths that don't exist, negative dentries can consume gigabytes of `SReclaimable` RAM.

#### 3.3 The `vm.vfs_cache_pressure` Trap: Why Evicting Inodes Drops Page Cache

The sysctl `vm.vfs_cache_pressure` (default `100`) controls how aggressively the kernel reclaims `dentry` and `inode` slab caches relative to the Page Cache and anonymous memory:

- Setting `vm.vfs_cache_pressure < 100` (e.g., `50`) retains `dentry` and `inode` caches longer in RAM, speeding up metadata-heavy workloads (`find`, `git status`, web servers doing frequent `stat()`).
- **The Trap of `vm.vfs_cache_pressure >> 100` (e.g., `500` or `1000`)**:
  look back at the object diagram in section 1: **`struct inode` owns `i_mapping` (`struct address_space`), which holds all of that file's Page Cache pages!**
  In the Linux kernel, **an inode with no open file descriptors cannot be evicted from `inode_cache` without first invalidating and dropping all of its cached 4 KB data pages in the Page Cache**. Therefore, cranking `vm.vfs_cache_pressure` up to `1000` causes `kswapd` to aggressively evict closed inodes—which silently flushes gigabytes of hot Page Cache data along with them and triggers a massive read I/O storm!

### 4. Mount Namespaces, Bind Mounts, and `inotify`

#### 4.1 Mount Propagation (`MS_SHARED` vs. `MS_PRIVATE` vs. `MS_SLAVE`)

A mount point attaches a child `super_block` onto a directory `dentry`. When containers (`CLONE_NEWNS`) clone a mount namespace, how do subsequent `mount()` or `umount()` calls propagate between the host and the container? Linux controls this per mount point via **Peer Groups** listed in `/proc/self/mountinfo`:

| Propagation Mode | Host $\rightarrow$ Container | Container $\rightarrow$ Host | Primary Use Case |
| :--- | :---: | :---: | :--- |
| **`shared` (`MS_SHARED`)** | Yes | Yes | Systemd default for `/` on the host so automounts propagate across host services. |
| **`private` (`MS_PRIVATE`)** | No | No | Container rootfs isolation—mounts inside the container never leak onto the host. |
| **`slave` (`MS_SLAVE`)** | Yes | No | Read-only volume propagation where host volume refreshes appear in the container, but container mounts stay private. |

#### 4.2 Event-Driven VFS Monitoring with `inotify`

Polling directories with `stat()` in a loop wastes CPU and hammers `dentry` caches. The Linux `inotify` subsystem (`inotify_init1(IN_NONBLOCK | IN_CLOEXEC)`, `inotify_add_watch()`) hooks directly into VFS operations (`vfs_write`, `vfs_unlink`, `vfs_rename`) and emits structured events over a pollable file descriptor.

> **Critical `inotify` Production Rule**: Never watch a single configuration file by inode alone (`inotify_add_watch(ifd, "/etc/app/config.yaml", IN_MODIFY)`) if the file is updated atomically by editors (`vim`), `sed -i`, or Kubernetes ConfigMap symlinks! Atomic updates write `/etc/app/.config.yaml.tmp` (a *new* inode) and call `rename()`, leaving your watch stuck on the old, unlinked inode (`IN_IGNORED`). **Always watch the parent directory** for `IN_MOVED_TO | IN_CREATE | IN_CLOSE_WRITE` and filter by filename.

### 5. Verification Lab: Unlinked Open Files and Inode Identity

The script below proves the VFS unlinked-open-file contract on Linux:

1. Creates a file, verifies its inode number (`st_ino`) and hard-link count (`st_nlink == 1`).
2. Calls `os.unlink()` while keeping the file descriptor open, proving `st_nlink` drops to `0` while `pread`/`pwrite` and `/proc/self/fd/<fd>` access continue working seamlessly.

```python
#!/usr/bin/env python3
"""
Verify the Linux VFS lifecycle of an unlinked open file:
1. Hard link increases st_nlink while sharing st_ino.
2. os.unlink() drops st_nlink to 0, yet the open fd remains readable/writable
   and visible as '(deleted)' in /proc/self/fd/<fd>.
"""
import os
import tempfile


def main() -> None:
    with tempfile.TemporaryDirectory() as tmpdir:
        path_a = os.path.join(tmpdir, "alpha.dat")
        path_b = os.path.join(tmpdir, "beta_hardlink.dat")

        fd = os.open(path_a, os.O_RDWR | os.O_CREAT | os.O_EXCL | os.O_CLOEXEC, 0o600)
        os.write(fd, b"VFS-INODE-PAYLOAD")

        # Create a hard link to path_a
        os.link(path_a, path_b)
        st_a = os.stat(path_a)
        st_b = os.stat(path_b)
        assert st_a.st_ino == st_b.st_ino
        assert st_a.st_nlink == 2
        print(f"[1] Hard link verified: ino={st_a.st_ino}, st_nlink={st_a.st_nlink}")

        # Unlink both directory entries while fd stays open
        os.unlink(path_a)
        os.unlink(path_b)

        st_open = os.fstat(fd)
        proc_link = os.readlink(f"/proc/self/fd/{fd}")
        payload = os.pread(fd, 64, 0)

        print(f"[2] After unlinking all names:")
        print(f"    fstat(fd).st_nlink = {st_open.st_nlink} (0 directory links remain)")
        print(f"    /proc/self/fd/{fd} -> {proc_link}")
        print(f"    os.pread(fd)       -> {payload!r}")

        # Closing the final open file description releases the inode and blocks
        os.close(fd)


if __name__ == "__main__":
    main()
```

#### Summary of VFS & Metadata Diagnostic Commands

| Symptom | Primary Tool | What to Inspect |
| :--- | :--- | :--- |
| `ENOSPC` (`No space left`) but `df -h` shows free GBs | `df -i` | Check `IUse%` (`100%` means inode table exhaustion from millions of small files) |
| `df -h` shows 99% full, `du -sh` shows low usage | `lsof +L1` | Find open file descriptors with `NLINK == 0` (`(deleted)` logs holding disk blocks) |
| High memory usage not visible in process `RSS` | `slabtop -s c`, `/proc/meminfo` | Check `SReclaimable` (`dentry`, `ext4_inode_cache`) vs `SUnreclaim` |
| High `dentry` / `inode` miss latency | `bcc/dcsnoop`, `vfsstat 1` | Monitor VFS `READ`/`WRITE`/`FSYNC`/`OPEN`/`CREATE` rates and dcache misses |
