## Linux Systems & Performance 05: Virtual Memory, Page Faults, kswapd Reclaim, Swap & Memory Leak Debugging

Memory issues in Linux rarely fail cleanly at the moment a bug occurs. Because the kernel overcommits virtual addresses (`vm.overcommit_memory = 0`), defers physical frame allocation until a page fault occurs, and runs background page reclaim (`kswapd0`) before invoking the Out-Of-Memory (OOM) killer, a memory bug often surfaces hours later as a mysterious CPU stall, a swap storm (`si`/`so` in `vmstat`), or a sudden `SIGKILL` of your database process.

This chapter connects the **Process & Virtual Memory Architecture** directly to the **Linux Memory Performance Debugging Playbook**: decoding process states (`R`, `S`, `D`, `Z`, `I`), distinguishing `VSS`/`RSS`/`PSS`/`USS`, understanding the three watermarks of `kswapd`, tuning `swappiness` and NUMA `zone_reclaim_mode`, and catching native heap or `mmap` leaks with `pmap` and eBPF `memleak`.

### 1. Process Lifecycle and Decoding `ps` / `top` States

In the Linux kernel, processes and threads are represented by the exact same C structure: **`struct task_struct`**. Calling `fork()` invokes `clone(SIGCHLD, 0)` to create a new process with a Copy-on-Write (CoW) duplicate of the parent's page tables (`mm_struct`), whereas `pthread_create()` invokes `clone(CLONE_VM | CLONE_FILES | CLONE_FS | CLONE_SIGHAND | CLONE_THREAD, ...)` so all threads in a Thread Group share the same `TGID` (what user space calls `PID`) and the same virtual address space.

#### 1.1 The Six Process States (`R`, `S`, `D`, `T`, `Z`, `I`)

When inspecting `top` or `ps aux`, the `STAT` column reveals what each `task_struct` is doing in the kernel scheduler:

| `STAT` Code | Kernel Macro | Meaning & Debugging Action |
| :--- | :--- | :--- |
| **`R`** | `TASK_RUNNING` | Executing on a CPU core **or** waiting in a CPU runqueue (`rq`). Counts toward Load Average. |
| **`S`** | `TASK_INTERRUPTIBLE` | Sleeping waiting for an event (`epoll_wait`, socket `read`, `futex`, `nanosleep`). Woken immediately by resource readiness or signals. |
| **`D`** | `TASK_UNINTERRUPTIBLE` | Sleeping inside the kernel waiting for hardware/disk/NFS completion. **Ignores all signals including `SIGKILL` (`kill -9`)** until the kernel operation finishes! Counts toward Load Average. Inspect where it is stuck in the kernel via `cat /proc/<PID>/stack` or `cat /proc/<PID>/wchan`. |
| **`Z`** | `EXIT_ZOMBIE` | Process has terminated (`do_exit()`) and freed all its memory/FDs, **except** its tiny `task_struct` slot in the PID table so its parent can read its exit status via `wait4()`. Zombies consume **zero RAM or CPU**, but if a buggy parent never calls `waitpid()` and ignores `SIGCHLD`, zombies exhaust `kernel.pid_max` (`/proc/sys/kernel/pid_max`), preventing any new process or SSH session from spawning! Fix by fixing/restarting the **parent (`PPID`)**, not `kill -9 <zombie_pid>`. |
| **`T` / `t`** | `TASK_STOPPED` / `TASK_TRACED` | Paused by job-control `SIGSTOP`/`SIGTSTP` (`T`) or halted by a debugger (`gdb`/`strace` via `ptrace`, `t`). Never leave `strace` or `gdb` paused on a production PID! |
| **`I`** | `TASK_IDLE` (Linux 4.14+) | Idle kernel worker thread (`kworker/*`). Internally combines `TASK_UNINTERRUPTIBLE | TASK_NOLOAD` so idle kernel threads can sleep without being woken by fake signals **and without inflating Load Average**. |

### 2. Virtual Memory Architecture and `VSS` / `RSS` / `PSS` / `USS`

Every 64-bit Linux process sees a private canonical virtual address space (`0x0000000000000000` to `0x00007fffffffffff`, 128 TB on 4-level page tables) divided into **Virtual Memory Areas (`struct vm_area_struct`, VMA)**:

```text
High User Virtual Address (0x00007fffffffffff)
  ┌────────────────────────────────────────────┐
  │ Stack (grows downward, 8 MB default ulimit)│
  ├─────────────────────┬──────────────────────┤
  │                     ▼                      │
  │   Memory Mapping Segment (mmap, vDSO,      │
  │   libc.so, thread stacks, malloc >= 128KB) │
  │                     ▲                      │
  ├─────────────────────┴──────────────────────┤
  │ Heap (grows upward via brk/sbrk, < 128KB)  │
  ├────────────────────────────────────────────┤
  │ .bss (uninitialized zero-paged globals)    │
  │ .data (initialized globals)                │
  │ .rodata & .text (read-only code, shared)   │
  └────────────────────────────────────────────┘
Low User Virtual Address (0x0000000000400000)
```

#### 2.1 Demand Paging: Minor vs. Major Page Faults

When a process calls `malloc(100 * 1024 * 1024)` (100 MB) or `mmap()`, the kernel **does not allocate a single physical 4 KB RAM frame**. It merely inserts or extends a `vm_area_struct` range in the process's red-black tree of VMAs.

Only when CPU instructions actually read or write a virtual address does the hardware MMU find the Page Table Entry (PTE) marked non-present and raise a **Page Fault (`#PF`)**:

- **Minor Page Fault (`minflt/s` in `pidstat -r`)**: The page does not require reading from disk. Either the kernel allocates a fresh zeroed RAM frame for an anonymous heap/stack touch, or the page is already sitting in the kernel Page Cache (e.g., `libc.so` or a cached file) and only needs a PTE wired up. Cost: ~1 $\mu$s.
- **Major Page Fault (`majflt/s` in `pidstat -r`)**: The page must be read synchronously from block storage—either faulting in an uncached `mmap()` file segment or swapping an evicted anonymous page back in from Swap space. Cost: milliseconds (puts the thread in `D` state!).

#### 2.2 Why Summing `RSS` in `top` Overcounts Memory: `VSS`, `RSS`, `PSS`, `USS`

If you run 20 worker processes that all link `libstdc++.so` (10 MB) and share a 500 MB `mmap(MAP_SHARED)` cache, summing the `RES` (`RSS`) column in `top` reports $20 \times 510\text{ MB} = 10.2\text{ GB}$, even though physical RAM usage is only ~510 MB!

To measure true process memory consumption, inspect `/proc/<PID>/smaps_rollup` (or use `smem`):

| Metric | Full Name | How Shared Pages Are Counted | Best Used For |
| :--- | :--- | :--- | :--- |
| **`VSS` (`VIRT`)** | Virtual Set Size | Total virtual address ranges mapped (includes unallocated address space!) | Checking address-space exhaustion (`vm.max_map_count`), **never** physical RAM usage. |
| **`RSS` (`RES`)** | Resident Set Size | 100% of every shared page is added to **every** process mapping it. | Quick single-process ceiling check. |
| **`PSS`** | Proportional Set Size | Shared pages are divided evenly among the $N$ processes mapping them ($\text{Private} + \sum \frac{\text{Shared}_i}{N_i}$). | **Accurate system-wide capacity planning**—the sum of `PSS` across all processes equals true physical memory mapped by user space! |
| **`USS`** | Unique Set Size (`Private_Clean + Private_Dirty`) | Counts **only** pages mapped exclusively by this single process (`0%` of shared pages). | **Measuring how much RAM will immediately be freed if you kill this process**, and hunting private heap leaks. |

### 3. Performance Debugging Playbook: `kswapd` Watermarks, Active/Inactive LRUs, and Swap Storms

#### 3.1 How Linux Decides When to Reclaim Memory: The 3 Watermarks

Every NUMA memory zone maintains three free-page watermarks configured by `vm.min_free_kbytes` (inspected via `cat /proc/zoneinfo`):

```text
Free Memory Pages in Zone
  ▲
  │   Normal Allocation: Kernel satisfies page faults immediately from buddy allocator
  ├── pages_high (High Watermark) ──► kswapd0 goes back to sleep!
  │
  │   Background Reclaim Zone: kswapd0 wakes up and reclaims pages asynchronously
  ├── pages_low  (Low Watermark)  ──► Kernel wakes background thread kswapd0
  │
  │   Direct Reclaim + OOM Danger Zone: Allocating threads are stalled synchronously!
  ├── pages_min  (Min Watermark)  ──► Direct Reclaim blocks caller; if fails -> OOM Killer!
  ▼
  0
```

1. **Above `pages_low`**: All memory allocations succeed immediately.
2. **Between `pages_min` and `pages_low` (Background Reclaim)**: Free memory has dipped below `pages_low`. The kernel wakes the background kernel thread **`kswapd0`**, which scans the zone's LRU lists asynchronously until free memory climbs back above **`pages_high`**.
3. **At or Below `pages_min` (Direct Reclaim Stall)**: Memory is critically low. Any application thread requesting a page fault or kernel buffer is **blocked synchronously inside the kernel (`try_to_free_pages`)** to reclaim pages itself before its allocation can proceed!
   - *Symptom*: Sudden multi-hundred-millisecond P99 latency spikes across all threads, accompanied by `kswapd0` burning CPU and `sar -B 1` showing spikes in `pgscand/s` (pages scanned synchronously in Direct Reclaim) alongside `pgscank/s` (pages scanned by `kswapd`).

#### 3.2 Asymmetric LRU Entry: Anonymous Pages vs. File Pages

In Chapter 03 we saw that newly faulted **File Cache pages** enter the **`Inactive(file)`** list first so one-shot file scans don't evict hot working sets.

What about **Anonymous Memory** (heap `malloc`, stack, `mmap(MAP_ANONYMOUS)`)?

- Because swapping anonymous memory out to disk (`SwapOut`) and faulting it back in (`SwapIn`) is orders of magnitude more disruptive to application latency than dropping a clean file page, **newly allocated anonymous pages have historically started on the `Active(anon)` list\*\* (kernels since 5.9 add them to `Inactive(anon)` and use workingset refault detection to promote them, so check `/proc/meminfo` on your kernel)
- They are only demoted to `Inactive(anon)` and swapped out when memory pressure is sustained and `vm.swappiness` permits anonymous scanning.

#### 3.3 Tuning `vm.swappiness` and the NUMA `zone_reclaim_mode` Trap

- **`vm.swappiness` (`0` to `100`, up to `200` on modern kernels; default `60`)**:
  Controls the relative weight between reclaiming **File Cache pages** vs. swapping out **Anonymous pages**.
  - Notice that **`vm.swappiness = 0` does NOT disable Swap!** It simply instructs the kernel not to swap out anonymous memory as long as plenty of file-backed Page Cache pages are available; if free + file pages drop near `pages_high` / `pages_min`, the kernel will still swap. For latency-sensitive databases or JVM/Go heaps where swap pauses are fatal, either disable swap (`swapoff -a`) or set `vm.swappiness = 1`.
- **The Multi-Socket NUMA Trap (`vm.zone_reclaim_mode`)**:
  On a 2-socket NUMA server (Node 0 and Node 1, each with 64 GB RAM), suppose a process pinned to Node 0 fills up Node 0's 64 GB while Node 1 still has 40 GB completely free.
  - If `vm.zone_reclaim_mode = 1` is enabled, the kernel **refuses to allocate idle memory from remote Node 1** and instead forces aggressive synchronous Direct Reclaim and Swap on Node 0—causing catastrophic stalls while 40 GB of server RAM sits idle!
  - **Production Rule**: Always verify `sysctl vm.zone_reclaim_mode` is set to **`0`** (so the kernel happily spills allocations to remote NUMA nodes before reclaiming/swapping local pages) and check per-node memory balance with `numactl --hardware` and `numastat -m`.

#### 3.4 Diagnosing Active Swap Thrashing (`vmstat 1` + `sar -B 1` + `/proc/PID/smaps`)

Seeing `Swap: used 2.0 GiB` in `free -h` is **not** an active incident if those 2 GB were swapped out two weeks ago and are never touched. Active swap thrashing is proven by **non-zero swap-in (`si`) and swap-out (`so`) rates in `vmstat 1`**:

```text
$ vmstat 1
procs -----------memory---------- ---swap-- -----io---- -system-- ------cpu-----
 r  b   swpd   free   buff  cache   si   so    bi    bo   in   cs us sy id wa st
 2  4 2097152 118420  12400 184200 8420 9120  8500  9200 4120 8900 12 18 15 55  0
```

To find which processes currently own swapped-out memory and which are faulting it in:

```bash
# 1. Rank processes by current Swap usage (VmSwap in /proc/<PID>/status)
$ for file in /proc/[0-9]*/status; do
    awk '/VmSwap|Name|^Pid/{printf $2 " " $3} END { print "" }' "$file"
  done | sort -k 3 -n -r | head -n 10

# 2. Watch live major page faults (majflt/s = disk/swap reads) per process
$ pidstat -r 1
```

### 4. Hunting Native Memory Leaks and OOM Kills

#### 4.1 Decoding an OOM Kill and `oom_score_adj`

When Direct Reclaim fails to keep free memory above `pages_min`, the kernel invokes `out_of_memory()`, calculates an OOM badness score (`0` to `1000`, proportional to the process's `RSS + Swap + PageTables`), adds `/proc/<PID>/oom_score_adj` (`-1000` to `+1000`), and sends `SIGKILL` to the highest-scoring process:

```bash
# Inspect past OOM kills in the kernel ring buffer (shows full RSS/Swap table at time of death!)
dmesg -T | grep -E -i 'Out of memory|Killed process|oom-kill'

# Protect a critical infrastructure daemon from the OOM killer (-1000 disables OOM kill)
echo -1000 | sudo tee /proc/<PID>/oom_score_adj
```

#### 4.2 Hunting Native (`malloc` / `mmap`) Leaks with `pmap` and eBPF `memleak`

When a C/C++/Rust/CGO service's `USS` (`Private_Dirty`) climbs steadily until OOM:

1. **Inspect Address Space Segments (`pmap -x <PID>`)**:
   Look for either a single gigantic `[ anon ]` heap segment growing via `brk()`, or thousands of 64 MB `[ anon ]` segments (glibc `MALLOC_ARENA_MAX` thread arenas or leaked `mmap` regions).
2. **Trace Unfreed Allocations in Production with eBPF `memleak`**:
   BCC's `memleak` attaches uprobes to `malloc`/`calloc`/`realloc`/`free`, tracking call stacks of allocations that remain unfreed after $N$ seconds:

```bash
# Track top 10 unfreed allocation call stacks every 5 seconds for PID 18420
# (-a prints the individual outstanding allocations)
$ sudo memleak-bpfcc -p 18420 -a 5
[08:40:10] Top 10 stacks with outstanding allocations:
    16777216 bytes in 16 allocations from stack
        allocate_session_buffer+0x24 [gateway]
        handle_request+0x118 [gateway]
        worker_loop+0x82 [gateway]
```

### 5. Verification Lab: Measuring `VSS`, `RSS`, `PSS`, `USS`, and Page Faults

The script below maps a 32 MB anonymous region (`mmap.MAP_ANONYMOUS | mmap.MAP_PRIVATE`), proves that **Demand Paging** allocates `0 KB` of physical `RSS`/`USS` until pages are written, touches half the pages (`16 MB`), and reads the exact kernel `minflt` (minor page faults) and `/proc/self/smaps_rollup` metrics (`Rss`, `Pss`, `Private_Dirty`).

```python
#!/usr/bin/env python3
"""
Verify Linux Demand Paging, Minor Page Faults, and /proc/self/smaps_rollup
(RSS, PSS, and USS = Private_Clean + Private_Dirty).
"""
import mmap
import resource


def read_smaps_rollup() -> dict[str, int]:
    """Read Rss, Pss, Private_Clean, Private_Dirty (in KB) from /proc/self/smaps_rollup."""
    metrics: dict[str, int] = {}
    with open("/proc/self/smaps_rollup", "r", encoding="utf-8") as f:
        for line in f:
            parts = line.split()
            if len(parts) >= 2 and parts[0].rstrip(":") in (
                "Rss",
                "Pss",
                "Private_Clean",
                "Private_Dirty",
            ):
                metrics[parts[0].rstrip(":")] = int(parts[1])
    return metrics


def main() -> None:
    size_mb = 32
    size_bytes = size_mb * 1024 * 1024

    before = read_smaps_rollup()
    flt_before = resource.getrusage(resource.RUSAGE_SELF).ru_minflt

    # 1. Allocate 32 MB virtual address range via mmap (Demand Paging: 0 physical frames!)
    buf = mmap.mmap(-1, size_bytes, mmap.MAP_PRIVATE | mmap.MAP_ANONYMOUS)
    after_mmap = read_smaps_rollup()

    print(f"[1] After 32 MB virtual mmap() (untouched):")
    print(f"    Private_Dirty delta : {after_mmap['Private_Dirty'] - before['Private_Dirty']:+d} KB")

    # 2. Touch 16 MB (4,096 pages of 4 KB each) by writing 1 byte per 4 KB page
    touched_pages = (size_bytes // 2) // 4096
    for i in range(touched_pages):
        buf[i * 4096] = 0x42

    after_touch = read_smaps_rollup()
    flt_after = resource.getrusage(resource.RUSAGE_SELF).ru_minflt

    uss_delta_kb = (
        (after_touch["Private_Clean"] + after_touch["Private_Dirty"])
        - (after_mmap["Private_Clean"] + after_mmap["Private_Dirty"])
    )
    print(f"[2] After writing 1 byte into {touched_pages} pages (16,384 KB):")
    print(f"    Minor Page Faults   : +{flt_after - flt_before} faults")
    print(f"    USS delta           : +{uss_delta_kb} KB")
    print(f"    PSS total           : {after_touch['Pss']} KB, RSS total: {after_touch['Rss']} KB")

    buf.close()


if __name__ == "__main__":
    main()
```

#### Summary of Memory Diagnostic Commands

| Symptom | Primary Tool | What to Inspect |
| :--- | :--- | :--- |
| How much memory is truly available? | `free -h`, `/proc/meminfo` | Check **`MemAvailable`** (not `MemFree`); inspect `Shmem` if `Cached` cannot be reclaimed |
| Latency spikes from memory pressure | `sar -B 1`, `vmstat 1` | Check `pgscand/s` (Direct Reclaim stalls), `pgscank/s` (`kswapd` background scan), and `si`/`so` (active Swap I/O) |
| True per-process RAM usage | `/proc/<PID>/smaps_rollup`, `pidstat -r 1` | Compare `Pss` (proportional shared) and `Private_Dirty` (`USS`) across processes |
| Growing native heap / `mmap` leak | `pmap -x <PID>`, `memleak-bpfcc -p <PID> -a` | Pinpoint the exact `[ anon ]` VMA and unfreed allocation call stack |
