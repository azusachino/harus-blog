## Before you start

When a program writes to a file, the call usually returns in microseconds, far faster than any disk. The kernel has only copied your data into spare RAM and promised to write it out later. This is the page cache. It is why a second read of the same file is nearly free, and also why a power cut can lose data you thought was saved. The cost shows up when the kernel has to flush a lot of buffered data at once: your program suddenly stalls for seconds while the disk catches up. Run `free -h` and look at the `buff/cache` column to see how much RAM is currently being used this way.

Chapter 2 covers file descriptors, which every read and write here goes through: [File Descriptors, Short-Lived Processes & CPU Profiling](/tech/series/linux-systems/02.universal-file-io/).

Terms used in this chapter:

- **page cache**: memory the kernel uses to hold recently read or written file data.
- **dirty page**: a cached page that has been changed in memory but not yet written to disk.
- **writeback**: the kernel's process of flushing dirty pages to storage.
- **`fsync()`**: a call that blocks until a file's dirty data has reached the storage device.
- **`O_DIRECT`**: an open flag that bypasses the page cache and sends I/O straight to the device, with alignment rules.
- **LRU**: least recently used; the ordering the kernel uses to decide which cached pages to drop first.
- **iowait (`%iowait`)**: the share of time CPUs sat idle while there was outstanding disk I/O.
- **block layer**: the kernel component that queues and merges I/O requests for storage devices.

## Linux Systems & Performance 03: Page Cache, Dirty Writeback, Direct I/O & Storage Latency Debugging

When an application calls `write(fd, buf, 4096)` and receives `4096` back in 3 microseconds, no data has touched the SSD. By default, Linux treats main memory as a write-back cache for block storage (**the Page Cache**). That design turns slow random disk operations into memory-speed copies and lets the block layer coalesce sequential writes—until a background writeback threshold is crossed or a database buffer pool fights the kernel's LRU lists, causing sudden multi-second latency spikes and `100%` `%iowait`.

This chapter connects the full Linux storage path—from `stdio` user buffers and the kernel's two-list Page Cache LRU down to the Block Layer and NVMe device queues—with a step-by-step **Storage I/O Debugging Playbook**.

### 1. The Double-Caching Path and the Kernel Page Cache

A standard C `fwrite()` traverses two separate caches before reaching a block device:

```text
User Space (Ring 3)
  Application Buffer ──fwrite()──► libc FILE* Buffer (8 KB)
                                          │
══════════════════════════════ fflush() / write() ══════════════════════════════
Kernel Space (Ring 0)                     ▼
  VFS (vfs_write) ───────────────► Page Cache (4 KB pages in struct address_space)
                                   │  • Marks page PG_dirty
                                   │  • Returns immediately unless O_SYNC / dirty_ratio hit
                                   │
                    fsync() OR kworker/flush dirty writeback
                                   ▼
  Block Layer (bio -> request_queue -> I/O Scheduler: mq-deadline / kyber / bfq / none)
                                   │
                                   ▼
  Device Driver & DMA Ring ──────► Physical NVMe / SSD Controller
```

#### 1.1 `Buffers` vs. `Cached` in `free` and `/proc/meminfo`

When you run `free -h` or `vmstat 1`, Linux reports two distinct memory columns (`buff` and `cache`). Their exact definitions come from `/proc/meminfo`:

- **`Buffers`**: Raw block-device pages (`bdev` page cache) plus filesystem metadata blocks buffered via the block layer (superblocks, block group descriptors, ext4 journal/inode tables).
- **`Cached`**: The **Page Cache** for regular files (`struct inode -> i_mapping`), plus **tmpfs / `shmem` / anonymous shared memory (`MMAP_SHARED`)** pages!
  - *Critical debugging trap*: Because `Cached` in `/proc/meminfo` includes `Shmem` (tmpfs mounts like `/dev/shm` and `/run`, plus SysV/POSIX shared memory), a memory leak inside a `/dev/shm` file or shared-memory segment inflates `Cached` **and cannot be reclaimed by dropping caches (`echo 3 > /proc/sys/vm/drop_caches`)**. Always inspect `Shmem:` in `/proc/meminfo` when `Cached` refuses to shrink!

#### 1.2 The Two-List Page Cache LRU (`Active(file)` vs. `Inactive(file)`)

Suppose a background `tar` backup or analytics query sequentially reads a 100 GB log file on a machine with 32 GB of RAM. If Linux used a naive Least-Recently-Used (LRU) list, that single scan would evict every hot database index page in memory (**cache pollution**).

To prevent one-shot scans from flushing hot working sets, the Linux kernel maintains **two separate LRU lists** for file-backed pages (and another pair for anonymous memory, covered in Chapter 05):

```text
                       mark_page_accessed() (2nd touch)
               ┌──────────────────────────────────────────────┐
               │                                              ▼
New Page ──► [ Inactive(file) LRU ]                      [ Active(file) LRU ]
Faulted In     (Probationary list)                         (Protected hot list)
               │                                              │
               ▼ Reclaimed first by kswapd                    │ Demoted when Active
               Evicted / Freed  ◄─────────────────────────────┘ grows too large
```

1. **First Access**: When a file page is read from disk for the first time, it enters the head of the **`Inactive(file)`** list (`PG_referenced = 0`).
2. **Second Access (Promotion)**: Only if the page is referenced again while still on `Inactive(file)` (`mark_page_accessed()`) does it get promoted to **`Active(file)`**. A one-time sequential scan (`tar`, `grep`, `mysqldump`) touches each 4 KB page once, cycling purely through `Inactive(file)` without evicting your hot `Active(file)` working set.
3. **Explicit Kernel Hints (`posix_fadvise`)**: A polite backup tool or streaming reader doesn't even leave its pages on `Inactive(file)`: it calls `posix_fadvise(fd, offset, len, POSIX_FADV_DONTNEED)` after reading each chunk, immediately freeing the clean Page Cache frames.

### 2. Dirty-Page Writeback, `fsync()`, and `O_DIRECT`

When you modify a file through buffered `write()` or `mmap()`, the kernel marks the 4 KB page frame `PG_dirty` in the Page Cache and returns to user space in microseconds.

#### 2.1 Background vs. Foreground Dirty Writeback Stalls

Why does a server doing steady buffered writes suddenly freeze for 3 seconds every minute? Because of the transition from **asynchronous background writeback** to **synchronous foreground throttling**:

| Kernel Parameter (`/proc/sys/vm/...`) | Default | Behavior When Crossed |
| :--- | :--- | :--- |
| `dirty_background_ratio` (or `_bytes`) | `10%` of available memory | Kernel wakes `kworker/u*:*-flush-*` threads to flush dirty pages to disk **asynchronously in the background**. Application `write()` calls remain fast. |
| `dirty_ratio` (or `_bytes`) | `20%` of available memory | **Hard synchronous throttle!** If disk write speed cannot keep up with incoming writes and dirty pages hit `20%`, the kernel blocks the **application threads calling `write()`** directly inside `balance_dirty_pages()`, forcing them to flush dirty pages synchronously. Latency jumps from $5\ \mu\text{s}$ to hundreds of milliseconds. |
| `dirty_expire_centisecs` | `3000` (30 sec) | Any page that has stayed dirty for $> 30\text{s}$ is eligible for flushing on the next `dirty_writeback_centisecs` (5 sec) wakeup. |

> **Production Tip**: On servers with 256 GB of RAM, `10%` (`dirty_background_ratio`) equals **25.6 GB** of buffered dirty data! When `kworker` finally wakes up—or when a checkpoint runs—flushing 25 GB at once saturates the NVMe queue for several seconds. On large-memory hosts, replace percentage ratios with explicit byte caps (`vm.dirty_background_bytes = 268435456` [256 MB] and `vm.dirty_bytes = 1073741824` [1 GB]) so writeback flows smoothly.

#### 2.2 Durability Contracts (`fsync` vs. `fdatasync`) and `O_DIRECT`

- **`fsync(fd)`**: Flushes all dirty file data pages **and** dirty inode metadata (mtime, file size, block bitmaps) to persistent media (`REQ_PREFLUSH | REQ_FUA`), issuing at least two disk writes when metadata changed.
- **`fdatasync(fd)`**: Flushes dirty file data pages and **only the metadata required to read that data back** (e.g., skips flushing `mtime` if the file size `i_size` did not change). Database write-ahead logs (WALs) pre-allocate fixed-size log files specifically so `fdatasync()` requires only **one** disk flush instead of two.
- **Directory Durability**: Creating or renaming a file (`rename("cfg.tmp", "cfg.json")`) updates the **parent directory's** data blocks. To guarantee the rename survives a power loss, you must `fsync(file_fd)`, `close(file_fd)`, and then **`fsync(dir_fd)`** on the parent directory!
- **`O_DIRECT` (Direct I/O)**: Bypasses the kernel Page Cache completely, transferring DMA buffers directly between user-space memory and the block device.
  - *When to use*: Self-caching database engines (PostgreSQL, MySQL InnoDB, RocksDB) that manage their own buffer pool and want to avoid double-caching and kernel writeback storms.
  - *Alignment rule*: The memory buffer address, file offset, and transfer length must all be integer multiples of the underlying logical block size (typically 512 or 4,096 bytes), or the syscall fails immediately with `EINVAL`.
  - *Never run `drop_caches` on a mixed DB host*: Even if InnoDB uses `O_DIRECT` for tablespaces, binlogs, sort temp files, or sibling services rely on the Page Cache; moreover, `echo 3 > /proc/sys/vm/drop_caches` walks and evicts dentry/inode slabs under kernel locks, causing sudden I/O storms as hot metadata and index pages are faulted back in from disk.

### 3. Performance Debugging Playbook: Diagnosing Storage I/O Bottlenecks

When `top` or `mpstat` shows elevated `%iowait` (or user requests time out on disk operations), follow a structured four-layer cascade: **System $\rightarrow$ Block Device (`iostat`) $\rightarrow$ Process (`pidstat -d` / `iotop`) $\rightarrow$ Page Cache & Syscall (`cachestat` / `biosnoop` / `strace`)**.

#### 3.1 Layer 1: Decoding `iostat -d -x 1` Metrics

Run `iostat -d -x 1` (from the `sysstat` package). Every column maps directly to `/proc/diskstats`:

```text
$ iostat -d -x 1
Device            r/s     rkB/s   rrqm/s  %rrqm r_await rareq-sz     w/s     wkB/s   wrqm/s  %wrqm w_await wareq-sz  aqu-sz  %util
nvme0n1         120.0     480.0     0.0    0.0    0.42     4.00  3450.0   13800.0     0.0    0.0   18.60     4.00   64.22  99.80
```

| `iostat -d -x` Metric | Meaning | How to Interpret in Production |
| :--- | :--- | :--- |
| `r/s` + `w/s` | Completed read/write IOPS (after merging) | Compare against device spec (e.g., ~3,000 IOPS for gp3 EBS, ~150 IOPS for HDD, ~500k IOPS for local NVMe). |
| `rkB/s` + `wkB/s` | Read/Write throughput (KB/s) | Compare against device bandwidth limit (e.g., 125 MB/s or 1,000 MB/s). |
| `r_await` / `w_await` | Average latency (ms) from block-layer submission to completion (queue wait + hardware service time) | SSD/NVMe should be $< 1\text{--}2\text{ ms}$. Above $10\text{ ms}$ on SSD indicates queue saturation or throttling. |
| `rareq-sz` / `wareq-sz` | Average request size in KB | $\sim 4\text{ KB}$ means **random I/O** (IOPS-bound); $\ge 128\text{ KB}$ means **sequential I/O** (bandwidth-bound). |
| `aqu-sz` (`avgqu-sz`) | Average number of I/O requests queued in flight | On modern multi-queue NVMe (`blk-mq`), `aqu-sz > 32` alongside rising `await` proves queue saturation. |
| `%util` | Percentage of elapsed time the device had **at least one** active I/O request in flight | **Warning**: `%util = 100%` saturates a single-queue spinning HDD, but a parallel 32-queue NVMe SSD can reach `%util = 100%` at just 1 queue depth while still having 10x IOPS headroom! Always judge NVMe saturation by **`aqu-sz` + rising `r_await`/`w_await`**, not `%util` alone. |

#### 3.2 Layer 2: Finding Which Process Is Generating the Disk I/O

Once `iostat` confirms `nvme0n1` is saturated (`w_await = 18.6 ms`, `aqu-sz = 64`), identify the offending PID:

```bash
# Show per-process block I/O rates and I/O delay every second
$ pidstat -d 1
08:30:01      UID       PID   kB_rd/s   kB_wr/s kB_ccwr/s iodelay  Command
08:30:02        0       412      0.00  13780.00      0.00      42  jbd2/nvme0n1p1-
08:30:02     1000     22190      0.00  13760.00      0.00     185  order-service
```

#### 3.3 Layer 3: The Classic Trap—Why Does `pidstat -d` Only Show `jbd2` or `kworker`?

Frequently during an `%iowait` incident, `pidstat -d 1` or `iotop` shows **only kernel threads** (`kworker/u16:2-flush-259:0` or `jbd2/sda1-8`) writing 200 MB/s to disk, while every application process shows `0.00 kB_wr/s`!

Why?

1. **Buffered Write Decoupling**: If an application writes into the Page Cache without calling `fsync()`, or writes via `mmap(MAP_SHARED)`, the actual block-layer bio submission happens later inside `kworker` writeback threads or the `jbd2` ext4 journaling thread.
2. **The converse trap (an application that really does hit the disk)**: watch out for small unbuffered writes (`write(fd, buf, 64)` followed by `fsync()` on every log line), which forces `jbd2` to commit metadata transactions thousands of times per second.

To see **every VFS-level file read/write** (even when buffered in the Page Cache) alongside **Page Cache hit rates** and **actual block-device I/O**:

```bash
# 1. Check system-wide Page Cache hit ratio per second (BCC)
$ cachestat 1
    HITS   MISSES  DIRTIES HITRATIO   BUFFERS_MB  CACHED_MB
   48210     4120    19400   92.13%          142       4812

# 2. Check per-process Page Cache hits/misses and dirty pages (BCC)
$ cachetop 5

# 3. Trace top files being read/written at the VFS layer (catches buffered writers!)
$ filetop -C 1

# 4. Trace every physical block I/O request with PID, latency (ms), and sector
$ biosnoop-bpfcc
TIME(s)     COMM           PID    DISK    T SECTOR     BYTES   LAT(ms)
0.000000    order-service  22190  nvme0n1 W 18941200   4096      18.42
```

### 4. Verification Lab: Inspecting Page Cache residency (`mincore` / `posix_fadvise`)

Linux 2.6+ and Python 3.3+ expose `os.posix_fadvise()` directly in the standard library. The script below writes a 16 MB file, measures its buffered read throughput from the Page Cache, evicts its pages deterministically using `POSIX_FADV_DONTNEED`, and verifies the change in `/proc/meminfo` `Cached` memory.

```python
#!/usr/bin/env python3
"""
Demonstrate Linux Page Cache residency control using os.fsync() and
os.posix_fadvise(POSIX_FADV_DONTNEED), verifying /proc/meminfo Cached delta.
"""
import os
import tempfile
import time


def read_meminfo_cached_kb() -> int:
    with open("/proc/meminfo", "r", encoding="utf-8") as f:
        for line in f:
            if line.startswith("Cached:"):
                return int(line.split()[1])
    return 0


def timed_sequential_read(fd: int, size: int) -> float:
    os.lseek(fd, 0, os.SEEK_SET)
    t0 = time.perf_counter()
    remaining = size
    while remaining > 0:
        chunk = os.read(fd, min(262144, remaining))
        if not chunk:
            break
        remaining -= len(chunk)
    return (time.perf_counter() - t0) * 1000.0


def main() -> None:
    size_bytes = 16 * 1024 * 1024  # 16 MB
    payload = b"A" * (1024 * 1024)

    with tempfile.NamedTemporaryFile(delete=False) as tmp:
        path = tmp.name

    try:
        fd = os.open(path, os.O_RDWR | os.O_CREAT | os.O_TRUNC | os.O_CLOEXEC, 0o600)
        for _ in range(16):
            os.write(fd, payload)
        # Flush dirty pages so POSIX_FADV_DONTNEED can immediately evict clean frames
        os.fsync(fd)

        cached_with_file = read_meminfo_cached_kb()
        warm_ms = timed_sequential_read(fd, size_bytes)

        # Instruct kernel to immediately drop this file's clean Page Cache pages
        if hasattr(os, "POSIX_FADV_DONTNEED"):
            os.posix_fadvise(fd, 0, size_bytes, os.POSIX_FADV_DONTNEED)

        cached_after_evict = read_meminfo_cached_kb()
        print(f"16 MB Warm Page Cache Read : {warm_ms:6.2f} ms")
        print(f"Page Cache delta after POSIX_FADV_DONTNEED: {cached_after_evict - cached_with_file:+d} KB")

        os.close(fd)
    finally:
        os.unlink(path)


if __name__ == "__main__":
    main()
```

#### Summary of Storage I/O Diagnostic Commands

| Symptom | Primary Tool | What to Inspect |
| :--- | :--- | :--- |
| High `%iowait` | `iostat -d -x 1` | Check `r_await`/`w_await` (ms), `aqu-sz` (queue depth), `rareq-sz`/`wareq-sz` (4 KB random vs 128 KB+ sequential), and IOPS (`r/s + w/s`) |
| Which PID is hitting disk? | `pidstat -d 1`, `iotop -o`, `biosnoop-bpfcc` | Inspect `kB_rd/s`, `kB_wr/s`, and `iodelay` |
| Only `kworker` or `jbd2` shows in `iotop` | `filetop -C 1`, `cachetop` | Catch processes doing buffered Page Cache writes or frequent metadata updates |
| Suspected Page Cache thrashing / low hit rate | `cachestat 1`, `/proc/meminfo` (`Active(file)` vs `Inactive(file)`) | Check if `HITRATIO` drops below 80% or if `Inactive(file)` is constantly churned by sequential scans |
