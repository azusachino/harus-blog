## Before you start

When your program opens a file, a socket or a pipe, Linux hands back a small integer such as `3`. Every later `read(3, ...)` or `close(3)` uses that number. It is like a cloakroom ticket: the number means nothing alone, but the kernel knows what it stands for. Two problems follow. A program that forgets to close tickets eventually runs out and fails with "Too many open files". And when a machine is busy at 100% CPU but `top` shows no single guilty process, the cause is often thousands of tiny processes that start and exit before `top` samples them. Try `ls -l /proc/self/fd` to see the descriptors your own shell holds.

Read [chapter 1](/tech/series/linux-systems/01.syscalls-and-abi/) first for what a system call is and what `pidstat` reports.

Terms used in this chapter:

- **file descriptor (FD)**: a non-negative integer a process uses to refer to an open file, socket, pipe or similar object.
- **`fork()` / `execve()`**: `fork` copies the current process; `execve` replaces the running program with another one.
- **`dup2()`**: makes one descriptor number point at the same open file as another, as in shell redirection.
- **`EMFILE`**: the error returned when a process has hit its limit of open descriptors.
- **`O_CLOEXEC`**: an open flag that closes the descriptor automatically when the process calls `execve`.
- **CPU saturation**: more work is runnable than the CPUs can run, so threads queue, even if utilization looks modest.
- **perf**: a Linux profiler that samples which functions the CPU is executing.

## Linux Systems & Performance 02: File Descriptors, Short-Lived Processes & CPU Profiling

"Everything is a file" in Linux does not mean everything is stored on a disk. It means sockets, pipes, epoll instances, timers (`timerfd`), signals (`signalfd`), and regular files all expose a uniform system-call contract—`read()`, `write()`, `poll()`, and `close()`—referenced through a non-negative integer called a **File Descriptor (FD)**.

Behind that small integer lies a three-tier kernel data structure that governs how parent and child processes share or isolate I/O state across `dup2()`, `fork()`, and `execve()`. And when things go wrong in production—whether file descriptors leak until `EMFILE` crashes an API gateway, or a tight loop of `fork()` + `execve()` drives CPU utilization and Load Average through the roof while `top` shows every process at `< 1%` CPU—you need both the structural model and the right profiling tools (`perf`, `pidstat`, `execsnoop`) to find the culprit.

### 1. The Three-Tier Open File Architecture

A common mistake is thinking a file descriptor points directly to a file on disk. In the Linux kernel, every open resource traverses three distinct tables:

```text
Process A (files_struct)      Kernel Open File Table       VFS Inode Table
┌──────────────────────┐      (struct file)                (struct inode)
│ FD 0 ────────────────┼───► ┌──────────────────────┐
│ FD 1 ───────────┐    │     │ f_pos = 4096         │     ┌──────────────────┐
│ FD 2            └────┼───► │ f_flags = O_RDWR     ├───► │ i_ino = 918273   │
│ FD 3 (FD_CLOEXEC) ───┼──┐  │ f_count = 3          │     │ i_size = 65536   │
└──────────────────────┘  │  └──────────────────────┘     │ i_mapping (pages)│
                          │              ▲                └──────────────────┘
Process B (after fork)    │              │                         ▲
┌──────────────────────┐  │  ┌───────────┴──────────┐              │
│ FD 1 ────────────────┼──┼─►│ (Shared struct file) │              │
│ FD 4 (indep. open) ──┼──┼──┼──────────────────────┼──► ┌─────────┴────────┐
└──────────────────────┘  │  └──────────────────────┘    │ f_pos = 0        │
                          └─────────────────────────────►│ f_flags = O_RDONLY│
                                                         └──────────────────┘
```

1. **Per-Process File Descriptor Table (`files_struct -> fdtable`)**:
   - Scoped to a process (or shared across threads created with `CLONE_FILES`).
   - Maps a small integer `fd` (`0`, `1`, `2`, ...) to two items:
     - **FD Flags**: Notably `FD_CLOEXEC` (close-on-exec), which belongs to this specific integer slot, *not* the underlying open file.
     - **A pointer** to a kernel-wide `struct file`.
2. **System-Wide Open File Description Table (`struct file`)**:
   - Allocated in kernel slab memory on every `open()`, `socket()`, or `pipe()` call.
   - Holds the **current file offset (`f_pos`)**, **open status flags (`f_flags`: `O_NONBLOCK`, `O_APPEND`)**, access mode (`O_RDONLY`, `O_RDWR`), and a reference count (`f_count`).
3. **VFS Inode Table (`struct inode`)**:
   - Represents the underlying filesystem object or pseudo-filesystem resource (owner UID, permissions, size, data block pointers, and the Page Cache `address_space`).

#### 1.1 Why the Middle Tier (`struct file`) Matters in Production

Distinguishing Tier 1 (`fd`) from Tier 2 (`struct file`) explains three classic concurrency bugs:

- **Scenario A: `dup()`, `dup2()`, or `fork()` shares `struct file`**:
  When a parent process opens a log file and calls `fork()`, or redirects stdout to stderr via `dup2(1, 2)`, both descriptors point to the **exact same `struct file`**.
  - *Consequence 1*: If the child calls `lseek()`, the parent's `f_pos` moves too.
  - *Consequence 2*: If the child toggles non-blocking mode via `fcntl(fd, F_SETFL, flags | O_NONBLOCK)` on a shared descriptor (like standard output or an inherited socket), it silently mutates `f_flags` for the parent process as well!
- **Scenario B: Independent `open()` calls create separate `struct file` instances**:
  If two processes independently call `open("/var/log/app.log", O_WRONLY)` without `O_APPEND`, each gets its own `f_pos = 0`. When both write concurrently, the slower writer overwrites the faster writer's bytes.
- **Scenario C: Closing an FD vs. Closing the File**:
  `close(fd)` only removes the entry from Tier 1 and decrements `struct file.f_count`. The kernel releases locks, flushes TCP `FIN` packets, and frees the `struct file` **only when `f_count` drops to zero**. If a background subprocess (e.g., a shell command spawned without `O_CLOEXEC`) inherits your listening socket or database lock FD, restarting your main server fails with `EADDRINUSE` because the child still holds `f_count > 0`.

#### 1.2 Atomic I/O Primitives: `O_CLOEXEC`, `O_APPEND`, and `pread`/`pwrite`

Never write a two-step sequence when the kernel offers an atomic primitive:

| Non-Atomic Anti-Pattern | Race Condition Window | Atomic Kernel Replacement |
| :--- | :--- | :--- |
| `fd = open(...); fcntl(fd, F_SETFD, FD_CLOEXEC);` | Another thread calls `fork() + execve()` between the two lines, leaking `fd` into the child process forever. | Pass `O_CLOEXEC` directly to `open()`, `socket(SOCK_CLOEXEC)`, `accept4(..., SOCK_CLOEXEC)`, `epoll_create1(EPOLL_CLOEXEC)`, and `dup3()`. |
| `lseek(fd, offset, SEEK_SET); read(fd, buf, n);` | Another thread sharing the FD calls `lseek()` in between, reading corrupt offsets and contending on the kernel `f_pos` mutex. | Use **`pread(fd, buf, n, offset)`** and **`pwrite(fd, buf, n, offset)`**, which read/write at `offset` without touching or locking `f_pos`. |
| `lseek(fd, 0, SEEK_END); write(fd, buf, n);` | Concurrent writers compute the same end-of-file offset and overwrite each other's log lines. | Open with **`O_APPEND`**, where the kernel VFS atomically sets `f_pos = i_size` under the inode lock immediately before copying bytes. |

### 2. Performance Debugging Playbook: CPU Utilization vs. CPU Saturation

While Load Average measures queue depth (`R` + `D` states), **CPU Utilization** measures the fraction of wall-clock time the CPU was non-idle during a sampling interval:

$$\text{CPU Utilization} = 1 - \frac{\Delta \text{idle}}{\Delta \text{total\_cpu\_time}}$$

The kernel exposes raw tick counters (in `USER_HZ`, typically $100\text{ Hz} = 10\text{ ms/tick}$) in `/proc/stat`:

```text
$ head -n 2 /proc/stat
cpu  2481920 4120 891042 48192011 98210 14210 89412 0 0 0
cpu0  310240  515 111380  6024010 12276  1776 11176 0 0 0
```

Each line tracks 10 cumulative counters (`mpstat -P ALL 1` converts their deltas into percentages):

| Metric (`mpstat` / `top`) | `/proc/stat` Field | Meaning & Primary Bottleneck |
| :--- | :--- | :--- |
| `%usr` (`us`) | `user` | Unprivileged user-space execution (application business logic, JSON parsing, crypto, GC, spin-loops). |
| `%nice` (`ni`) | `nice` | User-space execution of low-priority processes (`nice > 0`). |
| `%sys` (`sy`) | `system` | Privileged Ring 0 execution (system calls, VFS/page-table management, lock contention, context switching). |
| `%iowait` (`wa`) | `iowait` | CPU was completely idle *while at least one task on that CPU had pending disk I/O*. |
| `%irq` (`hi`) | `irq` | Hardware interrupt handlers (Top-Half IRQs). |
| `%soft` (`si`) | `softirq` | Software interrupt handlers (Bottom-Half: network RX/TX NAPI polling, block completion, timers). |
| `%steal` (`st`) | `steal` | Time a virtual CPU was runnable, but the hypervisor scheduled another tenant VM on the physical host. |
| `%guest` / `%gnice` | `guest` | Time spent running a guest virtual CPU for a VM hosted on this machine (`KVM`). |

### 3. Debugging Case Study 1: Pinpointing High `%usr` CPU with `perf`

When `mpstat -P ALL 1` shows `%usr` pinned near `100%` and `top` identifies a specific PID, how do you find the exact function inside a stripped or dynamically linked production service without restarting it?

#### Step 1: Live Symbol Sampling with `perf top`

Never attach `gdb` to a live production service—`ptrace` halts all threads and causes immediate health-check timeouts. Instead, use hardware performance counters via `perf`:

```bash
# Sample CPU cycles at 99 Hz across call graphs for a specific PID
perf top -g -p <PID> -F 99
```

Why `-F 99` (99 Hz) instead of 100 Hz or 1000 Hz? Sampling at 99 Hz avoids **lockstep aliasing** with periodic 100 Hz or 1000 Hz application timers, while keeping observer CPU overhead well under 1%.

#### Step 2: Recording On-CPU Flame Graphs with `perf record`

If the hotspot flickers too quickly in `perf top`, capture a 15-second profile for offline flame-graph inspection:

```bash
# Capture 15 seconds of call-stack samples (-g) at 99 Hz
perf record -F 99 -p <PID> -g -- sleep 15

# Inspect the hierarchical call tree in the terminal
perf report --stdio --no-children
```

- **`--no-children`** is critical when reading `perf report` quickly: by default, `perf` sorts by cumulative "Children" overhead (meaning `main()` and `start_thread()` always appear at `99%` at the top). Passing `--no-children` sorts by **Self** overhead so the leaf function burning CPU cycles jumps straight to line 1.

### 4. Debugging Case Study 2: High CPU / Load with No High-CPU Process in `top`

One of the most baffling production incidents looks like this:

1. `uptime` reports Load Average `12.5` on a 4-core server.
2. `mpstat 1` reports `%usr` at `55%` and `%sys` at `35%` (only `10%` idle).
3. `vmstat 1` shows `r = 10` runnable threads and thousands of context switches (`cs`).
4. Yet when you open `top` or `pidstat -u 1`, **every single listed process shows `< 1.5%` CPU utilization!**

#### 4.1 Why `top` and `pidstat` Miss the Culprit

`top` and `pidstat` work by scanning `/proc/<PID>/stat` at regular intervals (every 1 to 3 seconds) and computing the delta of CPU ticks per PID.

If a parent process (for example, a misconfigured PHP-FPM worker, cron script, health check, or CI agent) is spawning **short-lived child processes** in a tight loop—each running for only 15 milliseconds before exiting—almost every child PID is born and dies *between* `top`'s 3-second snapshots! The parent process itself only calls `fork()` and `wait4()`, consuming `< 1%` CPU, while the transient children consume `90%` of the machine's CPU and hammer the kernel with page-table allocations (`execve`) and file-descriptor setup.

```text
top Snapshot T=0s                                     top Snapshot T=3s
      │                                                     │
      ▼                                                     ▼
Parent (PID 4100): 0.8% CPU                           Parent (PID 4100): 0.8% CPU
      ├── fork+exec Child 8801 (15ms) -> EXIT (missed!)
      ├── fork+exec Child 8802 (15ms) -> EXIT (missed!)
      ├── ... 180 more short-lived processes ...
      └── fork+exec Child 8983 (alive at T=3s: shows 0.2% CPU)
```

#### 4.2 Catching Short-Lived Process Storms in 3 Steps

1. **Confirm Rapid PID Churn**:
   Check `/proc/loadavg`: the 5th field is the most recently allocated PID. If it jumps by hundreds per second, or `vmstat 1` shows high `cs` and `%sys`, short-lived processes are spawning.
2. **Locate the Parent Process Tree with `pstree`**:
   Even if each child lives only 15 ms, running `pstree -aps` a few times catches the transient children attached to their parent (`bash`, `cron`, `docker-containerd-shim`, or an application daemon).
3. **Trace Every `execve()` Event Kernel-Wide with `execsnoop` (or `perf sched`)**:
   Instead of polling `/proc`, hook the `sched_process_exec` tracepoint or `execve` syscall via eBPF (`execsnoop-bpfcc` / `bpftrace`):

```bash
# Trace every new process execution across the system in real time
$ execsnoop-bpfcc
PCOMM            PID    PPID   RET ARGS
sh               28411  4100     0 /bin/sh -c /usr/local/bin/check_stress.sh
grep             28412  28411    0 /bin/grep -E ^ERROR /var/log/huge.log
awk              28413  28411    0 /usr/bin/awk {print $4}
sh               28414  4100     0 /bin/sh -c /usr/local/bin/check_stress.sh
```

Within two seconds, `execsnoop` prints the exact command line (`ARGS`) and the parent PID (`PPID 4100`) responsible for the invisible CPU storm.

### 5. Verification Lab: Proving the 3-Tier Open File Model in Code

The script below demonstrates the behavioral difference between shared `struct file` descriptions (`os.dup`) and independent `os.open` calls, and shows how `pread` reads arbitrary offsets without mutating the shared `f_pos` cursor.

```python
#!/usr/bin/env python3
"""
Verify the Linux 3-tier open file table:
1. dup() shares the kernel open file description (f_pos and f_flags).
2. Independent open() calls have isolated f_pos cursors.
3. os.pread() reads without mutating the shared f_pos cursor.
"""
import fcntl
import os
import tempfile


def inspect_fdinfo(fd: int) -> dict[str, str]:
    """Read kernel-exposed struct file metadata from /proc/self/fdinfo/<fd>."""
    info: dict[str, str] = {}
    with open(f"/proc/self/fdinfo/{fd}", "r", encoding="utf-8") as f:
        for line in f:
            if ":" in line:
                k, v = line.split(":", 1)
                info[k.strip()] = v.strip()
    return info


def main() -> None:
    with tempfile.NamedTemporaryFile(delete=False) as tmp:
        tmp.write(b"0123456789ABCDEF")
        path = tmp.name

    try:
        # Tier 1 + Tier 2: open fd1, duplicate to fd2 (shares struct file)
        fd1 = os.open(path, os.O_RDONLY | os.O_CLOEXEC)
        fd2 = os.dup(fd1)
        # Independent open creates a separate struct file
        fd3 = os.open(path, os.O_RDONLY | os.O_CLOEXEC)

        # Advance fd1 by 6 bytes
        data = os.read(fd1, 6)
        assert data == b"012345"

        print(f"After reading 6 bytes on fd1:")
        print(f"  fd1 (original)   f_pos = {inspect_fdinfo(fd1)['pos']}")
        print(f"  fd2 (dup of fd1) f_pos = {inspect_fdinfo(fd2)['pos']}  <-- shared struct file!")
        print(f"  fd3 (indep open) f_pos = {inspect_fdinfo(fd3)['pos']}  <-- isolated struct file!")

        # Use pread on fd2 at offset 10; verify shared f_pos remains at 6
        chunk = os.pread(fd2, 4, 10)
        assert chunk == b"ABCD"
        print(f"After os.pread(fd2, 4, offset=10) -> {chunk!r}:")
        print(f"  fd1 f_pos is still     = {inspect_fdinfo(fd1)['pos']}")

        # Toggling O_NONBLOCK on fd2 mutates f_flags on fd1 as well
        flags_before = fcntl.fcntl(fd1, fcntl.F_GETFL)
        fcntl.fcntl(fd2, fcntl.F_SETFL, flags_before | os.O_NONBLOCK)
        flags_after = fcntl.fcntl(fd1, fcntl.F_GETFL)
        assert bool(flags_after & os.O_NONBLOCK)
        print("  Toggling O_NONBLOCK on fd2 mutated fd1 f_flags:", bool(flags_after & os.O_NONBLOCK))

        os.close(fd1)
        os.close(fd2)
        os.close(fd3)
    finally:
        os.unlink(path)


if __name__ == "__main__":
    main()
```

#### Summary of CPU & FD Diagnostic Commands

| Symptom | Primary Tool | What to Inspect |
| :--- | :--- | :--- |
| `EMFILE` (Too many open files) | `ls -l /proc/<PID>/fd \| wc -l`, `lsof -p <PID>` | Compare open FDs against `cat /proc/<PID>/limits` (`Max open files`) |
| High `%usr` CPU on a known process | `perf top -g -p <PID> -F 99` | Inspect live user-space function symbols and call chains |
| High `%usr` / `%sys` CPU, no heavy PID in `top` | `execsnoop-bpfcc`, `pstree -aps` | Catch short-lived child processes (`fork` + `execve` loops) and find their `PPID` |
| Child process holds parent port open across restart | `ss -lptn`, `fuser -v 8080/tcp` | Identify inherited FDs where `O_CLOEXEC` was omitted |
