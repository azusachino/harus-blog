When you run `ps auxf` on a Linux Kubernetes node or Docker host, you do not see your application containers parented to `dockerd` or `containerd`. Instead, every Pod or standalone container sits underneath a tiny companion process named **`containerd-shim-runc-v2`**, while `runc` (or `youki`) itself is nowhere to be found in the process tree!

Why did the container ecosystem split a single daemon into **Engine (`dockerd` / `kubelet`) $\to$ `containerd` $\to$ `containerd-shim-runc-v2` $\to$ OCI Runtime (`runc` / `youki`)**, and why does the OCI runtime exit immediately after starting your container?

This chapter traces the container execution path from the Kubernetes **Container Runtime Interface (CRI)** down to the `exec.fifo` synchronization pipe inside `runc` and the Rust-based OCI runtime **`youki`**.

## Before you start

Running `kubectl run` or `docker run` feels like one step, but several programs pass the request along before a process actually starts. The kubelet asks `containerd` to create a container, `containerd` starts a small helper called a shim, and the shim calls a low-level runtime such as `runc`, which sets up the namespaces and starts your program and then exits. This chapter explains why the work is split that way. The short answer is that you can restart `containerd` without killing every container on the machine, because the shim, not the daemon, is the parent of your process.

A small example: after starting a container, run `ps -ef --forest` on the node. You will find your app under a `containerd-shim-runc-v2` process, and no `runc` anywhere.

Know the ideas from [chapter 2](/tech/series/cncf-containers/02.oci-images-and-overlayfs/) first: an image is unpacked into a root filesystem, and the runtime starts a process inside it.

Terms used in this chapter:

- **CRI**: the Container Runtime Interface, the gRPC API the kubelet uses to ask a runtime to create pods and containers.
- **containerd**: a long-running daemon that pulls images, manages snapshots and supervises containers.
- **shim**: a small per-container process that stays alive as the container's parent and relays its state back to containerd.
- **OCI runtime**: the program that actually creates the container from a bundle (rootfs plus `config.json`); `runc` is the reference one.
- **youki**: an OCI runtime written in Rust, an alternative to the Go-based `runc`.
- **FIFO**: a named pipe, a file that one process writes into and another reads from; used here as a start signal.
- **gRPC**: a remote-procedure-call protocol over HTTP/2 that the components use to talk to each other.

## 1. Deconstructing the Runtime Stack: Who Owns What?

Early versions of Docker (`v0.x` through `v1.10`) packed image pulling, storage drivers, network bridges, API servers, and container process supervision into a single monolithic `dockerd` daemon. That design had a serious operational flaw: **restarting or upgrading `dockerd` sent `SIGHUP`/`SIGTERM` to every running container on the host** or orphaned their standard I/O pipes (`stdout`/`stderr`), causing applications writing to logs to crash with `SIGPIPE`.

To solve this, the CNCF and Open Container Initiative (OCI) split the stack into four decoupled layers with strict contracts:

| Component | Lifespan | Responsibility | What It Does **NOT** Do |
| :--- | :--- | :--- | :--- |
| **`kubelet` / `dockerd`** | Long-lived daemon | Orchestration agent (`kubelet` sync loop) or developer UX engine (`docker build`, Swarm, Compose). Speaks **CRI gRPC** to `containerd`. | Does not unpack image layers or call `clone3(2)`. |
| **`containerd`** | Long-lived daemon | Node-level image & container supervisor: **Content Store**, **BoltDB Metadata Store**, **Snapshotter** (OverlayFS mounts), **CNI** invocation, and Task management. | Does not directly parent container processes or hold their `stdout`/`stderr` pipes. |
| **`containerd-shim-runc-v2`** | **One process per Pod / container** (lives as long as the container) | Daemonless parent of the container process: keeps STDIO FIFOs open, sets `prctl(PR_SET_CHILD_SUBREAPER, 1)`, caches the container's exit status if `containerd` is restarting, and speaks lightweight **ttrpc** to `containerd`. | Does not parse Dockerfiles or manage image registries. |
| **OCI Runtime (`runc`, `youki`, `crun`)** | **Ephemeral CLI** (runs for milliseconds during `create` and `start`, then exits!) | Reads an **OCI Runtime Bundle** (`config.json` + mounted `rootfs/`), executes `clone3`/`unshare`/`setns`, configures cgroup v2, calls `pivot_root(2)`, drops capabilities, loads Seccomp-BPF filters, and `execve`s the application. | Does **not** stay resident in memory while the container runs! |

```text
Host Process Tree While Container Is Running
============================================
systemd (PID 1)
 ├── containerd (PID 842)                 <-- Can be restarted/upgraded at any time!
 ├── kubelet (PID 910)
 └── containerd-shim-runc-v2 (PID 14920)  <-- Detached session leader (setsid + subreaper)
      ├── pause (PID 14941)               <-- Holds Pod netns, ipcns, utsns
      └── nginx: master (PID 14988)       <-- Reparented to shim after runc/youki exits!
           └── nginx: worker (PID 14989)
```

## 2. Why `create` and `start` Are Split: The `exec.fifo` Handshake

If you read the [OCI Runtime Specification](https://github.com/opencontainers/runtime-spec), a container lifecycle is split into two distinct commands:

```bash
youki create --bundle /run/containerd/.../bundle my-container-id
# ... caller configures external network veth pairs or post-create hooks ...
youki start my-container-id
```

Why doesn't `create` simply `execve()` the user's application immediately?

Consider a race condition: suppose `containerd` or a network plugin needs the container's **PID** so it can move a `veth` interface into `/proc/<pid>/ns/net`, or attach an eBPF program to the container's cgroup, *before* the user's application starts binding sockets or sending traffic.

- Before `create` runs, the container's namespaces and PID do not exist yet.
- If `create` immediately executed the application binary (`nginx` or `postgres`), the application would race ahead and fail to bind to an IP address that CNI hasn't finished configuring!

### How `runc` and `youki` Implement the `exec.fifo` Barrier

1. **`youki create --bundle <dir> <id>`**:
   - The runtime creates a named pipe (`mkfifo`) at `/run/youki/<id>/exec.fifo`.
   - It spawns the container `init` child process inside the requested namespaces (`CLONE_NEWPID`, `CLONE_NEWNS`, `CLONE_NEWUTS`, etc.), places the child's PID into the cgroup v2 `cgroup.procs`, mounts the rootfs via `pivot_root(2)`, drops Linux capabilities, and installs the Seccomp-BPF filter.
   - Right before calling `execve(config.process.args)`, the container `init` child calls **`open("exec.fifo", O_WRONLY)`** (using a pre-opened directory FD inside `/run/youki/<id>` before `pivot_root` detached the host filesystem!).
   - In POSIX, opening a FIFO with `O_WRONLY` **blocks in the kernel** until another process opens the same FIFO with `O_RDONLY`.
   - The `youki create` parent process records `"status": "created"` and the child's host PID in `state.json`, and **exits cleanly**. The container child is now frozen at the exact doorstep of `execve()`, with all its namespaces, mounts, and cgroups active and inspectable at `/proc/<pid>/ns/*`!
2. **`youki start <id>`**:
   - Once `containerd` has finished wiring any external resources, `containerd-shim-runc-v2` invokes `youki start <id>`.
   - `youki start` opens `/run/youki/<id>/exec.fifo` with `O_RDONLY` and reads a single byte.
   - This immediately unblocks the container `init` child, which closes the FIFO and invokes **`execve(entrypoint, argv, envp)`** to replace its own memory image with the user's application!

## 3. Go `runc` (`nsenter` C Constructor) vs. Rust `youki`

Both **`runc`** (written in Go) and **`youki`** (a CNCF Sandbox OCI runtime written in Rust) implement the exact same OCI Runtime Specification (`config.json`), yet their internal process initialization differs sharply due to a fundamental Linux kernel constraint:

> **The Multi-Threaded Namespace Rule (`kernel/nsproxy.c` & `kernel/user_namespace.c`)**:
> The Linux kernel **forbids** a process with more than one OS thread from calling `setns(fd, CLONE_NEWUSER)`, `setns(fd, CLONE_NEWNS)`, or `unshare(CLONE_NEWUSER)`. They return `-EINVAL` immediately!

### Why Go `runc` Needs a Hidden C `nsenter` Pre-Runtime Hook

The Go runtime (`runtime.main`) spawns multiple OS threads (for the garbage collector, netpoller, and `sysmon` preemption monitor) *before* the Go `func main()` even executes its first line of code! By the time Go code runs, the process is already multi-threaded, so calling `unshare(CLONE_NEWUSER)` or `setns()` from Go fails with `EINVAL`.

To work around this, `runc` links a C library (`libcontainer/nsenter`) marked with the ELF constructor attribute `__attribute__((constructor))`:

1. When the `runc` child starts, the C dynamic linker executes `nsexec()` in C **before the Go runtime initializes** (while the process is still strictly single-threaded!).
2. The C code communicates over a `socketpair` with the parent to perform three-stage `clone()`, UID/GID map setup, and `setns()`/`unshare()`, and only lets the Go runtime boot once the namespaces are already entered.

### How Rust `youki` Eliminates the C Constructor

Because Rust has no background runtime threads or garbage collector, a Rust binary starts `fn main()` as a **strictly single-threaded OS process**. In `youki` (`crates/libcontainer`):

- There is no C/Go FFI split. The entire three-stage namespace & user-mapping handshake (`main process` $\to$ `intermediate process` $\to$ `init process`) is written in pure, memory-safe Rust using `nix` / `rustix` syscalls (`clone3`, `unshare`, `setns`, `pivot_root`) and Unix domain sockets.
- Removing the Go runtime boot overhead from every short-lived `create`/`start`/`state` invocation can lower per-container startup cost on high-churn nodes such as CI runners; measure it before relying on it.

## 4. Verification Lab: `containerd-shim-v2` & OCI `exec.fifo` Lifecycle Simulator

The following self-contained Python 3 verification script implements a real POSIX FIFO (`os.mkfifo`) synchronization barrier and subreaper state machine modeling **`containerd-shim-runc-v2`** and **`youki`**:

1. Verifies the OCI state transitions (`creating` $\to$ `created` $\to$ `running` $\to$ `stopped`).
2. Uses a real OS pipe/FIFO barrier to prove that during the `"created"` state, the child process's namespaces/PID are live and external CNI setup can inspect them *before* the user payload executes.
3. Models the shim's role in **daemonless survival**: the shim reaps the container and caches its exit status and buffered STDIO. (The script does not actually restart a `containerd` process; it only shows who holds the state.)

```python
#!/usr/bin/env python3
"""
Verification Lab 03: containerd-shim-runc-v2 & OCI Runtime (runc/youki) exec.fifo State Machine
Run directly: python3 lab03_shim_oci_runtime.py
"""
import os
import tempfile
import threading
import time
from dataclasses import dataclass, field
from typing import Dict, List, Optional


@dataclass
class OCIState:
    ociVersion: str = "1.1.0"
    id: str = ""
    status: str = "creating"  # creating -> created -> running -> stopped
    pid: int = 0
    bundle: str = ""
    annotations: Dict[str, str] = field(default_factory=dict)


class OCIRuntimeYoukiSimulator:
    """Models the short-lived OCI runtime CLI (youki / runc) using a real OS FIFO barrier."""

    def __init__(self, state_root: str):
        self.state_root = state_root
        self.states: Dict[str, OCIState] = {}
        self.exit_codes: Dict[str, int] = {}
        self.execution_trace: List[str] = []
        self._worker_threads: Dict[str, threading.Thread] = {}

    def _fifo_path(self, cid: str) -> str:
        return os.path.join(self.state_root, f"{cid}.exec.fifo")

    def create(self, cid: str, bundle: str, entrypoint_fn) -> OCIState:
        fifo_path = self._fifo_path(cid)
        os.mkfifo(fifo_path, 0o600)
        state = OCIState(id=cid, status="creating", pid=51000 + len(self.states) + 1, bundle=bundle)
        self.states[cid] = state

        ready_event = threading.Event()

        def container_init_process() -> None:
            # 1. Setup namespaces, cgroups v2, pivot_root, capabilities, seccomp
            self.execution_trace.append(f"[{cid}:init] namespaces + cgroups + pivot_root configured (pid={state.pid})")
            state.status = "created"
            ready_event.set()

            # 2. Block on opening exec.fifo for writing (no reader yet) until `youki start <cid>` opens it
            with open(fifo_path, "wb") as fifo_w:
                fifo_w.write(b"\x00")

            # 3. Unblocked! Replace process image via execve(entrypoint)
            os.unlink(fifo_path)
            state.status = "running"
            self.execution_trace.append(f"[{cid}:execve] exec.fifo unblocked -> running user entrypoint")
            rc = entrypoint_fn()
            self.exit_codes[cid] = rc
            state.status = "stopped"
            self.execution_trace.append(f"[{cid}:exit] process exited with code {rc}")

        t = threading.Thread(target=container_init_process, daemon=True)
        self._worker_threads[cid] = t
        t.start()
        ready_event.wait(timeout=2.0)
        # Note: 'youki create' CLI process now exits while container_init_process is blocked on exec.fifo!
        return state

    def start(self, cid: str) -> None:
        state = self.states[cid]
        assert state.status == "created", f"Cannot start container in state {state.status}"
        fifo_path = self._fifo_path(cid)
        # Opening the FIFO for reading unblocks the init process; read the single byte it wrote
        with open(fifo_path, "rb") as fifo_r:
            fifo_r.read(1)

    def wait_for_exit(self, cid: str) -> int:
        self._worker_threads[cid].join(timeout=2.0)
        return self.exit_codes[cid]


class ContainerdShimV2:
    """Per-Pod daemonless supervisor that survives containerd daemon restarts."""

    def __init__(self, runtime: OCIRuntimeYoukiSimulator):
        self.runtime = runtime
        self.cached_exit_status: Dict[str, int] = {}
        self.stdio_buffer: Dict[str, List[str]] = {}

    def ttrpc_create(self, cid: str, bundle: str, entrypoint_fn) -> OCIState:
        self.stdio_buffer[cid] = []
        return self.runtime.create(cid, bundle, entrypoint_fn)

    def ttrpc_start(self, cid: str) -> None:
        self.runtime.start(cid)

    def reap_and_cache_exit(self, cid: str) -> int:
        rc = self.runtime.wait_for_exit(cid)
        # The shim caches the exit code so a restarted containerd can still fetch it
        self.cached_exit_status[cid] = rc
        return rc


def main() -> None:
    with tempfile.TemporaryDirectory() as tmpdir:
        runtime = OCIRuntimeYoukiSimulator(state_root=tmpdir)
        shim = ContainerdShimV2(runtime=runtime)

        cid = "pod-web-01"

        def user_app() -> int:
            runtime.execution_trace.append(f"[{cid}:app] HTTP server bound to CNI veth0 IP 10.42.0.18:8080")
            shim.stdio_buffer[cid].append("INFO: request served 200 OK")
            return 0

        print("=== 1. OCI Create Phase (Blocked on exec.fifo Barrier) ===")
        st = shim.ttrpc_create(cid, bundle="/run/containerd/bundle", entrypoint_fn=user_app)
        print(f"  After 'youki create': status={st.status}, pid={st.pid}")
        assert st.status == "created"

        # Now kubelet/containerd configures CNI network using st.pid BEFORE user_app runs!
        runtime.execution_trace.append(f"[{cid}:cni] CNI ADD attached veth0 (10.42.0.18/24) to /proc/{st.pid}/ns/net")

        print("\n=== 2. OCI Start Phase & Daemonless Containerd Restart Simulation ===")
        shim.ttrpc_start(cid)
        # The container runs and exits under shim supervision; the shim caches the exit status
        exit_code = shim.reap_and_cache_exit(cid)
        print(f"  Shim reaped container exit_code={exit_code}, preserved logs={shim.stdio_buffer[cid]}")
        print("\n=== 3. Execution Ordering Trace ===")
        for idx, line in enumerate(runtime.execution_trace, 1):
            print(f"  {idx}. {line}")

        # Verify strict causal ordering: init setup -> CNI network wiring -> execve -> app bind -> exit
        cni_idx = next(i for i, s in enumerate(runtime.execution_trace) if ":cni]" in s)
        exec_idx = next(i for i, s in enumerate(runtime.execution_trace) if ":execve]" in s)
        app_idx = next(i for i, s in enumerate(runtime.execution_trace) if ":app]" in s)
        assert cni_idx < exec_idx < app_idx
        assert exit_code == 0 and runtime.states[cid].status == "stopped"
        print("\nAll Lab 03 containerd-shim-v2 & OCI runtime invariants verified.")


if __name__ == "__main__":
    main()
```

## Key Takeaways

1. **`containerd-shim-runc-v2` decouples daemon upgrades from running workloads**: Because each Pod's containers are parented to an independent `containerd-shim-runc-v2` process that holds open STDIO pipes and sets `PR_SET_CHILD_SUBREAPER`, restarting `containerd` or `kubelet` never kills running containers.
2. **The `exec.fifo` pipe eliminates creation race conditions**: Separating `create` from `start` via a blocking named FIFO lets `youki`/`runc` construct all namespaces and cgroups first, hand the living PID back to `containerd` for CNI network attachment, and only call `execve()` once `start` unblocks the FIFO.
3. **Rust `youki` avoids the multi-threaded `setns` trap natively**: Because Linux forbids `setns(CLONE_NEWUSER | CLONE_NEWNS)` from multi-threaded processes, Go `runc` requires a pre-runtime C constructor (`nsenter`), whereas Rust `youki` executes the entire namespace handshake in single-threaded Rust.

In **Chapter 04**, we examine **daemonless and rootless container security**: how **Podman** and **User Namespaces (`CLONE_NEWUSER`)** map container `UID 0` to an unprivileged host user, and how **Linux Capabilities**, **Seccomp-BPF**, and `no_new_privs` harden the syscall boundary.
