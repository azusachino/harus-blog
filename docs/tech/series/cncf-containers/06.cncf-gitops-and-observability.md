Containers (`runc` / `youki`), runtimes (`containerd`), and eBPF dataplanes (`Cilium`) give us isolated, networked Linux processes. However, running a production cloud-native platform requires answering three day-two operational questions:

1. **Supply Chain & Packaging**: How do we package, sign, and version-pin not just container root filesystems, but also Helm charts, SBOMs, and Kubernetes manifests without template spaghetti or silent tag drift?
2. **Continuous Delivery (GitOps)**: How do we converge live cluster state toward a Git repository's declared state without exposing cluster admin credentials to external CI runners or getting trapped in infinite `OutOfSync` loops against mutating admission webhooks?
3. **Observability (`OpenTelemetry` & `Prometheus`)**: How do we correlate logs, metrics, and distributed traces across dozens of containers while preventing high-cardinality labels from exhausting Prometheus TSDB memory?

This final chapter connects the container runtime to the CNCF operational plane: **OCI Artifacts**, **Argo CD GitOps**, **OpenTelemetry W3C Trace Context**, and **Prometheus TSDB internals**.

## Before you start

Once containers run, you have to answer three operational questions: what exactly is deployed, how does the cluster stay equal to what the Git repo says, and how do you see what it is doing. This chapter covers one answer for each. OCI artifacts let a registry hold things other than images, such as signatures. Argo CD watches a Git repository and keeps the cluster matching it. OpenTelemetry and Prometheus give you traces and metrics.

For example, if someone runs `kubectl edit` on a live Deployment, a GitOps tool notices that the cluster no longer matches Git and either reports the drift or puts the Git version back.

Read [chapter 5](/tech/series/cncf-containers/05.cni-networking-and-ebpf-dataplanes/) first if the cluster-networking vocabulary is unfamiliar; the earlier chapters on images (chapter 2) also help with the artifact section.

Terms used in this chapter:

- **OCI artifact**: any file type stored in an OCI registry using the image manifest format, for example a Helm chart or a signature.
- **GitOps**: managing a cluster by committing the desired state to Git and letting a controller apply it.
- **reconciliation**: a controller repeatedly comparing the desired state with the live state and fixing differences.
- **Argo CD**: a Kubernetes controller that syncs manifests from Git to a cluster.
- **trace / span**: a trace follows one request across services; a span is one timed step inside it.
- **traceparent**: the W3C HTTP header that carries the trace and parent span IDs between services.
- **Prometheus**: a metrics system that stores time series identified by a metric name plus labels.
- **cardinality**: the number of distinct label combinations; too many makes Prometheus use huge amounts of memory.

## 1. OCI v1.1 Artifacts, Typed Manifests & Version Pinning

In Chapter 02 we saw that an OCI registry stores content-addressable blobs indexed by SHA-256 digests (`config` + `layers[]`). The **OCI Image & Distribution v1.1 Specification** generalized this Merkle DAG via the `artifactType` and **`subject` (Referrers API)** fields so a single registry stores every deployment artifact alongside the container image:

```text
                   OCI Container Image Manifest
                   sha256:9f82a1... (registry.example.com/app:1.4.0)
                                ^
        +-----------------------+-----------------------+
        | subject                                       | subject
        |                                               |
+-------+--------------------------+    +---------------+------------------+
| Cosign Signature Artifact        |    | SPDX / CycloneDX SBOM Artifact   |
| artifactType:                    |    | artifactType:                    |
| application/vnd.dev.cosign...    |    | application/spdx+json            |
+----------------------------------+    +----------------------------------+
```

### Templating vs. Overlays vs. Typed Code Synthesis (`Helm`, `Kustomize`, `CDK8s`)

To generate the Kubernetes YAML manifests that consume those OCI images, three patterns dominate the CNCF ecosystem:

| Approach | Tooling | Strength | Failure Mode to Watch |
| :--- | :--- | :--- | :--- |
| **Go Text Templating** | **Helm** (`oci://registry/charts/...`) | De-facto standard for distributing third-party off-the-shelf software (`prometheus`, `cert-manager`, `argo-cd`). | Indentation bugs (`nindent 8`) and untyped string interpolation that only fail at `kubectl apply` time. |
| **Structural YAML Overlays** | **Kustomize** (`kubectl apply -k`) | Pure YAML strategic-merge and JSON6902 patches without template syntax. | Deep multi-environment overlay trees (`base/` + 6 patches) obscure the final rendered manifest. |
| **Typed Code Synthesis** | **CDK8s** (TypeScript / Python / Go, as used in `harus-charts`) | Full compiler type-checking, reusable constructs, and unit testing before emitting deterministic pure YAML into Git. | Requires a synthesis build step (`cdk8s synth`) so Argo CD or `kubectl` can read plain rendered YAML. |

> **Never Deploy Floating Image Tags**: Whether you author manifests via raw YAML, Kustomize, or CDK8s, never commit `:latest` or `:main`. Maintain a single version manifest (such as `SERVICE_VERSIONS.yaml` queried against upstream registries via `skopeo list-tags`), and verify before deployment that every `image:` tag in your manifests matches the pinned version *and* exists in `containerd`.

## 2. Pull-Based GitOps & Argo CD Reconciliation Internals

Traditional CI/CD pipelines use a **push model**: a GitHub Actions or GitLab runner holds a cluster-admin `KUBECONFIG` secret and runs `kubectl apply` or `helm upgrade` at the end of a build. If the CI runner is compromised, the attacker immediately owns the production Kubernetes cluster; if someone manually edits a live cluster resource (`kubectl edit`), Git and the cluster silently diverge.

**GitOps** (implemented by the CNCF projects **Argo CD** and **Flux**) inverts the control flow into a **pull-based reconciliation loop** running inside the cluster:

```text
  Developer / CI Pipeline                  Kubernetes Cluster (Argo CD)
  =======================                  ============================
  1. Commit rendered YAML / bump pin  -->  Git Repository (Source of Truth)
                                                   |
                                                   | 2. repo-server clones & renders
                                                   v
                                           application-controller
                                           Compares 3 States:
                                             (A) Target Git State (Desired)
                                             (B) Live Cluster State (etcd)
                                             (C) last-applied-configuration
                                                   |
                                                   | 3. SyncWaves (-5 -> 0 -> +5)
                                                   v
                                           kube-apiserver (Server-Side Apply)
```

### Why Argo CD Needs a 3-Way Diff & `ignoreDifferences`

Why can't `argocd-application-controller` simply run a naive 2-way diff (`Git YAML == Live etcd JSON`)?

Because the live object stored in `etcd` is **mutated continuously by the Kubernetes control plane** after creation!

1. **Defaulting & Admission Webhooks**: `kube-apiserver` injects default fields (`terminationGracePeriodSeconds: 30`, `imagePullPolicy: IfNotPresent`), and MutatingAdmissionWebhooks inject sidecar containers, CA bundles (`caBundle` on `ValidatingWebhookConfiguration`), or `metadata.annotations`.
2. **Runtime Controllers (`HPA` / `VPA`)**: When a `HorizontalPodAutoscaler` scales a Deployment from `replicas: 2` to `replicas: 7` during a traffic spike, `spec.replicas` in live `etcd` is `7`, while Git still says `replicas: 2` (or omits `spec.replicas`).

If Argo CD compared Git (`replicas: 2`) against Live (`replicas: 7`) naively, it would mark the Application **`OutOfSync`** and scale your production fleet back down to `2` right in the middle of a traffic spike!

To prevent this:

- **3-Way Structural Diff / Server-Side Apply (`managedFields`)**: Argo CD compares the **Target Git manifest** against the **`kubectl.kubernetes.io/last-applied-configuration`** (or field ownership in `metadata.managedFields`), ignoring fields defaulted by the API server that Git never claimed ownership of.
- **`ignoreDifferences` + `RespectIgnoreDifferences=true`**: For fields legitimately mutated by in-cluster controllers (such as `/spec/replicas` managed by an HPA or `/webhooks/*/clientConfig/caBundle` rotated by `cert-manager`), explicit JSONPointers in `ignoreDifferences` instruct both the diff engine and the sync engine to leave the live controller's value intact.
- **Deterministic Ordering with `sync-wave`**: By annotating resources with `argocd.argoproj.io/sync-wave: "-5"` (CRDs & Namespaces) $\to$ `"-1"` (database migration Jobs) $\to$ `"0"` (Deployments) $\to$ `"5"` (IngressRoutes), Argo CD waits for every resource in wave $W$ to report `Healthy` before applying wave $W+1$.

## 3. Cloud-Native Observability: OpenTelemetry & Prometheus TSDB

Once containers are running in production, observability leans on two CNCF projects: **OpenTelemetry (OTel)** for unified telemetry generation/collection, and **Prometheus** for time-series metric storage and alerting.

### W3C `traceparent` Context Propagation

How does a distributed trace connect an ingress gateway container (`Traefik` / `Envoy`), an API server container (`Go` / `Rust`), and a background worker across asynchronous RPC boundaries? Every outbound HTTP/gRPC request carries the standardized **W3C Trace Context (`traceparent`)** header:

```http
traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
             ^^ ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^ ^^^^^^^^^^^^^^^^ ^^
             |  |                                |                +-- trace-flags (01 = sampled)
             |  |                                +-- parent-id / span-id (8 bytes = 16 hex chars)
             |  +-- trace-id (16 bytes = 32 hex chars, shared across the entire request tree)
             +-- version (00)
```

When a container logs an error, injecting `trace_id="4bf92f3577b34da6a3ce929d0e0e4736"` and `span_id="00f067aa0ba902b7"` into the structured JSON log line allows you to jump directly from a Prometheus alert (`exemplar`) to the exact distributed trace waterfall and container stdout log line.

### Inside Prometheus TSDB: Why High-Cardinality Labels Crash Monitoring

In Prometheus, **every unique combination of metric name and `key="value"` label pairs defines a distinct Time Series (`SeriesID`)** in the in-memory `Head` block:

$$\text{Active Series} \le \prod_{i=1}^{k} \bigl|\text{Unique Values}(\text{Label}_i)\bigr|$$

Under the hood, Prometheus's Time-Series Database (TSDB) maintains an **in-memory Inverted Index** mapping every `(label_name, label_value)` pair to a sorted list of 64-bit `SeriesID`s (**Postings List**), plus a Gorilla XOR-compressed chunk buffer (very roughly 2–4 KiB of RAM per active series in the 2-hour `Head`):

- **Bounded Label Set (Good)**:
  `http_requests_total{service="checkout", method="POST", status="200", zone="ap-northeast-1a"}`
  $\to$ $1 \times 6 \times 15 \times 3 = \mathbf{270\text{ active series}}$ (under 1 MiB of RAM). Queries intersect small postings lists in microseconds.
- **Unbounded High-Cardinality Label Explosion (Catastrophic)**:
  A developer adds `user_id` (`500,000` users) or `request_id` / `client_ip` as a Prometheus label:
  `http_requests_total{service="checkout", method="POST", status="200", user_id="u_948192"}`
  $\to$ **Millions of ephemeral time series (`Series Churn`)**! Every new `user_id` allocates a new `SeriesID` struct, appends to the inverted index postings lists, bloats the Write-Ahead Log (`wal/`), and triggers a `cgroup` `OOMKill` on the Prometheus container during 2-hour block compaction.

> **The Cardinality Rule**: Never put unbounded identifiers (`user_id`, `email`, `request_id`, `trace_id`, `pod_uid`, raw URL paths with IDs like `/users/48192/profile`) inside metric labels. Put high-cardinality dimensions in **Traces / Logs**, or attach a single **`trace_id` Exemplar** to a Histogram bucket!

## 4. Verification Lab: Argo CD 3-Way Reconciler & Prometheus TSDB Inverted Index

The following self-contained Python 3 verification script implements and verifies both operational engines:

1. **Argo CD 3-Way Structural Diff + `ignoreDifferences` + `sync-wave` Reconciler**: Proves that server-defaulted fields (`terminationGracePeriodSeconds`) and HPA-mutated fields (`/spec/replicas` in `ignoreDifferences`) do **not** trigger false-positive `OutOfSync` overwrites, while genuine Git changes execute strictly in `sync-wave` (`-5` $\to$ `0` $\to$ `+5`) order.
2. **Prometheus TSDB Inverted Index & Cardinality Simulator**: Implements an inverted postings index (`(label_key, label_val) -> Set[SeriesID]`) with W3C `traceparent` exemplar attachment, proving how a single unbounded `user_id` label multiplies memory footprint by $500\times$ compared to attaching `trace_id` as a bounded Histogram Exemplar.

```python
#!/usr/bin/env python3
"""
Verification Lab 06: Argo CD 3-Way GitOps Reconciler & Prometheus TSDB Inverted-Index Cardinality
Run directly: python3 lab06_gitops_and_tsdb.py
"""
import copy
from dataclasses import dataclass, field
from typing import Dict, FrozenSet, List, Optional, Set, Tuple


# ---------------------------------------------------------------------------
# 1. Argo CD 3-Way Structural Diff & Sync-Wave Reconciler
# ---------------------------------------------------------------------------
@dataclass
class K8sResource:
    kind: str
    name: str
    sync_wave: int
    spec: Dict[str, object]


class ArgoCDReconciler:
    def __init__(self, ignored_fields_by_kind: Dict[str, Set[str]]):
        self.ignored_fields_by_kind = ignored_fields_by_kind

    def compute_3way_diff(
        self,
        git_desired: K8sResource,
        last_applied: K8sResource,
        live_cluster: K8sResource,
    ) -> Tuple[str, Dict[str, Tuple[object, object]]]:
        """
        Compares git_desired vs live_cluster while respecting:
        1. API-server defaulted fields present in live_cluster but never in git_desired or last_applied.
        2. Fields listed in ignoreDifferences (e.g. HPA-managed 'replicas').
        Returns (status,changed_fields_map).
        """
        ignored = self.ignored_fields_by_kind.get(git_desired.kind, set())
        diffs: Dict[str, Tuple[object, object]] = {}

        # Check all fields declared in Git desired state or previously applied by Git
        tracked_keys = set(git_desired.spec.keys()) | set(last_applied.spec.keys())
        for key in tracked_keys:
            if key in ignored:
                continue
            desired_val = git_desired.spec.get(key)
            live_val = live_cluster.spec.get(key)
            if desired_val != live_val:
                diffs[key] = (live_val, desired_val)

        status = "Synced" if not diffs else "OutOfSync"
        return status, diffs

    def plan_sync_waves(self, resources: List[K8sResource]) -> List[Tuple[int, str, str]]:
        ordered = sorted(resources, key=lambda r: (r.sync_wave, r.kind, r.name))
        return [(r.sync_wave, r.kind, r.name) for r in ordered]


# ---------------------------------------------------------------------------
# 2. Prometheus TSDB Head Block & Inverted Postings Index Simulator
# ---------------------------------------------------------------------------
@dataclass
class Exemplar:
    traceparent: str
    value: float


class PrometheusTSDBHead:
    BYTES_PER_ACTIVE_SERIES = 2048  # rough per-series estimate, not a measurement

    def __init__(self) -> None:
        self.series_table: Dict[FrozenSet[Tuple[str, str]], int] = {}
        self.postings: Dict[Tuple[str, str], Set[int]] = {}
        self.samples: Dict[int, List[float]] = {}
        self.exemplars: Dict[int, Exemplar] = {}
        self._next_series_id = 1

    def ingest(
        self,
        metric_name: str,
        labels: Dict[str, str],
        value: float,
        traceparent: Optional[str] = None,
    ) -> int:
        full_labels = dict(labels)
        full_labels["__name__"] = metric_name
        label_set = frozenset(full_labels.items())

        series_id = self.series_table.get(label_set)
        if series_id is None:
            series_id = self._next_series_id
            self._next_series_id += 1
            self.series_table[label_set] = series_id
            self.samples[series_id] = []
            for kv in label_set:
                self.postings.setdefault(kv, set()).add(series_id)

        self.samples[series_id].append(value)
        if traceparent is not None:
            # Bounded exemplar storage: overwrites latest exemplar for this series without creating new SeriesID!
            self.exemplars[series_id] = Exemplar(traceparent=traceparent, value=value)
        return series_id

    def query_postings_intersection(self, matchers: Dict[str, str]) -> Set[int]:
        posting_sets = [self.postings.get((k, v), set()) for k, v in matchers.items()]
        if not posting_sets:
            return set()
        return set.intersection(*posting_sets)

    @property
    def active_series_count(self) -> int:
        return len(self.series_table)

    @property
    def estimated_head_ram_kib(self) -> float:
        return (self.active_series_count * self.BYTES_PER_ACTIVE_SERIES) / 1024.0


def main() -> None:
    print("=== 1. Argo CD 3-Way Diff, ignoreDifferences & Sync-Wave Verification ===")
    reconciler = ArgoCDReconciler(ignored_fields_by_kind={"Deployment": {"replicas"}})

    git_deploy = K8sResource(
        kind="Deployment",
        name="api-gateway",
        sync_wave=0,
        spec={"image": "registry.example.com/api:1.2.0", "replicas": 2},
    )
    last_applied_deploy = copy.deepcopy(git_deploy)
    # In live etcd: HPA scaled replicas to 6, and kube-apiserver defaulted terminationGracePeriodSeconds=30
    live_deploy = K8sResource(
        kind="Deployment",
        name="api-gateway",
        sync_wave=0,
        spec={
            "image": "registry.example.com/api:1.2.0",
            "replicas": 6,
            "terminationGracePeriodSeconds": 30,
        },
    )
    status_1, diffs_1 = reconciler.compute_3way_diff(git_deploy, last_applied_deploy, live_deploy)
    print(f"  [HPA replicas=6 + K8s defaults] status={status_1}, diffs={diffs_1}")
    assert status_1 == "Synced" and len(diffs_1) == 0

    # Now developer bumps image pin in Git to 1.3.0
    git_deploy_v2 = K8sResource(
        kind="Deployment",
        name="api-gateway",
        sync_wave=0,
        spec={"image": "registry.example.com/api:1.3.0", "replicas": 2},
    )
    status_2, diffs_2 = reconciler.compute_3way_diff(git_deploy_v2, last_applied_deploy, live_deploy)
    print(f"  [Git image bumped to 1.3.0]     status={status_2}, diffs={diffs_2}")
    assert status_2 == "OutOfSync" and diffs_2 == {"image": ("registry.example.com/api:1.2.0", "registry.example.com/api:1.3.0")}

    waves = reconciler.plan_sync_waves(
        [
            K8sResource("IngressRoute", "api-route", sync_wave=5, spec={}),
            git_deploy_v2,
            K8sResource("Job", "db-migrate", sync_wave=-1, spec={}),
            K8sResource("CustomResourceDefinition", "ingressroutes.traefik.io", sync_wave=-5, spec={}),
        ]
    )
    print(f"  [Sync-Wave Execution Plan]      {waves}")
    assert [w[0] for w in waves] == [-5, -1, 0, 5]

    print("\n=== 2. Prometheus TSDB Inverted Index & Cardinality Verification ===")
    tsdb_good = PrometheusTSDBHead()
    tsdb_bad = PrometheusTSDBHead()

    methods = ["GET", "POST"]
    statuses = ["200", "500"]
    # Simulate 2,000 HTTP requests across 500 distinct user_ids and all 4 (method, status) pairs
    for req_i in range(2_000):
        m = methods[req_i % 2]
        st = statuses[(req_i // 2) % 2]
        uid = f"user_{req_i // 4}"
        traceparent = f"00-4bf92f3577b34da6a3ce929d0e0e{req_i:04x}-00f067aa0ba9{req_i:04x}-01"

        # Good design: bounded labels (method, status) + traceparent attached as an Exemplar!
        tsdb_good.ingest("http_req_duration_ms", {"method": m, "status": st}, value=12.4, traceparent=traceparent)
        # Bad design: unbounded user_id placed inside metric labels!
        tsdb_bad.ingest("http_req_duration_ms", {"method": m, "status": st, "user_id": uid}, value=12.4)

    print(
        f"  [Bounded Labels + Exemplars] active_series={tsdb_good.active_series_count:4d}, "
        f"head_ram={tsdb_good.estimated_head_ram_kib:6.1f} KiB, exemplars={len(tsdb_good.exemplars)}"
    )
    print(
        f"  [Unbounded user_id Label]    active_series={tsdb_bad.active_series_count:4d}, "
        f"head_ram={tsdb_bad.estimated_head_ram_kib:6.1f} KiB (500x cardinality inflation!)"
    )
    assert tsdb_good.active_series_count == 4
    assert tsdb_bad.active_series_count == 2_000
    assert len(tsdb_good.query_postings_intersection({"__name__": "http_req_duration_ms", "status": "500"})) == 2
    print("\nAll Lab 06 GitOps & Prometheus TSDB invariants verified.")


if __name__ == "__main__":
    main()
```

## Key Takeaways

1. **OCI v1.1 unifies artifacts and supply-chain provenance**: Container images, Helm charts, SBOMs, and Cosign signatures share the same content-addressable registry graph via the `subject` Referrers API; pair them with strict version manifests (`SERVICE_VERSIONS.yaml`) rather than floating tags.
2. **GitOps reconcilers require 3-way diffs and explicit ownership boundaries**: Use `sync-wave` annotations to enforce causal deployment order (`CRD` $\to$ `PreSync Migration Job` $\to$ `Deployment` $\to$ `IngressRoute`), and configure `ignoreDifferences` for fields actively mutated by in-cluster controllers (`HPA` replicas, webhook CA bundles).
3. **Keep metric labels bounded; link high-cardinality traces via Exemplars**: Store low-cardinality dimensions (`service`, `method`, `status_code`, `zone`) in Prometheus labels, propagate W3C `traceparent` headers across every RPC, and attach `trace_id` as a Histogram Exemplar so alerts link directly to distributed traces without blowing up TSDB postings memory.
