In Chapter 05, we saw how the Aeron Media Driver moves framed bytes across shared-memory Term Buffers and reliable UDP with sub-10-microsecond latency. However, core Aeron transport is deliberately **ephemeral**: once a term buffer rotates past its 3 partitions, old frames are overwritten.

To build a fault-tolerant financial exchange, order-matching engine, or replicated state machine (`harus-aeron-rs/crates/archive`, `crates/cluster`, and `sakuranbo`), we layer two additional modules on top of the Media Driver:

1. **`aeron-archive`:** Records live Aeron streams to disk at wire speed and replays any historical byte range on demand (`ReplayCursor`).
2. **`aeron-cluster`:** Orders client ingress through a Raft-based `ConsensusModule`, persists the ordered log via `aeron-archive`, and drives a **Deterministic Clustered Service**.

In **Chapter 06**, we examine the on-disk binary structures of `aeron-archive` (`RecordingDescriptor`, `catalog.dat`, `archive-mark.dat`) and `aeron-cluster` (`node-state.dat`, `recording.log`), and verify why determinism is the golden rule of replicated state machines.

## Before you start

A message stream that is gone once read is no use if a server crashes and must work out what it missed. Two additions solve this. The archive records a stream to disk and can play any part of it back later. The cluster runs the same program on several machines and keeps them in agreement, so if one dies another carries on with identical state. The idea is simple: if every copy starts empty and processes the same messages in the same order, all copies end in the same state. That only works if the program's logic is deterministic. A call to the system clock or a random number would make the copies diverge.

Read [chapter 05](/tech/series/rust-aeron/05.aeron-transport-and-logbuffers/) first. For the agreement protocol, see [consensus and Raft](/tech/series/data-systems/06.consensus-and-raft/).

Terms used in this chapter:

- **archive**: the Aeron component that records streams to disk and replays them.
- **recording**: one stored stream, described by a recording descriptor in a catalog file.
- **replay**: reading a recorded byte range back as a new stream.
- **SBE**: Simple Binary Encoding, a fixed-layout binary format used for the archive's records.
- **cluster**: several nodes running the same service and agreeing on the order of inputs.
- **Raft**: a consensus algorithm that elects a leader and replicates an ordered log to followers.
- **replicated state machine**: a program whose state depends only on the ordered inputs it has processed, so identical inputs give identical state.
- **deterministic**: producing the same output for the same input every time, with no clock, randomness or other hidden input.
- **snapshot**: a saved copy of the service state, so recovery need not replay the whole log.

## 1. Aeron Archive — Zero-Translation Stream Recording & `catalog.dat`

Why can `aeron-archive` record millions of messages per second to NVMe storage with almost zero CPU overhead?
**Because the bytes inside a live Aeron Term Buffer are *already* formatted as 32-byte-aligned `DataHeaderFlyweight` frames!** Recording a stream is literally copying contiguous aligned spans from a `Subscription`'s term buffer straight into on-disk segment files (`<recording_id>-<segment_base_position>.rec`).

### The 80-Byte SBE `RecordingDescriptor` & `Catalog` (`crates/archive/`)

In `harus-aeron-rs/crates/archive/src/protocol/recording_descriptor.rs`, every recorded stream is indexed in `catalog.dat` by a **Simple Binary Encoding (SBE) Template 22 `RecordingDescriptor`**. Its fixed block is exactly **80 bytes (`RecordingDescriptor::BLOCK_LENGTH = 80`)**, followed by three length-prefixed ASCII strings:

| Byte Offset | Field | Type | Meaning |
| :---: | :--- | :---: | :--- |
| `0..8` | `control_session_id` | `i64` | Control session that queried/owns the descriptor |
| `8..16` | `correlation_id` | `i64` | Request correlation ID |
| `16..24` | `recording_id` | `i64` | Sequential ID allocated by `CatalogHeader.next_recording_id` |
| `24..32` | `start_timestamp` | `i64` | Millisecond timestamp when recording started |
| `32..40` | `stop_timestamp` | `i64` | Millisecond timestamp when stopped (`NULL_TIMESTAMP = -1` while active) |
| `40..48` | `start_position` | `i64` | Exact initial stream byte position (`compute_position`) |
| `48..56` | `stop_position` | `i64` | Final stream byte position (`NULL_POSITION = -1` while active!) |
| `56..60` | `initial_term_id` | `i32` | Stream's initial term ID |
| `60..64` | `segment_file_length` | `i32` | Max bytes per `.rec` segment file (multiple of `term_buffer_length`) |
| `64..68` | `term_buffer_length` | `i32` | Power-of-two term length (e.g., 16 MB) |
| `68..72` | `mtu_length` | `i32` | Wire MTU length |
| `72..76` | `session_id` | `i32` | Aeron stream `session_id` |
| `76..80` | `stream_id` | `i32` | Aeron stream `stream_id` |
| `80+` | `stripped_channel`, `original_channel`, `source_identity` | `[u32 len + ASCII]` | Variable-length channel metadata |

Look at why separating the **80-byte fixed block** from the variable-length strings at the end is a classic SBE optimization: when `ArchiveConductor` scans thousands of recordings in `catalog.dat` looking for a matching `(stream_id, session_id)` or `[start_position, stop_position]`, it checks fixed-offset 32-bit/64-bit integers at offsets `40..80` in a single cache line without parsing a single string!

### `ReplayCursor` Modes & Late-Joining Subscribers (`runtime.rs`)

Once a stream is recorded in `aeron-archive`, a late-joining subscriber or recovering cluster follower can request a **Replay** over a standard Aeron channel (`ReplayCursor` in `crates/archive/src/service/runtime.rs`):

1. **Bounded Historical Replay (`length > 0`):** Replays exact byte range `[position, position + length)` from closed or active `.rec` segments and closes the replay publication cleanly.
2. **Live Follow Replay (`length == -1`):** Starts replaying from historical disk segments and seamlessly follows the live active recording as new bytes are appended (`ReplayMerge` uses this to catch a lagging subscriber up from disk Archive to live UDP multicast without dropping or duplicating a single frame!).
3. **Extending & Truncating Recordings:** If a publisher restarts, `ExtendRecording` validates that the new stream's `(initial_term_id, term_id, term_offset)` matches the stopped recording's exact `stop_position` before appending to the same `recording_id`.

## 2. Aeron Cluster — Consensus, `node-state.dat` & `recording.log`

How does **Aeron Cluster** (`harus-aeron-rs/crates/cluster/` and the Spring Boot/Aeron node pair in `sakuranbo`) turn a 3- or 5-node cluster into a fault-tolerant, linearizable state machine?

```text
Client Ingress (Orders / Commands)
       │
       ▼
┌──────────────────────────────────────────────────────────────────────┐
│ Leader ConsensusModule (Raft Quorum: (N / 2) + 1)                    │
│   1. Assigns monotonic leadership_term_id, log_position & cluster_ts │
│   2. Appends to Log Publication ──► Replicated to Follower Archives  │
│   3. Advances Commit Position Counter once majority Archive ACKs!    │
└──────────────────────────────────┬───────────────────────────────────┘
                                   │ (Reads only up to Commit Position)
                                   ▼
┌──────────────────────────────────────────────────────────────────────┐
│ ClusteredService (Deterministic State Machine on Every Node)         │
│   • Executes on_session_message(session, timestamp, buf) in exact    │
│     log_position order using injected cluster_ts                     │
│   • Emits responses to Client Egress channel                         │
└──────────────────────────────────────────────────────────────────────┘
```

### The Two Crash-Recovery Files on Disk (`node-state.dat` & `recording.log`)

As emphasized in Chapter 11 of `harus-aeron-rs/docs/tutorial/11-cluster-consensus-failover.md`, when a cluster node restarts at 3 AM after a power loss or leader failover, its entire recovery truth lives in two flat binary files:

1. **`node-state.dat` (`crates/cluster/src/node_state.rs`):**
   - Header: 8-byte ASCII magic **`AERONNS1`** + `version: u32`.
   - Body: Three 64-bit integers: **`(candidate_term_id, log_position, timestamp_ms)`**.
   - **Monotonicity Invariant:** `NodeStateFile::propose_max_candidate_term_id` only overwrites `node-state.dat` when `proposed_term > current_candidate_term_id`. Even across hard crashes, a node can **never** double-vote in the same Raft election term or regress its term Fencing Token!
2. **`recording.log` (`crates/cluster/src/recording_log.rs`):**
   - An append-only ledger of `RecordingLogEntry` rows tracking every committed **Leadership Term (`ENTRY_TYPE_TERM = 0`)** and **State Machine Snapshot (`ENTRY_TYPE_SNAPSHOT = 1`)**:
     - `(recording_id, leadership_term_id, term_base_log_position, log_position, timestamp, service_id, entry_type, is_valid)`
   - **How Recovery Uses `recording.log`:** When a node recovers, it scans `recording.log` for the latest valid `ENTRY_TYPE_SNAPSHOT`, loads that snapshot from `aeron-archive` to restore the in-memory state machine up to `snapshot.log_position`, and then replays all subsequent `ENTRY_TYPE_TERM` Archive recordings from `snapshot.log_position` to the cluster's committed `log_position`!

## 3. The Golden Rule of `ClusteredService`: Strict Determinism

Why can an Aeron Cluster sustain a far higher command rate than a typical distributed-transaction database? (Measure your own workload; the gap depends on hardware, message size and fsync policy.)
Because Aeron Cluster replicates the **compact input command log** *before* execution, and every node's `ClusteredService` executes the business logic independently in RAM (**Replicated State Machine**)!

For all replicas (`Leader`, `Follower 1`, `Follower 2`)—and any future node replaying the Archive log 6 months later—to arrive at the **exact same byte-for-byte state**, your `ClusteredService` code must obey five strict determinism rules:

| Hazard in `ClusteredService` | Why It Breaks State Machine Replication | The Deterministic Fix |
| :--- | :--- | :--- |
| **`Instant::now()` / `SystemTime::now()`** | Leader and Followers execute the command a few hundred microseconds apart; wall clocks differ! | Always read the **Leader-assigned `timestamp`** passed into `on_session_message(..., timestamp)` (stamped into the log header before replication)! |
| **`rand::thread_rng()` / `UUID::new_v4()`** | Every node generates a different random number or UUID! | Seed a deterministic PRNG (`ChaCha8Rng::seed_from_u64`) from the log's `leadership_term_id ^ log_position`. |
| **Standard `HashMap` Iteration Order** | Rust's default `std::collections::HashMap` uses random per-process SipHash seeds (`RandomState`) for DoS protection—iterating `map.iter()` visits keys in a **different order on every node**! | Use **`BTreeMap`** or a `HashMap` with a fixed deterministic `BuildHasher` (`FxHasher` / `IndexMap`) whenever iteration order affects output or snapshots! |
| **Multi-Threaded Worker Mutation** | OS thread scheduling interleavings are non-deterministic across machines. | Keep state-machine mutation strictly **single-threaded** on the `ClusteredService` agent thread. |
| **Direct Blocking HTTP / DB Calls Inside `on_session_message`** | During an Archive replay after a crash, re-executing `on_session_message` would fire duplicate external HTTP webhooks—or fail if the external service is down! | Emit external effects as idempotent **Egress events** keyed by `(leadership_term_id, log_position)` so external gateways deduplicate replays! |

## 4. Verification Lab — `node-state.dat`, `recording.log` Snapshot Recovery & Determinism Verifier

Run this verification script to compile and execute a Rust implementation of `harus-aeron-rs`'s `NodeStateFile` (`AERONNS1` monotonic term guard), `RecordingLog` (`ENTRY_TYPE_TERM` + `ENTRY_TYPE_SNAPSHOT` recovery planner), and a 3-replica deterministic order-matching state machine verifying that Snapshot + Replay produces the exact same state hash as full log execution:

```python
#!/usr/bin/env python3
"""Compile & run a Rust probe of Aeron Cluster node-state.dat, recording.log & deterministic replay."""
import shutil
import subprocess
import tempfile
from pathlib import Path

RUST_SOURCE = r"""
use std::collections::BTreeMap;

const MAGIC: &[u8; 8] = b"AERONNS1";
const ENTRY_TYPE_TERM: u8 = 0;
const ENTRY_TYPE_SNAPSHOT: u8 = 1;

#[derive(Clone, Debug, PartialEq, Eq)]
struct NodeStateFile {
    magic: [u8; 8],
    candidate_term_id: i64,
    log_position: i64,
    timestamp_ms: i64,
}

impl NodeStateFile {
    fn new() -> Self {
        Self {
            magic: *MAGIC,
            candidate_term_id: -1,
            log_position: 0,
            timestamp_ms: 0,
        }
    }

    fn propose_max_candidate_term_id(&mut self, candidate_term_id: i64, log_pos: i64, ts: i64) -> bool {
        assert_eq!(&self.magic, MAGIC, "Corrupt node-state.dat magic!");
        if candidate_term_id > self.candidate_term_id {
            self.candidate_term_id = candidate_term_id;
            self.log_position = log_pos;
            self.timestamp_ms = ts;
            true
        } else {
            false
        }
    }
}

#[derive(Clone, Debug)]
struct RecordingLogEntry {
    recording_id: i64,
    leadership_term_id: i64,
    term_base_log_position: i64,
    log_position: i64,
    timestamp: i64,
    entry_type: u8,
    is_valid: bool,
}

/// Deterministic Clustered Service (uses BTreeMap + injected log timestamp!)
#[derive(Clone, Debug, PartialEq, Eq)]
struct OrderBookService {
    balances: BTreeMap<String, i64>,
    last_cluster_ts: i64,
    applied_log_pos: i64,
}

impl OrderBookService {
    fn new() -> Self {
        Self {
            balances: BTreeMap::new(),
            last_cluster_ts: 0,
            applied_log_pos: 0,
        }
    }

    fn on_log_command(&mut self, log_pos: i64, cluster_ts: i64, account: &str, delta: i64) {
        *self.balances.entry(account.to_string()).or_insert(0) += delta;
        self.last_cluster_ts = cluster_ts;
        self.applied_log_pos = log_pos;
    }
}

fn main() {
    // 1. Verify NodeStateFile monotonic candidate_term_id persistence
    let mut node_state = NodeStateFile::new();
    assert!(node_state.propose_max_candidate_term_id(1, 0, 1000));
    assert!(node_state.propose_max_candidate_term_id(2, 640, 2000));
    assert!(!node_state.propose_max_candidate_term_id(1, 999, 3000)); // Stale term rejected!
    println!("NodeStateFile (AERONNS1)      : candidate_term_id={}, log_pos={}",
        node_state.candidate_term_id, node_state.log_position);

    // 2. Simulate full Cluster Command Log across 2 Leadership Terms + 1 Mid-Stream Snapshot
    let commands = vec![
        (64,  1713480001, "alice", 500),
        (128, 1713480002, "bob",   300),
        (192, 1713480005, "alice", -120), // <-- Snapshot taken right here at log_pos = 192!
        (256, 1713480009, "bob",   120),
        (320, 1713480015, "carol", 900),
    ];

    let recording_log = vec![
        RecordingLogEntry {
            recording_id: 10, leadership_term_id: 1, term_base_log_position: 0,
            log_position: 192, timestamp: 1713480005, entry_type: ENTRY_TYPE_TERM, is_valid: true,
        },
        RecordingLogEntry {
            recording_id: 11, leadership_term_id: 1, term_base_log_position: 0,
            log_position: 192, timestamp: 1713480005, entry_type: ENTRY_TYPE_SNAPSHOT, is_valid: true,
        },
        RecordingLogEntry {
            recording_id: 12, leadership_term_id: 2, term_base_log_position: 192,
            log_position: 320, timestamp: 1713480015, entry_type: ENTRY_TYPE_TERM, is_valid: true,
        },
    ];

    // Replica A: Processes all 5 commands from log_pos = 0
    let mut replica_a = OrderBookService::new();
    let mut snapshot_at_192: Option<OrderBookService> = None;
    for &(pos, ts, acct, delta) in &commands {
        replica_a.on_log_command(pos, ts, acct, delta);
        if pos == 192 {
            snapshot_at_192 = Some(replica_a.clone());
        }
    }

    // Replica B (Recovering Node): Finds latest valid ENTRY_TYPE_SNAPSHOT in recording.log,
    // loads snapshot at log_pos=192, and replays only commands with pos > 192!
    let latest_snap = recording_log
        .iter()
        .rev()
        .find(|e| e.is_valid && e.entry_type == ENTRY_TYPE_SNAPSHOT)
        .expect("Snapshot entry found");
    assert_eq!(latest_snap.log_position, 192);

    let mut replica_b = snapshot_at_192.unwrap();
    let replayed_count = commands
        .iter()
        .filter(|&&(pos, _, _, _)| pos > latest_snap.log_position)
        .map(|&(pos, ts, acct, delta)| replica_b.on_log_command(pos, ts, acct, delta))
        .count();

    println!("Recovering node loaded snap   : recording_id={} at log_pos={}, replayed {} tail commands",
        latest_snap.recording_id, latest_snap.log_position, replayed_count);
    println!("Final deterministic balances  : {:?}", replica_b.balances);
    assert_eq!(replica_a, replica_b);
    assert_eq!(replayed_count, 2);
}
"""

if __name__ == "__main__":
    rustc = shutil.which("rustc")
    assert rustc is not None
    with tempfile.TemporaryDirectory() as tmp:
        src = Path(tmp) / "cluster_probe.rs"
        bin_path = Path(tmp) / "cluster_probe"
        src.write_text(RUST_SOURCE, encoding="utf-8")
        subprocess.run([rustc, "--edition=2021", "-O", str(src), "-o", str(bin_path)], check=True)
        out = subprocess.run([str(bin_path)], capture_output=True, text=True, check=True)
        print(out.stdout.strip())
```

## 5. Series Synthesis — From Stack Bytes to Deterministic Clusters

Across these 6 chapters, we have traced a single unbroken engineering thread:

1. **Chapter 01 (Ownership & Layout):** Single ownership, Move vs. `Copy`, `#[repr(C)]`, and niche optimizations give us deterministic memory layouts with zero GC pauses.
2. **Chapter 02 (Lifetimes & Dispatch):** Lifetimes (`Header<'a>`) verify zero-copy flyweight views over `mmap` buffers, while monomorphization and 16-byte `&dyn Trait` fat pointers let us choose between inlined speed and dynamic flexibility.
3. **Chapter 03 (Interior Mutability & Memory Ordering):** `UnsafeCell<T>` and `Ordering::Release` / `Ordering::Acquire` (`put_i64_ordered` / `get_i64_volatile`) publish shared-memory frames safely across cores without `SeqCst` hardware fence penalties on x86_64.
4. **Chapter 04 (Cache Coherency & Agrona Rings):** 128-byte prefetcher-safe padding and the 768-byte trailer's `HEAD_CACHE_POSITION_OFFSET` (`+256`) eliminate cross-core cache invalidation on 99% of ring buffer writes.
5. **Chapter 05 (Aeron Transport & Three-Term Log Buffers):** Packing `(term_id, term_offset)` into a single 64-bit atomic word lets concurrent publishers claim space in one instruction, while Receiver-driven `SM` windows and `NAK` gap scanners deliver reliable low-latency UDP.
6. **Chapter 06 (Archive & Cluster):** Because wire frames are already 32-byte-aligned log records, `aeron-archive` records and replays streams directly from disk, and `aeron-cluster` drives deterministic replicated state machines (`node-state.dat` + `recording.log`) at high message rates.
