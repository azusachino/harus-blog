Every ultra-low-latency systems project—from high-frequency market data feeds and Aeron messaging drivers (`harus-aeron-rs`) to storage engines and kernel packet processors—faces the same architectural tension:

- **Garbage-Collected Runtimes (Java/Go):** Eliminate manual `free()` bugs, but object headers, pointer chasing, and Stop-the-World or concurrent GC safepoints inject unpredictable tail-latency spikes ($p99.9 > 1\text{--}10\text{ ms}$) unless you manually bypass the heap using off-heap byte buffers (`Unsafe` / Agrona `AtomicBuffer`).
- **C and C++:** Give direct control over stack frames, cache lines, and `mmap` buffers, but leave dangling pointers, double-frees, iterator invalidation, and data races entirely on the programmer's shoulders.

**Rust** resolves this tension by enforcing an affine type system (**Ownership and Borrowing**) entirely at compile time: every value has a deterministic lifetime tied to its stack owner, zero runtime garbage collector exists, and every struct or enum compiles down to an exact, inspectable byte layout.

In **Chapter 01**, we connect Rust's ownership rules directly to the physical stack and heap bytes they govern.

---

## Before you start

This series is for programmers who know one language and basic command-line use, and want to read low-latency Rust, using the `harus-aeron-rs` messaging code as the running example. The chapters build on each other.

Most languages free memory either by hand (C) or with a garbage collector (Java, Go). Rust does neither. Each value has exactly one owner, and when the owner goes out of scope the value is freed, at a point the compiler can see. Try `let a = String::from("hi"); let b = a;` and then print `a`: it will not compile, because ownership moved to `b`. That strictness is what lets Rust avoid double frees and dangling pointers without a collector, and it lets you predict exactly how many bytes a struct takes.

You only need basic Rust syntax. If the C++ side of ownership is new, [Effective C++ chapter 03](/tech/series/effective-cpp/03.resource-management/) covers the same cleanup idea.

Terms used in this chapter:

- **ownership**: the rule that every value has one owner, and the value is dropped when that owner goes out of scope.
- **move**: passing a value to a new owner; the old name can no longer be used.
- **`Copy`**: a marker for simple types such as integers that are duplicated bit for bit instead of moved.
- **borrow**: a reference (`&T` or `&mut T`) that uses a value without taking ownership.
- **aliasing XOR mutability**: at any time you may have many shared references or one mutable reference, never both.
- **stack and heap**: the stack holds fixed-size local values and is freed automatically; the heap holds dynamically sized data.
- **`#[repr(C)]`**: an attribute that fixes a struct's fields in declaration order, like C, instead of letting the compiler reorder them.
- **enum (tagged union)**: a type holding one of several variants, stored as a tag plus the data.

## 1. The Three Laws of Ownership & Stack-Bound Lifetimes

Rust's memory model starts from three compile-time invariants:

1. **Single Owner:** Every value in Rust is owned by exactly one variable (its *owner*).
2. **Exclusive Ownership Transfer (Move):** At any instant, only one owner exists. Assigning a non-`Copy` value to another variable, passing it by value to a function, or returning it transfers ownership (**Move semantics**), statically invalidating the previous variable.
3. **Deterministic Scope Drop (`RAII`):** When the owning variable's stack frame (or enclosing struct) goes out of scope, the compiler automatically inserts a call to `Drop::drop` (`std::ops::Drop`), freeing any owned heap buffer immediately and deterministically.

```text
Stack Frame (24 bytes on 64-bit)               Heap Allocation (jemalloc / system)
┌──────────────────────────────┐               ┌───┬───┬───┬───┬───┬───┬───┬───┐
│ s1: String                   │               │ 'h' 'e' 'l' 'l' 'o' .   .   . │
│   ptr : 0x7f8a_0040_1000 ────┼──────────────►└───┴───┴───┴───┴───┴───┴───┴───┘
│   cap : 8  (usize, 8 bytes)  │
│   len : 5  (usize, 8 bytes)  │
└──────────────────────────────┘
```

### Move vs. `Copy` at the Machine-Word Level

Wait: at runtime in generated x86_64 or ARM64 assembly, what is the difference between **Moving** a `String` (`let s2 = s1;`) and **Copying** a `[u64; 3]` (`let a2 = a1;`)?

- **At the hardware instruction level, both are a 24-byte `memcpy` on the stack!** Moving `s1` into `s2` never copies the heap bytes `"hello"`; it merely copies the 24-byte stack header `(ptr, cap, len)` into `s2`.
- **The difference is purely compile-time validity:**
  - If `s1` remained usable after `let s2 = s1;`, both `s1` and `s2` would point to `0x7f8a_0040_1000` and both would call `free(0x7f8a_0040_1000)` at the end of the block (**Double Free UB**). Therefore, for any type that owns a resource (`Drop`) or opts out of `Copy`, the compiler marks `s1` as uninitialized after the 24-byte stack copy (**Move**).
  - If a type is a plain value with no owned heap destructor—scalars (`i32`, `u64`, `f64`, `bool`, `char`), immutable references (`&T`), raw pointers (`*const T`, `*mut T`), function pointers (`fn()`), and fixed-size arrays/tuples thereof (`[u8; 4]`, `(&str, usize)`)—it implements the marker trait **`Copy`**, allowing the source variable to remain live after a bitwise stack copy.

> **Why `&mut T` Is NEVER `Copy`:** Notice that shared references `&T` implement `Copy` (you can duplicate read-only pointers freely), whereas exclusive mutable references `&mut T` **do not implement `Copy`**! If `&mut T` were `Copy`, a single line `let r2 = r1;` would create two simultaneous mutable aliases to the same memory address, violating Rust's core safety invariant.

## 2. Aliasing XOR Mutability — The Hardware & Reallocation Proof

Rust's borrow checker enforces **Read-Write Lock (`RwLock`) semantics at compile time**:

- You may have **any number of shared immutable references (`&T`)** simultaneously, **OR**
- **Exactly one exclusive mutable reference (`&mut T`)**, never both in overlapping live scopes.

Why is a harmless-looking shared reference `&v[0]` forbidden while calling `v.push(42)` on the same thread? Let's trace what happens in physical memory when a `Vec<i32>` grows past its capacity:

```text
1. Before v.push(): v has len=1, cap=1 at old heap address 0x1000
   let elem_ref: &i32 = &v[0];  ──► Points to 0x1000

2. During v.push(2): len == cap, so allocator:
   a) Allocates new heap buffer (cap=2) at 0x9000
   b) Copies v[0] from 0x1000 -> 0x9000
   c) FREES old heap buffer at 0x1000!

3. If elem_ref (&v[0]) were still allowed to be read:
   *elem_ref dereferences freed address 0x1000 ──► USE-AFTER-FREE!
```

Beyond preventing iterator invalidation and vector reallocation crashes, **Aliasing XOR Mutability** unlocks a major compiler optimization (`LLVM noalias`):

- In C and C++, unless you manually annotate pointers with `restrict`, the compiler must conservatively assume that two pointers `int *a` and `int *b` might point to overlapping addresses, forcing it to reload values from memory on every loop iteration instead of keeping them in CPU registers or auto-vectorizing with SIMD.
- In Rust, every `&mut T` and `&T` is emitted to LLVM IR with the **`noalias`** attribute by default!

## 3. Struct Alignment, Field Reordering & `#[repr(C)]`

Modern CPUs do not read memory one arbitrary byte at a time; they fetch aligned words (`2`, `4`, `8`, or `16` bytes) across cache lines. A type of alignment $A$ must be stored at a memory address that is a multiple of $A$ ($\text{addr} \bmod A == 0$), and the total `size_of::<T>()` is always rounded up to a multiple of `align_of::<T>()`.

### C Layout (`#[repr(C)]`) vs. Rust Default Layout (`#[repr(Rust)]`)

Suppose we declare a struct with mixed-width integer fields:

```rust
#[repr(C)]
struct CLayout {
    a: u8,   // offset 0 (1 byte) + 1 byte padding so `b` lands on an even address!
    b: u16,  // offset 2 (2 bytes, align 2)
    c: u8,   // offset 4 (1 byte) + 1 byte trailing padding so total size is a multiple of 2!
}            // Total size = 6 bytes, align = 2

struct RustDefaultLayout {
    a: u8,
    b: u16,
    c: u8,
}            // rustc is free to reorder fields (in practice to [b: u16, a: u8, c: u8]); the layout is unspecified!
             // Total size = 4 bytes, align = 2 (Zero padding bytes wasted!)
```

- **When to use default `#[repr(Rust)]`:** For all ordinary application and library structs. The compiler sorts fields by decreasing alignment to eliminate internal padding holes automatically.
- **When you MUST use `#[repr(C)]` or `#[repr(transparent)]`:**
  1. **FFI & C ABI Interop:** Passing structs across C boundaries or Linux kernel `io_uring` / `bpf` syscalls.
  2. **Zero-Copy Shared-Memory & Wire Flyweights (`harus-aeron-rs`):** When mapping an Aeron `DataHeaderFlyweight` or `CatalogHeader` over a memory-mapped file or network buffer, field offsets are fixed by protocol specification (`term_offset` *must* be at byte offset 8, `session_id` at offset 12). Allowing the compiler to reorder fields would scramble the wire protocol!

## 4. Tagged Unions (`enum`) & Compiler Niche Optimizations

In Java or Python, wrapping a value in `Optional<T>` or a sum type allocates a separate heap box header. In Rust, an `enum` is an inline **Tagged Union**: its size is the size of its largest variant plus a small discriminant tag (rounded up to alignment).

Even better, when the inner type has **invalid bit patterns ("Niches")**, the Rust compiler stores the `enum` discriminant **inside the unused bit pattern for free (`0` extra bytes!)**:

| Type `T` | `size_of::<T>()` | `size_of::<Option<T>>()` | Why? |
| :--- | :---: | :---: | :--- |
| `u64` | `8 B` | `16 B` | Every 64-bit integer (`0..=u64::MAX`) is valid; needs a 1-byte tag + 7 bytes alignment padding. |
| `NonZeroU64` | `8 B` | **`8 B`** | `0` is illegal for `NonZeroU64`, so `Option::None` is represented as `0x0000_0000_0000_0000`! |
| `&T` / `&mut T` / `Box<T>` | `8 B` | **`8 B`** | Safe Rust references and `Box<T>` are backed by `NonNull<T>` (never `0x0`); `None` uses the NULL pointer `0x0`! |
| `String` / `Vec<T>` | `24 B` | **`24 B`** | Their internal heap pointer is `NonNull<u8>`, so `Option<String>` and `Option<Vec<T>>` remain 24 bytes! |

> **Enum Bloat Pitfall in Production:** Because an `enum`'s size equals its **largest variant**, if `enum Event` has a frequently used 8-byte `Tick(u64)` variant and a rarely used 512-byte `Snapshot([u8; 512])` variant, **every single `Event::Tick` in a `Vec<Event>` consumes 520 bytes of RAM!** Boxing the cold oversized payload (`Snapshot(Box<[u8; 512]>)`) shrinks the entire `enum` from 520 bytes down to **16 bytes**, fitting 4 events per 64-byte CPU cache line.

## 5. Verification Lab — Proving `Vec` Reallocation, Alignment Reordering & Niche Sizes

Save and run this verification script (which compiles and runs a real `rustc` binary when `rustc` is available, or verifies the exact layout rules in Python) to inspect stack/heap pointers, struct field reordering, and `Option<T>` niche optimizations:

```python
#!/usr/bin/env python3
"""Compile & run a real rustc memory-layout probe (with standalone layout verification)."""
import shutil
import subprocess
import tempfile
from pathlib import Path

RUST_SOURCE = r"""
#![allow(dead_code)]
use std::mem::{align_of, offset_of, size_of};
use std::num::NonZeroU64;

#[repr(C)]
struct CRepr {
    a: u8,
    b: u16,
    c: u8,
}

struct RustRepr {
    a: u8,
    b: u16,
    c: u8,
}

enum UnboxedEvent {
    Tick(u64),
    LargePayload([u8; 256]),
}

enum BoxedEvent {
    Tick(u64),
    LargePayload(Box<[u8; 256]>),
}

fn main() {
    // 1. Prove Vec reallocation changes heap address (why &v[0] + v.push() is forbidden)
    let mut v: Vec<i32> = Vec::with_capacity(1);
    v.push(10);
    let _neighbor_heap_alloc = vec![0xABCD_u64; 32]; // Prevents in-place wilderness realloc
    let old_ptr = v.as_ptr();
    for i in 0..64 {
        v.push(i);
    }
    let new_ptr = v.as_ptr();
    println!("Vec heap reallocation : old_ptr={:p}, new_ptr={:p}, cap={}", old_ptr, new_ptr, v.capacity());
    assert_ne!(old_ptr, new_ptr, "Heap buffer moved on growth!");
    assert_eq!(_neighbor_heap_alloc[0], 0xABCD);

    // 2. Prove #[repr(C)] vs #[repr(Rust)] automatic field reordering
    println!(
        "#[repr(C)]    CRepr   : size={}B, align={}B, offsets=(a:{}, b:{}, c:{})",
        size_of::<CRepr>(), align_of::<CRepr>(),
        offset_of!(CRepr, a), offset_of!(CRepr, b), offset_of!(CRepr, c)
    );
    println!(
        "#[repr(Rust)] RustRepr: size={}B, align={}B, offsets=(a:{}, b:{}, c:{})",
        size_of::<RustRepr>(), align_of::<RustRepr>(),
        offset_of!(RustRepr, a), offset_of!(RustRepr, b), offset_of!(RustRepr, c)
    );
    assert_eq!(size_of::<CRepr>(), 6);
    assert_eq!(size_of::<RustRepr>(), 4);

    // 3. Prove Niche Optimization & Enum Boxing
    println!("Niche Optimization    : u64={}B vs Option<u64>={}B | NonZeroU64={}B vs Option<NonZeroU64>={}B",
        size_of::<u64>(), size_of::<Option<u64>>(),
        size_of::<NonZeroU64>(), size_of::<Option<NonZeroU64>>()
    );
    println!("Reference & Vec Niche : &u8={}B vs Option<&u8>={}B | Vec<u8>={}B vs Option<Vec<u8>>={}B",
        size_of::<&u8>(), size_of::<Option<&u8>>(),
        size_of::<Vec<u8>>(), size_of::<Option<Vec<u8>>>()
    );
    println!("Enum Tail-Size Bloat  : UnboxedEvent={}B vs BoxedEvent={}B",
        size_of::<UnboxedEvent>(), size_of::<BoxedEvent>()
    );
    assert_eq!(size_of::<Option<NonZeroU64>>(), 8);
    assert_eq!(size_of::<Option<&u8>>(), 8);
    assert_eq!(size_of::<Option<Vec<u8>>>(), 24);
    assert_eq!(size_of::<BoxedEvent>(), 16);
}
"""

if __name__ == "__main__":
    rustc = shutil.which("rustc")
    assert rustc is not None, "rustc is required to compile the verification probe"
    with tempfile.TemporaryDirectory() as tmp:
        src = Path(tmp) / "probe.rs"
        bin_path = Path(tmp) / "probe"
        src.write_text(RUST_SOURCE, encoding="utf-8")
        subprocess.run([rustc, "--edition=2021", "-O", str(src), "-o", str(bin_path)], check=True)
        out = subprocess.run([str(bin_path)], capture_output=True, text=True, check=True)
        print(out.stdout.strip())
```
