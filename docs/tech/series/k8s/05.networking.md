Networking in Kubernetes is notoriously intimidating. An incoming packet traverses physical NICs, host Linux routing tables, bridge devices, virtual ethernet (veth) pairs, packet filtering chains, and userspace proxies before finally arriving at an application socket.

Yet despite this perceived complexity, the entire networking subsystem is anchored by **four foundational rules**. Once you understand how these rules are implemented—and how the ecosystem evolved from brittle `iptables` and messy `Ingress` annotations to **`nftables`** and the modern **Gateway API**—the architecture is much easier to follow.

---

## Before you start

Pods come and go, and each new pod gets a new IP address. So how does the frontend find the backend? This chapter explains the rules Kubernetes sets for pod networking, the stable addresses called Services, name lookup through DNS, and how traffic from outside gets in.

A small case: your backend pods are at 10.1.0.5 and 10.1.0.9 today, and next week they will be different addresses. You create a Service named `backend`. The frontend just calls `http://backend`, DNS turns the name into one fixed virtual IP, and the node rewrites packets headed for that IP to one of the live pods.

Read [chapter 4](/tech/series/k8s/04.workloads/) first for pods. If IP addresses and ports are new to you, the [How Networks Work series](/tech/series/network/03.ip-ethernet/) explains them.

Terms used in this chapter:

- **Pod IP**: the address each pod gets; any pod can reach any other pod directly.
- **Service**: a stable virtual IP and name in front of a changing set of pods.
- **kube-proxy**: the node component that programs packet rules so Service addresses reach real pods.
- **nftables / iptables**: Linux packet-filtering rule systems; kube-proxy can use either.
- **CNI**: the Container Network Interface, the plugin standard for giving pods network connectivity.
- **CoreDNS**: the cluster's DNS server, answering names like `backend.default.svc.cluster.local`.
- **ndots**: a resolver setting; a name with fewer dots than this number is tried with each search suffix appended first, and only then as written.
- **Ingress / Gateway API**: Kubernetes objects for routing outside HTTP traffic to Services; Gateway API is the newer design.

## 1. The Fundamental Kubernetes Network Contract

Kubernetes imposes strict, clean constraints on any Container Network Interface (CNI) implementation:

1. **Every Pod has a unique, routable IP address**: There is no port mapping or NAT between pods.
2. **All Pods can communicate with all other Pods across all nodes directly without NAT**.
3. **All Nodes can communicate with all Pods (and vice-versa) directly without NAT**.
4. **The IP that a Pod sees itself as is the exact same IP that all other Pods see it as**.

This model completely eliminates the port-allocation nightmare of legacy microservices: two different pods on the same node can both bind to `:8080` without colliding, because each lives in an isolated network namespace (`netns`) with its own independent IP.

### CNI Implementations: Overlay vs. Direct Routing

- **Overlay Networks (e.g. Flannel VXLAN, Calico VXLAN)**: Encapsulate Pod L2/L3 packets inside UDP datagrams over the physical network. Easy to set up in cloud environments where the underlying network is opaque, but incurs minor packet header overhead and CPU serialization costs.
- **Direct Flat Routing (e.g. Calico BGP, Cilium with native routing)**: Uses BGP or Linux kernel eBPF to route Pod CIDRs natively over physical top-of-rack switches. No encapsulation overhead, so throughput is close to the underlying network.

## 2. Service Abstraction & kube-proxy: The nftables Shift

Pod IPs are ephemeral: when a pod crashes or rolls over, its IP vanishes. The **`Service`** abstraction creates a stable, virtual IP (**ClusterIP**) that load-balances traffic across a dynamic set of backend pod endpoints.

`kube-proxy` is the daemon responsible for programming this virtual routing logic into the host kernel. its internal engine has gone through several generations:

```text
[ kube-proxy Generational Evolution ]
1. Userspace Mode (Early K8s) ──> Context-switch between kernel & user proxy for every packet (Terrible latency)
2. iptables Mode (1.2+)         ──> Kernel Netfilter chains. O(N) sequential rule traversal (slow at scale)
3. IPVS Mode (GA 1.11)          ──> Kernel IP Virtual Server hash tables. O(1) lookups; recent releases deprecate it
4. nftables Mode (beta 1.31, GA 1.33) ──> Native tables, sets and verdict maps, atomic rule updates
```

### Why iptables Broke at Scale

In clusters with thousands of Services and Endpoints, `iptables` generated tens of thousands of linear sequential rules. Every time a single pod started or stopped, `kube-proxy` had to rewrite and flush the entire iptables rule blob atomically in the kernel.

Modern Kubernetes features the **`nftables` backend**:

- Replaces sequential chains with structured **sets and maps**, delivering $O(1)$ routing lookups.
- Supports incremental, atomic rule updates without freezing network traffic.

```bash
# Inspect kube-proxy's verdict maps and service endpoints in the kernel nftables table
nft list table ip kube-proxy
```

## 3. CoreDNS & The ndots:5 Latency Pitfall

Kubernetes deploys **CoreDNS** as an internal cluster DNS service. When Pod A requests `http://backend-service`, the DNS resolver resolves it to `10.96.0.45` (ClusterIP) based on the standard FQDN schema:

$$\text{<service-name>}.\text{<namespace>}.\text{svc}.\text{cluster}.\text{local}$$

### The `ndots:5` Hazard

If you inspect `/etc/resolv.conf` inside any Kubernetes container, you will find:

```text
nameserver 10.96.0.10
search default.svc.cluster.local svc.cluster.local cluster.local
options ndots:5
```

The `ndots:5` directive means: *If a requested domain name contains fewer than 5 dots, the resolver will append each local search domain sequentially before attempting an external query*.

When your application queries an external domain like `api.stripe.com` (which has 2 dots):

1. Query 1: `api.stripe.com.default.svc.cluster.local` (Fails / NXDOMAIN)
2. Query 2: `api.stripe.com.svc.cluster.local` (Fails / NXDOMAIN)
3. Query 3: `api.stripe.com.cluster.local` (Fails / NXDOMAIN)
4. Query 4: `api.stripe.com` (Succeeds!)

For every single outbound HTTP call, **three unnecessary DNS queries reach CoreDNS** (doubled again when A and AAAA are both asked), adding latency.

**Production Fix**: Always append a trailing dot to external URLs in microservice configs (`api.stripe.com.`) to tell the resolver it is already a fully qualified absolute domain, bypassing the search list. Lowering `ndots` per Pod (`dnsConfig.options: [{name: ndots, value: "2"}]`) is the other common fix.

## 4. The Gateway API

For years, getting external HTTP/HTTPS traffic into a cluster relied on the legacy **`Ingress`** resource:

```text
[ Why Legacy Ingress Failed ]
1. Anemic Core Spec: No native support for header rewrites, traffic splitting, canary rollouts, or gRPC.
2. Annotation Sprawl: Vendors invented custom strings ("nginx.ingress.kubernetes.io/rewrite-target").
3. Monolithic Role Bleed: A single YAML mixed cluster TLS secrets, port bindings, and app route paths.
```

### Enter Gateway API (`gateway.networking.k8s.io`)

The **Gateway API** is an expressive, role-oriented, vendor-neutral routing standard that explicitly splits responsibilities among three distinct organizational personas:

<Archify src="./diagrams/k8s-gateway-routing.workflow.json" />

1. **Infrastructure Provider (`GatewayClass`)**: Defines the controller implementation (e.g. Envoy Gateway, Cilium, Traefik).
2. **Cluster Operator (`Gateway`)**: Defines where external traffic enters the cluster: IP addresses, exposed ports (80/443), and TLS certificates. The app developer never needs access to these sensitive credentials.
3. **Application Developer (`HTTPRoute` / `GRPCRoute`)**: Defines routing rules: path prefixes, header matches, percentage-based canary traffic splits, and backend service targets.

### Modern Gateway + HTTPRoute Example

First, the **Cluster Operator** provisions the shared `Gateway` terminating TLS in the `infra` namespace, explicitly permitting `HTTPRoute` attachments from application namespaces:

```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: production-gateway
  namespace: infra
spec:
  gatewayClassName: cilium
  listeners:
    - name: https-api
      protocol: HTTPS
      port: 443
      hostname: "api.example.com"
      tls:
        mode: Terminate
        certificateRefs:
          - kind: Secret
            name: example-com-tls
      allowedRoutes:
        namespaces:
          from: Selector
          selector:
            matchLabels:
              networking/gateway-access: "true"
```

Next, the **Application Developer** binds an `HTTPRoute` in the `ecommerce` namespace to `production-gateway` without ever touching cluster TLS secrets:

```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: order-service-routes
  namespace: ecommerce
spec:
  parentRefs:
    - name: production-gateway # Attaches cleanly to the cluster-level Gateway
      namespace: infra
  hostnames:
    - "api.example.com"
  rules:
    - matches:
        - path:
            type: PathPrefix
            value: /v2/orders
          headers:
            - name: X-Beta-Tester
              value: "true"
      backendRefs:
        # 20% of matching (beta-header) requests go to the v2 backend
        - name: order-service-v2
          port: 8080
          weight: 20
        - name: order-service-v1
          port: 8080
          weight: 80
```

With Gateway API, canary rollouts, cross-namespace routing, and header-based traffic engineering are standard Kubernetes declarations rather than controller-specific annotations.
