Running Kubernetes in a homelab or on bare-metal hosts teaches the fundamental mechanics of Linux containers, networking, and storage. But taking Kubernetes into production on a hyperscale cloud provider like AWS shifts the engineering challenge: you no longer build control planes from scratch—you **integrate the declarative Kubernetes kernel with managed cloud primitives**.

In this chapter, we dissect the internal architecture of Amazon Elastic Kubernetes Service (EKS), explore the paradigm shift in node provisioning introduced by **Karpenter**, trace the evolution of cloud identity from IRSA to **EKS Pod Identity**, and solve real-world network and storage constraints at cloud scale.

---

## Before you start

Most teams do not run their own control plane; they rent one. EKS is Amazon's managed Kubernetes. This chapter is about what changes when the cluster lives in AWS: how nodes are added and removed, how pods get AWS permissions, how pod IP addresses fit into a cloud network, and how disks attach.

The tension is easy to see. Kubernetes thinks in pods; AWS thinks in virtual machines, IAM roles and network interfaces. Much of the work is mapping one onto the other, for instance giving one pod permission to read one S3 bucket without handing that permission to every pod on the machine.

Read [chapter 5](/tech/series/k8s/05.networking/) for pod networking. The [AWS series chapter on compute](/tech/series/aws-sap/04.cloud-native-compute-karpenter/) covers the same ground from the exam's angle.

Terms used in this chapter:

* **EKS**: Elastic Kubernetes Service, where AWS runs the control plane for you.
* **Karpenter**: an autoscaler that launches nodes directly when pods cannot be scheduled.
* **Cluster Autoscaler**: the older autoscaler that resizes predefined groups of nodes.
* **IAM role**: an AWS identity with a set of permissions.
* **IRSA / Pod Identity**: mechanisms for giving a pod its own IAM role.
* **VPC CNI**: the AWS plugin that gives each pod a real address from the VPC network.
* **Prefix delegation**: assigning whole blocks of addresses to a node's network interface so it can host more pods.
* **CSI driver**: a plugin that lets Kubernetes use a storage system; EBS gives block disks, EFS gives shared file storage.

## 1. Under the Hood of AWS EKS

Amazon EKS provides a managed, single-tenant Kubernetes control plane. It does not run inside your own AWS VPC; instead, it spans two isolated VPCs:

```text
┌────────────────────────────────────────────────────────┐
│ AWS-Managed Control Plane VPC                          │
│                                                        │
│  [ kube-apiserver ]  [ kube-controller-manager ]       │
│           │                       │                    │
│           ▼                       ▼                    │
│  [ etcd Instance 1 ]  [ etcd 2 ]  [ etcd 3 ] (Multi-AZ)│
└───────────────────────────┬────────────────────────────┘
                            │ Cross-Account
                            │ Managed ENIs
                            ▼
┌────────────────────────────────────────────────────────┐
│ Customer Data Plane VPC                                │
│                                                        │
│  [ Worker Node A ]    [ Worker Node B ] (EC2 / Spot)   │
│   ├─ kubelet           ├─ kubelet                      │
│   └─ containerd        └─ containerd                   │
└────────────────────────────────────────────────────────┘
```

### The Cross-Account ENI Architecture

To allow the managed `kube-apiserver` to communicate with worker nodes (for commands like `kubectl exec`, `logs`, and admission webhooks), AWS provisions **cross-account Elastic Network Interfaces (ENIs)** directly inside your designated customer subnets.

* Traffic between the API server and worker nodes travels through these managed ENIs over private AWS network backbones.
* Control plane components (etcd, controller-manager, scheduler) run across three distinct Availability Zones (AZs) behind an AWS Network Load Balancer (NLB) with automated failover and continuous snapshotting.
* The customer is solely responsible for managing the **data plane**: compute capacity, worker node lifecycle, IAM RBAC boundaries, and pod networking.

## 2. Compute Orchestration: Karpenter vs. Legacy Cluster Autoscaler

For years, Kubernetes autoscaling on AWS was handled by the **Cluster Autoscaler**. However, Cluster Autoscaler was fundamentally constrained because it did not speak AWS natively; it could only increment the desired capacity of static **EC2 Auto Scaling Groups (ASGs)**.

### The Limitations of Auto Scaling Groups

1. **Slow Provisioning**: When a pod enters `Pending`, Cluster Autoscaler must simulate scheduling, find a matching ASG, update desired capacity, wait for EC2 to launch the instance, wait for userdata to run, and wait for `kubelet` registration. The whole chain commonly takes several minutes.
2. **Homogeneous Node Pools**: An ASG is locked to identical or similar instance configurations. Running mixed workloads (e.g., small web servers, memory-heavy caches, and GPU inference models) requires maintaining dozens of separate ASGs.
3. **Capacity Inefficiencies**: ASGs cannot intelligently bin-pack heterogeneous pods into the cheapest available Spot or Graviton instances on the fly.

### The Karpenter Paradigm: Group-less, JIT Node Provisioning

**Karpenter** bypasses Auto Scaling Groups completely. It is an open-source, high-performance node autoscaler that talks directly to the AWS EC2 `CreateFleet` and `DescribeInstanceTypes` APIs.

```yaml
apiVersion: karpenter.sh/v1
kind: NodePool
metadata:
  name: general-compute
spec:
  template:
    spec:
      requirements:
        - key: kubernetes.io/arch
          operator: In
          values: ["arm64", "amd64"]
        - key: karpenter.sh/capacity-type
          operator: In
          values: ["spot", "on-demand"]
        - key: karpenter.k8s.aws/instance-category
          operator: In
          values: ["c", "m", "r"]
      nodeClassRef:
        group: karpenter.k8s.aws
        kind: EC2NodeClass
        name: default-linux
  disruption:
    consolidationPolicy: WhenEmptyOrUnderutilized
    consolidateAfter: 1m
```

When pods enter a `Pending` state, Karpenter calculates the exact aggregate CPU, memory, architecture, and topology requirements of the unscheduled pods. It then performs **real-time bin-packing**, selects the most cost-effective instance type from hundreds of available EC2 offerings (favoring Graviton ARM64 and Spot capacity-optimized pools), and requests the instance directly from EC2, which typically gets a node registered in about a minute or less.

Furthermore, Karpenter continuously monitors running nodes: if it determines that several underutilized nodes can be consolidated onto a single smaller instance to reduce cost, it automatically drains and terminates them.

## 4. Cloud-Native Identity Evolution: IRSA to EKS Pod Identity

Pods frequently require access to native cloud resources: writing objects to Amazon S3, reading parameters from AWS Secrets Manager, or sending events to Amazon SQS.

How should a container authenticate against AWS APIs?

### The Historical Evolution

1. **Hardcoded Access Keys (Anti-Pattern)**: Storing `AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY` in Kubernetes Secrets. If a container is compromised or secrets leak in git, credentials remain valid indefinitely until manually rotated.
2. **Node Instance Roles (Dangerous)**: Attaching broad IAM permissions directly to the EC2 worker node's IAM instance profile. **Every single Pod** on that node can query the Instance Metadata Service (`169.254.169.254`) and inherit whatever the node role allows.
3. **IAM Roles for Service Accounts (IRSA)**: Introduced in 2019, IRSA federated Kubernetes with AWS IAM using OpenID Connect (OIDC). The API server signs a JWT token for the ServiceAccount; the container exchanges this token with AWS STS for temporary IAM credentials via `AssumeRoleWithWebIdentity`.

### Modern Standard: EKS Pod Identity

While IRSA solved credential isolation, it added operational work: every cluster needs its own IAM OIDC identity provider, and IAM trust policies had to hardcode specific cluster OIDC issuer URLs and ServiceAccount names.

**EKS Pod Identity** (introduced in late 2023) removes the per-cluster OIDC provider and the issuer URLs in trust policies:

```text
[ Application Pod ]
         │
         │ Calls AWS SDK (GetCallerIdentity / S3 PutObject)
         ▼
[ EKS Pod Identity Agent ] (DaemonSet on Node via link-local proxy)
         │
         │ Authenticates caller via Kubernetes token review
         ▼
[ EKS Pod Identity Service ] (AWS Regional Backend)
         │
         │ Direct ABAC Authorization via PodIdentityAssociation
         ▼
[ Temporary, auto-refreshed STS Credentials Issued ]
```

Configuration requires a simple declarative binding:

```yaml
apiVersion: eks.services.k8s.aws/v1alpha1
kind: PodIdentityAssociation
metadata:
  name: payment-processor-iam-binding
spec:
  clusterName: prod-core-cluster
  namespace: finance
  serviceAccount: payment-sa
  roleARN: arn:aws:iam::123456789012:role/PaymentProcessorS3Access
```

The trust policy on the IAM role no longer references long OIDC strings; it simply trusts the principal `pods.eks.amazonaws.com`, allowing the same IAM role to be shared cleanly across hundreds of ephemeral clusters.

## 5. High-Density Networking: AWS VPC CNI & Prefix Delegation

Unlike simple overlay networks (like Flannel) that encapsulate traffic inside VXLAN packets, the default **AWS VPC CNI** allocates native AWS VPC IP addresses directly to every Kubernetes Pod.

### The ENI Limit Problem

Every EC2 instance type has a hard hardware limit on the number of Elastic Network Interfaces (ENIs) it can attach, and the number of secondary IPv4 addresses each ENI can hold.

For example, an `m5.large` instance supports a maximum of 3 ENIs, each supporting 10 IPv4 addresses. One address per ENI is consumed by the primary interface, leaving:

$$\text{Max Pods} = 3 \times (10 - 1) + 2 = 29\text{ Pods}$$

Even if an `m5.large` has plenty of spare CPU and memory, the node cannot run more than 29 pods because it runs out of IP addresses.

### Prefix Delegation (`/28` IPv4 Blocks)

To overcome this constraint, modern VPC CNI configurations enable **Prefix Delegation**. Instead of allocating individual secondary IP addresses, the CNI assigns an entire `/28` IPv4 subnet prefix (16 IP addresses) to each ENI slot:

```yaml
apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: aws-node
  namespace: kube-system
spec:
  template:
    spec:
      containers:
        - name: aws-node
          env:
            - name: ENABLE_PREFIX_DELEGATION
              value: "true"
            - name: WARM_PREFIX_TARGET
              value: "1"
```

With prefix delegation enabled, an `m5.large` can easily host **110 Pods** (the default Kubernetes node limit), which lets you pack pods more densely and run fewer, fuller nodes.

### Custom Subnet Routing & Security Groups for Pods

1. **Custom Networking**: If corporate VPC IPv4 addresses are exhausted, you can allocate secondary non-routable CIDRs (such as `100.64.0.0/10`) exclusively for Pod IP allocations, preserving primary corporate IPs for node hosts.
2. **Security Groups for Pods**: By leveraging trunk network interfaces, you can assign native AWS Security Groups directly to individual Kubernetes Pods, enforcing enterprise cloud firewalls at the container boundary.

## 6. Cloud Storage Integration: EBS CSI vs. EFS CSI

Stateful workloads on EKS rely on modern Container Storage Interface (CSI) drivers:

| Feature | AWS EBS CSI Driver | AWS EFS CSI Driver |
| :--- | :--- | :--- |
| **Storage Protocol** | Block Storage (`gp3`, `io2`) | Managed Network File System (NFSv4) |
| **Access Mode** | `ReadWriteOnce` (RWO) | `ReadWriteMany` (RWX) |
| **Topology Scope** | Locked to a single Availability Zone | Multi-AZ by default |
| **Throughput & IOPS** | Ultra-high (up to 256,000 IOPS on `io2`) | Scalable burst or provisioned throughput |
| **Primary Use Cases** | Databases (PostgreSQL, MySQL, Kafka) | Shared assets, content management, machine learning training sets |

When deploying high-availability databases using the EBS CSI driver, remember the **single-AZ attachment rule**: an EBS volume can only be mounted to an EC2 instance residing in the exact same Availability Zone. Therefore the volume carries a node-affinity constraint, and if a node fails the scheduler can only reschedule the Pod onto a node in that same AZ. Use a StorageClass with `volumeBindingMode: WaitForFirstConsumer` so the volume is created in the AZ where the Pod lands.
