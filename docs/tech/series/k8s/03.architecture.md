While the control plane calculates what the world *should* look like, the worker nodes are where physical compute, memory, disk, and network interfaces meet reality. A worker node is an execution machine that runs the container processes, enforces kernel boundaries, monitors health, and translates abstract API objects into concrete Linux syscalls.

This chapter descends into the node internals: tracing the path from the node agent (`kubelet`) through the Container Runtime Interface (CRI), into `containerd-shim`, and finally down to Linux **cgroups v2** and kernel namespaces.

---

### Node Status Conditions

When inspecting nodes via `kubectl describe node <name>`, the Kubelet reports four critical health conditions:

- **`Ready`**: True if the node is healthy and ready to accept new pod placements.
- **`MemoryPressure`**: True if host memory has dipped below the configured eviction threshold (e.g., `< 100MiB` free), triggering proactive pod evictions.
- **`DiskPressure`**: True if the root filesystem or image storage disk has filled up.
- **`PIDPressure`**: True if the number of allocated Linux process IDs on the host is approaching `/proc/sys/kernel/pid_max`, preventing fork bombs.

## 2. The Node Agent: Kubelet & PLEG

The `kubelet` is the only component on the node with direct authority over container execution. It runs as a systemd service directly on the host OS.

### The PLEG (Pod Lifecycle Event Generator)

Historically, kubelet polled the container runtime every few seconds to check whether containers were still alive—a pattern that resulted in massive CPU spikes on nodes hosting hundreds of containers.

Modern kubelet employs **PLEG**:

- Kubelet subscribes to real-time container lifecycle events directly from the CRI runtime stream.
- It aggregates lifecycle changes into internal event channels (`ContainerStarted`, `ContainerDied`).
- The internal **`syncPod` loop** reconciles the actual pod state against the pod specifications received from the API Server.

### Why containerd-shim-v2 Exists

A common architectural question: *Why have a `containerd-shim` process per pod instead of letting `containerd` manage container PIDs directly?*

The shim serves three mission-critical stability requirements:

1. **Daemonless Restarts**: If `containerd` or `kubelet` crashes, restarts, or is upgraded during node maintenance, **running containers continue executing uninterrupted**. The shim holds the file descriptors, standard I/O pipes, and exit status.
2. **Subreaper Responsibility**: In Unix, if a process forks and its parent dies, the child process is reparented to PID 1. The shim acts as a subreaper (`prctl(PR_SET_CHILD_SUBREAPER)`), cleanly reaping orphaned zombie processes inside the container without polluting the host PID 1.
3. **Resource Boundary**: The shim holds the exit status of the container exit codes until Kubelet can retrieve them.

## 4. Under the Hood: Kernel Isolation Primitives

Containers do not exist as physical entities inside the Linux kernel; they are standard Linux processes dressed in isolated namespaces and constrained by **cgroups v2**.

### 1. Linux Namespaces (What the Process Sees)

- **`net`**: Provides a dedicated network stack (own IP, routing table, iptables/nftables chains, and loopback interface). All containers in the same Pod share the same NetNS!
- **`pid`**: Isolates process trees. Inside the container, the primary application thinks it is PID 1, while on the host OS it runs as an ordinary high-numbered PID (e.g., PID 284912).
- **`mnt`**: Isolates filesystem mount points. The container sees its rootfs overlaid via `overlayfs`.
- **`ipc` & `uts`**: Isolates shared memory, message queues, and hostnames.
- **`user`**: Maps container root (UID 0) to an unprivileged non-zero UID on the host for defense-in-depth.

### 2. cgroups v2 (How Much the Process Can Consume)

All modern Kubernetes clusters (v1.25 through v1.37) require **unified cgroups v2**:

- In legacy cgroups v1, CPU, memory, and block I/O controllers lived in separate directory hierarchies, leading to broken out-of-memory (OOM) tracking when page-cache writeback crossed boundaries.
- Under cgroups v2, a unified hierarchy controls resources per slice:
  - **`cpu.max`**: Controls CFS bandwidth quota (maps to Kubernetes `limits.cpu`).
  - **`cpu.weight`**: Proportional CPU scheduling under contention (maps to Kubernetes `requests.cpu`).
  - **`memory.max`**: Hard memory ceiling. Breaching this immediately invokes the Linux kernel OOM Killer.
  - **`memory.high`**: Throttle threshold before OOM killing occurs.

## 5. Quality of Service (QoS) Classes & Kernel OOM Scoring

Kubernetes classifies every Pod into one of three QoS classes based strictly on its `requests` and `limits`:

| QoS Class | Condition | Host Behavior Under Memory Duress | `oom_score_adj` |
| :--- | :--- | :--- | :--- |
| **Guaranteed** | Every container has `requests == limits` for both CPU & Memory | Top priority. Never evicted unless nodes face catastrophic system-level starvation. | `-997` |
| **Burstable** | `requests < limits` or only requests specified | Middle tier. Allowed to burst past requests, but vulnerable if the node faces contention. | `max(2, 1000 - (1000 * req) / cap)` |
| **BestEffort** | No `requests` or `limits` declared | Lowest priority. First to be terminated and killed when memory runs out. | `1000` |

### How OOM Killer Uses `oom_score_adj`

When a host kernel runs completely out of memory, the kernel invokes the OOM Killer:

1. The kernel calculates an OOM score for every process between 0 and 1000 based on the percentage of RAM consumed.
2. The kernel adds the process's **`/proc/<pid>/oom_score_adj`** (which Kubelet configures based on the QoS table above).
3. The process with the highest total score is terminated with `SIGKILL` (Exit code 137).

A **BestEffort** pod has an adjustment of `+1000`, guaranteeing it will be sacrificed immediately to protect **Guaranteed** production workloads.
