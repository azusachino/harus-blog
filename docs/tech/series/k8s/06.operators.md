Out of the box, Kubernetes knows how to orchestrate stateless containers, scale pods, and route network packets. But it knows nothing about how to fail over a PostgreSQL primary, rebalance Apache Kafka partitions, or issue and rotate Let's Encrypt TLS certificates.

Traditionally, these stateful, domain-specific tasks required human Site Reliability Engineers (SREs) reading runbooks at 3:00 AM. The **Operator Pattern** fundamentally transforms this paradigm: **it captures human operational expertise in custom software and runs it inside a continuous reconciliation loop**.

This chapter explores how to extend Kubernetes using **Custom Resource Definitions (CRDs)** and the **Controller Pattern**, examining the internals of `controller-runtime`, cache informers, finalizers, and leader election.

---

## 1. The Operator Philosophy

Coined by CoreOS in 2016, an Operator is simply:

$$\text{Operator} = \text{Custom Resource Definition (CRD)} + \text{Custom Controller}$$

Instead of manually executing 20 imperative CLI commands to back up a database, you declare a custom Kubernetes resource:

```yaml
apiVersion: postgresql.cnpg.io/v1
kind: Backup
metadata:
  name: weekly-snapshot
spec:
  cluster:
    name: prod-db
  target: immediate
```

The Operator detects this declaration, pauses active write transactions, takes a consistent storage snapshot, uploads the Write-Ahead Log (WAL) to an S3 bucket, verifies archive checksums, and updates `status.phase: Succeeded`. If the controller pod crashes mid-execution, on reboot it inspects the state of the world and resumes exactly where it left off.

## 2. Anatomizing Custom Resource Definitions (CRDs)

A CRD teaches the `kube-apiserver` new RESTful API endpoints without requiring you to recompile Kubernetes.

### Production-Grade CRD Schema

In modern Kubernetes (**v1.37**), CRDs enforce strict **OpenAPI v3 schemas** and embedded **Common Expression Language (CEL)** validations:

```yaml
apiVersion: apiextensions.k8s.io/v1
kind: CustomResourceDefinition
metadata:
  name: databases.storage.example.com
spec:
  group: storage.example.com
  names:
    kind: Database
    listKind: DatabaseList
    plural: databases
    singular: database
    shortNames: ["db"]
  scope: Namespaced
  versions:
    - name: v1alpha1
      served: true
      storage: true
      subresources:
        status: {} # Enables dedicated /status subresource!
        scale:
          specReplicasPath: .spec.replicas
          statusReplicasPath: .status.replicas
      schema:
        openAPIV3Schema:
          type: object
          properties:
            spec:
              type: object
              required: ["storageSize", "engineVersion"]
              properties:
                storageSize:
                  type: string
                  pattern: '^[0-9]+(Gi|Ti)$'
                engineVersion:
                  type: string
                replicas:
                  type: integer
                  minimum: 1
                  maximum: 9
              # Inline CEL validation rules: zero webhook latency!
              x-kubernetes-validations:
                - rule: "self.replicas % 2 != 0"
                  message: "Replicas must be an odd number to maintain distributed consensus quorum."
            status:
              type: object
              properties:
                phase:
                  type: string
                observedGeneration:
                  type: integer
```

### Critical Details: The `/status` Subresource

Never store operational status in `spec`. Splitting `spec` and `status` via the `/status` subresource provides three massive architectural benefits:

1. **RBAC Isolation**: Developers can be granted write access to `spec` while only the Operator's ServiceAccount has write permission to `status`.
2. **ResourceVersion Decoupling**: Updating `status` does not increment `metadata.generation`, preventing infinite re-triggering loops.
3. **Optimistic Concurrency**: The controller can patch status without risking clobbering user spec edits.

## 3. The Controller-Runtime Engine: How Operators Reconcile

Almost all production operators (including Kubebuilder and Operator SDK) are built upon the Go **`sigs.k8s.io/controller-runtime`** library.

<Archify src="./diagrams/k8s-operator-reconcile.sequence.json" />

### The Internal Machinery

A controller does **not** query the API Server synchronously on every loop. Doing so would overwhelm `etcd` in clusters with thousands of resources:

1. **Reflector & Informer Cache**: An Informer opens an HTTP chunked watch stream (`watch(resource=databases)`) against the API Server. It maintains an in-memory, thread-safe cache (`client.Reader`). Read operations (`r.Get()`, `r.List()`) hit local RAM directly.
2. **Rate-Limiting WorkQueue**: When the Informer notices an object creation, update, or deletion, it pushes a lightweight key (`namespace/name`) into a rate-limiting workqueue.
3. **Worker Pool & `Reconcile()`**: Background worker goroutines pop keys from the queue and invoke the developer's reconciliation logic:

   ```go
   func (r *DatabaseReconciler) Reconcile(ctx context.Context, req ctrl.Request) (ctrl.Result, error)
   ```

## 4. Advanced Mechanics: Finalizers & Clean Teardown

When an engineer deletes a Custom Resource (`kubectl delete db prod-db`), Kubernetes by default deletes the object from `etcd` instantly. If that database had attached cloud block storage (EBS/Ceph) or external DNS records, those external resources become orphaned forever.

### The Two-Phase Finalizer Pattern

A **Finalizer** is an arbitrary string key placed in `metadata.finalizers`. When an object has finalizers, Kubernetes **refuses to delete it from etcd**. Instead, it sets `metadata.deletionTimestamp` to the current time:

```go
func (r *DatabaseReconciler) Reconcile(ctx context.Context, req ctrl.Request) (ctrl.Result, error) {
    db := &storagev1.Database{}
    if err := r.Get(ctx, req.NamespacedName, db); err != nil {
        return ctrl.Result{}, client.IgnoreNotFound(err)
    }

    finalizerName := "storage.example.com/cleanup-disks"

    // Examine DeletionTimestamp to determine if object is being deleted
    if db.DeletionTimestamp.IsZero() {
        // Object is active: ensure finalizer is registered
        if !controllerutil.ContainsFinalizer(db, finalizerName) {
            controllerutil.AddFinalizer(db, finalizerName)
            return ctrl.Result{}, r.Update(ctx, db)
        }
    } else {
        // Object is being deleted!
        if controllerutil.ContainsFinalizer(db, finalizerName) {
            // 1. Perform hazardous external teardown (e.g. destroy cloud storage volumes, backup logs)
            if err := r.deleteExternalStorage(ctx, db); err != nil {
                return ctrl.Result{}, err // Requeue on error; deletion remains blocked safely
            }

            // 2. Teardown succeeded: remove finalizer
            controllerutil.RemoveFinalizer(db, finalizerName)
            return ctrl.Result{}, r.Update(ctx, db)
        }
        // Finalizer removed: Kubernetes garbage collector purges the object from etcd!
        return ctrl.Result{}, nil
    }

    // Normal reconciliation logic (ensure StatefulSet, Service, etc.)...
    return ctrl.Result{}, nil
}
```

## 5. High Availability: Leader Election & Concurrency

In a production cluster, you never run a single replica of an Operator. If that pod crashes or gets evicted during node maintenance, reconciliations stall.

However, if you run two operator replicas concurrently without synchronization, both will attempt to reconcile the exact same database simultaneously, fighting over resource updates and causing catastrophic state thrashing.

### The Leader Election Lease

Kubernetes operators use **Lease Objects (`coordination.k8s.io`)** for active-passive leader election:

- All operator replicas race to acquire and renew a lightweight `Lease` object in the API Server every few seconds.
- The winner becomes the **Active Leader** and spins up its Informer workers.
- The remaining replicas sit in **Standby Mode**, tailing the lease.
- If the active leader fails to renew its lease within the deadline (e.g. 15 seconds), a standby instance immediately assumes leadership, guaranteeing uninterrupted automated operations with zero split-brain danger.
