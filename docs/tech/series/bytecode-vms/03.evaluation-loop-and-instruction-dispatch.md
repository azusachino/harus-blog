## Before you start

The heart of a virtual machine is a loop: read the next instruction, work out what it is, run the matching code, repeat. It sounds trivial, but this loop runs billions of times, so how it jumps from one instruction to the next has a measurable effect on speed.

The simplest version is a big `switch` statement on the opcode. The chapter compares it to two alternatives and explains why they can be faster. The reason is the CPU's branch predictor, hardware that guesses where a jump will go so the processor does not stall. One shared `switch` gives it a single jump to guess for every instruction; giving each handler its own jump gives it more context to guess from.

Read [Bytecode VMs 02](/tech/series/bytecode-vms/02.stack-vs-register-architectures/) first for what the instructions look like.

Terms used in this chapter:

- **evaluation loop**: the VM's main loop that fetches, decodes and executes instructions.
- **handler**: the piece of code that implements one opcode.
- **switch dispatch**: choosing the handler with a single `switch` on the opcode inside a loop.
- **computed goto**: a GCC/Clang extension that jumps to a label address stored in a table, so each handler can jump straight to the next.
- **branch predictor**: CPU hardware that guesses the target of a jump before it is known.
- **branch misprediction**: a wrong guess, which makes the CPU discard work and costs roughly a dozen or more cycles.
- **call threading**: dispatching by calling one function per instruction through a table of function pointers.

## Bytecode VMs 03: The Evaluation Loop and Instruction Dispatch

At the core of every bytecode virtual machine sits an engine known as the **evaluation loop** (or dispatch loop). Conceptually, the entire runtime is a continuous cycle:

$$\text{Fetch Opcode} \longrightarrow \text{Decode Instruction} \longrightarrow \text{Execute Handler} \longrightarrow \text{Repeat}$$

While simple to write in high-level pseudocode, the mechanics of how the interpreter transitions from one opcode handler to the next is often the single largest bottleneck in interpreter execution speed. On modern out-of-order superscalar CPUs (Intel Core, AMD Zen, Apple Silicon), the CPU hardware branch predictor—specifically the **Branch Target Buffer (BTB)**—dictates whether an instruction dispatch costs 1 cycle or stalls the pipeline for 15 to 20 clock cycles.

### 1. Three Dispatch Architectures

The interpreter loop can be implemented using three distinct architectural patterns:

<Archify src="./diagrams/instruction-dispatch-mechanisms.workflow.json" />

#### 1. The Central Switch Loop

The most common and portable implementation uses a standard C `switch` statement wrapped in an infinite `while` loop:

```c
void run_switch(const uint8_t* bytecode, size_t len) {
    const uint8_t* pc = bytecode;
    while (1) {
        switch (*pc++) {
            case OP_ADD:
                // pop, add, push
                break;
            case OP_SUB:
                // pop, sub, push
                break;
            case OP_RETURN:
                return;
        }
    }
}
```

When compiled to machine code, the C compiler transforms the `switch` statement into a **single indirect jump** instruction via a jump table:

```text
; Central switch dispatch in x86-64 assembly
movzx eax, byte ptr [rsi]    ; Fetch opcode: eax = *pc
inc   rsi                    ; pc++
jmp   qword ptr [rdi + rax*8] ; Indirect jump: jmp to jump_table[opcode]
```

**The Hardware Bottleneck (BTB Thrashing)**:
Every single opcode execution ends with a `break` jumping back to the top of the `while` loop, funneling through that **same single indirect `jmp` instruction**.

Because a program executes varied sequences of instructions (`LOAD` followed by `ADD`, then `STORE`, then `LOAD`, then `JUMP`), the CPU's Branch Target Buffer sees the single indirect branch jumping to dozens of different target addresses in rapid succession. The hardware branch predictor cannot establish a stable pattern, which on older CPUs produced **high branch misprediction rates**. Every misprediction flushes speculative instructions and stalls execution for roughly 15 to 20 clock cycles. (Caveat: Haswell-era and later Intel cores and recent AMD and Apple cores predict indirect branches using global history, and measurements such as Rohou et al., *Branch Prediction and the Performance of Interpreters - Don't Trust Folklore* (2015), found that much of the switch penalty disappeared there. The gap below is largest on older or simpler cores.)

#### 2. Call Threading (Function Pointer Table)

Call threading moves each opcode handler into an independent C function and uses an array of function pointers:

```c
typedef void (*OpcodeHandler)(VM* vm);
static const OpcodeHandler dispatch_table[256] = {
    [OP_ADD] = handle_add,
    [OP_SUB] = handle_sub,
    [OP_RETURN] = handle_return,
};

void run_call_threaded(VM* vm) {
    while (vm->running) {
        dispatch_table[*vm->pc++](vm);
    }
}
```

While clean and modular, call threading suffers from substantial C calling convention overhead: pushing arguments to registers, setting up stack frames (`push rbp; mov rbp, rsp`), adjusting the stack pointer, and executing `call` followed by `ret` on every single opcode. It is usually slower than a switch statement.

#### 3. Direct Threaded Code (Computed Gotos)

Pioneered by James Bell in 1973 and supported by GNU C / Clang via the `labels as values` extension (`&&label`), **direct threaded code** eliminates the centralized loop header entirely.

Instead of returning to a common `while` loop, **each opcode handler fetches the next opcode and directly jumps to its target label at the tail of its own body**:

```c
void run_threaded(const uint8_t* bytecode) {
    static const void* dispatch_table[] = {
        [OP_ADD] = &&label_add,
        [OP_SUB] = &&label_sub,
        [OP_RETURN] = &&label_return,
    };

    const uint8_t* pc = bytecode;

    // Primer: jump to first instruction
    goto *dispatch_table[*pc++];

label_add: {
    // 1. Execute addition logic
    int b = pop();
    int a = pop();
    push(a + b);
    // 2. Direct tail dispatch: jump directly to NEXT opcode handler
    goto *dispatch_table[*pc++];
}

label_sub: {
    int b = pop();
    int a = pop();
    push(a - b);
    goto *dispatch_table[*pc++];
}

label_return:
    return;
}
```

**Why Computed Gotos Win**:
In direct threaded code, each opcode handler ends with its **own distinct indirect jump instruction** in assembly.

If an instruction sequence frequently pairs `LOAD_FAST` followed by `BINARY_ADD` (a very common pattern in loops), the indirect jump instruction at the end of `LOAD_FAST` almost always branches to `label_add`. The CPU's Branch Target Buffer easily predicts this specific jump site with near 100% accuracy! By distributing the indirect branches across 100+ separate physical machine code locations, branch prediction improves, which historically gave speedups in the range of 15% to 25% over switch dispatch; on current CPUs the gain is usually smaller.

### 2. CPython's Historical Dispatch Evolution

The core dispatch loop in CPython lives in `Python/ceval.c`:

1. **CPython 3.1 onward (also backported to 2.7)**: Employs computed gotos when built with a compiler that supports them, such as GCC or Clang (`configure --with-computed-gotos`, on by default when available), falling back to a giant `switch (opcode)` loop on MSVC and other compilers.
2. **CPython 3.11 (PEP 659 Specialized Adaptive Interpreter)**: Introduced quickened opcodes and inline adaptive caches. An instruction like `LOAD_ATTR` observes the incoming types for several executions. Once determined to be monomorphic, the bytecode instruction itself is overwritten in-place with a specialized variant (`LOAD_ATTR_MODULE`, `LOAD_ATTR_INSTANCE_VALUE`), skipping dictionary lookups.
3. **CPython 3.12 - 3.13**: Instruction handlers are generated from a declarative description (`Python/bytecodes.c`), which also defines micro-operations (uops). 3.13 added an experimental, off-by-default tier-2 interpreter and JIT that run traces of hot uops.
4. **CPython 3.14**: Adds an opt-in build mode where handlers tail-call the next handler (requires a recent Clang); the gain depends on compiler and platform.

### 3. Verification Lab: Multi-Dispatch Simulator and Benchmark

The following self-contained Python lab implements a micro-virtual machine with two simulated dispatch engines:

1. A **Centralized Switch-Style Dispatcher** (tracking centralized indirect funneling).
2. A **Direct Handler Chain Dispatcher** (simulating computed goto tail calls).

It runs a hot 5,000-iteration arithmetic countdown loop and verifies execution correctness and dispatch metrics.

```python
"""
Bytecode VMs Lab 03 - Evaluation Loop and Instruction Dispatch
Simulates centralized switch vs direct-threaded dispatch on a hot loop.
"""

from typing import List, Tuple, Any, Dict, Callable, Optional
from enum import Enum, auto

class Op(Enum):
    LOAD_CONST = auto()
    LOAD_VAR = auto()
    STORE_VAR = auto()
    BINARY_SUB = auto()
    BINARY_ADD = auto()
    JUMP_IF_ZERO = auto()
    JUMP_ABSOLUTE = auto()
    HALT = auto()

# -------------------------------------------------------------
# 1. Centralized Switch Dispatch Simulator
# -------------------------------------------------------------
class SwitchInterpreter:
    def __init__(self, code: List[Tuple[Op, Any]], consts: List[Any]):
        self.code = code
        self.consts = consts
        self.stack: List[int] = []
        self.vars: Dict[str, int] = {}
        # Metrics
        self.dispatch_count = 0
        self.central_branch_hits = 0

    def run(self, initial_vars: Dict[str, int]) -> Dict[str, int]:
        self.vars = dict(initial_vars)
        pc = 0
        n_instr = len(self.code)

        while True:
            # Central dispatch bottleneck: single entry point
            self.central_branch_hits += 1
            if pc >= n_instr:
                break

            op, arg = self.code[pc]
            self.dispatch_count += 1
            pc += 1

            if op == Op.LOAD_CONST:
                self.stack.append(self.consts[arg])
            elif op == Op.LOAD_VAR:
                self.stack.append(self.vars[arg])
            elif op == Op.STORE_VAR:
                self.vars[arg] = self.stack.pop()
            elif op == Op.BINARY_SUB:
                b = self.stack.pop()
                a = self.stack.pop()
                self.stack.append(a - b)
            elif op == Op.BINARY_ADD:
                b = self.stack.pop()
                a = self.stack.pop()
                self.stack.append(a + b)
            elif op == Op.JUMP_IF_ZERO:
                cond = self.stack.pop()
                if cond == 0:
                    pc = arg
            elif op == Op.JUMP_ABSOLUTE:
                pc = arg
            elif op == Op.HALT:
                break
            else:
                raise RuntimeError(f"Unknown opcode {op}")

        return self.vars

# -------------------------------------------------------------
# 2. Threaded Jump Table Dispatch Simulator (Trampolined)
# -------------------------------------------------------------
class ThreadedInterpreter:
    def __init__(self, code: List[Tuple[Op, Any]], consts: List[Any]):
        self.code = code
        self.consts = consts
        self.stack: List[int] = []
        self.vars: Dict[str, int] = {}
        self.pc = 0
        self.running = True
        # Metrics
        self.dispatch_count = 0
        self.per_opcode_tail_jumps: Dict[Op, int] = {op: 0 for op in Op}

        # Dispatch table mapping opcodes directly to handler callables
        self.table: Dict[Op, Callable[[], Optional[Callable]]] = {
            Op.LOAD_CONST: self._op_load_const,
            Op.LOAD_VAR: self._op_load_var,
            Op.STORE_VAR: self._op_store_var,
            Op.BINARY_SUB: self._op_binary_sub,
            Op.BINARY_ADD: self._op_binary_add,
            Op.JUMP_IF_ZERO: self._op_jump_if_zero,
            Op.JUMP_ABSOLUTE: self._op_jump_absolute,
            Op.HALT: self._op_halt,
        }

    def _op_load_const(self) -> Optional[Callable]:
        arg = self.code[self.pc - 1][1]
        self.stack.append(self.consts[arg])
        return self._tail_dispatch(Op.LOAD_CONST)

    def _op_load_var(self) -> Optional[Callable]:
        arg = self.code[self.pc - 1][1]
        self.stack.append(self.vars[arg])
        return self._tail_dispatch(Op.LOAD_VAR)

    def _op_store_var(self) -> Optional[Callable]:
        arg = self.code[self.pc - 1][1]
        self.vars[arg] = self.stack.pop()
        return self._tail_dispatch(Op.STORE_VAR)

    def _op_binary_sub(self) -> Optional[Callable]:
        b = self.stack.pop()
        a = self.stack.pop()
        self.stack.append(a - b)
        return self._tail_dispatch(Op.BINARY_SUB)

    def _op_binary_add(self) -> Optional[Callable]:
        b = self.stack.pop()
        a = self.stack.pop()
        self.stack.append(a + b)
        return self._tail_dispatch(Op.BINARY_ADD)

    def _op_jump_if_zero(self) -> Optional[Callable]:
        arg = self.code[self.pc - 1][1]
        cond = self.stack.pop()
        if cond == 0:
            self.pc = arg
        return self._tail_dispatch(Op.JUMP_IF_ZERO)

    def _op_jump_absolute(self) -> Optional[Callable]:
        arg = self.code[self.pc - 1][1]
        self.pc = arg
        return self._tail_dispatch(Op.JUMP_ABSOLUTE)

    def _op_halt(self) -> Optional[Callable]:
        self.running = False
        return None

    def _tail_dispatch(self, source_op: Op) -> Optional[Callable]:
        self.per_opcode_tail_jumps[source_op] += 1
        if self.pc < len(self.code) and self.running:
            next_op, _ = self.code[self.pc]
            return self.table[next_op]
        return None

    def run(self, initial_vars: Dict[str, int]) -> Dict[str, int]:
        self.vars = dict(initial_vars)
        self.pc = 0
        self.running = True
        self.dispatch_count = 0

        # Primer jump
        if self.pc < len(self.code):
            first_op, _ = self.code[self.pc]
            next_handler = self.table[first_op]
            while self.running and next_handler is not None:
                self.dispatch_count += 1
                self.pc += 1
                next_handler = next_handler()

        return self.vars

def run_lab():
    # Program:
    # count = 1000
    # acc = 0
    # loop:
    #   if count == 0 goto end
    #   acc = acc + 2
    #   count = count - 1
    #   goto loop
    # end:
    #   halt
    consts = [0, 2, 1]  # const 0 = 0, const 1 = 2, const 2 = 1
    program: List[Tuple[Op, Any]] = [
        # Offset 0..5: loop test
        (Op.LOAD_VAR, "count"),        # 0: stack: [count]
        (Op.JUMP_IF_ZERO, 14),         # 1: if count == 0 goto HALT (offset 14)
        # Offset 2..7: acc = acc + 2
        (Op.LOAD_VAR, "acc"),          # 2: stack: [acc]
        (Op.LOAD_CONST, 1),            # 3: stack: [acc, 2]
        (Op.BINARY_ADD, None),         # 4: stack: [acc + 2]
        (Op.STORE_VAR, "acc"),         # 5: acc updated
        # Offset 6..11: count = count - 1
        (Op.LOAD_VAR, "count"),        # 6: stack: [count]
        (Op.LOAD_CONST, 2),            # 7: stack: [count, 1]
        (Op.BINARY_SUB, None),         # 8: stack: [count - 1]
        (Op.STORE_VAR, "count"),       # 9: count updated
        # Offset 10..13: loop back
        (Op.JUMP_ABSOLUTE, 0),         # 10: goto offset 0
        (Op.HALT, None),               # 11: halt
    ]
    # Note: Target for offset 14 is 11 in instruction index
    # Let's adjust target index:
    program[1] = (Op.JUMP_IF_ZERO, 11)

    initial_vars = {"count": 1000, "acc": 0}

    # 1. Test Switch Interpreter
    switch_vm = SwitchInterpreter(program, consts)
    switch_res = switch_vm.run(initial_vars)
    assert switch_res["count"] == 0
    assert switch_res["acc"] == 2000
    # 1000 iterations * 11 ops + 1 loop exit (3 ops: LOAD_VAR, JUMP_IF_ZERO, HALT) = 11003 dispatches
    assert switch_vm.dispatch_count == 11003
    assert switch_vm.central_branch_hits == 11003

    # 2. Test Threaded Interpreter
    threaded_vm = ThreadedInterpreter(program, consts)
    threaded_res = threaded_vm.run(initial_vars)
    assert threaded_res["count"] == 0
    assert threaded_res["acc"] == 2000
    assert threaded_vm.dispatch_count == 11003

    # Verify that in threaded dispatch, tail jumps are distributed across opcodes:
    # LOAD_VAR made 3001 dispatches (1000 loop body * 3 + 1 exit check)
    assert threaded_vm.per_opcode_tail_jumps[Op.LOAD_VAR] == 3001
    assert threaded_vm.per_opcode_tail_jumps[Op.JUMP_ABSOLUTE] == 1000
    assert threaded_vm.per_opcode_tail_jumps[Op.STORE_VAR] == 2000

    print(f"Switch VM Dispatches: {switch_vm.dispatch_count} funneled through 1 central branch")
    print(f"Threaded VM Dispatches: {threaded_vm.dispatch_count} distributed across {len(threaded_vm.table)} handlers")
    print("Bytecode VM Lab 03 passed: Evaluation loop and instruction dispatch verified.")

if __name__ == "__main__":
    run_lab()
```
