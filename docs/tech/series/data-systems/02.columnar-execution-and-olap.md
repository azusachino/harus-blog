In Chapter 01, we saw how B+ Trees and LSM-Trees serve **OLTP (Online Transaction Processing)** workloads: looking up or mutating a handful of rows by primary key in single-digit milliseconds.

What happens when a product analyst or observability dashboard runs this query over 1 billion HTTP access log rows?

```sql
SELECT service_name, status_code, COUNT(*), QUANTILE(0.99)(latency_ms)
FROM http_access_logs
WHERE event_date >= '2026-04-01' AND status_code >= 500
GROUP BY service_name, status_code;
```

In a row-oriented OLTP database like MySQL InnoDB or PostgreSQL, even if each row is 500 bytes wide across 40 columns (`user_agent`, `request_body`, `trace_id`, `headers`, etc.), scanning 100 million rows for April requires reading $10^8 \times 500\text{ B} \approx 50\text{ GB}$ of 16 KB pages into the Buffer Pool just to extract **4 columns** (`event_date`, `service_name`, `status_code`, `latency_ms`) totaling 18 bytes per row!

In **Chapter 02**, we explore how **OLAP (Online Analytical Processing)** engines—specifically **ClickHouse (`MergeTree`)**, DuckDB, and Apache Parquet—achieve $100\times$ higher analytical scan throughput through **Columnar Storage, Sparse Primary Indexes, Domain-Specific Compression, and SIMD Vectorized Execution**.

---

## 1. Row-Oriented vs. Column-Oriented Storage Layouts

### Row Store Layout (InnoDB `.ibd` / Postgres Heap)

In a row-oriented storage engine, all fields of row $i$ are stored contiguously inside a page:

```text
[Page 0]: [Row 1: ts | service | status | latency | ua | url] [Row 2: ts | service | status | ...]
```

- **Great for OLTP:** Fetching `SELECT * FROM logs WHERE id = 42` reads a single contiguous record from one page.
- **Terrible for OLAP:** Scanning 4 columns out of 40 wastes $>90\%$ of disk I/O bandwidth, pollutes the OS page cache and CPU L1/L2/L3 cache lines with unused columns, and prevents effective compression because adjacent bytes belong to *different data types* (a timestamp followed by a URL string followed by a float).

### Column Store Layout (ClickHouse `MergeTree` / Apache Parquet)

A column-oriented engine transposes the table on disk: **each column is stored in its own separate file or contiguous column chunk**, with row alignment preserved strictly by array index position $i$:

```text
ts.bin      : [ 1713484800, 1713484800, 1713484801, 1713484801, ... ]
service.bin : [ "auth",     "auth",     "auth",     "payment",  ... ]
status.bin  : [ 200,        200,        502,        200,        ... ]
latency.bin : [ 4.2,        3.9,        1240.5,     11.8,       ... ]
```

- **Zero wasted I/O:** If a query touches 4 columns out of 50, the storage engine opens only those 4 column streams (`ts.bin`, `service.bin`, `status.bin`, `latency.bin`).
- **Homogeneous vectors for compression & SIMD:** Every value in `status.bin` is a `UInt16` drawn from a tiny domain (`{200, 201, 301, 400, 404, 500, 502, 503}`). When the table is sorted by `(service, ts)`, identical values cluster into long runs that compress by $10\times\text{--}100\times$.

## 2. ClickHouse `MergeTree` Architecture & Sparse Granule Indexes

Why is ClickHouse's core engine family called **`MergeTree`**? Because it combines an **LSM-like immutable part-merging write path** with **columnar storage and a sparse primary index**.

### Data Parts, Granules & Why ClickHouse Primary Keys Are Sparse

When you `INSERT` a batch of 100,000 rows into a ClickHouse `MergeTree` table:

1. ClickHouse sorts the batch in memory according to the table's `ORDER BY` key (the **Sorting Key**, e.g., `ORDER BY (service_name, event_date, status_code)`).
2. It writes an immutable directory on disk called a **Data Part** (e.g., `202604_1_1_0/`). Background threads continuously merge smaller Data Parts into larger sorted Data Parts (`202604_1_8_2/`), just like LSM compaction!
3. Inside each Data Part, rows are logically divided into fixed-size chunks called **Granules** (`index_granularity = 8192` rows by default).

```text
Sorted Rows in Data Part (ORDER BY service_name, status_code):
┌──────────────────────────────┬──────────────────────────────┬──────────────────────────────┐
│ Granule 0 (Rows 0 .. 8191)   │ Granule 1 (Rows 8192..16383) │ Granule 2 (Rows 16384..24575)│
│ First row: ("api", 200)      │ First row: ("auth", 200)     │ First row: ("payment", 500)  │
└──────────────▲───────────────┴──────────────▲───────────────┴──────────────▲───────────────┘
               │                              │                              │
primary.idx: [ Mark 0: ("api", 200) ]       [ Mark 1: ("auth", 200) ]      [ Mark 2: ("payment", 500) ]
```

### Sparse Index (`primary.idx`) vs. B+ Tree Dense Index

In MySQL InnoDB, the primary key index has an entry for **every row** (or every 16 KB page of ~100 rows) and enforces **uniqueness**.
In ClickHouse `MergeTree`:

- **The primary key does NOT enforce uniqueness!** Multiple rows can have the exact same primary key.
- **`primary.idx` stores only 1 index mark per 8,192 rows (1 Granule).**
- **Memory footprint math:** For **1 billion ($10^9$) rows**, a dense per-row index would require $10^9$ entries (tens of gigabytes). ClickHouse's sparse index requires only:
  $$\frac{1,000,000,000}{8,192} \approx 122,070 \text{ marks}$$
  At 16 bytes per mark, the entire primary index for **1 billion rows fits in under $2\text{ MB}$ of RAM**, small enough to keep resident in memory and cheap to binary-search.

### How Marks (`mrk2`) Connect `primary.idx` to Compressed Column Blocks

Wait: if each column (`service.bin`, `status.bin`) is compressed with LZ4 or ZSTD into variable-length compressed blocks (typically 64 KB–1 MB uncompressed), how does ClickHouse jump directly to **Granule 42** inside `status.bin` without decompressing the entire file from the beginning?

Each column has a companion mark file (`.mrk2`) where entry $g$ (for Granule $g$) stores a two-part pointer:

1. **`compressed_block_offset`:** The physical byte offset in `status.bin` where the compressed block containing Granule $g$ begins.
2. **`decompressed_granule_offset`:** The byte offset *inside* that decompressed block where Granule $g$'s 8,192 values start.

When a query filters `WHERE service_name = 'payment'`, ClickHouse binary-searches `primary.idx` in RAM, identifies that only Granule 2 can match, reads the `(block_offset, granule_offset)` from `service.mrk2` and `status.mrk2`, seeks directly to that compressed block in `.bin`, decompresses just that 64 KB block, and scans the 8,192-row granule!

### Cardinality Ordering Rule for `ORDER BY`

How should you order columns in `ORDER BY (col_a, col_b, col_c)`?
**Order from lowest cardinality to highest cardinality** (e.g., `ORDER BY (tenant_id, status_code, event_timestamp)`):

1. **Granule Skipping:** A leftmost low-cardinality column (`tenant_id`) groups contiguous ranges of granules together so queries filtering on `tenant_id` (or `tenant_id AND status_code`) skip 99% of granules.
2. **Run-Length Compression:** When `tenant_id` and `status_code` come first in the sort order, identical values repeat thousands of times consecutively inside each 8,192-row granule, turning `tenant_id.bin` and `status_code.bin` into tiny RLE runs.

## 3. Columnar Compression Encodings

Columnar storage unlocks two layers of compression: **lightweight type-specific codecs** (which often allow querying compressed data directly or decoding inside L1 cache) followed by **general-purpose block compression** (`LZ4` for speed, `ZSTD` for higher ratio).

| Codec | Best For | Mechanism |
| :--- | :--- | :--- |
| **Run-Length Encoding (RLE)** | Low-cardinality columns sorted in `ORDER BY` (`status_code`, `country`) | Replaces `[200, 200, ..., 200]` (5,000 times) with a single pair `(value=200, run_length=5000)`. |
| **Dictionary Encoding (`LowCardinality(String)`)** | Strings with $< 10,000$ distinct values per part (`service_name`, `region`, `http_method`) | Replaces variable-length strings with compact 1-byte or 2-byte integer dictionary IDs (`0 -> "GET"`, `1 -> "POST"`). Group-by and hash operations run directly on integer IDs! |
| **Delta / DoubleDelta Encoding** | Monotonically increasing timestamps (`event_time`), sequence IDs, counters | Stores differences between consecutive values ($x_i - x_{i-1}$) or differences of differences ($\Delta_i - \Delta_{i-1}$). For timestamps ticking 1 second apart, `DoubleDelta` turns 64-bit integers into sequences of `0` bits. |
| **Bit-Packing & Frame-of-Reference (FOR)** | Narrow integer ranges (`status_code` in `[200..504]`) | Subtracts minimum value $200$ so all values fit in $[0..304]$, which requires only $\lceil \log_2(305) \rceil = 9\text{ bits}$ per value instead of 16 or 64 bits. |
| **Gorilla XOR Float Compression** | Time-series gauge metrics (CPU %, temperature, prices) | XORs consecutive IEEE-754 floats; if unchanged, stores a single `0` bit; otherwise stores only the changed mantissa/exponent window. |

## 4. Query Execution Models — Volcano Iterator vs. Vectorized SIMD

Even after reading data into RAM, why is an OLAP engine $10\text{--}50\times$ faster at CPU execution than a traditional relational engine?

### The Traditional Volcano / Iterator Model (`Next()` per Row)

Classic databases (MySQL, PostgreSQL, early SQLite) compile a SQL query plan into a tree of operators (`Projection -> Filter -> TableScan`), where each operator exposes a virtual method `next() -> Row`:

```text
Result = Filter.next()
           └── calls TableScan.next()  (Virtual function call #1 per row!)
           └── evaluates Predicate(row) (Virtual function call #2 + dynamic type switch per row!)
```

When scanning 100 million rows:

- The CPU executes **hundreds of millions of virtual function calls** (`vtable` pointer indirections).
- Branch predictors miss frequently on per-row type dispatch and NULL checks.
- The inner loop is too complex for the compiler to auto-vectorize into AVX2 / AVX-512 / NEON instructions.

### Vectorized Execution (Batch-of-Columns in L1 Cache)

Modern analytical engines (ClickHouse, DuckDB, Velox, DataFusion) pass **Columnar Batches (Vectors)** of $1,024\text{--}8,192$ contiguous typed values (`uint16_t status[4096]`, `double latency[4096]`) between operators:

```c
// Tight loop over contiguous array — zero virtual calls per row, 100% L1 cache hit rate,
// auto-vectorized into AVX2 (16 x uint16 per instruction) or AVX-512 (32 x uint16 per instruction):
for (size_t i = 0; i < 4096; ++i) {
    mask[i] = (status[i] >= 500);
}
```

1. **Amortized Function Dispatch:** One virtual call processes 4,096 rows instead of 1 row ($4,096\times$ reduction in call overhead).
2. **SIMD Parallelism:** A single 256-bit AVX2 instruction (`_mm256_cmpgt_epi16`) compares **16 `UInt16` status codes simultaneously** in a single CPU clock cycle.
3. **Cache Locality:** A 4,096-element vector of `UInt16` is $8\text{ KB}$, fitting entirely inside a 32 KB CPU L1 data cache.

## 5. Why `UPDATE` and `DELETE` Are Expensive in OLAP (`ReplacingMergeTree` & Mutations)

Because `MergeTree` data parts are immutable sorted compressed column files accompanied by sparse marks:

- You cannot overwrite row #5,412 in place without decompressing, shifting, re-compressing, and recomputing mark offsets across every column file in the Data Part.
- Therefore, `ALTER TABLE ... UPDATE / DELETE` in ClickHouse is a heavy asynchronous **Mutation** that rewrites entire Data Parts in the background.
- **Idiomatic OLAP Updates & Deduplication:**
  - **`ReplacingMergeTree(version_col)`:** Insert new versions of a row as normal appends. During background part merges, ClickHouse keeps only the row with the highest `version_col` for each sorting key (`ORDER BY`). Because merges are asynchronous, queries that need strict read-time deduplication use `SELECT ... FINAL` (or `argMax(col, version_col) GROUP BY key`).
  - **`CollapsingMergeTree(sign_col)`:** Instead of mutating a row in place, append a compensating cancel row with `sign = -1` (carrying the old state) and the updated row with `sign = +1`. Aggregations (`SUM(sign * bytes)`) become immediately accurate even before background merges collapse the `-1 / +1` pairs!

## 6. Verification Lab — Row Store vs. Sparse-Indexed RLE Columnar Engine

Run the following Python script to compare a **Row-Oriented Store** against a **ClickHouse-style Columnar `MergeTree` Store** (with `ORDER BY (service, status)`, 4,096-row granules, a sparse `primary.idx`, and Run-Length Encoding) across 200,000 log rows:

```python
#!/usr/bin/env python3
"""Benchmark & verify Row-Oriented scan vs Sparse-Indexed RLE Columnar scan."""
import bisect
import random
import time
from dataclasses import dataclass
from typing import Any, List, Tuple


@dataclass
class RLEColumn:
    """Run-Length Encoded column chunk inside a Granule."""
    values: List[Any]
    lengths: List[int]

    @classmethod
    def encode(cls, raw: List[Any]) -> "RLEColumn":
        if not raw:
            return cls([], [])
        vals, lens = [raw[0]], [1]
        for x in raw[1:]:
            if x == vals[-1]:
                lens[-1] += 1
            else:
                vals.append(x)
                lens.append(1)
        return cls(vals, lens)

    @property
    def storage_units(self) -> int:
        return len(self.values) * 2


class MiniMergeTreePart:
    def __init__(self, rows: List[Tuple[str, int, float, str]], granule_size: int = 4096):
        self.granule_size = granule_size
        # 1. Sort rows by ORDER BY (service, status)
        rows_sorted = sorted(rows, key=lambda r: (r[0], r[1]))
        self.num_rows = len(rows_sorted)

        # 2. Build Sparse Primary Index (1 mark per 4,096 rows) + Column Granules
        self.sparse_index: List[Tuple[str, int]] = []
        self.col_service: List[RLEColumn] = []
        self.col_status: List[RLEColumn] = []
        self.col_latency: List[List[float]] = []
        self.col_payload: List[List[str]] = []  # Heavy unused column!

        for offset in range(0, self.num_rows, granule_size):
            chunk = rows_sorted[offset : offset + granule_size]
            self.sparse_index.append((chunk[0][0], chunk[0][1]))
            self.col_service.append(RLEColumn.encode([r[0] for r in chunk]))
            self.col_status.append(RLEColumn.encode([r[1] for r in chunk]))
            self.col_latency.append([r[2] for r in chunk])
            self.col_payload.append([r[3] for r in chunk])

    def query_error_stats(self, target_service: str, min_status: int = 500) -> Tuple[int, float, int]:
        """SELECT COUNT(*), AVG(latency) WHERE service = target_service AND status >= min_status"""
        # Use sparse index to find candidate granule range [g_start, g_end]
        g_start = max(0, bisect.bisect_left(self.sparse_index, (target_service, min_status)) - 1)
        g_end = bisect.bisect_right(self.sparse_index, (target_service, 999))

        count = 0
        latency_sum = 0.0
        granules_scanned = 0

        for g in range(g_start, min(g_end, len(self.sparse_index))):
            granules_scanned += 1
            srv_rle = self.col_service[g]
            sts_rle = self.col_status[g]
            lat_vec = self.col_latency[g]
            # Fast RLE check: if target_service isn't in this granule at all, skip!
            if target_service not in srv_rle.values:
                continue
            # Decode RLE runs only for matching granules (never touching col_payload!)
            srv_idx = 0
            row_idx = 0
            for s_val, s_len in zip(srv_rle.values, srv_rle.lengths):
                if s_val == target_service:
                    # Check status_code inside [row_idx, row_idx + s_len)
                    st_pos = 0
                    for st_val, st_len in zip(sts_rle.values, sts_rle.lengths):
                        overlap_lo = max(row_idx, st_pos)
                        overlap_hi = min(row_idx + s_len, st_pos + st_len)
                        if overlap_hi > overlap_lo and st_val >= min_status:
                            count += overlap_hi - overlap_lo
                            latency_sum += sum(lat_vec[overlap_lo:overlap_hi])
                        st_pos += st_len
                row_idx += s_len

        return count, (latency_sum / count if count else 0.0), granules_scanned


if __name__ == "__main__":
    random.seed(42)
    services = ["auth", "billing", "catalog", "checkout", "edge", "feed", "Order", "search"]
    statuses = [200, 200, 200, 200, 200, 201, 400, 404, 500, 502, 503]
    N = 200_000
    rows = [
        (
            random.choice(services),
            random.choice(statuses),
            round(random.uniform(1.0, 250.0), 2),
            "x" * 200,  # 200-byte request metadata column not needed by query
        )
        for _ in range(N)
    ]

    part = MiniMergeTreePart(rows, granule_size=4096)

    # 1. Measure RLE compression ratio on sorted `service` and `status` columns
    raw_units = N * 2
    rle_units = sum(c.storage_units for c in part.col_service) + sum(c.storage_units for c in part.col_status)
    print(f"Total rows                   : {N:,} across {len(part.sparse_index)} granules (4,096 rows/granule)")
    print(f"Sparse primary.idx entries   : {len(part.sparse_index)} marks (vs {N:,} dense index entries)")
    print(f"RLE Compression on sort keys : {raw_units / rle_units:.1f}x reduction ({raw_units:,} -> {rle_units:,} units)")

    # 2. Compare Row-Scan vs Sparse-Indexed Columnar Query
    t0 = time.perf_counter()
    row_hits = [r[2] for r in rows if r[0] == "checkout" and r[1] >= 500]
    row_count, row_avg = len(row_hits), sum(row_hits) / len(row_hits)
    row_ms = (time.perf_counter() - t0) * 1000

    t1 = time.perf_counter()
    col_count, col_avg, gran_scanned = part.query_error_stats("checkout", 500)
    col_ms = (time.perf_counter() - t1) * 1000

    assert row_count == col_count and abs(row_avg - col_avg) < 1e-6
    print(f"Query result                 : count={col_count}, avg_latency={col_avg:.2f} ms")
    print(f"Granules scanned             : {gran_scanned}/{len(part.sparse_index)} ({gran_scanned/len(part.sparse_index)*100:.1f}% of table)")
    print(f"Execution time               : Row scan = {row_ms:.2f} ms | Sparse-RLE Columnar = {col_ms:.2f} ms ({row_ms/col_ms:.1f}x faster)")
```
