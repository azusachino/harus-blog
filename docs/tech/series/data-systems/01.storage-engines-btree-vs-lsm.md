Every database query eventually turns into block I/O syscalls (`pread64`, `pwrite64`, `io_uring_enter`, `fsync`) against an underlying storage engine. Whether you are running MySQL (InnoDB), PostgreSQL, RocksDB, TiKV, or Pebble, the storage engine's primary job is to map logical keys to physical disk bytes while balancing three competing forces: **Read Amplification (RA)**, **Write Amplification (WA)**, and **Space Amplification (SA)**.

In **Chapter 01**, we start with Martin Kleppmann's foundational framing from *Designing Data-Intensive Applications* (DDIA) and dissect the two dominant storage engine families for transactional workloads: **Page-oriented B+ Trees** (InnoDB) and **Log-Structured Merge-Trees** (LSM-Trees in LevelDB/RocksDB).

## Before you start

This series is for programmers who have used a database but never looked inside one, and the chapters build on each other, so read them in order.

A database has to turn "store this row" into bytes on a disk, and disks are bad at small random writes. Picture a paper address book. You can keep it sorted and squeeze each new name into the right page, which makes lookups fast but rewrites pages constantly. Or you can jot new entries at the end of a notebook and tidy up later, which makes writing cheap but reading harder. The first approach is a B+ tree (MySQL InnoDB); the second is an LSM-tree (RocksDB, LevelDB). This chapter compares them and shows what each one costs in disk reads, disk writes and space.

Nothing is required beyond basic programming. If `fsync` or page cache are unfamiliar, the Linux systems series covers them from the system-call side, starting at [syscalls and the ABI](/tech/series/linux-systems/01.syscalls-and-abi/).

Terms used in this chapter:

- **storage engine**: the part of a database that decides how data is laid out on disk and how it is read back.
- **B+ tree**: a sorted, wide, shallow tree of fixed-size pages where all the rows live in the leaf pages.
- **LSM-tree**: a design that buffers writes in memory, flushes them as sorted files, and merges those files in the background.
- **SSTable**: an immutable file of key-value pairs sorted by key.
- **compaction**: the background merge of sorted files that drops overwritten and deleted entries.
- **WAL (write-ahead log)**: a sequential log written before the real change, so a crash can be repaired by replaying it.
- **write amplification**: bytes physically written to disk divided by bytes the application asked to write.
- **p99 latency**: the response time that 99% of requests beat; the slowest 1% are worse.

## 1. The DDIA Lens — Reliability, Tail Latency & The RUM Conjecture

Before inspecting on-disk data structures, we establish how we measure a storage engine under load:

1. **Throughput vs. Response Time Percentiles:** Average latency is an operational vanity metric. If a single user HTTP request fans out to $k = 10$ storage shards in parallel and waits for all of them, the probability that the overall request is faster than the 99th percentile ($p99$) of an individual node is only $0.99^{10} \approx 90.4\%$. Tail-latency spikes ($p99$, $p99.9$) caused by B+ tree dirty-page flushing or LSM-Tree compaction stalls directly dictate user-visible latency.
2. **The RUM Conjecture (Read, Update, Memory/Space):** At most two of three costs can be minimized simultaneously:
   - **Read Amplification (RA):** Bytes read from storage divided by logical bytes returned to the caller.
   - **Write Amplification (WA):** Bytes written to underlying flash/disk divided by logical bytes written to the database. On SSDs with finite Flash Program/Erase (P/E) cycles and Flash Translation Layer (FTL) garbage collection, high WA directly degrades both SSD lifespan and write throughput.
   - **Space Amplification (SA):** Total size of database files on disk divided by total logical size of live un-deleted data (e.g., dead tuples, fragmentation, uncompacted SSTable versions).

```text
                     Read Amplification (RA)
                            /\
                           /  \
                          /    \
       B+ Tree (InnoDB)  /      \  Append-Only Log + Hash Index (Bitcask)
       Low RA, Moderate /        \ Low RA (1 seek), Low WA,
       SA, High WA     /   RUM    \ High Memory/Space overhead
                      /____________\
Write Amplification (WA)          Space Amplification (SA)
                     \              /
                      \ LSM-Tree   /
                       \ (RocksDB)/
                        \________/
                 Low WA, Low SA (Leveled),
                 Higher Point/Range RA
```

## 2. From Append-Only Logs to Bitcask Hash Indexes

What is the fastest way to write data to a disk or SSD? **Sequential append.**

Suppose we build a key-value store backed by an append-only log file where each write appends a binary record `[crc32 | timestamp | key_size | val_size | key | value]`:

- **Writes are $O(1)$ sequential I/O.** Even on spinning disks, sequential writes avoid mechanical head seeks; on NVMe SSDs, sequential large-block writes align cleanly with flash erase blocks.
- **Reads without an index are $O(N)$** full scans from the tail of the log backward.

### In-Memory Hash Table + Segmented Log (Bitcask / Riak Engine)

To make reads $O(1)$ without sacrificing sequential writes, **Bitcask** maintains an in-memory hash map (`KeyDir`) mapping every key to a lightweight tuple `(file_id, byte_offset, value_size, timestamp)`:

1. **Write Path:** Append the record to the active log segment file, then update `KeyDir[key]` to point to the new `(file_id, byte_offset)`.
2. **Read Path:** Look up `KeyDir[key]` in RAM and issue a single `pread64(fd, buf, value_size, byte_offset)` syscall. If the filesystem page cache holds the segment, it costs zero disk seeks; otherwise, exactly **1 disk read**.
3. **Compaction & Tombstones:** Because updates never overwrite old bytes in place, old log segments accumulate superseded values and deletion markers (**tombstones**). When an active segment reaches a size threshold (e.g., 256 MB), it is sealed as immutable, and a background thread compacts closed segments by keeping only the latest live version of each key, writing a clean segment file plus a `.hint` index file for fast startup recovery.

**Why doesn't every database use Bitcask?**

- **RAM Constraint:** Every single key in the database must fit in the in-memory hash table. If you have 10 billion keys of 64 bytes each, the hash index alone consumes $> 640\text{ GB}$ of RAM.
- **Range Scans are $O(N)$:** A hash map scrambles key order; executing `SELECT * FROM events WHERE key BETWEEN '2026-04-01' AND '2026-04-19'` requires scanning every key in memory.

To support range queries and keyspaces larger than RAM, we need ordered on-disk structures: **B+ Trees** or **LSM-Trees**.

## 3. B+ Tree Storage Engines (MySQL InnoDB Internals)

A **B+ Tree** partitions data into fixed-size on-disk blocks called **pages** (16 KB by default in MySQL InnoDB, 8 KB in PostgreSQL) and updates those pages **in place**.

```text
                   [ Root Page (16 KB, Level 3) ]
                   /             |              \
     [Internal Page L2]  [Internal Page L2]  [Internal Page L2]
          /        \
[Internal Page L1] [Internal Page L1]
     /          \
[Leaf Page L0] <===> [Leaf Page L0] <===> [Leaf Page L0]  (Doubly-linked for range scans)
(Full rows or        (Sorted by PK via
 indexed columns)     Page Directory slots)
```

### Why 4 Levels of InnoDB B+ Tree Can Hold ~25-250 TB

Why do B+ Trees in production almost never exceed depth 3 or 4? Let's do the exact page math for an InnoDB table with a `BIGINT` (8-byte) primary key:

- Each **non-leaf (internal) page** is $16,384\text{ bytes}$. Subtracting ~128 bytes for page headers (`FIL Header`, `Page Header`, infimum/supremum records, checksum trailer), roughly $16,256\text{ bytes}$ remain for child pointers.
- Each child entry stores `[8-byte BIGINT key + 6-byte child page pointer] = 14 bytes`.
- **Branching factor** $B \approx \lfloor 16,256 / 14 \rfloor \approx 1,160$ child pointers per internal page.
- At **Level 3** (1 Root + 2 Internal levels + 1 Leaf level):
  $$\text{Leaf Pages} = 1,160^3 \approx 1.56 \times 10^9 \text{ leaf pages}$$
- Since each leaf page is 16 KB, total addressable data at depth 4 is:
  $$1.56 \times 10^9 \times 16\text{ KB} \approx 25\text{ TB}$$
  (And if leaf rows are 1 KB each, 15 rows per leaf page yields **~23.4 billion rows** with at most **4 page lookups**—and because the root and top internal levels stay pinned in the `InnoDB Buffer Pool`, a point lookup typically performs **0 or 1 physical disk I/O**.)

### Clustered vs. Secondary Indexes & Covering Indexes

In InnoDB, every table is organized around a **Clustered Index** (the Primary Key B+ Tree):

- **Clustered Index Leaf Pages:** Store the entire row payload (`trx_id`, `roll_ptr`, and all non-indexed columns) sorted by Primary Key.
- **Secondary Index Leaf Pages:** Store only `(indexed_column_values, primary_key_value)`—never a raw physical byte pointer! Why? Because when a leaf page splits or rows move across pages, updating raw physical pointers across 5 secondary indexes would cause catastrophic write amplification. Instead, a secondary index lookup finds the `primary_key_value` and performs a second B+ Tree traversal on the Clustered Index (**Bookmark Lookup / 回表**).
- **Covering Index:** If a query `SELECT status, created_at FROM orders WHERE user_id = 42` can be satisfied entirely from the columns stored in `idx_user_status_created(user_id, status, created_at)`, InnoDB reads only the secondary index leaf page (`Using index` in `EXPLAIN`) and avoids the clustered index lookup altogether.
- **Index Condition Pushdown (ICP):** For `INDEX(a, b, c)` and query `WHERE a = 1 AND b LIKE '%foo%' AND c = 10`, the leftmost prefix rule stops range-seeking after `a = 1`. Without ICP, the storage engine fetches the full clustered row for every `a = 1` entry and hands it to the MySQL Server layer to filter `b` and `c`. With ICP (`Using index condition`), InnoDB evaluates `b LIKE '%foo%' AND c = 10` directly on the secondary index tuple before touching the clustered index.

### Write-Ahead Log (Redo Log), Two-Phase Commit & Change Buffer

Modifying a 16 KB B+ Tree page in place is dangerous and expensive:

1. **Torn Pages (Partial Page Writes):** Linux filesystems and hardware often write in 4 KB sectors. If power fails halfway through flushing a 16 KB InnoDB page, 4 KB is new and 12 KB is old—a corrupted page that even redo logs cannot patch because redo logs record physical-logical page deltas ("apply change $X$ to offset $Y$ of structurally valid page $P$"). InnoDB solves this with the **Doublewrite Buffer**: before flushing dirty pages to `.ibd` data files, InnoDB writes them sequentially to a 2 MB doublewrite area in the system tablespace (`ibdata1` / `.dblwr`). On crash recovery, if a page checksum fails, InnoDB restores the intact 16 KB page from the Doublewrite Buffer before replaying the Redo Log.
2. **Redo Log vs. Binlog Two-Phase Commit:**
   - **InnoDB Redo Log (`ib_logfile`):** Circular physical-logical WAL owned by the InnoDB storage engine for crash-safe durability (`prepare` $\rightarrow$ `commit`).
   - **MySQL Binlog:** Append-only logical event log owned by the MySQL Server layer for point-in-time recovery and replication.
   - To guarantee that crash recovery and replicas never diverge, MySQL executes an internal **XA Two-Phase Commit**:

     ```text
     [1. Write Redo Log (PREPARE)] ---> fsync (controlled by innodb_flush_log_at_trx_commit = 1)
                 |
                 v
     [2. Write Binlog]             ---> fsync (controlled by sync_binlog = 1)
                 |
                 v
     [3. Write Redo Log (COMMIT)]  ---> Marks transaction committed (no extra fsync needed;
                                        if crash occurs after step 2, recovery sees Redo=PREPARE
                                        + intact Binlog XID and commits the transaction!)
     ```

3. **Change Buffer:** When updating a **non-unique secondary index**, the target leaf page is rarely in the Buffer Pool because secondary key values are distributed randomly. Reading that 16 KB page from disk synchronously on every `INSERT/UPDATE` would ruin write throughput (`Unique Index` *must* read the page to check uniqueness constraints). For non-unique secondary indexes, InnoDB records the modification in the in-memory/persistent **Change Buffer** and merges it lazily the next time that leaf page is loaded into the Buffer Pool by a read query or background purge thread.

### Why `DELETE` Does Not Shrink the `.ibd` File

When you run `DELETE FROM logs WHERE created_at < '2025-01-01'`, InnoDB does **not** release bytes back to the ext4/XFS filesystem:

- Deleting a row merely flips the `delete_mask` flag in the record header (and later the background `purge` thread unlinks the record and adds its byte range to the page's internal `PAGE_FREE` linked list for reuse).
- If an entire 16 KB page becomes empty, that page is marked free inside the `.ibd` tablespace so future page splits can reuse it, creating **tablespace holes/fragmentation**.
- To reclaim OS disk space and rebuild dense leaf pages (typically packed to 15/16ths capacity), you must rebuild the tablespace via `ALTER TABLE tbl ENGINE=InnoDB` (Online DDL, which creates a shadow `.ibd` file and replays a row-log of concurrent DML).

## 4. LSM-Tree & SSTable Storage Engines (RocksDB / LevelDB)

While B+ Trees excel at predictable point reads, updating random keys in a B+ Tree causes severe **Write Amplification**: inserting a 100-byte row can dirty and eventually flush a full 16 KB page (plus Doublewrite + Redo Log), yielding $\text{WA} \ge 10\text{--}30\times$.

**Log-Structured Merge-Trees (LSM-Trees)** flip the trade-off: **never modify files in place.** Turn every random write, update, and delete into a sequential append and background multi-way merge sort.

### The RocksDB Write Path

<Archify src="./diagrams/lsm-write-and-compaction.workflow.json" />

```text
Client Write (Put / Delete)
   │
   ├──► 1. Append to WAL (on-disk sequential log for crash recovery)
   │
   └──► 2. Insert into active MemTable (in-memory concurrent SkipList, ~64 MB)
             │
             ▼ (When active MemTable fills up)
        3. Freeze as Immutable MemTable (IMM); allocate fresh active MemTable
             │
             ▼ (Background flush thread)
        4. Flush IMM to Level 0 (L0) SSTable file on disk
```

Notice why `Delete(key)` in an LSM-Tree does not free disk space immediately: because SSTables on disk are immutable, deleting a key appends a **Tombstone marker** (`key, seq_num, kTypeDeletion`) to the WAL and `MemTable`. Space is only reclaimed when compaction eventually merges that tombstone down to the bottommost level and drops both the old value and the tombstone.

### SSTable Internal Layout & The Read Path

An **SSTable (Sorted String Table)** is an immutable file divided into fixed-size compressed **Data Blocks** (e.g., 4 KB–16 KB, prefix-compressed with delta-encoded keys and restart points every $k=16$ keys) followed by metadata blocks at the tail of the file:

- **Filter Block:** Holds a **Bloom Filter** (or Ribbon Filter) over all keys in the SSTable (or per data block).
- **Index Block:** Maps the last key of each Data Block to its byte offset inside the SSTable.
- **Footer:** Fixed-size trailer pointing to the Index Block and Meta-Index Block.

When a client calls `Get(key)`:

1. Search the active `MemTable` (in-memory SkipList).
2. Search any unflushed `Immutable MemTables`.
3. Search **Level 0 (`L0`) SSTables**: Because `L0` files are direct dumps of `MemTable` time windows, **their key ranges overlap!** A point lookup that misses in memory must check the Bloom filter of *every* `L0` file whose `[min_key, max_key]` overlaps `key` (often 4 to 8 files).
4. Search **Level 1 (`L1`) through Level $K$ (`L6`)**: In Leveled Compaction, every level $\ge 1$ is partitioned into SSTables with **strictly disjoint, non-overlapping key ranges**. Using binary search on the level's file manifest, at most **1 SSTable per level** can contain `key`.

### How Bloom Filters Rescue LSM-Tree Point Reads

Without Bloom filters, looking up a non-existent key in an LSM-Tree with 4 `L0` files and 6 deeper levels (`L1`–`L6`) would require reading up to $4 + 6 = 10$ SSTables from disk.

A **Bloom filter** is a bit array of $m$ bits initialized to 0, paired with $k$ independent hash functions. For $n$ keys, the optimal number of hash functions is $k = \frac{m}{n} \ln 2$, yielding a false-positive probability:
$$p \approx \left(1 - e^{-kn/m}\right)^k = e^{-\frac{m}{n} (\ln 2)^2}$$
With the RocksDB standard setting of **$m/n = 10$ bits per key** ($k = 7$):
$$p \approx e^{-10 \times 0.48045} \approx 0.0082 \text{ (0.82\% false positive rate)}$$
Over 99% of checks against SSTables that do not contain `key` are rejected purely in RAM using $10\text{ bits} = 1.25\text{ bytes}$ per key!

> **Caveat (Range Queries & Prefix Filters):** A standard whole-key Bloom filter cannot help a range scan (`Seek("user:1000")`) because you don't know the exact keys inside the range ahead of time. RocksDB solves this for fixed-prefix queries by configuring a `prefix_extractor` (building a prefix Bloom filter so `Seek("user:1000:")` skips SSTables containing no keys with that prefix).

## 5. Compaction Strategies & RocksDB Write-Stall Debugging

### Size-Tiered (STCS) vs. Leveled Compaction (LCS)

| Dimension | Size-Tiered Compaction (Cassandra / ScyllaDB default) | Leveled Compaction (RocksDB / LevelDB default) |
| :--- | :--- | :--- |
| **How it works** | Merges $K$ (e.g., 4) similarly-sized SSTables into one $4\times$ larger SSTable. Overlapping key ranges exist across tiers. | Each level $L_i$ is $10\times$ larger than $L_{i-1}$ ($L_1 = 256\text{ MB}, L_2 = 2.56\text{ GB}, \dots$) and partitioned into non-overlapping 64 MB SSTables. |
| **Write Amplification (WA)** | **Low ($\sim 4\text{--}8\times$):** Each SSTable is rewritten only once per size tier promotion. | **Higher ($\sim 10\text{--}30\times$):** Merging one SSTable from $L_{i-1}$ into $L_i$ can overlap up to 10 SSTables in $L_i$, rewriting all of them. |
| **Space Amplification (SA)** | **High (up to $50\%+$ free space required):** Compacting the largest tier temporarily duplicates almost half the database on disk; obsolete keys linger longer. | **Very Low ($\sim 10\text{--}15\%$):** Roughly $90\%$ of all data lives in the bottommost level ($L_{\max}$), and only $1/10$th is duplicated in upper levels. |
| **Read Amplification (RA)** | **Higher:** Multiple overlapping SSTables across tiers must be checked on point/range reads. | **Lower:** At most 1 SSTable per level ($L_1\dots L_{\max}$) overlaps any given key. |

### Debugging RocksDB Production Write Stalls

One of the most common production incidents in RocksDB, TiKV, or Kafka Streams state stores is a sudden **Write Stall** (throughput drops from 100k ops/s to near zero, or `Status::Incomplete("Write stall")` is returned). Why does an engine designed for fast writes suddenly throttle writes?

Because if client writes enter the `MemTable` faster than background threads can flush `MemTable -> L0` or compact `L0 -> L1 -> L2`, two bad things happen if unchecked:

1. Unbounded `L0` file accumulation causes point-read latency to explode ($O(\text{number of } L0 \text{ files})$).
2. Unbounded compaction debt eventually exhausts disk space.

RocksDB triggers write throttling or full stops on **three specific thresholds**:

1. **MemTable Flush Backpressure (`max_write_buffer_number`):** If all `max_write_buffer_number` (e.g., 4) MemTables are full waiting to be flushed to `L0`, writes halt completely.
2. **L0 File Count Stall (`level0_slowdown_writes_trigger` / `level0_stop_writes_trigger`):** Default 20 (slowdown) and 36 (stop). When `L0` files pile up faster than the single-threaded `L0 -> L1` compaction can drain them, RocksDB artificially sleeps client write threads.
3. **Pending Compaction Bytes (`soft_pending_compaction_bytes_limit` = 64 GB, `hard_pending_compaction_bytes_limit` = 256 GB):** Even if `L0` looks small, if `L1..L5` exceed their target byte budgets by $> 64\text{ GB}$ (for instance, after a bulk backfill or a massive `TTL` expiration storm in `TTLDB`), RocksDB throttles incoming writes to a low `delayed_write_rate` so background compactions (`max_background_jobs`) can catch up.

## 6. Verification Lab — LSM-Tree, Bloom Filter & Leveled Compaction Simulator

Save and run the following self-contained Python script to observe how a `MemTable`, a 10-bits/key Bloom Filter, `L0` overlapping SSTables, Tombstones, and `L0 -> L1` non-overlapping Leveled Compaction work together, and measure empirical Bloom Filter false-positive rates and Write/Space Amplification:

```python
#!/usr/bin/env python3
"""LSM-Tree Storage Engine + Bloom Filter + Leveled Compaction Verifier."""
import hashlib
import math
from dataclasses import dataclass, field
from typing import Dict, List, Optional, Tuple

TOMBSTONE = "__TOMBSTONE__"


class BloomFilter:
    """Standard m-bit, k-hash Bloom Filter."""

    def __init__(self, expected_keys: int, bits_per_key: int = 10):
        self.m = max(64, expected_keys * bits_per_key)
        self.k = max(1, int(round(bits_per_key * math.log(2))))
        self.bits = bytearray((self.m + 7) // 8)

    def _hashes(self, key: str) -> List[int]:
        digest = hashlib.sha256(key.encode("utf-8")).digest()
        h1 = int.from_bytes(digest[:8], "big")
        h2 = int.from_bytes(digest[8:16], "big") or 1
        return [(h1 + i * h2) % self.m for i in range(self.k)]

    def add(self, key: str) -> None:
        for bit_idx in self._hashes(key):
            self.bits[bit_idx >> 3] |= 1 << (bit_idx & 7)

    def might_contain(self, key: str) -> bool:
        return all(
            (self.bits[bit_idx >> 3] & (1 << (bit_idx & 7))) != 0
            for bit_idx in self._hashes(key)
        )


@dataclass
class SSTable:
    sst_id: int
    level: int
    # Sorted list of (key, seq_num, value_or_tombstone)
    entries: List[Tuple[str, int, str]]
    bloom: BloomFilter = field(init=False)

    def __post_init__(self) -> None:
        self.entries.sort(key=lambda x: (x[0], -x[1]))
        self.bloom = BloomFilter(len(self.entries), bits_per_key=10)
        for k, _, _ in self.entries:
            self.bloom.add(k)

    @property
    def min_key(self) -> str:
        return self.entries[0][0]

    @property
    def max_key(self) -> str:
        return self.entries[-1][0]

    def lookup(self, key: str) -> Tuple[Optional[str], bool]:
        """Returns (value_or_tombstone, did_block_io)."""
        if key < self.min_key or key > self.max_key:
            return None, False
        if not self.bloom.might_contain(key):
            return None, False
        # Binary search sorted entries (simulating Index Block + Data Block read)
        lo, hi = 0, len(self.entries) - 1
        while lo <= hi:
            mid = (lo + hi) // 2
            mk, _, mv = self.entries[mid]
            if mk == key:
                return mv, True
            elif mk < key:
                lo = mid + 1
            else:
                hi = mid - 1
        return None, True  # Bloom filter false positive!


class MiniLSM:
    def __init__(self, memtable_cap: int = 50, l0_compaction_trigger: int = 4):
        self.memtable_cap = memtable_cap
        self.l0_trigger = l0_compaction_trigger
        self.seq = 0
        self.memtable: Dict[str, Tuple[int, str]] = {}
        self.l0: List[SSTable] = []  # Newest first, overlapping key ranges
        self.l1: List[SSTable] = []  # Sorted, strictly non-overlapping key ranges
        self.next_sst_id = 1
        self.logical_records_written = 0
        self.physical_records_written = 0

    def put(self, key: str, value: str) -> None:
        self._write(key, value)

    def delete(self, key: str) -> None:
        self._write(key, TOMBSTONE)

    def _write(self, key: str, value: str) -> None:
        self.seq += 1
        self.memtable[key] = (self.seq, value)
        self.logical_records_written += 1
        self.physical_records_written += 1  # WAL write
        if len(self.memtable) >= self.memtable_cap:
            self.flush_memtable()

    def flush_memtable(self) -> None:
        if not self.memtable:
            return
        entries = [(k, seq, val) for k, (seq, val) in self.memtable.items()]
        sst = SSTable(self.next_sst_id, level=0, entries=entries)
        self.next_sst_id += 1
        self.l0.insert(0, sst)  # Newest L0 at index 0
        self.physical_records_written += len(entries)
        self.memtable.clear()
        if len(self.l0) >= self.l0_trigger:
            self.compact_l0_to_l1(bottommost=True)

    def compact_l0_to_l1(self, bottommost: bool = True) -> None:
        """Merge all overlapping L0 SSTables and existing L1 SSTables into disjoint L1 files."""
        merged: Dict[str, Tuple[int, str]] = {}
        for sst in reversed(self.l1):
            for k, seq, val in sst.entries:
                if k not in merged or seq > merged[k][0]:
                    merged[k] = (seq, val)
        for sst in reversed(self.l0):  # Oldest to newest
            for k, seq, val in sst.entries:
                if k not in merged or seq > merged[k][0]:
                    merged[k] = (seq, val)

        # Deduplicate and drop tombstones at bottommost level
        clean_entries = sorted(
            (k, seq, val)
            for k, (seq, val) in merged.items()
            if not (bottommost and val == TOMBSTONE)
        )
        self.l0.clear()
        self.l1.clear()
        chunk_size = self.memtable_cap
        for i in range(0, len(clean_entries), chunk_size):
            chunk = clean_entries[i : i + chunk_size]
            self.l1.append(SSTable(self.next_sst_id, level=1, entries=chunk))
            self.next_sst_id += 1
            self.physical_records_written += len(chunk)

    def get(self, key: str) -> Tuple[Optional[str], int]:
        """Returns (value, sst_block_reads)."""
        if key in self.memtable:
            _, val = self.memtable[key]
            return (None if val == TOMBSTONE else val), 0
        io_reads = 0
        for sst in self.l0:
            val, did_io = sst.lookup(key)
            io_reads += int(did_io)
            if val is not None:
                return (None if val == TOMBSTONE else val), io_reads
        # L1 has disjoint key ranges: at most 1 SSTable can overlap `key`
        for sst in self.l1:
            if sst.min_key <= key <= sst.max_key:
                val, did_io = sst.lookup(key)
                io_reads += int(did_io)
                if val is not None:
                    return (None if val == TOMBSTONE else val), io_reads
                break
        return None, io_reads


if __name__ == "__main__":
    db = MiniLSM(memtable_cap=100, l0_compaction_trigger=4)

    # 2. Verify point lookups & Bloom filter false-positive suppression
```

### Summary of B+ Tree vs. LSM-Tree Selection Rules

| Workload Characteristic | Choose B+ Tree (InnoDB / PostgreSQL) | Choose LSM-Tree (RocksDB / TiKV / Cassandra) |
| :--- | :--- | :--- |
| **Write-heavy random ingestion / time-series** | High WA from 16 KB page rewrites & random page splits | **Winner:** Sequential WAL + MemTable append; 5–10x higher write throughput |
| **Low-latency point reads & predictable $p99$** | **Winner:** Predictable depth-3/4 page lookup; no compaction CPU/IO storms | Tail latency sensitive to `L0` file accumulation and compaction stalls |
| **Disk space efficiency & compression** | ~25–35% internal page fragmentation (`fill_factor` + deleted slots) | **Winner (Leveled):** Dense block compression, no page fragmentation, $\text{SA} \approx 1.1\times$ |
| **Transactional row-level locking (`SELECT FOR UPDATE`)** | **Winner:** Page/record-level locks integrate naturally with in-place pages | Requires external lock table in memory because on-disk SSTables are immutable |
