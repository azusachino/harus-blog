When multiple clients read and mutate the same database simultaneously, concurrency bugs emerge that no amount of network retry logic can fix: partial failures halfway through a multi-row update, race conditions overwriting another user's changes (**Lost Updates**), or two transactions reading overlapping invariants and breaking a business rule (**Write Skew**).

**Transactions** collapse a complex combinatorial space of concurrent interleavings and partial crash states into a simple contract: either the entire group of reads and writes succeeds atomically as if isolated from concurrent transactions, or it aborts cleanly with zero side effects.

In **Chapter 05**, we look past textbook ACID definitions and inspect the exact data structures and algorithms that power concurrency control in production: **MVCC (`ReadView` + Undo Log chains in MySQL InnoDB vs. `xmin/xmax` heap tuples in PostgreSQL)**, **Current Read vs. Snapshot Read**, **Next-Key Locking**, **Write Skew**, and **Serializable Snapshot Isolation (SSI)**.

## Before you start

Two people book the last seat on a flight at the same moment. Each program reads "1 seat left", each decides to sell it, each writes "0 left", and two tickets exist for one seat. A transaction is the database's tool against this: a group of reads and writes that either all take effect or none do, while behaving as if other transactions were not running at the same time. Perfect isolation is expensive, so databases offer weaker levels, and the gaps between them are where real bugs live.

This chapter shows how InnoDB and PostgreSQL keep several versions of a row so readers do not block writers, which locks InnoDB takes, and which anomalies (lost update, write skew) still slip through.

Chapter 01's [WAL and undo concepts](/tech/series/data-systems/01.storage-engines-btree-vs-lsm/) are reused here. Knowing basic SQL (`BEGIN`, `COMMIT`, `SELECT ... FOR UPDATE`) is enough.

Terms used in this chapter:

- **transaction**: a group of operations that commit together or roll back together.
- **isolation level**: a setting (read committed, repeatable read, serializable) controlling what a transaction may see of concurrent ones.
- **MVCC**: multi-version concurrency control, keeping old versions of rows so reads see a consistent snapshot without locking.
- **undo log**: records of previous row values, used for rollback and to rebuild older versions.
- **ReadView**: InnoDB's snapshot, a list of which transactions counted as committed when it was taken.
- **gap lock / next-key lock**: InnoDB locks on the space between index entries, used to block phantom rows.
- **lost update**: two transactions read the same value and the later write silently erases the earlier one.
- **write skew**: two transactions read overlapping data, write different rows, and together break a rule neither broke alone.
- **SSI**: serializable snapshot isolation, which detects dangerous read-write patterns and aborts one transaction.

## 1. ACID in Practice & The Isolation Hierarchy

1. **Atomicity (Abortability):** Not about concurrency! Atomicity means if a transaction fails after updating 3 of 5 rows, the storage engine uses its **Undo Log** to roll back those 3 changes so no partial state remains.
2. **Consistency:** An application-level property (invariants like $\text{debits} + \text{credits} = 0$). The database preserves invariants only if the application selects a sufficiently strong **Isolation Level**.
3. **Isolation:** Controls how much a running transaction can be affected by concurrent transactions.
4. **Durability:** Once `COMMIT` returns `OK`, the transaction's WAL / Redo Log has been flushed to non-volatile storage (or replicated to a consensus quorum).

### Concurrency Anomalies & SQL Isolation Levels

| Isolation Level | Dirty Read | Non-Repeatable Read | Phantom Read | Lost Update | Write Skew |
| :--- | :---: | :---: | :---: | :---: | :---: |
| **Read Uncommitted** | Possible | Possible | Possible | Possible | Possible |
| **Read Committed (RC)** *(Postgres / Oracle default)* | Prevented | Possible | Possible | Possible | Possible |
| **Repeatable Read (RR) / Snapshot Isolation** *(MySQL InnoDB default)* | Prevented | Prevented | Prevented *(via MVCC + Next-Key Locks in InnoDB)* | Prevented *(in Postgres SI; needs `FOR UPDATE` or CAS in InnoDB!)* | **Possible!** |
| **Serializable (2PL or SSI)** | Prevented | Prevented | Prevented | Prevented | **Prevented** |

Let's examine each anomaly and the mechanism that prevents it.

## 2. Multi-Version Concurrency Control (MVCC): InnoDB vs. PostgreSQL

How can a database serve thousands of concurrent `SELECT` queries without blocking `UPDATE` transactions, and without letting `UPDATE` transactions block `SELECT` queries?
**Multi-Version Concurrency Control (MVCC):** Instead of overwriting a row in place and holding an exclusive read/write lock, the database maintains **multiple timestamped/transaction-tagged versions** of the row so readers can view a consistent historical snapshot while writers create a new version.

MySQL InnoDB and PostgreSQL implement MVCC in two fundamentally different ways on disk:

### A. MySQL InnoDB: In-Place Clustered Page + Undo Log Version Chain

In InnoDB, every row in the Clustered Index leaf page carries two hidden system columns:

- **`DB_TRX_ID` (6 bytes):** The monotonic transaction ID (`trx_id`) that last inserted or updated this row.
- **`DB_ROLL_PTR` (7 bytes):** A rollback pointer pointing to the previous version of this row inside the **Undo Log segment**.

```text
Clustered Index Leaf Page (Latest Version in place)
┌────────────────────────────────────────────────────────┐
│ id = 1 | balance = 300 | trx_id = 105 | roll_ptr ──────┼───┐
└────────────────────────────────────────────────────────┘   │
                                                             ▼
Undo Log Version Chain (Constructed lazily if an older ReadView needs it):
┌────────────────────────────────────────────────────────┐
│ id = 1 | balance = 200 | trx_id = 98  | roll_ptr ──────┼───┐
└────────────────────────────────────────────────────────┘   │
                                                             ▼
┌────────────────────────────────────────────────────────┐
│ id = 1 | balance = 100 | trx_id = 80  | roll_ptr = NIL │
└────────────────────────────────────────────────────────┘
```

#### InnoDB `ReadView` Visibility Algorithm

<Archify src="./diagrams/innodb-mvcc-two-phase-commit.sequence.json" />

When a transaction executes a normal `SELECT` (**Consistent Snapshot Read**), InnoDB captures a **`ReadView`** structure containing four fields:

- `m_creator_trx_id`: The reader transaction's own `trx_id`.
- `m_ids`: The sorted list of all **currently active (uncommitted)** read-write transaction IDs at the instant the `ReadView` was created.
- `m_up_limit_id`: The minimum `trx_id` in `m_ids` (**Low Watermark**: every `trx_id < m_up_limit_id` was already committed before the snapshot!).
- `m_low_limit_id`: The next transaction ID to be allocated by InnoDB (**High Watermark**: every `trx_id >= m_low_limit_id` started *after* the snapshot was taken!).

When scanning a row version with `row.trx_id`, InnoDB checks visibility in $O(1)$ / $O(\log |m\_ids|)$ steps:

1. If `row.trx_id == m_creator_trx_id` $\lor$ `row.trx_id < m_up_limit_id`: **Visible!** (Written by self, or committed before snapshot.)
2. If `row.trx_id >= m_low_limit_id`: **Invisible!** (Started after snapshot.) Follow `roll_ptr` to the previous Undo Log version.
3. If `m_up_limit_id <= row.trx_id < m_low_limit_id`: Binary-search `m_ids`:
   - If `row.trx_id in m_ids`: **Invisible!** (That transaction was still uncommitted when our snapshot was taken.) Follow `roll_ptr`.
   - If `row.trx_id not in m_ids`: **Visible!** (Committed before our snapshot.)

> **How InnoDB implements `READ COMMITTED` vs. `REPEATABLE READ` with the exact same `ReadView` code:**
>
> - Under **`READ COMMITTED`**, InnoDB creates a **brand-new `ReadView` at the start of every single `SELECT` statement** inside the transaction.
> - Under **`REPEATABLE READ`**, InnoDB creates the **`ReadView` once at the first `SELECT` statement** (or `START TRANSACTION WITH CONSISTENT SNAPSHOT`) and **reuses that exact same `ReadView` for the entire lifetime of the transaction!**

### B. PostgreSQL: Append-Only Heap Tuples (`xmin` / `xmax`) + `VACUUM`

Unlike InnoDB (which keeps only the latest row in the B+ Tree leaf page and reconstructs older versions from the Undo Log), **PostgreSQL stores all versions of a row directly in the table heap pages!**

- Every heap tuple header carries `xmin` (the transaction XID that inserted this tuple version) and `xmax` (0 if still live, or the XID that deleted/updated this tuple).
- An `UPDATE` in PostgreSQL is literally a **`DELETE` (setting `xmax = current_xid` on the old tuple) + an `INSERT` (writing a new tuple with `xmin = current_xid`)** in the heap page!
- **Trade-off:**
  - *Postgres Advantage:* Rollbacks are instantaneous ($O(1)$: just mark the transaction XID as aborted in `pg_xact`; no Undo Log replay needed!), and reading older versions doesn't require chasing long Undo chains.
  - *Postgres Cost (Write Amplification & `VACUUM` Bloat):* Unless the new tuple fits on the exact same 8 KB page and modifies zero indexed columns (**HOT — Heap-Only Tuple update**), every `UPDATE` in Postgres must insert new index entries into **every secondary index** on the table! Furthermore, dead tuples (`xmax` committed and older than all active snapshots) remain in the heap pages until **Autovacuum (`VACUUM`)** sweeps the table to reclaim space and freezes old 32-bit `xmin` XIDs to prevent **Transaction ID Wraparound**.

## 3. Current Read vs. Snapshot Read & The InnoDB Phantom Read Trap

Wait: what happens if Transaction A is running at `REPEATABLE READ`, and while Transaction A is open, Transaction B inserts and commits a row `(id = 5, val = 'B')`?

1. **Snapshot Read (`SELECT * FROM t WHERE id = 5`):** Uses Transaction A's frozen `ReadView`. Since `trx_B >= m_low_limit_id`, row `id = 5` is **invisible**—no Phantom Read!
2. **Current Read (`SELECT ... LOCK IN SHARE MODE`, `SELECT ... FOR UPDATE`, `UPDATE`, `DELETE`):**
   - **A write (`UPDATE` / `DELETE`) CANNOT use an old `ReadView`!** If Transaction A runs `UPDATE t SET val = 'A' WHERE id = 5`, it *must* read the latest committed version on disk (**Current Read**), otherwise it would corrupt or lose Transaction B's committed update!
   - And here is the famous InnoDB surprise: **once Transaction A updates row `id = 5` via a Current Read, row `id = 5`'s `DB_TRX_ID` becomes `m_creator_trx_id` (Transaction A itself)!**
   - Consequently, if Transaction A subsequently runs a normal `SELECT * FROM t`, row `id = 5` now passes Rule #1 (`row.trx_id == m_creator_trx_id`) and **suddenly appears in Transaction A's snapshot**!

## 4. InnoDB Locking Rules: Record Locks, Gap Locks & Next-Key Locks

To prevent Phantom Reads during **Current Reads** (`SELECT ... FOR UPDATE` / `UPDATE` / `DELETE`) under `REPEATABLE READ`, InnoDB cannot rely on `ReadView`—it must physically prevent concurrent transactions from inserting new rows into the scanned range using **Next-Key Locks**.

InnoDB has three index-level lock primitives (remember: **InnoDB locks index records, not raw rows!**):

1. **Record Lock:** Locks a single existing index entry (e.g., `id = 10`).
2. **Gap Lock:** Locks the open interval *between* two index records (e.g., `(5, 10)`), preventing any concurrent transaction from inserting `id = 7`. **Gap locks never block other Gap locks**—two sessions can hold Gap locks on `(5, 10)` simultaneously; their sole purpose is to block `INSERT Intention Locks`.
3. **Next-Key Lock:** The combination of a Gap Lock + the Record Lock on the right boundary: a left-open, right-closed interval **`(previous_key, current_key]`** (e.g., `(5, 10]`).

### The 5 Golden Rules of InnoDB Next-Key Locking (`REPEATABLE READ`)

Suppose a table has existing rows with `id` (Primary Key) and `age` (Non-Unique Secondary Index) at values **`5, 10, 15, 20`**:

1. **Base Unit:** Every Current Read acquires **Next-Key Locks `(prev, curr]`** on all index records visited during the scan.
2. **Only Visited Indexes Are Locked:** If a query uses a covering secondary Index (`SELECT id FROM t WHERE age = 10 LOCK IN SHARE MODE`), the Clustered Index is never visited and therefore **not locked** (concurrent `UPDATE`s via Primary Key can still proceed unless `FOR UPDATE` is used).
3. **Unique Index Exact Match Degrades to a Record Lock:** If you run `SELECT * FROM t WHERE id = 10 FOR UPDATE` on a **Unique/Primary index** and `id = 10` exists, InnoDB knows no second row with `id = 10` can ever be inserted, so it downgrades the Next-Key Lock `(5, 10]` to a single **Record Lock `[10]`**!
4. **Unique Index Miss Degrades to a Gap Lock:** If you run `WHERE id = 12 FOR UPDATE` and `12` does not exist, the scan visits `15` and downgrades `(10, 15]` to a **Gap Lock `(10, 15)`**.
5. **Non-Unique Index Match Scans Until the First Non-Matching Key:** If you run `WHERE age = 10 FOR UPDATE` on a non-unique index, InnoDB acquires a Next-Key Lock `(5, 10]` on `age = 10`, continues scanning rightward to `age = 15`, and locks the gap **`(10, 15)`** so no concurrent transaction can insert another row with `age = 10`!

## 5. Lost Updates, Write Skew & Serializable Snapshot Isolation (SSI)

Even with MVCC Snapshot Isolation (`REPEATABLE READ`), two dangerous concurrency bugs remain possible unless you understand how reads and writes interact:

### 1. Lost Update (Read-Modify-Write Cycle)

Two transactions concurrently read `counter = 100` in application memory, add `1`, and execute `UPDATE counters SET val = 101 WHERE id = 1`:

- **Fixes:**
  1. **Atomic SQL operations:** `UPDATE counters SET val = val + 1 WHERE id = 1` (takes an exclusive Current-Read lock inside the storage engine).
  2. **Explicit Pessimistic Locking:** `SELECT val FROM counters WHERE id = 1 FOR UPDATE`.
  3. **Compare-and-Swap (Optimistic Locking):** `UPDATE counters SET val = 101, version = version + 1 WHERE id = 1 AND version = 42` (and retry if `affected_rows == 0`).

### 2. Write Skew (Disjoint Write Sets, Overlapping Reads)

Suppose a hospital requires **at least 1 doctor on call** at all times. Currently both **Alice (`on_call = true`)** and **Bob (`on_call = true`)** are on call for Shift #99:

```text
Transaction 1 (Alice)                           Transaction 2 (Bob)
─────────────────────                           ───────────────────
BEGIN (Snapshot Isolation / RR);                BEGIN (Snapshot Isolation / RR);

SELECT COUNT(*) FROM doctors                    SELECT COUNT(*) FROM doctors
WHERE shift = 99 AND on_call = true;            WHERE shift = 99 AND on_call = true;
──► Returns 2 (Safe to leave!)                  ──► Returns 2 (Safe to leave!)

UPDATE doctors SET on_call = false              UPDATE doctors SET on_call = false
WHERE name = 'Alice' AND shift = 99;            WHERE name = 'Bob' AND shift = 99;
(Updates Alice's row — no row lock conflict!)   (Updates Bob's row — no row lock conflict!)

COMMIT; ──► Succeeds!                           COMMIT; ──► Succeeds!
───────────────────────────────────────────────────────────────────────────────────
RESULT: 0 doctors on call! Invariant violated under REPEATABLE READ / Snapshot Isolation!
```

Why did Snapshot Isolation allow this? Because Alice updated **Alice's row** and Bob updated **Bob's row**—their write sets are completely disjoint! Neither transaction modified a row that the other transaction modified; instead, **each transaction modified a row that the other transaction's `SELECT` predicate depended on (`rw-antidependency` cycle)!**

### How to Prevent Write Skew: Materializing Conflicts or SSI

1. **Pessimistic `SELECT ... FOR UPDATE` (or Materializing Conflicts):** If both Alice and Bob run `SELECT * FROM doctors WHERE shift = 99 AND on_call = true FOR UPDATE`, Transaction 1 locks both rows, forcing Transaction 2 to wait until Transaction 1 commits and sees `COUNT = 1`. (If the predicate checks for the *absence* of rows, e.g., booking a meeting room at 14:00, and your DB lacks Gap locks, you lock a materialized `(room_id, hour_slot)` calendar row).
2. **Serializable Snapshot Isolation (SSI, PostgreSQL `SERIALIZABLE`; CockroachDB's serializable isolation is a related but different design):**
   Instead of blocking readers with Two-Phase Locking (2PL), **SSI** lets all transactions run on lock-free MVCC snapshots while recording **`SIREAD` locks** (lightweight in-memory predicate markers tracking which rows/pages each transaction read).
   - If Transaction $T_1$ reads predicate $P$ and Transaction $T_2$ modifies a row matching $P$, that creates a **Read-Write Antidependency ($T_1 \xrightarrow{rw} T_2$)**.
   - When both $T_1 \xrightarrow{rw} T_2$ and $T_2 \xrightarrow{rw} T_1$ form a dangerous cycle, PostgreSQL's SSI engine detects the cycle at `COMMIT` time and aborts one transaction with `SQLSTATE 40001 (could not serialize access due to read/write dependencies among transactions)`, instructing the client to retry cleanly!

## 6. Verification Lab — InnoDB MVCC `ReadView` + Write-Skew / SSI Cycle Detector

Run this self-contained Python script to verify InnoDB's exact 4-watermark `ReadView` visibility algorithm (demonstrating `READ COMMITTED` vs. `REPEATABLE READ` and Undo Log version chain traversal) and see how **Serializable Snapshot Isolation (SSI)** catches the Hospital On-Call **Write Skew** anomaly that Snapshot Isolation misses:

```python
#!/usr/bin/env python3
"""Verify InnoDB MVCC ReadView + Undo Chain and SSI Write-Skew Detection."""
from dataclasses import dataclass, field
from typing import Any, Callable, Dict, List, Optional, Set, Tuple


@dataclass
class RowVersion:
    value: Dict[str, Any]
    trx_id: int
    roll_ptr: Optional["RowVersion"] = None


@dataclass
class ReadView:
    creator_trx_id: int
    active_ids: Set[int]
    up_limit_id: int    # Low watermark: all trx_id < up_limit_id are committed
    low_limit_id: int   # High watermark: next_trx_id to be allocated

    def is_visible(self, trx_id: int) -> bool:
        if trx_id == self.creator_trx_id or trx_id < self.up_limit_id:
            return True
        if trx_id >= self.low_limit_id:
            return False
        return trx_id not in self.active_ids


class MiniMVCCEngine:
    def __init__(self) -> None:
        self.next_trx_id = 100
        self.active_trxs: Set[int] = set()
        self.committed_trxs: Set[int] = set()
        self.rows: Dict[str, RowVersion] = {}
        # SSI tracking: trx_id -> list of read predicates & written keys
        self.siread_keys: Dict[int, Set[str]] = {}
        self.written_keys: Dict[int, Set[str]] = {}
        self.rr_views: Dict[int, ReadView] = {}

    def begin(self) -> int:
        tid = self.next_trx_id
        self.next_trx_id += 1
        self.active_trxs.add(tid)
        self.siread_keys[tid] = set()
        self.written_keys[tid] = set()
        return tid

    def _create_read_view(self, tid: int) -> ReadView:
        active = set(self.active_trxs)
        up = min(active) if active else self.next_trx_id
        return ReadView(tid, active, up_limit_id=up, low_limit_id=self.next_trx_id)

    def select(self, tid: int, key: str, isolation: str = "RR") -> Optional[Dict[str, Any]]:
        if isolation == "RC" or tid not in self.rr_views:
            self.rr_views[tid] = self._create_read_view(tid)
        view = self.rr_views[tid]
        self.siread_keys[tid].add(key)

        curr = self.rows.get(key)
        while curr is not None:
            if view.is_visible(curr.trx_id):
                return dict(curr.value)
            curr = curr.roll_ptr
        return None

    def upsert(self, tid: int, key: str, value: Dict[str, Any]) -> None:
        old = self.rows.get(key)
        self.rows[key] = RowVersion(value=dict(value), trx_id=tid, roll_ptr=old)
        self.written_keys[tid].add(key)

    def commit(self, tid: int, enforce_ssi: bool = False) -> None:
        if enforce_ssi:
            # Check for dangerous rw-antidependency cycle with any already-committed concurrent transaction
            for other in self.committed_trxs:
                # T1 read what T2 wrote AND T2 read what T1 wrote -> Write Skew cycle!
                t1_rw_t2 = bool(self.siread_keys[tid] & self.written_keys.get(other, set()))
                t2_rw_t1 = bool(self.siread_keys[other] & self.written_keys.get(tid, set()))
                if t1_rw_t2 and t2_rw_t1:
                    self.active_trxs.discard(tid)
                    raise RuntimeError(
                        f"SQLSTATE 40001 (SSI Serialization Failure): rw-antidependency cycle "
                        f"detected between Trx {tid} and committed Trx {other}!"
                    )
        self.active_trxs.discard(tid)
        self.committed_trxs.add(tid)


if __name__ == "__main__":
    eng = MiniMVCCEngine()

    # Part 1: Verify InnoDB ReadView (RC vs RR) + Undo Chain traversal
    t_init = eng.begin()
    eng.upsert(t_init, "doc:alice", {"name": "Alice", "on_call": True})
    eng.upsert(t_init, "doc:bob", {"name": "Bob", "on_call": True})
    eng.commit(t_init)

    t_rr = eng.begin()  # Repeatable Read transaction
    t_rc = eng.begin()  # Read Committed transaction
    assert eng.select(t_rr, "doc:alice", "RR")["on_call"] is True
    assert eng.select(t_rc, "doc:alice", "RC")["on_call"] is True

    # Concurrent writer updates Alice and commits
    t_writer = eng.begin()
    eng.upsert(t_writer, "doc:alice", {"name": "Alice", "on_call": False})
    eng.commit(t_writer)

    # RR still sees True via Undo Chain; RC creates a fresh ReadView and sees False!
    rr_val = eng.select(t_rr, "doc:alice", "RR")["on_call"]
    rc_val = eng.select(t_rc, "doc:alice", "RC")["on_call"]
    print(f"MVCC Check after concurrent commit -> RR sees on_call={rr_val} (via Undo Log), RC sees on_call={rc_val}")
    assert rr_val is True and rc_val is False
    eng.commit(t_rr)
    eng.commit(t_rc)

    # Reset Alice to on_call=True for Part 2: Hospital Write Skew Test
    t_reset = eng.begin()
    eng.upsert(t_reset, "doc:alice", {"name": "Alice", "on_call": True})
    eng.commit(t_reset)

    # Both Alice (t1) and Bob (t2) read both doctor rows under Snapshot Isolation
    t1, t2 = eng.begin(), eng.begin()
    c1 = sum(1 for k in ("doc:alice", "doc:bob") if eng.select(t1, k, "RR")["on_call"])
    c2 = sum(1 for k in ("doc:alice", "doc:bob") if eng.select(t2, k, "RR")["on_call"])
    assert c1 == 2 and c2 == 2

    # Alice updates doc:alice, Bob updates doc:bob
    eng.upsert(t1, "doc:alice", {"name": "Alice", "on_call": False})
    eng.upsert(t2, "doc:bob", {"name": "Bob", "on_call": False})
    eng.commit(t1, enforce_ssi=True)  # First commit succeeds

    try:
        eng.commit(t2, enforce_ssi=True)  # Second commit catches the rw-cycle!
        raise AssertionError("SSI should have aborted t2!")
    except RuntimeError as err:
        print(f"SSI Write-Skew Protection Verified -> {err}")
```
