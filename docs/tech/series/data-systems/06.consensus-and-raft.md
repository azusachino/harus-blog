In a single-node kernel, threads share one physical RAM bus and one monotonic CPU timestamp counter (`CLOCK_MONOTONIC`). In a distributed data system, **there is no shared memory, no global physical clock, and no way to distinguish a crashed node from a node across a slow or partitioned network link.**

Every catastrophic outage in distributed storage—split-brain leaders corrupting a database, expired distributed locks allowing double charges, or a cluster freezing during a coordinator failure—traces back to violating one of these physical truths.

In **Chapter 06**, we close our Data Systems series by connecting **Distributed Time (Physical vs. Logical/Hybrid Clocks)**, **Fencing Tokens**, **Atomic Commit (2PC)**, **Raft Consensus**, and **Gossip/SWIM Epidemic Protocols**.

---

## Before you start

On one machine, "which happened first" and "is the other process alive" have clear answers. Across machines they do not: clocks drift, a message that never arrives could mean a crashed node or a slow network, and a process can freeze for seconds (a garbage-collection pause) and wake up believing it is still in charge. Systems that ignore this end up with two leaders both accepting writes.

Here the series ends with the tools that cope: clocks that only count forward, fencing tokens that let storage reject a stale leader, why two-phase commit can get stuck, how Raft elects a leader and agrees on a log, and gossip for spreading membership news.

It builds on [replication in chapter 03](/tech/series/data-systems/03.replication-and-quorums/), where leaders and followers first appear, and on [transactions in chapter 05](/tech/series/data-systems/05.transactions-and-mvcc/) for the commit side.

Terms used in this chapter:

- **wall clock**: the time-of-day clock, which can jump when it is corrected over NTP.
- **monotonic clock**: a clock that only moves forward, good for measuring durations on one machine.
- **logical clock**: a counter that orders events by causality instead of by real time.
- **lease**: a time-limited right to act as leader or hold a lock.
- **fencing token**: an increasing number issued with each lease, so the resource can refuse writes carrying an older one.
- **split brain**: two nodes each believing they are the leader.
- **two-phase commit (2PC)**: a protocol where a coordinator asks all participants to prepare, then tells them to commit.
- **Raft**: a consensus algorithm that elects a leader and replicates a log by majority vote.
- **gossip**: nodes periodically exchange state with random peers until news spreads cluster-wide.

## 1. Unreliable Clocks — Time-of-Day vs. Monotonic vs. Logical Clocks

Every Linux server exposes two fundamentally different hardware-backed software clocks via `clock_gettime(2)`:

| Clock Type | Linux Syscall | Behavior Across NTP Sync | Safe For | Never Use For |
| :--- | :--- | :--- | :--- | :--- |
| **Time-of-Day (Wall Clock)** | `CLOCK_REALTIME` (`gettimeofday`) | **Jumps forward or backward** when NTP detects drift against UTC servers; leaps on leap-seconds. | Human timestamps, coarse log correlation. | Measuring elapsed durations or ordering distributed events (LWW)! |
| **Monotonic Clock** | `CLOCK_MONOTONIC` | Guaranteed strictly non-decreasing on **one** CPU/OS since boot; NTP only slews its rate by up to 0.05%. | Measuring local timeouts, request latency, lease countdowns. | Comparing timestamps across two different machines (meaningless offset!). |

### Logical Clocks (Lamport Timestamps & Hybrid Logical Clocks)

Because physical wall clocks across machines cannot be trusted to order events ($t_A < t_B$ does not imply $A$ happened before $B$), Leslie Lamport introduced **Logical Clocks**:

- Every node maintains an integer counter $L$, incremented on every local event.
- Every network message carries the sender's $L_{\text{msg}}$. Upon receipt, the receiver sets:
  $$L \leftarrow \max(L, L_{\text{msg}}) + 1$$
- **Guarantee:** If event $A$ causally happened before event $B$ ($A \to B$), then strictly $(L(A), \text{node}_A) < (L(B), \text{node}_B)$.
- **Hybrid Logical Clocks (HLC, used in CockroachDB & MongoDB):** Combine the best of physical time and Lamport counters into a tuple `(physical_ms, logical_counter)`: when physical wall-clock time advances, `physical_ms` advances and `logical_counter` resets to `0`; if a message arrives from a node whose clock is slightly ahead (or multiple events occur in the same millisecond), `logical_counter` increments monotonically so causal order is preserved *without* waiting for wall clocks to catch up (while Google Spanner's **TrueTime** API explicitly bounds hardware GPS/atomic clock uncertainty $[t_{\text{earliest}}, t_{\text{latest}}]$ and performs a **Commit Wait** of $2\epsilon \approx 7\text{ ms}$ before releasing locks).

## 2. Process Pauses, Expired Leases & Monotonic Fencing Tokens

Suppose your service acquires a distributed lock or leader lease (with a 5-second TTL) from Redis or ZooKeeper to mutate a shared storage file:

1. **Client 1** acquires the lease (`TTL = 5s`), prepares to write to the storage server, and immediately hits a **10-second JVM Stop-the-World Garbage Collection pause** (or Linux kernel page-reclaim freeze / hypervisor live-migration pause).
2. During those 10 seconds, Client 1's lease expires!
3. **Client 2** acquires the new lease and writes its update to the storage server.
4. **Client 1 wakes up from GC**, has no idea 10 seconds elapsed right after its `if (lease.isValid())` check, and sends its delayed write packet—**corrupting Client 2's committed data!**

```text
Client 1 (Old Leader)          Lock / Consensus Service          Storage Engine
        │                                  │                            │
        ├── Acquire Lease ────────────────►│                            │
        │◄── Granted (Fencing Token = 33) ─┤                            │
        │                                  │                            │
   [10s JVM GC Pause — Lease Expires!]     │                            │
        │                                  │◄── Client 2 Acquires Lease ┤
        │                                  ├──► Granted (Token = 34)    │
        │                                  │                            │
        │                    Client 2 Writes (Token = 34) ─────────────►│ (Accepts 34; sets max_seen=34)
   [Wakes up from GC]                      │                            │
        ├── Delayed Write (Token = 33) ────┼───────────────────────────►│ REJECTED! (33 < max_seen 34!)
```

### The Fix: Monotonic Fencing Tokens

You can never prevent a process pause on the client side—**the storage resource itself must enforce ordering!**

- Every time the lock/consensus service grants a lock or elects a new leader, it increments a strictly monotonic integer called a **Fencing Token** (`33`, `34`, `35`—in ZooKeeper this is `zxid`; in Raft/etcd this is `(term, mod_revision)`).
- Every write request to the storage engine carries the sender's `fencing_token`.
- The storage engine remembers `max_fencing_token_seen = 34` and **rejects any write carrying a token `< 34`**.

## 3. Atomic Commit (2PC) vs. Consensus (Raft)

Before examining Raft, it is critical to distinguish **Two-Phase Commit (2PC)** from **Consensus (Paxos / Raft)**:

- **Two-Phase Commit (2PC)** achieves **Atomic Commit across heterogeneous partitions** (where **all** $N$ participants must say `YES` to commit a cross-shard transaction):
  - *Phase 1 (Prepare):* Coordinator asks all participants `"Can you commit Trx #88?"`. Each participant writes its redo/undo records to disk and replies `YES` (surrendering its right to abort unilaterally!).
  - *Phase 2 (Commit/Abort):* If all replied `YES`, the coordinator writes `COMMIT` to its own log and sends `COMMIT` to all participants.
  - **Why 2PC is a Blocking Protocol:** Once a participant votes `YES` in Phase 1, if the **Coordinator crashes** before broadcasting Phase 2, the participant is **stuck in doubt (`IN DOUBT`) holding row locks forever**! It cannot abort (because another participant might have already received `COMMIT` from the coordinator) and cannot commit (because another participant might have voted `NO`).
- **Consensus (Raft / Paxos)** achieves **Fault-Tolerant Replicated State Machines** where any **majority quorum ($\lfloor N/2 \rfloor + 1$)** can elect a new leader and make progress even when up to $\lfloor (N-1)/2 \rfloor$ nodes crash! (Modern distributed databases like Spanner, TiKV, and CockroachDB make 2PC non-blocking by storing the 2PC coordinator's state inside a **Raft group**!)

## 4. The Raft Consensus Algorithm Internals

Designed by Diego Ongaro and John Ousterhout to be an understandable equivalent to Multi-Paxos, **Raft** decomposes replicated log consensus into three sub-problems: **Leader Election**, **Log Replication**, and **Safety**.

### 1. Terms, Node States & Randomized Election Timeouts

Time in Raft is divided into monotonically increasing **Terms** (`currentTerm`), which act directly as **Fencing Tokens**. At any moment, a node is in one of three states: **Follower**, **Candidate**, or **Leader**.

```text
                   Timeout elapses without Leader heartbeat
                  ┌─────────────────────────────────────────┐
                  ▼                                         │
┌──────────┐  Starts Election   ┌───────────┐  Wins Majority│  ┌────────┐
│ Follower │ ─────────────────► │ Candidate │ ──────────────┼─►│ Leader │
└──────────┘                    └───────────┘               │  └────────┘
     ▲                                │                     │       │
     └────────────────────────────────┴─────────────────────┴───────┘
                Discovers node with higher Term (steps down)
```

- **Why Election Timeouts Are Randomized (`150 ms – 300 ms`):** If 3 followers all used a fixed 200 ms timeout when a leader crashed, all 3 would become Candidates simultaneously, vote for themselves, and split the vote (`1-1-1`) forever! Randomizing each follower's election timeout between `[150ms, 300ms]` guarantees with high probability that one follower wakes up first, wins a majority of votes, and sends `AppendEntries` heartbeats before the other followers' timers expire.

### 2. The Election Safety Rule — Why `term = 100` Alone Cannot Win

Here is the most common interview and engineering misconception about Raft:
> **Question:** Suppose a 5-node Raft cluster (`N1..N5`) is running in `term = 2`. Node `N5` gets isolated by a network partition, repeatedly times out, and increments its `currentTerm` all the way to **`term = 100`**, though its log only has entries up to `(index=5, term=1)`. Meanwhile, `N1..N4` have committed entries up to `(index=20, term=2)`. When the network partition heals, `N5` broadcasts `RequestVote(term=100)`. **Does `N5` become the new Leader because `100 > 2`?**

**Answer: NO!**

1. When `N1..N4` see `N5`'s message with `term = 100 > 2`, they immediately update their `currentTerm = 100` and step down to **Follower**.
2. **However, they all vote `voteGranted = FALSE`!** Why? Because Raft's **Election Restriction (Section 5.4.1)** states that a voter rejects `RequestVote` unless the candidate's log is **at least as up-to-date** as the voter's own log, compared lexicographically by **`(lastLogTerm, lastLogIndex)`**:
   $$\text{CandidateUpToDate} \iff (\text{cand.lastLogTerm} > \text{voter.lastLogTerm}) \lor \bigl(\text{cand.lastLogTerm} == \text{voter.lastLogTerm} \land \text{cand.lastLogIndex} \ge \text{voter.lastLogIndex}\bigr)$$
3. Because `N5`'s last log entry has `lastLogTerm = 1 < 2`, every node in `{N1..N4}` denies `N5`'s vote, and one of `{N1..N4}` subsequently times out at `term = 101` and wins the election with all committed entries intact!

### 3. Log Replication & The Log Matching Property

<Archify src="./diagrams/raft-election-and-fencing.sequence.json" />

When a client sends a command to the Raft Leader:

1. The Leader appends the entry `(term, index, cmd)` to its local log and sends `AppendEntries` RPCs in parallel to all followers, including `(prevLogIndex, prevLogTerm)`—the index and term of the entry immediately preceding the new entry.
2. **Log Matching Property:** A follower refuses `AppendEntries` unless its local log contains an entry at `prevLogIndex` whose term equals `prevLogTerm`. By mathematical induction, if two logs contain an entry with the **same index and same term**, then **their logs are byte-for-byte identical from index 1 up to that index!**
3. If a follower's log has conflicting uncommitted entries from a crashed old leader, the current leader decrements `nextIndex[follower]` until it finds the highest matching prefix, overwrites the follower's conflicting tail, and once a **majority ($\lfloor N/2 \rfloor + 1$)** of nodes have written the current-term entry, the Leader advances `commitIndex` and applies the command to its State Machine.

> **Subtle Raft Safety Rule (Figure 8 of the Raft Paper):** A newly elected Leader **never** commits log entries from *previous* terms directly by counting replicas! It only commits an entry from its **own `currentTerm`** by majority replication; once that current-term entry is committed, the Log Matching Property indirectly commits all preceding entries from earlier terms.

## 5. Gossip & SWIM Epidemic Protocols (Cluster Membership at Scale)

Raft and Paxos require all-to-all leader heartbeats and majority quorums—ideal for small strongly-consistent groups (3, 5, or 7 nodes in etcd, or per-region Raft groups in TiKV). What if a cluster has **1,000 nodes** (like a large Cassandra, Consul, or ScyllaDB ring) and nodes need to track cluster membership, failure detection, or schema metadata without a single leader bottleneck?

They use **Gossip (Epidemic) Protocols**:

1. Every $\Delta t$ (e.g., 1 second), each node picks $k$ (e.g., $k = 3$) random peer nodes and exchanges its membership/version state (**Push-Pull Gossip**).
2. **Convergence Speed:** Just like a biological epidemic, information reaches all $N$ nodes in **$O(\log N)$ rounds**! Even in a $1,000$-node cluster with $k = 3$, $\log_3(1000) \approx 7\text{ rounds}$ (7 seconds), while each node sends only a tiny constant number of packets per second.
3. **SWIM Failure Detector (`Ping` $\rightarrow$ `Ping-Req` $\rightarrow$ `Suspect` $\rightarrow$ `Dead`):** To avoid false-positive node evictions caused by asymmetric packet loss between Node A and Node B, **SWIM** works in three steps:
   - If Node A's direct `PING` to Node B times out, Node A does *not* immediately declare Node B dead.
   - Instead, Node A asks $k=3$ random intermediary nodes to send an indirect **`PING-REQ(B)`** on its behalf.
   - Even if the direct link `A <-> B` is congested, if any intermediary reaches B, B stays `Alive`. If all intermediaries also fail, B is marked **`SUSPECT`** for a grace period (giving B a chance to refute the suspicion by incrementing its incarnation number) before being gossiped as **`DEAD`**.

## 6. Verification Lab — Raft Election Safety, Log Matching & Fencing Token Verifier

Save and run this self-contained Python script to verify three critical properties of distributed consensus:

1. **The `term = 100` Stale-Candidate Election Rejection:** A partitioned node (`N5`) that inflates its term to `100` forces the cluster to advance to `term = 100`, yet is **rejected** by the Election Restriction because its `lastLogTerm` is stale.
2. **Log Healing & Commit Advancement:** A newly elected leader heals a follower with conflicting uncommitted entries via `(prevLogIndex, prevLogTerm)` backtracking.
3. **Storage Engine Fencing Token Enforcement:** A paused old leader waking up from a GC pause has its stale write rejected by the storage engine.

```python
#!/usr/bin/env python3
"""Verify Raft Election Restriction (Stale Term-100 Rejection), Log Healing & Fencing Tokens."""
from dataclasses import dataclass, field
from typing import List, Optional, Tuple


@dataclass(frozen=True)
class LogEntry:
    term: int
    cmd: str


@dataclass
class RaftNode:
    node_id: str
    current_term: int = 0
    voted_for: Optional[str] = None
    role: str = "Follower"
    log: List[LogEntry] = field(default_factory=list)  # 0-indexed in Python
    commit_index: int = -1

    @property
    def last_log_index(self) -> int:
        return len(self.log) - 1

    @property
    def last_log_term(self) -> int:
        return self.log[-1].term if self.log else 0

    def request_vote(
        self, cand_id: str, cand_term: int, cand_last_idx: int, cand_last_term: int
    ) -> Tuple[int, bool]:
        """Raft Section 5.2 & 5.4.1 Election Restriction."""
        if cand_term < self.current_term:
            return self.current_term, False
        if cand_term > self.current_term:
            self.current_term = cand_term
            self.voted_for = None
            self.role = "Follower"

        # Section 5.4.1: Is candidate's log at least as up-to-date as voter's log?
        log_ok = (cand_last_term > self.last_log_term) or (
            cand_last_term == self.last_log_term and cand_last_idx >= self.last_log_index
        )
        can_vote = self.voted_for in (None, cand_id)
        if can_vote and log_ok:
            self.voted_for = cand_id
            return self.current_term, True
        return self.current_term, False

    def append_entries(
        self,
        leader_term: int,
        prev_log_idx: int,
        prev_log_term: int,
        entries: List[LogEntry],
        leader_commit: int,
    ) -> Tuple[int, bool]:
        """Raft Section 5.3 Log Matching Property."""
        if leader_term < self.current_term:
            return self.current_term, False
        if leader_term > self.current_term:
            self.current_term = leader_term
            self.voted_for = None
        self.role = "Follower"

        # Check prevLogIndex / prevLogTerm match
        if prev_log_idx >= 0:
            if prev_log_idx >= len(self.log) or self.log[prev_log_idx].term != prev_log_term:
                return self.current_term, False

        # Truncate any conflicting uncommitted suffix and append new entries
        insert_pos = prev_log_idx + 1
        for entry in entries:
            if insert_pos < len(self.log):
                if self.log[insert_pos].term != entry.term:
                    self.log = self.log[:insert_pos]
                    self.log.append(entry)
            else:
                self.log.append(entry)
            insert_pos += 1

        if leader_commit > self.commit_index:
            self.commit_index = min(leader_commit, len(self.log) - 1)
        return self.current_term, True


def run_election(candidate: RaftNode, cluster: List[RaftNode]) -> bool:
    candidate.current_term += 1
    candidate.role = "Candidate"
    candidate.voted_for = candidate.node_id
    votes = 1
    for peer in cluster:
        if peer.node_id == candidate.node_id:
            continue
        reply_term, granted = peer.request_vote(
            candidate.node_id,
            candidate.current_term,
            candidate.last_log_index,
            candidate.last_log_term,
        )
        if reply_term > candidate.current_term:
            candidate.current_term = reply_term
            candidate.role = "Follower"
            candidate.voted_for = None
            return False
        if granted:
            votes += 1
    if votes >= (len(cluster) // 2) + 1:
        candidate.role = "Leader"
        return True
    return False


def replicate_log_to_follower(leader: RaftNode, follower: RaftNode) -> int:
    """Backtracks next_idx until prevLogIndex/prevLogTerm matches, then heals follower."""
    next_idx = len(leader.log)
    while next_idx >= 0:
        prev_idx = next_idx - 1
        prev_term = leader.log[prev_idx].term if prev_idx >= 0 else 0
        _, ok = follower.append_entries(
            leader.current_term,
            prev_idx,
            prev_term,
            leader.log[next_idx:],
            leader.commit_index,
        )
        if ok:
            return next_idx
        next_idx -= 1
    raise RuntimeError("Unreachable: empty prefix always matches")


class FencedStorage:
    def __init__(self) -> None:
        self.max_token = 0
        self.data: dict = {}

    def write(self, fencing_token: int, key: str, val: str) -> bool:
        if fencing_token < self.max_token:
            return False  # Zombie leader write rejected!
        self.max_token = fencing_token
        self.data[key] = val
        return True


if __name__ == "__main__":
    # Create 5-node Raft cluster where N1..N4 have committed entries through Term 2,
    # while N5 was partitioned during Term 2 and also has 1 uncommitted stray entry from Term 1.
    committed_log = [LogEntry(1, "SET x=1"), LogEntry(2, "SET x=2"), LogEntry(2, "SET y=9")]
    nodes = [RaftNode(f"N{i+1}", current_term=2, log=list(committed_log), commit_index=2) for i in range(4)]
    n5 = RaftNode("N5", current_term=99, log=[LogEntry(1, "SET x=1"), LogEntry(1, "STALE_UNCOMMITTED")])
    cluster = nodes + [n5]

    # 1. N5 reconnects and attempts election at Term 100
    n5_won = run_election(n5, cluster)
    print(f"Step 1 (Stale N5 requests vote at Term {n5.current_term}):")
    print(f"       Did N5 win election? {n5_won} (N1..N4 stepped up to Term {nodes[0].current_term} but rejected N5's stale log!)")
    assert not n5_won and nodes[0].current_term == 100

    # 2. Up-to-date N1 runs election at Term 101 and wins!
    n1 = nodes[0]
    n1_won = run_election(n1, cluster)
    print(f"Step 2 (Up-to-date N1 runs election at Term {n1.current_term}) -> Won: {n1_won}, Role: {n1.role}")
    assert n1_won and n1.current_term == 101

    # 3. N1 appends a Term-101 entry and heals N5's conflicting uncommitted tail
    n1.log.append(LogEntry(101, "SET z=42"))
    n1.commit_index = 3
    matched_from = replicate_log_to_follower(n1, n5)
    print(f"Step 3 (Log Matching Backtrack on N5) -> Matched at index {matched_from}, N5 log now matches N1: {n5.log == n1.log}")
    assert n5.log == n1.log and n5.commit_index == 3

    # 4. Verify Fencing Token protection against a GC-paused old leader (Term 2)
    storage = FencedStorage()
    assert storage.write(fencing_token=n1.current_term, key="z", val="42") is True
    zombie_ok = storage.write(fencing_token=2, key="z", val="CORRUPT_FROM_TERM_2")
    print(f"Step 4 (Fenced Storage) -> Term-2 zombie leader write accepted? {zombie_ok}, Final z={storage.data['z']}")
    assert not zombie_ok and storage.data["z"] == "42"
```

## 7. Series Synthesis — Choosing & Combining Data Systems

Across these 6 chapters, we have traced how modern data systems are built from first principles:

1. **Chapter 01 (Storage Engines):** Choose **B+ Trees** (InnoDB/Postgres) for predictable low-latency point lookups and in-place row locking, or **LSM-Trees** (RocksDB/TiKV/Cassandra) for high write throughput and low space amplification.
2. **Chapter 02 (OLAP & Columnar Execution):** Separate analytical scans from transactional row stores using **Columnar layouts, Sparse Granule Indexes (`MergeTree`), RLE/Delta compression, and SIMD Vectorized Execution**.
3. **Chapter 03 (Replication):** Replicate across nodes using **Single-Leader** (with semi-sync replication and GTID Read-Your-Writes), **Multi-Leader** (with Version Vectors/CRDTs), or **Leaderless Quorums ($w + r > n$)**.
4. **Chapter 04 (Partitioning):** Scale beyond one machine with **Dynamic Key-Range Splits** or **Virtual-Node Consistent Hashing**, carefully weighing **Local (scatter-gather reads)** vs. **Global (distributed writes)** secondary indexes.
5. **Chapter 05 (Transactions & MVCC):** Understand how `ReadView` undo chains (InnoDB) and `xmin/xmax` heap tuples (Postgres) isolate snapshots, how **Next-Key Locks** prevent phantoms on current reads, and how **SSI** prevents **Write Skew**.
6. **Chapter 06 (Consensus & Distributed Time):** Never trust wall clocks (`CLOCK_REALTIME`) for ordering; guard resources against GC-paused zombie leaders with **Monotonic Fencing Tokens**, and rely on **Raft / Paxos** quorums for non-blocking consensus.
