Once our storage engine (B+ Tree or LSM-Tree) can persist data reliably on one disk, we face the fundamental reality of distributed hardware: **single machines fail, networks partition, and read traffic outgrows a single CPU.**

We replicate data across multiple nodes for three reasons:

1. **High Availability:** Keep serving traffic when a machine crashes or undergoes kernel maintenance.
2. **Read Scalability:** Scale read-heavy workloads across replicas.
3. **Geographic Latency:** Place copies of data closer to users around the globe.

Every challenge in replication stems from **propagating writes across an asynchronous, unreliable network**. DDIA categorizes replication algorithms into three classic topologies: **Single-Leader**, **Multi-Leader**, and **Leaderless (Dynamo-style)**.

---

## Before you start

One machine holding your only copy of the data is a bad bet: it will crash, and one machine can only answer so many reads. So databases keep copies on several machines. The hard part is that a write has to reach every copy over a network that is slow and sometimes broken. Post a comment, refresh, and get a page that does not show it yet: that is one copy being behind another.

This chapter covers the three ways to arrange the copies (one writer, several writers, or no designated writer), the odd behaviour users see when copies lag, and the quorum rule that lets leaderless systems stay usable when nodes are down.

Chapter 01 explained how one node stores data durably; if you have not read it, start with [storage engines](/tech/series/data-systems/01.storage-engines-btree-vs-lsm/). Basic familiarity with MySQL or PostgreSQL helps with the binlog examples.

Terms used in this chapter:

- **replica**: one copy of the data on one node.
- **leader and follower**: the leader accepts writes and streams its change log to followers, which apply it.
- **replication lag**: how far a follower is behind the leader, in time or log position.
- **binlog**: MySQL's log of changes, which followers replay.
- **semi-synchronous replication**: the leader waits for at least one follower to confirm receipt before reporting success.
- **read-your-writes**: the guarantee that a user always sees their own earlier writes.
- **quorum**: the minimum number of replicas that must answer a read or write for it to count.
- **version vector**: per-replica counters that show whether two versions of a value are ordered or concurrent.

## 1. Single-Leader (Active/Passive) Replication

In single-leader replication (MySQL, PostgreSQL, MongoDB replica sets, Kafka partitions), **all writes (`INSERT`, `UPDATE`, `DELETE`) must go to the single designated Leader**, which streams a replication log to one or more Followers (Read Replicas).

### Replication Log Formats — Statement vs. Row vs. Logical

How should the leader describe changes to its followers?

1. **Statement-Based Replication (`binlog_format = STATEMENT`):** The leader logs the literal SQL string (`UPDATE accounts SET balance = balance + 10 WHERE id = 1`) and every follower executes it.
   - *Fatal flaw:* Any **non-deterministic function** (`NOW()`, `RAND()`, `UUID()`, `LIMIT 1` without `ORDER BY`, or user-defined triggers) produces **different rows on the follower than on the leader**, silently corrupting replica state!
2. **Write-Ahead Log Shipping (Physical Page/Byte Deltas):** PostgreSQL's physical streaming replication ships the exact raw WAL bytes (`"write these 24 bytes at offset 1088 of block 412"`).
   - *Trade-off:* Zero CPU translation overhead, but tightly couples followers to the exact same storage engine version and on-disk page layout—making zero-downtime major version upgrades impossible via physical replication alone.
3. **Logical (Row-Based) Replication (`binlog_format = ROW` / Postgres Logical Replication):** The log records the actual column values of every modified row (`table=accounts, op=UPDATE, before={id:1, bal:100}, after={id:1, bal:110}`).
   - *Why it wins:* Completely deterministic regardless of `NOW()` or `RAND()`, decoupled from physical B+ Tree page splits (allowing rolling major-version upgrades), and directly usable by Change Data Capture (**CDC**) pipelines like Debezium to stream database mutations into Kafka or ClickHouse.

### Synchronous vs. Semi-Synchronous vs. Asynchronous Replication

```text
Client                Leader                 Follower 1 (Sync)       Follower 2 (Async)
  │                     │                           │                        │
  ├── Write(x=42) ─────►│                           │                        │
  │                     ├── Local WAL + Binlog      │                        │
  │                     ├── Replicate Binlog ──────►│                        │
  │                     ├───────────────────────────┼────────────────────────►
  │                     │◄── ACK (written to relay) ┤                        │
  │◄── 200 OK ──────────┤                           │                        │
  │                     │                      (Apply to DB)            (Apply later)
```

- **Pure Synchronous (All Replicas):** If *any* follower crashes or suffers a network hiccup, the leader blocks all writes until that follower recovers—destroying availability!
- **Pure Asynchronous:** The leader replies `200 OK` as soon as the local WAL/binlog is flushed. Writes are fast and never blocked by followers, **but if the leader suffers an unrecoverable disk failure, any committed writes not yet shipped to followers are permanently lost ($RPO > 0$).**
- **Semi-Synchronous Replication (`rpl_semi_sync_master_wait_point = AFTER_SYNC`, renamed `rpl_semi_sync_source_wait_point` in MySQL 8.0.26+):** The production sweet spot. The leader keeps $N-1$ followers asynchronous, while requiring **at least 1 follower** to acknowledge receipt of the binlog event into its local relay log *before* the leader makes the transaction visible or returns `200 OK` to the client. If that follower stalls beyond a timeout (or in Raft/Paxos quorum replication, as long as a majority $\lfloor N/2 \rfloor + 1$ responds), another follower immediately satisfies the semi-sync acknowledgment.

## 2. Replication Lag Anomalies & How to Fix Them

When reads are scaled across asynchronous followers, a follower may lag behind the leader by a few milliseconds—or several seconds during a bulk write spike. This **Eventual Consistency** window exposes three classic user-visible anomalies:

### 1. Read-After-Write (Read-Your-Writes) Anomaly

- **Symptom:** A user updates their profile bio (`POST /profile` $\rightarrow$ Leader), immediately reloads the page (`GET /profile` $\rightarrow$ lagging Follower 2), and sees their *old* bio, thinking their update was lost.
- **Production Fixes:**
  1. **Route owner reads to the Leader:** When reading data that *only the current user* can modify (their own profile or account settings), route the owner's reads to the Leader and everyone else's reads to Followers.
  2. **Track client write timestamps or GTIDs:** After a write commits on the MySQL leader, return the transaction's **GTID (`Global Transaction ID`, e.g., `3E11FA47-...:42`)** to the client session. When the client issues a subsequent read to a follower, run:

     ```sql
     SELECT WAIT_FOR_EXECUTED_GTID_SET('3E11FA47-71CA-11E1-9E33-C80AA9429562:42', 1.0);
     ```

     The follower blocks the read until its SQL apply thread catches up to `:42` (or falls back to the leader if the 1-second timeout expires).

### 2. Monotonic Reads Anomaly (Moving Backward in Time)

- **Symptom:** A user refreshes a comments thread twice. Refresh #1 hits Follower 1 (lag = 0 ms) and shows a newly posted comment. Refresh #2 load-balances to Follower 2 (lag = 500 ms) and **the comment vanishes!**
- **Fix:** **Session-sticky replica routing.** Hash the `user_id` or `session_id` consistently to the same healthy read replica so a single user never observes state from an older point in the replication log than they have already seen.

### 3. Consistent Prefix Reads (Causality Violation)

- **Symptom:** In a partitioned/sharded system without causal ordering, Question message $Q$ ("Shall we deploy at 17:00?") is written to Partition A, and Answer message $A$ ("Yes, approved!") is written to Partition B. An observer whose replica for Partition B is faster than Partition A sees `"Yes, approved!"` *before* `"Shall we deploy at 17:00?"`.
- **Fix:** Keep causally related records in the same partition, or attach explicit **Causal Version Vectors / Lamport Timestamps** so replicas buffer causally dependent writes until their predecessors arrive.

### Single-Leader Failover Hazards

When the leader stops responding to heartbeats for e.g. 15 seconds, a consensus controller (Orchestrator, Patroni/etcd) promotes the follower with the most up-to-date GTID position. Three hazards lurk here:

1. **Discarded Committed Writes:** Under async replication, the old leader may have acknowledged writes `#101..#105` before crashing. When it rejoins as a follower, those conflicting local transactions must be rolled back or discarded—which is catastrophic if external systems (like a Redis cache or billing webhook) already observed `#101..#105`!
2. **Split-Brain (Two Active Leaders):** If the old leader wasn't dead—only isolated by an asymmetric network partition or frozen in a GC pause—both the old leader and the newly promoted leader accept writes simultaneously, corrupting data. (We solve this with **Fencing Tokens** and **Raft Consensus** in Chapter 06.)

## 3. Multi-Leader Replication & Conflict Resolution

In **Multi-Leader (Active/Active)** topologies—such as multi-region deployments where each datacenter has its own local write leader, or offline-first local apps (Linear, Figma, Obsidian Sync) where every device acts as a local leader—concurrent writes to the same record across two leaders create **Write Conflicts**.

```text
User A (Tokyo Leader)                   User B (Frankfurt Leader)
        │                                          │
  SET title = "B"                            SET title = "C"
        │             \              /             │
        │              \            /              │
        │        Async Replication Crosses         │
        ▼                                          ▼
  Receives "C" while local is "B"            Receives "B" while local is "C"
  (CONFLICT! Both must converge to the exact same final state)
```

### Why Last-Write-Wins (LWW) with Wall-Clock Timestamps Is Dangerous

The simplest conflict resolution rule attaches a wall-clock timestamp (`CLOCK_REALTIME`) to every write and keeps the highest timestamp (**Last-Write-Wins, LWW**, used in Cassandra).

- **Why LWW silently drops committed data:** Physical NTP clocks across servers routinely drift by 10–100 ms. If Node A's clock is 50 ms fast and writes `v1` at $t = 100.050$, and 10 ms later in real time a user updates the same key on Node B (whose clock is accurate at $t = 100.010$) to `v2`, **Node B's causally newer write (`100.010 < 100.050`) is silently overwritten and lost!**
- LWW is only safe if writes are immutable (every write gets a unique UUID key) or if losing concurrent updates within the clock-skew window is explicitly acceptable.

### Capturing True Concurrency with Version Vectors

How does a database know whether Write $B$ **causally superseded** Write $A$ ($A \to B$, no conflict) vs. Write $A$ and Write $B$ happened **concurrently without knowing about each other** ($A \parallel B$, true conflict)?

Instead of a single timestamp, each key maintains a **Version Vector**—a map of `{replica_id: counter}`:

- Let $V_1$ and $V_2$ be two version vectors:
  - $V_2$ **dominates (causally follows)** $V_1$ ($V_1 < V_2$) if and only if for every replica $r$, $V_1[r] \le V_2[r]$, and for at least one replica $r^*$, $V_1[r^*] < V_2[r^*]$. In this case, $V_2$ saw everything in $V_1$ and can safely overwrite it.
  - Otherwise, if neither $V_1 \le V_2$ nor $V_2 \le V_1$ (for example, $V_1 = \{A: 2, B: 1\}$ and $V_2 = \{A: 1, B: 2\}$), then **$V_1 \parallel V_2$ are concurrent siblings!**
- Once concurrency is detected via Version Vectors, the database either keeps both **siblings** for the application to merge (the merged write carries a version vector that dominates both siblings) or merges them automatically using **CRDTs** (Conflict-Free Replicated Data Types, such as PN-Counters, OR-Sets, or RGA collaborative text trees where merge operations are commutative, associative, and idempotent: $A \sqcup B = B \sqcup A$).

## 4. Leaderless (Dynamo-Style) Replication & Quorums

Inspired by Amazon's 2007 **Dynamo** paper (and adopted by Riak, Cassandra, ScyllaDB, and Voldemort), **Leaderless Replication** eliminates the leader role entirely—which means **there is no failover pause!**

### Quorum Math: $w + r > n$

Suppose a key is replicated across $n$ nodes (e.g., $n = 3$):

1. **Client Write:** The client (or a stateless coordinator node) sends `Put(k, v, version)` to **all $n$ replicas in parallel** and waits for at least **$w$ replicas** to acknowledge success.
2. **Client Read:** The client sends `Get(k)` to **all $n$ replicas in parallel**, waits for at least **$r$ replicas** to respond, and picks the response with the newest version vector/timestamp.

```text
          Replica 1         Replica 2         Replica 3   (n = 3)
          ┌───────┐         ┌───────┐         ┌───────┐
Write(v2) │  v2   │         │  v2   │         │  v1   │ (Network timeout on R3;
(w = 2)   └───────┘         └───────┘         └───────┘  R1 + R2 ACK -> Write succeeds!)
              ▲                 ▲                 ▲
              │                 └────────┬────────┘
              │                          │
          Read (r = 2) reads from R2 (v2) and R3 (v1)
          ──► Overlap at R2 guarantees client sees v2!
          ──► Client triggers Read Repair: sends v2 to R3!
```

By the Pigeonhole Principle, as long as:
$$w + r > n$$
every read set of size $r$ and every write set of size $w$ **must overlap in at least $w + r - n \ge 1$ replica** that holds the latest acknowledged write!

- Common production setting: $n = 3, w = 2, r = 2$ ($\text{QUORUM}$). Tolerates 1 dead or slow node for both reads and writes.
- Fast-read / write-all setting: $n = 3, w = 3, r = 1$. Any single node can serve a read locally, but 1 dead node blocks writes.

### Self-Healing: Read Repair & Anti-Entropy Merkle Trees

How does Replica 3 (which missed `v2` above) catch up without a leader replication log?

1. **Read Repair (Opportunistic):** When a client read (`r = 2`) receives `v2` from Replica 2 and stale `v1` from Replica 3, the client/coordinator returns `v2` to the caller and asynchronously sends `Put(k, v2)` to Replica 3.
2. **Anti-Entropy via Merkle Trees (Background):** What if a key is written once and not read for 6 months, and one replica later loses its disk? Read Repair never triggers on cold keys! Background processes continuously compare **Merkle Trees** (hash trees over key ranges) between replicas: if the root hash of range `[0x0000..0xFFFF]` matches between R1 and R3, zero keys are transferred; if the root hash differs, the nodes traverse only the differing branches down to the exact out-of-sync keys in $O(\log K)$ messages.

### Sloppy Quorums & Hinted Handoff (Availability vs. Consistency)

What if a network partition isolates all 3 home replicas $(R_1, R_2, R_3)$ for key $k$, or 2 of the 3 home replicas are unreachable so $w = 2$ cannot be met?

- **Strict Quorum:** Reject the write (`503 Unavailable`) to preserve $w + r > n$ consistency.
- **Sloppy Quorum + Hinted Handoff:** Accept the write anyway by temporarily storing it on a healthy neighbor node $R_4$ outside key $k$'s home replica set $n$, tagged with a **"Hint"** (`"belongs to R2"`). Once $R_2$ recovers, $R_4$ hands the hinted writes back.
  - *Crucial Caveat:* While a write is sitting in Hinted Handoff on $R_4$, a read of $r = 2$ against the home nodes $(R_1, R_2, R_3)$ **will NOT see the write** even though $w + r > n$! Sloppy quorums are purely a write-availability optimization, not a read-your-writes guarantee.

### Why Even Strict $w + r > n$ Is Not Automatically Linearizable

Even with strict quorums ($n=3, w=2, r=2$), Dynamo-style quorums do **not** provide strict Linearizability without an extra write-back step:

- Suppose a write `x = 1` is in flight: it has reached $R_1$ (`x=1`), is still in flight to $R_2$ (`x=0`), and failed on $R_3$ (`x=0`).
- Reader A reads from $\{R_1, R_2\}$, sees `x = 1` on $R_1$, and returns `1`.
- Immediately afterward, Reader B reads from $\{R_2, R_3\}$ (before $R_2$ receives `x = 1` or Read Repair completes), sees `x = 0` on both, and returns `0`! Reader B observed an older value *after* Reader A observed the newer value. To make quorum reads linearizable (ABD algorithm), **the reader must write the winning version back to a quorum $w$ of replicas before returning the value to the caller.**

## 5. Verification Lab — Dynamo Quorum & Version-Vector Causality Simulator

Run this Python script to verify Version Vector causal dominance vs. true concurrent conflict detection ($V_1 \parallel V_2$), Quorum read overlap ($n=3, w=2, r=2$), and automatic Read Repair:

```python
#!/usr/bin/env python3
"""Verify Version Vectors (Causal Dominance vs Concurrent Siblings) and Dynamo Quorums."""
from dataclasses import dataclass, field
from typing import Dict, List, Set, Tuple


@dataclass(frozen=True)
class VersionVector:
    clock: Tuple[Tuple[str, int], ...] = ()

    @staticmethod
    def from_dict(d: Dict[str, int]) -> "VersionVector":
        return VersionVector(tuple(sorted((k, v) for k, v in d.items() if v > 0)))

    def to_dict(self) -> Dict[str, int]:
        return dict(self.clock)

    def increment(self, node_id: str) -> "VersionVector":
        d = self.to_dict()
        d[node_id] = d.get(node_id, 0) + 1
        return VersionVector.from_dict(d)

    def merge(self, other: "VersionVector") -> "VersionVector":
        d = self.to_dict()
        for k, v in other.to_dict().items():
            d[k] = max(d.get(k, 0), v)
        return VersionVector.from_dict(d)

    def dominates(self, other: "VersionVector") -> bool:
        """True iff self >= other on all keys and strictly > on at least one key."""
        d1, d2 = self.to_dict(), other.to_dict()
        all_keys = set(d1.keys()) | set(d2.keys())
        ge_all = all(d1.get(k, 0) >= d2.get(k, 0) for k in all_keys)
        gt_one = any(d1.get(k, 0) > d2.get(k, 0) for k in all_keys)
        return ge_all and gt_one


@dataclass
class ReplicaNode:
    node_id: str
    # key -> list of concurrent sibling (VersionVector, value)
    store: Dict[str, List[Tuple[VersionVector, str]]] = field(default_factory=dict)

    def apply_put(self, key: str, vv: VersionVector, value: str) -> None:
        existing = self.store.get(key, [])
        # Keep only siblings that are NOT dominated by the incoming version
        survivors: List[Tuple[VersionVector, str]] = []
        dominated_by_existing = False
        for old_vv, old_val in existing:
            if old_vv == vv:
                dominated_by_existing = True
                survivors.append((old_vv, old_val))
            elif old_vv.dominates(vv):
                dominated_by_existing = True
                survivors.append((old_vv, old_val))
            elif not vv.dominates(old_vv):
                # True concurrent sibling! Keep both.
                survivors.append((old_vv, old_val))
        if not dominated_by_existing:
            survivors.append((vv, value))
        self.store[key] = survivors


class DynamoCluster:
    def __init__(self, n: int = 3, w: int = 2, r: int = 2):
        assert w + r > n, "Strict quorum requires w + r > n"
        self.n, self.w, self.r = n, w, r
        self.nodes = [ReplicaNode(f"R{i+1}") for i in range(n)]

    def quorum_put(
        self, key: str, value: str, context: VersionVector, coord_node: str, reachable_indices: List[int]
    ) -> VersionVector:
        if len(reachable_indices) < self.w:
            raise RuntimeError(f"Write failed: only {len(reachable_indices)} < w={self.w} nodes reachable")
        new_vv = context.increment(coord_node)
        for idx in reachable_indices:
            self.nodes[idx].apply_put(key, new_vv, value)
        return new_vv

    def quorum_get(self, key: str, read_indices: List[int]) -> Tuple[List[str], VersionVector, List[str]]:
        if len(read_indices) < self.r:
            raise RuntimeError(f"Read failed: only {len(read_indices)} < r={self.r} nodes reachable")
        # Gather all versions across the r contacted replicas
        all_candidates: List[Tuple[VersionVector, str]] = []
        for idx in read_indices:
            all_candidates.extend(self.nodes[idx].store.get(key, []))

        # Filter to maximal (non-dominated) frontier versions
        frontier: List[Tuple[VersionVector, str]] = []
        for vv, val in all_candidates:
            if not any(other_vv.dominates(vv) for other_vv, _ in all_candidates):
                if (vv, val) not in frontier:
                    frontier.append((vv, val))

        merged_context = VersionVector()
        for vv, _ in frontier:
            merged_context = merged_context.merge(vv)

        # Trigger Read Repair on any contacted replica missing the frontier versions
        repaired_nodes: List[str] = []
        for idx in read_indices:
            node_versions = set(self.nodes[idx].store.get(key, []))
            for f_vv, f_val in frontier:
                if (f_vv, f_val) not in node_versions:
                    self.nodes[idx].apply_put(key, f_vv, f_val)
                    repaired_nodes.append(self.nodes[idx].node_id)

        return [val for _, val in frontier], merged_context, repaired_nodes


if __name__ == "__main__":
    cluster = DynamoCluster(n=3, w=2, r=2)

    # 1. Initial write reaches R1 and R2 (R3 misses it due to transient packet drop)
    vv1 = cluster.quorum_put("cart:42", "['book']", VersionVector(), coord_node="R1", reachable_indices=[0, 1])
    print(f"Step 1 (Write v1 to R1, R2) : vv={vv1.to_dict()}, R3 store={cluster.nodes[2].store.get('cart:42', [])}")

    # 2. Quorum read contacts R2 and R3 -> R2 has v1, R3 is empty -> Read Repair heals R3!
    vals, ctx, repaired = cluster.quorum_get("cart:42", read_indices=[1, 2])
    print(f"Step 2 (Read R2, R3)        : values={vals}, Read-Repaired nodes={repaired}")
    assert len(cluster.nodes[2].store["cart:42"]) == 1

    # 3. Concurrent writes from two clients starting from the SAME context `ctx` (Cart conflict!)
    vv_alice = cluster.quorum_put("cart:42", "['book', 'pen']", ctx, coord_node="R1", reachable_indices=[0, 1])
    vv_bob = cluster.quorum_put("cart:42", "['book', 'mug']", ctx, coord_node="R2", reachable_indices=[1, 2])

    siblings, merged_ctx, _ = cluster.quorum_get("cart:42", read_indices=[0, 1, 2])
    print(f"Step 3 (Concurrent writes)  : Alice={vv_alice.to_dict()} || Bob={vv_bob.to_dict()}")
    print(f"       Detected Siblings    : {siblings} (neither dominates the other!)")
    assert set(siblings) == {"['book', 'pen']", "['book', 'mug']"}

    # 4. Client resolves conflict by unioning the shopping cart and writing with `merged_ctx`
    vv_resolved = cluster.quorum_put("cart:42", "['book', 'pen', 'mug']", merged_ctx, "R1", [0, 1, 2])
    final_vals, final_ctx, _ = cluster.quorum_get("cart:42", read_indices=[0, 2])
    print(f"Step 4 (Merged resolution)  : values={final_vals}, context={final_ctx.to_dict()}")
    assert final_vals == ["['book', 'pen', 'mug']"]
```
