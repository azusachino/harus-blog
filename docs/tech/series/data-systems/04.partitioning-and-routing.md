Replication (Chapter 03) gives us fault tolerance and read scalability, but if every replica holds 100% of the data, we hit a hard ceiling when our dataset exceeds a single disk's capacity or our write throughput exceeds a single node's I/O bandwidth.

To scale writes and storage horizontally, we **partition** (called **sharding** in MongoDB, MySQL Vitess, and Elasticsearch; **regions** in HBase/TiKV; **tablets** in Bigtable/YugabyteDB; **vnodes** in Cassandra/Riak): splitting a large dataset into smaller subsets so each record belongs to exactly one home partition (which is then replicated across $n$ nodes for fault tolerance).

In **Chapter 04**, we examine how databases assign keys to partitions, prevent **skew and write hotspots**, maintain **secondary indexes across partitions**, and route client queries without central bottlenecks.

---

## Before you start

Copies protect you from a machine dying, but every copy still holds everything. When the data or the write rate outgrows one machine, you have to split it up so each key lives on one machine (and its replicas). The question is how to decide which one. Handing out surnames A to D to one clerk and E to H to the next is simple and keeps neighbours together, but if half your customers are called Smith, one clerk drowns.

This chapter looks at splitting by key range versus by hash, why the obvious `hash(key) % N` breaks the moment you add a server, how consistent hashing limits the damage, what happens to secondary indexes, and how a client finds the right node.

It follows [replication in chapter 03](/tech/series/data-systems/03.replication-and-quorums/), whose leaders and replicas this chapter assumes.

Terms used in this chapter:

- **partition (shard)**: a slice of the dataset that lives on one node plus its replicas.
- **skew**: uneven distribution of data or load across partitions.
- **hotspot**: a partition receiving a disproportionate share of traffic.
- **key-range partitioning**: giving each partition a contiguous, sorted range of keys.
- **hash partitioning**: assigning keys to partitions by the hash of the key, which spreads load but destroys key order.
- **consistent hashing**: placing nodes and keys on a ring so that adding or removing a node moves only a small share of keys.
- **virtual node**: one of many ring positions given to a physical node to even out its share.
- **rebalancing**: moving partitions between nodes when the cluster changes.

## 1. Key-Range Partitioning vs. Hash Partitioning

The goal of partitioning is to spread both data volume and query load evenly across $N$ nodes. If partitioning is unfair, **Skew** occurs—and in the extreme case, a single partition becomes a **Hotspot** receiving 90% of traffic while the remaining $N-1$ nodes sit idle.

### Strategy A: Key-Range Partitioning (Bigtable, HBase, TiKV, CockroachDB)

We assign each partition a contiguous, sorted range of keys—just like volumes of a printed encyclopedia (`[A..D) -> Partition 1`, `[D..H) -> Partition 2`):

```text
Key Space:  ["0000" ────────► "3999"] ["4000" ────────► "7999"] ["8000" ────────► "FFFF"]
                  Partition 1               Partition 2               Partition 3
```

- **Dynamic Range Splits & Merges:** Ranges do not have to be evenly spaced! In TiKV or HBase, a table starts as a single region `["", "")`. Whenever a region grows past a size threshold (e.g., 96 MB in older TiKV defaults; newer releases use larger regions), the storage engine splits it at the median key into two child regions (`["", "m")` and `["m", "")`) and migrates one child to an underutilized node.
- **Big Advantage:** **Range scans are fast and local.** Fetching `WHERE user_id = 'alice' AND event_time BETWEEN '2026-04-01' AND '2026-04-02'` scans a single contiguous slice on one partition.
- **Fatal Pitfall (Sequential Timestamp Hotspots):** If your primary key is a timestamp or auto-incrementing ID (`2026-04-19T10:00:00Z`), **100% of current writes land on the very last partition** (`[2026-04-19..MAX)`), while all historical partitions sit completely idle!
  - *Fix:* Prefix the key with a high-cardinality entity or hash salt (`(sensor_id, timestamp)` or `(hash(timestamp) % 16, timestamp)`), trading a small fan-out on global time-range reads to distribute write load across all partitions.

### Strategy B: Hash Partitioning (Cassandra, DynamoDB, Redis Cluster)

Instead of partitioning on the raw key, we apply a fast non-cryptographic hash function (`MurmurHash3`, `xxHash`, or `CRC16` in Redis Cluster) to map any key uniformly onto a fixed integer space $[0, 2^{64}-1]$:

- **Big Advantage:** Even nearly identical keys (`user:1001`, `user:1002`, or sequential timestamps) scatter uniformly across all partitions.
- **Big Trade-off:** **Range queries over the partition key become full-cluster scatter-gather scans.** Because adjacent keys hash to completely different nodes, `WHERE key BETWEEN 'a' AND 'b'` must query every partition in the cluster.
- **Compound Key Compromise (Cassandra / DynamoDB):** Define a two-part primary key `PRIMARY KEY ((partition_key), clustering_key_1, clustering_key_2)`:
  - The database **hashes** `partition_key` (`user_id`) to pick the partition node.
  - Inside that partition's LSM-Tree, rows are **sorted by** `clustering_key` (`event_time`). Thus `WHERE user_id = 42 AND event_time BETWEEN t1 AND t2` executes an efficient single-partition range scan!

## 2. Why `hash(key) % N` Fails & How Virtual-Node Consistent Hashing Works

Why don't distributed databases simply assign keys using `node_index = hash(key) % N`?

Suppose you have $N = 10$ nodes and add 1 node ($N = 11$). For almost every key $k$, `hash(k) % 10 != hash(k) % 11`—in fact, **$\frac{N}{N+1} = \frac{10}{11} \approx 90.9\%$ of all keys in the database must move across the network simultaneously!** During a scale-out event, moving 91% of your data saturates NICs and disks, bringing the cluster down.

### Consistent Hashing with Virtual Nodes (`vnodes`)

**Consistent Hashing** maps both keys and nodes onto a circular hash ring $[0, 2^{32}-1]$. A key $k$ belongs to the first node encountered moving clockwise from `hash(k)` on the ring (`bisect_left` on sorted ring tokens).

If each physical machine only placed **1 point** on the ring, random token spacing would cause severe size skew ($3\times\text{--}5\times$ load difference between lucky and unlucky nodes). Instead, production systems assign each physical machine **$V$ Virtual Nodes (`vnodes`, e.g., $V = 128$ or $256$ tokens per physical node)** interspersed around the ring:

```text
                   Token 0x00000000
                    ┌─────●─────┐  Node A (vnode 1)
         Node C     │           │
       (vnode 2) ●──┤           ├──● Node B (vnode 1)
                    │   Hash    │
                    │   Ring    │
       Node A    ●──┤           ├──● Node C (vnode 1)
       (vnode 2)    │           │
                    └─────●─────┘  Node B (vnode 2)
```

Why do Virtual Nodes solve all three problems at once?

1. **Minimal Data Movement ($O(K / N)$):** When a new node (`Node D`) joins an $N$-node cluster, it claims $V$ positions around the ring, taking a tiny slice of keys evenly from *every* existing node. Instead of moving $91\%$ of keys, adding an 11th node moves **only $\frac{1}{11} \approx 9.09\%$ of keys**—the theoretical minimum required to balance the cluster!
2. **Uniform Load Distribution:** By the Law of Large Numbers, with $V = 150$ virtual nodes per machine, standard deviation of key load across nodes drops below $\sim \frac{1}{\sqrt{150}} \approx 8\%$.
3. **Heterogeneous Hardware Support:** If `Node D` has $2\times$ the NVMe capacity and CPU cores of `Node A`, we simply assign `Node D` $2V = 300$ virtual nodes instead of $150$.

### Mitigating Celebrity / Skewed Key Hotspots

Wait: what if **one single key** receives 500,000 writes/sec (e.g., a celebrity account with 100 million followers posting a live video, or a flash-sale SKU)?
**Consistent hashing cannot split a single key!** All 500,000 writes/sec for `key = "celebrity_88"` hash to the exact same token and hammer a single partition.

How is this solved at the application/storage layer?

- **Write Salting (Key Splitting):** Detect or configure hot keys and append a random shard suffix `[0..K-1]` (e.g., `celebrity_88#00` through `celebrity_88#31`), splitting writes across 32 partitions.
- **Read Trade-off:** Reading the total count for `celebrity_88` now requires reading and summing all 32 salted keys (`#00..#31`), whereas normal cold keys pay zero fan-out overhead.

## 3. Secondary Indexes Across Partitions — Local vs. Global

Partitioning works seamlessly when queries always include the Primary/Partition Key (`GET /users/42`). What happens when a user searches by a **Secondary Index** (`SELECT * FROM orders WHERE status = 'PENDING'` or `WHERE merchant_id = 99`) in a table partitioned by `order_id`?

There are only two architectural ways to build secondary indexes in a partitioned database, and **they trade Read Amplification against Distributed Write Coordination**:

```text
┌─────────────────────────────────────────────────────────────────────────┐
│ 1. Document-Partitioned (LOCAL) Index — Elasticsearch, MongoDB, Cassandra│
│                                                                         │
│   Partition 1 (Orders 1..1000)         Partition 2 (Orders 1001..2000)  │
│   Local Index: status="PENDING"->[12]  Local Index: status="PENDING"->[1044]│
│                                                                         │
│   ► Write(Order 12): Fast! Single-node local write + local index update │
│   ► Read(status="PENDING"): SCATTER-GATHER across ALL partitions!       │
├─────────────────────────────────────────────────────────────────────────┤
│ 2. Term-Partitioned (GLOBAL) Index — TiDB, CockroachDB, DynamoDB GSI    │
│                                                                         │
│   Index Partition A (status A..M)      Index Partition B (status N..Z)  │
│   "COMPLETED" -> [Order 5, Order 1099] "PENDING" -> [Order 12, 1044]    │
│                                                                         │
│   ► Read(status="PENDING"): Fast! Hits ONLY Index Partition B!          │
│   ► Write(Order 12): Slow! Cross-node write to Data Part 1 + Index B!   │
└─────────────────────────────────────────────────────────────────────────┘
```

### 1. Document-Partitioned Index (Local Index)

Each partition maintains its own secondary index covering **only the documents/rows stored on that local partition**.

- **Writes are fast and local:** Inserting `Order 12` on Partition 1 updates Partition 1's local B+ Tree / inverted index in the same local transaction.
- **Reads suffer Scatter-Gather Tail Latency Amplification:** To find all orders with `status = 'PENDING'`, the coordinator must fan out the query to **all $P$ partitions in parallel** and merge the results. As we saw in Chapter 01, if you scatter-gather across $P = 50$ partitions, the query's latency is the **slowest ($p99$) of 50 nodes**!

### 2. Term-Partitioned Index (Global Secondary Index, GSI)

The secondary index itself is partitioned by the **indexed term** (`status`), completely independent of how the base table is partitioned:

- **Reads are single-partition:** Looking up `WHERE status = 'PENDING'` hashes or range-routes `'PENDING'` directly to Index Partition B, returning matching primary keys without touching the rest of the cluster.
- **Writes require cross-partition coordination:** Inserting or updating a single row whose primary key lives on Data Partition 1 and whose old/new `status` values live on Index Partitions A and B must update **three different machines**:
  - In **DynamoDB Global Secondary Indexes (GSIs)**, the global index is updated **asynchronously** within milliseconds (eventual consistency—you cannot do strongly consistent reads on a DynamoDB GSI).
  - In **NewSQL databases (TiDB, CockroachDB, Spanner)**, updating the base table row and the global secondary index row executes inside a **distributed 2PC + Raft transaction**, guaranteeing strong consistency at the cost of cross-node network RTTs during writes.

## 4. Request Routing & Cluster Metadata Coordination

When a client wants to read or write `key = "order:8842"`, how does it know which IP address currently owns the partition for `"order:8842"`—especially when partitions split and rebalance across nodes dynamically?

```text
Approach 1 (Any-Node Gossip)    Approach 2 (Routing Proxy)     Approach 3 (Smart Client)
      Client                          Client                         Client (SDK)
        │ (Hits any node)               │                              │ (Caches Partition Map)
        ▼                               ▼                              ├─────────┐
   [Node 1] ──Forwards──► [Node 2] [Stateless Proxy] ──► [Node 2]      ▼         ▼
   (Cassandra / Riak)              (Vitess / Mongos)             [Node 1]    [Node 2]
                                        ▲                        (Redis Cluster / TiKV / Kafka)
                                        └─── Watches ZooKeeper / etcd / PD ──────┘
```

1. **Contact Any Node (Cassandra / Riak):** Every storage node gossips partition ring topology. The client connects to any node via round-robin DNS; if that node does not own the key, it acts as a coordinator and forwards the request to the owning node (adding 1 extra network hop).
2. **Routing Tier / Proxy (`mongos` in MongoDB, `vtgate` in Vitess, `codis-proxy`):** Clients speak standard database wire protocols to a stateless routing proxy, which tracks partition assignments via **etcd / ZooKeeper** and forwards queries to the right shard.
3. **Partition-Aware Smart Client (Redis Cluster, Kafka Producer/Consumer, TiKV Client):** The client SDK caches the full slot/region map locally (`16,384 hash slots` in Redis Cluster) and connects **directly** to the authoritative node in 1 hop. If a partition migrated since the client last refreshed its map, the storage node returns a `-MOVED 3999 10.0.1.5:6379` redirect (or `NotLeader / EpochNotMatch` in TiKV), prompting the client to refresh its cached route table.

## 5. Verification Lab — Virtual-Node Consistent Hashing & Rebalance Movement Verifier

Run this Python script to compare **Modulo Hashing (`hash(k) % N`)** against a **Virtual-Node Consistent Hash Ring** across 100,000 keys when scaling a cluster from $N = 10$ to $N = 11$ nodes, and verify both key movement percentage and per-node load standard deviation:

```python
#!/usr/bin/env python3
"""Verify Modulo Hashing vs Virtual-Node Consistent Hashing (Key Movement & Skew)."""
import bisect
import hashlib
import math
import statistics
from typing import Dict, List


def hash32(text: str) -> int:
    return int.from_bytes(hashlib.md5(text.encode("utf-8")).digest()[:4], "big")


class ConsistentHashRing:
    def __init__(self, vnodes_per_node: int = 150):
        self.vnodes_per_node = vnodes_per_node
        self.ring_tokens: List[int] = []
        self.token_to_node: Dict[int, str] = {}

    def add_node(self, node_id: str) -> None:
        for v in range(self.vnodes_per_node):
            token = hash32(f"{node_id}#vnode#{v}")
            if token not in self.token_to_node:
                bisect.insort(self.ring_tokens, token)
                self.token_to_node[token] = node_id

    def remove_node(self, node_id: str) -> None:
        tokens_to_remove = [t for t, n in self.token_to_node.items() if n == node_id]
        for t in tokens_to_remove:
            del self.token_to_node[t]
        self.ring_tokens = sorted(self.token_to_node.keys())

    def get_node(self, key: str) -> str:
        h = hash32(key)
        idx = bisect.bisect_left(self.ring_tokens, h)
        if idx == len(self.ring_tokens):
            idx = 0
        return self.token_to_node[self.ring_tokens[idx]]


if __name__ == "__main__":
    N_INITIAL = 10
    N_EXPANDED = 11
    NUM_KEYS = 100_000
    keys = [f"order:{i:07d}" for i in range(NUM_KEYS)]

    # 1. Naive Modulo Hashing: hash(k) % N
    mod_before = [f"node-{hash32(k) % N_INITIAL}" for k in keys]
    mod_after = [f"node-{hash32(k) % N_EXPANDED}" for k in keys]
    mod_moved = sum(1 for a, b in zip(mod_before, mod_after) if a != b)

    # 2. Consistent Hashing with 150 Virtual Nodes per physical machine
    ring = ConsistentHashRing(vnodes_per_node=150)
    for i in range(N_INITIAL):
        ring.add_node(f"node-{i}")

    ch_before = [ring.get_node(k) for k in keys]
    ring.add_node(f"node-{N_INITIAL}")  # Add 11th node (node-10)
    ch_after = [ring.get_node(k) for k in keys]
    ch_moved = sum(1 for a, b in zip(ch_before, ch_after) if a != b)

    # 3. Check load balance across the 11 nodes
    counts: Dict[str, int] = {f"node-{i}": 0 for i in range(N_EXPANDED)}
    for n in ch_after:
        counts[n] += 1
    ideal_per_node = NUM_KEYS / N_EXPANDED
    stdev_pct = (statistics.stdev(counts.values()) / ideal_per_node) * 100

    print(f"Scaling cluster from {N_INITIAL} -> {N_EXPANDED} nodes across {NUM_KEYS:,} keys:")
    print(f"  Naive Modulo (hash % N) keys moved : {mod_moved:,} ({mod_moved / NUM_KEYS * 100:.2f}% - catastrophic!)")
    print(f"  Consistent Hash (150 vnodes) moved : {ch_moved:,} ({ch_moved / NUM_KEYS * 100:.2f}%, theoretical ideal 1/11 = 9.09%)")
    print(f"  Ideal keys per node                : {ideal_per_node:,.0f}")
    print(f"  Actual min / max keys per node     : {min(counts.values()):,} / {max(counts.values()):,} (Relative StdDev: {stdev_pct:.2f}%)")

    assert mod_moved > 0.85 * NUM_KEYS
    assert abs(ch_moved / NUM_KEYS - (1.0 / N_EXPANDED)) < 0.015
```
